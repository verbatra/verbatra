Professionelle Übersetzerinnen und Sprachdienstleister arbeiten in CAT-Tools wie Trados, memoQ, OmegaT, Matecat und Phrase, und XLIFF ist das Dateiformat, das diese Tools austauschen. Eine Arbeitsmappe oder eine CSV-Datei kommt dort als Tabelle an; eine XLIFF-Datei kommt als Segmente mit Status, Notizen und geschützten Platzhaltern an, und genau darauf sind ihre Werkzeuge, ihr Übersetzungsspeicher und ihre QA-Prüfungen ausgelegt.

verbatra schreibt diese Datei aus jedem Projektformat, nicht nur aus einem XLIFF-Projekt: i18next-JSON, Android-`strings.xml`, gettext-`.po` und jedes andere Format, das verbatra liest, gehen als dasselbe XLIFF hinaus und kommen über denselben Import zurück.

## Der Roundtrip

```bash
# 1. Export one XLIFF 2.0 file per target locale into handoff/
verbatra export --format xliff2 --out handoff

# 2. The agency translates handoff/de.xlf, handoff/fr.xlf ... in its CAT tool and sends them back

# 3. Import every returned file, recording who signed off on the reviewed ones
verbatra import handoff --format xliff2 --reviewer "Agency GmbH"
```

Nimm `--format xliff12` für ein Tool, das XLIFF 2.0 noch nicht liest. Beide schreiben eine `<locale>.xlf` pro Ziel-Locale in das `--out`-Verzeichnis (Standard `verbatra-translations`), dazu dasselbe versteckte Manifest wie ein CSV-Export (hier `.verbatra-export-xliff.json`). Eine Datei, die von einem früheren, breiteren Export übrig ist, wird beim Import also mit `HANDOFF_FILE_STALE` abgelehnt statt angewendet.

Eine einzelne zurückgeschickte Datei lässt sich auch allein importieren. Ein Pfad, der auf `.xlf` oder `.xliff` endet, wird ohne `--format` als XLIFF gelesen, und die Version kommt aus der Datei selbst; `--format xliff2` und `--format xliff12` lesen also beide Versionen:

```bash
verbatra import handoff/de.xlf
```

Die Locale kommt aus dem Dateinamen. Hat ein Tool die Datei umbenannt (etwa in `project_de.xlf`), wird stattdessen die Zielsprache, die die Datei angibt, mit deinen konfigurierten Locales abgeglichen.

## Was in der Datei landet

Der Export wählt dieselben Keys wie ein Arbeitsmappen-Export: die fehlenden und veralteten, mit `--include-unchanged` auch die aktuellen. Jeder Key wird zu einer Unit:

- **Der Key benennt die Unit.** XLIFF 2.0 legt ihn in `name` der Unit ab (ihre `id` ist ein erzeugtes `u1`, `u2` ..., weil XLIFF-2.0-IDs nicht jeden Key fassen können); XLIFF 1.2 verwendet ihn als `id` und `resname` der `trans-unit`.
- **Platzhalter, Inline-Markup und ICU-Struktur werden zu Inline-Codes.** `{{name}}`, `%1$s`, `<b>`, `&amp;` und die Syntax eines ICU-`plural` oder `select` werden zu `<ph>`-Elementen, mit dem Originaltext in `disp` und `equiv` (XLIFF 2.0, gestützt auf `<originalData>`) oder als Inhalt des Elements (XLIFF 1.2). Ein CAT-Tool zeigt sie als Tags an, die die Übersetzerin platziert, aber nicht bearbeiten kann, während der lesbare Text jedes ICU-Zweigs übersetzbar bleibt. Der Import löst jeden Code wieder in seinen exakten Originaltext auf, Byte für Byte.
- **Kontext reist als Notizen mit.** Beschreibung und Bedeutung eines Keys werden, wo das Projektformat sie trägt, zu `<note>`-Elementen.
- **Der Quell-Hash reist als Metadaten mit.** XLIFF 2.0 speichert ihn im Standard-Metadatenmodul (`<mda:meta type="source-hash">` in einer `verbatra`-Metagruppe), XLIFF 1.2 im Attribut `extradata`. CAT-Tools behalten beides auf dem Rückweg; was passiert, wenn eines das nicht tut, steht weiter unten.
- **Ein veralteter Key bringt seine alte Übersetzung mit.** Ein Key, dessen Quelle sich seit der Übersetzung geändert hat, wird mit der bisherigen Übersetzung als Ziel exportiert, als Ausgangspunkt, aber weiterhin im Anfangsstatus.

### Segmentstatus

Der Status jedes Segments kommt aus der Lock-Datei und dem [Review-Status](/docs/review-in-studio):

| Der Key ist | XLIFF 2.0 `state` | XLIFF 1.2 `state` |
| --- | --- | --- |
| fehlend | `initial`, kein Ziel | kein Ziel |
| veraltet (Quelle geändert) | `initial`, alte Übersetzung als Ziel | `needs-translation`, alte Übersetzung als Ziel |
| aktuell, nicht geprüft | `translated` | `translated` |
| aktuell und freigegeben | `reviewed` | `signed-off` und `approved="yes"` |
| aktuell, aber abgelehnt | `initial` | `needs-translation` |

Die Herkunft eines aktuellen Werts ändert seinen Status nicht: eine maschinelle Übersetzung, ein Treffer aus dem Übersetzungsspeicher und ein von einer Person getippter Wert sind alle `translated`, bis jemand sie freigibt.

## Was der Import annimmt

Jede zurückgeschickte Unit durchläuft genau die Prüfungen, die ein [Arbeitsmappen-Import](/docs/manual-translation#was-der-import-akzeptiert) anwendet: das Integritäts-Gate für Platzhalter, Markup und ICU-Syntax, den Schutz vor veralteten Quellen, `[[CLEAR]]` zum absichtlichen Leeren einer Übersetzung und ein leeres Ziel mit der Bedeutung „noch nicht übersetzt“. Was XLIFF hinzufügt:

- **Ein unverändert exportiertes Ziel ändert nichts.** Eine Unit, deren Ziel genau dem aktuellen Wert des Projekts entspricht, wird nicht erneut geschrieben; ein aktueller Key bleibt also Byte für Byte gleich in deiner Locale-Datei und behält seine Provenienz. Ein veralteter Key, dessen alte Übersetzung unangetastet zurückkommt, bleibt veraltet, es sei denn, der Status der Unit ist über `initial` hinaus gewandert. So bestätigt eine Übersetzerin, dass die alte Übersetzung noch zur neuen Quelle passt.
- **Jedes andere Ziel ist eine Übersetzung, egal in welchem Status.** Manche Tools schreiben die Übersetzung, lassen aber den Status stehen; ein geändertes Ziel wird deshalb auch im Status `initial` importiert.
- **`reviewed` und `final` halten eine Freigabe fest.** Eine Unit im Status `reviewed` oder `final` (XLIFF 1.2: `signed-off`, `final` oder `approved="yes"`) wird in `verbatra.provenance.json` als freigegeben festgehalten, sowohl wenn ihr Wert importiert wurde als auch wenn die Übersetzerin nur den vorhandenen Wert bestätigt hat. Die Freigabe nennt `--reviewer`, wenn du es angibst, ist wie jede andere Freigabe an den aktuellen Quell-Hash gebunden und wird mit dem Hinweis `HANDOFF_REVIEWS_RECORDED` gemeldet. Ein importierter Wert behält die Herkunft `import`; ein bestätigter Wert behält die Herkunft, die er hatte, etwa `machine`.
- **Ein entfernter Quell-Hash fällt auf den Quelltext zurück.** Hat ein Tool die Metadaten verworfen, wird stattdessen der Quelltext der Unit mit der aktuellen Quelle verglichen: Eine identische Quelle wird importiert, eine geänderte als Drift zurückgehalten.
- **Schäden werden gemeldet, nicht fatal.** Eine Unit, deren ID keinen Quell-Key nennt oder deren Inline-Codes sich nicht auflösen lassen, wird als fehlerhafte Zeile gemeldet (mit Unit-Nummer und `id`, `source` oder `target`), und ein wiederholter Key wird als Duplikat gemeldet, wobei der erste gewinnt. Der Rest der Datei wird trotzdem importiert.
- **Das XML wird sicher geparst.** Ein Dokument, das eine XML-Entität oder ein internes DTD-Subset deklariert, wird vor dem Parsen abgelehnt, ebenso Dateien über 32 MB.

`verbatra import --dry-run` zeigt all das, einschließlich der Freigaben, die festgehalten würden, ohne eine Datei zu schreiben.

XLIFF 1.2 kann kein Zeichen tragen, das XML 1.0 verbietet (ein Steuerzeichen wie U+0007); ein solches Zeichen fällt beim 1.2-Export weg. XLIFF 2.0 trägt es als `<cp>`-Element und bringt es exakt zurück; nimm also `xliff2`, wann immer das Tool es liest.

## Ein Tool von Hand prüfen: OmegaT

Die automatischen Tests bearbeiten die exportierten Dateien so, wie es ein CAT-Tool tut, starten aber keins. Um einen Roundtrip durch ein echtes Tool zu prüfen, ist [OmegaT](https://omegat.org) kostenlos und liest XLIFF:

1. Exportiere eine Übergabe: `verbatra export --format xliff12 --out handoff` (oder `xliff2`).
2. Lege in OmegaT ein Projekt mit deiner Quell- und Zielsprache an und kopiere `handoff/de.xlf` in den Ordner `source` des Projekts.
3. Öffne das Projekt. Platzhalter wie `{{name}}` erscheinen als Tags: Übersetze den Text drumherum und füge jedes Tag mit Strg+T (Cmd+T unter macOS) ein, statt es zu tippen.
4. Übersetze einige Segmente, lass einige unübersetzt und speichere.
5. Erzeuge die übersetzten Dokumente (Projekt, Übersetzte Dokumente erstellen). OmegaT schreibt `de.xlf` in den Ordner `target` des Projekts.
6. Prüfe zuerst: `verbatra import pfad/zu/target/de.xlf --dry-run`. Die übersetzten Segmente stehen unter `translated`, die unberührten unter `unfilled`, und nichts wird abgelehnt, solange kein Tag verloren ging.
7. Importiere: `verbatra import pfad/zu/target/de.xlf`, danach `verbatra check`.

## Aus dem SDK

Die CLI umhüllt dieselben zwei Funktionen wie die Arbeitsmappen-Übergabe:

```ts
import { exportWorkbook, importWorkbook, loadConfig } from "@verbatra/sdk";

const config = await loadConfig();

await exportWorkbook({ config, format: "xliff2", out: "handoff" });

const summary = await importWorkbook({
  config,
  workbook: "handoff",
  format: "xliff2",
  reviewer: "Agency GmbH",
});
```
