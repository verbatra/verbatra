<AvailableFrom version="0.12.0" />

If you publish text that a provider or an AI agent translated, you may be asked to show which text
that is and whether a person looked at it before it shipped. verbatra already records that per key
in `verbatra.provenance.json`. This page shows the two ways to get it out: a report you can archive
as an audit file, and markers in the XLIFF and TMX files you hand to other tools.

<Callout type="warn" title="Supporting evidence, not legal advice">
Article 50 of the EU AI Act sets transparency obligations for AI-generated text, and text a person
reviewed under editorial responsibility is treated differently from text that was not. How those
rules apply to translation, and to your product, is not settled in a way verbatra can decide for
you. The report and the markers are supporting evidence you can hand to whoever makes that call.
They are not legal advice, and using them does not make a product compliant with anything.
</Callout>

## What the record can and cannot tell you

Every value verbatra writes is recorded with the write path that produced it. The full list of
origins is on [the lock file page](/docs/the-lock-file#provenance-who-wrote-each-value); in short:

- `machine`, `memory`, `fuzzy` and `agent` are the machine class: a provider, the translation
  memory, a fuzzy memory match, or an AI agent wrote the value. The memory counts as machine because
  it does not record who wrote an entry, so a memory hit can be earlier machine output.
- `human` and `import` are people: an edit through Studio or the SDK, or a value imported from a
  translator's handoff.
- `external` means the value changed outside verbatra since its record was written, `unrecorded`
  means it has no record (for example a value from before the provenance file existed), and
  `unknown` means it was recorded without a known author.

A review decision (approved or rejected) and the reviewer's name, when one was given, sit next to
the origin. An approval given before the source text changed reads as unreviewed.

Keep the limits in mind when you hand the record to someone:

- **It is not tamper-evident.** Anyone who can edit your locale files can edit the provenance file.
  Its value comes from being committed next to the code, where your git history and code review
  already apply.
- **It has no timestamps.** The record deliberately stores none, so the report carries none per
  key. When a value was written or approved is in the git history of `verbatra.provenance.json`
  (`git log -p verbatra.provenance.json`).
- **It errs toward machine.** Memory hits, fuzzy matches and agent edits all count as machine, and
  a machine value a person has not approved counts as unreviewed, even when its text is fine.

## The provenance report

`verbatra report provenance` reads the committed files and prints, per target locale, how many
values fall into each bucket. It calls no provider, needs no API key, and writes nothing.

```bash
verbatra report provenance
```

```text
verbatra report provenance (source en, verbatra 0.12.0, 2026-09-29T08:00:00.000Z)
  locale  machine, unreviewed  machine, reviewed  human  import  external  unrecorded  unknown  total
  de      12                   40                 3      85      1         0           0        141
  fr      52                   0                  3      85      1         0           0        141
Supporting evidence from verbatra.provenance.json, not legal advice. --json lists every key.
```

| Bucket | The value was written by | Reviewed? |
| --- | --- | --- |
| `machine-unreviewed` | `machine`, `memory`, `fuzzy` or `agent` | not approved, including a rejected value that is back in the file |
| `machine-reviewed` | `machine`, `memory`, `fuzzy` or `agent` | approved by a person |
| `human` | a person, through verbatra | either |
| `import` | a translator's handoff | either |
| `external` | something outside verbatra, since its record was written | not known |
| `unrecorded` | nobody verbatra knows of: there is no record | not known |
| `unknown` | recorded without a known author | either |

Only keys that have a value in both the source and the target locale are listed. A key missing from
a locale has no text to account for, and a key no longer in the source is not shipped as a
translation of it.

### An audit file from CI

With `--json` the report lists every key, which makes it an audit file you can archive with each
release:

```bash
verbatra report provenance --json > provenance-report.json
```

The command exits `0` with a report, `1` when `verbatra.provenance.json` is corrupt or was written by
a newer verbatra, and `2` when it could not run at all (see [`verbatra report`](/docs/cli/report)).
Exit `1` is deliberate: a report built without the record would list every value as `unrecorded`,
which reads as "we have no idea" rather than as the error it is, so the job fails instead of
archiving it. That is the same fail-closed rule [`check --require-reviewed`](/docs/cli/check) follows.

If you need every machine translation reviewed before a release, gate on
`verbatra check --require-reviewed` and archive the report next to it.

### The JSON schema

The report is the `result` of the usual [JSON envelope](/docs/cli/output#json-output), with
`command` set to `"report"`. SDK callers get the same object from `provenanceReport`.

```json
{
  "ok": true,
  "version": 1,
  "command": "report",
  "result": {
    "available": true,
    "generatedAt": "2026-09-29T08:00:00.000Z",
    "toolVersion": "0.12.0",
    "sourceLocale": "en",
    "locales": [
      {
        "locale": "de",
        "total": 2,
        "counts": {
          "machine-unreviewed": 1,
          "machine-reviewed": 1,
          "human": 0,
          "import": 0,
          "external": 0,
          "unrecorded": 0,
          "unknown": 0
        },
        "entries": [
          {
            "key": "cart.checkout",
            "bucket": "machine-unreviewed",
            "origin": "machine",
            "reviewState": "unreviewed",
            "provider": "anthropic",
            "model": "claude-sonnet-4-5"
          },
          {
            "key": "home.title",
            "bucket": "machine-reviewed",
            "origin": "machine",
            "reviewState": "approved",
            "provider": "deepl",
            "reviewer": "Ana"
          }
        ]
      }
    ]
  }
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `available` | `true` | the report was built from the committed files |
| `generatedAt` | string | when the report was generated, ISO 8601 in UTC |
| `toolVersion` | string | the verbatra version that generated it, or `unknown` when an SDK caller passes none |
| `sourceLocale` | string | the configured source locale |
| `locales[]` | array | one entry per target locale, in configured order, narrowed by `--locales` |
| `locales[].locale` | string | the target locale |
| `locales[].total` | number | how many keys are listed for the locale |
| `locales[].counts` | object | how many keys fall into each bucket; all seven buckets are always present |
| `locales[].entries[]` | array | one entry per key with a value in the source and the locale, in source order |
| `entries[].key` | string | the translation key |
| `entries[].bucket` | string | one of the seven buckets above |
| `entries[].origin` | string | `machine`, `memory`, `fuzzy`, `agent`, `human`, `import`, `unknown`, `unrecorded` or `external` |
| `entries[].reviewState` | string | `unreviewed`, `approved` or `rejected` |
| `entries[].provider` | string, optional | the provider `id` that answered, for a `machine` value |
| `entries[].model` | string, optional | the configured model, when the record names one |
| `entries[].reviewer` | string, optional | the reviewer named with the decision, when one was given |

When the provenance file cannot be read, the result is `{ "available": false, "reason": "provenance-unreadable" }`
and the command exits `1`. There is no per-key date field, because the record holds no timestamps.
New optional fields may be added in later versions; existing ones keep their meaning.

## Markers in exports

The same origin travels into the files you hand to other tools, so a CAT tool, a translation
memory or a reviewer on the other side can tell machine output from human work.

### XLIFF

`verbatra export --format xliff12` or `--format xliff2` marks every unit that has a target:

| The target is | XLIFF 1.2 | XLIFF 2.0 |
| --- | --- | --- |
| machine class, not approved | `state-qualifier="mt-suggestion"` on `<target>` | `<mda:meta type="origin">` and `<mda:meta type="review-state">` |
| machine class, approved | no qualifier (a person reviewed it) | the same two meta entries |
| human, import, external, unrecorded or unknown | no qualifier | the same two meta entries |

In XLIFF 1.2, `mt-suggestion` is the spec's own value for "the translation is suggested by machine
translation", and every CAT tool that reads 1.2 knows it. The qualifier sits next to the unit's
usual `state`, so an unreviewed machine translation that is up to date reads
`state="translated" state-qualifier="mt-suggestion"`, and a stale one keeps its
`state="needs-translation"`. An approved machine translation is `signed-off` with no qualifier:
a person reviewed it, so calling it a machine suggestion would understate that review. Values from
people, and values whose origin verbatra cannot vouch for, get no qualifier either, because a
qualifier is a claim that a machine wrote the text.

XLIFF 2.0 has no state qualifier, so the unit's `verbatra` metadata group, which already carries the
source hash, gets two more entries with the full origin and review state from the report:

```xml
<mda:metaGroup category="verbatra">
  <mda:meta type="source-hash">8f3a0c1e2b4d6f70</mda:meta>
  <mda:meta type="origin">machine</mda:meta>
  <mda:meta type="review-state">unreviewed</mda:meta>
</mda:metaGroup>
```

The metadata module is part of XLIFF 2.0 itself, and tools that support it keep it on the way
back. The ITS 2.0 Provenance and MT Confidence data categories were the alternative; the ITS module
only exists from XLIFF 2.1, MT Confidence needs a score verbatra does not have, and few CAT tools
act on either, so verbatra uses the module that fits the file it writes.

### TMX

`verbatra tmx export` writes a property on every target segment:

```xml
<tuv xml:lang="de"><prop type="x-origin">machine</prop><prop type="x-review">unreviewed</prop><seg>Zur Kasse</seg></tuv>
```

`x-origin` is `machine`, `human`, `import` or `unknown`. `x-review` accompanies `machine` only and
is `approved`, `unreviewed` or `rejected`. TMX gets this coarser vocabulary on purpose. A memory
entry is a pair of texts, not a key, and one text can belong to several keys that were written in
different ways, so the export looks at every key whose source matches and whose record describes
exactly this text: if any of them is machine class, the segment is `machine`, and it counts as
`approved` only when every machine-class one is. A text no record describes is `unknown`. The
per-key detail, including `memory`, `fuzzy` and `agent`, stays in the report.

### Importing marked files

Import ignores every marker. An XLIFF unit is judged by its target and its `state` exactly as
before, and a TMX segment by its text. Origin is never read back from a file: a value imported from a
handoff is recorded as `import`, and a TMX import only fills the translation memory, which records
no origin. A marker a tool rewrote, dropped or invented therefore cannot change what your record
says.

### When the record cannot be read

If `verbatra.provenance.json` is corrupt or from a newer verbatra (or, for TMX, the lock file cannot
be read), the export still succeeds but writes no marker at all, rather than a marker it cannot back
up. The command says so on its summary, and the `--json` result carries
`provenanceMarkers: "unavailable"` instead of `"written"`.
