Usa la acción cuando un job de GitHub Actions deba ejecutar verbatra y mostrarte qué pasó. Ejecuta `translate`, `check` o `diff` con `--json`; para cualquier otro comando o flag, como `--prune`, ejecuta [la CLI directamente](/docs/ci-and-exit-codes).

Antes de empezar, necesitas:

- Una configuración de verbatra directamente dentro del directorio en el que se ejecuta la acción (consulta [Descubrimiento de la configuración](#descubrimiento-de-la-configuración)).
- Una versión exacta de `@verbatra/cli` que fijar, `0.9.3` o posterior.
- Solo para `translate`: la clave de API de tu proveedor como secreto del repositorio.

## Añade la acción a un workflow

La acción vive en [verbatra/action](https://github.com/verbatra/action) y en el [GitHub Marketplace](https://github.com/marketplace/actions/verbatra); no hay paquete npm. Fíjala a un SHA de commit, como abajo, o usa la etiqueta móvil `verbatra/action@v1`. La antigua forma por ruta dentro del monorepo de verbatra ya no se resuelve.

```yaml title=".github/workflows/translate.yml"
name: translate
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  verbatra:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-sha>
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0 # an exact @verbatra/cli release, 0.9.3 or newer
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
```

La acción instala `@verbatra/cli` y `@verbatra/sdk` exactamente en esa versión en un directorio temporal, así que el job no necesita un paso de instalación propio. Sube la versión fijada de forma deliberada; [npm](https://www.npmjs.com/package/@verbatra/cli) muestra la versión actual.

### Pasa la clave del proveedor

Pasa la clave desde los secretos del repositorio con la variable que lee tu proveedor; [Proveedores](/docs/providers#las-claves-vienen-del-entorno) las enumera. La acción no tiene una entrada para la clave, así que una clave nunca viaja como entrada ni como argumento de la CLI.

## Protege un pull request

Pon `command: check` para que falle un pull request cuyos archivos de locale se hayan desviado, o `command: diff` para listar además las claves pendientes. Ambos son de solo lectura y no llaman a ningún proveedor, así que no necesitan clave y se ejecutan en pull requests desde forks:

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
```

## Comprobar la calidad de la traducción

<AvailableFrom version="0.12.0" />

Añade `qa: "true"` a `command: check` para ejecutar [`verbatra check --qa`](/docs/cli/check#control-de-calidad) sobre cada traducción confirmada, incluidos los valores escritos a mano. Sigue siendo de solo lectura y sin clave.

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
          qa: "true"
```

- Cada hallazgo se convierte en una anotación titulada `verbatra qa: <locale>`: un error para un valor que la puerta de integridad rechazaría, un aviso para un motivo de revisión.
- El paso falla con cualquier hallazgo de error. Añade `qa-strict: "true"` para fallar también con avisos y plurales incompletos, o `qa-severity: error` para informar solo de errores.
- Una `version` menor que `0.12.0`, o una prerelease como `0.12.0-next.0`, hace fallar el paso antes de instalar nada. Lo mismo vale para `require-reviewed`.

## Exigir traducciones revisadas

<AvailableFrom version="0.12.0" />

Añade `require-reviewed: "true"` a `command: check` para ejecutar [`verbatra check --require-reviewed`](/docs/cli/check#exigir-traducciones-revisadas). El paso falla mientras una traducción escrita por máquina no esté aprobada en el `verbatra.provenance.json` confirmado, donde [Studio](/docs/review-in-studio) guarda las decisiones de revisión. Sigue siendo de solo lectura y sin clave, y se combina con `qa`.

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
          require-reviewed: "true"
```

- Cada locale con claves sin aprobar recibe una anotación de error [`REVIEW_REQUIRED`](/docs/error-codes#review_required) que las nombra, y el resumen del job añade una columna `unreviewed`.
- Un `verbatra.provenance.json` dañado o escrito por un verbatra más reciente hace fallar la puerta con una sola anotación `REVIEW_STATE_UNREADABLE`.

## Modo solo humano

<AvailableFrom version="0.12.0" />

Con `provider: { id: "none" }` (consulta [Flujo solo humano](/docs/human-only-workflow)), `translate` sale con `3` cuando deja claves para una persona. La acción lo trata como trabajo que entregar, no como un fallo: el paso pasa, cada locale afectado recibe un aviso `NEEDS_HUMAN`, el resumen del job lista las claves y la salida `needs-human` vale `"true"`. Ramifica sobre ella:

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        id: verbatra
        with:
          version: 0.12.0
      - if: steps.verbatra.outputs.needs-human == 'true'
        run: echo "Some keys need a human translation; see the job summary."
```

Solo `translate` recibe este trato. Un `3` de `check` o `diff` sigue haciendo fallar el paso.

## Descubrimiento de la configuración

Con `config-path` vacío, la acción exige un archivo de configuración reconocido directamente dentro de `working-directory` (por defecto, la raíz del repositorio). Nunca busca en un directorio padre, así que en un monorepo apunta `working-directory` a la app y deja su configuración ahí:

```yaml
      with:
        version: 0.12.0
        working-directory: apps/docs
```

Si no encuentra configuración, el paso falla antes de instalar la CLI y nombra el directorio que comprobó. Para cargar una configuración de otro sitio, define `config-path`: una ruta relativa se resuelve contra `working-directory`.

## Conserva las traducciones

`translate` escribe los archivos de locale actualizados en el checkout del runner y se detiene ahí: la acción nunca hace commit. Añade tu propio paso que haga commit y push, o que abra un pull request, y concede `contents: write` o `pull-requests: write` solo a ese job. Para informar sin escribir, pon `dry-run: "true"` o usa `command: check`.

## Entradas

| Entrada | Por defecto | Efecto |
| --- | --- | --- |
| `version` | obligatoria | versión exacta de `@verbatra/cli`, `0.9.3` o posterior; una dist-tag, un rango o un prefijo `^`/`~` hace fallar el paso |
| `command` | `translate` | `translate`, `check` o `diff`; cualquier otro valor hace fallar el paso |
| `config-path` | `""` | archivo de configuración que cargar (`--config`); relativo a `working-directory` |
| `working-directory` | `""` | directorio en el que se ejecuta la CLI (`--cwd`); vacío, es la raíz del repositorio |
| `dry-run` | `"false"` | `"true"` previsualiza sin llamar a un proveedor ni escribir (`--dry-run`); solo `translate` |
| `qa` | `"false"` | `"true"` añade el control de calidad (`--qa`); solo `check` |
| `qa-severity` | `""` | severidad mínima que informar, `error` o `warning` (`--severity`); requiere `qa` |
| `qa-strict` | `"false"` | `"true"` falla también con avisos (`--strict`); requiere `qa` |
| `require-reviewed` | `"false"` | `"true"` falla también con traducciones de máquina sin aprobar (`--require-reviewed`); solo `check` |
| `node-version` | `"24"` | versión de Node.js que la acción prepara para ejecutar la CLI |

Las entradas booleanas solo aceptan `"true"` o `"false"`. Un valor o una combinación no válidos hacen fallar el paso con salida `1` antes de instalar nada.

## Salidas

| Salida | Valor |
| --- | --- |
| `needs-human` | `"true"` cuando `translate` salió con `3` y dejó claves para una persona; si no, `"false"` |

## Qué te muestra una ejecución

- **Anotaciones.** Con `translate`, cada locale fallido o parcial se convierte en una anotación de error titulada `verbatra: <locale>`. Con `check` o `diff`, cada locale desviado recibe una titulada `verbatra check: <locale>` o `verbatra diff: <locale>`. La anotación `LOCALE_PARTIAL` de un locale parcial nombra las claves retenidas, agrupadas por causa. Cada `check` añade un aviso `PLURAL_CATEGORIES_INCOMPLETE` por locale cuyos plurales carecen de una categoría CLDR que usa el idioma. Una ejecución que falla por completo recibe una sola anotación `verbatra` con el código de error, su causa como `(cause: X)` y una pista `Next step:` cuando la CLI las da. GitHub muestra como mucho 10 anotaciones por severidad, así que la acción las ordena por desviación, revisión, errores de calidad y avisos, y añade un aviso que cuenta el resto.
- **Resumen del job.** Una fila por locale con los recuentos del comando ejecutado, una línea agregada y los locales parciales y fallidos. Con `qa` añade una tabla de hallazgos de hasta 1000 hallazgos; los plurales incompletos tienen su propia sección.
- **Estado de salida.** La acción emite primero las anotaciones y el resumen y luego sale con el [código de salida](/docs/cli/output#códigos-de-salida) de la propia CLI, así que el paso falla solo después de mostrar por qué.

## Seguridad

Fija las dos referencias: `uses:` a un SHA de commit y `version` a una versión exacta; la acción rechaza todo lo que pudiera resolverse a `latest`. Las entradas llegan a la CLI como un array de argumentos entre comillas, nunca insertadas en texto de shell, así que un valor de entrada manipulado sigue siendo un argumento.
