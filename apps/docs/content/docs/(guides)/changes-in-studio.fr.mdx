Utilise ceci avant de committer une exécution : tu vois quels fichiers de locale une exécution de traduction ou une modification a touchés, et quelles clés ont changé dans chacun, sans quitter Studio. Studio ne fait que lire ; il ne fait jamais de stage, de commit ni de restauration.

## Ouvre la section Changes

Démarre Studio ([Réviser dans Studio](/fr/docs/review-in-studio#démarrer-studio)) et descends sur la page Overview jusqu'à **Changes**, sous le tableau des locales. Elle indique la branche active (ou **Detached HEAD**) et liste chaque fichier qui diffère du dernier commit :

| État | Signification |
| --- | --- |
| **Modified** | le fichier diffère du dernier commit |
| **Added** | le fichier est nouveau et indexé |
| **Deleted** | le fichier a disparu de l'arbre de travail ou de l'index |
| **Untracked** | git ne suit pas encore le fichier |
| **Conflicted** | le fichier a des conflits de fusion non résolus |

Tes fichiers de locale source et cible sont listés, ainsi que `verbatra.lock.json` et `verbatra.provenance.json`, qui affichent un état et aucun changement de clés. Un projet propre indique qu'aucun fichier de locale ne diffère.

## Lis les changements de clés

**Key changes (de)** ouvre le fichier de cette locale sous forme de clés, comparé au dernier commit : les clés **Changed** avec l'ancien et le nouveau texte côte à côte, les clés **Added** et les clés **Removed**. Une clé modifiée ou ajoutée renvoie vers son entrée dans Translations. Appuie de nouveau sur le bouton pour fermer.

- **Un fichier, plusieurs locales :** un catalogue comme `apple-xcstrings` garde toutes les locales dans un fichier, donc il a un bouton par locale. Chacun compare cette locale seulement.
- **Longues listes :** une liste contient au plus 500 clés et chaque texte est coupé à 2000 caractères. Quand cela arrive, Studio dit que la liste est incomplète ; la différence complète se trouve dans git. Une longue liste montre 50 clés à la fois.
- **Conflits :** un fichier avec des conflits de fusion non résolus affiche son état et aucun changement de clés. Résous d'abord les conflits dans git.
- **Texte sûr :** les clés et les valeurs s'affichent en texte brut, dans la langue et le sens de la locale, jamais comme du balisage.

## Quand il n'y a rien à montrer

Studio explique au lieu de lever une erreur quand il ne peut pas comparer, par exemple quand :

- le projet n'est pas dans un dépôt git, ou git n'est pas installé ou trop ancien pour un clone partiel ;
- git refuse le dossier parce qu'un autre utilisateur en est propriétaire, ou que le dossier est dans un dépôt bare ;
- le dépôt configure un filtre de contenu que Studio n'exécute pas ;
- une lecture a pris trop de temps ou a renvoyé trop de sortie.

Un projet au format `custom:` montre ses fichiers modifiés mais jamais leurs changements de clés : Studio compare le fichier commité aux seuls adaptateurs de format intégrés, qui ne peuvent pas exécuter un adaptateur personnalisé. Voir [Écrire un adaptateur de format personnalisé](/fr/docs/custom-format-adapters).

## Sache à quel point c'est à jour

La section relit quand un fichier de locale, de verrouillage ou de provenance change sur le disque. Un `git commit` ou un `git add` seul ne change aucun de ces fichiers, donc il apparaît après le prochain changement de fichier ou un rechargement de la page. Si une lecture échoue, Studio garde la dernière réponse et le dit.

Ton propre code dispose des mêmes lectures sous le nom [`localeGitStatus` et `localeGitDiff`](/fr/docs/sdk/review#localegitstatus), qui énumèrent chaque raison pour laquelle une comparaison peut être indisponible et les garde-fous git appliqués.
