Nutze die Action, wenn ein GitHub-Actions-Job verbatra ausführen und dir zeigen soll, was passiert ist. Sie führt `translate`, `check` oder `diff` mit `--json` aus; für jeden anderen Befehl oder jedes andere Flag, etwa `--prune`, führst du [die CLI direkt](/docs/ci-and-exit-codes) aus.

Bevor du anfängst, brauchst du:

- Eine verbatra-Konfiguration direkt in dem Verzeichnis, in dem die Action läuft (siehe [Konfigurationssuche](#konfigurationssuche)).
- Eine exakte `@verbatra/cli`-Version zum Pinnen, `0.9.3` oder neuer.
- Nur für `translate`: den API-Schlüssel deines Providers als Repository-Secret.

## Die Action in einen Workflow einbauen

Die Action liegt in [verbatra/action](https://github.com/verbatra/action) und im [GitHub Marketplace](https://github.com/marketplace/actions/verbatra); ein npm-Paket gibt es nicht. Pinne sie wie unten auf einen Commit-SHA oder nutze den mitwandernden Tag `verbatra/action@v1`. Die alte Pfad-Form aus dem verbatra-Monorepo wird nicht mehr aufgelöst.

```yaml title=".github/workflows/translate.yml"
name: translate
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  verbatra:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-sha>
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0 # an exact @verbatra/cli release, 0.9.3 or newer
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
```

Die Action installiert `@verbatra/cli` und `@verbatra/sdk` in genau dieser Version in ein temporäres Verzeichnis, daher braucht der Job keinen eigenen Installationsschritt. Hebe den Pin bewusst an; [npm](https://www.npmjs.com/package/@verbatra/cli) zeigt das aktuelle Release.

### Den Provider-Schlüssel übergeben

Reiche den Schlüssel aus deinen Repository-Secrets unter der Variable weiter, die dein Provider liest; [Provider](/docs/providers#keys-kommen-aus-der-umgebung) listet sie auf. Die Action hat keine Schlüssel-Eingabe, ein Schlüssel reist also nie als Eingabe oder CLI-Argument.

## Einen Pull Request absichern

Setze `command: check`, damit ein Pull Request mit abweichenden Locale-Dateien fehlschlägt, oder `command: diff`, um zusätzlich die offenen Keys aufzulisten. Beide sind nur lesend und rufen keinen Provider auf, brauchen also keinen Schlüssel und laufen auch bei Pull Requests aus Forks:

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
```

## Übersetzungsqualität prüfen

<AvailableFrom version="0.12.0" />

Ergänze `command: check` um `qa: "true"`, um [`verbatra check --qa`](/docs/cli/check#qualitätsprüfung) über jede eingecheckte Übersetzung laufen zu lassen, auch über von Hand getippte Werte. Es bleibt nur lesend und ohne Schlüssel.

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
          qa: "true"
```

- Jeder Befund wird zu einer Annotation mit dem Titel `verbatra qa: <locale>`: ein Fehler für einen Wert, den das Integritäts-Gate ablehnen würde, eine Warnung für einen Review-Grund.
- Der Schritt schlägt bei jedem Fehler-Befund fehl. Mit `qa-strict: "true"` schlägt er auch bei Warnungen und unvollständigen Pluralen fehl, mit `qa-severity: error` meldet er nur Fehler.
- Eine `version` unter `0.12.0` oder ein Prerelease wie `0.12.0-next.0` lässt den Schritt fehlschlagen, bevor irgendetwas installiert wird. Dasselbe gilt für `require-reviewed`.

## Freigegebene Übersetzungen verlangen

<AvailableFrom version="0.12.0" />

Ergänze `command: check` um `require-reviewed: "true"`, um [`verbatra check --require-reviewed`](/docs/cli/check#freigegebene-übersetzungen-verlangen) auszuführen. Der Schritt schlägt fehl, solange eine maschinell geschriebene Übersetzung in der committeten `verbatra.provenance.json` nicht freigegeben ist; dort speichert [Studio](/docs/review-in-studio) die Review-Entscheidungen. Es bleibt nur lesend und ohne Schlüssel und lässt sich mit `qa` kombinieren.

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
          require-reviewed: "true"
```

- Jede Locale mit nicht freigegebenen Keys bekommt eine [`REVIEW_REQUIRED`](/docs/error-codes#review_required)-Fehler-Annotation, die sie nennt, und die Job-Zusammenfassung ergänzt eine Spalte `unreviewed`.
- Ist `verbatra.provenance.json` beschädigt oder stammt sie von einem neueren verbatra, schlägt das Gate mit einer einzigen `REVIEW_STATE_UNREADABLE`-Annotation fehl.

## Rein menschlicher Modus

<AvailableFrom version="0.12.0" />

Mit `provider: { id: "none" }` (siehe [Rein menschlicher Workflow](/docs/human-only-workflow)) endet `translate` mit `3`, wenn es Keys für eine Person übrig lässt. Die Action behandelt das als Arbeit zur Übergabe, nicht als Fehlschlag: Der Schritt besteht, jede betroffene Locale bekommt eine `NEEDS_HUMAN`-Warnung, die Job-Zusammenfassung listet die Keys, und der Output `needs-human` ist `"true"`. Verzweige darauf:

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        id: verbatra
        with:
          version: 0.12.0
      - if: steps.verbatra.outputs.needs-human == 'true'
        run: echo "Some keys need a human translation; see the job summary."
```

Nur `translate` wird so behandelt. Ein Exit `3` von `check` oder `diff` lässt den Schritt weiterhin fehlschlagen.

## Konfigurationssuche

Ist `config-path` leer, verlangt die Action eine erkannte Konfigurationsdatei direkt in `working-directory` (standardmäßig das Repository-Root). Sie sucht nie in einem übergeordneten Verzeichnis, also richte `working-directory` in einem Monorepo auf die App und lege ihre Konfiguration dort ab:

```yaml
      with:
        version: 0.12.0
        working-directory: apps/docs
```

Wird keine Konfiguration gefunden, schlägt der Schritt vor der Installation der CLI fehl und nennt das geprüfte Verzeichnis. Um eine Konfiguration von woanders zu laden, setze `config-path`: Ein relativer Pfad wird gegen `working-directory` aufgelöst.

## Übersetzungen behalten

`translate` schreibt die aktualisierten Locale-Dateien in den Checkout des Runners und hört dort auf: Die Action committet nie. Füge einen eigenen Schritt hinzu, der committet und pusht oder einen Pull Request öffnet, und gib nur diesem Job `contents: write` oder `pull-requests: write`. Um nur zu berichten, ohne zu schreiben, setze `dry-run: "true"` oder nutze `command: check`.

## Eingaben

| Eingabe | Standard | Wirkung |
| --- | --- | --- |
| `version` | Pflicht | exaktes `@verbatra/cli`-Release, `0.9.3` oder neuer; ein Dist-Tag, ein Bereich oder ein `^`/`~`-Präfix lässt den Schritt fehlschlagen |
| `command` | `translate` | `translate`, `check` oder `diff`; alles andere lässt den Schritt fehlschlagen |
| `config-path` | `""` | zu ladende Konfigurationsdatei (`--config`); relativ zu `working-directory` |
| `working-directory` | `""` | Verzeichnis, in dem die CLI läuft (`--cwd`); leer ist es das Repository-Root |
| `dry-run` | `"false"` | `"true"` zeigt eine Vorschau ohne Provider-Aufruf und ohne Schreiben (`--dry-run`); nur `translate` |
| `qa` | `"false"` | `"true"` ergänzt die Qualitätsprüfung (`--qa`); nur `check` |
| `qa-severity` | `""` | niedrigste gemeldete Schwere, `error` oder `warning` (`--severity`); verlangt `qa` |
| `qa-strict` | `"false"` | `"true"` lässt auch Warnungen fehlschlagen (`--strict`); verlangt `qa` |
| `require-reviewed` | `"false"` | `"true"` lässt auch nicht freigegebene maschinelle Übersetzungen fehlschlagen (`--require-reviewed`); nur `check` |
| `node-version` | `"24"` | Node.js-Version, die die Action zum Ausführen der CLI einrichtet |

Die booleschen Eingaben akzeptieren nur `"true"` oder `"false"`. Ein ungültiger Wert oder eine ungültige Kombination lässt den Schritt mit Exit `1` fehlschlagen, bevor etwas installiert wird.

## Outputs

| Output | Wert |
| --- | --- |
| `needs-human` | `"true"`, wenn `translate` mit `3` geendet und Keys für eine Person übrig gelassen hat, sonst `"false"` |

## Was ein Lauf dir zeigt

- **Annotationen.** Unter `translate` wird jede fehlgeschlagene oder teilweise Locale zu einer Fehler-Annotation mit dem Titel `verbatra: <locale>`. Unter `check` oder `diff` bekommt jede abweichende Locale eine mit dem Titel `verbatra check: <locale>` oder `verbatra diff: <locale>`. Die `LOCALE_PARTIAL`-Annotation einer teilweisen Locale nennt die zurückgehaltenen Keys, nach Ursache gruppiert. Jeder `check` ergänzt pro Locale eine `PLURAL_CATEGORIES_INCOMPLETE`-Warnung, wenn ihren Pluralen eine CLDR-Kategorie fehlt, die die Sprache nutzt. Ein Lauf, der als Ganzes fehlschlägt, bekommt eine einzige `verbatra`-Annotation mit dem Fehlercode, der Ursache als `(cause: X)` und einem `Next step:`-Hinweis, sofern die CLI sie liefert. GitHub zeigt höchstens 10 Annotationen pro Schweregrad, daher sortiert die Action sie nach Drift, Review, Qualitätsfehlern und Warnungen und ergänzt einen Hinweis, der den Rest zählt.
- **Job-Zusammenfassung.** Eine Zeile pro Locale mit den Zahlen des ausgeführten Befehls, eine Gesamtzeile und die teilweisen und fehlgeschlagenen Locales. Mit `qa` kommt eine Befundtabelle mit bis zu 1000 Befunden hinzu; unvollständige Plurale bekommen einen eigenen Abschnitt.
- **Exit-Status.** Die Action gibt zuerst die Annotationen und die Zusammenfassung aus und endet dann mit dem [Exit-Code](/docs/cli/output#exit-codes) der CLI, sodass der Schritt erst fehlschlägt, nachdem er gezeigt hat, warum.

## Sicherheit

Pinne beide Referenzen: `uses:` auf einen Commit-SHA und `version` auf ein exaktes Release; die Action lehnt alles ab, was sich zu `latest` auflösen könnte. Eingaben erreichen die CLI als Argument-Array in Anführungszeichen und werden nie in Shell-Text eingefügt, ein präparierter Eingabewert bleibt also ein Argument.
