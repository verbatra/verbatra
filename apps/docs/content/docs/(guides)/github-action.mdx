Use the action when a GitHub Actions job should run verbatra and show you what happened. It runs the CLI with `--json`, turns failures into annotations, writes a job summary and exits with the CLI's exit code. It runs `translate`, `check` or `diff`; for any other command or flag, such as `--prune`, run the [CLI directly](/docs/ci-and-exit-codes).

Before you start, you need:

- A verbatra config directly inside the directory the action runs in (see [Config discovery](#config-discovery)).
- An exact `@verbatra/cli` version to pin, `0.9.3` or newer.
- For `translate` only: your provider's API key as a repository secret.

## Add the action to a workflow

The action lives in [verbatra/action](https://github.com/verbatra/action) and on the [GitHub Marketplace](https://github.com/marketplace/actions/verbatra). There is no npm package; you reference it with `uses:`. Pin it to a commit SHA, as below, or use the moving `verbatra/action@v1` tag. The old path form from the verbatra monorepo no longer resolves.

```yaml title=".github/workflows/translate.yml"
name: translate
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  verbatra:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-sha>
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.11.1 # an exact @verbatra/cli release, 0.9.3 or newer
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
```

The action installs `@verbatra/cli` and `@verbatra/sdk` at exactly that version into a scratch directory, so the job needs no install step of its own. Check [`@verbatra/cli` on npm](https://www.npmjs.com/package/@verbatra/cli) for the current release and bump the pin deliberately.

### Pass the provider key

Map the key from your repository secrets under the variable your provider reads; [Providers](/docs/providers#keys-come-from-the-environment) lists them. The action has no key input, so a key never travels as an input or a CLI argument.

## Gate a pull request

Set `command: check` to fail a pull request whose locale files drifted, or `command: diff` to list the pending keys as well. Both are read-only and call no provider, so they need no key and run on pull requests from forks:

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.11.1
          command: check
```

## Checking translation quality

<AvailableFrom version="0.12.0" />

Add `qa: "true"` to `command: check` to run [`verbatra check --qa`](/docs/cli/check#quality-check) over every committed translation, including values typed by hand. It stays read-only and keyless.

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
          qa: "true"
```

- Each finding becomes one annotation titled `verbatra qa: <locale>`: an error for a value the integrity gate would refuse, a warning for a review reason.
- The step fails on any error finding. Add `qa-strict: "true"` to fail on warnings too, or `qa-severity: error` to report errors only.
- `qa` needs a `version` of `0.12.0` or newer. A lower pin fails the step before anything is installed, and so does a prerelease such as `0.12.0-next.0`, so pin the release.

## Human-only mode

<AvailableFrom version="0.12.0" />

With `provider: { id: "none" }` (see [Human-only workflow](/docs/human-only-workflow)), `translate` exits `3` when it leaves keys for a person. The action treats that as work to hand off, not a failure: the step passes, each affected locale gets a `NEEDS_HUMAN` warning, the job summary lists the keys, and the `needs-human` output is `"true"`. Branch on it:

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        id: verbatra
        with:
          version: 0.12.0
      - if: steps.verbatra.outputs.needs-human == 'true'
        run: echo "Some keys need a human translation; see the job summary."
```

Only `translate` gets this treatment. An exit `3` from `check` or `diff` still fails the step.

## Config discovery

With `config-path` empty, the action requires a recognized config file directly inside `working-directory` (the repository root by default). It never looks in a parent directory, so in a monorepo point `working-directory` at the app and keep its config there:

```yaml
      with:
        version: 0.11.1
        working-directory: apps/docs
```

If no config is found, the step fails before installing the CLI and names the directory it checked. To load a config from elsewhere, set `config-path`: a relative path resolves against `working-directory`. The action always passes the resolved file to the CLI with `--config`.

## Persist translations

`translate` writes the updated locale files into the runner's checkout and stops there: the action never commits. Add your own step that commits and pushes, or opens a pull request, and grant `contents: write` or `pull-requests: write` to that job only. To report without writing, set `dry-run: "true"` or use `command: check`.

## Inputs

| Input | Default | Effect |
| --- | --- | --- |
| `version` | required | exact `@verbatra/cli` release to run, `0.9.3` or newer; a dist-tag, range or `^`/`~` prefix fails the step |
| `command` | `translate` | `translate`, `check` or `diff`; anything else fails the step |
| `config-path` | `""` | config file to load (`--config`); relative to `working-directory` |
| `working-directory` | `""` | directory to run in (`--cwd`); the repository root when empty |
| `dry-run` | `"false"` | `"true"` previews without calling a provider or writing (`--dry-run`); `translate` only |
| `qa` | `"false"` | `"true"` adds the quality check (`--qa`); `check` only, needs `0.12.0` or newer |
| `qa-severity` | `""` | lowest severity to report, `error` or `warning` (`--severity`); requires `qa` |
| `qa-strict` | `"false"` | `"true"` also fails on warnings (`--strict`); requires `qa` |
| `node-version` | `"24"` | Node.js version the action sets up to run the CLI |

The boolean inputs accept only `"true"` or `"false"`. An invalid value or combination fails the step with exit `1` before anything is installed.

## Outputs

| Output | Value |
| --- | --- |
| `needs-human` | `"true"` when `translate` exited `3` and left keys for a person, otherwise `"false"` |

## What a run shows you

- **Annotations.** Under `translate`, each failed or partial locale becomes one error annotation titled `verbatra: <locale>`. Under `check` or `diff`, each drifted locale gets one titled `verbatra check: <locale>` or `verbatra diff: <locale>`. A partial locale's `LOCALE_PARTIAL` annotation names the withheld keys, grouped by cause. A run that fails as a whole gets one `verbatra` annotation with the error. GitHub shows at most 10 annotations per severity, so the action adds one notice counting the rest.
- **Job summary.** One row per locale with the counts for the command that ran, an aggregate line, and the partial and failed locales. With `qa` it adds a findings table of up to 1000 findings.
- **Exit status.** The action emits the annotations and the summary first, then exits with the CLI's own code, so the step fails on `1` or `2` only after showing why. The codes are on [Exit codes and JSON output](/docs/cli/output#exit-codes).

## Security

Pin both references: `uses:` to a commit SHA and `version` to an exact release; the action rejects anything that could resolve `latest`. Keep the workflow at `contents: read` unless a later step writes. Inputs reach the CLI as a quoted argument array, never spliced into shell text, so a crafted input stays an argument.
