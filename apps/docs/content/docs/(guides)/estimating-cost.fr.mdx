Utilise ceci avant une première exécution sur un vrai projet, ou avant toute exécution que quelqu'un doit approuver. verbatra ne publie aucun prix, car les tarifs appartiennent au fournisseur et changent sans prévenir. Il compte ce qui te sera facturé, et le convertit en argent dès que tu lui donnes les tarifs actuels de ton fournisseur.

Pour un projet typique, quelques centaines de clés vers quelques locales avec un petit modèle coûtent quelques centimes, et l'exécution suivante presque rien, car seules les clés modifiées sont envoyées.

## Compte le travail

```bash
verbatra translate --dry-run
```

```text output
verbatra translate (dry run)
  de: 400 would translate, 0 unchanged
  es: 400 would translate, 0 unchanged
  fr: 400 would translate, 0 unchanged
3 succeeded, 0 partial, 0 failed (dry run: nothing written)
```

`would translate` est le nombre de clés qu'une vraie exécution enverrait : celles qui manquent dans le fichier cible plus celles dont le texte source a changé. Un dry run ne construit aucun fournisseur, ne lit aucune clé et n'écrit rien. Considère ce nombre comme une borne haute : il ignore [le cache](/docs/the-cache), qui sert gratuitement les chaînes répétées lors d'une vraie exécution, et il ne regroupe pas les chaînes source identiques, qu'une vraie exécution n'envoie qu'une fois.

## Estime la dépense

<AvailableFrom version="0.11.0" />

```bash
verbatra translate --estimate
```

```text output
verbatra translate (estimate)
  de: 400 would translate, 0 unchanged
  es: 400 would translate, 0 unchanged
  fr: 400 would translate, 0 unchanged
  estimate: 1200 keys in 24 requests, ~40944 input + ~30720 output tokens
  estimated spend: no rate on file for gemini/gemini-2.5-flash; add rates.table["gemini/gemini-2.5-flash"] to your config to see a currency figure
  estimate excludes: cache hits, duplicate source strings, provider-side retries, translation length, tokenizer differences, repair requests
3 succeeded, 0 partial, 0 failed (dry run: nothing written)
```

`--estimate` implique `--dry-run`, il ne dépense donc rien. Il indique l'unité que facture ton fournisseur : des tokens pour un LLM, des caractères source pour DeepL et Google Cloud Translation, et aucun coût d'API pour un serveur `openai-compatible` ou `libretranslate` auto-hébergé. Avec `--json`, les mêmes chiffres se trouvent sous `result.estimate`, par locale et au total, pour qu'un script puisse s'appuyer dessus.

Pour voir un montant, cherche le tarif actuel de ton modèle sur la page de tarifs du fournisseur lui-même :

| Fournisseur | Facturé au | Tarifs |
| --- | --- | --- |
| Gemini | tokens d'entrée et de sortie (niveau gratuit disponible) | [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing) |
| Anthropic | tokens d'entrée et de sortie | [Anthropic pricing](https://www.anthropic.com/pricing) |
| OpenAI | tokens d'entrée et de sortie | [OpenAI API pricing](https://openai.com/api/pricing/) |
| DeepL | caractères source | [DeepL Pro pricing](https://www.deepl.com/pro) |
| Google Cloud Translation | caractères source | [Cloud Translation pricing](https://cloud.google.com/translate/pricing) |
| openai-compatible, LibreTranslate | rien : ton propre serveur | aucun coût d'API |

Ajoute-le ensuite à la configuration avec la date à laquelle tu l'as relevé :

```ts title="verbatra.config.ts"
export default defineConfig({
  // ...
  rates: {
    asOf: "2026-01-15",
    currency: "USD",
    table: {
      "gemini/gemini-2.5-flash": { inputPerMillionTokens: 0.1, outputPerMillionTokens: 0.4 },
    },
  },
});
```

Les tarifs ci-dessus sont des exemples, pas des prix cités. Chaque montant calculé à partir d'eux porte la date `asOf`, donc une grille tarifaire ancienne se voit. verbatra n'invente jamais un tarif manquant et n'affiche jamais `0.00` pour un modèle qu'il ne sait pas chiffrer ; il nomme l'entrée manquante à la place. Le format des clés et les unités sont décrits dans [`rates`](/docs/config-file#rates).

## Comprends ce que couvre le chiffre

L'estimation fait le calcul que tu ferais sinon à la main :

- **Requêtes.** Les clés de chaque locale sont réparties en lots d'au plus [`maxBatchSize`](/docs/config-file#maxbatchsize) (`50` par défaut), une requête par lot, plus les lots qu'enverrait [`generatePlurals`](/docs/config-file#generateplurals).
- **Entrée.** Chaque requête LLM porte des règles système fixes (environ 550 tokens) et un schéma de réponse (environ 100 tokens), puis les clés, leurs descriptions, le ton et le glossaire complet de la locale cible. Le prompt est mesuré en sérialisant la charge qui serait envoyée, donc un grand glossaire compte à chaque requête qui le transporte.
- **Sortie.** La traduction n'existe pas encore, elle est donc évaluée comme le texte source plus 50 pour cent, car l'allemand, le français et le russe sont souvent d'un tiers à la moitié plus longs que l'anglais.
- **Tokens.** Les caractères sont convertis à raison d'environ quatre par token, ce qui convient à de la prose anglaise ; d'autres écritures sont plus denses.

Une vraie exécution coûte en général moins, pour les deux raisons qui font du chiffre du dry run une borne haute. Elle peut aussi coûter plus, et la ligne `estimate excludes` nomme chaque cause. Deux comptent le plus :

- **Nouvelles tentatives.** Le SDK de chaque fournisseur relance lui-même une requête échouée : deux tentatives de plus pour Anthropic, OpenAI, `openai-compatible` et Gemini, et cinq pour DeepL. Une tentative qui a atteint le modèle est facturée.
- **Réparations.** Quand des clés reviennent manquantes, verbatra envoie une requête de réparation, qui reporte en entier les règles système, le glossaire et le ton.

Planifie avec ce chiffre, mais ne le promets pas comme plafond. L'estimation ne couvre d'ailleurs que `translate` : retraduire une entrée depuis [Studio](/docs/review-in-studio) ou un outil d'agent dépense par son propre chemin.

## Plafonne l'exécution

<AvailableFrom version="0.12.0" />

Donne à l'exécution validée un arrêt ferme un peu au-dessus de la somme des tokens d'entrée et de sortie estimés :

```bash
verbatra translate --max-tokens 80000
```

Une requête qui dépasserait le plafond est retenue au lieu d'être envoyée, et ses clés restent en attente pour l'exécution suivante. Si la configuration fixe aussi `maxTokens`, c'est la valeur la plus basse qui s'applique. DeepL, Google Cloud Translation et LibreTranslate ne rapportent pas de tokens, donc le plafond s'applique alors à la projection de verbatra lui-même. Voir [Plafond de tokens](/docs/cli/translate#plafond-de-tokens), et [`maxTokens` et `budgetBehavior`](/docs/config-file#maxtokens-et-budgetbehavior) pour un budget valable à chaque exécution.

## Calibre sur une locale

Le chiffre exact vient d'une vraie exécution. Traduis une locale et lis la consommation :

```bash
verbatra translate --locales de
```

```text output
verbatra translate
  de: 400 translated, 0 unchanged, 18400 tokens (10800 in, 7600 out)
  total: 18400 tokens (10800 in, 7600 out)
1 succeeded, 0 partial, 0 failed
```

Multiplie par le nombre de locales restantes. Avec `--json`, les chiffres sont `usage.inputTokens` et `usage.outputTokens`. L'exécution dépense de l'argent réel, mais le travail est gardé : cette locale est terminée.

## Fournisseurs de traduction automatique

DeepL, Google Cloud Translation et LibreTranslate facturent des caractères source, pas des tokens. verbatra ne leur envoie que le texte source, sans règles système, noms de clés ni JSON autour, il n'y a donc aucun coût fixe par requête. Les chaînes contenant des placeholders ou de la syntaxe ICU sont retenues plutôt que risquées, si bien que les caractères envoyés peuvent être moins nombreux que le total brut.

### Google Cloud Translation

<AvailableFrom version="0.10.0" />

Google Cloud Translation est compté comme DeepL : des caractères source dans l'estimation, et un nombre de tokens projeté pour un budget `maxTokens`, marqué comme estimé dans le résumé de l'exécution.

## Estime depuis un agent

Deux outils d'agent renvoient ce qu'affiche `translate --estimate --json`, pour toutes les locales ou une partie, et n'appellent jamais de fournisseur :

| Outil | Où |
| --- | --- |
| `translation.estimate` | le [serveur MCP](/docs/cli/mcp) <AvailableFrom version="0.3.0" pkg="@verbatra/mcp" /> |
| `verbatra_translation_estimate` | [les outils d'agent de Studio](/docs/agent-tools-in-studio) <AvailableFrom version="0.6.0" pkg="@verbatra/studio" /> |

`translation.translatePending` accepte ensuite les mêmes `locales` et un plafond `maxTokens`. Voir [Estimer avant de payer](/docs/cli/mcp#estimer-avant-de-payer).

## Pourquoi l'exécution suivante coûte moins

Les chiffres ci-dessus sont le coût de la première exécution. Ensuite, verbatra n'envoie que les clés manquantes ou dont la source a changé depuis la référence [du fichier de verrouillage](/docs/the-lock-file), et [le cache](/docs/the-cache) réutilise les traductions antérieures de chaînes identiques. Au quotidien, tu paies pour les chaînes que tu as modifiées. Pour répéter gratuitement, utilise le niveau gratuit de Gemini ou pointe `openai-compatible` vers un modèle local ; voir [Fournisseurs](/docs/providers).
