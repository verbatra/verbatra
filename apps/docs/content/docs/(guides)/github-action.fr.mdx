Utilise l'action quand un job GitHub Actions doit exécuter verbatra et te montrer ce qui s'est passé. Elle exécute `translate`, `check` ou `diff` avec `--json` ; pour toute autre commande ou option, comme `--prune`, lance [la CLI directement](/docs/ci-and-exit-codes).

Avant de commencer, il te faut :

- Une configuration verbatra directement dans le répertoire où l'action s'exécute (consulte [Découverte de la configuration](#découverte-de-la-configuration)).
- Une version exacte de `@verbatra/cli` à épingler, `0.9.3` ou plus récente.
- Pour `translate` uniquement : la clé d'API de ton fournisseur en secret du dépôt.

## Ajouter l'action à un workflow

L'action se trouve dans [verbatra/action](https://github.com/verbatra/action) et sur le [GitHub Marketplace](https://github.com/marketplace/actions/verbatra) ; il n'y a pas de paquet npm. Épingle-la sur un SHA de commit, comme ci-dessous, ou utilise le tag mobile `verbatra/action@v1`. L'ancienne forme par chemin dans le monorepo verbatra ne se résout plus.

```yaml title=".github/workflows/translate.yml"
name: translate
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  verbatra:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-sha>
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0 # an exact @verbatra/cli release, 0.9.3 or newer
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
```

L'action installe `@verbatra/cli` et `@verbatra/sdk` exactement dans cette version dans un répertoire temporaire, donc le job n'a pas besoin d'étape d'installation à lui. Fais monter l'épinglage délibérément ; [npm](https://www.npmjs.com/package/@verbatra/cli) montre la version actuelle.

### Passer la clé du fournisseur

Fais passer la clé depuis les secrets du dépôt sous la variable que lit ton fournisseur ; [Fournisseurs](/docs/providers#les-clés-viennent-de-lenvironnement) les liste. L'action n'a pas d'entrée pour la clé, donc une clé ne circule jamais comme entrée ni comme argument de la CLI.

## Contrôler une pull request

Mets `command: check` pour faire échouer une pull request dont les fichiers de locale ont dérivé, ou `command: diff` pour lister en plus les clés en attente. Les deux sont en lecture seule et n'appellent aucun fournisseur : ils n'ont besoin d'aucune clé et tournent sur les pull requests venant de forks :

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
```

## Vérifier la qualité des traductions

<AvailableFrom version="0.12.0" />

Ajoute `qa: "true"` à `command: check` pour lancer [`verbatra check --qa`](/docs/cli/check#contrôle-qualité) sur chaque traduction commitée, y compris les valeurs saisies à la main. Cela reste en lecture seule et sans clé.

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
          qa: "true"
```

- Chaque constat devient une annotation intitulée `verbatra qa: <locale>` : une erreur pour une valeur que le contrôle d'intégrité refuserait, un avertissement pour un motif de relecture.
- L'étape échoue sur tout constat d'erreur. Ajoute `qa-strict: "true"` pour échouer aussi sur les avertissements et les pluriels incomplets, ou `qa-severity: error` pour ne signaler que les erreurs.
- Une `version` inférieure à `0.12.0`, ou une préversion telle que `0.12.0-next.0`, fait échouer l'étape avant toute installation.

## Exiger des traductions relues

<AvailableFrom version="0.12.0" />

Ajoute `require-reviewed: "true"` à `command: check` pour lancer [`verbatra check --require-reviewed`](/docs/cli/check#exiger-des-traductions-relues). L'étape échoue tant qu'une traduction écrite par une machine n'est pas approuvée dans le `verbatra.provenance.json` commité, où [Studio](/docs/review-in-studio) enregistre les décisions de relecture. Cela reste en lecture seule et sans clé, et se combine avec `qa`.

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        with:
          version: 0.12.0
          command: check
          require-reviewed: "true"
```

- Chaque locale avec des clés non approuvées reçoit une annotation d'erreur [`REVIEW_REQUIRED`](/docs/error-codes#review_required) qui les nomme, et le résumé de job ajoute une colonne `unreviewed`.
- Un `verbatra.provenance.json` corrompu ou écrit par un verbatra plus récent fait échouer le contrôle avec une seule annotation `REVIEW_STATE_UNREADABLE`.
- Comme `qa`, il demande une `version` `0.12.0` ou plus récente, et une préversion fait échouer l'étape.

## Mode humain uniquement

<AvailableFrom version="0.12.0" />

Avec `provider: { id: "none" }` (consulte [Flux 100 % humain](/docs/human-only-workflow)), `translate` sort avec `3` quand il laisse des clés à une personne. L'action le traite comme du travail à transmettre, pas comme un échec : l'étape réussit, chaque locale concernée reçoit un avertissement `NEEDS_HUMAN`, le résumé de job liste les clés et la sortie `needs-human` vaut `"true"`. Branche-toi dessus :

```yaml
      - uses: verbatra/action@<commit-sha> # a commit on the v1 line
        id: verbatra
        with:
          version: 0.12.0
      - if: steps.verbatra.outputs.needs-human == 'true'
        run: echo "Some keys need a human translation; see the job summary."
```

Seul `translate` reçoit ce traitement. Un `3` venant de `check` ou `diff` fait toujours échouer l'étape.

## Découverte de la configuration

Quand `config-path` est vide, l'action exige un fichier de configuration reconnu directement dans `working-directory` (par défaut la racine du dépôt). Elle ne cherche jamais dans un répertoire parent, donc dans un monorepo, pointe `working-directory` vers l'app et garde sa configuration là :

```yaml
      with:
        version: 0.12.0
        working-directory: apps/docs
```

Si aucune configuration n'est trouvée, l'étape échoue avant d'installer la CLI et nomme le répertoire contrôlé. Pour charger une configuration d'ailleurs, définis `config-path` : un chemin relatif se résout par rapport à `working-directory`.

## Conserver les traductions

`translate` écrit les fichiers de locale mis à jour dans le checkout du runner et s'arrête là : l'action ne commite jamais. Ajoute ta propre étape qui commite et pousse, ou ouvre une pull request, et n'accorde `contents: write` ou `pull-requests: write` qu'à ce job. Pour signaler sans écrire, mets `dry-run: "true"` ou utilise `command: check`.

## Entrées

| Entrée | Défaut | Effet |
| --- | --- | --- |
| `version` | obligatoire | version exacte de `@verbatra/cli`, `0.9.3` ou plus récente ; un dist-tag, une plage ou un préfixe `^`/`~` fait échouer l'étape |
| `command` | `translate` | `translate`, `check` ou `diff` ; toute autre valeur fait échouer l'étape |
| `config-path` | `""` | fichier de configuration à charger (`--config`) ; relatif à `working-directory` |
| `working-directory` | `""` | répertoire où la CLI s'exécute (`--cwd`) ; vide, c'est la racine du dépôt |
| `dry-run` | `"false"` | `"true"` prévisualise sans appeler de fournisseur ni écrire (`--dry-run`) ; `translate` uniquement |
| `qa` | `"false"` | `"true"` ajoute le contrôle qualité (`--qa`) ; `check` uniquement |
| `qa-severity` | `""` | gravité minimale signalée, `error` ou `warning` (`--severity`) ; exige `qa` |
| `qa-strict` | `"false"` | `"true"` échoue aussi sur les avertissements (`--strict`) ; exige `qa` |
| `require-reviewed` | `"false"` | `"true"` échoue aussi sur les traductions machine non approuvées (`--require-reviewed`) ; uniquement `check` |
| `node-version` | `"24"` | version de Node.js que l'action installe pour exécuter la CLI |

Les entrées booléennes n'acceptent que `"true"` ou `"false"`. Une valeur ou une combinaison invalide fait échouer l'étape avec la sortie `1` avant toute installation.

## Sorties

| Sortie | Valeur |
| --- | --- |
| `needs-human` | `"true"` quand `translate` est sorti avec `3` et a laissé des clés à une personne, sinon `"false"` |

## Ce qu'une exécution te montre

- **Annotations.** Avec `translate`, chaque locale en échec ou partielle devient une annotation d'erreur intitulée `verbatra: <locale>`. Avec `check` ou `diff`, chaque locale qui a dérivé en reçoit une intitulée `verbatra check: <locale>` ou `verbatra diff: <locale>`. L'annotation `LOCALE_PARTIAL` d'une locale partielle nomme les clés retenues, regroupées par cause. Chaque `check` ajoute un avertissement `PLURAL_CATEGORIES_INCOMPLETE` par locale dont les pluriels n'ont pas une catégorie CLDR que la langue utilise. Une exécution qui échoue dans son ensemble reçoit une seule annotation `verbatra` avec le code d'erreur, sa cause sous la forme `(cause: X)` et une piste `Next step:` quand la CLI les fournit. GitHub affiche au plus 10 annotations par gravité, donc l'action les ordonne par dérive, relecture, erreurs de qualité puis avertissements, et ajoute une notice qui compte le reste.
- **Résumé de job.** Une ligne par locale avec les compteurs de la commande exécutée, une ligne agrégée et les locales partielles et en échec. Avec `qa`, il ajoute un tableau de constats jusqu'à 1000 constats ; les pluriels incomplets ont leur propre section.
- **Statut de sortie.** L'action émet d'abord les annotations et le résumé, puis sort avec le [code de sortie](/docs/cli/output#codes-de-sortie) de la CLI elle-même, donc l'étape n'échoue qu'après avoir montré pourquoi.

## Sécurité

Épingle les deux références : `uses:` sur un SHA de commit et `version` sur une version exacte ; l'action refuse tout ce qui pourrait se résoudre en `latest`. Les entrées atteignent la CLI sous forme de tableau d'arguments entre guillemets, jamais insérées dans du texte shell, donc une valeur d'entrée forgée reste un argument.
