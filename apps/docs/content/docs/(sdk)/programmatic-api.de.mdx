Die [SDK-Referenz](/docs/sdk) katalogisiert jeden Einstiegspunkt. Diese Seite ist der praktische
Begleiter: End-to-End-Rezepte, die du in ein Skript kopieren und ausführen kannst. Eine Sache
vorab: das SDK lädt keine `.env`-Dateien (das macht die CLI), stelle also sicher, dass die
Umgebungsvariable des Providers gesetzt ist, bevor dein Skript läuft, zum Beispiel:

```bash
node --env-file=.env translate.mjs
```

## Einmal übersetzen in einem Skript

Lade die Konfiguration, führe den Flow aus, dann lies die Zusammenfassung: das Gesamtbild aus
`succeeded` und `failed`, den Token-Verbrauch aus `usage` und die Keys, die einen menschlichen
Blick verdienen, aus dem `needsReview` jeder Locale. Probleme des gesamten Laufs werfen einen
`SdkError`; Ergebnisse pro Locale sind Daten auf der Zusammenfassung.

```ts
import { loadConfig, translate } from "@verbatra/sdk";

const config = await loadConfig();
const summary = await translate({ config });

console.log(
  `${summary.succeeded.length} ok, ${summary.partial.length} partial, ${summary.failed.length} failed`,
);

if (summary.usage !== undefined) {
  console.log(`tokens: ${summary.usage.inputTokens} in, ${summary.usage.outputTokens} out`);
}

for (const locale of summary.locales) {
  if (locale.status === "failed") {
    console.error(`${locale.locale}: ${locale.error?.code} ${locale.error?.message}`);
    continue;
  }
  for (const entry of locale.needsReview) {
    console.warn(`review ${locale.locale}/${entry.key}: ${entry.reasons.join(", ")}`);
  }
}

if (summary.failed.length > 0 || summary.partial.length > 0) {
  process.exitCode = 1;
}
```

Eine als `partial` gemeldete Locale ist eine, deren Datei mit weiterhin fehlenden Keys
geschrieben wurde. Das ist kein Erfolg: Die CLI endet darauf mit `1`, und dein eigenes Skript
sollte es genauso behandeln, deshalb prüft die Abfrage oben `partial` neben `failed`.

Übergib `dryRun: true`, um ohne Provider-Aufruf und ohne Schreiben eine Vorschau zu bekommen, und
`prune: true` oder `generatePlurals: true`, um diese Konfigurationsoptionen für einen Lauf zu
überschreiben. Übergib `locales: ["de"]`, um den Lauf auf eine Teilmenge der konfigurierten Ziele
zu beschränken; so arbeitest du einen ratenbegrenzten Provider Sprache für Sprache ab. Eine nicht
konfigurierte Locale wirft `UNKNOWN_LOCALE`, bevor irgendetwas gelesen oder Geld ausgegeben wird. Setze
`concurrency` über 1, um Locales parallel zu übersetzen (bei einem Live-Lauf nicht mit einem
`maxTokens`-Budget erlaubt), und `cache: false`, um den
[Übersetzungsspeicher-Cache](/docs/the-cache) zu umgehen.

## Einen Lauf schätzen, bevor du ausgibst

<AvailableFrom version="0.11.0" />

`estimate: true` impliziert `dryRun`, der Lauf konstruiert also keinen Provider, liest keinen
API-Key und schreibt nichts. Die Zahl landet auf `RunSummary.estimate`. Verzweige über `unit`
für die abgerechnete Dimension und über `pricing` dafür, ob eine Währungszahl verfügbar war:
verbatra liefert keine eigenen Raten mit, ein Preis erscheint also nur, wenn die Konfiguration
einen `rates`-Block für diesen Provider und dieses Modell trägt.

```ts
import { loadConfig, translate } from "@verbatra/sdk";

const summary = await translate({ config: await loadConfig(), estimate: true });
const estimate = summary.estimate;

if (estimate !== undefined) {
  console.log(`${estimate.keys} keys in ${estimate.requests} requests to ${estimate.rateKey}`);

  if (estimate.unit === "tokens") {
    console.log(`about ${estimate.inputTokens} in, ${estimate.outputTokens} out`);
  } else {
    console.log(`about ${estimate.sourceCharacters} source characters`);
  }

  if (estimate.pricing === "priced") {
    console.log(`about ${estimate.cost} ${estimate.currency}, rates read ${estimate.asOf}`);
    for (const locale of estimate.locales) {
      console.log(`  ${locale.locale}: ${locale.cost}`);
    }
  } else {
    console.log(`no currency figure: ${estimate.pricing}`);
  }

  console.log(`leaves out: ${estimate.caveats.join(", ")}`);
}
```

Es begrenzt den Plan, nicht die Rechnung: Ein echter Lauf gibt meist weniger aus, weil er den
[Übersetzungsspeicher-Cache](/docs/the-cache) befragt und identische Quellstrings zusammenfasst,
und er kann aus jedem Grund mehr ausgeben, den `caveats` nennt. `resolveDryRun` ist die eine
Stelle, an der die Regel "`estimate` impliziert `dryRun`" entschieden wird, rufe es also auf,
statt sie erneut auszuformulieren. Die Methode hinter den Zahlen steht in
[Kosten abschätzen](/docs/estimating-cost).

`caveats` ist nie leer. Seine Codes (`EstimateCaveatCode`) sind:

- `CACHE_NOT_CONSULTED`: Der Übersetzungsspeicher wird nicht gelesen, Keys, die ein echter Lauf
  aus dem Cache bedienen würde, werden also trotzdem mitgezählt. Gilt für jede Schätzung.
- `SOURCE_DUPLICATES_NOT_DEDUPLICATED`: Ein echter Lauf sendet einen Vertreter pro identischem
  Quellstring; die Schätzung zählt jeden Key. Gilt für jede Schätzung.
- `TRANSPORT_RETRIES_NOT_COUNTED`: Pro geplanter Anfrage wird ein abrechenbarer Aufruf gezählt,
  obwohl die Provider-SDKs einen fehlgeschlagenen Aufruf darunter wiederholen können und ein
  wiederholter Versuch trotzdem abgerechnet werden kann. Gilt für jede Schätzung.
- `TRANSLATION_LENGTH_IS_ESTIMATED`: Die Antwort wird aus der Quelle plus einem festen Zuschlag für
  Textverlängerung bemessen, eine Zielsprache mit längeren Texten meldet also mehr
  Completion-Tokens. Nur Provider mit Token-Abrechnung.
- `TOKEN_COUNT_IS_HEURISTIC`: Tokens werden aus Zeichenzahlen abgeleitet, nicht aus dem eigenen
  Tokenizer des Providers. Nur Provider mit Token-Abrechnung.
- `REPAIR_REQUESTS_NOT_COUNTED`: Die Reparaturrunde für Keys, die fehlend zurückkamen, und der
  Retry in Hälften bei einer abgeschnittenen Antwort werden nicht gezählt. Nur Provider mit
  Token-Abrechnung.

## In CI prüfen, ohne zu schreiben

`check` liest und vergleicht, ohne einen Provider aufzurufen oder irgendeine Datei anzufassen, und
sein `inSync`-Flag ist genau dann true, wenn nichts fehlt und nichts veraltet ist. Das macht es
zum natürlichen CI-Gate.

```ts
import { check, loadConfig } from "@verbatra/sdk";

const summary = await check({ config: await loadConfig() });

if (!summary.inSync) {
  for (const locale of summary.locales) {
    if (!locale.inSync) {
      console.error(`${locale.locale}: ${locale.missing} missing, ${locale.stale} stale`);
    }
  }
  process.exitCode = 1;
}
```

Du brauchst die Key-Namen statt der Anzahlen? Tausche `diff` ein, das die Key-Listen `missing`,
`changed` und `orphaned` pro Locale zurückgibt, mit demselben `hasPendingChanges`-Gate. Du führst
stattdessen die CLI in CI aus? Siehe [CI und Exit-Codes](/docs/ci-and-exit-codes).

## Beobachten in einem langlaufenden Prozess

`watch` feuert beim Start sofort einen Lauf, danach einen pro entprellter Quelländerung, und
meldet jeden über `onRun`. Für ein sauberes Herunterfahren warte auf `controller.stop()`: es
schließt den Watcher und wartet auf den laufenden Lauf, bevor dein Prozess endet.

```ts
import { loadConfig, watch } from "@verbatra/sdk";

const config = await loadConfig();
const controller = await watch({
  config,
  onRun: (result) => {
    if (result.status === "succeeded") {
      console.log(`ran: ${result.summary.succeeded.length} ok, ${result.summary.failed.length} failed`);
    } else {
      console.error(`run failed: ${result.error.code} ${result.error.message}`);
    }
  },
});

process.on("SIGINT", () => {
  void controller.stop().then(() => {
    process.exit(0);
  });
});
```

Ein Lauf-Fehlschlag nach dem Start wirft nie; er kommt als `{ status: "failed" }` an, und das
Beobachten geht weiter.

## Keys aus deinem Quellcode extrahieren

<AvailableFrom version="0.11.0" />

`extract` ist der eine Einstiegspunkt, der Anwendungscode statt einer Locale-Datei liest. Er
schreibt nur den Quellkatalog, und nur wirklich neue Keys: Ein vorhandener Key behält seinen Wert,
und ein Key, den keine Aufrufstelle nennt, bleibt unangetastet. Alles, was der Scan nicht auflösen
kann, kommt als Daten zurück, ein Dry Run ist also ein gutes Gate vor dem schreibenden Lauf.

```ts
import { extract, loadConfig } from "@verbatra/sdk";

const config = await loadConfig();
const preview = await extract({ config, dryRun: true });

console.log(`${preview.scannedFiles} files scanned, ${preview.existingKeys} keys already present`);
for (const added of preview.added) {
  console.log(`+ ${added.key} = ${JSON.stringify(added.value)} (${added.file}:${added.line})`);
}
for (const conflict of preview.conflicts) {
  console.warn(`${conflict.key} has two defaults: ${conflict.values.join(" | ")}`);
}
for (const site of preview.dynamic) {
  console.warn(`non-static key argument at ${site.file}:${site.line}`);
}
for (const diagnostic of preview.diagnostics) {
  console.warn(`${diagnostic.file}: ${diagnostic.reason}`);
}

if (preview.added.length > 0 && preview.conflicts.length === 0) {
  const run = await extract({ config });
  console.log(`wrote ${run.added.length} keys to ${run.sourcePath}: ${run.written}`);
}
```

`config.extract` muss das Framework und die Quellverzeichnisse nennen, sonst wirft der Aufruf
`EXTRACT_NOT_CONFIGURED`. Die Dateisuche läuft über das optionale `readDirectory`-Member von
`SdkFs`, ein eigenes `deps.fs` ohne dieses Member wird also mit `EXTRACT_FS_UNSUPPORTED`
abgelehnt, und ein Quellkatalog, der nicht geschrieben werden kann, löst `SOURCE_UNWRITABLE` aus.

## Einen typisierten Katalog erzeugen

<AvailableFrom version="0.11.0" />

`generateTypes` deklariert den Quellkatalog als TypeScript: eine Union aus jedem Key plus den
Argumenten, die jede Nachricht interpoliert. Es liest eine Datei und schreibt eine Datei, und zwei
Läufe über einen unveränderten Katalog schreiben Byte für Byte dasselbe: genau das macht den
`check`-Modus zu einem brauchbaren CI-Gate.

```ts
import { generateTypes, loadConfigWithMeta } from "@verbatra/sdk";

const loaded = await loadConfigWithMeta();
const out = "src/generated/messages.d.ts";
const configPath = loaded.source.kind === "override" ? undefined : loaded.source.filepath;

const result = await generateTypes({
  config: loaded.config,
  out,
  ...(configPath !== undefined ? { configPath } : {}),
});

console.log(`${result.keys} keys in ${result.path}, ${result.withArguments} take arguments`);
for (const message of result.unresolved) {
  console.warn(`arguments not claimed for ${message.key}: ${message.reason}`);
}

// In CI, compare instead of writing.
const gate = await generateTypes({ config: loaded.config, out, check: true });
if (gate.stale) {
  console.error(`${gate.path} is out of date, re-generate it`);
  process.exitCode = 1;
}
```

Übergib `configPath`, damit die vom Lauf geladene Konfigurationsdatei als Ausgabepfad abgelehnt
wird. Ein `check`-Lauf schreibt nichts, lehnt nichts wegen seines Inhalts ab und meldet nur
`stale`. Alles, was ein schreibender Lauf mit `TYPES_OUTPUT_CONFLICT` ablehnt, steht auf der Seite
[`verbatra types`](/docs/cli/types); eine Deklaration, die nicht geschrieben werden kann, löst
`TYPES_UNWRITABLE` aus.

## Eine Pseudo-Locale bauen

<AvailableFrom version="0.11.0" />

`pseudolocalize` baut allein aus den Quellstrings eine künstliche Locale, sodass abgeschnittene
Layouts und nie extrahierte Strings auftauchen, bevor es überhaupt einen API-Key gibt. Es
konstruiert keinen Provider und stellt keine Netzwerkanfrage, und seine Ausgabe landet außerhalb
von `files.pattern`, `translate` gibt also nie Geld dafür aus, und `check` und `diff` melden sie
nie als abgedriftet.

```ts
import { loadConfig, pseudolocalize } from "@verbatra/sdk";

const result = await pseudolocalize({ config: await loadConfig() });

console.log(`${result.locale} written to ${result.path}: ${result.written}`);
console.log(`${result.transformed} of ${result.entries} entries transformed`);
for (const key of result.copied) {
  console.warn(`copied from source verbatim, a pseudolocalized value would not pass the gate: ${key}`);
}
```

`locale` ist standardmäßig `en-XA` und `out` `.verbatra-local/pseudo`. Eine Pseudo-Locale, die eine
konfigurierte Locale benennt, oder ein `out`, das auf einer konfigurierten Locale-Datei landen
würde, wird mit `PSEUDO_OUTPUT_CONFLICT` abgelehnt, bevor irgendetwas gelesen oder geschrieben
wird. Die Transformation ist deterministisch, ein zweiter Lauf über unveränderte Quelle schreibt
also nichts neu und meldet `written` als false.

## Einen einzelnen Key bearbeiten und neu übersetzen

Das sind die Nahtstellen, an denen Verbatra Studio ansetzt; nutze sie, um deinen eigenen
Review-Flow zu bauen. Lies die aktuellen Werte mit `keyValue`, speichere eine menschliche Korrektur
mit `editEntry` oder lass den Provider für einen Key mit `retranslateEntry` neu laufen. Beide
schreibenden Einstiegspunkte schicken den Kandidatenwert durch dieselben Integritätsprüfungen wie
ein voller Lauf und geben ein zweiarmiges Ergebnis zurück, statt bei einem abgelehnten Wert zu
werfen.

```ts
import { editEntry, keyValue, loadConfig, retranslateEntry } from "@verbatra/sdk";

const config = await loadConfig();

// Read the live values feeding your edit UI.
const current = await keyValue({ config, locale: "de", key: "checkout.title" });
console.log(`source: ${current.source}, target: ${current.target ?? "(not yet translated)"}`);

// Save a human-typed correction. No provider call.
const edit = await editEntry({
  config,
  locale: "de",
  key: "checkout.title",
  value: "Zur Kasse",
});
if (!edit.accepted) {
  console.error(`rejected (${edit.reason} check failed), nothing written`);
}

// Or ask the provider for a fresh translation of just this key.
const retry = await retranslateEntry({ config, locale: "de", key: "checkout.title" });
if (retry.accepted) {
  console.log(`wrote: ${retry.value}`);
  if (retry.reviewReasons.length > 0) {
    console.warn(`flagged for review: ${retry.reviewReasons.join(", ")}`);
  }
}
```

Eine unbekannte Locale oder ein unbekannter Key wirft `UNKNOWN_LOCALE` oder `UNKNOWN_KEY`, und
`retranslateEntry` wirft den eigenen `ProviderError` des Providers (zum Beispiel `RATE_LIMITED`),
wenn der Aufruf selbst fehlschlägt. Dieselben Nahtstellen hinter einer Oberfläche zeigt
[Review in Studio](/docs/review-in-studio).

## Alle Werte auf einmal lesen

<AvailableFrom version="0.10.0" />

`localeValues` ist das Gegenstück zu `keyValue` für große Mengen: ein Durchgang über die Dateien,
die schon auf der Platte liegen, der pro Locale den aktuellen Quell- und Zieltext jedes Keys
zurückgibt. Greif darauf zurück, wenn ein Aufrufer Übersetzungsinhalte statt Key-Namen durchsuchen
oder scannen muss.

```ts
import { loadConfig, localeValues } from "@verbatra/sdk";

const report = await localeValues({ config: await loadConfig(), locales: ["de", "fr"] });

for (const { locale, values } of report) {
  for (const [key, pair] of Object.entries(values)) {
    if (pair.source === undefined) {
      console.warn(`${locale}/${key}: orphaned, no source key any more`);
    } else if (pair.target === undefined) {
      console.warn(`${locale}/${key}: not translated yet`);
    } else if (pair.target.includes("TODO")) {
      console.log(`${locale}/${key}: ${pair.target}`);
    }
  }
}
```

Nur lesend: Es ruft keinen Provider auf, schreibt nichts und berührt weder die Lock-Datei noch den
Cache. Lass `locales` weg, um jede konfigurierte Ziel-Locale abzudecken.

## Der Arbeitsmappen-Roundtrip

Exportiere die zu übersetzenden Strings in eine Excel-Arbeitsmappe, gib sie an eine Übersetzerin,
dann importiere die ausgefüllte Datei zurück. `importWorkbook` führt dieselben Drift- und
Integritätsprüfungen aus wie `translate` und gibt dieselbe `RunSummary`-Form zurück; eine
manuelle Übergabe fügt sich also in exakt das Reporting ein, das du für einen automatischen Lauf
nutzt.

```ts
import { exportWorkbook, importWorkbook, loadConfig } from "@verbatra/sdk";

const config = await loadConfig();

// Write a workbook of the missing and changed strings.
const exported = await exportWorkbook({ config });
for (const sheet of exported.locales) {
  console.log(`${sheet.locale}: ${sheet.rows} rows`);
}
console.log(`wrote ${exported.path}`);

// ...later, after the translator returns the file, import it back.
const summary = await importWorkbook({ config, workbook: exported.path });
console.log(`${summary.succeeded.length} locales ok, ${summary.failed.length} failed`);
```

Übergib `dryRun: true` an `importWorkbook`, um eine zurückgekommene Datei zu validieren, ohne
etwas zu schreiben. Was Übersetzerinnen bearbeiten dürfen und wie Zeilen validiert werden, steht
in [Menschliche Übersetzung](/docs/manual-translation).

## Der TMX-Roundtrip

<AvailableFrom version="0.11.0" />

`importTmx` und `exportTmx` bewegen den [Übersetzungsspeicher](/docs/the-cache) in TMX hinein und
wieder heraus, in das Austauschformat, das die gängigen Übersetzungsplattformen erzeugen und lesen.
Das ist nicht das Arbeitsmappen-Paar in einem anderen Format: Die Arbeitsmappe gibt das ausstehende
Delta einer Locale an eine menschliche Übersetzerin, dieses Paar bewegt den ganzen
Übersetzungsspeicher als eine mehrsprachige Datei zwischen Werkzeugen.

```ts
import { exportTmx, importTmx, loadConfig, tmxErrorLocation } from "@verbatra/sdk";

const config = await loadConfig();

// Validate another tool's file before it touches the memory.
try {
  const preview = await importTmx({ config, file: "legacy.tmx", dryRun: true });
  console.log(`${preview.units} units, source language ${preview.sourceLanguage ?? "undeclared"}`);
  for (const locale of preview.locales) {
    console.log(
      `${locale.locale}: +${locale.added}, kept ${locale.kept}, conflicting ${locale.conflicting}`,
    );
  }

  // Then land it. Pass overwrite: true to let the file win where the two disagree.
  const landed = await importTmx({ config, file: "legacy.tmx" });
  if (!landed.memoryWritable) {
    console.error("the memory file was written by a newer verbatra and was left untouched");
  }
} catch (error) {
  const at = tmxErrorLocation(error);
  if (at === undefined) {
    throw error;
  }
  console.error(`legacy.tmx is malformed at line ${at.line}, column ${at.column}`);
}

// ...and hand this project's memory to another tool.
const exported = await exportTmx({ config, out: "out/memory.tmx" });
console.log(`${exported.units} units to ${exported.path}`);
```

Keines von beiden konstruiert einen Provider, liest einen API-Key oder macht einen
Netzwerkaufruf. `importTmx` meldet beschädigte Daten, statt bei ihnen zu werfen: Eine abgelehnte
Datei löst `SOURCE_INVALID` aus, und `tmxErrorLocation` liest die Stelle aus diesem Fehler, ohne
ihn oder sein `cause` zu casten. Exportiert werden nur Einträge unter dem aktuellen
Konfigurations-Fingerprint, also genau die Menge, die ein Lauf wiederverwenden würde.

## Eine Konfiguration ohne Datei

`loadConfig` akzeptiert ein `configOverride` im Speicher, das genau wie eine geladene Datei
validiert wird; du kannst verbatra also komplett aus Code heraus steuern, ganz ohne
Konfigurationsdatei auf der Platte.

```ts
import { loadConfig, translate } from "@verbatra/sdk";

const config = await loadConfig({
  configOverride: {
    sourceLocale: "en",
    targetLocales: ["de", "fr"],
    format: "i18next-json",
    files: { pattern: "locales/{locale}.json" },
    provider: { id: "gemini", options: { model: "gemini-2.5-flash", maxOutputTokens: 4096 } },
  },
});

await translate({ config });
```

Jede Eingabeform, die vollständige `RunSummary`-Anatomie und die `SdkError`-Code-Tabelle stehen in
der [SDK-Referenz](/docs/sdk).
