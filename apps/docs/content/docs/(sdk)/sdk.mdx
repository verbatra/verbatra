`@verbatra/sdk` is the engine the `verbatra` command runs on. The CLI is a thin wrapper, so whatever
the command line does, you can do in code. This page catalogs the whole public surface, grouped by
the job each entry point does. For end-to-end examples, see [SDK recipes](/docs/programmatic-api).

## Install

```npm
npm install --save-dev @verbatra/sdk
```

Requires Node.js `>=22.14.0`.

The pnpm line installs correctly but exits `1` with `ERR_PNPM_IGNORED_BUILDS`: pnpm gates the
install scripts of the bundled Gemini SDK and its `protobufjs`, and leaves an unanswered
`pnpm-workspace.yaml` behind that makes every later pnpm command in the project fail the same way.
Run `pnpm approve-builds` once and approve neither entry, or see
[Troubleshooting](/docs/troubleshooting) for the non-interactive fix. There is no `npx` shortcut
around this the way there is for the CLI, because you are importing a library, not running a
binary.

<Callout title="API keys and the environment">
The SDK never reads, holds, or accepts an API key. The provider reads its key from the environment
(for example `ANTHROPIC_API_KEY`) when it is constructed. Unlike the CLI, the SDK does not load
`.env` files: in your own script, set the variable yourself, for example with
`node --env-file=.env script.js`.
</Callout>

Every entry point takes one input object whose first field is the validated `config` (from
`loadConfig`), except where noted. Most also accept an optional second `deps` argument that injects
a registry, provider builder, or file system; you can ignore it in normal use. See
[The dependency seam](#the-dependency-seam) for what `deps.fs` reaches.

## Run translations

### translate

The one-shot flow: read the source, diff each target locale against the lock baseline, send the
missing and changed keys to the provider, run the integrity checks, write the
locale files, and update the lock. Use it for scripts, build steps, and CI jobs.

Input: `{ config, cwd?, locales?, dryRun?, estimate?, prune?, generatePlurals?, concurrency?, cache?, humanEdits?, maxTokens?, onProgress?, onLockWait?, lockAcquireTimeoutMs? }`.

- `locales` restricts the run to a subset of the configured target locales, exactly as on `check`
  and `diff`. A locale that is not configured throws `UNKNOWN_LOCALE` before anything is read or
  spent. Omit it to cover every target locale.
- `dryRun` reads, diffs, and reports without constructing or calling the provider and without
  writing anything.
- `estimate` adds a pre-run cost estimate on `RunSummary.estimate` and implies `dryRun`, so it
  constructs no provider, reads no API key, and writes nothing. The quantity is always reported; a
  currency figure needs a `rates` block in the config naming the configured provider and model.
- `prune` removes orphaned keys (target keys absent from source) from the written file and the
  lock. `generatePlurals` synthesizes missing CLDR plural forms (i18next-JSON with an LLM provider
  only). Both default to off; when set, each overrides the matching config option for that run.
- `concurrency` runs up to that many target locales at once (default 1, strictly serial). A value
  below 1 throws `CONCURRENCY_INVALID`; on a live run a value above 1 with a `maxTokens` budget
  throws `CONCURRENCY_BUDGET_CONFLICT` (a dry run is exempt). A whole-run error raised once locales
  are already running stops any further locale from being started, and the locales in flight finish
  and release their write locks before `translate` rejects, so the rejection arrives after the
  slowest one rather than instantly.
- `cache` defaults to true and reuses the local [translation-memory cache](/docs/the-cache)
  (`verbatra.cache.json`, also exported as `CACHE_FILE_NAME`); set it to false to bypass the cache
  for the run (the CLI's `--no-cache`).
- `humanEdits` overrides the config's `humanEdits` for this run: `"overwrite"` also retranslates stale keys whose value a person wrote, imported, or changed outside verbatra (the CLI's `--include-human`). By default such keys are kept and listed in `LocaleSummary.protected`; keys matching `pinnedKeys` stay protected whatever this says. See [Protecting human translations](/docs/protecting-human-translations). A dry run now reads `verbatra.provenance.json` too, unless `humanEdits` resolves to `"overwrite"`.
- `onProgress` is called as the run advances (per locale start and finish, and per provider
  sub-batch), and `onLockWait` fires while a locale's write lock is contended. Both are
  notification callbacks; the SDK writes no output itself. `lockAcquireTimeoutMs` overrides how long
  a contended write lock retries before failing with `LOCK_CONTENDED`. It bounds only the per-locale
  write lock taken before any provider call; the lock-file guard taken to record a locale whose file
  is already written always allows the ten-minute default, so a written file is never left
  unrecorded. `onLockWait` fires first once a wait has lasted a second, and never for a lock the
  same process holds, such as the guard a sibling locale holds with `concurrency` above 1.
- `maxTokens` (from 0.12.0) sets a token ceiling for this run alone (the CLI's `--max-tokens`). It
  always acts as `budgetBehavior: "stop"`, and when the config also sets `maxTokens` the lower of the
  two applies, so it can tighten the configured budget but never loosen it. A value that is not a
  whole number of at least 1 throws `MAX_TOKENS_INVALID`, and like a configured budget it cannot be
  combined with a `concurrency` above 1 on a live run.
- `maxBatchSize` and `budgetBehavior` are config-only; there is no per-run override.

Returns a `RunSummary` (see [its anatomy below](#the-runsummary-anatomy)). Whole-run problems throw
an `SdkError`; a single locale failing never throws and lands as `status: "failed"` on that
locale's entry while the run continues.

### resolveDryRun

<AvailableFrom version="0.11.0" />

Answers whether a set of run options resolves to a dry run. It takes the `dryRun` and `estimate`
you are about to hand `translate` and returns whether that run will construct a provider, write a
file, or spend anything. This is the one place the rule that `estimate` implies `dryRun` is
decided, so reach for it whenever something around a run has to know in advance rather than
restating the implication and drifting from it.

```ts
import { resolveDryRun, translate } from "@verbatra/sdk";

const options = { dryRun: false, estimate: true };
resolveDryRun(options); // true

const summary = await translate({ config, ...options });
```

### watch

Watches the source locale file and re-runs `translate` on every debounced change. It fires one
initial run immediately at startup, then one run per settled change. Runs are serialized: changes
during a run collapse into a single follow-up.

Input: `{ config, cwd?, locales?, debounceMs?, onRun, concurrency?, cache?, onProgress?, onLockWait?, lockAcquireTimeoutMs? }`.
`debounceMs` defaults to 300. `onRun` is called once per run with a `WatchRunResult`:
`{ status: "succeeded", summary }` or `{ status: "failed", error: { code, message } }`. The SDK does
no logging; `onRun` is the only output. `concurrency`, `cache`, `onProgress`, `onLockWait`, and
`lockAcquireTimeoutMs` are passed through to every run and behave exactly as on `translate`.
`locales` narrows every run of the session to that subset and is validated once at startup, not per
cycle.

Returns a `WatchController` with one method, `stop()`, which closes the watcher and awaits the
in-flight run. Three problems are refused at startup, before the watcher exists, so `watch` itself
rejects rather than returning a controller: a `concurrency` that is not an integer of at least 1
throws `CONCURRENCY_INVALID`, a `concurrency` above 1 against a config that sets `maxTokens` throws
`CONCURRENCY_BUDGET_CONFLICT` (there is no dry-run watch, so the budget conflict always applies),
and a missing source file throws `SOURCE_UNREADABLE`. Every failure after startup is surfaced
through `onRun` and watching continues.

### releaseHeldLocks

<AvailableFrom version="0.12.0" />

Deletes every write lock the current process holds, for a process about to exit without letting
its in-flight runs finish: the CLI calls it when an interrupt stops `translate` or `import`, and
when a second interrupt force-stops `watch`. The runs that took those locks lose their protection,
so call it only immediately before the process exits. It takes no arguments and never rejects.

A lock left behind anyway, by a process killed outright, does not need it: a waiting run on the
same machine sees that the recorded process is gone and reclaims the lock itself. See
[the write lock](/docs/the-lock-file#the-write-lock).

## Pseudolocalization

### pseudolocalize

<AvailableFrom version="0.11.0" />

Builds a fake locale from the source strings alone, so layout truncation and strings that were
never extracted for translation show up before any API key exists. Every value is accented,
expanded by roughly a third of its translatable length, and wrapped in `[` and `]` boundary
markers, while placeholders stay untouched in every syntax the adapters recognise, including ICU
plural and select arms, markup tags, and escape sequences. It constructs no provider, reads no API
key, and makes no network request.

Every generated value is held to the same integrity gate a provider translation must pass. One
that would not pass it is copied from the source verbatim and named in `copied` rather than written
in a broken form, so the entry is still present and still renders.

Input: `{ config, cwd?, locale?, out? }`. `locale` defaults to `en-XA` and `out` to
`.verbatra-local/pseudo`, which `verbatra init` already adds to `.gitignore`; the configured
`files.pattern` is expanded inside it, so the file keeps the layout the application expects. A
pseudolocale that names a configured locale, or that would land on a configured locale file, is
refused with `PSEUDO_OUTPUT_CONFLICT` before anything is read or written, so it can neither
overwrite a real translation nor stand in for one; so is an `out` that is absolute, climbs out of
`cwd`, or names `cwd` itself, such as `.`, and, when `deps.fs` implements `realpath` as the
default does, one that does any of this, lands in the directory of a configured locale file, or
lands on another file the project depends on, once symbolic links are resolved. Because the file lives outside `files.pattern`,
`translate` never spends on it and `check` and `diff` never report it as drifted.

Returns a `PseudolocalizeResult`: the `locale`, the absolute `path`, how many `entries` were
processed, how many were `transformed`, the keys that were `copied`, and whether anything was
`written`. The transform is deterministic, so a second run over unchanged source rewrites nothing
and reports `written` as false. For `xliff` and `apple-xcstrings`, whose writers only patch a
document that already exists, the output is re-copied from the source on every write, so a key
added to the source after the first run still reaches the pseudolocale, and a copied XLIFF has its
`target-language` rewritten to the pseudolocale.

## Typed catalogs

### generateTypes

<AvailableFrom version="0.11.0" />

Declares a project's source catalog as TypeScript: a union of every key it holds and, per key, the
arguments its message interpolates. Type a translation function against the result and a misspelled
key or a missing interpolation argument becomes a compile error instead of a runtime lookup failure.
It spends nothing: no provider is constructed, no API key environment variable is read, and no
network request is made.

It reads one file (the source locale catalog) and writes one file (the declaration); a target locale
file is never touched. The keys are exactly what the format adapter already produced, in document
order, so two runs over an unchanged catalog write byte-identical bytes. Arguments come from the
placeholder tokens the adapter extracted, except in the ICU message formats (`next-intl-json` and
`arb`), where each message is read with the same ICU parser the adapter uses. Every key is emitted
as a quoted string literal, so one carrying a dot, a reserved word, a leading digit, a quote, or
nothing at all is declared verbatim rather than dropped or re-split, and a key the adapter reported
in `excludedLeafPaths` is never declared at all.

What it declines to claim matters as much as what it declares. A message with no placeholders gets a
shape that makes passing any argument a type error; one whose placeholders name their arguments gets
an object shape; one whose placeholders are numbered or anonymous gets a readonly tuple. An ICU
argument only some `select` or `plural` branches use is declared as an optional member. Argument
types come only from what the catalog records: `number` for an ICU `number`, `plural` or
`selectordinal` argument and for a numeric formatter or conversion, `Date | number` for an ICU
`date` or `time` argument and an i18next `datetime` formatter, `string` for an ICU `select` argument
and a printf string conversion, and a `string | number` alias everywhere else, never a permissive
`any`. An i18next unescaped interpolation (`{{- name}}`) is declared by the name behind its prefix.
A message the adapter reported as invalid, one that appears to both name and number its arguments,
and one whose placeholder index is out of range are declared with their arguments reported in
`unresolved` rather than silently declared as taking none. Plural siblings are never collapsed: each
is declared on its own, and the ones the adapter marked plural are listed.

Input: `{ config, cwd?, out?, configPath?, glossaryPath?, check? }`. `out` defaults to
`DEFAULT_TYPES_PATH` (`verbatra-types.d.ts`). Before anything is read or written,
`TYPES_OUTPUT_CONFLICT` refuses an `out` that names no file (including one ending in a path
separator), is absolute, climbs out of `cwd` with `..`, names `cwd` itself (`.`), or does not end
in `.ts`, `.mts` or `.cts`,
and one naming a configured locale file, the lock file, the provenance file, the translation-memory cache, a file
verbatra searches for its configuration, `configPath`, the configuration file `config` was loaded
from, or `glossaryPath`, the glossary file it names; names are compared case-insensitively, and when
`deps.fs` implements `realpath`, as the default does, the same checks run again on where the path
lands once symbolic links are resolved. A generating run also refuses, with the same code, to
replace an existing file that does not begin with the header line verbatra writes, and leaves that
file untouched. The full list is on the [`verbatra types`](/docs/cli/types) page. With `check` set
nothing is written at all, nothing is refused for its content, and the run only reports whether the
committed file still matches, which is the shape a CI gate wants.

Returns a `GenerateTypesResult`: the absolute `path`, the `sourcePath` it was built from, how many
`keys` were declared and how many of those take at least one argument verbatra could determine
(`withArguments`, which never counts an `unresolved` key), the `unresolved` keys and the `excluded`
and `plural` ones, whether anything was `written`, whether the file on disk was `stale` when the run
started, and whether this was a `check` run.

## Inspect state without writing

None of these call a provider, write a file, or mutate the lock.

### doctor

<AvailableFrom version="0.9.0" />

Validates the project setup and spends nothing: it constructs no provider, makes no network
request, and never reads an API key value. Nine checks run, each with its own `pass`, `fail`, or
`skipped` verdict. Five cover the basics: the config loads and validates, the configured format resolves to an adapter,
the configured provider ID resolves to a factory, the environment variable that provider reads its
key from is set, and the source locale file can be read. Every check runs even when an earlier one
failed, so one call reports every independent problem. The API key is checked by name only. The
source-file check reads and parses the file rather than only probing for it, so a directory in its
place, an empty file, and malformed content are all reported here.

<AvailableFrom version="0.12.0" />

The `network-policy` check passes when the effective [network policy](/docs/network-policy),
from the config's `network` block and the `VERBATRA_NETWORK_POLICY` environment variable, permits
the host the configured provider connects to and any proxy it would use. Its detail names the
policy, both of its sources, and the host. It fails when that host is refused or a network
environment variable holds an invalid value, passes for the `none` provider, and resolves no host
name.

The `plural-rules` check is informational and always passes: its detail names the ICU and
CLDR versions the runtime derives each target language's plural categories from, and any target
locale ICU has no plural rules for.

The `locale-codes` check is informational too and always passes: its detail names every
configured locale code that is valid but not in canonical BCP 47 form, such as `zh-hant-tw` or the
deprecated `iw`, with the canonical form `Intl.getCanonicalLocales` suggests. Nothing is renamed.

The `locale-state` check is informational too and always passes: its detail names every
locale the lock file, the translation memory, or the provenance file holds state for that the config
does not list, such as `pt_BR` left behind after a respelling to `pt-BR`, and says whether the next
`translate` run carries it over. A file it cannot read is named in the detail.

Input: `{ cwd?, configPath?, literals? }`. With `literals` set, `doctor` runs only the `config`
check and an `untranslated-literals` check instead, scanning the source roots of the config's
`extract` block, as [`verbatra doctor --literals`](/docs/cli/doctor#untranslated-literals) does. No
loaded config needed: `doctor` loads it itself, so a project with no config at all still gets a
report rather than a thrown error. Returns a `DoctorResult` whose `ok` is true exactly when no
check failed. It throws `CONFIG_NOT_FOUND` only for an explicit `configPath` that does not exist.

### extract

<AvailableFrom version="0.11.0" />

Scans your application source for translation call sites and merges what it finds into the source
locale catalog. It is the one entry point that reads application code rather than a locale file,
which is what makes verbatra usable on a project that has no catalog yet. It spends nothing: no
provider is constructed, no API key environment variable is read, and no network request is made.

Only the source locale file is ever written, and only genuinely new keys are added: a key already
in the catalog keeps its value exactly as it stands, and a key in the catalog that no call site
mentions is left alone. A run that finds nothing new writes nothing at all. Everything the scan
cannot resolve comes back as data rather than thrown: a non-static key argument in `dynamic`, a key
found with two different defaults in `conflicts` (neither value is written), and an unreadable file
in `diagnostics`. The result carries keys, values, and file and line locations only, never a source
file's contents.

Input: `{ config, cwd?, dryRun? }`, where `config.extract` names the framework and the source roots.
Returns an `ExtractResult`. Discovery goes through the optional `readDirectory` member of `SdkFs`;
a `deps.fs` without it is reported as `EXTRACT_FS_UNSUPPORTED`.

### check

Reports per-locale drift as counts: `missing` (in source, absent from target), `stale` (source
changed since last translated), and `upToDate`. Use it as a CI gate.

Input: `{ config, cwd?, locales?, consistency?, qa?, qaSeverity? }`. Returns a `CheckSummary` whose `inSync` is true
exactly when every checked locale has nothing missing and nothing stale.

<AvailableFrom version="0.11.0" />

With `consistency: true`, each `LocaleCheckSummary` also carries `inconsistencies`: one
`InconsistencyGroup` per source string the locale translates more than one way under different
keys, naming the `source`, every distinct translation as `{ value, keys }`, and the `context`,
`description`, `meaning`, `isPlural`, and `pluralForm` the grouped keys share. Only up-to-date keys
are compared, values are compared after NFC normalization and trimming surrounding whitespace, keys
whose description, meaning, plural flag, or gettext `msgctxt` differ are never grouped, and plural
forms stored under their own keys are compared per form. It is a report only: it never changes
`inSync`, a count, or any file, and it calls no provider.

<AvailableFrom version="0.12.0" />

Each `LocaleCheckSummary` also carries `provenance`: counts `byOrigin` and `byReviewState` over the
keys the locale has a value for, read from `verbatra.provenance.json`. See
[The lock file](/docs/the-lock-file#provenance-who-wrote-each-value) for what each origin means.
This and every other provenance field in a report is left out, never an error, when the file is
corrupt or was written by a newer verbatra.

<AvailableFrom version="0.12.0" />

Each `LocaleCheckSummary` also carries `protected`, how many of its missing and stale keys a `translate` run would leave for a person under the config's `humanEdits` and `pinnedKeys`. They still count as missing or stale, so `inSync` stays false until a person resolves them. When `verbatra.provenance.json` is corrupt or from a newer verbatra, no origin can be read and only pinned keys are counted.

<AvailableFrom version="0.12.0" />

With `qa: true`, `check` also runs the quality check over every committed value, keyless and
without writing anything: each `LocaleCheckSummary` carries a `qa` report of
`{ checked, errors, warnings, findings }`, and the summary carries `qa` totals of
`{ errors, warnings, invalidSourceKeys }`. A finding is `{ key, severity: "error", reason, details? }`
for a value the integrity gate would refuse (`reason` from `INTEGRITY_GATE_REASONS`), or
`{ key, severity: "warning", reason }` for a value that passes but carries a review reason from
`REVIEW_REASON_CODES`. `qaSeverity: "error"` skips the review reasons. The severities are published
as the `QA_SEVERITIES` tuple (`"error"`, `"warning"`). The report never changes `inSync`; a CI gate
reads `qa.errors`, and `qa.warnings` for a strict gate. See
[the quality check](/docs/cli/check#quality-check) for which values are checked.

### diff

The detailed sibling of `check`: the same computation, but it returns the key lists per locale
(`missing`, `changed`, `orphaned`) instead of counts. Orphaned keys are report-only and never flip
`hasPendingChanges`, since a default run does not prune.

With `unused: true` it also scans the roots of the config's `extract` block and adds an `unused`
report, separate from every `orphaned` list: the source-locale keys no static reference names, in
catalog order. It is read-only and keyless, and it models the i18next runtime (`t` calls and their
aliases, static `keyPrefix` and `getFixedT` prefixes, `Trans` keys, namespace-qualified keys, and
plural and context variants), comparing keys in the catalog format's encoding. Each listed key
carries its decoded `key` and its `catalogKey`. Keys matched by `extract.unused.ignore` land in
`ignored`, and keys a template literal with a static head could reach land in `possiblyDynamic`. Its
`status` is `complete`, `unreliable` (with `unreliableBecause` naming each reason with its sites),
or `not-run` (with a `reason` and no key list). See [Unused source
keys](/docs/cli/diff#unused-source-keys) for every reason. The report never flips
`hasPendingChanges`.

Input: `{ config, cwd?, locales?, unused? }`. Returns a `DiffSummary`.

<AvailableFrom version="0.12.0" />

Each `LocaleDiff` also carries `changedOrigins`, the interpreted origin of each `changed` key's
current value (for example `machine`, `human`, or `external`), so you can see whose work a
retranslation would replace before you run it.

<AvailableFrom version="0.12.0" />

Each `LocaleDiff` also carries `protected`, the missing and changed keys a `translate` run would leave alone, sorted. They still count as pending. When the provenance file is unreadable, only pinned keys are listed.

### keyIntegrity

Reports, for each locale's changed keys, whether the current target value still matches the source's
placeholders, whether it still carries the source's inline markup, and whether it is valid ICU. Each
entry carries `key`, `hasPlaceholders`, `matches`, the `missing` and `extra` placeholder tokens on a
mismatch, `icuValid`, `markupMatches`, and `markupDetails` naming the tags behind a markup mismatch.
Entries never carry a source or target string value. Reporting markup here is what makes drift that
predates the write-time gate visible: a translation written before the check existed, edited outside
verbatra, or produced by a path that never crossed the gate is judged here by the same rule. This is
the per-key integrity report Studio surfaces.

<AvailableFrom version="0.12.0" />

Each entry also carries `icuArmsMatch` and `icuArmDetails`: whether the value's ICU `plural`,
`selectordinal`, and `select` arms fit the target language, judged exactly as the write-time gate
judges them, and one short problem per missing or extra arm, such as `{count} plural: missing arm
"few" required by the target language`. `icuArmsMatch` is always true for a format that does not
check arms (every shipped format except next-intl and ARB).

Input: `{ config, cwd?, locales?, keys? }`. `keys` narrows the check; only keys that are "changed"
for a locale are ever checked. Returns one `LocaleKeyIntegrity` per checked locale.

### lockState

Reports the lock file's existence, version, and per-locale drift (baseline key count plus missing,
stale, and up-to-date counts). `exists` comes from an explicit probe, so "no lock file yet" and "an
empty but present lock file" stay distinguishable. When the file is absent the result is
`{ exists: false }` and nothing else is read.

Input: `{ config, cwd?, locales? }`. Returns a `LockStateResult`.

Each locale also carries the same `provenance` counts `check` reports.

### loadLockFile

Reads the lock file itself (`verbatra.lock.json`, also exported as `LOCK_FILE_NAME`) and returns
its parsed shape: `{ version, locales }`, where each locale maps keys to the source content hash
they were last translated from. A missing file degrades to an empty lock, the same first-run
behavior `translate` relies on; use `lockState` when you need to distinguish absence.

Input: `{ cwd? }`. No config needed. Returns a `LockFile`.

### loadProvenance

<AvailableFrom version="0.12.0" />

Reads the provenance file itself (`verbatra.provenance.json`, also exported as
`PROVENANCE_FILE_NAME`) and returns its stored shape: `{ version, locales }`, where each locale maps
keys to a record `{ origin, provider?, model?, valueHash, reviewState?, reviewer?, reviewedSourceHash? }`. It holds no
translated text. A missing file, or one written by a newer verbatra, reads as empty; a corrupt one
throws `PROVENANCE_FILE_INVALID`. `keyValue`, `localeValues`, `check`, `diff`, and `lockState`
already report the interpreted view (`KeyProvenance`), which also tells a value with no record
(`unrecorded`) from one edited outside verbatra since it was recorded (`external`).

Input: `{ cwd? }`. No config needed. Returns a `ProvenanceFile`.

### runStatus

Reads the review-flag and token-usage snapshot the most recent non-dry-run `translate` or `watch`
run persisted to `.verbatra-local/run-status.json`. Never throws: a missing, corrupt, or
unrecognized file degrades to `{ available: false }`. This file is best-effort telemetry, not a
correctness baseline.

Input: `{ cwd? }`. No config needed. Returns `{ available: false }` or
`{ available: true, version, generatedAt, usage?, budget?, locales }`.

A snapshot written by a release from before the token budget was enforced is still read, but its
`budget` is left out when it says `supported: false`: back then that meant nothing was counted, so
its `tokensUsed: 0` is not a count. Snapshots written now keep the same `version` and only add a
marker field that an older Studio or agent server ignores, so an older reader keeps showing the
review queue and usage. Until it is upgraded, it may show an estimated budget as not tracked.

### reviewQueue

<AvailableFrom version="0.12.0" />

Reads the review queue: the keys the last run flagged (the `runStatus` snapshot), minus every key
dealt with since. A flag leaves the queue once its current value is approved or rejected in
`verbatra.provenance.json`, once a person wrote or imported a new value for it, or once it has no
translation any more; a value an agent rewrote stays. Because the decisions come from committed
files, a teammate with the same run status sees the same queue. Never throws: an unusable status
file gives `{ available: false }`, an unreadable provenance file leaves the flags unnarrowed, and a
locale whose file cannot be read keeps its flags as recorded.

Input: `{ config, cwd? }`. Returns the `runStatus` shape, with each `needsReview` entry also
carrying `provenance`, the `KeyProvenance` of its current value, when the provenance file is
readable.

## Single-key operations

These are the seams Verbatra Studio drives; use them to build your own review tooling. All of them
resolve `locale` and `key` fresh on every call and throw `UNKNOWN_LOCALE` or `UNKNOWN_KEY` when
either does not exist.

### keyValue

Reads one key's current source value and, when present, its current target value for one locale.
Read-only.

Input: `{ config, cwd?, locale, key }`. Returns `{ source, target? }`; `target` is absent exactly
when the key does not yet exist in that locale.

When `target` is present the result also carries `provenance`, the key's interpreted
`KeyProvenance`: `{ origin, provider?, model?, reviewState, reviewer? }`.

### editEntry

Writes one human-typed correction for one key and locale. The candidate value passes the same
integrity gate as a provider translation before anything reaches disk; on acceptance the
locale file and the lock entry for that key are updated inside the locale's write lock. Never
calls a provider.

Input: `{ config, cwd?, locale, key, value }`. Returns a two-armed result:
`{ accepted: true, value }`, or
`{ accepted: false, reason: "placeholder" | "markup" | "icu" | "degenerate" | "empty", value }` with
nothing written. `"empty"` covers an empty or whitespace-only value for a source that has text: an
edit cannot express clearing a key, so use the workbook's `[[CLEAR]]` sentinel for that. The reason
set is published as the `INTEGRITY_GATE_REASONS` tuple, so build any runtime schema or exhaustive
lookup from it rather than retyping the members. A `placeholder` or `markup` refusal also carries
`details`: the placeholders or tags behind it, each prefixed with `-` for one the source had and
the candidate dropped or `+` for one the candidate invented.

The written value is recorded in `verbatra.provenance.json` with the origin `human`. Pass
`actor: "agent"` when an AI agent wrote the value, so the record says so; the calling surface
asserts it and nothing verifies it. The provenance file is checked before the value is gated: a
corrupt one throws `PROVENANCE_FILE_INVALID` and nothing is written, and one from a newer verbatra,
or one the record would grow past the size verbatra reads back, is left untouched while the value
is written without a record.

<AvailableFrom version="0.12.0" />

With `actor: "agent"`, a key matching the config's `pinnedKeys` throws `KEY_PINNED` before anything is read or written. A person's edit of a pinned key is accepted.

### retranslateEntry

Re-runs the provider for exactly one key and locale: a single-entry call through the same provider
path `translate` uses, gated through the same integrity checks. On acceptance it writes the
locale file and lock entry for that key only.

Input: `{ config, cwd?, locale, key, includeHuman? }`. Returns `{ accepted: true, value, reviewReasons }` (the
review reason codes, if any, that apply to the new value) or
`{ accepted: false, reason: "placeholder" | "markup" | "icu" | "degenerate" | "empty", value }`.
Unlike `translate`, a provider failure here throws: a `ProviderError`, exported from `@verbatra/sdk`,
with a stable `code` such as `RATE_LIMITED` or `AUTH_FAILED`. Under `provider: { id: "none" }` it throws `MACHINE_TRANSLATION_DISABLED` first, before reading or locking anything.

The new value is recorded in `verbatra.provenance.json` as `machine`, with the `id` of the provider
that answered and the configured model. A provider from your own `createProvider` is recorded
under its own `id`, and without the model when that `id` differs from the configured one. A corrupt provenance file throws `PROVENANCE_FILE_INVALID` before the provider is called.

<AvailableFrom version="0.12.0" />

A key whose current value a person wrote, imported, or changed outside verbatra throws `KEY_PROTECTED` inside the write lock, before the provider is called, unless `includeHuman: true` is passed or the config sets `humanEdits: "overwrite"`. When the provenance file is from a newer verbatra, any existing value counts as protected. A key matching `pinnedKeys` throws `KEY_PINNED` before the provider is constructed, even with `includeHuman`.

### approveEntry

<AvailableFrom version="0.12.0" />

Records that a person reviewed one key's current value in one locale and accepts it. It writes only
`verbatra.provenance.json`, never a locale file or the lock file, and calls no provider. The
approval also stores the lock file's source hash for the key, so it reads as unreviewed again once
the source changes; any later write that changes the value starts a fresh, unreviewed record.

Input: `{ config, cwd?, locale, key, expectedValue, reviewer? }`. `expectedValue` is the text the
reviewer saw: the call throws `REVIEW_VALUE_CHANGED` when the key has no value or a different one,
and `REVIEW_SOURCE_CHANGED` when the source changed since the value was written. `reviewer` is
optional free text of at most 64 characters with no control characters (`REVIEWER_INVALID`
otherwise), stored in the committed file and never filled in by verbatra. Returns
`{ locale, key, provenance }`. A value with no record yet, or one changed outside verbatra, is
recorded with the origin `unknown`.

### rejectEntry

<AvailableFrom version="0.12.0" />

Records that a person reviewed one key's current value in one locale and refuses it, and removes
that value so it gets replaced. The key is dropped from the locale file and its lock entry is
removed, so `check` and `diff` report it as missing and the next `translate` fills it again (under
`provider: { id: "none" }` it stays missing until someone writes a value). The provenance record is
kept as `rejected` with a hash of the removed text, and the matching translation-memory entry on
this machine is dropped. A later `translate` skips any exact or fuzzy memory hit for the key whose
text matches that hash, so another machine's memory cannot bring the text back either. Calls no
provider.

Input: `{ config, cwd?, locale, key, expectedValue, reviewer? }`, checked like `approveEntry`
except that a stale source does not block a rejection. Returns `{ locale, key, provenance }`. A
format that keeps a key it was not given, XLIFF, throws `REVIEW_REJECT_UNSUPPORTED` after
restoring the file.

Both calls check the provenance file before anything is written and never report a decision they
could not save: a file from a newer verbatra, or one the decision would grow past the size verbatra
reads back, throws `PROVENANCE_FILE_UNWRITABLE`.

## Batch review and retranslation

<AvailableFrom version="0.12.0" />

Each of these runs the matching single-key call once per entry, in the order given, and returns
`{ results }` with one outcome per entry in that order. An entry that fails does not stop the
batch: its outcome is `{ locale, key, ok: false, code, message }`, carrying the code of the
`SdkError`, adapter error, or `ProviderError` that stopped it and a redacted message, and the next
entry runs. Any other error is thrown, and the entries after it do not run. An empty `entries` list
returns an empty `results`.

### approveEntries

Input: `{ config, cwd?, entries: [{ locale, key, expectedValue }], reviewer? }`. Runs `approveEntry`
per entry with the same checks; `reviewer` applies to every entry. A successful outcome is
`{ ok: true, locale, key, provenance }`.

### rejectEntries

Input: the same as `approveEntries`. Runs `rejectEntry` per entry, removing each rejected value. A
successful outcome is `{ ok: true, locale, key, provenance }`.

### retranslateEntries

Input: `{ config, cwd?, entries: [{ locale, key }], includeHuman? }`. Runs `retranslateEntry` per
entry, so it makes up to one provider call per entry. A completed outcome is
`{ ok: true, locale, key, result }`, where `result` is what `retranslateEntry` returned, including a
value the integrity gate refused. A value a person wrote fails with `KEY_PROTECTED` unless
`includeHuman: true` is passed.

## Bulk content reads

<AvailableFrom version="0.10.0" />

### localeValues

Reads every key's current source and target text, across every requested target locale, in one
pass over the files already on disk. It is the bulk counterpart to `keyValue`: use it when a
caller needs translation content in bulk, for instance to search or scan values rather than key
names, since `keyValue` only answers for one key at a time. Read-only.

Input: `{ config, cwd?, locales? }`; an omitted `locales` covers every configured target locale.
Returns an array of `{ locale, values }`, one entry per locale, where `values` maps each key to
`{ source?, target? }`. An absent `target` means the key has not been translated in that locale
yet; an absent `source` means the key is orphaned, present in the target locale but no longer in
the source. `values` has no prototype, so every key, including one named `__proto__` or
`constructor`, is an own property, and a key absent from the catalog reads as `undefined`.

Each pair with a `target` also carries `provenance`, the same `KeyProvenance` `keyValue` reports.

## Locale-file snapshots

The building blocks of a live-refresh watcher such as Studio's: capture a locale file's state, then
count what changed since.

### readLocaleFileSnapshot

Reads one locale file (the source locale or any target locale) and reduces it to a content hash per
key. A file that does not exist yet reads as an empty snapshot rather than throwing.

Input: `{ config, locale, cwd? }`. Returns `{ locale, hashes }`.

### diffLocaleSnapshots

Compares two snapshots of the same file, taken at different times, and counts the keys added,
changed, and removed between them. A plain synchronous function: `diffLocaleSnapshots(previous,
current)` returns `{ added, changed, removed }`. Counts only, never key names.

## Locale paths

### createLocalePathResolver

Resolves the project's locale-to-path mapping in both directions, from `files.pattern`, the
configured locales, and `files.localeStyle`. `createLocalePathResolver(cwd, config)` returns
`{ pathFor, localeFor }`: `pathFor(locale)` is the absolute path of one locale's file, and
`localeFor(path)` is the locale that owns a path, or `undefined` for a path this project does not
own. Every SDK entry point resolves paths through it, so a watcher or dashboard built on the SDK
sees exactly the paths a run writes.

Every check runs when the resolver is created, before any file is read: a pattern and style that
cannot be combined, or a locale the style has no correct spelling for, throws
`LOCALE_LAYOUT_INVALID`, and two locales resolving to one path throws `LOCALE_PATH_COLLISION`.

## The workbook pair

The translator handoff, as an Excel workbook or as delimited text; see [Manual translation](/docs/manual-translation).

### exportWorkbook

Writes the strings that still need translating (missing and changed keys per locale; add unchanged
ones with `includeUnchanged`) into a styled `.xlsx` workbook. Rows carry the same review-flag
signal a translate run computes. No provider call, no lock write.

Input: `{ config, cwd?, out?, configPath?, glossaryPath?, locales?, includeUnchanged?, format? }`. `format` is `xlsx` by
default; `csv` and `tsv` write one `<locale>.csv` or `<locale>.tsv` per locale instead, so `out`
names a directory for them (created if missing) and a file path for `xlsx`. `out` defaults to
`DEFAULT_WORKBOOK_PATH` (`verbatra-translations.xlsx`) or `DEFAULT_DELIMITED_PATH`
(`verbatra-translations`), both exported as constants. The accepted values are exported as `EXCHANGE_FORMATS` and the default as `DEFAULT_EXCHANGE_FORMAT`, so a tool that wraps the SDK can validate a format argument without hardcoding the list. Returns `{ path, locales }`: the absolute
path written and a per-locale row count.

Before anything is read, `EXPORT_OUTPUT_CONFLICT` refuses an `out` that resolves outside `cwd`, and
one that, or a file the export would write into it, names a configured locale file, the lock file,
the provenance file, the translation-memory cache, a file verbatra searches for its configuration,
the `configPath` file, or the `glossaryPath` file, compared case-insensitively and, when `deps.fs`
implements `realpath` as the default does, again after symbolic links are resolved. An `xlsx` path
is also refused when it names no file (including one ending in a path separator) or names `cwd`
itself; a `csv` or `tsv` directory may be `cwd`. A write that fails, because the directory is not
writable, a directory or file is in the way, or the disk is full, throws `EXPORT_UNWRITABLE` naming
the file and the file-system code, with the file-system error as its `cause`.

### importWorkbook

Reads a filled workbook back into the locale files, running the same source-drift and integrity
checks as `translate`. Only accepted rows advance their lock baseline; a blank or rejected
row keeps re-exporting until it is genuinely resolved.

Input: `{ config, workbook, cwd?, dryRun?, format?, onLockWait?, lockAcquireTimeoutMs? }`. With `csv` or `tsv`, `workbook` is either
one interchange file or the directory holding one per locale, and the locale comes from the file
name. Returns the same `RunSummary` shape as `translate`
(with `needsReview` always empty, since no provider is involved). A sheet for a locale that is not
a configured target fails that locale with `CONFIG_INVALID` as data on the summary, not a throw.

`onLockWait` and `lockAcquireTimeoutMs` behave exactly as on `translate`. `lockAcquireTimeoutMs`
bounds the wait for a locale's write lock, taken before that locale's file is written, and a locale
still contended after it fails with `LOCK_CONTENDED` on its own summary while the other locales
import. Recording a written file in the lock file always allows the ten-minute default. A dry run
takes no lock, so neither option applies to it.

<AvailableFrom version="0.12.0" />

Each locale's `integrityRefusals` names the rows the integrity gate refused, with the reason and
its `details`, such as each ICU arm that does not fit the target language. A row withheld because
its source changed since the export is listed in `integrityMismatches` only. `exportWorkbook` flags
a current translation with the wrong arms as `icu-arms` in its review columns.

## The TMX pair

<AvailableFrom version="0.11.0" />

`importTmx` and `exportTmx` move the [translation memory](/docs/the-cache) in and out of TMX, the
interchange format the mainstream translation platforms produce and consume. Neither constructs a
provider, reads an API key, nor makes a network call: every value comes from the file or from the
memory already on disk. This is not the workbook pair in another format. The workbook pair hands a
per-locale slice of the pending delta to a human translator; this pair moves the whole memory as one
multilingual file between tools.

### importTmx

Reads a TMX file into the project's memory. Input:
`{ config, file, cwd?, dryRun?, overwrite?, locales? }`.

Nothing from the file is trusted. The XML is parsed under the interchange package's hardening, so an
entity declaration, an internal DTD subset, an oversized file, or a malformed one is refused with a
structured `SOURCE_INVALID` error rather than parsed. When the problem has a place in the file, the
message names its line, column and, inside a translation unit, the unit's 1-based ordinal, and
`tmxErrorLocation(error)` returns the same place as a `TmxErrorLocation`, or `undefined` for any
other error, so you never cast the error or its `cause`. A language tag is resolved to a configured
locale by an explicit rule: exact spelling after lowercasing and folding underscores to hyphens;
failing that, the longest configured locale that is a subtag prefix of the tag (RFC 4647 lookup), or
else a configured locale that extends the tag only by region or variant subtags, never by a script,
so two tags whose script or region subtags differ (`sr-Latn` and `sr-Cyrl`, `de-AT` and `de-CH`) never match; and a tag is
reported as ambiguous only when the locales it could reach do not lie on one prefix chain. Segments
of one unit that resolve to the same locale, the source locale included, never let the last one win:
an exact tag outranks a prefix match, and two equal-ranked segments with different values store
nothing for that locale and are counted as `conflicting` (for the source locale, the unit is refused
and counted in `conflictingSourceUnits`). Every candidate translation then passes the same
placeholder, inline markup, ICU, degeneracy, and emptiness gate that provider output and a filled workbook row
already face, checked as the record enters the memory rather than left to the run that later reads
it.

Where an imported unit disagrees with a translation the memory already holds, the memory wins unless
`overwrite` is set. Units are stored under the current configuration fingerprint, the same key a real
run writes, so they stop matching when the provider, model, tone, glossary, or provider `localeMap` changes. Importing the
same file twice changes nothing the second time.

Returns a report rather than throwing on damaged data: how many units were read, a per-locale
account of `added`, `unchanged`, `overwritten`, `kept`, `duplicates`, `conflicting`, and `rejected`
by reason, plus the units that were skipped, carried no source segment, lost inline markup, or had
`sub` text left out (`subflowDroppedUnits`), and the language tags that matched nothing or matched
ambiguously. `memoryWritable` is false when the memory file was written by a newer verbatra, in
which case it is left untouched. The per-locale counts are still reported then, as on a dry run, so
`added` and `overwritten` describe what would have landed; with `memoryWritable` false, nothing did.

<AvailableFrom version="0.12.0" />

Each locale also lists its `refusals`, one `TmxUnitRefusal` per unit counted under a gate reason:
`{ unit, reason, details? }`, where `unit` is the unit's 1-based ordinal in the file and `details`
names what is wrong, such as each ICU arm that does not fit the target language.

### tmxErrorLocation

Reads where a refused TMX file went wrong from whatever `importTmx` threw. It returns a
`TmxErrorLocation` (`{ line, column, unit? }`, all 1-based) for a `SOURCE_INVALID` refusal that has
a place in the file, and `undefined` for any other error, including a missing or oversized file, so
you never cast the error or its `cause`.

```ts
try {
  await importTmx({ config, file: "legacy.tmx" });
} catch (error) {
  const at = tmxErrorLocation(error);
  if (at !== undefined) console.error(`line ${at.line}, column ${at.column}`);
}
```

### exportTmx

Writes the memory out as TMX 1.4b. Input: `{ config, out?, cwd?, configPath?, glossaryPath?,
locales?, toolVersion? }`, with `out` defaulting to `DEFAULT_TMX_PATH` (`verbatra-memory.tmx`),
exported as a constant. Before the memory is read, `TMX_OUTPUT_CONFLICT` refuses an `out` that names
no file (including one ending in a path separator), resolves outside `cwd` or to `cwd` itself, or
names a configured locale file, the lock file, the provenance file, the translation-memory cache, a file verbatra
searches for its configuration, the `configPath` file, or the `glossaryPath` file, compared
case-insensitively and, when `deps.fs` implements `realpath` as the default does, again after
symbolic links are resolved. A write that fails, because the directory is not writable, a directory
sits at that path, or the disk is full, throws `TMX_UNWRITABLE` naming the file and the file-system
code. Only entries under the current configuration fingerprint are written, which is the same set a
run would reuse. Language tags are written in BCP 47 form (`en_US` becomes `en-US`), which does not
change how the memory is keyed. An empty memory produces a valid, empty file rather than an error.
Returns `{ path, units, locales, withoutSource, illegalCharactersRemoved }`; `withoutSource` counts
entries left out because the memory holds no source text for them, which happens only for entries
carried forward from a cache written before the memory stored source text, and
`illegalCharactersRemoved` counts the characters XML 1.0 cannot represent that were removed from
segment text.

## Config

### loadConfig

Finds, loads, and validates the project config, returning a `VerbatraConfig`. Options:
`{ cwd?, configPath?, configOverride? }`, with precedence `configOverride` (validate an in-memory
object) over `configPath` (load one explicit file) over search. The search starts at `cwd` and
covers `verbatra.config.ts` (also `.js`/`.cjs`), the `.verbatrarc` family (`.json`, `.yaml`,
`.yml`, `.js`, `.cjs`, `.ts`), and a `"verbatra"` property in `package.json`. A `glossary` given as
a file path is read and validated here, so downstream code always sees a plain record.

Throws `CONFIG_NOT_FOUND` when nothing is found, `CONFIG_INVALID` when a config is found but
invalid. See [The config file](/docs/config-file) for the schema.

### loadConfigWithMeta

The same load, plus provenance: returns `{ config, source, glossary }`, where `source` says whether
the config came from a search hit, an explicit path, or an in-memory override (with the absolute
`filepath` when there is one), and `glossary` records whether the glossary was absent, inline, or
resolved from a file. Use it when you need to display where the config came from.

### readGlossaryFile

<AvailableFrom version="0.9.0" />

Reads a file-backed glossary fresh from disk and returns it as a normalized `Glossary`:
`{ version, terms, doNotTranslate }`, where `version` is `1` for a flat term map and `2` for a
[per-locale glossary](/docs/config-file#glossary), and every term carries `source`, an optional
`target`, `targets`, `forbidden`, `caseSensitive`, and an optional `note` and `partOfSpeech`. Takes
`{ glossary }`, the `GlossaryProvenance` from `loadConfigWithMeta`, so the file it reads is always
the one the config names; there is no path argument. Use it in a long-running tool that has to show
the glossary as it is now rather than as it was when the config was loaded.

Throws `GLOSSARY_NOT_FILE_BACKED` when the glossary is inline or absent, and `CONFIG_INVALID` when
the file is missing, oversized, not UTF-8, not valid JSON, neither a flat string map nor a valid
version 2 glossary, or declares another version.

<AvailableFrom version="0.12.0" />

Up to 0.11 it returned the flat term map itself.

### updateGlossaryTerm

<AvailableFrom version="0.9.0" />

Adds, changes, or removes exactly one term in a file-backed glossary and returns the normalized
glossary as it now stands. Takes `{ glossary, cwd?, term, translation }`, where `translation` is
the new text or `null` to remove the term. The rest of the file keeps its key order and its
indentation, the write is atomic, and the whole read-modify-write is held under a project-wide
glossary lock, so two concurrent edits are serialized rather than interleaved.

<AvailableFrom version="0.12.0" />

It also takes `locale` (then `translation` is that locale's own and `null` removes only it),
`forbidden` (the renderings `locale` must never use; `null` or `[]` removes them), `note`,
`partOfSpeech` (each `null` to remove), `caseSensitive`, and `doNotTranslate` (`true` adds the term
to the terms kept untranslated, `false` removes it; it cannot be combined with the term fields).
A version 1 file stays version 1 while an edit only sets or removes a translation for every
locale; any other edit rewrites it as version 2, every existing term keeping its translation as
`target`. `translation: null` without `locale` now removes only the shared translation; the term itself is removed once it has no translation and no forbidden rendering left, which for a version 1 term is at once.

An inline glossary is refused with `GLOSSARY_NOT_FILE_BACKED` rather than converted: it lives inside
an executable config module. A blank field, an edit that sets no field or mixes `doNotTranslate`
with the term fields, forbidden renderings without a locale, an invalid locale, an edit that would
leave an invalid glossary, and an edit whose result would exceed the 1 MiB glossary limit are
refused with `CONFIG_INVALID`; a failed write, including a glossary write lock that cannot be created in a read-only project or cannot be released after a saved edit, is `GLOSSARY_UNWRITABLE`, with the file-system error as its `cause`. An edit that leaves the
glossary as it already is succeeds and writes nothing.

### glossaryForLocale

<AvailableFrom version="0.12.0" />

Resolves the part of a glossary that applies to one target locale:
`glossaryForLocale(config.glossary, "de")` returns `{ terms, doNotTranslate }`, each term with the
locale's `target` (its own entry, then its base language's, then the shared one), its `forbidden`
renderings, `caseSensitive`, and its `note` and `partOfSpeech`, or `undefined` when nothing in the
glossary applies there. This is exactly what a translation request into that locale carries as
`TranslateRequest.glossary`, and what the review checks and the cache fingerprint of that locale
see.

### normalizeGlossary

<AvailableFrom version="0.12.0" />

Converts a glossary in either shape, a version 1 flat map or a version 2 definition, to the
normalized `Glossary` that `readGlossaryFile` returns, with every default filled in. Use it to show
an inline glossary the same way as a file-backed one. It does not validate again; `loadConfig` has.

### sharedGlossaryTranslations

<AvailableFrom version="0.12.0" />

Projects a normalized `Glossary` onto a flat map of each term that has a shared `target` to that
translation, in glossary order. Per-locale translations, forbidden renderings, and do-not-translate
terms are left out, so use it only where a consumer can show nothing but a flat term map. A term
named `__proto__` stays an own key.

### redactGlossary

<AvailableFrom version="0.12.0" />

Passes every translation, forbidden rendering, note, and part of speech of a normalized `Glossary`
through `redact`, and returns `{ glossary, redactedTerms }`, where `redactedTerms` names each term
that had a value replaced. Source terms and do-not-translate terms are left as they are. The MCP
server and Studio use it before a glossary leaves the process; use it the same way in your own
tool.

### readCurrentGlossary

<AvailableFrom version="0.12.0" />

Reads the glossary a loaded config names as it is now: `readCurrentGlossary({ loaded })`,
where `loaded` is what `loadConfigWithMeta` returns. A file-backed glossary is read fresh from disk,
an inline one comes from the config, and either way the result is the normalized `Glossary`, or
`undefined` when the config declares none. To see what one target locale is held to, pass the result
to `glossaryForLocale`.

### editConfiguredGlossaryTerm

<AvailableFrom version="0.12.0" />

`updateGlossaryTerm` for a tool that holds a loaded config: takes `{ loaded, cwd?, term, ... }` with
the same edit fields, treats a field left `undefined` as absent, and checks `locale` against the
configured target locales first, failing with `UNKNOWN_LOCALE` and writing nothing when it is not
one of them. The MCP server and Studio write the glossary through it.

### defineConfig

An identity helper for authoring a typed `verbatra.config.ts`: it returns its argument unchanged,
and exists purely for type inference and editor autocomplete, including completion of the selected
provider's known model IDs. The model restriction is authoring-only; at runtime any non-empty
string passes validation.

### verbatraConfigSchema

The zod schema `loadConfig` validates with, exported so your own tooling can validate a config
object the same way the SDK does. Unknown top-level keys are rejected, so a stray secret cannot
hide in the config. The one exception is `$schema`, an optional string accepted so a JSON or YAML
config can point an editor at the JSON Schema document the package ships as
`@verbatra/sdk/config-schema.json`. It is ignored at runtime.

### scaffoldingMetadata

Read-only metadata the CLI `init` command derives its prompts from: `providerEnv` (provider id to
the environment variable its key is read from), `scaffoldModels` (a default scaffold model per LLM
provider), `providerTokenLimitKeys` (the option key each LLM provider takes its output token limit
under), and `supportedFormats` (the closed set of format ids). Read the token-limit key from
`providerTokenLimitKeys` rather than assuming one: Anthropic calls it `maxTokens` and the others
`maxOutputTokens`, the schema validates each provider's options strictly, and DeepL has no entry
because it takes no token limit. The `ScaffoldableProviderId` type is
`Exclude<ProviderId, "openai-compatible" | "none">`, so it covers the five hosted providers;
`openai-compatible` is excluded because it has no single required environment variable.

`scaffoldingMetadata.humanOnlyProviderId` is `"none"`, the id that disables machine translation. It has no `providerEnv` entry, since it reads no key.

`scaffoldingMetadata.openAiCompatibleKeyEnv` is `"OPENAI_COMPATIBLE_API_KEY"`, the variable an `openai-compatible` provider reads when its options name no `apiKeyEnvVar`. `scaffoldingMetadata.configSearchPlaces` lists every file name `loadConfig` searches for a config, in the order it checks them; a generator writing `verbatra.config.ts` should refuse when another of them already exists, since the first one found wins.

### detectProject

<AvailableFrom version="0.12.0" />

Detects a project's locale file format and layout from its files, the way `verbatra init` does before writing a config. It writes nothing and calls no provider. It scans the directory (skipping hidden directories, `node_modules`, and build output, within a bounded depth and entry count) for files a registered adapter claims, finds the path segment that spells a locale in each, and keeps the file pattern covering the most locales. The format is the one whose adapter `canHandle` claims every matched file given its content; for JSON, where every JSON adapter does, a single matching i18n library in `package.json` decides.

```ts
import { detectProject } from "@verbatra/sdk";

const detection = await detectProject({ cwd: "/path/to/project" });
if (detection.ambiguities.length > 0) {
  // several formats or file patterns fit: choose one of detection.ambiguities[0].candidates
}
const format = detection.format?.id;          // for example "yaml"
const pattern = detection.layout?.pattern;    // for example "config/locales/{locale}.yml"
```

The result carries `format` (with `from`: `input`, `files`, or `dependencies`), `layout` (`pattern`, `localeStyle`, `locales`, `sourceLocale`, `files`, `unqualifiedSourceFile`), `ambiguities` (each with a `subject` of `format` or `layout` and its `candidates`), a `confidence` of `high`, `medium`, `low`, or `none`, and `reasons`, one sentence per decision. Ties are reported as ambiguities, never guessed. The optional `format`, `pattern`, and `sourceLocale` inputs narrow the search, and `deps.fs` and `deps.adapterRegistry` swap the file system and the adapters, so a third-party adapter's files are detected too. It never throws for a missing, unreadable, or malformed file; it reports less instead. `layout.unqualifiedSourceFile` names a file beside the layout that holds strings under no locale name, such as `messages.properties` or a gettext `.pot` template; the source locale is then left open rather than guessed, since the source is read from the file the pattern names for it.

### isMachineTranslationEnabled

<AvailableFrom version="0.12.0" />

Returns `false` exactly when the config sets `provider: { id: "none" }`, the [human-only](/docs/human-only-workflow) mode in which no provider is ever constructed and no API key is read. A surface that offers provider-spending actions reads it to leave them out altogether, which is how Studio and the MCP server withhold spend even with `--allow-spend`.

### assertMachineTranslationEnabled

<AvailableFrom version="0.12.0" />

Takes the config and a short phrase naming the action, and throws `SdkError` `MACHINE_TRANSLATION_DISABLED` under `provider: { id: "none" }`. Call it before wrapping `translate` in an explicit "translate everything pending" action, so the action fails the same way `retranslateEntry` does instead of quietly filling from the translation memory alone.

## Format adapters

<AvailableFrom version="0.11.0" />

Everything needed to build a format adapter for a format verbatra does not ship, and to register it alongside the built-in ones. A format from outside verbatra is named with a `custom:` identifier, such as `custom:toml`, which the config accepts exactly like a built-in name. See [Custom format adapters](/docs/custom-format-adapters) for the full walkthrough, including what you are trusting when you install a third-party adapter: it is fully trusted code, and verbatra does not sandbox it.

### createDefaultRegistry

Builds an `AdapterRegistry` holding every adapter verbatra ships, in detection order. Start here rather than from an empty registry, so your own format joins the built-in ones instead of replacing them, then pass the result as `deps.adapterRegistry` to any flow. `register` returns the registry so registrations chain, and raises an `AdapterError` with code `DUPLICATE_FORMAT` if the format is already taken.

```ts
import { createDefaultRegistry, translate } from "@verbatra/sdk";

const adapterRegistry = createDefaultRegistry().register(tomlAdapter);
const summary = await translate({ config }, { adapterRegistry });
```

### createFlatFileAdapter

Builds a `FormatAdapter` for a flat key/value format, one where every entry is addressed by a single key with no nesting. You supply the format's own `parseEntries`, `serializeEntries` and `extractPlaceholders`; the factory supplies the size-bounded read, the atomic write, extension detection and the structured error handling. `parseEntries` also receives the locale the file is read as, for a format whose one file holds both source and target text, and `serializeEntries` receives the caller's write context, whose optional `sourcePath` names the source-locale file. Give it a `sniff` whenever your extension is a generic one, or your adapter claims every file that shares it and detection reports an ambiguity instead of choosing.

### createTreeFileAdapter

Builds a `FormatAdapter` for a nested-tree format, one whose entries live at paths through nested objects. It takes `parse` and `serialize` over a tree plus a `deriveEntry` that reports each leaf's placeholders and whether it is a plural form, and handles flattening and unflattening itself. It also carries the optional hooks a structured format needs: `validateTree`, `validateMessage`, `comparePlaceholders`, `compareBranchArms`, `deriveDescriptions` and `keyMode`.

### nodeAdapterFs

The file-system port, typed `AdapterFs`, that every adapter factory uses when none is supplied: a size-bounded read that reports a missing or oversized file as a state rather than throwing, and a write that goes through a temporary file and a rename so an interrupted write never leaves a half-finished locale file. Read and write through this port rather than reaching for `node:fs` in an adapter of your own. It is a convention rather than a boundary, and verbatra cannot enforce it on code it does not own.

### isCustomFormatId

Narrows a format identifier to a third-party one: true for a well-formed `custom:` identifier, false for every built-in format name. Useful when your own tooling has to tell the two apart, for example to decide whether a registry has to be supplied before a config can run.

## Secret redaction

<AvailableFrom version="0.10.0" />

### redact

Scrubs provider API key shapes and the exact current value of any configured provider environment
variable out of a string, replacing each match with `[REDACTED]`. `@verbatra/studio` and
`@verbatra/mcp` both apply it to every value they return to a caller that they did not themselves
generate, such as a glossary term, a file path, or an upstream error message, so a key already
present in your environment or written into a project file can never reach a browser tab, an
agent, or a log line. The `verbatra` CLI runs everything it writes to stdout and stderr, the
`--json` envelope included, through it as a last step.

That includes the variable an `openai-compatible` provider names through `apiKeyEnvVar`. It is
declared when `loadConfig` loads a config naming it or when that provider is built, and from then on
its value is scrubbed exactly like the built-in ones. Declarations are never removed. A value
shorter than eight characters is not scrubbed by value, so a short variable can never wipe
unrelated text.

A DeepL key is recognized by its shape alone only when it carries the `:fx` suffix of a free key,
or when a bare UUID sits in a key context: after a `DeepL-Auth-Key` header, or after a name such as
`auth_key`, `authKey`, `--auth-key`, `api_key`, `deeplKey`, `DEEPL_API_KEY`, or `DEEPL_AUTH_KEY`
followed by `:`, `=`, a URL-encoded `%3D`, or a space, quoted or not, also inside JSON that was
serialized into a string. Any other UUID, such as one in a file path or a request id, stays
readable. A Pro key held in `DEEPL_API_KEY` is still scrubbed wherever it appears, by its value.

An `sk-` token is redacted once at least 32 letters and digits follow `sk-`, counted across its `-`
and `_` segments, whatever its prefix. That one rule covers every OpenAI and Anthropic key shape;
a known prefix such as `sk-proj-` or `sk-ant-` does not redact a shorter token on its own. The token
counts only when no letter or digit directly precedes it: a JSON escape such as `\n` or `\u0007`, a
percent-encoded character such as `%3D`, an ANSI CSI sequence such as `\x1b[31m`, `\x1b[2K` or
`\x1b[?25h`, an ANSI charset designation such as `\x1b(B`, or either ANSI form JSON-escaped as
`\u001b` is a boundary too. A Slovak locale path or key such as `locales/sk-SK.json` or
`sk-banner_headline` stays readable. A long Slovak-like key reaches the threshold and is redacted,
though: `sk-SK_settings_notifications_email_digest` holds 34 letters and digits after `sk-`, just
like a long camelCase key such as `sk-onboardingWelcomeScreenPrimaryButton`.

### declareProviderKeyEnvVar

<AvailableFrom version="0.12.0" />

Declares the variable a `provider` block names as its key source, so `redact` scrubs its value.
Today only an `openai-compatible` provider with `apiKeyEnvVar` names one; any other provider is a
no-op. `loadConfig` and building the provider already do this, and Studio and the MCP server also
do it for the config they receive, so call it only when a config reaches your own code some other
way. The declaration is process-wide and shared by every copy of the SDK loaded in the process.

## The dependency seam

<AvailableFrom version="0.9.0" />

`deps.fs` replaces the file-system port the SDK's own I/O travels through, typed as `SdkFs`. The
seam is complete: the run-status file, the lock file, the glossary file tools, workbook and
interchange I/O, and the locale files themselves all go through it, because the format adapters read and write
through a port built from the same object. A whole run can therefore be held in memory, which is
how the SDK's own tests avoid touching disk and how an embedding application can back part of a
project with something other than a local disk.

```ts
import { translate, type SdkFs } from "@verbatra/sdk";

const summary = await translate({ config }, { fs: inMemoryFs satisfies SdkFs });
```

Two contract points an implementation has to honor. Reads are size-bounded, so `readFileBounded`
and `readBytesBounded` take a byte limit and report `missing` or `too-large` as a state rather than
throwing, which is what keeps a hostile or accidentally huge file from exhausting memory. Writes are
expected to be atomic, so a crash mid-write never leaves a half-written file behind, and
`createExclusive` must be atomic against other processes because it is the primitive behind the
per-locale write lock. Directory creation is the caller's job.

`readDirectory` is optional, so an implementation written before source extraction existed keeps
compiling. [`extract`](#extract) is the only entry point that needs it, and reports its absence as
`EXTRACT_FS_UNSUPPORTED`. It lists one directory's immediate entries as `{ name, kind }`, where
`kind` is `"file"`, `"directory"`, or `"other"`. A symbolic link belongs in `"other"`: the scan
never follows one, which is what keeps it inside the roots it was given.

`realpath` is optional too. It resolves every symbolic link in an existing path, and the output
guards of [`generateTypes`](#generatetypes), [`exportTmx`](#exporttmx),
[`exportWorkbook`](#exportworkbook), and [`pseudolocalize`](#pseudolocalize) use it to see where an
output path really lands, so a link cannot carry a written file outside `cwd` or onto a file the
project depends on. Without it, those guards compare paths as written. A link at the output path
whose target does not exist cannot be resolved, so the guards assume `writeFile` and `writeBytes`
replace a link there rather than writing through it, as the default atomic write does.

`rename` is optional as well.

<AvailableFrom version="0.12.0" />

It moves a file to a new name in the same directory in one atomic step, replacing any file already
there, and rejects with an error whose `code` is `ENOENT` when the source is missing. The write lock
uses it to remove a lock or reclaim guard left by a process that is gone: the file is moved aside
under a unique name and deleted only when it is still the abandoned record the lock observed.
Anything else, such as a lock another process took in the meantime, is put back with
`createExclusive`, and when a third process has taken the path in between, it is left aside rather
than deleted. Without `rename`, the lock reads the file and deletes it when unchanged, and clears an
abandoned reclaim guard only after seeing it unchanged across two polls, which narrows but cannot
close the window in which a lock another process just took is deleted.

`deps.fs` cannot reach a caller-supplied `deps.adapterRegistry`. Those adapters
were constructed by the caller, so their file access is whatever the caller wired into them.
Supplying both means the caller owns that wiring.

Config loading sits outside the seam as well. `loadConfig` and `loadConfigWithMeta` take no `deps`:
they read the config file itself from the real disk, and a glossary file the config names through
their own `fs` option, so the `deps.fs` a later flow receives reaches neither read. To keep a whole
project in memory, pass the same `SdkFs` as `loadConfig({ fs })`, and hand the config in as
`configOverride` rather than as a file.

## The RunSummary anatomy

`translate`, `importWorkbook`, and each successful `watch` run resolve to a `RunSummary`:

```ts
interface RunSummary {
  dryRun: boolean;          // true when nothing was written and no provider was called
  locales: LocaleSummary[]; // one entry per target locale, in config order
  succeeded: string[];      // locales whose run succeeded
  partial: string[];        // locales written with keys still missing; the CLI exits 1 on these
  failed: string[];         // locales whose run failed
  usage?: UsageSummary;     // summed input/output tokens; absent when no call reported usage
  budget?: RunBudget;       // present only when maxTokens is configured
  estimate?: RunEstimate;   // present only when the run was asked for a pre-run estimate
}

interface LocaleSummary {
  locale: string;
  status: "succeeded" | "partial" | "failed";
  translated: string[];          // keys translated this run (in dry-run, keys that would be)
  cacheHits: string[];           // keys served from the translation-memory cache this run
  fuzzyHits: FuzzyCacheHit[];    // reuses for a source string that changed, with their scores
  unchanged: string[];           // keys already up to date
  orphaned: string[];            // target keys with no matching source key (always reported)
  pruned: string[];              // orphaned keys removed this run; empty unless pruning is on
  invalidIcuSource: string[];    // source keys skipped for invalid ICU
  integrityMismatches: string[]; // translations the integrity gate withheld
  integrityRefusals?: { key: string; reason: string; details?: string[] }[]; // why each was withheld; translate and watch only
  providerFailures: string[];    // keys withheld because nothing was translated for them
  budgetWithheld: string[];      // keys never sent because a "stop" budget already tripped
  generated: string[];           // CLDR plural forms synthesized this run
  unfilled: string[];            // blank import rows, or keys a human-only translate left for a human
  protected: { key: string; reason: string; suggestion?: string; suggestionStatus?: string }[]; // keys left for a person
  malformedRows: { row: number; line?: number; column: string }[]; // import only: rows the reader could not parse
  duplicateKeys: { key: string; row: number; line?: number }[];    // import only: later rows for a duplicated key
  notices: LocaleNotice[];       // provider notices and SDK notices for this locale
  needsReview: { key: string; reasons: string[] }[]; // accepted keys flagged for a second look
  usage?: UsageSummary;          // this locale's summed tokens; absent if nothing reported usage
  error?: { code: string; message: string }; // only on a "failed" locale, and not on every one
}
```

The parts worth knowing:

- **needsReview** lists accepted, written keys the review heuristics flagged, each with its reason
  codes: `LENGTH_RATIO_OUTLIER`, `MAX_LENGTH_EXCEEDED`, `EQUALS_SOURCE`, `GLOSSARY_TERM_MISSED`,
  `GLOSSARY_FORBIDDEN_TERM`, `INTEGRITY_REORDERED`, `PROVIDER_DEGRADED`, and `FUZZY_CACHE_REUSE`. The set ships as the
  `REVIEW_REASON_CODES` tuple, so build any runtime schema or exhaustive lookup from that rather
  than retyping the members. A review flag is advisory and never withholds a key, so a key never
  appears in both `needsReview` and `integrityMismatches`. See
  [Translation safety](/docs/translation-safety) for what each code means and
  [Review in Studio](/docs/review-in-studio) for working the queue.
- **notices** live per locale, never at the top level. They cover provider notices (say, a DeepL
  degradation) and SDK notices with the codes `PLURAL_CATEGORIES_INCOMPLETE`, `SUB_BATCH_FAILED`,
  `BLANK_ROW_BASELINE_RETAINED`, `BUDGET_TOKENS_EXCEEDED`, `CACHE_VERSION_UNRECOGNIZED`,
  `PROVENANCE_VERSION_UNRECOGNIZED`, `LOCALE_STATE_CARRIED_OVER` (state recorded under an underscore spelling such as `pt_BR` was moved to the configured `pt-BR`; see [A respelled locale code](/docs/the-lock-file#a-respelled-locale-code)), `LOCALE_STATE_CARRY_OVER_SKIPPED` (that move was left for the next run because the lock-file guard stayed contended or could not be read or created, or a file could not be written; unless only the translation memory stayed behind, the locale did not run and failed with `LOCALE_STATE_NOT_CARRIED_OVER`), and `PROVENANCE_FILE_TOO_LARGE` (recording a locale would have
  grown `verbatra.provenance.json` past what verbatra reads back, so the file was kept as it was). The
  cache notice is run-wide (one file, shared by every locale), so it is attached to each locale in
  the run.
- **usage** is `undefined`, never a fabricated zero, whenever nothing in that scope reported usage:
  a dry run never calls a provider, and DeepL never reports tokens. `RunSummary.usage` is the sum
  over the locales.
- **budget** appears only when `maxTokens` is configured: `{ maxTokens, behavior, supported,
  tokensUsed, exceeded }`. `supported` says whether `tokensUsed` is entirely the provider's own
  reported usage; it is `false` as soon as one request came back without a usable figure, and the
  total is then partly verbatra's projection, which is counted and enforced just the same. A dry run
  reports it with `tokensUsed: 0`, since nothing was sent. Under `behavior: "stop"` the ceiling is
  checked before every request the run sends, each half of a re-split request included, so
  `tokensUsed` lands at or below `maxTokens` apart from one residual: the last request admitted is
  reconciled to what the provider reported, which can push the total past the ceiling after the
  fact. Nothing further is sent once it does. Two things sit outside what a reservation can bound,
  because they happen inside a request it already admitted: the provider layer sends one repair call
  of its own when keys come back missing, so one admitted batch can cost up to about twice its
  projection, and the count is only as good as what the provider reports. Both land at
  reconciliation, and nothing further is admitted once they do. The budget bounds one `translate`
  call: `watch` starts a fresh one per run, and `retranslateEntry` is not covered by it at all.
- **error.code** on a failed locale is a preserved string (the underlying provider or adapter code,
  with `LOCALE_FAILED` only as a fallback), so do not treat it as a closed set. A `failed` locale
  does not always carry `error`: one whose every key was withheld, and so listed in
  `integrityMismatches`, `providerFailures`, or `budgetWithheld`, fails with nothing thrown. Its
  reason is in those lists and in its `notices`, such as `SUB_BATCH_FAILED` for a failed provider
  batch or `BUDGET_TOKENS_EXCEEDED` for the token budget. Test `status`, never the presence of
  `error`.
- **cacheHits** lists keys served from the [translation-memory cache](/docs/the-cache) rather than
  the provider. **fuzzyHits** lists the keys that reused a translation for a source string
  that had changed, each carrying `key`, `similarity`, and the `previousSource` it matched; it is
  empty unless `fuzzyCache` is enabled, and those keys are never counted in **cacheHits**. **unfilled**, **malformedRows**, and **duplicateKeys** are populated only by
  `importWorkbook` (a `translate` run leaves them empty): a blank row whose key still needs a
  translation at import time (whether it was exported as `new` or as `changed`), a workbook row the
  reader could not parse, and a duplicated key whose first occurrence won. The optional `line` on
  the last two is the file line the record starts on, present only for a delimited (`csv` or `tsv`)
  import. The one exception is a [human-only](/docs/human-only-workflow) project: there `translate` and `watch` list in **unfilled** every key the translation memory had no exact entry for, and **fuzzyHits** stays empty because fuzzy reuse is never applied there.
- **protected** lists the keys a `translate` run left alone, each with its `reason` (`human`, `import`, `external`, or `pinned`) and, under `humanEdits: "suggest"`, a `suggestion` (the provider's answer or an exact translation-memory entry, never a fuzzy match), which was not written, and a `suggestionStatus`: `planned` on a dry run, `suggested`, or why not (`integrity-mismatch`, `provider-failure`, `budget-withheld`). A failed suggestion never changes the locale's status. They are not in **translated**, never change a locale's status, and stay stale for `check`. `importWorkbook` leaves it empty. See [Protecting human translations](/docs/protecting-human-translations).

### budgetStanding

<AvailableFrom version="0.11.0" />

Classifies a `RunBudget` into one of three `BudgetStanding` values, the same classification the CLI
budget line, Studio, and the `usage.summary` agent tool report: `"within"` when the run never
reached its ceiling, `"stopped-before-ceiling"` when a `"stop"` budget withheld a request while
`tokensUsed` was still below `maxTokens`, and `"reached"` when `tokensUsed` reached or passed
`maxTokens`. Use it rather than reading `exceeded` alone, which is `true` in both of the last two
cases.

## The error model

Whole-run failures throw an `SdkError`: one class, a stable `code`, and a secret-free `message`.
Branch on the code, not the message. Per-locale failures, provider notices, and integrity findings
are surfaced as data on the `RunSummary`, never thrown.

| Code | When |
| --- | --- |
| `CONFIG_NOT_FOUND` | no config was found by search, or an explicit `configPath` does not exist (thrown by `loadConfig`) |
| `CONFIG_INVALID` | a config was found but is unparseable or fails validation, or its glossary file could not be resolved |
| `UNKNOWN_FORMAT` | no adapter is registered for the configured format; thrown before any file is read |
| `UNKNOWN_LOCALE` | a requested locale is not among the configured target locales |
| `UNKNOWN_KEY` | a requested key is not in the source resource (`keyValue`, `editEntry`, `retranslateEntry`, `approveEntry`, `rejectEntry`) |
| `KEY_PROTECTED` | `retranslateEntry` refused to replace a value a person wrote, imported, or changed outside verbatra, because neither `includeHuman` nor `humanEdits: "overwrite"` allowed it |
| `KEY_PINNED` | the key matches the config's `pinnedKeys`, so a machine write was refused (`retranslateEntry`, and `editEntry` with `actor: "agent"`) |
| `PROVIDER_CONSTRUCTION_FAILED` | the provider could not be built; wraps the provider's own error, including a missing API key |
| `MACHINE_TRANSLATION_DISABLED` | the config sets `provider: { id: "none" }`, so a provider-spending action was refused before any provider was built (`retranslateEntry`, `assertMachineTranslationEnabled`); `translate` and `watch` never throw it |
| `NETWORK_POLICY_VIOLATION` | the effective [network policy](/docs/network-policy) does not permit the provider's endpoint or its proxy; thrown by a non-dry-run `translate`, by `watch` at startup, and by `retranslateEntry`, before the provider is built or any API key read |
| `SOURCE_UNREADABLE` | the source locale file does not exist |
| `SOURCE_INVALID` | the source locale file could not be read or parsed; wraps the adapter's read error |
| `LOCK_FILE_INVALID` | the lock file is present but corrupt, oversized, or at an unsupported version |
| `PROVENANCE_FILE_INVALID` | the provenance file is present but corrupt, oversized, or structurally wrong; thrown by a write (`translate`, `watch`, `importWorkbook`, `editEntry`, `retranslateEntry`) before it changes anything, and by `loadProvenance`, never by a report; one from a newer verbatra is left untouched instead, and `translate`, `watch`, and `importWorkbook` report the notice `PROVENANCE_VERSION_UNRECOGNIZED` |
| `PROVENANCE_FILE_UNWRITABLE` | a review decision could not be saved because the provenance file is from a newer verbatra or would grow past the size verbatra reads back (`approveEntry`, `rejectEntry`); nothing is written |
| `REVIEW_VALUE_CHANGED` | the key has no value, or its value is not the `expectedValue` the reviewer saw (`approveEntry`, `rejectEntry`) |
| `REVIEW_SOURCE_CHANGED` | the source changed since the value was written, so it cannot be approved as it stands (`approveEntry`) |
| `REVIEW_REJECT_UNSUPPORTED` | the format keeps a key's value when the file is written without it, as XLIFF does, so `rejectEntry` restored the file instead |
| `REVIEW_RESTORE_FAILED` | `rejectEntry` failed after it rewrote the locale file, and restoring the locale file or the provenance file failed too; the message names the original failure (also the `cause`) and the files to restore from version control |
| `REVIEWER_INVALID` | the `reviewer` is empty, longer than 64 characters, or contains a control character (`approveEntry`, `rejectEntry`) |
| `LOCK_CONTENDED` | a locale's write lock could not be acquired before its timeout; the message names the lock file's path |
| `GLOSSARY_NOT_FILE_BACKED` | the config's glossary is inline or absent, so there is no glossary file to read or rewrite (`readGlossaryFile`, `updateGlossaryTerm`) |
| `GLOSSARY_UNWRITABLE` | the glossary file could not be written, or the glossary write lock could not be created, for instance in a read-only project, or released after a saved edit (`updateGlossaryTerm`); the file-system error is the `cause` |
| `LOCALE_LAYOUT_INVALID` | `files.pattern` and `files.localeStyle` cannot be combined, or the style has no valid path spelling for a configured locale |
| `LOCALE_PATH_COLLISION` | two configured locales resolve to the same absolute file path |
| `CONCURRENCY_INVALID` | `concurrency` was set but is not an integer of at least 1; raised before any locale runs |
| `CONCURRENCY_BUDGET_CONFLICT` | a live run set `concurrency` above 1 while a token budget applies, configured or per-run; raised before any provider call (a dry run is exempt) |
| `MAX_TOKENS_INVALID` | `translate`'s per-run `maxTokens` was set but is not a whole number of at least 1; raised before anything is read or spent |
| `TARGET_UNWRITABLE` | a target locale file could not be written (its directory is not writable, does not exist, is read-only, or is out of space); the message names the target file and the file-system code, never the internal temporary file the atomic write uses |
| `PSEUDO_OUTPUT_CONFLICT` | `pseudolocalize` was asked for a pseudolocale that names a configured locale, or for an output path that would write onto a configured locale file or outside `cwd`, also after symbolic links are resolved; refused before anything is read or written |
| `SOURCE_UNWRITABLE` | the source locale file could not be written (`extract` only); `xliff` and `apple-xcstrings` reach it when no catalog exists yet, because neither is created from nothing |
| `EXTRACT_NOT_CONFIGURED` | `extract` was called with a config that carries no `extract` block |
| `EXTRACT_FS_UNSUPPORTED` | `extract` was given a `deps.fs` that implements no `readDirectory`, so no source file can be discovered |
| `TYPES_OUTPUT_CONFLICT` | `generateTypes` refused its output path: one that names no file (or ends in a path separator), is absolute, climbs out of `cwd` or names `cwd` itself, or does not end in `.ts`, `.mts` or `.cts`, and one naming a configured locale file, the lock file, the provenance file, the translation-memory cache, a file verbatra searches for its configuration, the config file the run loaded, or the glossary file the config names, also after symbolic links are resolved; a generating run also refuses to replace an existing file that does not begin with verbatra's header line |
| `TYPES_UNWRITABLE` | the declaration file `generateTypes` produces could not be written (its directory is not writable, does not exist, or the disk is out of space); the message names the file and the file-system code |
| `TMX_OUTPUT_CONFLICT` | `exportTmx` refused its output path: one that names no file (or ends in a path separator) or resolves outside `cwd` or to `cwd` itself, and one naming a configured locale file, the lock file, the provenance file, the translation-memory cache, a file verbatra searches for its configuration, the config file the run loaded, or the glossary file the config names, also after symbolic links are resolved; refused before the memory is read |
| `TMX_UNWRITABLE` | the TMX file `exportTmx` produces could not be written (its directory is not writable, a directory already sits at that path, or the disk is out of space); the message names the file and the file-system code |
| `EXPORT_OUTPUT_CONFLICT` | `exportWorkbook` refused its output path: one that resolves outside `cwd`, and one that, or a file the export would write into it, names a configured locale file, the lock file, the provenance file, the translation-memory cache, a file verbatra searches for its configuration, the config file the run loaded, or the glossary file the config names, also after symbolic links are resolved; an `xlsx` path that names no file or names `cwd` itself is refused too; refused before anything is read |
| `EXPORT_UNWRITABLE` | the handoff `exportWorkbook` produces could not be written (its directory is not writable, a directory or file is in the way, or the disk is out of space); the message names the file and the file-system code, and the file-system error is the `cause` |
| `LOCALE_STATE_NOT_CARRIED_OVER` | never thrown: recorded on the `error` of a locale `translate` or `watch` did not run because its state under a respelled code such as `pt_BR` could not be moved to it in the lock file or the provenance file; the next run tries again ([A respelled locale code](/docs/the-lock-file#a-respelled-locale-code)) |
| `LOCALE_FAILED` | never thrown: the fallback `code` recorded on a failed locale's `error` |

A few codes also carry the error they wrap as the standard `cause`: `SOURCE_INVALID` when a
parser or adapter failed (not when a file is refused for its size), `PROVIDER_CONSTRUCTION_FAILED`
(the provider factory's own error, whose message is also redacted into the `SdkError` message),
`EXPORT_UNWRITABLE` and `GLOSSARY_UNWRITABLE` (the file-system error), and `REVIEW_RESTORE_FAILED` (the failure that
interrupted the decision). `CONFIG_NOT_FOUND` and `CONFIG_INVALID` deliberately carry none, because
a config parser's error can quote the file's content, and a key written into the config must not
travel with the error. Only the message of a `PROVIDER_CONSTRUCTION_FAILED` error is redacted: its
`cause` is the original error, untouched. The built-in provider factories throw errors that carry
no secret, and an error thrown by a `createProvider` you supply comes back exactly as you threw it,
so keep secrets out of it or redact it yourself before you log the `cause`.

Two exceptions to the one-error-class rule: `retranslateEntry` re-throws the provider's own
`ProviderError` when the single call fails, and `runStatus` never throws at all. For how these
codes map to CLI exit codes, see [CI and exit codes](/docs/ci-and-exit-codes); for symptom-first
help, see [Troubleshooting](/docs/troubleshooting).

`ProviderError` and its `ProviderErrorCode` type are exported from `@verbatra/sdk`, so test a
`retranslateEntry` failure with `error instanceof ProviderError` and branch on `error.code`; the
[providers page](/docs/providers) lists every code. On an older version, which does not export the
class, check `error.name === "ProviderError"` and read `code`.
