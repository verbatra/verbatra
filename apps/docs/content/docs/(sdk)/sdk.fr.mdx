`@verbatra/sdk` est le moteur sur lequel tourne la commande `verbatra`. La CLI est une surcouche légère, donc tout ce que la ligne de commande fait, tu peux le faire en code. Cette page catalogue toute la surface publique, groupée par la tâche de chaque point d'entrée. Pour des exemples de bout en bout, voir [Recettes SDK](/docs/programmatic-api).

## Installation

```bash
npm install --save-dev @verbatra/sdk
# pnpm
pnpm add -D @verbatra/sdk
# yarn
yarn add -D @verbatra/sdk
```

Requiert Node.js `>=22.14.0`.

La ligne pnpm installe correctement mais sort en `1` avec `ERR_PNPM_IGNORED_BUILDS` : pnpm bloque les scripts d'installation du SDK Gemini embarqué et de son `protobufjs`, et laisse un `pnpm-workspace.yaml` sans réponse qui fait échouer de la même façon toutes les commandes pnpm suivantes du projet. Lance `pnpm approve-builds` une fois sans approuver aucune des deux entrées, ou consulte le [Dépannage](/docs/troubleshooting) pour la solution non interactive. Il n'y a pas de raccourci `npx` ici comme pour la CLI, puisque tu importes une bibliothèque au lieu de lancer un binaire.

<Callout title="Clés d'API et environnement">
Le SDK ne lit, ne détient ni n'accepte jamais de clé d'API. Le fournisseur lit sa clé depuis l'environnement (par exemple `ANTHROPIC_API_KEY`) au moment de sa construction. Contrairement à la CLI, le SDK ne charge pas les fichiers `.env` : dans ton propre script, définis la variable toi-même, par exemple avec `node --env-file=.env script.js`.
</Callout>

Chaque point d'entrée prend un objet d'entrée dont le premier champ est la `config` validée (issue de `loadConfig`), sauf mention contraire. La plupart acceptent aussi un second argument optionnel `deps` qui injecte un registre, un constructeur de fournisseur ou un système de fichiers ; tu peux l'ignorer en usage normal. Voir [Le point d'injection de dépendances](#le-point-dinjection-de-dépendances) pour ce que `deps.fs` atteint.

## Lancer des traductions

### translate

Le flux en une passe : lire la source, comparer chaque locale cible à la ligne de base du verrou, envoyer les clés manquantes et modifiées au fournisseur, exécuter les vérifications d'intégrité, écrire les fichiers de locale et mettre à jour le verrou. Utilise-le pour les scripts, les étapes de build et les jobs CI.

Entrée : `{ config, cwd?, locales?, dryRun?, estimate?, prune?, generatePlurals?, concurrency?, cache?, onProgress?, onLockWait?, lockAcquireTimeoutMs? }`.

- `locales` restreint l'exécution à un sous-ensemble des locales cibles configurées, exactement comme sur `check` et `diff`. Une locale non configurée lève `UNKNOWN_LOCALE` avant toute lecture et toute dépense. Omets-le pour couvrir toutes les locales cibles.
- `dryRun` lit, compare et rapporte sans construire ni appeler le fournisseur et sans rien écrire.
- `estimate` ajoute sur `RunSummary.estimate` une estimation de coût avant exécution et implique `dryRun` : il ne construit aucun fournisseur, ne lit aucune clé d'API et n'écrit rien. La quantité est toujours rapportée ; une somme exige un bloc `rates` dans la config nommant le fournisseur et le modèle configurés.
- `prune` supprime les clés orphelines (clés cibles absentes de la source) du fichier écrit et du verrou. `generatePlurals` synthétise les formes plurielles CLDR manquantes (i18next-JSON avec un fournisseur LLM uniquement). Les deux sont désactivés par défaut ; quand ils sont définis, chacun remplace l'option de config correspondante pour cette exécution.
- `concurrency` traduit jusqu'à ce nombre de locales cibles à la fois (par défaut 1, strictement en série). Une valeur inférieure à 1 lève `CONCURRENCY_INVALID` ; sur une exécution réelle, une valeur supérieure à 1 avec `maxTokens` configuré lève `CONCURRENCY_BUDGET_CONFLICT` (un dry-run est exempté). Une erreur globale levée alors que des locales tournent déjà empêche toute autre locale d'être démarrée, et les locales en cours terminent et libèrent leurs verrous d'écriture avant que `translate` ne rejette, donc le rejet arrive après la plus lente plutôt qu'instantanément.
- `cache` est activé par défaut et réutilise le [cache de mémoire de traduction](/docs/the-cache) local (`verbatra.cache.json`, exporté aussi comme `CACHE_FILE_NAME`) ; mets-le à false pour contourner le cache le temps de l'exécution (le `--no-cache` de la CLI).
- `onProgress` est appelé à mesure que l'exécution avance (au démarrage et à la fin de chaque locale, et par sous-lot du fournisseur), et `onLockWait` se déclenche pendant qu'un verrou d'écriture de locale est disputé. Les deux sont des callbacks de notification ; le SDK n'écrit rien de lui-même. `lockAcquireTimeoutMs` remplace la durée pendant laquelle un verrou d'écriture disputé réessaie avant d'échouer avec `LOCK_CONTENDED`.
- `maxBatchSize`, `maxTokens` et `budgetBehavior` sont réservés à la config ; il n'y a pas de surcharge par exécution.

Renvoie un `RunSummary` (voir [son anatomie plus bas](#anatomie-du-runsummary)). Les problèmes globaux lèvent une `SdkError` ; une locale seule qui échoue ne lève jamais et atterrit comme `status: "failed"` sur l'entrée de cette locale pendant que l'exécution continue.

### resolveDryRun

<AvailableFrom version="0.11.0" />

Répond si un ensemble d'options d'exécution se résout en dry run. La fonction prend le `dryRun` et
l'`estimate` que tu t'apprêtes à passer à `translate` et renvoie si cette exécution construira un
fournisseur, écrira un fichier ou dépensera quoi que ce soit. C'est le seul endroit où la règle
voulant qu'`estimate` implique `dryRun` est décidée : utilise-la dès que quelque chose autour d'une
exécution doit le savoir à l'avance, plutôt que de redire l'implication et de t'en écarter.

```ts
import { resolveDryRun, translate } from "@verbatra/sdk";

const options = { dryRun: false, estimate: true };
resolveDryRun(options); // true

const summary = await translate({ config, ...options });
```

### watch

Surveille le fichier de la locale source et relance `translate` à chaque changement temporisé. Il déclenche une exécution initiale immédiatement au démarrage, puis une exécution par changement stabilisé. Les exécutions sont sérialisées : les changements survenus pendant une exécution se regroupent en une seule exécution de suivi.

Entrée : `{ config, cwd?, locales?, debounceMs?, onRun, concurrency?, cache?, onProgress?, onLockWait?, lockAcquireTimeoutMs? }`. `debounceMs` vaut 300 par défaut. `onRun` est appelé une fois par exécution avec un `WatchRunResult` : `{ status: "succeeded", summary }` ou `{ status: "failed", error: { code, message } }`. Le SDK n'écrit aucun log ; `onRun` est la seule sortie. `concurrency`, `cache`, `onProgress`, `onLockWait` et `lockAcquireTimeoutMs` sont transmis à chaque exécution et se comportent exactement comme sur `translate`. `locales` restreint chaque exécution de la session à ce sous-ensemble et est validé une seule fois au démarrage, pas à chaque cycle.

Renvoie un `WatchController` avec une seule méthode, `stop()`, qui ferme la surveillance et attend l'exécution en cours. Trois problèmes sont refusés au démarrage, avant que la surveillance n'existe, donc `watch` lui-même rejette au lieu de renvoyer un contrôleur : un `concurrency` qui n'est pas un entier d'au moins 1 lève `CONCURRENCY_INVALID`, un `concurrency` supérieur à 1 face à une config qui fixe `maxTokens` lève `CONCURRENCY_BUDGET_CONFLICT` (il n'existe pas de watch en dry-run, donc le conflit de budget s'applique toujours), et un fichier source manquant lève `SOURCE_UNREADABLE`. Tout échec après le démarrage remonte via `onRun` et la surveillance continue.

## Pseudo-localisation

### pseudolocalize

<AvailableFrom version="0.11.0" />

Construit une locale factice à partir des seules chaînes source, si bien que les troncatures de
mise en page et les chaînes qui n'ont jamais été extraites pour la traduction apparaissent avant
même qu'une clé d'API existe. Chaque valeur est accentuée, allongée d'environ un tiers de sa
longueur traduisible et entourée des marqueurs `[` et `]`, tandis que les marqueurs de substitution
restent intacts dans toutes les syntaxes que reconnaissent les adaptateurs, y compris les branches
`plural` et `select` d'ICU, les balises de balisage et les séquences d'échappement. Elle ne
construit aucun fournisseur, ne lit aucune clé d'API et ne fait aucune requête réseau.

Chaque valeur générée passe le même contrôle d'intégrité que la traduction d'un fournisseur. Une
valeur qui ne le passerait pas est copiée telle quelle depuis la source et nommée dans `copied`
plutôt qu'écrite cassée, l'entrée reste donc présente et continue de s'afficher.

Entrée : `{ config, cwd?, locale?, out? }`. `locale` vaut `en-XA` par défaut et `out`
`.verbatra-local/pseudo`, que `verbatra init` ajoute déjà à `.gitignore` ; le `files.pattern`
configuré y est développé, le fichier garde donc la disposition qu'attend l'application. Une
pseudo-locale qui nomme une locale configurée, ou qui se poserait sur un fichier de locale
configuré, est refusée avec `PSEUDO_OUTPUT_CONFLICT` avant que quoi que ce soit ne soit lu ou
écrit, elle ne peut donc ni écraser une vraie traduction ni en tenir lieu ; il en va de même d'un
`out` absolu ou qui sort de `cwd`. Comme le fichier vit en
dehors de `files.pattern`, `translate` ne dépense jamais pour lui et `check` et `diff` ne le
signalent jamais comme désynchronisé.

Renvoie un `PseudolocalizeResult` : la `locale`, le `path` absolu, combien d'`entries` ont été
traitées, combien ont été `transformed`, les clés qui ont été `copied`, et si quelque chose a été
`written`. La transformation est déterministe, une seconde exécution sur une source inchangée ne
réécrit donc rien et signale `written` à false. Pour `xliff` et `apple-xcstrings`, dont les
écrivains ne corrigent qu'un document déjà existant, la sortie est recopiée depuis la source à
chaque écriture, si bien qu'une clé ajoutée à la source après la première exécution parvient quand
même à la pseudo-locale, et un XLIFF copié voit son `target-language` réécrit vers la
pseudo-locale.

## Catalogues typés

### generateTypes

<AvailableFrom version="0.11.0" />

Déclare le catalogue source d'un projet en TypeScript : une union de toutes les clés qu'il contient
et, par clé, les arguments que son message interpole. Type une fonction de traduction sur le
résultat et une clé mal orthographiée ou un argument d'interpolation manquant devient une erreur de
compilation au lieu d'un échec de recherche à l'exécution. Cela ne coûte rien : aucun fournisseur
n'est construit, aucune variable d'environnement contenant une clé d'API n'est lue et aucune requête
réseau n'est faite.

Un fichier est lu (le catalogue de la locale source) et un fichier est écrit (la déclaration) ; un
fichier de locale cible n'est jamais touché. Les clés sont exactement ce que l'adaptateur de format
avait déjà produit, dans l'ordre du document, si bien que deux exécutions sur un catalogue inchangé
écrivent des octets identiques. Les arguments viennent des jetons de marqueurs que l'adaptateur a
extraits, sauf dans les formats de messages ICU (`next-intl-json` et `arb`), où chaque message est
lu avec le même parseur ICU que celui de l'adaptateur. Chaque clé est émise comme un littéral de
chaîne entre guillemets : une clé portant un point, un mot réservé, un chiffre en tête, un
guillemet, ou même la clé vide, est donc déclarée telle quelle plutôt qu'abandonnée ou redécoupée,
et une clé que l'adaptateur a signalée dans `excludedLeafPaths` n'est pas déclarée du tout.

Ce qu'elle refuse d'affirmer compte autant que ce qu'elle déclare. Un message sans marqueur reçoit
une forme qui fait de tout argument passé une erreur de type ; un message dont les marqueurs nomment
leurs arguments reçoit une forme d'objet ; un message aux marqueurs numérotés ou anonymes reçoit un
tuple readonly. Un argument ICU que seules certaines branches `select` ou `plural` utilisent est
déclaré comme membre optionnel. Les types d'arguments viennent uniquement de ce que le catalogue
enregistre : `number` pour un argument ICU `number`, `plural` ou `selectordinal` et pour un
formateur ou une conversion numériques, `Date | number` pour un argument ICU `date` ou `time` et un
formateur i18next `datetime`, `string` pour un argument ICU `select` et une conversion printf de
chaîne, et un alias de `string | number` partout ailleurs, jamais un `any` permissif. Une
interpolation i18next non échappée (`{{- name}}`) est déclarée sous le nom qui suit son préfixe. Un
message que l'adaptateur a signalé comme invalide, un message qui semble à la fois nommer et
numéroter ses arguments, et un message dont un index de marqueur est hors limites sont déclarés avec
leurs arguments signalés dans `unresolved` plutôt que déclarés en silence comme n'en prenant aucun.
Les clés plurielles sœurs ne sont jamais fusionnées : chacune est déclarée à part, et celles que
l'adaptateur a marquées au pluriel sont listées.

Entrée : `{ config, cwd?, out?, configPath?, check? }`. `out` vaut par défaut `DEFAULT_TYPES_PATH`
(`verbatra-types.d.ts`). Avant toute lecture ou écriture, `TYPES_OUTPUT_CONFLICT` refuse un `out`
qui ne nomme aucun fichier, est absolu, sort de `cwd` avec `..` ou ne se termine pas par `.ts`,
`.mts` ou `.cts`, ainsi qu'un `out` qui nomme un fichier de locale configuré, le fichier de
verrouillage, le cache de mémoire de traduction, un fichier où verbatra cherche sa configuration, ou
`configPath`, le fichier de configuration d'où `config` a été chargée ; les noms sont comparés sans
tenir compte de la casse. Une exécution qui génère refuse aussi, avec le même code, de remplacer un
fichier existant qui ne commence pas par la ligne d'en-tête qu'écrit verbatra, et laisse ce fichier
intact. La liste complète se trouve sur la page de [`verbatra types`](/docs/cli/types). Avec
`check`, rien n'est écrit du tout, rien n'est refusé à cause de son contenu, et l'exécution signale
seulement si le fichier versionné correspond toujours, ce qui est exactement la forme qu'attend un
garde-fou de CI.

Renvoie un `GenerateTypesResult` : le `path` absolu, le `sourcePath` dont il a été construit,
combien de `keys` ont été déclarées et combien d'entre elles prennent au moins un argument que
verbatra a pu déterminer (`withArguments`, qui ne compte jamais une clé de `unresolved`), les clés
`unresolved` ainsi que les `excluded` et `plural`, si quelque chose a été `written`, si le fichier
sur disque était `stale` au démarrage de l'exécution, et s'il s'agissait d'une exécution `check`.

## Inspecter l'état sans écrire

Aucune de ces fonctions n'appelle de fournisseur, n'écrit de fichier ni ne modifie le verrou.

### doctor

<AvailableFrom version="0.9.0" />

Valide la configuration du projet et ne dépense rien : il ne construit aucun fournisseur, ne fait aucune requête réseau et ne lit jamais la valeur d'une clé d'API. Cinq vérifications s'exécutent, chacune avec son propre verdict `pass`, `fail` ou `skipped` : la config se charge et se valide, le format configuré se résout en un adaptateur, l'ID de fournisseur configuré se résout en une fabrique, la variable d'environnement dans laquelle ce fournisseur lit sa clé est définie, et le fichier de locale source peut être lu. Chaque vérification s'exécute même si une précédente a échoué : un seul appel signale donc tous les problèmes indépendants. La clé d'API est vérifiée par son nom uniquement. La vérification du fichier source le lit et le parse au lieu de seulement sonder son existence : un répertoire à sa place, un fichier vide et un contenu malformé sont donc tous signalés ici.

Entrée : `{ cwd?, configPath? }`. Aucune config déjà chargée n'est nécessaire : `doctor` la charge lui-même, donc un projet sans aucune config obtient quand même un rapport plutôt qu'une erreur levée. Renvoie un `DoctorResult` dont `ok` est vrai exactement quand aucune vérification n'a échoué. Il lève `CONFIG_NOT_FOUND` uniquement pour un `configPath` explicite qui n'existe pas.

### extract

<AvailableFrom version="0.11.0" />

Analyse le code de ton application à la recherche des appels de traduction et fusionne ce qu'il trouve dans le catalogue de la locale source. C'est le seul point d'entrée qui lit du code applicatif plutôt qu'un fichier de locale, et c'est ce qui rend verbatra utilisable sur un projet qui n'a pas encore de catalogue. Il ne dépense rien : aucun fournisseur n'est construit, aucune variable d'environnement contenant une clé d'API n'est lue et aucune requête réseau n'est faite.

Seul le fichier de la locale source est écrit, et seules les clés réellement nouvelles sont ajoutées : une clé déjà présente dans le catalogue conserve sa valeur telle quelle, et une clé du catalogue qu'aucun appel ne mentionne reste intacte. Une exécution qui ne trouve rien de nouveau n'écrit rien du tout. Tout ce que l'analyse ne peut pas résoudre revient sous forme de données plutôt que d'être levé : un argument de clé non statique dans `dynamic`, une clé trouvée avec deux valeurs par défaut différentes dans `conflicts` (aucune n'est écrite) et un fichier illisible dans `diagnostics`. Le résultat ne porte que des clés, des valeurs et des emplacements fichier et ligne, jamais le contenu d'un fichier source.

Entrée : `{ config, cwd?, dryRun? }`, où `config.extract` nomme le framework et les racines de code. Renvoie un `ExtractResult`. La découverte passe par le membre optionnel `readDirectory` de `SdkFs` ; un `deps.fs` qui ne l'implémente pas est signalé comme `EXTRACT_FS_UNSUPPORTED`.

### check

Rapporte la dérive par locale sous forme de comptes : `missing` (dans la source, absent de la cible), `stale` (source modifiée depuis la dernière traduction) et `upToDate`. Utilise-le comme contrôle CI.

Entrée : `{ config, cwd?, locales?, consistency? }`. Renvoie un `CheckSummary` dont `inSync` est vrai exactement quand chaque locale vérifiée n'a rien de manquant ni d'obsolète.

<AvailableFrom version="0.11.0" />

Avec `consistency: true`, chaque `LocaleCheckSummary` porte aussi `inconsistencies` : un `InconsistencyGroup` par chaîne source que la locale traduit de plusieurs façons sous des clés différentes, avec la `source`, chaque traduction distincte sous forme `{ value, keys }` et le `context`, la `description`, le `meaning`, `isPlural` et `pluralForm` que partagent les clés regroupées. Seules les clés à jour sont comparées, les valeurs sont comparées après normalisation NFC et sans les espaces de début et de fin, les clés dont la description, le sens, la marque de pluriel ou le `msgctxt` gettext diffèrent ne sont jamais regroupées, et les formes plurielles rangées sous leur propre clé sont comparées forme par forme. Ce n'est qu'un rapport : il ne change jamais `inSync`, un compte ou un fichier, et n'appelle aucun fournisseur.

### diff

Le frère détaillé de `check` : le même calcul, mais il renvoie les listes de clés par locale (`missing`, `changed`, `orphaned`) au lieu de comptes. Les clés orphelines sont rapportées seulement et ne font jamais basculer `hasPendingChanges`, puisqu'une exécution par défaut ne les supprime pas.

Avec `unused: true`, il analyse aussi les racines du bloc `extract` de la config et ajoute un rapport `unused`, séparé de chaque liste `orphaned` : les clés de la locale source qu'aucune référence statique ne nomme, dans l'ordre du catalogue. Il est en lecture seule, ne demande aucune clé et modélise le runtime i18next (appels `t` et leurs alias, préfixes statiques `keyPrefix` et `getFixedT`, clés de `Trans`, clés avec namespace et variantes de pluriel et de contexte), en comparant les clés dans l'encodage du format du catalogue. Chaque clé listée porte sa `key` décodée et son `catalogKey`. Les clés qui correspondent à `extract.unused.ignore` vont dans `ignored`, et celles qu'un template literal au début statique pourrait atteindre dans `possiblyDynamic`. Son `status` vaut `complete`, `unreliable` (avec `unreliableBecause` nommant chaque raison et ses emplacements) ou `not-run` (avec une `reason` et sans liste de clés). Toutes les raisons sont dans [Clés source inutilisées](/docs/cli/diff#clés-source-inutilisées). Le rapport ne fait jamais basculer `hasPendingChanges`.

Entrée : `{ config, cwd?, locales?, unused? }`. Renvoie un `DiffSummary`.

### keyIntegrity

Rapporte, pour les clés modifiées de chaque locale, si la valeur cible actuelle correspond toujours aux placeholders de la source, si elle porte toujours le balisage en ligne de la source et si elle est de l'ICU valide. Chaque entrée porte `key`, `hasPlaceholders`, `matches`, les jetons de placeholder `missing` et `extra` en cas de discordance, `icuValid`, `markupMatches` et `markupDetails` qui nomme les balises en cause. Les entrées ne portent jamais de valeur de chaîne source ou cible. Rapporter le balisage ici est ce qui rend visible la dérive antérieure à la porte d'écriture : une traduction écrite avant que la vérification existe, modifiée hors de verbatra, ou produite par un chemin qui n'a jamais franchi la porte est jugée ici selon la même règle. C'est le rapport d'intégrité par clé que Studio affiche.

Entrée : `{ config, cwd?, locales?, keys? }`. `keys` restreint la vérification ; seules les clés "modifiées" pour une locale sont vérifiées. Renvoie un `LocaleKeyIntegrity` par locale vérifiée.

### lockState

Rapporte l'existence du fichier de verrouillage, sa version et la dérive par locale (nombre de clés de la ligne de base, plus les comptes manquants, obsolètes et à jour). `exists` vient d'une sonde explicite, donc "pas encore de fichier de verrouillage" et "un fichier de verrouillage présent mais vide" restent distinguables. Quand le fichier est absent, le résultat est `{ exists: false }` et rien d'autre n'est lu.

Entrée : `{ config, cwd?, locales? }`. Renvoie un `LockStateResult`.

### loadLockFile

Lit le fichier de verrouillage lui-même (`verbatra.lock.json`, aussi exporté sous `LOCK_FILE_NAME`) et renvoie sa forme parsée : `{ version, locales }`, où chaque locale associe les clés au hash du contenu source depuis lequel elles ont été traduites pour la dernière fois. Un fichier manquant se dégrade en verrou vide, le même comportement de première exécution sur lequel `translate` s'appuie ; utilise `lockState` quand tu dois distinguer l'absence.

Entrée : `{ cwd? }`. Aucune config requise. Renvoie un `LockFile`.

### runStatus

Lit l'instantané des signalements de révision et de la consommation de tokens que la dernière exécution `translate` ou `watch` hors dry run a persisté dans `.verbatra-local/run-status.json`. Ne lève jamais : un fichier manquant, corrompu ou non reconnu se dégrade en `{ available: false }`. Ce fichier est de la télémétrie au mieux, pas une source de vérité.

Entrée : `{ cwd? }`. Aucune config requise. Renvoie `{ available: false }` ou `{ available: true, version, generatedAt, usage?, budget?, locales }`.

Un instantané écrit par une version antérieure à l'application du budget de tokens est toujours lu, mais son `budget` est omis quand il indique `supported: false` : à l'époque, cela voulait dire que rien n'était compté, donc son `tokensUsed: 0` n'est pas un décompte. Les instantanés écrits désormais gardent la même `version` et ajoutent seulement un champ marqueur qu'un Studio ou un serveur d'agents plus ancien ignore : un lecteur plus ancien continue donc d'afficher la file de révision et l'usage. Tant qu'il n'est pas mis à jour, il peut afficher un budget estimé comme non suivi.

## Opérations sur une seule clé

Ce sont les interfaces que Verbatra Studio pilote ; utilise-les pour construire ton propre outillage de révision. Toutes les trois résolvent `locale` et `key` à neuf à chaque appel et lèvent `UNKNOWN_LOCALE` ou `UNKNOWN_KEY` quand l'un des deux n'existe pas.

### keyValue

Lit la valeur source actuelle d'une clé et, quand elle existe, sa valeur cible actuelle pour une locale. En lecture seule.

Entrée : `{ config, cwd?, locale, key }`. Renvoie `{ source, target? }` ; `target` est absent exactement quand la clé n'existe pas encore dans cette locale.

### editEntry

Écrit une correction saisie par un humain pour une clé et une locale. La valeur candidate passe la même barrière d'intégrité qu'une traduction de fournisseur avant que quoi que ce soit n'atteigne le disque ; à l'acceptation, le fichier de locale et l'entrée de verrou de cette clé sont mis à jour sous le verrou d'écriture de la locale. N'appelle jamais de fournisseur.

Entrée : `{ config, cwd?, locale, key, value }`. Renvoie un résultat à deux branches : `{ accepted: true, value }`, ou `{ accepted: false, reason: "placeholder" | "markup" | "icu" | "degenerate" | "empty", value }` sans rien écrire. `"empty"` couvre une valeur vide ou uniquement composée d'espaces pour une source qui a du texte : une modification ne peut pas exprimer l'effacement d'une clé, alors utilise pour ça la sentinelle `[[CLEAR]]` du classeur. L'ensemble des raisons est livré sous forme du tuple `INTEGRITY_GATE_REASONS` : construis tout schéma d'exécution ou table exhaustive à partir de lui plutôt que de retaper les membres. Un refus `markup` porte en plus `details`, les balises en cause, chacune préfixée de `-` pour une que la source avait et que la candidate a perdue, ou de `+` pour une que la candidate a inventée.

### retranslateEntry

Relance le fournisseur pour exactement une clé et une locale : un appel à entrée unique via le même chemin de fournisseur que `translate`, passé par les mêmes vérifications d'intégrité. À l'acceptation, il écrit le fichier de locale et l'entrée de verrou pour cette clé seulement.

Entrée : `{ config, cwd?, locale, key }`. Renvoie `{ accepted: true, value, reviewReasons }` (les codes de raison de révision, s'il y en a, qui s'appliquent à la nouvelle valeur) ou `{ accepted: false, reason: "placeholder" | "markup" | "icu" | "degenerate" | "empty", value }`. Contrairement à `translate`, un échec de fournisseur lève ici : une `ProviderError` de `@verbatra/ai-providers` avec un code stable comme `RATE_LIMITED` ou `AUTH_FAILED`.

### localeValues

Lit le texte source et cible actuel de chaque clé, sur chaque locale cible demandée, en un seul passage sur les fichiers déjà présents sur le disque. C'est le pendant en masse de `keyValue` : utilise-la quand tu as besoin de contenu de traduction en masse, par exemple pour chercher ou parcourir des valeurs plutôt que de simples noms de clé, puisque `keyValue` ne répond que pour une clé à la fois. En lecture seule.

## Instantanés de fichiers de locale

Les briques d'un observateur à rafraîchissement en direct comme celui de Studio : capture l'état d'un fichier de locale, puis compte ce qui a changé depuis.

### readLocaleFileSnapshot

Lit un fichier de locale (la locale source ou n'importe quelle locale cible) et le réduit à un hash de contenu par clé. Un fichier qui n'existe pas encore se lit comme un instantané vide plutôt que de lever.

## Chemins de locale

### createLocalePathResolver

Résout la correspondance entre locales et chemins du projet dans les deux sens, à partir de
`files.pattern`, des locales configurées et de `files.localeStyle`. `createLocalePathResolver(cwd,
config)` renvoie `{ pathFor, localeFor }` : `pathFor(locale)` est le chemin absolu du fichier d'une
locale, et `localeFor(path)` est la locale à laquelle appartient un chemin, ou `undefined` pour un
chemin qui n'appartient pas à ce projet. Tous les points d'entrée du SDK résolvent les chemins par
lui, donc un watcher ou un tableau de bord bâti sur le SDK voit exactement les chemins qu'une
exécution écrit.

Toutes les vérifications ont lieu à la création du resolver, avant toute lecture de fichier : un
pattern et un style incompatibles, ou une locale pour laquelle le style n'a pas d'écriture
correcte, lèvent `LOCALE_LAYOUT_INVALID`, et deux locales qui résolvent vers le même chemin lèvent
`LOCALE_PATH_COLLISION`.

## La paire classeur

La passation pour les traducteurs humains, sous forme de classeur Excel ou de texte délimité ; voir [Traduction humaine](/docs/manual-translation).

### exportWorkbook

Écrit les chaînes encore à traduire (clés manquantes et modifiées par locale ; ajoute les inchangées avec `includeUnchanged`) dans un classeur `.xlsx` stylisé. Les lignes portent le même signal de révision qu'une exécution translate calcule. Aucun appel de fournisseur, aucune écriture du verrou.

Entrée : `{ config, cwd?, out?, locales?, includeUnchanged?, format? }`. `format` vaut `xlsx` par défaut ; `csv` et `tsv` écrivent à la place un `<locale>.csv` ou `<locale>.tsv` par locale, donc `out` désigne pour eux un répertoire (créé s'il manque) et un chemin de fichier pour `xlsx`. `out` vaut par défaut `DEFAULT_WORKBOOK_PATH` (`verbatra-translations.xlsx`) ou `DEFAULT_DELIMITED_PATH` (`verbatra-translations`), tous deux exportés comme constantes. Les valeurs acceptées sont exportées comme `EXCHANGE_FORMATS` et la valeur par défaut comme `DEFAULT_EXCHANGE_FORMAT`, pour qu'un outil qui enveloppe le SDK puisse valider un argument de format sans coder la liste en dur. Renvoie `{ path, locales }` : le chemin absolu écrit et un compte de lignes par locale.

### importWorkbook

Relit un classeur rempli dans les fichiers de locale, en exécutant les mêmes vérifications de dérive de source et d'intégrité que `translate`. Seules les lignes acceptées font avancer leur ligne de base du verrou ; une ligne vide ou rejetée continue de se réexporter jusqu'à sa vraie résolution.

Entrée : `{ config, workbook, cwd?, dryRun?, format? }`. Avec `csv` ou `tsv`, `workbook` est soit un seul fichier de remise, soit le répertoire qui en contient un par locale, et la locale vient du nom du fichier. Renvoie la même forme `RunSummary` que `translate` (avec `needsReview` toujours vide, puisqu'aucun fournisseur n'intervient). Une feuille pour une locale qui n'est pas une cible configurée fait échouer cette locale avec `CONFIG_INVALID` comme donnée sur le résumé, pas comme exception.

## La paire TMX

`importTmx` et `exportTmx` font entrer et sortir la [mémoire de traduction](/docs/the-cache) en TMX,
le format d'échange que produisent et lisent les principales plateformes de traduction. Aucune des
deux ne construit un fournisseur, ne lit une clé d'API ni ne fait de requête réseau : chaque valeur
vient du fichier ou de la mémoire déjà présente sur le disque. Ce n'est pas la paire classeur dans un
autre format. La paire classeur remet à une traductrice une tranche par locale du delta en attente ;
cette paire déplace la mémoire entière sous la forme d'un seul fichier multilingue entre outils.

### importTmx

Lit un fichier TMX dans la mémoire du projet. Entrée :
`{ config, file, cwd?, dryRun?, overwrite?, locales? }`.

Rien du fichier n'est tenu pour fiable. Le XML est analysé sous le durcissement du paquet d'échange,
si bien qu'une déclaration d'entité, un sous-ensemble DTD interne, un fichier surdimensionné ou mal
formé est refusé par une erreur structurée `SOURCE_INVALID` plutôt qu'analysé. Quand le problème a
un emplacement dans le fichier, le message indique la ligne, la colonne et, à l'intérieur d'une
unité de traduction, son rang en comptant à partir de 1, et `tmxErrorLocation(error)` renvoie le
même emplacement sous forme de `TmxErrorLocation`, ou `undefined` pour toute autre erreur, si bien
que tu n'as jamais à caster l'erreur ni son `cause`. Une étiquette de langue est résolue vers une
locale configurée par une règle explicite : écriture exacte après mise en minuscules et conversion
des tirets bas en traits d'union ; à défaut, la plus longue locale configurée qui est un préfixe de
sous-étiquettes de l'étiquette (recherche de la RFC 4647), ou sinon une locale configurée qui ne
prolonge l'étiquette que par des sous-étiquettes de région ou de variante, jamais par une écriture,
si bien que deux étiquettes aux sous-étiquettes d'écriture ou de région différentes (`zh-CN` et
`zh-TW`) ne correspondent jamais ; et une étiquette n'est signalée comme ambiguë que lorsque les
locales qu'elle pourrait atteindre ne se trouvent pas sur une même chaîne de préfixes. Les segments
d'une unité qui se résolvent vers la même locale, locale source comprise, ne laissent jamais le
dernier l'emporter : une étiquette exacte l'emporte sur une correspondance par préfixe, et deux
segments de même rang aux valeurs différentes ne stockent rien pour cette locale et sont comptés
comme `conflicting` (pour la locale source, l'unité est refusée et comptée dans
`conflictingSourceUnits`). Chaque traduction candidate passe ensuite la même barrière de variables,
de balisage en ligne, d'ICU, de dégénérescence et de vacuité que subissent déjà la sortie du fournisseur et une ligne de
classeur remplie, vérifiée à l'entrée de l'enregistrement dans la mémoire plutôt que laissée à
l'exécution qui la lira plus tard.

Quand une unité importée contredit une traduction que la mémoire possède déjà, la mémoire l'emporte,
sauf si `overwrite` est passé. Les unités sont stockées sous l'empreinte de configuration actuelle,
la même clé qu'écrit une exécution réelle, et cessent donc de correspondre dès que le fournisseur, le
modèle, le ton ou le glossaire changent. Importer deux fois le même fichier ne change rien la seconde
fois.

Face à des données abîmées, renvoie un rapport au lieu de lever : combien d'unités ont été lues, un
décompte par locale de `added`, `unchanged`, `overwritten`, `kept`, `duplicates`, `conflicting` et
`rejected` par motif, plus les unités ignorées, sans segment source, ayant perdu leur balisage en
ligne ou dont le texte `sub` a été laissé de côté (`subflowDroppedUnits`), et les étiquettes de
langue sans correspondance ou à correspondance ambiguë. `memoryWritable` vaut `false` quand le
fichier de mémoire a été écrit par un verbatra plus récent, auquel cas il est laissé intact.

### tmxErrorLocation

Lit, à partir de ce que `importTmx` a levé, où un fichier TMX refusé a échoué. Renvoie une
`TmxErrorLocation` (`{ line, column, unit? }`, le tout en comptant à partir de 1) pour un refus
`SOURCE_INVALID` qui a un emplacement dans le fichier, et `undefined` pour toute autre erreur, y
compris un fichier absent ou surdimensionné, si bien que tu n'as jamais à caster l'erreur ni son
`cause`.

```ts
try {
  await importTmx({ config, file: "legacy.tmx" });
} catch (error) {
  const at = tmxErrorLocation(error);
  if (at !== undefined) console.error(`line ${at.line}, column ${at.column}`);
}
```

### exportTmx

Écrit la mémoire en TMX 1.4b. Entrée : `{ config, out?, cwd?, locales?, toolVersion? }`, où `out`
vaut par défaut `DEFAULT_TMX_PATH` (`verbatra-memory.tmx`), exporté comme constante. Seules les
entrées sous l'empreinte de configuration actuelle sont écrites, c'est-à-dire l'ensemble qu'une
exécution réutiliserait. Les étiquettes de langue sont écrites sous forme BCP 47 (`en_US` devient
`en-US`), ce qui ne change pas l'indexation de la mémoire. Une mémoire vide produit un fichier
valide et vide, pas une erreur. Renvoie `{ path, units, locales, withoutSource,
illegalCharactersRemoved }` ; `withoutSource` compte les entrées laissées de côté parce que la
mémoire n'a pas de texte source pour elles, ce qui n'arrive qu'aux entrées héritées d'un cache écrit
avant que la mémoire ne stocke le texte source, et `illegalCharactersRemoved` compte les caractères
que XML 1.0 ne peut pas représenter et qui ont été retirés du texte des segments.

## Config
### loadConfig

Trouve, charge et valide la config du projet, en renvoyant une `VerbatraConfig`. Options : `{ cwd?, configPath?, configOverride? }`, avec la précédence `configOverride` (valider un objet en mémoire) sur `configPath` (charger un fichier explicite) sur la recherche. La recherche démarre à `cwd` et couvre `verbatra.config.ts` (aussi `.js`/`.cjs`), la famille `.verbatrarc` (`.json`, `.yaml`, `.yml`, `.js`, `.cjs`, `.ts`) et une propriété `"verbatra"` dans `package.json`. Un `glossary` donné comme chemin de fichier est lu et validé ici, donc le code en aval voit toujours un simple enregistrement.

Lève `CONFIG_NOT_FOUND` quand rien n'est trouvé, `CONFIG_INVALID` quand une config est trouvée mais invalide. Voir [Le fichier de configuration](/docs/config-file) pour le schéma.

### loadConfigWithMeta

Le même chargement, plus la provenance : renvoie `{ config, source, glossary }`, où `source` dit si la config vient d'une recherche, d'un chemin explicite ou d'une surcharge en mémoire (avec le `filepath` absolu quand il y en a un), et `glossary` note si le glossaire était absent, inline ou résolu depuis un fichier. Utilise-le quand tu dois afficher d'où vient la config.

### readGlossaryFile

<AvailableFrom version="0.9.0" />

Lit un glossaire stocké dans un fichier directement depuis le disque et le renvoie sous forme de table plate de termes. Prend `{ glossary }`, la `GlossaryProvenance` renvoyée par `loadConfigWithMeta`, si bien que le fichier lu est toujours celui que la config nomme ; il n'y a aucun argument de chemin. Utilise-le dans un outil de longue durée qui doit montrer le glossaire tel qu'il est maintenant, et non tel qu'il était au chargement de la config.

Lève `GLOSSARY_NOT_FILE_BACKED` quand le glossaire est inline ou absent, et `CONFIG_INVALID` quand le fichier est manquant, trop volumineux, non UTF-8, invalide en JSON ou n'est pas une table plate de chaînes.

### updateGlossaryTerm

<AvailableFrom version="0.9.0" />

Ajoute, remplace ou supprime exactement un terme d'un glossaire stocké dans un fichier et renvoie le glossaire tel qu'il est désormais. Prend `{ glossary, cwd?, term, translation }`, où `translation` est le nouveau texte ou `null` pour supprimer le terme. Le reste du fichier garde son ordre de clés et son indentation, l'écriture est atomique, et tout le cycle lecture, modification, écriture se déroule sous un verrou de glossaire valable pour le projet entier : deux modifications simultanées sont donc sérialisées plutôt qu'entrelacées.

Un glossaire inline est refusé avec `GLOSSARY_NOT_FILE_BACKED` plutôt que converti : il vit dans un module de config exécutable. Un terme ou une traduction vide, ainsi qu'une modification dont le résultat dépasserait la limite de 1 Mio du glossaire, sont refusés avec `CONFIG_INVALID` ; une écriture en échec donne `GLOSSARY_UNWRITABLE`.

### defineConfig

Un assistant identité pour écrire un `verbatra.config.ts` typé : il renvoie son argument inchangé et n'existe que pour l'inférence de types et l'autocomplétion de l'éditeur, y compris la complétion des IDs de modèles connus du fournisseur sélectionné. La restriction de modèle ne vaut qu'à l'écriture ; à l'exécution, toute chaîne non vide passe la validation.

### verbatraConfigSchema

Le schéma zod avec lequel `loadConfig` valide, exporté pour que ton propre outillage puisse valider un objet de config de la même façon que le SDK. Les clés de premier niveau inconnues sont rejetées, donc un secret égaré ne peut pas se cacher dans la config. La seule exception est `$schema`, une chaîne optionnelle acceptée pour qu'une config JSON ou YAML puisse pointer un éditeur vers le document JSON Schema que le paquet livre sous `@verbatra/sdk/config-schema.json`. Elle est ignorée à l'exécution.

### scaffoldingMetadata

Métadonnées en lecture seule dont la commande `init` de la CLI dérive ses questions : `providerEnv` (id de fournisseur vers la variable d'environnement où sa clé est lue), `scaffoldModels` (un modèle d'échafaudage par défaut par fournisseur LLM), `providerTokenLimitKeys` (la clé d'option sous laquelle chaque fournisseur LLM reçoit sa limite de tokens de sortie) et `supportedFormats` (l'ensemble fermé des ids de format). Lis la clé de limite de tokens dans `providerTokenLimitKeys` plutôt que d'en supposer une : Anthropic l'appelle `maxTokens` et les autres `maxOutputTokens`, le schéma valide strictement les options de chaque fournisseur, et DeepL n'a pas d'entrée car il ne prend aucune limite de tokens. Le type `ScaffoldableProviderId` couvre les quatre fournisseurs hébergés ; `openai-compatible` en est exclu parce qu'il n'a pas de variable d'environnement unique requise.

## Adaptateurs de format

<AvailableFrom version="0.11.0" />

Tout ce qu'il faut pour construire un adaptateur de format que verbatra ne fournit pas et l'enregistrer à côté des adaptateurs intégrés. Un format venu d'ailleurs que verbatra se nomme avec un identifiant `custom:`, par exemple `custom:toml`, que la configuration accepte exactement comme un nom intégré. Voir [Adaptateurs de format personnalisés](/docs/custom-format-adapters) pour le parcours complet, y compris ce à quoi tu accordes ta confiance en installant un adaptateur tiers : c'est du code pleinement de confiance, et verbatra ne le met pas en bac à sable.

### createDefaultRegistry

Construit une `AdapterRegistry` contenant tous les adaptateurs fournis par verbatra, dans l'ordre de détection. Pars de là plutôt que d'une registry vide, pour que ton format rejoigne les adaptateurs intégrés au lieu de les remplacer, puis passe le résultat comme `deps.adapterRegistry` à n'importe quel flow. `register` renvoie la registry, les enregistrements s'enchaînent donc, et lève une `AdapterError` avec le code `DUPLICATE_FORMAT` si le format est déjà pris.

```ts
import { createDefaultRegistry, translate } from "@verbatra/sdk";

const adapterRegistry = createDefaultRegistry().register(tomlAdapter);
const summary = await translate({ config }, { adapterRegistry });
```

### createFlatFileAdapter

Construit un `FormatAdapter` pour un format plat clé/valeur, où chaque entrée est adressée par une seule clé sans imbrication. Tu fournis les `parseEntries`, `serializeEntries` et `extractPlaceholders` propres à ton format ; la fabrique fournit la lecture bornée en taille, l'écriture atomique, la détection par extension et la gestion structurée des erreurs. Donne-lui un `sniff` dès que ton extension est générique, sinon ton adaptateur revendique tous les fichiers qui la partagent et la détection signale une ambiguïté au lieu de choisir.

### createTreeFileAdapter

Construit un `FormatAdapter` pour un format arborescent, dont les entrées vivent sur des chemins à travers des objets imbriqués. Il prend `parse` et `serialize` sur un arbre plus un `deriveEntry` qui indique les marqueurs de chaque feuille et si elle est une forme plurielle, et gère lui-même l'aplatissement et la reconstruction. Il porte aussi les hooks optionnels dont un format structuré a besoin : `validateTree`, `validateMessage`, `comparePlaceholders`, `deriveDescriptions` et `keyMode`.

### nodeAdapterFs

Le port système de fichiers, de type `AdapterFs`, que chaque fabrique d'adaptateur utilise quand aucun n'est fourni : une lecture bornée en taille qui signale un fichier absent ou trop grand comme un état plutôt qu'en levant, et une écriture qui passe par un fichier temporaire puis un renommage, de sorte qu'une écriture interrompue ne laisse jamais un fichier de locale à moitié fini. Dans un adaptateur à toi, lis et écris par ce port plutôt que d'aller chercher `node:fs`. C'est une convention, pas une frontière, et verbatra ne peut pas l'imposer à du code qui ne lui appartient pas.

### isCustomFormatId

Restreint un identifiant de format à un identifiant tiers : true pour un identifiant `custom:` bien formé, false pour tout nom de format intégré. Utile quand ton propre outillage doit distinguer les deux, par exemple pour décider s'il faut fournir une registry avant qu'une configuration puisse tourner.

## Le point d'injection de dépendances

<AvailableFrom version="0.9.0" />

`deps.fs` remplace le port de système de fichiers par lequel passe l'I/O propre au SDK, typé `SdkFs`. Le point d'injection est complet : le fichier d'état d'exécution, le fichier de verrouillage, le glossaire de la config, l'I/O de classeur et d'échange, ainsi que les fichiers de locale eux-mêmes y passent tous, car les adaptateurs de format lisent et écrivent via un port construit à partir du même objet. Une exécution entière peut donc être tenue en mémoire : c'est ainsi que les tests du SDK évitent de toucher au disque, et qu'une application hôte peut adosser une partie d'un projet à autre chose qu'un disque local.

```ts
import { translate, type SdkFs } from "@verbatra/sdk";

const summary = await translate({ config }, { fs: inMemoryFs satisfies SdkFs });
```

Une implémentation doit respecter deux points du contrat. Les lectures sont bornées en taille : `readFileBounded` et `readBytesBounded` prennent une limite d'octets et rapportent `missing` ou `too-large` comme un état plutôt que de lever, ce qui empêche un fichier hostile ou accidentellement énorme d'épuiser la mémoire. Les écritures doivent être atomiques, pour qu'un crash en cours d'écriture ne laisse jamais un fichier à moitié écrit, et `createExclusive` doit être atomique face aux autres processus, car c'est la primitive derrière le verrou d'écriture par locale. La création de répertoires revient à l'appelant.

`readDirectory` est optionnel, pour qu'une implémentation écrite avant l'extraction depuis le code continue de compiler. [`extract`](#extract) est le seul point d'entrée qui en a besoin, et signale son absence par `EXTRACT_FS_UNSUPPORTED`. Il liste les entrées immédiates d'un répertoire sous la forme `{ name, kind }`, où `kind` vaut `"file"`, `"directory"` ou `"other"`. Un lien symbolique relève de `"other"` : l'analyse ne le suit jamais, et c'est ce qui la maintient à l'intérieur des racines qu'on lui a données.

La seule chose que `deps.fs` n'atteint pas est un `deps.adapterRegistry` fourni par l'appelant. Ces adaptateurs ont été construits par l'appelant, donc leur accès aux fichiers est celui que l'appelant y a câblé. Fournir les deux signifie que l'appelant possède ce câblage.

## Anatomie du RunSummary

`translate`, `importWorkbook` et chaque exécution `watch` réussie se résolvent en un `RunSummary` :

```ts
interface RunSummary {
  dryRun: boolean;          // true when nothing was written and no provider was called
  locales: LocaleSummary[]; // one entry per target locale, in config order
  succeeded: string[];      // locales whose run succeeded
  partial: string[];        // locales written with keys still missing; the CLI exits 1 on these
  failed: string[];         // locales whose run failed
  usage?: UsageSummary;     // summed input/output tokens; absent when no call reported usage
  budget?: RunBudget;       // present only when maxTokens is configured
  estimate?: RunEstimate;   // present only when the run was asked for a pre-run estimate
}

interface LocaleSummary {
  locale: string;
  status: "succeeded" | "partial" | "failed";
  translated: string[];          // keys translated this run (in dry-run, keys that would be)
  cacheHits: string[];           // keys served from the translation-memory cache this run
  fuzzyHits: FuzzyCacheHit[];    // reuses for a source string that changed, with their scores
  unchanged: string[];           // keys already up to date
  orphaned: string[];            // target keys with no matching source key (always reported)
  pruned: string[];              // orphaned keys removed this run; empty unless pruning is on
  invalidIcuSource: string[];    // source keys skipped for invalid ICU
  integrityMismatches: string[]; // translations withheld for a placeholder mismatch
  providerFailures: string[];    // keys withheld because nothing was translated for them
  budgetWithheld: string[];      // keys never sent because a "stop" budget already tripped
  generated: string[];           // CLDR plural forms synthesized this run
  unfilled: string[];            // import only: blank rows whose key still needs a translation
  malformedRows: { row: number; line?: number; column: string }[]; // import only: rows the reader could not parse
  duplicateKeys: { key: string; row: number; line?: number }[];    // import only: later rows for a duplicated key
  notices: LocaleNotice[];       // provider notices and SDK notices for this locale
  needsReview: { key: string; reasons: string[] }[]; // accepted keys flagged for a second look
  usage?: UsageSummary;          // this locale's summed tokens; absent if nothing reported usage
  error?: { code: string; message: string }; // present only when status is "failed"
}
```

Les parties à connaître :

- **needsReview** liste les clés acceptées et écrites que les heuristiques de révision ont signalées, chacune avec ses codes de raison : `LENGTH_RATIO_OUTLIER`, `MAX_LENGTH_EXCEEDED`, `EQUALS_SOURCE`, `GLOSSARY_TERM_MISSED`, `INTEGRITY_REORDERED`, `PROVIDER_DEGRADED` et `FUZZY_CACHE_REUSE`. L'ensemble est livré sous forme du tuple `REVIEW_REASON_CODES` : construis tout schéma d'exécution ou table exhaustive à partir de lui plutôt que de retaper les membres. Un signalement de révision est consultatif et ne retient jamais une clé, donc une clé n'apparaît jamais à la fois dans `needsReview` et `integrityMismatches`. Voir [Sûreté de la traduction](/docs/translation-safety) pour la signification de chaque code et [Réviser les traductions dans Studio](/docs/review-in-studio) pour traiter la file.
- **notices** vivent par locale, jamais au premier niveau. Ils couvrent les avis de fournisseur (par exemple une dégradation DeepL) et les avis du SDK avec les codes `PLURAL_CATEGORIES_INCOMPLETE`, `SUB_BATCH_FAILED`, `BLANK_ROW_BASELINE_RETAINED`, `BUDGET_TOKENS_EXCEEDED` et `CACHE_VERSION_UNRECOGNIZED`. L'avis de cache concerne toute l'exécution (un seul fichier, partagé par chaque locale), il est donc attaché à chaque locale de l'exécution.
- **usage** est `undefined`, jamais un zéro fabriqué, dès que rien dans ce périmètre n'a rapporté d'usage : un dry run n'appelle jamais de fournisseur, et DeepL ne rapporte jamais de tokens. `RunSummary.usage` est la somme sur les locales.
- **budget** n'apparaît que quand `maxTokens` est configuré : `{ maxTokens, behavior, supported, tokensUsed, exceeded }`. `supported` indique si `tokensUsed` est entièrement l'usage rapporté par le fournisseur lui-même ; il vaut `false` dès qu'une requête revient sans chiffre exploitable, et le total est alors en partie la projection de verbatra, comptée et appliquée de la même façon. Un dry run le rapporte avec `tokensUsed: 0`, puisque rien n'a été envoyé. Sous `behavior: "stop"`, le plafond est vérifié avant chaque requête que l'exécution envoie, y compris chaque moitié d'une requête redécoupée, donc `tokensUsed` finit au plafond ou en dessous, à un résidu près : la dernière requête admise est réconciliée avec ce que le fournisseur a rapporté, ce qui peut pousser le total au-dessus du plafond après coup. Plus rien n'est envoyé ensuite. Deux choses échappent à ce qu'une réservation peut borner, car elles se produisent à l'intérieur d'une requête déjà admise : la couche fournisseur envoie une requête de réparation qui lui est propre quand des clés manquent, donc un lot admis peut coûter jusqu'à près du double de sa projection, et le compte ne vaut que ce que rapporte le fournisseur. Les deux arrivent à la réconciliation, et plus rien n'est admis ensuite. Le budget borne un appel à `translate` : `watch` en démarre un neuf par exécution, et `retranslateEntry` n'est pas couvert du tout.
- **error.code** sur une locale échouée est une chaîne préservée (le code du fournisseur ou de l'adaptateur sous-jacent, avec `LOCALE_FAILED` seulement en dernier recours), donc ne le traite pas comme un ensemble fermé.
- **cacheHits** liste les clés servies depuis le [cache de mémoire de traduction](/docs/the-cache) plutôt que par le fournisseur. **fuzzyHits** liste les clés qui ont réutilisé une traduction pour une chaîne source qui avait changé, chacune portant `key`, `similarity` et le `previousSource` correspondant ; elle est vide tant que `fuzzyCache` n'est pas activé, et ces clés ne sont jamais comptées dans **cacheHits**. **unfilled**, **malformedRows** et **duplicateKeys** ne sont remplis que par `importWorkbook` (une exécution `translate` les laisse vides) : une ligne vide dont la clé demande toujours une traduction au moment de l'import (qu'elle ait été exportée comme `new` ou comme `changed`), une ligne du classeur que le lecteur n'a pas pu analyser, et une clé en double dont la première occurrence a gagné. Le `line` optionnel des deux derniers est la ligne du fichier où commence l'enregistrement, présent uniquement pour un import délimité (`csv` ou `tsv`).

### budgetStanding

<AvailableFrom version="0.11.0" />

Transforme un `RunBudget` en l'une des trois valeurs `BudgetStanding`, la même classification que rapportent la ligne de budget de la CLI, Studio et l'outil d'agent `usage.summary` : `"within"` quand l'exécution n'a jamais atteint son plafond, `"stopped-before-ceiling"` quand un budget `"stop"` a retenu une requête alors que `tokensUsed` restait sous `maxTokens`, et `"reached"` quand `tokensUsed` a atteint ou dépassé `maxTokens`. Utilise-la plutôt que de lire seulement `exceeded`, qui vaut `true` dans les deux derniers cas.

## Le modèle d'erreur

Les échecs globaux lèvent une `SdkError` : une seule classe, un `code` stable et un `message` sans secret. Branche-toi sur le code, pas sur le message. Les échecs par locale, les avis de fournisseur et les constats d'intégrité remontent comme données sur le `RunSummary`, jamais comme exceptions.

| Code | Quand |
| --- | --- |
| `CONFIG_NOT_FOUND` | aucune config trouvée par la recherche, ou un `configPath` explicite n'existe pas (levé par `loadConfig`) |
| `CONFIG_INVALID` | une config a été trouvée mais est imparsable ou échoue la validation, ou son fichier de glossaire n'a pas pu être résolu |
| `UNKNOWN_FORMAT` | aucun adaptateur n'est enregistré pour le format configuré ; levé avant toute lecture de fichier |
| `UNKNOWN_LOCALE` | une locale demandée n'est pas parmi les locales cibles configurées |
| `UNKNOWN_KEY` | une clé demandée n'est pas dans la ressource source (`keyValue`, `editEntry`, `retranslateEntry`) |
| `PROVIDER_CONSTRUCTION_FAILED` | le fournisseur n'a pas pu être construit ; enveloppe l'erreur du fournisseur lui-même, y compris une clé d'API manquante |
| `SOURCE_UNREADABLE` | le fichier de la locale source n'existe pas |
| `SOURCE_INVALID` | le fichier de la locale source n'a pas pu être lu ou parsé ; enveloppe l'erreur de lecture de l'adaptateur |
| `LOCK_FILE_INVALID` | le fichier de verrouillage est présent mais corrompu, trop volumineux ou à une version non prise en charge |
| `LOCK_CONTENDED` | le verrou d'écriture d'une locale n'a pas pu être acquis avant son délai ; le message nomme le chemin du fichier de verrou |
| `GLOSSARY_NOT_FILE_BACKED` | le glossaire de la config est inline ou absent : il n'y a donc aucun fichier de glossaire à lire ou à réécrire (`readGlossaryFile`, `updateGlossaryTerm`) |
| `GLOSSARY_UNWRITABLE` | le fichier de glossaire n'a pas pu être écrit (`updateGlossaryTerm`) |
| `LOCALE_LAYOUT_INVALID` | `files.pattern` et `files.localeStyle` ne peuvent pas être combinés, ou le style n'a pas d'écriture de chemin valide pour une locale configurée |
| `LOCALE_PATH_COLLISION` | deux locales configurées résolvent vers le même chemin absolu |
| `CONCURRENCY_INVALID` | `concurrency` a été défini mais n'est pas un entier d'au moins 1 ; levé avant l'exécution de toute locale |
| `CONCURRENCY_BUDGET_CONFLICT` | une exécution réelle a défini `concurrency` au-dessus de 1 alors que `maxTokens` est configuré ; levé avant tout appel au fournisseur (un dry-run est exempté) |
| `TARGET_UNWRITABLE` | un fichier de locale cible n'a pas pu être écrit (son répertoire n'est pas inscriptible, n'existe pas, est en lecture seule ou est plein) ; le message nomme le fichier cible et le code du système de fichiers, jamais le fichier temporaire interne qu'utilise l'écriture atomique |
| `SOURCE_UNWRITABLE` | le fichier de la locale source n'a pas pu être écrit (`extract` uniquement) ; `xliff` et `apple-xcstrings` l'atteignent quand aucun catalogue n'existe encore, car ni l'un ni l'autre n'est créé à partir de rien |
| `EXTRACT_NOT_CONFIGURED` | `extract` a été appelé avec une config qui ne porte aucun bloc `extract` |
| `EXTRACT_FS_UNSUPPORTED` | `extract` a reçu un `deps.fs` qui n'implémente pas `readDirectory` : aucun fichier source ne peut donc être découvert |
| `LOCALE_FAILED` | jamais levé : le `code` de repli enregistré sur l'`error` d'une locale échouée |

Deux exceptions à la règle de la classe d'erreur unique : `retranslateEntry` relance la `ProviderError` du fournisseur quand l'appel unique échoue, et `runStatus` ne lève jamais. Pour la correspondance entre ces codes et les codes de sortie de la CLI, voir [CI et codes de sortie](/docs/ci-and-exit-codes) ; pour de l'aide par symptôme, voir [Dépannage](/docs/troubleshooting).
