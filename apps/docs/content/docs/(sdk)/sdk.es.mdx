`@verbatra/sdk` es el motor sobre el que corre el comando `verbatra`. La CLI es una envoltura fina, así que todo
lo que hace la línea de comandos lo puedes hacer en código. Esta página cataloga toda la superficie pública,
agrupada por la tarea que hace cada punto de entrada. Para ejemplos de principio a fin, consulta
[Recetas del SDK](/docs/programmatic-api).

## Instalación

```npm
npm install --save-dev @verbatra/sdk
```

Requiere Node.js `>=22.14.0`.

La línea de pnpm instala bien, pero sale con `1` y `ERR_PNPM_IGNORED_BUILDS`: pnpm bloquea los
scripts de instalación del SDK de Gemini incluido y de su `protobufjs`, y deja un
`pnpm-workspace.yaml` sin responder con el que cualquier comando pnpm posterior del proyecto falla
igual. Ejecuta `pnpm approve-builds` una vez y no apruebes ninguna de las dos entradas, o consulta
la [Solución de problemas](/docs/troubleshooting) para la solución no interactiva. Aquí no hay
atajo con `npx` como en la CLI, porque estás importando una biblioteca, no ejecutando un binario.

<Callout title="Las claves de API y el entorno">
El SDK nunca lee, guarda ni acepta una clave de API. El proveedor lee su clave del entorno
(por ejemplo `ANTHROPIC_API_KEY`) cuando se construye. A diferencia de la CLI, el SDK no carga
archivos `.env`: en tu propio script, define tú la variable, por ejemplo con
`node --env-file=.env script.js`.
</Callout>

Cada punto de entrada toma un objeto de entrada cuyo primer campo es la `config` validada (de
`loadConfig`), salvo donde se indica. La mayoría también acepta un segundo argumento opcional `deps` que
inyecta un registro, un constructor de proveedor o un sistema de archivos; puedes ignorarlo
en el uso normal. Consulta
[El punto de inyección de dependencias](#el-punto-de-inyección-de-dependencias) para ver hasta dónde
llega `deps.fs`.

## Ejecuta traducciones

### translate

El flujo de una sola pasada: leer el origen, comparar cada locale de destino con la línea base del
bloqueo, enviar al proveedor las claves faltantes y modificadas, ejecutar las comprobaciones de
integridad, escribir los archivos de locale y actualizar el bloqueo.
Úsalo para scripts, pasos de build y jobs de CI.

Entrada: `{ config, cwd?, locales?, dryRun?, estimate?, prune?, generatePlurals?, concurrency?, cache?, humanEdits?, maxTokens?, onProgress?, onLockWait?, lockAcquireTimeoutMs? }`.

- `locales` restringe la ejecución a un subconjunto de los locales de destino configurados, igual
  que en `check` y `diff`. Un locale no configurado lanza `UNKNOWN_LOCALE` antes de leer o gastar
  nada. Omítelo para cubrir todos los locales de destino.
- `dryRun` lee, compara e informa sin construir ni llamar al proveedor y sin escribir nada.
- `estimate` añade en `RunSummary.estimate` una estimación de coste previa a la ejecución e implica
  `dryRun`: no construye ningún proveedor, no lee ninguna clave de API y no escribe nada. La cantidad
  se informa siempre; una cifra en moneda necesita un bloque `rates` en la configuración que nombre
  el proveedor y el modelo configurados.
- `prune` elimina del archivo escrito y del bloqueo las claves huérfanas (claves de destino ausentes
  del origen). `generatePlurals` sintetiza las formas de plural CLDR que faltan (solo i18next-JSON con
  un proveedor LLM). Ambos están desactivados por defecto; cuando se definen, cada uno anula la opción
  de configuración correspondiente para esa ejecución.
- `concurrency` traduce hasta ese número de locales de destino a la vez (por defecto 1, estrictamente
  en serie). Un valor menor que 1 lanza `CONCURRENCY_INVALID`; en una ejecución real, un valor mayor
  que 1 con un presupuesto `maxTokens` lanza `CONCURRENCY_BUDGET_CONFLICT` (un dry run queda exento). Un
  error de toda la ejecución que surge cuando ya hay locales en marcha impide que se arranque
  ningún locale más, y los locales en vuelo terminan y liberan sus bloqueos de escritura antes de que
  `translate` rechace, así que el rechazo llega después del más lento en vez de al instante.
- `cache` está activado por defecto y reutiliza la [caché de memoria de traducción](/docs/the-cache)
  local (`verbatra.cache.json`, exportada también como `CACHE_FILE_NAME`); ponlo en false para omitir
  la caché en la ejecución (el `--no-cache` de la CLI).
- `humanEdits` (desde 0.12.0) sobrescribe el `humanEdits` de la configuración para esta ejecución: `"overwrite"` retraduce también las claves obsoletas cuyo valor escribió, importó o cambió una persona fuera de verbatra (el `--include-human` de la CLI). Por defecto esas claves se conservan y se listan en `LocaleSummary.protected`; las claves que coinciden con `pinnedKeys` siguen protegidas diga lo que diga esto. Consulta [Proteger traducciones humanas](/docs/protecting-human-translations). Un dry run ahora también lee `verbatra.provenance.json`, salvo que `humanEdits` resulte en `"overwrite"`.
- `onProgress` se llama a medida que avanza la ejecución (por inicio y fin de cada locale, y por
  sub-lote del proveedor), y `onLockWait` se dispara mientras el bloqueo de escritura de un locale
  está en disputa. Ambos son callbacks de notificación; el SDK no escribe nada por sí mismo.
  `lockAcquireTimeoutMs` anula cuánto tiempo reintenta un bloqueo de escritura en disputa antes de
  fallar con `LOCK_CONTENDED`; un valor que no sea un número entero de milisegundos de al menos 0
  lanza `LOCK_TIMEOUT_INVALID` antes de leer nada. Solo limita el bloqueo de escritura del locale tomado antes de
  cualquier llamada al proveedor; el guard del archivo de bloqueo que registra un locale cuyo
  archivo ya está escrito siempre espera hasta el valor por defecto de diez minutos, para que un
  archivo escrito nunca quede sin registrar. `onLockWait` se dispara cuando una espera ya dura un
  segundo, y nunca para un bloqueo que tiene el mismo proceso, como el guard de un locale hermano
  con `concurrency` mayor que 1.
- `maxTokens` (desde 0.12.0) fija un techo de tokens solo para esta ejecución (el `--max-tokens` de la
  CLI). Siempre actúa como `budgetBehavior: "stop"`, y cuando la configuración también fija
  `maxTokens` se aplica el menor de los dos, así que puede endurecer el presupuesto configurado pero
  nunca relajarlo. Un valor que no sea un número entero de al menos 1 lanza `MAX_TOKENS_INVALID` y,
  como un presupuesto configurado, no se puede combinar con una `concurrency` mayor que 1 en una
  ejecución real.
- `maxBatchSize` y `budgetBehavior` son solo de configuración; no hay anulación por ejecución.

Devuelve un `RunSummary` (consulta [su anatomía más abajo](#la-anatomía-de-runsummary)). Los problemas
de toda la ejecución lanzan un `SdkError`; que falle un solo locale nunca lanza y queda como
`status: "failed"` en la entrada de ese locale mientras la ejecución continúa.

### Eventos de progreso

<AvailableFrom version="0.12.0" />

`onProgress` recibe un `ProgressEvent`, una unión discriminada por `type`. Una versión menor puede añadir tipos, así que ignora un `type` que no reconozcas.

| `type` | Cuándo | Campos |
| --- | --- | --- |
| `locale-started` | empieza el trabajo de un locale | `locale`, `localeIndex`, `totalLocales` |
| `locale-planned` | tras consultar la memoria de traducción y antes de enviar el primer lote; solo cuando se llama a un proveedor | `locale`, `keys`, `batches`, `cacheHits` |
| `sub-batch` | justo antes de intentar cada lote de traducción | `locale`, `batchIndex`, `totalBatches` |
| `provider-retry` | un proveedor integrado reintenta una petición que falló con un estado reintentable | `attempt`, `delayMs?`, `status?` |
| `repair` | un proveedor LLM vuelve a pedir las claves que su primera respuesta omitió | `locale`, `keys` |
| `split-retry` | un lote cuya salida se cortó se reintenta en dos mitades | `locale`, `keys` |
| `batch-finished` | un lote ha terminado, con éxito o no | `locale`, `batchIndex`, `totalBatches`, `durationMs`, `usage?` |
| `writing` | justo antes de escribir el archivo de un locale | `locale` |
| `locale-finished` | termina el trabajo de un locale | `locale`, `translated`, `localeIndex`, `totalLocales` |
| `run-finished` | todos los locales han terminado | `localesCompleted` |
| `change-detected` | solo `watch`: un cambio en el archivo de origen se ha asentado | `paths` |
| `idle` | solo `watch`: una ejecución terminó y no hay otra en cola | ninguno |

`provider-retry` no nombra ningún locale, porque un solo proveedor atiende toda la ejecución. Gemini informa de la espera y del estado, Anthropic, OpenAI y openai-compatible informan del intento cuando su cliente lo inicia, y DeepL y Google Cloud Translation no informan de nada. Un dry run y una estimación solo emiten `locale-started`, `locale-finished` y `run-finished`. Los registros de progreso `--json` de la CLI se limitan a los cuatro tipos originales: `locale-started`, `sub-batch`, `locale-finished` y `run-finished`.

`extract`, `diff` con `unused` y `doctor` con `literals` aceptan su propio `onProgress`. Recibe un `ScanProgressEvent`, `{ type: "files-scanned", scanned, total }`, una vez tras cada archivo de código de la aplicación que lee el escaneo.

Un `CreateProvider` propio recibe un tercer argumento, `CreateProviderHooks`, siempre que una ejecución informa de progreso. Llama a su `onRetry` con `{ attempt, delayMs?, status? }` y los reintentos de tu proveedor aparecerán como eventos `provider-retry`.

### resolveDryRun

<AvailableFrom version="0.11.0" />

Responde si un conjunto de opciones de ejecución se resuelve como un dry run. Toma el
`dryRun` y el `estimate` que estás a punto de pasar a `translate` y devuelve si esa ejecución
construirá un proveedor, escribirá un archivo o gastará algo. Es el único sitio donde se decide
que `estimate` implica `dryRun`, así que recurre a él siempre que algo alrededor de una ejecución tenga
que saberlo de antemano, en lugar de repetir la implicación y acabar desviándote de ella.

```ts
import { resolveDryRun, translate } from "@verbatra/sdk";

const options = { dryRun: false, estimate: true };
resolveDryRun(options); // true

const summary = await translate({ config, ...options });
```

### watch

Vigila el archivo del locale de origen y vuelve a ejecutar `translate` en cada cambio asentado por el
anti-rebote. Dispara una ejecución inicial inmediatamente al arrancar, y luego una ejecución por cambio
asentado. Las ejecuciones se serializan: los cambios durante una ejecución se colapsan en un único
seguimiento.

Entrada: `{ config, cwd?, locales?, debounceMs?, onRun, concurrency?, cache?, onProgress?, onLockWait?, lockAcquireTimeoutMs? }`.
`debounceMs` es 300 por defecto. `onRun` se llama una vez por ejecución con un `WatchRunResult`:
`{ status: "succeeded", summary }` o `{ status: "failed", error: { code, message } }`. El SDK no
registra nada; `onRun` es la única salida. `concurrency`, `cache`, `onProgress`, `onLockWait` y
`lockAcquireTimeoutMs` se pasan a cada ejecución y se comportan igual que en `translate`. `locales`
acota cada ejecución de la sesión a ese subconjunto y se valida una sola vez al arrancar, no en cada
ciclo.

Devuelve un `WatchController` con un solo método, `stop()`, que cierra el watcher y espera la ejecución
en curso. Tres problemas se rechazan al arrancar, antes de que el watcher exista, así que `watch` mismo
rechaza en lugar de devolver un controlador: un `concurrency` que no es un entero de al menos 1 lanza
`CONCURRENCY_INVALID`, un `concurrency` mayor que 1 contra una configuración que fija `maxTokens` lanza
`CONCURRENCY_BUDGET_CONFLICT` (no existe un watch en dry run, así que el conflicto de presupuesto siempre
se aplica), y un archivo de origen ausente lanza `SOURCE_UNREADABLE`. Todo fallo posterior al arranque se
comunica a través de `onRun` y la vigilancia continúa.

### releaseHeldLocks

<AvailableFrom version="0.12.0" />

Elimina todos los bloqueos de escritura que tiene el proceso actual, para un proceso que va a
terminar sin dejar que acaben sus ejecuciones en curso: la CLI lo llama cuando una interrupción
detiene `translate` o `import`, y cuando una segunda interrupción fuerza la parada de `watch`. Las
ejecuciones que tomaron esos bloqueos pierden su protección, así que llámalo solo justo antes de
que el proceso termine. No recibe argumentos y nunca rechaza.

Un bloqueo que queda atrás de todos modos, porque un proceso se mató de golpe, no lo necesita: una
ejecución en espera en la misma máquina ve que el proceso registrado ya no existe y recupera el
bloqueo por sí misma. Consulta [el bloqueo de escritura](/docs/the-lock-file#el-bloqueo-de-escritura).

## Pseudolocalización

### pseudolocalize

<AvailableFrom version="0.11.0" />

Construye un locale falso solo con las cadenas de origen, de modo que los recortes de maquetación y las
cadenas que nunca se extrajeron para traducir aparezcan antes de que exista clave de API alguna.
Cada valor se acentúa, se expande alrededor de un tercio de su longitud traducible y se envuelve en
los marcadores de límite `[` y `]`, mientras que los placeholders quedan intactos en
todas las sintaxis que reconocen los adaptadores, incluidas las ramas `plural` y `select` de ICU,
las etiquetas de marcado y las secuencias de escape. No construye ningún proveedor, no lee ninguna
clave de API y no hace ninguna petición de red.

Cada valor generado pasa por la misma puerta de integridad que debe superar la traducción de
un proveedor. Uno que no la superaría se copia literalmente del origen y se nombra en `copied` en
lugar de escribirse roto, así que la entrada sigue presente y sigue renderizándose.

Entrada: `{ config, cwd?, locale?, out? }`. `locale` es `en-XA` por defecto y `out` es
`.verbatra-local/pseudo`, que `verbatra init` ya añade a `.gitignore`; el `files.pattern`
configurado se expande dentro, así que el archivo conserva la disposición que espera la aplicación.
Un pseudolocale que nombre un locale configurado, o que aterrizaría sobre un archivo de locale
configurado, se rechaza con `PSEUDO_OUTPUT_CONFLICT` antes de leer o escribir nada, así que no
puede sobrescribir una traducción real ni hacerse pasar por una; lo mismo ocurre con un `out`
absoluto, que se salga de `cwd` o que nombre el propio `cwd`, como `.`, y, cuando `deps.fs` implementa `realpath` como el valor por
defecto, con uno que acaba así, en el directorio de un archivo de locale configurado o sobre otro
archivo del que depende el proyecto, una vez resueltos los enlaces simbólicos. Como el archivo vive fuera de
`files.pattern`, `translate` nunca gasta en él y `check` y `diff` nunca informan de él como
desfasado.

Devuelve un `PseudolocalizeResult`: el `locale`, el `path` absoluto, cuántas `entries` se
procesaron, cuántas se `transformed`, las claves que se `copied` y si se escribió algo (`written`).
La transformación es determinista, así que una segunda ejecución sobre un origen sin cambios no
reescribe nada e informa de `written` como false. Para `xliff` y `apple-xcstrings`, cuyos escritores
solo parchean un documento que ya existe, la salida se vuelve a copiar desde el origen en cada
escritura, así que una clave añadida al origen después de la primera ejecución sigue llegando al
pseudolocale, y a un XLIFF copiado se le reescribe su `target-language` al pseudolocale.

## Catálogos tipados

### generateTypes

<AvailableFrom version="0.11.0" />

Declara el catálogo de origen de un proyecto como TypeScript: una unión de todas las claves que
contiene y, por clave, los argumentos que interpola su mensaje. Tipa una función de traducción
contra el resultado y una clave mal escrita o un argumento de interpolación que falta pasa a ser un
error de compilación en lugar de un fallo de búsqueda en tiempo de ejecución. No gasta nada: no se
construye ningún proveedor, no se lee ninguna variable de entorno con una clave de API y no se hace
ninguna petición de red.

Lee un archivo (el catálogo del locale de origen) y escribe un archivo (la declaración); nunca
toca un archivo de locale de destino. Las claves son exactamente lo que el adaptador de formato ya
produjo, en orden del documento, así que dos ejecuciones sobre un catálogo sin cambios escriben
bytes idénticos. Los argumentos vienen de los tokens de placeholder que el adaptador extrajo, salvo
en los formatos de mensajes ICU (`next-intl-json` y `arb`), donde cada mensaje se lee con el mismo
parser ICU que usa el adaptador. Cada clave se emite como un literal de cadena entrecomillado, así
que una con un punto, una palabra reservada, un dígito inicial, una comilla, o incluso la clave
vacía, se declara tal cual en lugar de descartarse o volver a partirse, y una clave que el adaptador
informó en `excludedLeafPaths` no se declara en absoluto.

Lo que se niega a afirmar importa tanto como lo que declara. Un mensaje sin placeholders recibe una
forma que convierte en error de tipo pasar cualquier argumento; uno cuyos placeholders nombran sus
argumentos recibe una forma de objeto; uno con placeholders numerados o anónimos recibe una tupla
readonly. Un argumento ICU que solo usan algunas ramas `select` o `plural` se declara como miembro
opcional. Los tipos de argumento vienen solo de lo que el catálogo registra: `number` para un
argumento ICU `number`, `plural` o `selectordinal` y para un formateador o una conversión numéricos,
`Date | number` para un argumento ICU `date` o `time` y un formateador `datetime` de i18next,
`string` para un argumento ICU `select` y una conversión printf de cadena, y un alias de `string |
number` en los demás casos, nunca un `any` permisivo. Una interpolación sin escapar de i18next (`{{-
name}}`) se declara con el nombre detrás de su prefijo. Un mensaje que el adaptador informó como
inválido, uno que parece nombrar y numerar sus argumentos a la vez, y uno con un índice de placeholder
fuera de rango se declaran con sus argumentos informados en `unresolved` en lugar de declararse en
silencio como si no tomaran ninguno. Los hermanos de plural nunca se agrupan: cada uno se declara
por su cuenta, y los que el adaptador marcó como plurales se listan.

Entrada: `{ config, cwd?, out?, configPath?, glossaryPath?, check? }`. `out` toma por defecto
`DEFAULT_TYPES_PATH` (`verbatra-types.d.ts`). Antes de leer o escribir nada, `TYPES_OUTPUT_CONFLICT`
rechaza un `out` que no nombra ningún archivo (también uno que termina en un separador de ruta), es
absoluto, se sale de `cwd` con `..`, nombra el propio `cwd` (`.`) o no termina en `.ts`, `.mts` o
`.cts`, y uno que nombra un
archivo de locale configurado, el archivo de bloqueo, el archivo de procedencia, la caché de memoria de traducción, un archivo
donde verbatra busca su configuración, `configPath`, el archivo de configuración desde el que se
cargó `config`, o `glossaryPath`, el archivo de glosario al que apunta; los nombres se comparan sin
distinguir mayúsculas de minúsculas, y cuando `deps.fs` implementa `realpath`, como hace el valor
por defecto, las mismas comprobaciones se repiten sobre el sitio donde cae la ruta una vez resueltos
los enlaces simbólicos. Una ejecución que genera también se niega, con el mismo código, a reemplazar
un archivo existente que no empieza con la línea de cabecera que escribe verbatra, y deja ese
archivo intacto. La lista completa está en la página de [`verbatra types`](/docs/cli/types). Con
`check` activado no se escribe nada en absoluto, no se rechaza nada por su contenido, y la ejecución
solo informa de si el archivo confirmado sigue coincidiendo, que es justo lo que quiere una puerta
de CI.

Devuelve un `GenerateTypesResult`: el `path` absoluto, el `sourcePath` del que se construyó, cuántas
`keys` se declararon y cuántas de ellas toman al menos un argumento que verbatra pudo determinar
(`withArguments`, que nunca cuenta una clave de `unresolved`), las claves `unresolved` y las
`excluded` y `plural`, si se escribió algo (`written`), si el archivo en disco estaba `stale` al
arrancar la ejecución, y si esta fue una ejecución de `check`.

## Inspecciona el estado sin escribir

Ninguna de estas llama a un proveedor, escribe un archivo ni muta el bloqueo.

### doctor

<AvailableFrom version="0.9.0" />

Valida la configuración del proyecto y no gasta nada: no construye ningún proveedor, no hace
ninguna petición de red y nunca lee el valor de una clave de API. Se ejecutan nueve comprobaciones,
cada una con su propio veredicto `pass`, `fail` o `skipped`. Cinco cubren lo básico: la configuración se carga y se valida
(`config`), el formato configurado resuelve a un adaptador (`format-adapter`), el ID de proveedor
configurado resuelve a una fábrica (`provider`), la variable de entorno de la que ese proveedor lee
su clave está definida (`api-key`), y el archivo del locale de origen se puede leer (`source-file`). Todas las comprobaciones se ejecutan aunque una anterior haya fallado, así que una
sola llamada informa de cada problema independiente. La clave de API se comprueba solo por nombre.
La comprobación del archivo de origen lo lee y lo parsea en lugar de solo sondear su existencia, así
que un directorio en su lugar, un archivo vacío y contenido malformado se informan todos aquí.

<AvailableFrom version="0.12.0" />

La comprobación `network-policy` pasa cuando la [política de red](/docs/network-policy)
efectiva, que sale del bloque `network` de la configuración y de la variable de entorno
`VERBATRA_NETWORK_POLICY`, permite el host al que se conecta el proveedor configurado y cualquier
proxy que usaría. Su detalle nombra la política, sus dos fuentes y el host. Falla cuando ese host
se rechaza o una variable de entorno de red tiene un valor no válido, pasa para el proveedor `none`
y no resuelve ningún nombre de host.

La comprobación `plural-rules` es informativa y siempre pasa: su detalle nombra las
versiones de ICU y CLDR de las que el runtime deriva las categorías de plural de cada idioma de
destino, y cualquier locale de destino para el que ICU no tiene reglas de plural.

La comprobación `locale-codes` también es informativa y siempre pasa: su detalle nombra
cada código de locale configurado que es válido pero no está en forma BCP 47 canónica, como
`zh-hant-tw` o el obsoleto `iw`, con la forma canónica que sugiere `Intl.getCanonicalLocales`. No
se renombra nada.

La comprobación `locale-state` también es informativa y siempre pasa: su detalle nombra
cada locale para el que el archivo de bloqueo, la memoria de traducción o el archivo de procedencia
guardan estado y que la configuración no incluye, como `pt_BR` tras reescribirlo como `pt-BR`, y
dice si la siguiente ejecución de `translate` lo traslada. Un archivo que no puede leer se nombra en
el detalle.

Entrada: `{ cwd?, configPath?, literals?, onProgress? }`. Con `literals` activado, `doctor` solo ejecuta la
comprobación `config` y, en lugar de las demás, una comprobación `untranslated-literals` que
recorre las raíces de código del bloque `extract` de la configuración, igual que
[`verbatra doctor --literals`](/docs/cli/doctor#literales-sin-traducir). No necesita una
configuración ya cargada: `doctor` la carga por sí mismo, así que un proyecto sin ninguna
configuración sigue obteniendo un informe en lugar de un error lanzado.
Devuelve un `DoctorResult` cuyo `ok` es true exactamente cuando ninguna comprobación falló. Lanza
`CONFIG_NOT_FOUND` solo para un `configPath` explícito que no existe.

### extract

<AvailableFrom version="0.11.0" />

Analiza el código de tu aplicación en busca de llamadas de traducción y fusiona lo que encuentra en
el catálogo del locale de origen. Es el único punto de entrada que lee código de aplicación en lugar
de un archivo de locale, y eso es lo que hace que verbatra sirva en un proyecto que todavía no tiene
catálogo. No gasta nada: no construye ningún proveedor, no lee ninguna variable de entorno con una
clave de API y no hace ninguna petición de red.

Solo se escribe el archivo del locale de origen, y solo se añaden claves realmente nuevas: una clave
que ya está en el catálogo conserva su valor tal cual, y una clave del catálogo que ninguna llamada
menciona se deja intacta. Una ejecución que no encuentra nada nuevo no escribe nada en absoluto.
Todo lo que el análisis no puede resolver vuelve como datos en lugar de lanzarse: un argumento de
clave no estático en `dynamic`, una clave encontrada con dos valores por defecto distintos en
`conflicts` (no se escribe ninguno) y un archivo ilegible en `diagnostics`. El resultado lleva
únicamente claves, valores y ubicaciones de archivo y línea, nunca el contenido de un archivo de
código.

Entrada: `{ config, cwd?, dryRun?, onProgress? }`, donde `config.extract` nombra el framework y las raíces de
código. Devuelve un `ExtractResult`. El descubrimiento pasa por el miembro opcional `readDirectory`
de `SdkFs`; un `deps.fs` sin él se informa como `EXTRACT_FS_UNSUPPORTED`.

### check

Informa del desfase por locale como contadores: `missing` (en el origen, ausente del destino), `stale`
(el origen cambió desde la última traducción) y `upToDate`. Úsalo como puerta de CI.

Entrada: `{ config, cwd?, locales?, consistency?, qa?, qaSeverity? }`. Devuelve un `CheckSummary` cuyo `inSync` es true
exactamente cuando cada locale comprobado no tiene nada faltante ni obsoleto.

<AvailableFrom version="0.11.0" />

Con `consistency: true`, cada `LocaleCheckSummary` lleva además `inconsistencies`: un
`InconsistencyGroup` por cada cadena de origen que el locale traduce de más de una forma bajo claves
distintas, con el `source`, cada traducción distinta como `{ value, keys }` y el `context`, la
`description`, el `meaning`, `isPlural` y `pluralForm` que comparten las claves agrupadas. Solo se
comparan las claves al día, los valores se comparan tras la normalización NFC y sin los espacios
del principio y del final, las claves con distinta descripción, significado, marca de plural o
`msgctxt` de gettext nunca se agrupan, y las formas plurales guardadas bajo su propia clave se
comparan forma por forma. Es solo un informe: nunca cambia `inSync`, un contador ni un archivo, y
no llama a ningún proveedor.

<AvailableFrom version="0.12.0" />

Cada `LocaleCheckSummary` lleva además `provenance`: contadores `byOrigin` y `byReviewState` sobre
las claves para las que el locale tiene un valor, leídos de `verbatra.provenance.json`. Qué
significa cada origen está en [El archivo de bloqueo](/docs/the-lock-file#procedencia-quién-escribió-cada-valor).
Este y cualquier otro campo de procedencia de un informe se omite, en lugar de dar un error, cuando
el archivo está corrupto o lo escribió un verbatra más nuevo.

<AvailableFrom version="0.12.0" />

Cada `LocaleCheckSummary` lleva además `protected`: cuántas de sus claves ausentes y obsoletas dejaría una ejecución de `translate` para una persona según el `humanEdits` y los `pinnedKeys` de la configuración. Siguen contando como ausentes u obsoletas, así que `inSync` sigue en false hasta que una persona las resuelva. Si `verbatra.provenance.json` está dañado o es de un verbatra más nuevo, no se puede leer ningún origen y solo se cuentan las claves fijadas.

<AvailableFrom version="0.12.0" />

Con `qa: true`, `check` también ejecuta el control de calidad sobre cada valor confirmado, sin
clave y sin escribir nada: cada `LocaleCheckSummary` lleva un informe `qa` de
`{ checked, errors, warnings, findings }`, y el resumen lleva los totales `qa` de
`{ errors, warnings, invalidSourceKeys }`. Un hallazgo es `{ key, severity: "error", reason, details? }`
para un valor que la puerta de integridad rechazaría (`reason` de `INTEGRITY_GATE_REASONS`), o
`{ key, severity: "warning", reason }` para un valor que pasa pero lleva un motivo de revisión de
`REVIEW_REASON_CODES`. `qaSeverity: "error"` omite los motivos de revisión. Las severidades se
publican como la tupla `QA_SEVERITIES` (`"error"`, `"warning"`). El informe nunca cambia `inSync`;
una puerta de CI lee `qa.errors`, y `qa.warnings` para una puerta estricta. Consulta
[el control de calidad](/docs/cli/check#control-de-calidad) para ver qué valores se comprueban.

### diff

El hermano detallado de `check`: el mismo cálculo, pero devuelve las listas de claves por locale
(`missing`, `changed`, `orphaned`) en lugar de contadores. Las claves huérfanas son solo informativas y
nunca activan `hasPendingChanges`, porque una ejecución por defecto no elimina claves.

Con `unused: true` también analiza las raíces del bloque `extract` de la configuración y añade un
informe `unused`, separado de cada lista `orphaned`: las claves del locale de origen que ninguna
referencia estática nombra, en el orden del catálogo. Es de solo lectura, no necesita clave y modela
el runtime de i18next (llamadas `t` y sus alias, prefijos estáticos de `keyPrefix` y `getFixedT`,
claves de `Trans`, claves con namespace y variantes de plural y de contexto), comparando las claves
en la codificación del formato del catálogo. Cada clave listada lleva su `key` decodificada y su
`catalogKey`. Las claves que coinciden con `extract.unused.ignore` van a `ignored`, y las que podría
alcanzar un literal de plantilla con cabecera estática, a `possiblyDynamic`. Su `status` es `complete`,
`unreliable` (con `unreliableBecause` nombrando cada motivo con sus ubicaciones) o `not-run` (con un
`reason` y sin lista de claves). Consulta todos los motivos en [Claves de origen sin
uso](/docs/cli/diff#claves-de-origen-sin-uso). El informe nunca activa `hasPendingChanges`.

Entrada: `{ config, cwd?, locales?, unused?, onProgress? }`. Devuelve un `DiffSummary`.

<AvailableFrom version="0.12.0" />

Cada `LocaleDiff` lleva además `changedOrigins`, el origen interpretado del valor actual de cada
clave `changed` (por ejemplo `machine`, `human` o `external`), para que veas antes de ejecutar qué
trabajo reemplazaría una retraducción.

<AvailableFrom version="0.12.0" />

Cada `LocaleDiff` lleva además `protected`, las claves ausentes y cambiadas que una ejecución de `translate` dejaría en paz, ordenadas. Siguen contando como pendientes. Si el archivo de procedencia no se puede leer, solo se listan las claves fijadas.

### keyIntegrity

Informa, para las claves modificadas de cada locale, de si el valor de destino actual sigue
coincidiendo con los placeholders del origen, de si sigue llevando el marcado en línea del
origen y de si es ICU válido. Cada entrada lleva `key`, `hasPlaceholders`, `matches`, los tokens de
placeholder `missing` y `extra` en una discrepancia, `icuValid`, `markupMatches` y `markupDetails` con
las etiquetas causantes de una discordancia de marcado. Las entradas nunca llevan un valor de cadena
de origen o destino. Informar del marcado aquí es lo que hace visible el desfase anterior a la puerta
del momento de escritura: una traducción escrita antes de que existiera la comprobación, editada fuera de
verbatra o producida por una ruta que nunca pasó por la puerta se juzga aquí con la misma regla.
Este es el informe de integridad por clave que muestra Studio.

<AvailableFrom version="0.12.0" />

Cada entrada lleva además `icuArmsMatch` e `icuArmDetails`: si las ramas ICU de `plural`,
`selectordinal` y `select` del valor encajan con el idioma de destino, juzgadas exactamente como las
juzga la puerta del momento de escritura, y un problema breve por cada rama que falta o sobra, como
`{count} plural: missing arm "few" required by the target language`. `icuArmsMatch` siempre es true
para un formato que no comprueba ramas (todos los formatos incluidos salvo next-intl y ARB).

Entrada: `{ config, cwd?, locales?, keys? }`. `keys` acota la comprobación; solo se comprueban las
claves que están "modificadas" para un locale. Devuelve un `LocaleKeyIntegrity` por locale comprobado.

### localeIntegrity

<AvailableFrom version="0.12.0" />

Encuentra cada traducción de los locales de destino que está rota ahora mismo: una que perdió o
ganó un placeholder, perdió o añadió marcado en línea, ya no se analiza como ICU o lleva ramas ICU
de `plural`, `selectordinal` o `select` que no encajan con el idioma de destino. A diferencia de
`keyIntegrity`, juzga cada clave presente tanto en el origen como en un locale de destino, sea cual
sea su estado de sincronización, así que también encuentra un defecto en una traducción que nadie ha
tocado desde que se escribió. Cada clave se juzga con las mismas reglas que `keyIntegrity` y la
puerta del momento de escritura, y solo vuelven las claves que fallan: una lista `entries` vacía
significa que todas las traducciones de ese locale pasan.

El coste es una lectura y un análisis del archivo de origen y de cada archivo de destino pedido,
más una comprobación por clave traducida. No se guarda nada en caché; cada llamada lee de nuevo del
disco.

Entrada: `{ config, cwd?, locales? }`. Devuelve un `LocaleKeyIntegrity` por locale comprobado, con
solo sus entradas que fallan.

### lockState

Informa de la existencia del archivo de bloqueo, su versión y el desfase por locale (número de claves de
la línea base más contadores de faltantes, obsoletas y al día). `exists` viene de una sonda explícita,
así que "todavía no hay archivo de bloqueo" y "un archivo de bloqueo vacío pero presente" siguen siendo
distinguibles. Cuando el archivo está ausente el resultado es `{ exists: false }` y no se lee nada más.

Entrada: `{ config, cwd?, locales? }`. Devuelve un `LockStateResult`.

Cada locale lleva además los mismos contadores `provenance` que informa `check`.

### loadLockFile

Lee el propio archivo de bloqueo (`verbatra.lock.json`, exportado también como `LOCK_FILE_NAME`) y
devuelve su forma parseada: `{ version, locales }`, donde cada locale asigna claves al hash del
contenido de origen desde el que se tradujeron por última vez. Un archivo ausente degrada a un bloqueo
vacío, el mismo comportamiento de primera ejecución en el que se apoya `translate`; usa `lockState`
cuando necesites distinguir la ausencia.

Entrada: `{ cwd? }`. No necesita configuración. Devuelve un `LockFile`.

### loadProvenance

<AvailableFrom version="0.12.0" />

Lee el propio archivo de procedencia (`verbatra.provenance.json`, también exportado como
`PROVENANCE_FILE_NAME`) y devuelve su forma guardada: `{ version, locales }`, donde cada locale
asigna a cada clave un registro `{ origin, provider?, model?, valueHash, reviewState?, reviewer?, reviewedSourceHash? }`.
No contiene texto traducido. Un archivo ausente, o uno escrito por un verbatra más nuevo, se lee
como vacío; uno corrupto lanza `PROVENANCE_FILE_INVALID`. `keyValue`, `localeValues`, `check`,
`diff` y `lockState` ya informan la vista interpretada (`KeyProvenance`), que además distingue un
valor sin registro (`unrecorded`) de uno editado fuera de verbatra desde que se registró
(`external`).

Entrada: `{ cwd? }`. No necesita configuración. Devuelve un `ProvenanceFile`.

### runStatus

Lee la instantánea de señales de revisión y uso de tokens que la ejecución más reciente de `translate` o
`watch` que no fue un dry run persistió en `.verbatra-local/run-status.json`. Nunca lanza: un archivo ausente,
corrupto o no reconocido degrada a `{ available: false }`. Este archivo es telemetría de mejor esfuerzo,
no una línea base de corrección.

Entrada: `{ cwd? }`. No necesita configuración. Devuelve `{ available: false }` o
`{ available: true, version, generatedAt, usage?, budget?, locales }`.

Una instantánea escrita por una versión anterior a que el presupuesto de tokens se hiciera cumplir
se sigue leyendo, pero su `budget` se omite cuando indica `supported: false`: entonces eso
significaba que no se contaba nada, así que su `tokensUsed: 0` no es un recuento. Las instantáneas
que se escriben ahora conservan la misma `version` y solo añaden un campo marcador que un Studio o
un servidor de agentes más antiguo ignora, así que un lector más antiguo sigue mostrando la cola de
revisión y el uso. Hasta que lo actualices, puede mostrar un presupuesto estimado como no
registrado.

### reviewQueue

<AvailableFrom version="0.12.0" />

Lee la cola de revisión: las claves que marcó la última ejecución (la instantánea de `runStatus`),
menos todas las que alguien ya atendió desde entonces. Una señal sale de la cola en cuanto su valor
actual se aprueba o se rechaza en `verbatra.provenance.json`, en cuanto una persona escribe o
importa un valor nuevo para ella, o en cuanto ya no tiene traducción; un valor que reescribió un
agente se queda. Como las decisiones vienen de archivos con commit, alguien de tu equipo con el
mismo estado de ejecución ve la misma cola. Nunca lanza: un archivo de estado inservible da
`{ available: false }`, un archivo de procedencia ilegible deja las señales sin filtrar, y un locale
cuyo archivo no se puede leer conserva sus señales tal como se registraron.

Entrada: `{ config, cwd? }`. Devuelve la forma de `runStatus`, y cada entrada de `needsReview`
además lleva `provenance`, la `KeyProvenance` de su valor actual, cuando el archivo de procedencia
se puede leer.

## Operaciones de una sola clave

Estos son los puntos de integración que usa Verbatra Studio; úsalos para construir tu propia herramienta
de revisión. Todas resuelven `locale` y `key` de nuevo en cada llamada y lanzan `UNKNOWN_LOCALE` o
`UNKNOWN_KEY` cuando alguno no existe.

### keyValue

Lee el valor de origen actual de una clave y, cuando existe, su valor de destino actual para un locale.
Solo lectura.

Entrada: `{ config, cwd?, locale, key }`. Devuelve `{ source, target? }`; `target` está ausente
exactamente cuando la clave todavía no existe en ese locale.

Cuando `target` está presente, el resultado lleva además `provenance`, la `KeyProvenance`
interpretada de la clave: `{ origin, provider?, model?, reviewState, reviewer? }`.

<AvailableFrom version="0.12.0" />

El resultado también lleva `description` cuando el archivo del locale de origen da una para la
clave: una `@key.description` de ARB, una nota de XLIFF, un comentario de gettext, un comentario de
`.strings` de Apple o un comentario de `.resx` de .NET.

### editEntry

Escribe una corrección tecleada por un humano para una clave y un locale. El valor candidato pasa por la
misma puerta de integridad que una traducción del proveedor antes de que nada llegue
al disco; al aceptarse, el archivo de locale y la entrada del bloqueo de esa clave se actualizan dentro
del bloqueo de escritura del locale. Nunca llama a un proveedor.

Entrada: `{ config, cwd?, locale, key, value }`. Devuelve un resultado de dos ramas:
`{ accepted: true, value }`, o
`{ accepted: false, reason: "placeholder" | "markup" | "icu" | "degenerate" | "empty", value }` sin
escribir nada. `"empty"` cubre un valor vacío o solo con espacios para un origen que sí tiene texto:
una edición no puede expresar el vaciado de una clave, así que usa para eso el centinela `[[CLEAR]]`
del libro. El conjunto de motivos se publica como la tupla `INTEGRITY_GATE_REASONS`, así que
construye cualquier esquema en tiempo de ejecución o tabla exhaustiva a partir de ella en lugar de
reescribir sus miembros. Un rechazo `placeholder` o `markup` lleva además
`details`: los marcadores o etiquetas causantes, cada uno con `-` si el origen lo tenía y la
candidata lo perdió o `+` si la candidata lo inventó.

El valor escrito queda registrado en `verbatra.provenance.json` con el origen `human`. Pasa
`actor: "agent"` cuando lo escribió un agente de IA, para que el registro lo diga; lo afirma la
superficie que llama y nada lo verifica. El archivo de procedencia se comprueba antes de pasar el
valor por la puerta: uno corrupto lanza `PROVENANCE_FILE_INVALID` y no se escribe nada, y uno de un
verbatra más nuevo, o uno que el registro haría crecer por encima de lo que verbatra vuelve a leer,
se deja intacto mientras el valor se escribe sin registro.

<AvailableFrom version="0.12.0" />

Con `actor: "agent"`, una clave que coincide con los `pinnedKeys` de la configuración lanza `KEY_PINNED` antes de leer o escribir nada. La edición de una clave fijada por parte de una persona se acepta.

### retranslateEntry

Vuelve a ejecutar el proveedor para exactamente una clave y un locale: una llamada de una sola entrada a
través de la misma ruta de proveedor que usa `translate`, protegida por las mismas comprobaciones de
integridad. Al aceptarse escribe el archivo de locale y la entrada del bloqueo solo para esa clave.

Entrada: `{ config, cwd?, locale, key, includeHuman?, onLockWait?, lockAcquireTimeoutMs? }`. Devuelve `{ accepted: true, value, reviewReasons }` (los
códigos de motivo de revisión, si los hay, que se aplican al nuevo valor) o
`{ accepted: false, reason: "placeholder" | "markup" | "icu" | "degenerate" | "empty", value }`. A
diferencia de `translate`, aquí un fallo del proveedor lanza: un `ProviderError`, exportado desde
`@verbatra/sdk`, con un `code` estable como `RATE_LIMITED` o `AUTH_FAILED`. Con `provider: { id: "none" }` lanza primero `MACHINE_TRANSLATION_DISABLED`, antes de leer o bloquear nada.

El nuevo valor queda registrado en `verbatra.provenance.json` como `machine`, con el `id` del
proveedor que respondió y el modelo configurado. Un proveedor de tu propio `createProvider` queda
registrado con su propio `id`, y sin el modelo cuando ese `id` no coincide con el configurado. Un archivo de procedencia corrupto lanza `PROVENANCE_FILE_INVALID` antes de
llamar al proveedor.

<AvailableFrom version="0.12.0" />

Una clave cuyo valor actual escribió, importó o cambió una persona fuera de verbatra lanza `KEY_PROTECTED` dentro del bloqueo de escritura, antes de llamar al proveedor, salvo que pases `includeHuman: true` o la configuración fije `humanEdits: "overwrite"`. Si el archivo de procedencia es de un verbatra más nuevo, cualquier valor existente cuenta como protegido. Una clave que coincide con `pinnedKeys` lanza `KEY_PINNED` antes de construir el proveedor, incluso con `includeHuman`.

### approveEntry

<AvailableFrom version="0.12.0" />

Registra que una persona revisó el valor actual de una clave en un locale y lo acepta. Solo escribe
`verbatra.provenance.json`, nunca un archivo de locale ni el archivo de bloqueo, y no llama a ningún
proveedor. La aprobación también guarda el hash de origen de la clave en el archivo de bloqueo, así
que vuelve a contar como sin revisar en cuanto cambia el origen; cualquier escritura posterior que
cambie el valor empieza un registro nuevo, sin revisar.

Entrada: `{ config, cwd?, locale, key, expectedValue, reviewer?, onLockWait?, lockAcquireTimeoutMs? }`. `expectedValue` es el texto que
vio quien revisa: la llamada lanza `REVIEW_VALUE_CHANGED` cuando la clave no tiene valor o tiene
otro, y `REVIEW_SOURCE_CHANGED` cuando el origen cambió desde que se escribió el valor. `reviewer` es
texto libre opcional de 64 caracteres como máximo y sin caracteres de control (si no,
`REVIEWER_INVALID`), se guarda en el archivo con commit y verbatra nunca lo rellena. Devuelve
`{ locale, key, provenance }`. Un valor sin registro previo, o uno cambiado fuera de verbatra, se
registra con el origen `unknown`.

### rejectEntry

<AvailableFrom version="0.12.0" />

Registra que una persona revisó el valor actual de una clave en un locale y lo rechaza, y elimina
ese valor para que se reemplace. La clave sale del archivo de locale y se borra su entrada del
bloqueo, así que `check` y `diff` la reportan como faltante y la siguiente ejecución de `translate`
la vuelve a llenar (con `provider: { id: "none" }` sigue faltando hasta que alguien escriba un
valor). El registro de procedencia se queda como `rejected` con un hash del texto eliminado, y la
entrada correspondiente de la memoria de traducción de esta máquina se borra. Un `translate`
posterior omite cualquier acierto exacto o difuso de la memoria para la clave cuyo texto coincida
con ese hash, así que la memoria de otra máquina tampoco puede devolver el texto. No llama a ningún
proveedor.

Entrada: `{ config, cwd?, locale, key, expectedValue, reviewer?, onLockWait?, lockAcquireTimeoutMs? }`, comprobada como en
`approveEntry`, salvo que un origen desactualizado no impide un rechazo. Devuelve
`{ locale, key, provenance }`. Un formato que conserva una clave que no recibió, XLIFF, lanza
`REVIEW_REJECT_UNSUPPORTED` después de restaurar el archivo.

Ambas llamadas comprueban el archivo de procedencia antes de escribir nada y nunca informan de una
decisión que no pudieron guardar: un archivo de un verbatra más nuevo, o uno que la decisión haría
crecer por encima del tamaño que verbatra vuelve a leer, lanza `PROVENANCE_FILE_UNWRITABLE`.

## Revisión y retraducción por lotes

<AvailableFrom version="0.12.0" />

Cada una de estas llamadas ejecuta la llamada de una sola clave correspondiente una vez por
entrada, en el orden dado, y devuelve `{ results }` con un resultado por entrada en ese orden. Una
entrada que falla no detiene el lote: su resultado es `{ locale, key, ok: false, code, message }`,
con el código del `SdkError`, del error de adaptador o del `ProviderError` que la detuvo y un
mensaje censurado, y se ejecuta la siguiente entrada. Cualquier otro error detiene el lote con un
`BatchInterruptedError` que lleva los resultados de las entradas ya ejecutadas, cuyas escrituras ya
están en disco. Una lista `entries` vacía devuelve `results` vacío.

### approveEntries

Entrada: `{ config, cwd?, entries: [{ locale, key, expectedValue }], reviewer?, onLockWait?, lockAcquireTimeoutMs? }`.
Ejecuta `approveEntry` por entrada con las mismas comprobaciones; `reviewer` se aplica a todas las
entradas. Un resultado correcto es `{ ok: true, locale, key, provenance }`. `lockAcquireTimeoutMs`
limita la espera de cada entrada por el bloqueo de escritura de su locale, y `onLockWait` informa
de esa espera. Una entrada cuyo bloqueo sigue ocupado pasado el tiempo límite falla con
`LOCK_CONTENDED`, y cada entrada posterior que necesita el mismo bloqueo recibe
`{ locale, key, ok: false, skipped: true, code: "LOCK_CONTENDED", message }` en lugar de volver a
esperar; las entradas de otros locales se siguen decidiendo. Las llamadas de una sola entrada
`approveEntry` y `rejectEntry` aceptan las mismas dos opciones.

### rejectEntries

Entrada: la misma que `approveEntries`. Ejecuta `rejectEntry` por entrada y elimina cada valor
rechazado. Un resultado correcto es `{ ok: true, locale, key, provenance }`. Un tiempo límite de
bloqueo omite las entradas posteriores que necesitan ese bloqueo, como en `approveEntries`.

### retranslateEntries

Entrada: `{ config, cwd?, entries: [{ locale, key }], includeHuman?, onLockWait?, lockAcquireTimeoutMs? }`.
Ejecuta `retranslateEntry` por entrada, así que hace hasta una llamada al proveedor por entrada. No
es una ejecución de `translate`: `maxTokens` y `budgetBehavior` no se aplican, y el número de
entradas es el único límite de lo que gasta. Un resultado completado es
`{ ok: true, locale, key, result }`, donde `result` es lo que devolvió `retranslateEntry`, incluido
un valor que la puerta de integridad rechazó. Un valor que escribió una persona falla con
`KEY_PROTECTED` salvo que pases `includeHuman: true`. `lockAcquireTimeoutMs` limita la espera de
cada entrada por el bloqueo de escritura de su locale, antes de llamar al proveedor, y
`onLockWait` informa de esa espera.

<AvailableFrom version="0.12.0" />

Un error que haría fallar igual a todas las entradas detiene las llamadas al proveedor:
`MISSING_API_KEY`, `AUTH_FAILED`, `RATE_LIMITED` (que incluye una cuota agotada),
`NETWORK_POLICY_VIOLATION`, `PROVIDER_CONSTRUCTION_FAILED`, `CONFIG_INVALID` o
`MACHINE_TRANSLATION_DISABLED`. La entrada que lo provocó falla como siempre, y cada entrada
posterior recibe `{ locale, key, ok: false, skipped: true, code, message }` con ese código, sin
otra llamada al proveedor.

Una entrada cuyo bloqueo de escritura del locale sigue ocupado pasado `lockAcquireTimeoutMs` falla
con `LOCK_CONTENDED`, y cada entrada posterior que necesita el mismo bloqueo se omite del mismo modo
con ese código en lugar de volver a esperar: las entradas de ese locale, o de todos los locales en
un formato que guarda todos los locales en un solo archivo. Las entradas de otros locales siguen
ejecutándose.

### BatchInterruptedError

<AvailableFrom version="0.12.0" />

Lo lanzan `approveEntries`, `rejectEntries` y `retranslateEntries` cuando un error que no es el
resultado de una sola entrada, como un fallo inesperado del sistema de archivos, detiene un lote a
medias. `results` contiene los resultados de las entradas completadas antes, en orden, `entry`
nombra el `{ locale, key }` que se estaba ejecutando y `cause` es el error original. Las entradas
posteriores a `entry` no se ejecutaron.

## Lecturas de contenido en bloque

<AvailableFrom version="0.10.0" />

### localeValues

Lee el texto de origen y de destino actual de cada clave, en cada locale de destino solicitado, en
una sola pasada sobre los archivos que ya están en disco. Es la contraparte en bloque de `keyValue`:
úsala cuando necesites contenido de traducción en bloque, por ejemplo para buscar o recorrer
valores en lugar de solo nombres de clave, ya que `keyValue` solo responde para una clave a la vez.
Solo lectura.

Entrada: `{ config, cwd?, locales? }`; un `locales` omitido cubre cada locale de destino
configurado. Devuelve un array de `{ locale, values }`, una entrada por locale, donde `values`
asigna cada clave a `{ source?, target? }`. Un `target` ausente significa que la clave todavía no
se ha traducido en ese locale; un `source` ausente significa que la clave está huérfana, presente
en el locale de destino pero ya no en el origen. `values` no tiene prototipo: cada clave, incluida
una llamada `__proto__` o `constructor`, es una propiedad propia, y una clave que no está en el
catálogo se lee como `undefined`.

Cada par con un `target` lleva además `provenance`, la misma `KeyProvenance` que informa `keyValue`.

## Instantáneas de archivos de locale

Los bloques con los que se construye un watcher de actualización en vivo como el de Studio: captura el
estado de un archivo de locale y luego cuenta qué cambió desde entonces.

### readLocaleFileSnapshot

Lee un archivo de locale (el locale de origen o cualquier locale de destino) y lo reduce a un hash de
contenido por clave. Un archivo que todavía no existe se lee como una instantánea vacía en lugar de
lanzar.

Entrada: `{ config, locale, cwd? }`. Devuelve `{ locale, hashes }`.

### diffLocaleSnapshots

Compara dos instantáneas del mismo archivo, tomadas en momentos distintos, y cuenta las claves añadidas,
modificadas y eliminadas entre ambas. Una función síncrona normal: `diffLocaleSnapshots(previous,
current)` devuelve `{ added, changed, removed }`. Solo contadores, nunca nombres de claves.

## Rutas de locale

### createLocalePathResolver

Resuelve la correspondencia entre locales y rutas del proyecto en ambos sentidos, a partir de
`files.pattern`, los locales configurados y `files.localeStyle`. `createLocalePathResolver(cwd,
config)` devuelve `{ pathFor, localeFor }`: `pathFor(locale)` es la ruta absoluta del archivo de un
locale, y `localeFor(path)` es el locale al que pertenece una ruta, o `undefined` para una ruta que
este proyecto no posee. Todos los puntos de entrada del SDK resuelven rutas a través de él, así que
un watcher o un panel construido sobre el SDK ve exactamente las rutas que escribe una ejecución.

Todas las comprobaciones se ejecutan al crear el resolver, antes de leer ningún archivo: un patrón
y un estilo que no se pueden combinar, o un locale para el que el estilo no tiene una escritura
correcta, lanzan `LOCALE_LAYOUT_INVALID`, y dos locales que resuelven a la misma ruta lanzan
`LOCALE_PATH_COLLISION`.

## El par del libro

La entrega para traductores humanos, como libro de Excel o como texto delimitado; consulta [Traducción humana](/docs/manual-translation).

### exportWorkbook

Escribe las cadenas que todavía necesitan traducción (claves faltantes y modificadas por locale; añade
las sin cambios con `includeUnchanged`) en un libro `.xlsx` con estilos. Las filas llevan la misma señal
de revisión que calcula una ejecución de translate. Sin llamada al proveedor, sin escritura del bloqueo.

Entrada: `{ config, cwd?, out?, configPath?, glossaryPath?, locales?, includeUnchanged?, format? }`. `format` es `xlsx` por
defecto; `csv` y `tsv` escriben en su lugar un `<locale>.csv` o `<locale>.tsv` por locale, así que `out`
nombra un directorio para ellos (creado si falta) y una ruta de archivo para `xlsx`. `out` es por
defecto `DEFAULT_WORKBOOK_PATH` (`verbatra-translations.xlsx`) o `DEFAULT_DELIMITED_PATH`
(`verbatra-translations`), ambos exportados como constantes. Los valores aceptados se exportan como `EXCHANGE_FORMATS` y el valor por defecto como `DEFAULT_EXCHANGE_FORMAT`, para que una herramienta que envuelve el SDK pueda validar un argumento de formato sin fijar la lista en el código. Devuelve `{ path, locales }`: la ruta
absoluta escrita y un número de filas por locale.

Antes de leer nada, `EXPORT_OUTPUT_CONFLICT` rechaza un `out` que queda fuera de `cwd`, y uno que,
por sí mismo o a través de un archivo que la exportación escribiría dentro, nombra un archivo de
locale configurado, el archivo de bloqueo, el archivo de procedencia, la caché de memoria de
traducción, un archivo que verbatra busca para su configuración, el archivo `configPath` o el
archivo `glossaryPath`, sin distinguir mayúsculas de minúsculas y, cuando `deps.fs` implementa
`realpath` como el valor por defecto, otra vez tras resolver los enlaces simbólicos. Una ruta
`xlsx` también se rechaza cuando no nombra ningún archivo (también una que termina en un separador
de ruta) o nombra el propio `cwd`; un directorio `csv` o `tsv` puede ser `cwd`. Una escritura que
falla, porque el directorio no es escribible, hay un directorio o un archivo en medio o el disco
está lleno, lanza `EXPORT_UNWRITABLE` con el archivo y el código del sistema de archivos en el
mensaje, y el error del sistema de archivos como `cause`.

### importWorkbook

Lee un libro rellenado de vuelta a los archivos de locale, ejecutando las mismas comprobaciones de
desfase del origen e integridad que `translate`. Solo las filas aceptadas avanzan su
línea base del bloqueo; una fila en blanco o rechazada se sigue exportando hasta que se resuelve de
verdad.

Entrada: `{ config, workbook, cwd?, dryRun?, format?, onLockWait?, lockAcquireTimeoutMs? }`. Con `csv` o `tsv`, `workbook` es un solo
archivo de entrega o el directorio que contiene uno por locale, y el locale viene del nombre del
archivo. Devuelve la misma forma `RunSummary` que `translate`
(con `needsReview` siempre vacío, ya que no interviene ningún proveedor). Una hoja de un locale que no
es un destino configurado hace fallar ese locale con `CONFIG_INVALID` como dato en el resumen, no como
excepción.

<AvailableFrom version="0.12.0" />

`onLockWait` y `lockAcquireTimeoutMs` se comportan exactamente como en `translate`.
`lockAcquireTimeoutMs` limita la espera por el bloqueo de escritura de un locale, que se toma antes
de escribir el archivo de ese locale, y un locale que sigue bloqueado después falla con
`LOCK_CONTENDED` en su propio resumen mientras los demás locales se importan. Registrar un archivo ya
escrito en el archivo de bloqueo siempre admite la espera predeterminada de diez minutos. Un dry run
no toma ningún bloqueo, así que ninguna de las dos opciones se le aplica.

<AvailableFrom version="0.12.0" />

`integrityRefusals` de cada locale nombra las filas que rechazó la puerta de integridad, con el motivo
y sus `details`, como cada rama ICU que no encaja con el idioma de destino. Una fila retenida porque su
origen cambió desde la exportación aparece solo en `integrityMismatches`. `exportWorkbook` marca como
`icu-arms` en sus columnas de revisión una traducción actual con ramas incorrectas.

## El par TMX

<AvailableFrom version="0.11.0" />

`importTmx` y `exportTmx` mueven la [memoria de traducción](/docs/the-cache) hacia y desde TMX, el
formato de intercambio que producen y leen las plataformas de traducción más extendidas. Ninguna de
las dos construye un proveedor, lee una clave de API ni hace una petición de red: cada valor sale del
archivo o de la memoria que ya está en disco. No es el par del libro en otro formato. El par del libro
entrega a un traductor humano un corte por locale del delta pendiente; este par mueve la memoria
entera como un único archivo multilingüe entre herramientas.

### importTmx

Lee un archivo TMX hacia la memoria del proyecto. Entrada:
`{ config, file, cwd?, dryRun?, overwrite?, locales? }`.

Nada del archivo se da por bueno. El XML se analiza con el endurecimiento del paquete de
intercambio, de modo que una declaración de entidad, un subconjunto DTD interno, un archivo
demasiado grande o uno mal formado se rechaza con un error estructurado `SOURCE_INVALID` en lugar de
analizarse. Cuando el problema tiene un lugar en el archivo, el mensaje indica la línea, la columna
y, dentro de una unidad de traducción, su ordinal contando desde 1, y `tmxErrorLocation(error)`
devuelve el mismo lugar como `TmxErrorLocation`, o `undefined` para cualquier otro error, así que
nunca tienes que hacer cast del error ni de su `cause`. Una etiqueta de idioma se resuelve a un
locale configurado por una regla explícita: coincidencia exacta tras pasar a minúsculas y convertir
guiones bajos en guiones; si no, el locale configurado más largo que sea prefijo de subetiquetas de
la etiqueta (búsqueda de RFC 4647), o en su defecto un locale configurado que amplía la etiqueta
solo con subetiquetas de región o de variante, nunca con una escritura, de modo que dos etiquetas
con subetiquetas de escritura o de región distintas (`sr-Latn` y `sr-Cyrl`, `de-AT` y `de-CH`) nunca coinciden; y una
etiqueta solo se informa como ambigua cuando los locales a los que podría llegar no están en una
misma cadena de prefijos. Los segmentos de una unidad que resuelven al mismo locale, incluido el de
origen, nunca dejan ganar al último: una etiqueta exacta supera a una coincidencia por prefijo, y
dos segmentos del mismo rango con valores distintos no guardan nada para ese locale y se cuentan
como `conflicting` (en el locale de origen, la unidad se rechaza y se cuenta en
`conflictingSourceUnits`). Cada traducción candidata pasa después por la misma puerta de placeholders,
marcado en línea, ICU, degeneración y vacío que ya afrontan la salida del proveedor y una fila de libro rellenada,
y se comprueba cuando el registro entra en la memoria, no se deja para la ejecución que luego lo lee.

Cuando una unidad importada contradice una traducción que la memoria ya tiene, gana la memoria salvo
que se pase `overwrite`. Las unidades se guardan bajo la huella de configuración actual, la misma
clave que escribe una ejecución real, así que dejan de coincidir cuando cambian el proveedor, el
modelo, el tono, el glosario o el `localeMap` del proveedor. Importar el mismo archivo dos veces no cambia nada la segunda vez.

Ante datos dañados devuelve un informe en lugar de lanzar: cuántas unidades se leyeron, una cuenta
por locale de `added`, `unchanged`, `overwritten`, `kept`, `duplicates`, `conflicting` y `rejected`
por motivo, más las unidades omitidas, sin segmento de origen, que perdieron marcado en línea o cuyo
texto `sub` se dejó fuera (`subflowDroppedUnits`), y las etiquetas de idioma que no coincidieron o
coincidieron de forma ambigua. `memoryWritable` es `false` cuando el archivo de memoria lo escribió
un verbatra más nuevo, en cuyo caso se deja intacto. Los recuentos por locale se siguen informando
entonces, como en una ejecución de prueba, así que `added` y `overwritten` describen lo que habría
entrado; con `memoryWritable` en `false`, no entró nada.

<AvailableFrom version="0.12.0" />

Cada locale lista además sus `refusals`, un `TmxUnitRefusal` por cada unidad contada bajo un motivo
de la puerta: `{ unit, reason, details? }`, donde `unit` es la posición de la unidad en el archivo,
empezando en 1, y `details` nombra lo que falla, como cada rama ICU que no encaja con el idioma de
destino.

### tmxErrorLocation

Lee, a partir de lo que lanzó `importTmx`, dónde falló un archivo TMX rechazado. Devuelve una
`TmxErrorLocation` (`{ line, column, unit? }`, todo contando desde 1) para un rechazo
`SOURCE_INVALID` que tiene un lugar en el archivo, y `undefined` para cualquier otro error, incluido
un archivo que falta o es demasiado grande, así que nunca tienes que hacer cast del error ni de su
`cause`.

```ts
try {
  await importTmx({ config, file: "legacy.tmx" });
} catch (error) {
  const at = tmxErrorLocation(error);
  if (at !== undefined) console.error(`line ${at.line}, column ${at.column}`);
}
```

### exportTmx

Escribe la memoria como TMX 1.4b. Entrada: `{ config, out?, cwd?, configPath?, glossaryPath?,
locales?, toolVersion? }`, donde `out` por defecto es `DEFAULT_TMX_PATH` (`verbatra-memory.tmx`),
exportado como constante. Antes de leer la memoria, `TMX_OUTPUT_CONFLICT` rechaza un `out` que no
nombra ningún archivo (también uno que termina en un separador de ruta), que queda fuera de `cwd` o
en el propio `cwd`, o que nombra un archivo de locale configurado, el archivo de bloqueo, la caché
de memoria de traducción, un archivo que verbatra busca para su configuración, el archivo
`configPath` o el archivo `glossaryPath`, sin distinguir mayúsculas de minúsculas y, cuando
`deps.fs` implementa `realpath` como el valor por defecto, otra vez tras resolver los enlaces
simbólicos. Una escritura que falla, porque el directorio no es escribible, ya hay un directorio en
esa ruta o el disco está lleno, lanza `TMX_UNWRITABLE` con el archivo y el código del sistema de
archivos en el mensaje. Solo se escriben las entradas bajo la huella de configuración actual, que es
el mismo conjunto que reutilizaría una ejecución. Las etiquetas de idioma se escriben en forma BCP
47 (`en_US` pasa a `en-US`), lo que no cambia cómo se indexa la memoria. Una memoria vacía produce
un archivo válido y vacío, no un error. Devuelve `{ path, units, locales, withoutSource,
illegalCharactersRemoved }`; `withoutSource` cuenta las entradas dejadas fuera porque la memoria no
tiene texto de origen para ellas, lo que solo ocurre con entradas arrastradas de una caché escrita
antes de que la memoria guardase el texto de origen, e `illegalCharactersRemoved` cuenta los
caracteres que XML 1.0 no puede representar y que se eliminaron del texto de los segmentos.

## Configuración

### loadConfig

Encuentra, carga y valida la configuración del proyecto, devolviendo una `VerbatraConfig`. Opciones:
`{ cwd?, configPath?, configOverride?, fs? }`, con precedencia de `configOverride` (validar un objeto en
memoria) sobre `configPath` (cargar un archivo explícito) sobre la búsqueda. La búsqueda empieza en
`cwd` y cubre `verbatra.config.ts` (también `.js`/`.cjs`), la familia `.verbatrarc` (`.json`, `.yaml`,
`.yml`, `.js`, `.cjs`, `.ts`) y una propiedad `"verbatra"` en `package.json`. Un `glossary` dado como
ruta de archivo se lee y valida aquí, así que el código posterior siempre ve un glosario en memoria:
un mapa de versión 1 de término de origen a traducción, o una definición de versión 2.

Lanza `CONFIG_NOT_FOUND` cuando no se encuentra nada, `CONFIG_INVALID` cuando se encuentra una
configuración pero es inválida. Consulta el [Archivo de configuración](/docs/config-file) para ver el esquema.
`fs` es el puerto del sistema de archivos a través del cual se lee un archivo de glosario, como se
describe en [El punto de inyección de dependencias](#el-punto-de-inyección-de-dependencias).

### loadConfigWithMeta

La misma carga, más la procedencia: devuelve `{ config, source, glossary }`, donde `source` dice si la
configuración vino de un acierto de búsqueda, de una ruta explícita o de una anulación en memoria (con
el `filepath` absoluto cuando lo hay), y `glossary` registra si el glosario estaba ausente, en línea o
resuelto desde un archivo. Úsalo cuando necesites mostrar de dónde salió la configuración.

### readGlossaryFile

<AvailableFrom version="0.9.0" />

Lee un glosario respaldado por archivo directamente del disco y lo devuelve como un `Glossary`
normalizado: `{ version, terms, doNotTranslate }`, donde `version` es `1` para un mapa plano de
términos y `2` para un [glosario por locale](/docs/config-file#glossary), y cada término lleva
`source`, un `target` opcional, `targets`, `forbidden`, `caseSensitive` y, de forma opcional, `note`
y `partOfSpeech`. Recibe `{ glossary }`, la `GlossaryProvenance` de `loadConfigWithMeta`, de modo
que el archivo que lee siempre es el que nombra la configuración; no hay ningún argumento de ruta.
Úsalo en una herramienta de larga duración que deba mostrar el glosario tal como está ahora y no
como estaba cuando se cargó la configuración.

Lanza `GLOSSARY_NOT_FILE_BACKED` cuando el glosario está en línea o ausente, y `CONFIG_INVALID`
cuando el archivo falta, es demasiado grande, no es UTF-8, no es JSON válido, no es ni un mapa plano
de cadenas ni un glosario válido de la versión 2, o declara otra versión.

<AvailableFrom version="0.12.0" />

Hasta la 0.11 devolvía el propio mapa plano de términos.

### updateGlossaryTerm

<AvailableFrom version="0.9.0" />

Añade, cambia o elimina exactamente un término de un glosario respaldado por archivo y devuelve el
glosario normalizado tal como queda. Recibe `{ glossary, cwd?, term, translation }`, donde
`translation` es el texto nuevo o `null` para eliminar el término. El resto del archivo conserva su
orden de claves y su sangría, la escritura es atómica y todo el ciclo de leer, modificar y escribir
se mantiene bajo un bloqueo de glosario para todo el proyecto, así que dos ediciones simultáneas se
serializan en vez de entrelazarse.

<AvailableFrom version="0.12.0" />

También recibe `locale` (entonces `translation` es la traducción propia de ese locale y `null` solo
elimina esa), `forbidden` (las traducciones que `locale` nunca debe usar; `null` o `[]` las
elimina), `note`, `partOfSpeech` (cada uno `null` para eliminarlo), `caseSensitive` y
`doNotTranslate` (`true` añade el término a los que no se traducen, `false` lo quita; no se puede
combinar con los campos del término). Un archivo de la versión 1 sigue siendo versión 1 mientras la
edición solo fije o elimine una traducción para todos los locales; cualquier otra edición lo
reescribe como versión 2, y cada término existente conserva su traducción como `target`. `translation: null` sin `locale` ahora elimina solo la traducción compartida; el término en sí
se elimina cuando ya no le queda ninguna traducción ni traducción prohibida, lo que en un término de
la versión 1 ocurre de inmediato.

Un glosario en línea se rechaza con `GLOSSARY_NOT_FILE_BACKED` en lugar de convertirse: vive dentro
de un módulo de configuración ejecutable. Un campo vacío, una edición que no fija ningún campo o que mezcla
`doNotTranslate` con los campos del término, traducciones prohibidas sin locale, un locale no válido,
una edición que dejaría un glosario no válido y una edición cuyo resultado superaría el límite de
1 MiB del glosario se rechazan con `CONFIG_INVALID`; una escritura fallida, incluido un bloqueo de escritura del glosario que no se puede crear en un proyecto de solo lectura o liberar tras una edición guardada, es `GLOSSARY_UNWRITABLE`, con el error del sistema de archivos como `cause`.
Una edición que deja el glosario tal como ya está tiene éxito y no escribe nada.

### glossaryForLocale

<AvailableFrom version="0.12.0" />

Resuelve la parte de un glosario que se aplica a un locale de destino:
`glossaryForLocale(config.glossary, "de")` devuelve `{ terms, doNotTranslate }`, cada término con el
`target` del locale (su propia entrada, luego la de su idioma base, luego la compartida), sus
traducciones `forbidden`, `caseSensitive`, y su `note` y `partOfSpeech`, o `undefined` cuando nada
del glosario se aplica allí. Es exactamente lo que una petición de traducción a ese locale lleva como
`TranslateRequest.glossary`, y lo que ven las comprobaciones de revisión y la huella de caché de
ese locale.

### glossaryHits

<AvailableFrom version="0.12.0" />

`glossaryHits(glossary, locale, sourceLocale, text)` devuelve las entradas del glosario que se
aplican a un texto de origen en un locale de destino, como `{ terms, doNotTranslate }` con la forma
que devuelve `glossaryForLocale`: cada término cuyo origen aparece en `text` como término completo,
con la traducción y las traducciones prohibidas a las que está sujeto ese locale, y cada término que
se mantiene sin traducir y aparece en él. Un término coincide con o sin mayúsculas según indique,
normalizando para `sourceLocale`. Usa la misma coincidencia que aplica una ejecución de traducción
al marcar un término de glosario omitido, y no lee nada.

### glossaryDraftCheck

<AvailableFrom version="0.12.0" />

`glossaryDraftCheck({ glossary, locale, sourceLocale, source, draft })` comprueba un borrador de
traducción contra las entradas del glosario que `glossaryHits` encuentra en el texto de origen,
antes de que lo escribas. Cada término vuelve con `targetUsed` (si el borrador lleva la traducción
obligatoria; ausente en un término que solo prohíbe traducciones) y `forbiddenUsed` (las
traducciones prohibidas que usa el borrador y no el origen), y cada término que se mantiene sin
traducir con `kept`. Son las reglas con las que una ejecución de traducción marca
`GLOSSARY_TERM_MISSED` y `GLOSSARY_FORBIDDEN_TERM`. No lee nada.

### normalizeGlossary

<AvailableFrom version="0.12.0" />

Convierte un glosario en cualquiera de sus formas, un mapa plano de la versión 1 o una definición de
la versión 2, al `Glossary` normalizado que devuelve `readGlossaryFile`, con todos los valores por
defecto rellenados. Úsalo para mostrar un glosario en línea igual que uno respaldado por archivo. No
vuelve a validar; `loadConfig` ya lo hizo.

### sharedGlossaryTranslations

<AvailableFrom version="0.12.0" />

Proyecta un `Glossary` normalizado sobre un mapa plano de cada término que tiene un `target`
compartido a esa traducción, en el orden del glosario. Las traducciones por locale, las traducciones
prohibidas y los términos de `doNotTranslate` quedan fuera, así que úsalo solo donde un consumidor
no pueda mostrar más que un mapa plano de términos. Un término llamado `__proto__` sigue siendo una
clave propia.

### redactGlossary

<AvailableFrom version="0.12.0" />

Pasa cada traducción, traducción prohibida, nota y categoría gramatical de un `Glossary`
normalizado por `redact` y devuelve `{ glossary, redactedTerms }`, donde `redactedTerms` nombra cada
término al que se le sustituyó un valor. Los términos de origen y los de `doNotTranslate` quedan
como están. El servidor MCP y Studio lo usan antes de que un glosario salga del proceso; úsalo igual
en tu propia herramienta.

### readCurrentGlossary

<AvailableFrom version="0.12.0" />

Lee el glosario que nombra una configuración cargada tal como está ahora:
`readCurrentGlossary({ loaded })`, donde `loaded` es lo que devuelve `loadConfigWithMeta`.
Un glosario respaldado por archivo se lee directamente del disco, uno en línea sale de la
configuración, y en ambos casos el resultado es el `Glossary` normalizado, o `undefined` cuando la
configuración no declara ninguno. Para ver a qué está sujeto un locale de destino, pasa el resultado
a `glossaryForLocale`.

### editConfiguredGlossaryTerm

<AvailableFrom version="0.12.0" />

`updateGlossaryTerm` para una herramienta que tiene una configuración cargada: recibe
`{ loaded, cwd?, term, ... }` con los mismos campos de edición, trata un campo dejado en `undefined`
como ausente y comprueba primero `locale` contra los locales de destino configurados; si no es uno de
ellos, falla con `UNKNOWN_LOCALE` y no escribe nada. El servidor MCP y Studio escriben el glosario
a través de ella.

### defineConfig

Un ayudante de identidad para escribir un `verbatra.config.ts` tipado: devuelve su argumento sin cambios y
existe puramente para la inferencia de tipos y el autocompletado del editor, incluido el completado de
los IDs de modelo conocidos del proveedor seleccionado. La restricción de modelos es solo al escribir;
en tiempo de ejecución cualquier cadena no vacía pasa la validación.

### verbatraConfigSchema

El esquema zod con el que valida `loadConfig`, exportado para que tu propia herramienta pueda validar un
objeto de configuración igual que lo hace el SDK. Las claves desconocidas de nivel superior se rechazan,
así que un secreto extraviado no puede esconderse en la configuración. La única excepción es
`$schema`, una cadena opcional que se acepta para que una configuración JSON o YAML pueda apuntar a
un editor hacia el documento JSON Schema que el paquete publica como
`@verbatra/sdk/config-schema.json`. Se ignora en tiempo de ejecución.

### scaffoldingMetadata

Metadatos de solo lectura de los que el comando `init` de la CLI deriva sus preguntas: `providerEnv` (de
id de proveedor a la variable de entorno de la que se lee su clave), `scaffoldModels` (un modelo de
scaffold por defecto por proveedor LLM), `providerTokenLimitKeys` (la clave de opción bajo la que cada
proveedor LLM recibe su límite de tokens de salida) y `supportedFormats` (el conjunto cerrado de ids de
formato). Lee la clave del límite de tokens de `providerTokenLimitKeys` en lugar de suponer una:
Anthropic la llama `maxTokens` y los demás `maxOutputTokens`, el esquema valida estrictamente las
opciones de cada proveedor, y DeepL y Google Cloud Translation no tienen entrada porque no reciben límite de tokens. El
tipo `ScaffoldableProviderId` es `Exclude<ProviderId, "openai-compatible" | "none">`, así que cubre los cinco
proveedores alojados; `openai-compatible` queda excluido porque no tiene una única variable de
entorno obligatoria.

`scaffoldingMetadata.humanOnlyProviderId` es `"none"`, el id que desactiva la traducción automática. No tiene entrada en `providerEnv`, porque no lee ninguna clave.

`scaffoldingMetadata.openAiCompatibleKeyEnv` es `"OPENAI_COMPATIBLE_API_KEY"`, la variable que lee un proveedor `openai-compatible` cuando sus opciones no nombran ningún `apiKeyEnvVar`. `scaffoldingMetadata.configSearchPlaces` lista cada nombre de archivo que `loadConfig` busca como configuración, en el orden en que los comprueba; un generador que escribe `verbatra.config.ts` debería negarse cuando ya existe otro de ellos, porque gana el primero que se encuentra.

### detectProject

<AvailableFrom version="0.12.0" />

Detecta el formato de los archivos de locale de un proyecto y su estructura a partir de sus archivos, igual que hace `verbatra init` antes de escribir una configuración. No escribe nada y no llama a ningún proveedor. Recorre el directorio (saltándose los directorios ocultos, `node_modules` y la salida de compilación, dentro de una profundidad y un número de entradas acotados) en busca de archivos que reclame un adaptador registrado, encuentra en cada uno el segmento de la ruta que escribe un locale, y se queda con el patrón de archivo que cubre más locales. El formato es aquel cuyo adaptador reclama con `canHandle` cada archivo encontrado según su contenido; para JSON, donde todos los adaptadores JSON lo hacen, decide una única biblioteca de i18n coincidente en `package.json`.

```ts
import { detectProject } from "@verbatra/sdk";

const detection = await detectProject({ cwd: "/path/to/project" });
if (detection.ambiguities.length > 0) {
  // several formats or file patterns fit: choose one of detection.ambiguities[0].candidates
}
const format = detection.format?.id;          // for example "yaml"
const pattern = detection.layout?.pattern;    // for example "config/locales/{locale}.yml"
```

El resultado lleva `format` (con `from`: `input`, `files` o `dependencies`), `layout` (`pattern`, `localeStyle`, `locales`, `sourceLocale`, `files`, `unqualifiedSourceFile`), `ambiguities` (cada una con un `subject` de `format` o `layout` y sus `candidates`), una `confidence` de `high`, `medium`, `low` o `none`, y `reasons`, una frase por decisión. Los empates se informan como ambigüedades, nunca se adivinan. Las entradas opcionales `format`, `pattern` y `sourceLocale` acotan la búsqueda, y `deps.fs` y `deps.adapterRegistry` sustituyen el sistema de archivos y los adaptadores, así que también se detectan los archivos de un adaptador de terceros. Nunca lanza una excepción por un archivo ausente, ilegible o malformado; en su lugar informa de menos. `layout.unqualifiedSourceFile` nombra un archivo junto al layout que guarda cadenas sin nombre de locale, como `messages.properties` o una plantilla `.pot` de gettext; entonces el locale de origen queda abierto en lugar de adivinarse, ya que el origen se lee del archivo que el patrón nombra para él.

### isMachineTranslationEnabled

<AvailableFrom version="0.12.0" />

Devuelve `false` exactamente cuando la configuración fija `provider: { id: "none" }`, el modo [solo humano](/docs/human-only-workflow) en el que nunca se construye un proveedor ni se lee una clave de API. Una interfaz que ofrece acciones que gastan en el proveedor lo lee para omitirlas por completo; así es como Studio y el servidor MCP retienen el gasto incluso con `--allow-spend`.

### assertMachineTranslationEnabled

<AvailableFrom version="0.12.0" />

Recibe la configuración y una frase corta que nombra la acción, y lanza un `SdkError` `MACHINE_TRANSLATION_DISABLED` con `provider: { id: "none" }`. Llámalo antes de envolver `translate` en una acción explícita de "traducir todo lo pendiente", para que la acción falle igual que `retranslateEntry` en lugar de rellenar en silencio solo desde la memoria de traducción.

## Adaptadores de formato

<AvailableFrom version="0.11.0" />

Todo lo necesario para construir un adaptador de un formato que verbatra no trae y registrarlo junto a los integrados. Un formato externo a verbatra se nombra con un identificador `custom:`, como `custom:toml`, que la configuración acepta igual que un nombre integrado. En [Adaptadores de formato propios](/docs/custom-format-adapters) tienes el recorrido completo, incluido en qué confías al instalar un adaptador de terceros: es código de plena confianza, y verbatra no lo aísla.

### createDefaultRegistry

Construye una `AdapterRegistry` con todos los adaptadores que verbatra trae, en orden de detección. Empieza aquí en lugar de con un registro vacío, para que tu formato se sume a los integrados en vez de reemplazarlos, y pasa el resultado como `deps.adapterRegistry` a cualquier flujo. `register` devuelve el registro, así que las altas se encadenan, y lanza un `AdapterError` con código `DUPLICATE_FORMAT` si el formato ya está ocupado.

```ts
import { createDefaultRegistry, translate } from "@verbatra/sdk";

const adapterRegistry = createDefaultRegistry().register(tomlAdapter);
const summary = await translate({ config }, { adapterRegistry });
```

### createFlatFileAdapter

Construye un `FormatAdapter` para un formato plano de clave/valor, donde cada entrada se direcciona con una sola clave sin anidamiento. Tú aportas `parseEntries`, `serializeEntries` y `extractPlaceholders` de tu formato; la fábrica aporta la lectura acotada por tamaño, la escritura atómica, la detección por extensión y el manejo estructurado de errores. `parseEntries` recibe además el locale con el que se lee el archivo, para un formato cuyo único archivo contiene a la vez el texto de origen y el de destino, y `serializeEntries` recibe el contexto de escritura de quien llama, cuyo `sourcePath` opcional nombra el archivo del locale de origen. Dale un `sniff` siempre que tu extensión sea genérica, o tu adaptador reclamará todos los archivos que la compartan y la detección informará de una ambigüedad en lugar de elegir. Los hooks opcionales son `validateMessage`, `computeInvalidIcuKeys`, `comparePlaceholders` y, desde 0.12.0, `compareBranchArms`; `fs` sustituye el puerto del sistema de archivos, `nodeAdapterFs` por defecto.

### createTreeFileAdapter

Construye un `FormatAdapter` para un formato de árbol, cuyas entradas viven en rutas a través de objetos anidados. Toma `parse` y `serialize` sobre un árbol más un `deriveEntry` que informa de los placeholders de cada hoja y de si es una forma plural, además de `extractPlaceholders` para un solo valor, y se encarga por su cuenta de aplanar y volver a anidar. Igual que la fábrica plana, toma `format`, `extensions` y un `sniff` opcional. También lleva los hooks opcionales que necesita un formato estructurado: `validateTree`, `validateMessage`, `computeInvalidIcuKeys`, `comparePlaceholders`, `compareBranchArms` (desde 0.12.0), `deriveDescriptions`, `buildWriteTree` y `keyMode`, y `fs` sustituye el puerto del sistema de archivos, `nodeAdapterFs` por defecto.

### nodeAdapterFs

El puerto de sistema de archivos, de tipo `AdapterFs`, que usa cada fábrica de adaptadores cuando no se le pasa ninguno: una lectura acotada por tamaño que informa de un archivo ausente o demasiado grande como estado en lugar de lanzar, y una escritura que pasa por un archivo temporal y un renombrado, de modo que una escritura interrumpida nunca deja un archivo de locale a medias. Lee y escribe a través de este puerto en un adaptador propio en lugar de recurrir a `node:fs`. Es una convención, no una frontera, y verbatra no puede imponerla en código que no le pertenece.

### isCustomFormatId

Acota un identificador de formato a uno externo: true para un identificador `custom:` bien formado, false para cualquier nombre de formato integrado. Útil cuando tus propias herramientas tienen que distinguirlos, por ejemplo para decidir si hace falta aportar un registro antes de poder ejecutar una configuración.

## Redacción de secretos

<AvailableFrom version="0.10.0" />

### redact

Elimina de una cadena las formas de clave de API de proveedor y el valor exacto actual de cualquier
variable de entorno de proveedor configurada, reemplazando cada coincidencia por `[REDACTED]`.
`@verbatra/studio` y `@verbatra/mcp` lo aplican los dos a todo valor que devuelven a quien llama y
que no han generado ellos mismos, como un término del glosario, una ruta de archivo o un mensaje de
error de un sistema previo, así que una clave ya presente en tu entorno o escrita en un archivo del
proyecto nunca puede llegar a una pestaña del navegador, un agente ni una línea de log. La CLI
`verbatra` pasa por él, como último paso, todo lo que escribe en stdout y stderr, incluido el sobre
`--json`.

Esto incluye la variable que un proveedor `openai-compatible` nombra con `apiKeyEnvVar`. Se declara
cuando `loadConfig` carga una config que la nombra o cuando se construye ese proveedor, y desde ese
momento su valor se elimina igual que el de las variables integradas. Las declaraciones nunca se
retiran. Un valor de menos de ocho caracteres no se elimina por su valor, así que una variable corta
nunca puede borrar texto ajeno.

Una clave de DeepL se reconoce solo por su forma únicamente cuando lleva el sufijo `:fx` de una
clave gratuita, o cuando un UUID suelto está en un contexto de clave: tras una cabecera
`DeepL-Auth-Key`, o tras un nombre como `auth_key`, `authKey`, `--auth-key`, `api_key`, `deeplKey`,
`DEEPL_API_KEY` o `DEEPL_AUTH_KEY` seguido de `:`, `=`, un `%3D` codificado en URL o un espacio, con
o sin comillas, también dentro de JSON serializado en una cadena. Cualquier otro UUID, como uno en
una ruta de archivo o un id de petición, sigue legible. Una clave Pro guardada en `DEEPL_API_KEY`
se sigue eliminando por su valor dondequiera que aparezca.

Un token `sk-` se redacta en cuanto le siguen al menos 32 letras y dígitos tras `sk-`, contados en
todos sus segmentos `-` y `_`, sea cual sea su prefijo. Esa única regla cubre todas las formas de
clave de OpenAI y Anthropic; un prefijo conocido como `sk-proj-` o `sk-ant-` no redacta por sí solo
un token más corto. El token solo cuenta cuando no le precede directamente una letra ni un dígito:
un escape JSON como `\n` o `\u0007`, un carácter codificado en porcentaje como `%3D`, una secuencia
ANSI CSI como `\x1b[31m`, `\x1b[2K` o `\x1b[?25h`, una selección de juego de caracteres ANSI como
`\x1b(B`, o cualquiera de las dos formas ANSI escapada en JSON como `\u001b` también es un límite.
Una ruta o clave de locale eslovaco como `locales/sk-SK.json` o `sk-banner_headline` sigue legible.
Pero una clave larga con aspecto eslovaco alcanza el umbral y se redacta:
`sk-SK_settings_notifications_email_digest` tiene 34 letras y dígitos tras `sk-`, igual que una
clave camelCase larga como `sk-onboardingWelcomeScreenPrimaryButton`.

### declareProviderKeyEnvVar

<AvailableFrom version="0.12.0" />

Declara la variable que un bloque `provider` nombra como origen de la clave, para que `redact`
elimine su valor. Hoy solo un proveedor `openai-compatible` con `apiKeyEnvVar` nombra una; con
cualquier otro proveedor no hace nada. `loadConfig` y la construcción del proveedor ya lo hacen, y
Studio y el servidor MCP también lo hacen para la config que reciben, así que llámalo solo cuando
una config llegue a tu propio código por otra vía. La declaración vale para todo el proceso y la
comparten todas las copias del SDK cargadas en él.

## El punto de inyección de dependencias

<AvailableFrom version="0.9.0" />

`deps.fs` sustituye el puerto de sistema de archivos por el que viaja la propia I/O del SDK, con el
tipo `SdkFs`. El punto de inyección es completo: el archivo de estado de la ejecución, el archivo
de bloqueo, las herramientas del archivo de glosario, la I/O de libros e intercambio y los propios archivos
de locale pasan todos por él, porque los adaptadores de formato leen y escriben a través de un
puerto construido con ese mismo objeto. Así una ejecución entera se puede mantener en memoria, que
es como las pruebas del propio SDK evitan tocar el disco y como una aplicación anfitriona puede
respaldar parte de un proyecto con algo que no sea un disco local.

```ts
import { translate, type SdkFs } from "@verbatra/sdk";

const summary = await translate({ config }, { fs: inMemoryFs satisfies SdkFs });
```

Una implementación tiene que respetar dos puntos del contrato. Las lecturas están acotadas por
tamaño: `readFileBounded` y `readBytesBounded` reciben un límite de bytes e informan de `missing` o
`too-large` como estado en lugar de lanzar, que es lo que impide que un archivo hostil o
accidentalmente enorme agote la memoria. Las escrituras deben ser atómicas, de modo que una caída a
mitad de escritura nunca deje un archivo a medio escribir, y `createExclusive` debe ser atómica
frente a otros procesos porque es la primitiva detrás del bloqueo de escritura por locale. Crear
directorios es tarea de quien llama.

`readDirectory` es opcional, para que una implementación escrita antes de que existiera la
extracción desde código siga compilando. [`extract`](#extract) es el único punto de entrada que lo
necesita, e informa de su ausencia como `EXTRACT_FS_UNSUPPORTED`. Lista las entradas inmediatas de
un directorio como `{ name, kind }`, donde `kind` es `"file"`, `"directory"` u `"other"`. Un enlace
simbólico pertenece a `"other"`: el análisis nunca lo sigue, y eso es lo que lo mantiene dentro de
las raíces que recibió.

`realpath` también es opcional. Resuelve todos los enlaces simbólicos de una ruta existente, y las
guardas de salida de [`generateTypes`](#generatetypes), [`exportTmx`](#exporttmx),
[`exportWorkbook`](#exportworkbook) y [`pseudolocalize`](#pseudolocalize) lo usan para ver
dónde cae de verdad una ruta de salida, así que un enlace no puede llevar un archivo escrito fuera
de `cwd` ni sobre un archivo del que depende el proyecto. Sin él, esas guardas comparan las rutas
tal como están escritas. Un enlace en la ruta de salida cuyo destino no existe no se puede resolver,
así que las guardas dan por hecho que `writeFile` y `writeBytes` reemplazan ese enlace en lugar de escribir a través
de él, como hace la escritura atómica por defecto.

`rename` también es opcional.

<AvailableFrom version="0.12.0" />

Mueve un archivo a un nombre nuevo en el mismo directorio en un solo paso atómico, reemplazando
cualquier archivo que ya esté allí, y rechaza con un error cuyo `code` es `ENOENT` cuando falta el
origen. El bloqueo de escritura lo usa para quitar un bloqueo o una guarda de recuperación que dejó
un proceso que ya no existe, y para liberar su propio bloqueo: el archivo se aparta con un nombre
único `<name>.<pid>.<tag>.<uuid>.stale` y solo se borra si sigue siendo el registro que esperaba el
bloqueo. Cualquier otra cosa, como un bloqueo que otro proceso tomó entretanto, se devuelve a su
sitio con `createExclusive`. Un renombrado que falla con `EPERM`, `EBUSY` o `EACCES`, como informa
Windows de un archivo que otro proceso tiene abierto, cuenta como "no recuperado en este sondeo", y
el bloqueo sigue sondeando hasta su tiempo límite. Cuando el renombrado que libera un bloqueo falla
por cualquier motivo, la liberación recurre a leer el archivo de bloqueo y borrarlo mientras siga
llevando el token de quien lo tiene, y reintenta unas cuantas veces, con un sondeo de separación, un
fallo con `EPERM`, `EBUSY` o `EACCES`. Un registro que debería devolverse a su sitio pero no puede,
porque un tercer proceso tomó la ruta entretanto, se borra, ya que la comprobación del token de
quien lo tenía falla a partir de ese momento. Sin `rename`, el bloqueo lee el archivo y lo
borra si no ha cambiado, lo que deja una ventana más amplia en la que se borra un bloqueo que otro
proceso acaba de tomar.

Apartar un archivo y devolverlo son dos pasos, así que en intercalados poco frecuentes dos procesos
pueden creer durante un momento que tienen el mismo bloqueo. Por eso cada bloqueo registra un token
de propiedad aleatorio, y antes de cada escritura que protege el bloqueo (el archivo del locale, el
archivo de bloqueo, el archivo de procedencia, el glosario) quien lo tiene comprueba que el archivo
de bloqueo sigue llevando su token. Si no es así, la operación se detiene con `LOCK_CONTENDED` y no
escribe nada. Un archivo de bloqueo que falta o lleva otro token al liberar se informa igual cuando
la operación terminó bien, porque el otro proceso puede haber cambiado los mismos archivos desde
entonces; una operación que falló lanza su propio error. La comprobación y la escritura siguen
siendo dos pasos, y nada limita el tiempo entre ellos: quien tiene el bloqueo y se pausa justo
después de la comprobación (una máquina suspendida, un proceso detenido, un depurador, un salto del
reloj o un bucle de eventos bloqueado mucho tiempo) deja de latir, así que cuando su bloqueo tiene
tres intervalos (30 segundos por defecto) otro proceso de la misma máquina lo toma, y quien estaba
pausado todavía puede escribir una vez al continuar. La comprobación del token da por hecho que `createExclusive` crea un archivo que `readFileBounded` lee
de vuelta, así que una implementación propia tiene que cumplirlo.

`touch` y `mtimeMs` también son opcionales.

<AvailableFrom version="0.12.0" />

`touch(path)` pone la fecha de modificación de un archivo existente en el momento actual, y
`mtimeMs(path)` la devuelve en milisegundos, o `undefined` si falta el archivo. Con `touch`, quien
tiene un bloqueo registra en él un intervalo de latido de 10 segundos y refresca la fecha de
modificación del archivo a ese ritmo mientras lo tiene. También la refresca justo después de
crearlo, para que la antigüedad del archivo se mida con el reloj de este proceso y no con el del
servidor de archivos. Con `mtimeMs`, un proceso en espera trata
como abandonado un bloqueo de su propia máquina cuyo proceso sigue en marcha pero cuyo archivo no
se ha refrescado durante tres de los intervalos registrados (30 segundos por defecto). Eso cubre un
registro de bloqueo que sobrevivió a su uso, por ejemplo uno devuelto a su sitio para un proceso de
Studio, `watch` o del servidor MCP de larga duración que ya lo había liberado. Una guarda de
recuperación no registra latido: se quita cuando su proceso ya no existe de forma demostrable y se
ha visto sin cambios en dos sondeos. Sin estos miembros, un bloqueo solo se considera abandonado cuando su
proceso ya no existe de forma demostrable.

Un proceso que se cae mientras tiene un bloqueo apartado puede dejar un archivo `.stale` en
`.verbatra-local/locks/`. Puedes borrar esos archivos a mano sin riesgo, y la siguiente adquisición
de un bloqueo los borra cuando el proceso que los movió ya no existe o, si `touch` está
implementado, cuando superan el umbral de caducidad, contado desde que se apartaron. Un sistema de
archivos sin `touch` los conserva hasta que su proceso ya no existe.

`deps.fs` no alcanza un `deps.adapterRegistry` suministrado por quien llama. Esos
adaptadores los construyó quien llama, así que su acceso a archivos es el que quien llama haya
cableado en ellos. Suministrar ambos significa que quien llama es dueño de ese cableado.

La carga de la configuración también queda fuera del punto de inyección. `loadConfig` y
`loadConfigWithMeta` no reciben `deps`: leen el propio archivo de configuración del disco real, y un
archivo de glosario que nombre la configuración a través de su propia opción `fs`, así que el
`deps.fs` que recibe un flujo posterior no alcanza ninguna de las dos lecturas. Para mantener un
proyecto entero en memoria, pasa el mismo `SdkFs` como `loadConfig({ fs })` y entrega la
configuración como `configOverride` en lugar de como archivo.

## La anatomía de RunSummary

`translate`, `importWorkbook` y cada ejecución exitosa de `watch` resuelven a un `RunSummary`:

```ts
interface RunSummary {
  dryRun: boolean;          // true when nothing was written and no provider was called
  locales: LocaleSummary[]; // one entry per target locale, in config order
  succeeded: string[];      // locales whose run succeeded
  partial: string[];        // locales written with keys still missing; the CLI exits 1 on these
  failed: string[];         // locales whose run failed
  usage?: UsageSummary;     // summed input/output tokens; absent when no call reported usage
  budget?: RunBudget;       // present only when maxTokens is configured
  estimate?: RunEstimate;   // present only when the run was asked for a pre-run estimate
}

interface LocaleSummary {
  locale: string;
  status: "succeeded" | "partial" | "failed";
  translated: string[];          // keys translated this run (in dry-run, keys that would be)
  cacheHits: string[];           // keys served from the translation-memory cache this run
  fuzzyHits: FuzzyCacheHit[];    // reuses for a source string that changed, with their scores
  unchanged: string[];           // keys already up to date
  orphaned: string[];            // target keys with no matching source key (always reported)
  pruned: string[];              // orphaned keys removed this run; empty unless pruning is on
  invalidIcuSource: string[];    // source keys skipped for invalid ICU
  integrityMismatches: string[]; // translations the integrity gate withheld
  integrityRefusals?: { key: string; reason: string; details?: string[] }[]; // why each was withheld; translate, watch, and importWorkbook
  providerFailures: string[];    // keys withheld because nothing was translated for them
  budgetWithheld: string[];      // keys never sent because a "stop" budget already tripped
  generated: string[];           // CLDR plural forms synthesized this run
  unfilled: string[];            // blank import rows, or keys a human-only translate left for a human
  protected: { key: string; reason: string; suggestion?: string; suggestionStatus?: string }[]; // keys left for a person
  malformedRows: { row: number; line?: number; column: string }[]; // import only: rows the reader could not parse
  duplicateKeys: { key: string; row: number; line?: number }[];    // import only: later rows for a duplicated key
  notices: LocaleNotice[];       // provider notices and SDK notices for this locale
  needsReview: { key: string; reasons: string[] }[]; // accepted keys flagged for a second look
  usage?: UsageSummary;          // this locale's summed tokens; absent if nothing reported usage
  error?: { code: string; message: string }; // only on a "failed" locale, and not on every one
}
```

Las partes que conviene conocer:

- **needsReview** lista claves aceptadas y escritas que las heurísticas de revisión marcaron, cada una
  con sus códigos de motivo: `LENGTH_RATIO_OUTLIER`, `MAX_LENGTH_EXCEEDED`, `EQUALS_SOURCE`,
  `GLOSSARY_TERM_MISSED`, `GLOSSARY_FORBIDDEN_TERM`, `INTEGRITY_REORDERED`, `PROVIDER_DEGRADED` y `FUZZY_CACHE_REUSE`. El
  conjunto se publica como la tupla `REVIEW_REASON_CODES`, así que construye a partir de ella
  cualquier esquema en tiempo de ejecución o búsqueda exhaustiva, en lugar de reescribir los
  miembros. Una señal de revisión es orientativa y nunca retiene una
  clave, así que una clave nunca aparece a la vez en `needsReview` y en `integrityMismatches`. Consulta
  [Seguridad de la traducción](/docs/translation-safety) para saber qué significa cada código y
  [Revisión en Studio](/docs/review-in-studio) para trabajar la cola.
- **notices** vive por locale, nunca en el nivel superior. Cubre avisos del proveedor (por ejemplo, una
  degradación de DeepL) y avisos del SDK con los códigos `PLURAL_CATEGORIES_INCOMPLETE`,
  `SUB_BATCH_FAILED`, `BLANK_ROW_BASELINE_RETAINED`, `BUDGET_TOKENS_EXCEEDED`,
  `CACHE_VERSION_UNRECOGNIZED`, `PROVENANCE_VERSION_UNRECOGNIZED`, `LOCALE_STATE_CARRIED_OVER` (el estado guardado bajo una grafía con guion bajo como `pt_BR` se trasladó al `pt-BR` configurado; consulta [Un código de locale reescrito](/docs/the-lock-file#un-código-de-locale-reescrito)), `LOCALE_STATE_CARRY_OVER_SKIPPED` (ese traslado queda para la siguiente ejecución porque el guard del archivo de bloqueo siguió ocupado o no se pudo leer ni crear, o no se pudo escribir un archivo; salvo que solo quedara atrás la memoria de traducción, el locale no se ejecutó y falló con `LOCALE_STATE_NOT_CARRIED_OVER`) y `PROVENANCE_FILE_TOO_LARGE`
  (registrar un locale habría hecho crecer `verbatra.provenance.json` por encima de lo que verbatra
  vuelve a leer, así que el archivo se dejó como estaba). El aviso de caché es de toda la ejecución (un solo archivo, compartido
  por cada locale), así que se adjunta a cada locale de la ejecución.
- **usage** es `undefined`, nunca un cero inventado, siempre que nada en ese ámbito informara de uso:
  un dry run nunca llama a un proveedor, y DeepL nunca informa de tokens. `RunSummary.usage`
  es la suma sobre los locales.
- **budget** aparece solo cuando `maxTokens` está configurado: `{ maxTokens, behavior, supported,
  tokensUsed, exceeded }`. `supported` dice si `tokensUsed` es enteramente el uso que informa el
  propio proveedor; es `false` en cuanto una petición vuelve sin una cifra utilizable, y entonces el
  total es en parte la proyección de verbatra, que se cuenta y se aplica igualmente. Un dry run lo
  informa con `tokensUsed: 0`, porque no se envió nada. Con `behavior: "stop"` el techo
  se comprueba antes de cada petición que envía la ejecución, incluida cada mitad de una petición
  vuelta a partir, así que `tokensUsed` queda en el techo o por debajo salvo por un residuo: la
  última petición admitida se reconcilia con lo que informó el proveedor, lo que puede empujar el
  total por encima del techo a posteriori. Después de eso no se envía nada más. Dos cosas quedan
  fuera de lo que una reserva puede acotar, porque pasan dentro de una petición ya admitida: la capa
  de proveedor envía una petición de reparación propia cuando faltan claves, así que un lote
  admitido puede costar hasta cerca del doble de su proyección, y el recuento no es mejor que lo que
  informa el proveedor. Ambas llegan en la reconciliación, y después de eso no se admite nada
  más. El presupuesto acota una llamada a `translate`: `watch` arranca uno nuevo por ejecución, y
  `retranslateEntry` no queda cubierto en absoluto.
- **error.code** en un locale fallido es una cadena preservada (el código subyacente del proveedor o del
  adaptador, con `LOCALE_FAILED` solo como reserva), así que no lo trates como un conjunto cerrado. Un
  locale `failed` no siempre lleva `error`: uno cuyas claves se retuvieron todas, y por eso aparecen
  en `integrityMismatches`, `providerFailures` o `budgetWithheld`, falla sin que se lance nada. El
  motivo está en esas listas y en sus `notices`, como `SUB_BATCH_FAILED` para un lote del proveedor
  que falló o `BUDGET_TOKENS_EXCEEDED` para el presupuesto de tokens. Comprueba `status`, nunca si
  `error` está presente.
- **cacheHits** lista las claves servidas desde la [caché de memoria de traducción](/docs/the-cache)
  en lugar del proveedor. **fuzzyHits** lista las claves que reutilizaron una traducción para
  una cadena de origen que había cambiado, cada una con `key`, `similarity` y el `previousSource` con
  el que coincidió; está vacía salvo que `fuzzyCache` esté activado, y esas claves nunca se cuentan en
  **cacheHits**. **unfilled**, **malformedRows** y **duplicateKeys** solo los rellena
  `importWorkbook` (una ejecución de `translate` los deja vacíos): una fila en blanco cuya clave
  todavía necesita traducción en el momento de la importación (tanto si se exportó como `new` como si
  se exportó como `changed`), una fila del libro que el lector no pudo parsear y una clave duplicada
  cuya primera aparición ganó. El `line` opcional de las dos últimas es la línea del archivo en la
  que empieza el registro, y solo está presente en una importación delimitada (`csv` o `tsv`). La única excepción es un proyecto [solo humano](/docs/human-only-workflow): ahí `translate` y `watch` listan en **unfilled** cada clave para la que la memoria de traducción no tenía una entrada exacta, y **fuzzyHits** queda vacía porque ahí nunca se aplica una reutilización aproximada.
- **protected** lista las claves que una ejecución de `translate` dejó en paz, cada una con su `reason` (`human`, `import`, `external` o `pinned`) y, con `humanEdits: "suggest"`, una `suggestion` (la respuesta del proveedor o una entrada exacta de la memoria de traducción, nunca una coincidencia aproximada), que no se escribió, y un `suggestionStatus`: `planned` en un dry run, `suggested` o por qué no (`integrity-mismatch`, `provider-failure`, `budget-withheld`). Una sugerencia fallida nunca cambia el estado de un locale. No están en **translated**, nunca cambian el estado de un locale y siguen obsoletas para `check`. `importWorkbook` lo deja vacío. Consulta [Proteger traducciones humanas](/docs/protecting-human-translations).

### budgetStanding

<AvailableFrom version="0.11.0" />

Clasifica un `RunBudget` en uno de tres valores `BudgetStanding`, la misma clasificación que
informan la línea de presupuesto de la CLI, Studio y la herramienta de agente `usage.summary`:
`"within"` cuando la ejecución nunca llegó a su techo, `"stopped-before-ceiling"` cuando un
presupuesto `"stop"` retuvo una petición mientras `tokensUsed` seguía por debajo de `maxTokens`, y
`"reached"` cuando `tokensUsed` alcanzó o superó `maxTokens`. Úsalo en lugar de leer solo
`exceeded`, que vale `true` en los dos últimos casos.

## El modelo de errores

Los fallos de toda la ejecución lanzan un `SdkError`: una sola clase, un `code` estable y un `message`
sin secretos. Ramifica sobre el código, no sobre el mensaje. Los fallos por locale, los avisos del
proveedor y los hallazgos de integridad se comunican como datos en el `RunSummary`, nunca se lanzan.

| Código | Cuándo |
| --- | --- |
| `CONFIG_NOT_FOUND` | la búsqueda no encontró ninguna configuración, o un `configPath` explícito no existe (lanzado por `loadConfig`) |
| `CONFIG_INVALID` | se encontró una configuración pero no se puede parsear o falla la validación, o su archivo de glosario no se pudo resolver; un `translate` que no es dry run y `retranslateEntry` también lo lanzan cuando `VERBATRA_NETWORK_POLICY` o `VERBATRA_NETWORK_ALLOWED_HOSTS` tiene un valor no válido, antes de construir ningún proveedor |
| `UNKNOWN_FORMAT` | no hay adaptador registrado para el formato configurado; se lanza antes de leer ningún archivo |
| `UNKNOWN_LOCALE` | un locale solicitado no está entre los locales de destino configurados |
| `UNKNOWN_KEY` | una clave solicitada no está en el recurso de origen (`keyValue`, `editEntry`, `retranslateEntry`, `approveEntry`, `rejectEntry`) |
| `KEY_PROTECTED` | `retranslateEntry` se negó a reemplazar un valor que escribió, importó o cambió una persona fuera de verbatra, porque ni `includeHuman` ni `humanEdits: "overwrite"` lo permitían |
| `KEY_PINNED` | la clave coincide con los `pinnedKeys` de la configuración, así que se rechazó una escritura automática (`retranslateEntry`, y `editEntry` con `actor: "agent"`) |
| `PROVIDER_CONSTRUCTION_FAILED` | el proveedor no se pudo construir; envuelve el error propio del proveedor, incluida una clave de API ausente |
| `MACHINE_TRANSLATION_DISABLED` | la configuración fija `provider: { id: "none" }`, así que se rechazó una acción que gasta en el proveedor antes de construir ningún proveedor (`retranslateEntry`, `assertMachineTranslationEnabled`); `translate` y `watch` nunca lo lanzan |
| `NETWORK_POLICY_VIOLATION` | la [política de red](/docs/network-policy) efectiva no permite el endpoint del proveedor ni su proxy; lo lanzan `translate` fuera de una ejecución de prueba, `watch` al arrancar y `retranslateEntry`, antes de construir el proveedor o leer ninguna clave de API |
| `SOURCE_UNREADABLE` | el archivo del locale de origen no existe |
| `SOURCE_INVALID` | el archivo del locale de origen no se pudo leer o parsear; envuelve el error de lectura del adaptador |
| `LOCK_FILE_INVALID` | el archivo de bloqueo está presente pero corrupto, es demasiado grande o está en una versión no admitida |
| `PROVENANCE_FILE_INVALID` | el archivo de procedencia está presente pero corrupto, es demasiado grande o tiene una forma incorrecta; lo lanza una escritura (`translate`, `watch`, `importWorkbook`, `editEntry`, `retranslateEntry`, `approveEntry`, `rejectEntry`) antes de cambiar nada, y `loadProvenance`, nunca un informe; uno de un verbatra más nuevo se deja intacto en su lugar, y `translate`, `watch` e `importWorkbook` informan el aviso `PROVENANCE_VERSION_UNRECOGNIZED` |
| `PROVENANCE_FILE_UNWRITABLE` | una decisión de revisión no se pudo guardar porque el archivo de procedencia es de un verbatra más nuevo o crecería por encima del tamaño que verbatra vuelve a leer (`approveEntry`, `rejectEntry`); no se escribe nada |
| `REVIEW_VALUE_CHANGED` | la clave no tiene valor, o su valor no es el `expectedValue` que vio quien revisa (`approveEntry`, `rejectEntry`) |
| `REVIEW_SOURCE_CHANGED` | el origen cambió desde que se escribió el valor, así que no se puede aprobar tal cual (`approveEntry`) |
| `REVIEW_REJECT_UNSUPPORTED` | el formato conserva el valor de una clave cuando el archivo se escribe sin ella, como XLIFF, o el archivo del locale es demasiado grande para guardar una copia que restaurar, así que `rejectEntry` dejó el archivo como estaba |
| `REVIEW_RESTORE_FAILED` | `rejectEntry` falló después de reescribir el archivo de locale, y también falló la restauración del archivo de locale o del archivo de procedencia; el mensaje nombra el fallo original (también la `cause`) y los archivos que tienes que recuperar del control de versiones |
| `REVIEWER_INVALID` | `reviewer` está vacío, tiene más de 64 caracteres o contiene un carácter de control (`approveEntry`, `rejectEntry`) |
| `LOCK_CONTENDED` | el bloqueo de escritura de un locale, o el bloqueo del glosario que toma `updateGlossaryTerm`, no se pudo adquirir antes de su tiempo límite, u otro proceso lo tomó antes de una escritura que protege, y no se escribió nada; el mensaje nombra la ruta del archivo de bloqueo |
| `GLOSSARY_NOT_FILE_BACKED` | el glosario de la configuración está en línea o ausente, así que no hay ningún archivo de glosario que leer o reescribir (`readGlossaryFile`, `updateGlossaryTerm`) |
| `GLOSSARY_UNWRITABLE` | el archivo de glosario no se pudo escribir, o no se pudo crear el bloqueo de escritura del glosario, por ejemplo en un proyecto de solo lectura, o liberarlo tras una edición guardada (`updateGlossaryTerm`); el error del sistema de archivos es la `cause` |
| `LOCALE_LAYOUT_INVALID` | `files.pattern` y `files.localeStyle` no se pueden combinar, o el estilo no tiene una escritura de ruta válida para un locale configurado |
| `LOCALE_PATH_COLLISION` | dos locales configurados resuelven al mismo archivo absoluto |
| `CONCURRENCY_INVALID` | se definió `concurrency` pero no es un entero de al menos 1; se lanza antes de que se ejecute ningún locale |
| `CONCURRENCY_BUDGET_CONFLICT` | una ejecución real fijó `concurrency` por encima de 1 mientras rige un presupuesto de tokens, configurado o de la ejecución; se lanza antes de cualquier llamada al proveedor (un dry run queda exento) |
| `MAX_TOKENS_INVALID` | el `maxTokens` por ejecución de `translate` se fijó pero no es un número entero de al menos 1; se lanza antes de leer o gastar nada |
| `LOCK_TIMEOUT_INVALID` | `lockAcquireTimeoutMs` se fijó pero no es un número entero de milisegundos de al menos 0 (`translate`, `watch` al arrancar, `importWorkbook`, `retranslateEntry`, `retranslateEntries`); se lanza antes de leer o bloquear nada |
| `TARGET_UNWRITABLE` | un archivo de locale de destino no se pudo escribir (su directorio no es escribible, no existe, es de solo lectura o se quedó sin espacio); el mensaje nombra el archivo de destino y el código del sistema de archivos, nunca el archivo temporal interno que usa la escritura atómica |
| `PSEUDO_OUTPUT_CONFLICT` | se pidió a `pseudolocalize` un pseudolocale que nombra un locale configurado, o una ruta de salida que escribiría sobre un archivo de locale configurado o fuera de `cwd`, también tras resolver los enlaces simbólicos; se rechaza antes de leer o escribir nada |
| `SOURCE_UNWRITABLE` | el archivo del locale de origen no se pudo escribir (solo `extract`); `xliff` y `apple-xcstrings` llegan aquí cuando todavía no existe un catálogo, porque ninguno se crea desde cero |
| `EXTRACT_NOT_CONFIGURED` | se llamó a `extract` con una configuración que no lleva bloque `extract` |
| `EXTRACT_FS_UNSUPPORTED` | se pasó a `extract` un `deps.fs` que no implementa `readDirectory`, así que no se puede descubrir ningún archivo de código |
| `TYPES_OUTPUT_CONFLICT` | `generateTypes` rechazó su ruta de salida: una que no nombra ningún archivo (o termina en un separador de ruta), es absoluta, sale de `cwd` con `..` o nombra el propio `cwd` o no termina en `.ts`, `.mts` o `.cts`, y una que nombra un archivo de locale configurado, el archivo de bloqueo, el archivo de procedencia, la caché de memoria de traducción, un archivo que verbatra busca para su configuración, el archivo de configuración que cargó la ejecución, o el archivo de glosario de la configuración, también tras resolver los enlaces simbólicos; una ejecución que escribe también se niega a reemplazar un archivo existente que no empieza con la línea de cabecera de verbatra |
| `TYPES_UNWRITABLE` | el archivo de declaraciones que produce `generateTypes` no se pudo escribir (su directorio no es escribible, no existe, o el disco se quedó sin espacio); el mensaje nombra el archivo y el código del sistema de archivos |
| `TMX_OUTPUT_CONFLICT` | `exportTmx` rechazó su ruta de salida: una que no nombra ningún archivo (o termina en un separador de ruta) o que queda fuera de `cwd` o en el propio `cwd`, y una que nombra un archivo de locale configurado, el archivo de bloqueo, el archivo de procedencia, la caché de memoria de traducción, un archivo que verbatra busca para su configuración, el archivo de configuración que cargó la ejecución, o el archivo de glosario de la configuración, también tras resolver los enlaces simbólicos; se rechaza antes de leer la memoria |
| `TMX_UNWRITABLE` | el archivo TMX que produce `exportTmx` no se pudo escribir (su directorio no es escribible, ya hay un directorio en esa ruta, o el disco se quedó sin espacio); el mensaje nombra el archivo y el código del sistema de archivos |
| `EXPORT_OUTPUT_CONFLICT` | `exportWorkbook` rechazó su ruta de salida: una que queda fuera de `cwd`, y una que, por sí misma o a través de un archivo que la exportación escribiría dentro, nombra un archivo de locale configurado, el archivo de bloqueo, el archivo de procedencia, la caché de memoria de traducción, un archivo que verbatra busca para su configuración, el archivo de configuración que cargó la ejecución, o el archivo de glosario de la configuración, también tras resolver los enlaces simbólicos; una ruta `xlsx` que no nombra ningún archivo o nombra el propio `cwd` también se rechaza; se rechaza antes de leer nada |
| `EXPORT_UNWRITABLE` | el archivo de entrega que produce `exportWorkbook` no se pudo escribir (su directorio no es escribible, hay un directorio o un archivo en medio, o el disco se quedó sin espacio); el mensaje nombra el archivo y el código del sistema de archivos, y el error del sistema de archivos es la `cause` |
| `LOCALE_STATE_NOT_CARRIED_OVER` | nunca se lanza: se registra en el `error` de un locale que `translate` o `watch` no ejecutó porque su estado bajo un código reescrito como `pt_BR` no se pudo trasladar a él en el archivo de bloqueo o en el de procedencia; la siguiente ejecución lo vuelve a intentar ([Un código de locale reescrito](/docs/the-lock-file#un-código-de-locale-reescrito)) |
| `LOCALE_FAILED` | nunca se lanza: el `code` de reserva registrado en el `error` de un locale fallido |

Algunos códigos llevan además el error que envuelven como `cause` estándar: `SOURCE_INVALID` cuando
falló un analizador o un adaptador (no cuando un archivo se rechaza por su tamaño),
`PROVIDER_CONSTRUCTION_FAILED` (el propio error de la factoría del proveedor, cuyo mensaje también
pasa redactado al mensaje del `SdkError`), `EXPORT_UNWRITABLE` y `GLOSSARY_UNWRITABLE` (el error del sistema de archivos) y
`REVIEW_RESTORE_FAILED` (el fallo que interrumpió la decisión). `CONFIG_NOT_FOUND` y
`CONFIG_INVALID` no llevan ninguno a propósito, porque el error de un analizador de configuración
puede citar el contenido del archivo, y una clave escrita en la configuración no debe viajar con el
error. En `PROVIDER_CONSTRUCTION_FAILED` solo se redacta el mensaje: su `cause` es el error original,
intacto. Las factorías de proveedor integradas lanzan errores sin secretos, y un error lanzado por un
`createProvider` que pasas tú vuelve exactamente como lo lanzaste, así que mantén los secretos fuera
de él o redáctalo tú antes de registrar el `cause`.

Dos excepciones a la regla de una sola clase de error: `retranslateEntry` relanza el `ProviderError`
propio del proveedor cuando la llamada única falla, y `runStatus` no lanza nunca. Para cómo estos
códigos se corresponden con los códigos de salida de la CLI, consulta
[CI y códigos de salida](/docs/ci-and-exit-codes); para ayuda a partir del síntoma, consulta
[Solución de problemas](/docs/troubleshooting).

<AvailableFrom version="0.12.0" />

`ProviderError` y su tipo `ProviderErrorCode` se exportan desde `@verbatra/sdk`, así que comprueba
un fallo de `retranslateEntry` con `error instanceof ProviderError` y ramifica según `error.code`; la
[página de proveedores](/docs/providers) lista todos los códigos. En una versión anterior, que no
exporta la clase, comprueba `error.name === "ProviderError"` y lee `code`.
