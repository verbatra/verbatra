La [référence SDK](/docs/sdk) catalogue chaque point d'entrée. Cette page est le compagnon pratique : des recettes de bout en bout à copier dans un script et à lancer. Une chose à préparer d'abord : le SDK ne charge pas les fichiers `.env` (c'est la CLI qui fait ça), donc assure-toi que la variable d'environnement du fournisseur est définie avant que ton script tourne, par exemple :

```bash
node --env-file=.env translate.mjs
```

## Traduire en une passe dans un script

Charge la config, lance le flux, puis lis le résumé : l'essentiel dans `succeeded` et `failed`, la dépense de tokens dans `usage`, et les clés qui méritent un regard humain dans le `needsReview` de chaque locale. Les problèmes globaux lèvent une `SdkError` ; les résultats par locale sont des données sur le résumé.

```ts
import { loadConfig, translate } from "@verbatra/sdk";

const config = await loadConfig();
const summary = await translate({ config });

console.log(
  `${summary.succeeded.length} ok, ${summary.partial.length} partial, ${summary.failed.length} failed`,
);

if (summary.usage !== undefined) {
  console.log(`tokens: ${summary.usage.inputTokens} in, ${summary.usage.outputTokens} out`);
}

for (const locale of summary.locales) {
  if (locale.status === "failed") {
    console.error(`${locale.locale}: ${locale.error?.code} ${locale.error?.message}`);
    continue;
  }
  for (const entry of locale.needsReview) {
    console.warn(`review ${locale.locale}/${entry.key}: ${entry.reasons.join(", ")}`);
  }
}

if (summary.failed.length > 0 || summary.partial.length > 0) {
  process.exitCode = 1;
}
```

Une locale `partial` est une locale dont le fichier a été écrit alors que des clés manquent encore. Ce n'est pas un succès : la CLI se termine avec le code `1` dans ce cas, et ton propre script devrait la traiter de la même façon, d'où le test de `partial` à côté de `failed` ci-dessus.

Passe `dryRun: true` pour prévisualiser sans appeler de fournisseur ni rien écrire, et `prune: true` ou `generatePlurals: true` pour surcharger ces options de config le temps d'une exécution. Passe `locales: ["de"]` pour restreindre l'exécution à un sous-ensemble des cibles configurées, ce qui te permet d'avancer une langue à la fois avec un fournisseur soumis à une limite de débit ; une locale non configurée lève `UNKNOWN_LOCALE` avant que quoi que ce soit ne soit lu ou dépensé. Mets `concurrency` au-dessus de 1 pour traduire les locales en parallèle (non autorisé avec un budget `maxTokens` sur une exécution réelle) et `cache: false` pour contourner le [cache de mémoire de traduction](/docs/the-cache).

## Estimer une exécution avant de dépenser

<AvailableFrom version="0.11.0" />

`estimate: true` implique `dryRun` : l'exécution ne construit aucun fournisseur, ne lit aucune clé
d'API et n'écrit rien. Le chiffre arrive sur `RunSummary.estimate`. Base ton branchement sur `unit`
pour la dimension facturée et sur `pricing` pour savoir si un chiffre en devise était disponible :
verbatra ne livre aucun tarif qui lui soit propre, donc un coût n'apparaît que si la configuration
porte un bloc `rates` pour ce fournisseur et ce modèle.

```ts
import { loadConfig, translate } from "@verbatra/sdk";

const summary = await translate({ config: await loadConfig(), estimate: true });
const estimate = summary.estimate;

if (estimate !== undefined) {
  console.log(`${estimate.keys} keys in ${estimate.requests} requests to ${estimate.rateKey}`);

  if (estimate.unit === "tokens") {
    console.log(`about ${estimate.inputTokens} in, ${estimate.outputTokens} out`);
  } else {
    console.log(`about ${estimate.sourceCharacters} source characters`);
  }

  if (estimate.pricing === "priced") {
    console.log(`about ${estimate.cost} ${estimate.currency}, rates read ${estimate.asOf}`);
    for (const locale of estimate.locales) {
      console.log(`  ${locale.locale}: ${locale.cost}`);
    }
  } else {
    console.log(`no currency figure: ${estimate.pricing}`);
  }

  console.log(`leaves out: ${estimate.caveats.join(", ")}`);
}
```

Cela borne le plan, pas la facture : une exécution réelle dépense généralement moins, parce qu'elle
consulte le [cache de mémoire de traduction](/docs/the-cache) et regroupe les chaînes source
identiques, et elle peut dépenser plus pour chacune des raisons que nomme `caveats`.
`resolveDryRun` est le seul endroit où la règle "`estimate` implique `dryRun`" est décidée :
appelle-le plutôt que de la reformuler. Pour la méthode derrière les chiffres, voir
[Estimer le coût](/docs/estimating-cost).

## Vérifier en CI sans écrire

`check` lit et compare sans appeler de fournisseur ni toucher aucun fichier, et son champ `inSync` est vrai exactement quand rien n'est manquant ni obsolète. Cela en fait le garde-fou de CI naturel.

```ts
import { check, loadConfig } from "@verbatra/sdk";

const summary = await check({ config: await loadConfig() });

if (!summary.inSync) {
  for (const locale of summary.locales) {
    if (!locale.inSync) {
      console.error(`${locale.locale}: ${locale.missing} missing, ${locale.stale} stale`);
    }
  }
  process.exitCode = 1;
}
```

Besoin des noms de clés plutôt que des comptes ? Remplace par `diff`, qui renvoie les listes de clés `missing`, `changed` et `orphaned` par locale, avec le même verdict `hasPendingChanges`. Tu lances plutôt la CLI en CI ? Voir [CI et codes de sortie](/docs/ci-and-exit-codes).

## Surveiller dans un processus de longue durée

`watch` déclenche une exécution immédiatement au démarrage, puis une par changement temporisé de la source, en rapportant chacune via `onRun`. Pour un arrêt propre, attends `controller.stop()` : il ferme la surveillance et attend la fin de l'exécution en cours avant que ton processus se termine.

```ts
import { loadConfig, watch } from "@verbatra/sdk";

const config = await loadConfig();
const controller = await watch({
  config,
  onRun: (result) => {
    if (result.status === "succeeded") {
      console.log(`ran: ${result.summary.succeeded.length} ok, ${result.summary.failed.length} failed`);
    } else {
      console.error(`run failed: ${result.error.code} ${result.error.message}`);
    }
  },
});

process.on("SIGINT", () => {
  void controller.stop().then(() => {
    process.exit(0);
  });
});
```

Un échec d'exécution après le démarrage ne lève jamais ; il arrive comme `{ status: "failed" }` et la surveillance continue.

## Extraire les clés de ton code source

<AvailableFrom version="0.11.0" />

`extract` est le seul point d'entrée qui lit du code applicatif plutôt qu'un fichier de locale. Il
n'écrit que le catalogue source, et seulement les clés vraiment nouvelles : une clé déjà présente
garde sa valeur, et une clé qu'aucun site d'appel ne mentionne est laissée telle quelle. Tout ce
que l'analyse ne peut pas résoudre revient sous forme de données, donc un dry run fait un bon
garde-fou avant l'exécution qui écrit.

```ts
import { extract, loadConfig } from "@verbatra/sdk";

const config = await loadConfig();
const preview = await extract({ config, dryRun: true });

console.log(`${preview.scannedFiles} files scanned, ${preview.existingKeys} keys already present`);
for (const added of preview.added) {
  console.log(`+ ${added.key} = ${JSON.stringify(added.value)} (${added.file}:${added.line})`);
}
for (const conflict of preview.conflicts) {
  console.warn(`${conflict.key} has two defaults: ${conflict.values.join(" | ")}`);
}
for (const site of preview.dynamic) {
  console.warn(`non-static key argument at ${site.file}:${site.line}`);
}
for (const diagnostic of preview.diagnostics) {
  console.warn(`${diagnostic.file}: ${diagnostic.reason}`);
}

if (preview.added.length > 0 && preview.conflicts.length === 0) {
  const run = await extract({ config });
  console.log(`wrote ${run.added.length} keys to ${run.sourcePath}: ${run.written}`);
}
```

`config.extract` doit nommer le framework et les racines de sources, sinon l'appel lève
`EXTRACT_NOT_CONFIGURED`. La découverte passe par le membre optionnel `readDirectory` de `SdkFs` :
un `deps.fs` personnalisé qui ne l'implémente pas est refusé avec `EXTRACT_FS_UNSUPPORTED`, et un
catalogue source qui ne peut pas être écrit lève `SOURCE_UNWRITABLE`.

## Générer un catalogue typé

<AvailableFrom version="0.11.0" />

`generateTypes` déclare le catalogue source en TypeScript : une union de toutes les clés, plus les
arguments que chaque message interpole. Il lit un fichier et écrit un fichier, et deux exécutions
sur un catalogue inchangé écrivent des octets identiques, ce qui fait du mode `check` un garde-fou
de CI exploitable.

```ts
import { generateTypes, loadConfigWithMeta } from "@verbatra/sdk";

const loaded = await loadConfigWithMeta();
const out = "src/generated/messages.d.ts";
const configPath = loaded.source.kind === "override" ? undefined : loaded.source.filepath;

const result = await generateTypes({
  config: loaded.config,
  out,
  ...(configPath !== undefined ? { configPath } : {}),
});

console.log(`${result.keys} keys in ${result.path}, ${result.withArguments} take arguments`);
for (const message of result.unresolved) {
  console.warn(`arguments not claimed for ${message.key}: ${message.reason}`);
}

// In CI, compare instead of writing.
const gate = await generateTypes({ config: loaded.config, out, check: true });
if (gate.stale) {
  console.error(`${gate.path} is out of date, re-generate it`);
  process.exitCode = 1;
}
```

Passe `configPath` pour que le fichier de configuration chargé par l'exécution soit refusé comme
chemin de sortie. Une exécution avec `check` n'écrit rien, ne refuse rien pour son contenu et ne
signale que `stale`. Tout ce qu'une exécution qui génère refuse, avec `TYPES_OUTPUT_CONFLICT`, est
listé sur la page [`verbatra types`](/docs/cli/types) ; une déclaration qui ne peut pas être écrite
lève `TYPES_UNWRITABLE`.

## Construire une pseudo-locale

<AvailableFrom version="0.11.0" />

`pseudolocalize` construit une locale factice à partir des seules chaînes source, pour que les
troncatures de mise en page et les chaînes jamais extraites apparaissent avant même qu'une clé
d'API existe. Il ne construit aucun fournisseur et ne fait aucune requête réseau, et sa sortie
atterrit hors de `files.pattern` : `translate` ne dépense donc jamais dessus, et `check` et `diff`
ne la signalent jamais comme ayant dérivé.

```ts
import { loadConfig, pseudolocalize } from "@verbatra/sdk";

const result = await pseudolocalize({ config: await loadConfig() });

console.log(`${result.locale} written to ${result.path}: ${result.written}`);
console.log(`${result.transformed} of ${result.entries} entries transformed`);
for (const key of result.copied) {
  console.warn(`copied from source verbatim, a pseudolocalized value would not pass the gate: ${key}`);
}
```

`locale` vaut `en-XA` par défaut et `out` vaut `.verbatra-local/pseudo`. Une pseudo-locale qui
nomme une locale configurée, ou un `out` qui atterrirait sur un fichier de locale configuré, est
refusé avec `PSEUDO_OUTPUT_CONFLICT` avant toute lecture et toute écriture. La transformation est
déterministe : une seconde exécution sur une source inchangée ne réécrit rien et signale `written`
à false.

## Modifier et retraduire une seule clé

Ce sont les points d'accroche que Verbatra Studio pilote ; utilise-les pour construire ton propre flux de révision. Lis les valeurs actuelles avec `keyValue`, enregistre une correction humaine avec `editEntry`, ou relance le fournisseur pour une clé avec `retranslateEntry`. Les deux fonctions d'écriture passent la valeur candidate par les mêmes contrôles d'intégrité qu'une exécution complète et renvoient un résultat à deux branches au lieu de lever sur une valeur rejetée.

```ts
import { editEntry, keyValue, loadConfig, retranslateEntry } from "@verbatra/sdk";

const config = await loadConfig();

// Read the live values feeding your edit UI.
const current = await keyValue({ config, locale: "de", key: "checkout.title" });
console.log(`source: ${current.source}, target: ${current.target ?? "(not yet translated)"}`);

// Save a human-typed correction. No provider call.
const edit = await editEntry({
  config,
  locale: "de",
  key: "checkout.title",
  value: "Zur Kasse",
});
if (!edit.accepted) {
  console.error(`rejected (${edit.reason} check failed), nothing written`);
}

// Or ask the provider for a fresh translation of just this key.
const retry = await retranslateEntry({ config, locale: "de", key: "checkout.title" });
if (retry.accepted) {
  console.log(`wrote: ${retry.value}`);
  if (retry.reviewReasons.length > 0) {
    console.warn(`flagged for review: ${retry.reviewReasons.join(", ")}`);
  }
}
```

Une locale ou une clé inconnue lève `UNKNOWN_LOCALE` ou `UNKNOWN_KEY`, et `retranslateEntry` lève la `ProviderError` du fournisseur lui-même (par exemple `RATE_LIMITED`) quand l'appel échoue. Voir [Réviser les traductions dans Studio](/docs/review-in-studio) pour les mêmes points d'accroche derrière une UI.

## Lire toutes les valeurs en bloc

<AvailableFrom version="0.10.0" />

`localeValues` est le pendant en masse de `keyValue` : une passe sur les fichiers déjà présents sur
le disque, qui renvoie par locale le texte source et le texte cible actuels de chaque clé.
Utilise-le quand l'appelant doit chercher ou parcourir du contenu traduit plutôt que des noms de
clés.

```ts
import { loadConfig, localeValues } from "@verbatra/sdk";

const report = await localeValues({ config: await loadConfig(), locales: ["de", "fr"] });

for (const { locale, values } of report) {
  for (const [key, pair] of Object.entries(values)) {
    if (pair.source === undefined) {
      console.warn(`${locale}/${key}: orphaned, no source key any more`);
    } else if (pair.target === undefined) {
      console.warn(`${locale}/${key}: not translated yet`);
    } else if (pair.target.includes("TODO")) {
      console.log(`${locale}/${key}: ${pair.target}`);
    }
  }
}
```

En lecture seule : il n'appelle aucun fournisseur, n'écrit rien et ne touche ni au fichier de
verrouillage ni au cache. Omets `locales` pour couvrir toutes les locales cibles configurées.

## L'aller-retour du classeur

Exporte les chaînes à traduire dans un classeur Excel, confie-le à un traducteur, puis réimporte le fichier rempli. `importWorkbook` exécute les mêmes vérifications de dérive et d'intégrité que `translate` et renvoie la même forme `RunSummary`, donc une remise manuelle s'insère exactement dans les rapports que tu utilises pour une exécution automatisée.

```ts
import { exportWorkbook, importWorkbook, loadConfig } from "@verbatra/sdk";

const config = await loadConfig();

// Write a workbook of the missing and changed strings.
const exported = await exportWorkbook({ config });
for (const sheet of exported.locales) {
  console.log(`${sheet.locale}: ${sheet.rows} rows`);
}
console.log(`wrote ${exported.path}`);

// ...later, after the translator returns the file, import it back.
const summary = await importWorkbook({ config, workbook: exported.path });
console.log(`${summary.succeeded.length} locales ok, ${summary.failed.length} failed`);
```

Passe `dryRun: true` à `importWorkbook` pour valider un fichier renvoyé sans rien écrire. Voir [Traduction humaine](/docs/manual-translation) pour ce que les traducteurs peuvent modifier et comment les lignes sont validées.

## L'aller-retour TMX

<AvailableFrom version="0.11.0" />

`importTmx` et `exportTmx` font entrer et sortir la [mémoire de traduction](/docs/the-cache) au
format TMX, le format d'échange que produisent et lisent les plateformes de traduction courantes.
Ce n'est pas la paire classeur dans un autre format : le classeur remet à un traducteur humain
le delta en attente d'une locale, tandis que cette paire déplace la mémoire entière comme un seul
fichier multilingue entre outils.

```ts
import { exportTmx, importTmx, loadConfig, tmxErrorLocation } from "@verbatra/sdk";

const config = await loadConfig();

// Validate another tool's file before it touches the memory.
try {
  const preview = await importTmx({ config, file: "legacy.tmx", dryRun: true });
  console.log(`${preview.units} units, source language ${preview.sourceLanguage ?? "undeclared"}`);
  for (const locale of preview.locales) {
    console.log(
      `${locale.locale}: +${locale.added}, kept ${locale.kept}, conflicting ${locale.conflicting}`,
    );
  }

  // Then land it. Pass overwrite: true to let the file win where the two disagree.
  const landed = await importTmx({ config, file: "legacy.tmx" });
  if (!landed.memoryWritable) {
    console.error("the memory file was written by a newer verbatra and was left untouched");
  }
} catch (error) {
  const at = tmxErrorLocation(error);
  if (at === undefined) {
    throw error;
  }
  console.error(`legacy.tmx is malformed at line ${at.line}, column ${at.column}`);
}

// ...and hand this project's memory to another tool.
const exported = await exportTmx({ config, out: "out/memory.tmx" });
console.log(`${exported.units} units to ${exported.path}`);
```

Ni l'un ni l'autre ne construit de fournisseur, ne lit de clé d'API ni ne fait d'appel réseau.
`importTmx` signale les données abîmées au lieu de lever dessus : un fichier refusé lève
`SOURCE_INVALID`, et `tmxErrorLocation` lit cet emplacement dans l'erreur sans avoir à la caster ni à caster
son `cause`. Seules les entrées sous l'empreinte de configuration actuelle sont exportées, soit
exactement l'ensemble qu'une exécution réutiliserait.

## Une config sans fichier

`loadConfig` accepte un `configOverride` en mémoire, validé exactement comme un fichier chargé, donc tu peux piloter verbatra entièrement depuis le code, sans fichier de config sur disque.

```ts
import { loadConfig, translate } from "@verbatra/sdk";

const config = await loadConfig({
  configOverride: {
    sourceLocale: "en",
    targetLocales: ["de", "fr"],
    format: "i18next-json",
    files: { pattern: "locales/{locale}.json" },
    provider: { id: "gemini", options: { model: "gemini-2.5-flash", maxOutputTokens: 4096 } },
  },
});

await translate({ config });
```

Pour chaque forme d'entrée, l'anatomie complète du `RunSummary` et la table des codes `SdkError`, voir la [référence SDK](/docs/sdk).
