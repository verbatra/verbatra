## Inspecciona el estado sin escribir

Ninguna de estas llama a un proveedor, escribe un archivo ni muta el bloqueo.

### doctor

<AvailableFrom version="0.9.0" />

Valida la configuración del proyecto y no gasta nada: no construye ningún proveedor, nunca lee el
valor de una clave de API y no hace ninguna petición de red salvo que `live` pida una. Cada
comprobación devuelve su propio veredicto `pass`, `fail` o `skipped`, y todas se ejecutan aunque una
anterior haya fallado, así que una sola llamada informa de cada problema independiente.
[`verbatra doctor`](/docs/cli/doctor#qué-comprueba) enumera las comprobaciones. La clave de API se
comprueba solo por nombre, y la comprobación del archivo de origen lo parsea, así que un directorio
en su lugar, un archivo vacío y contenido malformado se informan todos.

```ts title="Firma"
function doctor(
  input?: DoctorInput,
  deps?: DoctorDeps,
): Promise<DoctorResult>;
```

<SdkTypeTable name="DoctorInput" />

**Devuelve:** `DoctorResult`

**Lanza:** [`CONFIG_NOT_FOUND`](/docs/error-codes#config_not_found)

<AvailableFrom version="0.12.0" />

La comprobación `network-policy` falla cuando la [política de red](/docs/network-policy) efectiva
rechaza el host al que se conecta el proveedor configurado o su proxy, o cuando una variable de
entorno de red tiene un valor no válido. Pasa para el proveedor `none`. La comprobación
`plural-rules` es informativa y siempre pasa; su detalle nombra las versiones de ICU y CLDR detrás
de las categorías de plural de cada idioma de destino.

<AvailableFrom version="0.12.0" />

Las comprobaciones `plural-completeness`, `locale-codes` y `locale-state` también son informativas y
siempre pasan. Sus detalles nombran los plurales a los que les falta una categoría CLDR que usa su
idioma de destino (lo que `check` informa como `incompletePlurals`), los códigos de locale
configurados que no están en forma BCP 47 canónica y los locales para los que el lock, la memoria o
el archivo de procedencia guardan estado pero que la configuración ya no incluye. No se renombra
nada.

<AvailableFrom version="0.12.0" />

La comprobación `locales` juzga cada locale configurado frente al soporte de idiomas del proveedor,
como hace `translate` antes de gastar nada: falla con un locale no soportado y es `skipped` para el
proveedor `none`. Los veredictos por locale viajan en `DoctorResult.locales` como un
`LocaleCapabilityReport`. Con `live: true`, `doctor` obtiene primero la lista de idiomas actual del
proveedor, que no consume cuota de traducción; `LocaleCapabilityReport.live` dice cómo fue. Consulta
[Soporte de idiomas](/docs/language-support#comprobar-el-soporte-antes-de-una-ejecución).

Con `literals` activado, `doctor` solo ejecuta la
comprobación `config` y, en lugar de las demás, una comprobación `untranslated-literals` que
recorre las raíces de código del bloque `extract` de la configuración, igual que
[`verbatra doctor --literals`](/docs/cli/doctor#literales-sin-traducir). No necesita una
configuración ya cargada: `doctor` la carga por sí mismo, así que un proyecto sin ninguna
configuración sigue obteniendo un informe en lugar de un error lanzado.
Devuelve un `DoctorResult` cuyo `ok` es true exactamente cuando ninguna comprobación falló. Lanza
`CONFIG_NOT_FOUND` solo para un `configPath` explícito que no existe.

<AvailableFrom version="0.12.0" />

Cada comprobación fallida lleva `fix`, un siguiente paso breve en imperativo como "Set
ANTHROPIC_API_KEY in the environment or in a .env file in the project directory.". Una
comprobación que pasó o se omitió no tiene `fix`. Igual que `detail`, nombra variables y rutas,
nunca el valor de una clave.

### extract

<AvailableFrom version="0.11.0" />

Analiza el código de tu aplicación en busca de llamadas de traducción y fusiona lo que encuentra en
el catálogo del locale de origen. Es el único punto de entrada que lee código de aplicación en lugar
de un archivo de locale, y eso es lo que hace que verbatra sirva en un proyecto que todavía no tiene
catálogo. No gasta nada: no construye ningún proveedor, no lee ninguna variable de entorno con una
clave de API y no hace ninguna petición de red.

```ts title="Firma"
function extract(
  input: ExtractInput,
  deps?: ExtractDeps,
): Promise<ExtractResult>;
```

<SdkTypeTable name="ExtractInput" />

**Devuelve:** `ExtractResult`

**Lanza:** [`EXTRACT_NOT_CONFIGURED`](/docs/error-codes#extract_not_configured), [`EXTRACT_FS_UNSUPPORTED`](/docs/error-codes#extract_fs_unsupported), [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_INVALID`](/docs/error-codes#source_invalid), [`SOURCE_UNWRITABLE`](/docs/error-codes#source_unwritable)

Solo se escribe el archivo del locale de origen, y solo se añaden claves realmente nuevas: una clave
que ya está en el catálogo conserva su valor tal cual, y una clave del catálogo que ninguna llamada
menciona se deja intacta. Una ejecución que no encuentra nada nuevo no escribe nada en absoluto.
Todo lo que el análisis no puede resolver vuelve como datos en lugar de lanzarse: un argumento de
clave no estático en `dynamic`, una clave encontrada con dos valores por defecto distintos en
`conflicts` (no se escribe ninguno) y un archivo ilegible en `diagnostics`. El resultado lleva
únicamente claves, valores y ubicaciones de archivo y línea, nunca el contenido de un archivo de
código.

`config.extract` nombra el framework y las raíces de código. El descubrimiento pasa por el miembro opcional `readDirectory`
de `SdkFs`; un `deps.fs` sin él se informa como `EXTRACT_FS_UNSUPPORTED`.

### check

Informa del desfase por locale como contadores: `missing` (en el origen, ausente del destino), `stale`
(el origen cambió desde la última traducción) y `upToDate`. Úsalo como puerta de CI.

```ts title="Firma"
function check(
  input: CheckInput,
  deps?: CheckDeps,
): Promise<CheckSummary>;
```

<SdkTypeTable name="CheckInput" />

**Devuelve:** `CheckSummary`

**Lanza:** [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_UNREADABLE`](/docs/error-codes#source_unreadable), [`SOURCE_INVALID`](/docs/error-codes#source_invalid), [`LOCK_FILE_INVALID`](/docs/error-codes#lock_file_invalid), [`UNKNOWN_LOCALE`](/docs/error-codes#unknown_locale)

Devuelve un `CheckSummary` cuyo `inSync` es true
exactamente cuando cada locale comprobado no tiene nada faltante ni obsoleto.

<AvailableFrom version="0.11.0" />

Con `consistency: true`, cada `LocaleCheckSummary` lleva además `inconsistencies`: un
`InconsistencyGroup` por cada cadena de origen que el locale traduce de más de una forma bajo claves
distintas, con el `source`, cada traducción distinta como `{ value, keys }` y el `context`, la
`description`, el `meaning`, `isPlural` y `pluralForm` que comparten las claves agrupadas. Es solo un informe: nunca cambia `inSync`, un contador ni un archivo, y
no llama a ningún proveedor.

<AvailableFrom version="0.12.0" />

Cada `LocaleCheckSummary` lleva además `provenance`: contadores `byOrigin` y `byReviewState` sobre
las claves para las que el locale tiene un valor, leídos de `verbatra.provenance.json`. Qué
significa cada origen está en [El archivo de bloqueo](/docs/the-lock-file#procedencia-quién-escribió-cada-valor).
Este y cualquier otro campo de procedencia de un informe se omite, en lugar de dar un error, cuando
el archivo está corrupto o lo escribió un verbatra más nuevo.

<AvailableFrom version="0.12.0" />

Cada `LocaleCheckSummary` lleva además `protected`: cuántas de sus claves obsoletas dejaría una ejecución de `translate` para una persona según el `humanEdits` y los `pinnedKeys` de la configuración: la parte protegida de `stale`. Una clave fijada que falta aún no tiene un valor que proteger y cuenta solo como ausente. Siguen contando como obsoletas, así que `inSync` sigue en false hasta que una persona las resuelva. Si `verbatra.provenance.json` está dañado o es de un verbatra más nuevo, no se puede leer ningún origen y solo se cuentan las claves fijadas.

<AvailableFrom version="0.12.0" />

Con `qa: true`, `check` también ejecuta el control de calidad sobre cada valor confirmado, sin
clave y sin escribir nada: cada `LocaleCheckSummary` lleva un informe `qa` de
`{ checked, errors, warnings, findings }`, y el resumen lleva los totales `qa` de
`{ errors, warnings, invalidSourceKeys }`. Un hallazgo es `{ key, severity: "error", reason, details? }`
para un valor que la puerta de integridad rechazaría (`reason` de `INTEGRITY_GATE_REASONS`), o
`{ key, severity: "warning", reason }` para un valor que pasa pero lleva un motivo de revisión de
`REVIEW_REASON_CODES`. `qaSeverity: "error"` omite los motivos de revisión. Las severidades se
publican como la tupla `QA_SEVERITIES` (`"error"`, `"warning"`). El informe nunca cambia `inSync`;
una puerta de CI lee `qa.errors`, y `qa.warnings` para una puerta estricta. Consulta
[el control de calidad](/docs/cli/check#control-de-calidad) para ver qué valores se comprueban.

<AvailableFrom version="0.12.0" />

Cada `LocaleCheckSummary` también lleva `incompletePlurals`: un `IncompletePlural` por cada plural
cuyas formas confirmadas no tienen categorías de plural CLDR que usa el idioma de destino, como
`{ code: "PLURAL_CATEGORIES_INCOMPLETE", key, argument?, ruleType, missing }`, ordenado por clave y
vacío cuando todos los plurales están completos. Cubre `i18next-json`, `android-xml`, `apple-strings`,
`apple-xcstrings` y los mensajes ICU con `plural` y `selectordinal` de `next-intl-json` y `arb`.
`other` es siempre obligatoria, una rama de valor exacto como `=1` nunca sustituye a una categoría, y
una categoría que el idioma no usa no se informa. Es una advertencia: nunca cambia `inSync` ni un
recuento. Consulta [categorías de plural](/docs/cli/check#categorías-de-plural).

Con `requireReviewed: true`, `check` también ejecuta la puerta de revisión, sin clave y sin escribir
nada: cada `LocaleCheckSummary` lleva `review: { unreviewed }`, las claves cuyo valor tiene un
origen de máquina y no está aprobado, y el resumen lleva `review: { reviewed, unreviewed, code? }`.
`code` es `REVIEW_REQUIRED` cuando un valor no está aprobado, o `REVIEW_STATE_UNREADABLE` cuando el
archivo de procedencia está dañado o viene de una versión más nueva de verbatra, lo que hace fallar
la puerta en vez de dejarla pasar. El informe nunca cambia `inSync`; una puerta de CI lee
`review.reviewed`. Consulta [`verbatra check`](/docs/cli/check).

### checkFile

<AvailableFrom version="0.12.0" />

Comprueba un solo archivo de locale, la vía rápida para validar un archivo justo después de que una
persona o un agente lo edite. Lee ese archivo y, para un locale de destino, el archivo del locale de
origen, y nada más: ningún otro locale, ni el archivo de bloqueo, ni código fuente, ni proveedor, ni
clave de API, y no escribe nada.

```ts title="Firma"
function checkFile(
  input: CheckFileInput,
  deps?: CheckFileDeps,
): Promise<CheckFileSummary>;
```

<SdkTypeTable name="CheckFileInput" />

**Devuelve:** `CheckFileSummary`

**Lanza:** [`NOT_A_LOCALE_FILE`](/docs/error-codes#not_a_locale_file), [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_UNREADABLE`](/docs/error-codes#source_unreadable), [`SOURCE_INVALID`](/docs/error-codes#source_invalid)

`file` es absoluto o relativo a `cwd`. El `CheckFileSummary` es `{ file, role, locales, qa }`: `role` es `"source"`, `"target"` o
`"catalogue"` (el único archivo de `apple-xcstrings`), cada entrada de `locales` es un
`LocaleFileCheck` de `{ locale, incompletePlurals, qa }` cuyo `qa` tiene la forma del informe `qa`
que devuelve `check` con `qa: true`, y `qa` contiene los totales. Un archivo que no se puede analizar
no se lanza: su locale lleva un `QaSyntaxFinding` de
`{ severity: "error", reason: "syntax", code, message, line?, column? }`, con el código del
adaptador de formato y, en JSON y YAML, la posición que informa `AdapterError.position`. Un archivo
de destino que se puede analizar se comprueba frente al origen como `check` con `qa: true`; el
archivo de origen solo en su sintaxis. Una ruta que no es el archivo de ningún locale configurado, o
un archivo que no existe, lanza `NOT_A_LOCALE_FILE`. Consulta
[Un solo archivo](/docs/cli/check#un-solo-archivo).

### diff

El hermano detallado de `check`: el mismo cálculo, pero devuelve las listas de claves por locale
(`missing`, `changed`, `orphaned`) en lugar de contadores. Las claves huérfanas son solo informativas y
nunca activan `hasPendingChanges`, porque una ejecución por defecto no elimina claves.

```ts title="Firma"
function diff(
  input: DiffInput,
  deps?: DiffDeps,
): Promise<DiffSummary>;
```

<SdkTypeTable name="DiffInput" />

**Devuelve:** `DiffSummary`

**Lanza:** [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_UNREADABLE`](/docs/error-codes#source_unreadable), [`SOURCE_INVALID`](/docs/error-codes#source_invalid), [`LOCK_FILE_INVALID`](/docs/error-codes#lock_file_invalid), [`UNKNOWN_LOCALE`](/docs/error-codes#unknown_locale)

Con `unused: true` también analiza las raíces del bloque `extract` de la configuración y añade un
informe `unused`, separado de cada lista `orphaned`: las claves del locale de origen que ninguna
referencia estática nombra, en el orden del catálogo. Es de solo lectura, no necesita clave y modela el runtime de i18next. Cada clave listada lleva su `key` decodificada y su
`catalogKey`. Las claves que coinciden con `extract.unused.ignore` van a `ignored`, y las que podría
alcanzar un literal de plantilla con cabecera estática, a `possiblyDynamic`. Su `status` es `complete`,
`unreliable` (con `unreliableBecause` nombrando cada motivo con sus ubicaciones) o `not-run` (con un
`reason` y sin lista de claves). Consulta todos los motivos en [Claves de origen sin
uso](/docs/cli/diff#claves-de-origen-sin-uso). El informe nunca activa `hasPendingChanges`.

<AvailableFrom version="0.12.0" />

Cada `LocaleDiff` lleva además `changedOrigins`, el origen interpretado del valor actual de cada
clave `changed` (por ejemplo `machine`, `human` o `external`), para que veas antes de ejecutar qué
trabajo reemplazaría una retraducción.

<AvailableFrom version="0.12.0" />

Cada `LocaleDiff` lleva además `protected`, las claves ausentes y cambiadas que una ejecución de `translate` dejaría en paz, ordenadas. Siguen contando como pendientes. Si el archivo de procedencia no se puede leer, solo se listan las claves fijadas.

### keyIntegrity

Informa, para las claves modificadas de cada locale, de si el valor de destino actual sigue
coincidiendo con los placeholders del origen, de si sigue llevando el marcado en línea del
origen y de si es ICU válido. Cada entrada lleva `key`, `hasPlaceholders`, `matches`, los tokens de
placeholder `missing` y `extra` en una discrepancia, `icuValid`, `markupMatches` y `markupDetails` con
las etiquetas causantes de una discordancia de marcado. Las entradas nunca llevan un valor de cadena
de origen o destino. Un valor escrito antes de que existiera la puerta del momento de escritura o editado fuera de verbatra se juzga con la misma regla.
Este es el informe de integridad por clave que muestra Studio.

```ts title="Firma"
function keyIntegrity(
  input: KeyIntegrityInput,
  deps?: KeyIntegrityDeps,
): Promise<readonly LocaleKeyIntegrity[]>;
```

<SdkTypeTable name="KeyIntegrityInput" />

**Devuelve:** `readonly LocaleKeyIntegrity[]`

**Lanza:** [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_UNREADABLE`](/docs/error-codes#source_unreadable), [`SOURCE_INVALID`](/docs/error-codes#source_invalid), [`LOCK_FILE_INVALID`](/docs/error-codes#lock_file_invalid), [`UNKNOWN_LOCALE`](/docs/error-codes#unknown_locale)

<AvailableFrom version="0.12.0" />

Cada entrada lleva además `icuArmsMatch` e `icuArmDetails`: si las ramas ICU de `plural`,
`selectordinal` y `select` del valor encajan con el idioma de destino, juzgadas exactamente como las
juzga la puerta del momento de escritura, y un problema breve por cada rama que falta o sobra, como
`{count} plural: missing arm "few" required by the target language`. `icuArmsMatch` siempre es true
para un formato que no comprueba ramas (todos los formatos incluidos salvo next-intl y ARB).

`keys` acota la comprobación; solo se comprueban las
claves que están "modificadas" para un locale. Devuelve un `LocaleKeyIntegrity` por locale comprobado.

### localeIntegrity

<AvailableFrom version="0.12.0" />

Encuentra cada traducción de los locales de destino que está rota ahora mismo: una que perdió o
ganó un placeholder, perdió o añadió marcado en línea, ya no se analiza como ICU o lleva ramas ICU
de `plural`, `selectordinal` o `select` que no encajan con el idioma de destino. A diferencia de
`keyIntegrity`, juzga cada clave presente tanto en el origen como en un locale de destino, sea cual
sea su estado de sincronización, así que también encuentra un defecto en una traducción que nadie ha
tocado desde que se escribió. Cada clave se juzga con las mismas reglas que `keyIntegrity` y la
puerta del momento de escritura, y solo vuelven las claves que fallan: una lista `entries` vacía
significa que todas las traducciones de ese locale pasan.

```ts title="Firma"
function localeIntegrity(
  input: LocaleIntegrityInput,
  deps?: LocaleIntegrityDeps,
): Promise<readonly LocaleKeyIntegrity[]>;
```

<SdkTypeTable name="LocaleIntegrityInput" />

**Devuelve:** `readonly LocaleKeyIntegrity[]`

**Lanza:** [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_UNREADABLE`](/docs/error-codes#source_unreadable), [`SOURCE_INVALID`](/docs/error-codes#source_invalid), [`UNKNOWN_LOCALE`](/docs/error-codes#unknown_locale)

El coste es una lectura y un análisis del archivo de origen y de cada archivo de destino pedido,
más una comprobación por clave traducida. No se guarda nada en caché; cada llamada lee de nuevo del
disco.

Devuelve un `LocaleKeyIntegrity` por locale comprobado, con
solo sus entradas que fallan.

### lockState

Informa de la existencia del archivo de bloqueo, su versión y el desfase por locale (número de claves de
la línea base más contadores de faltantes, obsoletas y al día). `exists` viene de una sonda explícita,
así que "todavía no hay archivo de bloqueo" y "un archivo de bloqueo vacío pero presente" siguen siendo
distinguibles. Cuando el archivo está ausente el resultado es `{ exists: false }` y no se lee nada más.

```ts title="Firma"
function lockState(
  input: LockStateInput,
  deps?: LockStateDeps,
): Promise<LockStateResult>;
```

<SdkTypeTable name="LockStateInput" />

**Devuelve:** `LockStateResult`

**Lanza:** [`UNKNOWN_LOCALE`](/docs/error-codes#unknown_locale), [`LOCK_FILE_INVALID`](/docs/error-codes#lock_file_invalid), [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_UNREADABLE`](/docs/error-codes#source_unreadable), [`SOURCE_INVALID`](/docs/error-codes#source_invalid)

Cada locale lleva además los mismos contadores `provenance` que informa `check`.

### loadProvenance

<AvailableFrom version="0.12.0" />

valor sin registro (`unrecorded`) de uno editado fuera de verbatra desde que se registró

### runStatus

Lee la instantánea de señales de revisión y uso de tokens que la ejecución más reciente de `translate` o
`watch` que no fue un dry run persistió en `.verbatra-local/run-status.json`. Nunca lanza: un archivo ausente,
corrupto o no reconocido degrada a `{ available: false }`. Este archivo es telemetría de mejor esfuerzo,
no una línea base de corrección.

```ts title="Firma"
function runStatus(
  input?: RunStatusInput,
  deps?: RunStatusDeps,
): Promise<RunStatusResult>;
```

<SdkTypeTable name="RunStatusInput" />

**Devuelve:** `RunStatusResult`

No necesita configuración. Devuelve `{ available: false }` o
`{ available: true, version, generatedAt, usage?, budget?, locales }`.

Una instantánea escrita por una versión anterior a que el presupuesto de tokens se hiciera cumplir
se sigue leyendo, pero su `budget` se omite cuando indica `supported: false`: entonces eso
significaba que no se contaba nada, así que su `tokensUsed: 0` no es un recuento. Las instantáneas
que se escriben ahora conservan la misma `version` y solo añaden un campo marcador que un Studio o
un servidor de agentes más antiguo ignora, así que un lector más antiguo sigue mostrando la cola de
revisión y el uso. Hasta que lo actualices, puede mostrar un presupuesto estimado como no
registrado.

### reviewQueue

<AvailableFrom version="0.12.0" />

Lee la cola de revisión de los archivos del repositorio: cada clave cuyo valor actual tiene un
origen de máquina (`machine`, `memory`, `fuzzy` o `agent`, publicado como la tupla
`MACHINE_CLASS_ORIGINS`) y no está aprobado, por locale de destino y en el orden del origen. Lee los
archivos de locale, `verbatra.lock.json` y `verbatra.provenance.json`, así que cada persona de tu
equipo con el mismo commit ve la misma cola. Una clave sale de ella en cuanto su valor se aprueba o
se rechaza, o una persona escribe o importa un valor nuevo; un valor que reescribió un agente se
queda, y también una aprobación anterior a un cambio del origen de la clave. La instantánea de la
última ejecución de `runStatus` solo añade detalle: las `reasons` de cada entrada (vacías si la
ejecución no la marcó), los `fuzzyHits` del locale y `lastRunAt`.

```ts title="Firma"
function reviewQueue(
```

### provenanceReport

<AvailableFrom version="0.12.0" />

Construye el informe por locale que imprime `verbatra report provenance`: cada clave con un valor
tanto en el origen como en un locale de destino, en el orden del origen, con su origen, estado de
revisión, proveedor, modelo y revisor, contada en uno de siete grupos (`machine-unreviewed`,
`machine-reviewed`, `human`, `import`, `external`, `unrecorded`, `unknown`, publicados en ese orden
como la tupla `PROVENANCE_BUCKETS`). Lee los archivos de locale, `verbatra.lock.json` y
`verbatra.provenance.json`, no llama a ningún proveedor y no escribe nada.

## Lecturas de contenido en bloque

### localeValues

Lee el texto de origen y de destino actual de cada clave, en cada locale de destino solicitado, en
una sola pasada sobre los archivos que ya están en disco. Es la contraparte en bloque de `keyValue`:
úsala cuando necesites contenido de traducción en bloque, por ejemplo para buscar o recorrer
valores en lugar de solo nombres de clave, ya que `keyValue` solo responde para una clave a la vez.
Solo lectura.

```ts title="Firma"
function localeValues(
  input: LocaleValuesInput,
  deps?: LocaleValuesDeps,
): Promise<readonly LocaleValues[]>;
```

<SdkTypeTable name="LocaleValuesInput" />

**Devuelve:** `readonly LocaleValues[]`

**Lanza:** [`UNKNOWN_FORMAT`](/docs/error-codes#unknown_format), [`LOCALE_LAYOUT_INVALID`](/docs/error-codes#locale_layout_invalid), [`LOCALE_PATH_COLLISION`](/docs/error-codes#locale_path_collision), [`SOURCE_UNREADABLE`](/docs/error-codes#source_unreadable), [`SOURCE_INVALID`](/docs/error-codes#source_invalid), [`UNKNOWN_LOCALE`](/docs/error-codes#unknown_locale)

Un `locales` omitido cubre cada locale de destino
configurado. Devuelve un array de `{ locale, values }`, una entrada por locale, donde `values`
asigna cada clave a `{ source?, target? }`. Un `target` ausente significa que la clave todavía no
se ha traducido en ese locale; un `source` ausente significa que la clave está huérfana, presente
en el locale de destino pero ya no en el origen. `values` no tiene prototipo: cada clave, incluida
una llamada `__proto__` o `constructor`, es una propiedad propia, y una clave que no está en el
catálogo se lee como `undefined`.

Cada par con un `target` lleva además `provenance`, la misma `KeyProvenance` que informa `keyValue`.
