## Die Anatomie der RunSummary

`translate`, `importWorkbook` und jeder erfolgreiche `watch`-Lauf lösen zu einer `RunSummary` auf:

```ts
interface RunSummary {
  dryRun: boolean;          // true when nothing was written and no provider was called
  locales: LocaleSummary[]; // one entry per target locale, in config order
  succeeded: string[];      // locales whose run succeeded
  partial: string[];        // locales written with keys still missing; the CLI exits 1 on these
  failed: string[];         // locales whose run failed
  usage?: UsageSummary;     // summed input/output tokens; absent when no call reported usage
  budget?: RunBudget;       // present only when maxTokens is configured
  estimate?: RunEstimate;   // present only when the run was asked for a pre-run estimate
}

interface LocaleSummary {
  locale: string;
  status: "succeeded" | "partial" | "failed";
  translated: string[];          // keys translated this run (in dry-run, keys that would be)
  cacheHits: string[];           // keys served from the translation-memory cache this run
  fuzzyHits: FuzzyCacheHit[];    // reuses for a source string that changed, with their scores
  unchanged: string[];           // keys already up to date
  orphaned: string[];            // target keys with no matching source key (always reported)
  pruned: string[];              // orphaned keys removed this run; empty unless pruning is on
  invalidIcuSource: string[];    // source keys skipped for invalid ICU
  integrityMismatches: string[]; // translations the integrity gate withheld
  integrityRefusals?: { key: string; reason: string; details?: string[] }[]; // why each was withheld; translate, watch, and importWorkbook
  providerFailures: string[];    // keys withheld because nothing was translated for them
  budgetWithheld: string[];      // keys never sent because a "stop" budget already tripped
  generated: string[];           // CLDR plural forms synthesized this run
  unfilled: string[];            // blank import rows, or keys a human-only translate left for a human
  protected: { key: string; reason: string; suggestion?: string; suggestionStatus?: string }[]; // keys left for a person
  malformedRows: { row: number; line?: number; column: string }[]; // import only: rows the reader could not parse
  duplicateKeys: { key: string; row: number; line?: number }[];    // import only: later rows for a duplicated key
  notices: LocaleNotice[];       // provider notices and SDK notices for this locale
  needsReview: { key: string; reasons: string[] }[]; // accepted keys flagged for a second look
  usage?: UsageSummary;          // this locale's summed tokens; absent if nothing reported usage
  error?: { code: string; message: string }; // only on a "failed" locale, and not on every one
}
```

Die Teile, die du kennen solltest:

- **needsReview** listet akzeptierte, geschriebene Keys, die die Review-Heuristiken markiert
  haben, jeder mit seinen Grund-Codes: `LENGTH_RATIO_OUTLIER`, `MAX_LENGTH_EXCEEDED`,
  `EQUALS_SOURCE`, `GLOSSARY_TERM_MISSED`, `GLOSSARY_FORBIDDEN_TERM`, `INTEGRITY_REORDERED`, `PROVIDER_DEGRADED` und
  `FUZZY_CACHE_REUSE`. Die Menge wird als Tupel `REVIEW_REASON_CODES` ausgeliefert; baue jedes
  Laufzeitschema und jede vollständige Zuordnung daraus, statt die Mitglieder abzutippen. Ein
  Review-Flag ist nur ein Hinweis und hält nie einen Key zurück; ein Key erscheint also nie in
  `needsReview` und `integrityMismatches` zugleich. Was jeder Code bedeutet, steht in
  [Übersetzungssicherheit](/docs/translation-safety), das Abarbeiten der Warteschlange in
  [Review in Studio](/docs/review-in-studio).
- **notices** leben pro Locale, nie auf oberster Ebene. Dazu zählen Provider-Notices (etwa eine
  DeepL-Degradation) und SDK-Notices mit den Codes `PLURAL_CATEGORIES_INCOMPLETE`,
  `SUB_BATCH_FAILED`, `BLANK_ROW_BASELINE_RETAINED`, `HANDOFF_REVIEWS_RECORDED` (ab 0.12.0: Keys, die eine XLIFF-Übergabe als geprüft oder final markiert hat, wurden als freigegeben festgehalten), `BUDGET_TOKENS_EXCEEDED`,
  `CACHE_VERSION_UNRECOGNIZED`, `PROVENANCE_VERSION_UNRECOGNIZED`, `LOCALE_STATE_CARRIED_OVER` (Zustand unter einer Unterstrich-Schreibweise wie `pt_BR` wurde zum konfigurierten `pt-BR` verschoben; siehe [Ein umgeschriebener Locale-Code](/docs/the-lock-file#ein-umgeschriebener-locale-code)), `LOCALE_STATE_CARRY_OVER_SKIPPED` (dieses Verschieben bleibt dem nächsten Lauf überlassen, weil der Guard der Lock-Datei belegt blieb oder sich nicht lesen oder anlegen ließ oder eine Datei nicht geschrieben werden konnte; blieb nicht nur das Translation Memory zurück, lief die Locale nicht und scheiterte mit `LOCALE_STATE_NOT_CARRIED_OVER`), `PROVENANCE_FILE_TOO_LARGE`
  (das Festhalten einer Locale hätte `verbatra.provenance.json` über die Größe wachsen lassen,
  die verbatra zurückliest, daher blieb die Datei, wie sie war) und ab 0.12.0 die vier Warnungen der Prüfung der Locale-Unterstützung, erhoben, bevor irgendetwas ausgegeben wird, und auch bei einem Dry-Run: `LOCALE_UNVERIFIED_BY_PROVIDER` (der gesendete Code steht nicht in der Tabelle des Providers, nur seine Grundsprache, oder er stammt aus `localeMap`), `LOCALE_NOT_WELL_TESTED` (ein LLM-Ziel außerhalb der gut getesteten Liste), `GLOSSARY_UNSUPPORTED_BY_PROVIDER` und `FORMALITY_UNSUPPORTED_BY_PROVIDER` (ein Glossar oder Tonfall, den der Provider für die Locale nicht anwenden kann). Die Cache-Notice gilt für den gesamten Lauf (eine Datei, die
  sich alle Locales teilen) und wird deshalb an jede Locale des Laufs gehängt.
- **usage** ist `undefined`, nie eine erfundene Null, wann immer nichts in diesem Bereich einen
  Verbrauch gemeldet hat: ein Dry-Run ruft nie einen Provider auf, und DeepL meldet nie Tokens.
  `RunSummary.usage` ist die Summe über die Locales.
- **budget** erscheint nur, wenn `maxTokens` konfiguriert ist: `{ maxTokens, behavior, supported,
  tokensUsed, exceeded }`. `supported` sagt, ob `tokensUsed` vollständig der vom Provider selbst
  gemeldete Verbrauch ist; es ist `false`, sobald eine Anfrage ohne brauchbare Zahl zurückkam, und
  die Summe ist dann teils verbatras Projektion, die genauso gezählt und durchgesetzt wird. Ein
  Dry-Run, oder jeder Lauf ohne Anfrage, meldet `supported: true` mit `tokensUsed: 0`: Es wurde
  nichts gesendet, also nichts projiziert. Unter `behavior: "stop"` wird
  die Obergrenze vor jeder Anfrage geprüft, die der Lauf sendet, auch vor jeder Hälfte einer neu
  aufgeteilten Anfrage. `tokensUsed` landet also auf oder unter `maxTokens`, bis auf einen Rest: Die
  zuletzt zugelassene Anfrage wird auf das abgeglichen, was der Provider gemeldet hat, was die Summe
  nachträglich über die Obergrenze schieben kann. Danach wird nichts weiter gesendet. Zwei Dinge
  liegen außerhalb dessen, was eine Reservierung begrenzen kann, weil sie in einer bereits
  zugelassenen Anfrage passieren: Die Provider-Schicht sendet eine eigene Reparatur-Anfrage, wenn
  Keys fehlen, ein zugelassener Batch kann also bis zu etwa das Doppelte seiner Projektion kosten,
  und die Zählung ist nur so gut wie das, was der Provider meldet. Beides landet beim Abgleich, und
  danach wird nichts weiter zugelassen. Das Budget begrenzt einen `translate`-Aufruf: `watch`
  startet je Lauf ein frisches, und `retranslateEntry` fällt gar nicht darunter.
- **error.code** auf einer fehlgeschlagenen Locale ist ein durchgereichter String (der Code des
  zugrunde liegenden Providers oder Adapters, mit `LOCALE_FAILED` nur als Rückfall); behandle ihn
  also nicht als geschlossene Menge. Eine `failed`-Locale trägt nicht immer ein `error`: Eine, deren
  Keys alle zurückgehalten wurden und deshalb in `integrityMismatches`, `providerFailures` oder
  `budgetWithheld` stehen, scheitert, ohne dass etwas geworfen wurde. Der Grund steht in diesen
  Listen und in ihren `notices`, etwa `SUB_BATCH_FAILED` für einen gescheiterten Provider-Batch oder
  `BUDGET_TOKENS_EXCEEDED` für das Token-Budget. Prüf `status`, nie, ob `error` vorhanden ist.
- **cacheHits** listet Keys, die aus dem [Übersetzungsspeicher-Cache](/docs/the-cache) statt vom
  Provider bedient wurden. **fuzzyHits** listet die Keys, die eine Übersetzung für einen
  geänderten Quellstring wiederverwendet haben, jeweils mit `key`, `similarity` und dem getroffenen
  `previousSource`; sie ist leer, solange `fuzzyCache` nicht aktiviert ist, und diese Keys zählen nie
  in **cacheHits** mit. **unfilled**, **malformedRows** und **duplicateKeys** werden nur von
  `importWorkbook` befüllt (ein `translate`-Lauf lässt sie leer): eine leere Zeile, deren Key zum
  Importzeitpunkt weiterhin eine Übersetzung braucht (egal ob sie als `new` oder als `changed`
  exportiert wurde), eine Arbeitsmappen-Zeile, die der Reader nicht parsen konnte, und ein
  doppelter Key, dessen erstes Vorkommen gewonnen hat. Das optionale `line` bei den letzten beiden
  ist die Dateizeile, in der der Datensatz beginnt; es ist nur bei einem Import mit Trennzeichen
  (`csv` oder `tsv`) vorhanden. Die einzige Ausnahme ist ein [rein menschliches](/docs/human-only-workflow) Projekt: Dort listen `translate` und `watch` in **unfilled** jeden Key, für den das Translation Memory keinen exakten Eintrag hatte, und **fuzzyHits** bleibt leer, weil dort nie unscharf wiederverwendet wird.
- **protected** listet die Keys, die ein `translate`-Lauf in Ruhe gelassen hat, jeweils mit ihrem `reason` (`human`, `import`, `external` oder `pinned`) und, unter `humanEdits: "suggest"`, einer `suggestion` (die Antwort des Providers oder ein exakter Translation-Memory-Eintrag, nie ein Fuzzy-Treffer), die nicht geschrieben wurde, sowie einem `suggestionStatus`: `planned` bei einem Dry Run, `suggested` oder warum nicht (`integrity-mismatch`, `provider-failure`, `budget-withheld`). Ein fehlgeschlagener Vorschlag ändert nie den Status einer Locale. Sie stehen nicht in **translated**, ändern nie den Status einer Locale und bleiben für `check` veraltet. `importWorkbook` lässt das Feld leer. Siehe [Menschliche Übersetzungen schützen](/docs/protecting-human-translations).

### budgetStanding

<AvailableFrom version="0.11.0" />

Macht aus einem `RunBudget` einen von drei `BudgetStanding`-Werten, dieselbe Einordnung, die die
Budgetzeile der CLI, Studio und das Agent-Tool `usage.summary` melden: `"within"`, wenn der Lauf
seine Obergrenze nie erreicht hat, `"stopped-before-ceiling"`, wenn ein `"stop"`-Budget eine Anfrage
zurückgehalten hat, während `tokensUsed` noch unter `maxTokens` lag, und `"reached"`, wenn
`tokensUsed` `maxTokens` erreicht oder überschritten hat. Nutze es, statt nur `exceeded` zu lesen,
das in beiden letzten Fällen `true` ist.

```ts title="Signatur"
function budgetStanding(budget: RunBudget): BudgetStanding;
```

**Rückgabe:** `BudgetStanding`
