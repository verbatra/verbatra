Sélectionne un fournisseur par `id` dans le bloc `provider` de ta [configuration](/docs/config-file). Anthropic, OpenAI, Gemini et openai-compatible sont des modèles de langage ; DeepL, Google Cloud Translation et LibreTranslate sont des services de traduction automatique ; `none` désactive la traduction automatique. Les identifiants de modèle sur cette page sont des exemples, pas des recommandations. La couverture des langues se trouve dans [Langues et locales](/docs/language-support), et ce que reçoit chaque fournisseur dans [Traitement des données et confidentialité](/docs/data-handling).

## Lequel choisir ?

Tout fournisseur fonctionne avec tout format et toute commande, et en changer plus tard revient à modifier un seul `id`.

| Si tu veux | Utilise |
| --- | --- |
| Gratuit, pour un petit projet aux chaînes non confidentielles | **Gemini** : une offre d'API gratuite, clés sur [Google AI Studio](https://aistudio.google.com/apikey). Hors EEE, Suisse et Royaume-Uni, Google peut utiliser les requêtes de l'offre gratuite et les faire lire par des humains ([conditions](/docs/data-handling#conservation-et-traitement-des-données-chez-le-fournisseur)). |
| La meilleure qualité pour une appli en production | **Anthropic** ou **OpenAI**, tous deux payants. |
| Gros volume, un glossaire natif, pas de LLM | **DeepL**, offre gratuite ou payante. |
| La couverture la plus large avec une clé d'API sur Google Cloud | **Google Cloud Translation** (Basic, v2). |
| Hors ligne, sans coût, rien ne quitte ton réseau | **openai-compatible** avec LM Studio, Ollama ou vLLM. |
| Pas de modèle de langage, mais auto-hébergé | **LibreTranslate** sur ton propre serveur. |
| Aucune traduction automatique | **none** : mémoire et humains uniquement. |

## Les clés viennent de l'environnement

verbatra ne lit jamais une clé depuis la configuration. Chaque fournisseur hébergé lit une variable :

| Id du fournisseur | Variable d'environnement |
| --- | --- |
| `anthropic` | `ANTHROPIC_API_KEY` |
| `openai` | `OPENAI_API_KEY` |
| `gemini` | `GEMINI_API_KEY` |
| `deepl` | `DEEPL_API_KEY` |
| `google-translate` | `GOOGLE_TRANSLATE_API_KEY` |

Définis-la dans `.env` (que `verbatra init` ajoute au `.gitignore`), dans ton shell ou dans le coffre de secrets de ta CI, et ne la commite jamais. Une variable absente ou vide échoue avec `MISSING_API_KEY`, en nommant la variable mais jamais une valeur. Le SDK l'enveloppe dans `PROVIDER_CONSTRUCTION_FAILED` : la CLI affiche ce code avec `(cause: MISSING_API_KEY)`, et `--json` porte `"causeCode": "MISSING_API_KEY"`. Depuis 0.12.0, l'erreur porte aussi `envVar`, et la CLI affiche un indice `next:` qui nomme la variable à définir. `openai-compatible` et `libretranslate` n'ont généralement besoin d'aucune clé ; voir leurs sections.

## Anthropic

```ts title="verbatra.config.ts"
provider: {
  id: "anthropic",
  options: {
    model: "claude-sonnet-4-6", // example model id
    maxTokens: 4096,
  },
}
```

| Option | Type | Défaut | Effet |
| --- | --- | --- | --- |
| `model` | chaîne | requis | L'identifiant du modèle. |
| `maxTokens` | entier positif | requis | Plafonne les tokens de sortie d'une réponse ([limites](#limites-de-tokens-de-sortie)) ; sans lien avec le budget de premier niveau. |
| `requestTimeoutMs` | entier positif | `120000` | Borne chaque tentative de requête ([Délai de requête](#délai-de-requête)). |
| `localeMap` | table de locale vers code | aucun | Remplace le code envoyé par locale ([Codes de locale](#codes-de-locale-envoyés-au-fournisseur)). |

Lit `ANTHROPIC_API_KEY`.

```ts title="verbatra.config.ts"
  },
```


| Option | Type | Défaut | Effet |
| --- | --- | --- | --- |
| `model` | chaîne | requis | L'identifiant du modèle. |
| `maxOutputTokens` | entier positif | requis | Plafonne les tokens de sortie d'une réponse. |
| `requestTimeoutMs` | entier positif | `120000` | Borne chaque tentative de requête. |
| `localeMap` | table de locale vers code | aucun | Remplace le code envoyé par locale. |

Lit `GEMINI_API_KEY`.

<Callout title="L'offre gratuite et ses limites">
Une clé de [Google AI Studio](https://aistudio.google.com/apikey) ne demande aucune facturation. L'offre gratuite plafonne les requêtes par minute et par jour, donc une première exécution sur beaucoup de locales peut atteindre le plafond. Les brèves limites de débit sont retentées, un plafond durable ne l'est pas : traduis une locale à la fois ou baisse `maxBatchSize`, puis relance, ce qui ne reprend que ce qui manque encore.
</Callout>

## DeepL

```ts title="verbatra.config.ts"
provider: {
  id: "deepl",
  options: {
    glossaryId: "<your-glossary-id>",
  },
}
```

| Option | Type | Défaut | Effet |
| --- | --- | --- | --- |
| `glossaryId` | chaîne | aucun | Un glossaire que tu as créé dans DeepL, appliqué nativement. |
| `requestTimeoutMs` | entier positif | `120000` | L'attente minimale par tentative, jusqu'à cinq tentatives. |
| `localeMap` | table de locale vers code | aucun | Remplace le code envoyé par locale. |

Lit `DEEPL_API_KEY` ; `options` peut valoir `{}`. DeepL n'a ni modèle ni limite de tokens de sortie, et se dégrade avec un avis plutôt que d'échouer :

- **Les placeholders** voyagent comme des marqueurs numérotés dans une balise ignorée (`Hello {{name}}` comme `Hello <x>{0}</x>`) puis sont restaurés. `PLACEHOLDER_UNSUPPORTED` retient une valeur dont un placeholder n'y figure pas littéralement, ou dont le reste du texte contient `<`, `>`, `{` ou `}` (arguments ICU, balisage, signes de comparaison), et un résultat avec un marqueur perdu, répété, modifié ou nu, une entité inconnue ou une balise étrangère. Le balisage seul part en texte brut. <AvailableFrom version="0.12.0" />
- **Glossaire.** Les traductions et les termes à ne pas traduire du glossaire de ta configuration ne sont pas appliqués (`GLOSSARY_IGNORED`) ; les traductions interdites ne sont vérifiées qu'après coup.
- **Le ton** se mappe sur la formalité (`formal` plus formel, `informal` moins, `neutral` omis). Une clé de l'offre gratuite, ou une langue sans formalité comme le suédois, retombe sur le registre par défaut avec `FORMALITY_DOWNGRADED` ; verbatra demande avec `prefer_more` et `prefer_less` pour que la requête n'échoue pas.

<AvailableFrom version="0.12.0" />

verbatra embarque la [table de langues](https://developers.deepl.com/docs/getting-started/supported-languages) datée de DeepL et refuse une langue non listée avec `LOCALE_UNSUPPORTED_BY_PROVIDER` avant toute dépense. Un `glossaryId` ne fonctionne que si les deux langues figurent dans la liste des glossaires de DeepL (comme `DE`, `EN`, `FR`, `JA`, `ZH`).

## Google Cloud Translation

<AvailableFrom version="0.10.0" />

```ts title="verbatra.config.ts"
provider: {
  id: "google-translate",
  options: {},
}
```

| Option | Type | Défaut | Effet |
| --- | --- | --- | --- |
| `requestTimeoutMs` | entier positif | `120000` | Borne l'appel entier (sans nouvelle tentative). |
| `localeMap` | table de locale vers code | aucun | Remplace le code envoyé par locale. |

Lit `GOOGLE_TRANSLATE_API_KEY`, une simple clé d'API d'un projet Google Cloud où l'API Cloud Translation est activée. Il utilise le niveau Basic (v2) ; le niveau Advanced (v3) exige un compte de service, qui ne rentre pas dans une clé en variable d'environnement.

- **Ni formalité ni glossaire.** Un ton `formal` ou `informal` signale `FORMALITY_DOWNGRADED` ; une traduction de glossaire ou un terme à ne pas traduire signale `GLOSSARY_IGNORED`.
- **Les placeholders** sont masqués comme pour DeepL, dans `<span translate="no">` ; les sauts de ligne, tabulations et doubles espaces sont aussi retenus. <AvailableFrom version="0.12.0" />
- **Codes.** Chaque code envoyé est vérifié comme du BCP 47 bien formé avant tout appel (`en_US` échoue avec `INVALID_REQUEST`). Les codes régionaux sont autorisés ; une paire que Google rejette échoue avec `INVALID_REQUEST` venant de l'API.

<AvailableFrom version="0.12.0" />

verbatra embarque la [table de langues](https://docs.cloud.google.com/translate/docs/languages) datée de Google et refuse une langue non listée avant toute dépense. Un code régional dont la langue n'est listée que dans son ensemble, comme `de-AT`, est envoyé tel qu'il est écrit avec un avertissement.

## openai-compatible

Tout serveur qui parle l'API Chat Completions d'OpenAI : LM Studio, Ollama, vLLM, ou une API hébergée avec le même protocole.

```ts title="verbatra.config.ts"
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct", // example: whatever your server exposes
    maxOutputTokens: 1024,
  },
}
```

| Option | Type | Défaut | Effet |
| --- | --- | --- | --- |
| `baseUrl` | URL `http` ou `https` | requis | Le serveur, chemin d'API compris, généralement `/v1`. Une URL sans lui passe la validation et échoue au moment de la requête. |
| `model` | chaîne | requis | Le modèle que ton serveur expose. |
| `maxOutputTokens` | entier positif | requis | Plafonne les tokens de sortie d'une réponse. |
| `apiKeyEnvVar` | nom de variable | aucun | La variable qui contient une clé pour ce serveur ; jamais la variable d'un fournisseur hébergé. |
| `requestTimeoutMs` | entier positif | `120000` | Borne chaque tentative de requête. |
| `localeMap` | table de locale vers code | aucun | Remplace le code envoyé par locale. |

Une API hébergée fonctionne de la même façon, par exemple Mistral :

```ts title="verbatra.config.ts"
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "https://api.mistral.ai/v1",
    model: "mistral-large-latest", // example: check Mistral's current model list
    maxOutputTokens: 4096,
    apiKeyEnvVar: "MISTRAL_API_KEY",
  },
}
```

Le format de réponse est le même schéma strict que pour `openai`, mais le premier objet JSON équilibré est extrait de toute prose ou bloc de code qui l'entoure avant la validation. La sortie passe quand même par tous les contrôles de schéma et d'intégrité. `verbatra init --provider openai-compatible --base-url <url> --model <name>` écrit ce bloc ([init](/docs/cli/init#fournisseurs)), et `--api-key-env-var <NAME>` ajoute le nom de la variable.

### Les clés sont optionnelles

La clé se résout dans cet ordre :

1. **`apiKeyEnvVar`** : s'il est défini, sa variable doit contenir une clé, sinon l'exécution échoue avec `MISSING_API_KEY`.
2. **`OPENAI_COMPATIBLE_API_KEY`** : utilisée quand elle est définie et non vide ; sinon verbatra passe à la suite.
3. **`"local"`** : un placeholder fixe et non secret, qui est ce qui fait fonctionner un serveur sans clé.

`apiKeyEnvVar` ne peut pas nommer la variable d'un fournisseur hébergé, et le client ne lit jamais `OPENAI_API_KEY`, donc une clé hébergée n'atteint jamais un `baseUrl` personnalisé.

<Callout type="warn" title="Une vraie clé envoyée en http non chiffré circule en clair">
Le `http://` en clair est autorisé vers n'importe quel hôte, ce qui est sûr tant qu'aucune clé n'est configurée. Avec une clé et une URL `http://` non loopback, la clé traverse ton réseau sans chiffrement, et verbatra n'avertit pas à ce sujet. Utilise `https://` pour un serveur qui exige une clé.
</Callout>

### Choisir un modèle local

Préfère un modèle ajusté par instructions, sans raisonnement et avec une bonne couverture multilingue, aussi grand que ton matériel l'exécute bien ; `qwen2.5-14b-instruct` est un choix par défaut raisonnable. Les modèles de raisonnement et les builds fortement quantifiés ont tendance à envelopper la réponse dans de la prose ou à la tronquer, ce qui échoue en `INVALID_RESPONSE` ou `OUTPUT_TRUNCATED` au lieu d'écrire une traduction corrompue. Si tu as besoin d'un modèle de raisonnement, donne-lui de la place ([Limites de tokens de sortie](#limites-de-tokens-de-sortie)).

## LibreTranslate

<AvailableFrom version="0.12.0" />

Un serveur [LibreTranslate](https://github.com/LibreTranslate/LibreTranslate) auto-hébergé : de la traduction automatique neuronale (Argos Translate), sans modèle de langage. verbatra appelle seulement son API HTTP, donc la licence AGPL-3.0 du serveur ne s'étend pas à ton projet.

```ts title="verbatra.config.ts"
provider: {
  id: "libretranslate",
  options: {
    baseUrl: "http://localhost:5000",
  },
}
```

| Option | Type | Défaut | Effet |
| --- | --- | --- | --- |
| `baseUrl` | URL `http` ou `https` | requis | La racine de l'API, sans `/translate`. |
| `requestTimeoutMs` | entier positif | `120000` | Borne l'appel entier (sans nouvelle tentative). |
| `localeMap` | table de locale vers code | aucun | Remplace le code envoyé par locale. |

Ses langues sont les modèles installés sur ton serveur :

```bash
docker run -p 5000:5000 libretranslate/libretranslate --load-only en,de,fr
```

- **Clé.** `LIBRETRANSLATE_API_KEY` est envoyée comme `api_key` seulement si elle est définie. Un serveur démarré avec `--api-keys` fait échouer l'exécution avec `MISSING_API_KEY` quand elle est absente, et avec `AUTH_FAILED` quand il la rejette.
- **Ni formalité ni glossaire** : `FORMALITY_DOWNGRADED` et `GLOSSARY_IGNORED`, comme pour Google ; la sortie est quand même vérifiée par rapport au glossaire.
- **Les placeholders** sont masqués comme pour DeepL, par de simples marqueurs `{0}` ; le balisage est conservé, donc seules les accolades à côté d'un placeholder comptent.
- **Balisage.** Une valeur avec des balises de style HTML est envoyée au format `html`, donc le texte à l'intérieur des balises est traduit et les balises restent ; une formulation qui traverse une balise peut en souffrir, et des balises modifiées sont refusées.
- **Vérification des langues.** Chaque cible est `unverified` avec un avertissement `LOCALE_UNVERIFIED_BY_PROVIDER` à chaque exécution ; `verbatra doctor --locales --live` les vérifie d'après la liste `/languages` du serveur.

`verbatra init --provider libretranslate --base-url <url>` écrit ce bloc.

## none

<AvailableFrom version="0.12.0" />

Désactive la traduction automatique par principe, pour un NDA ou une règle de l'entreprise qui interdit d'envoyer des chaînes à un service.

```ts title="verbatra.config.ts"
provider: { id: "none" }
```

`options` peut être omis ou valoir `{}`. Aucun fournisseur n'est construit, aucune clé n'est lue et aucune requête n'est faite. `translate` et `watch` ne remplissent les clés que depuis [la mémoire de traduction](/docs/the-cache) et signalent le reste comme `unfilled` (`translate` sort avec `3`). [Studio](/docs/cli/studio) et le [serveur MCP](/docs/cli/mcp) ne proposent jamais d'actions qui dépensent, et `retranslateEntry` du SDK échoue avec `MACHINE_TRANSLATION_DISABLED`. La mémoire est un compartiment à part : reprends des entrées avec `tmx export` avant la bascule et `tmx import` après. `verbatra init --provider none` le génère ; voir [Travailler sans traduction automatique](/docs/human-only-workflow).

## Ton et glossaire selon les fournisseurs

Chaque requête ne porte que les termes du glossaire de sa locale cible, et la sortie de chaque fournisseur est ensuite vérifiée par rapport à eux.

| Fournisseur | `tone` | `glossary` |
| --- | --- | --- |
| Anthropic, OpenAI, Gemini, openai-compatible | envoyé et respecté | traductions, traductions interdites, termes à ne pas traduire et notes envoyés comme données contraignantes |
| DeepL | mappé sur la formalité ; `FORMALITY_DOWNGRADED` avec une clé gratuite ou une langue sans formalité | `GLOSSARY_IGNORED` ; seul `glossaryId` s'applique |
| Google Cloud Translation, LibreTranslate | `FORMALITY_DOWNGRADED` pour `formal` ou `informal` | `GLOSSARY_IGNORED` |

## Comportement partagé par tous les fournisseurs

### Découpage en lots

Le travail d'une locale part en sous-lots séquentiels d'au plus [`maxBatchSize`](/docs/config-file#maxbatchsize) entrées (`50` par défaut). Un sous-lot échoué est retenu et retenté à l'exécution suivante pendant que les autres avancent. DeepL et Google Cloud Translation découpent aussi un sous-lot pour respecter leurs propres plafonds par requête.

### Nouvelles tentatives

Les limites de débit et les erreurs serveur sont retentées avec un court backoff : les clients d'OpenAI, d'Anthropic et de DeepL le font eux-mêmes, et verbatra ajoute la même chose pour Gemini. Google Cloud Translation et LibreTranslate ne réessaient pas : une limite de débit ou une erreur serveur remonte aussitôt comme `RATE_LIMITED` ou `PROVIDER_UNAVAILABLE`, et le sous-lot est repris à l'exécution suivante.

### Délai de requête

`requestTimeoutMs` borne chaque requête, pour qu'un serveur qui accepte une connexion mais ne répond jamais ne puisse pas bloquer une exécution ni garder le verrou d'écriture d'une locale. La valeur par défaut est `120000` ms (deux minutes) ; augmente-la pour un modèle local lent ou un gros `maxBatchSize`.

```ts title="verbatra.config.ts"
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct",
    maxOutputTokens: 1024,
    requestTimeoutMs: 300000, // 5 minutes
  },
}
```

- **Par tentative.** Les clients réessaient `429` et `5xx` quelques fois, chaque tentative disposant du délai complet. Anthropic, OpenAI, openai-compatible et Gemini réessaient aussi une tentative qui a dépassé le délai, et tous sauf Gemini une erreur de connexion : un serveur figé met donc jusqu'à trois délais plus les pauses avant d'être abandonné.
- **L'erreur nomme la cause.** Des limites de débit, erreurs serveur ou connexions refusées répétées échouent en `RATE_LIMITED`, `PROVIDER_UNAVAILABLE` ou `PROVIDER_ERROR` ; `TIMEOUT` veut dire qu'une tentative n'a reçu aucune réponse à temps.
- **DeepL** attend au moins le délai par tentative, jusqu'à cinq tentatives, et ne peut pas interrompre une requête en cours : une exécution interrompue la laisse donc aller à son terme chez DeepL.
- **Google Cloud Translation et LibreTranslate** envoient une seule requête sans nouvelle tentative, donc le délai couvre l'appel entier.

Seul le sous-lot échoué est touché ; ses clés reviennent à l'exécution suivante.

### Codes de locale envoyés au fournisseur

<AvailableFrom version="0.12.0" />

Les fichiers, le fichier de verrouillage et la mémoire utilisent toujours les codes de ta configuration. Seule la requête est traduite vers ce qu'attend le fournisseur :

| Fournisseur | Locale source | Locale cible |
| --- | --- | --- |
| DeepL | La langue seule : `en-US` comme `EN`, `zh-Hant-TW` comme `ZH`. | `zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO` comme `ZH-HANT` ; `zh-Hans`, `zh-CN`, `zh-SG` comme `ZH-HANS`. Les variantes DeepL sont conservées (`EN-GB`, `EN-US`, `PT-BR`, `PT-PT`, `ES-419`, `FR-CA`, `FR-FR`, `DE-CH`, `DE-DE`). L'espagnol avec une région d'Amérique latine ou des Caraïbes (`MX`, `AR`, `CO`, `CL`, `PE`, `VE`, `EC`, `GT`, `CU`, `BO`, `DO`, `HN`, `PY`, `SV`, `NI`, `CR`, `PA`, `UY`, `PR`, `US`, `419`) comme `ES-419`. Les autres régions et écritures sont retirées : `de-AT` comme `DE`. |
| Google Cloud Translation | `zh-Hant` (`zh-HK`, `zh-MO`) comme `zh-TW`, `zh-Hans` (`zh-SG`) comme `zh-CN`, `nb` comme `no` ; tout le reste tel qu'il est écrit. | Comme pour la source. |
| LibreTranslate | La langue seule (`de-AT` comme `de`), sauf que `pt-BR` est conservé et que le chinois part comme `zh-Hans` ou `zh-Hant` (`zh-TW` comme `zh-Hant`). | Comme pour la source. |
| Anthropic, OpenAI, Gemini, openai-compatible | Tel qu'il est écrit, avec le nom anglais de sa langue. | Tel qu'il est écrit, avec les noms anglais de sa langue, de son écriture et de sa région. |

Un LLM reçoit par exemple `sr-Latn` avec `{ "name": "Serbian (Latin)", "script": "Latin" }`, et une règle fixe lui demande d'écrire dans cette écriture et cette variante ; un code que Node.js ne sait pas nommer est envoyé sans nom. DeepL n'a pas de cible anglaise ni portugaise générique, donc une cible qui aboutit à un `en` ou `pt` nu (comme `en-AU`) est refusée avant l'exécution : fais-la correspondre à `EN-GB`, `EN-US`, `PT-BR` ou `PT-PT`.

`localeMap` remplace le code par locale, et une entrée l'emporte toujours :

```ts title="verbatra.config.ts"
provider: {
  id: "deepl",
  options: {
    localeMap: {
      "en-AU": "EN-GB",
      "fr-BE": "FR-FR",
    },
  },
}
```

- **Les clés** doivent être `sourceLocale` ou une locale cible, écrites comme dans la configuration ; toute autre clé échoue avec `CONFIG_INVALID`. Elle se place sous `options` (directement sous `provider`, elle échoue), pour tous les fournisseurs sauf `none`.
- **Les valeurs** sont des chaînes non vides de 64 caractères au plus, envoyées telles quelles : comme code de langue à un fournisseur de traduction automatique, à la place du code pour un LLM (`"pt-BR (Brazilian Portuguese)"` fonctionne). Les noms de langue pour un LLM viennent toujours de la clé. Une valeur qui envoie encore à DeepL un `EN` ou `PT` nu échoue avec `INVALID_REQUEST` ; une valeur que le fournisseur rejette fait échouer son sous-lot.
- **Effet sur la mémoire.** Seules les chaînes nouvelles et modifiées partent avec un nouveau code. Une table non vide fait partie de l'empreinte de la [mémoire](/docs/the-cache), donc la modifier ouvre un compartiment séparé.

### Vérifier les langues prises en charge par un fournisseur

<AvailableFrom version="0.12.0" />

Chaque locale configurée est jugée avant toute dépense :

| Fournisseur | Jugé d'après | Refusé avant l'exécution | Avertissement pour |
| --- | --- | --- | --- |
| DeepL | Sa table de langues embarquée, avec la prise en charge du glossaire et de la formalité par langue | Une langue source ou cible non listée | Un glossaire pour une paire hors des langues de glossaire, un ton sans formalité, un code listé seulement en partie |
| Google Cloud Translation | Sa table de langues embarquée | Une langue non listée | Tout glossaire, un ton `formal` ou `informal`, un code régional listé seulement comme langue |
| LibreTranslate | Rien avant une exécution ; la liste `/languages` du serveur avec `doctor --live` | Jamais | Chaque locale cible à chaque exécution, tout glossaire, un ton `formal` ou `informal` |
| Anthropic, OpenAI, Gemini, openai-compatible | Rien : un LLM accepte toutes les langues | Jamais | Une langue hors de la [liste des langues bien testées](/docs/language-support#vérifier-la-prise-en-charge-avant-une-exécution) |
| none | Sans objet | Jamais | Jamais |

[`verbatra doctor`](/docs/cli/doctor#prise-en-charge-des-locales) donne chaque verdict, et `--locales` ajoute le code envoyé ainsi que la prise en charge du glossaire et de la formalité. `translate` (exécution à blanc et estimation comprises), `watch` au démarrage et une retraduction d'une seule clé refusent une locale non prise en charge avec `LOCALE_UNSUPPORTED_BY_PROVIDER` et le code de sortie `2` avant qu'aucun fournisseur ne soit construit. Les avertissements ne refusent jamais rien ; ils apparaissent comme avis (`LOCALE_UNVERIFIED_BY_PROVIDER`, `LOCALE_NOT_WELL_TESTED`, `GLOSSARY_UNSUPPORTED_BY_PROVIDER`, `FORMALITY_UNSUPPORTED_BY_PROVIDER`).

Les tables sont des copies datées. `verbatra doctor --live` récupère d'abord la liste actuelle (`/v3/languages` chez DeepL, `languages` chez Cloud Translation, `/languages` chez LibreTranslate, sans consommer de quota) quand la clé est définie (LibreTranslate n'en a pas besoin) et que la [politique réseau](/docs/network-policy) l'autorise. La liste en direct n'alimente que le rapport ; `translate` utilise toujours la table embarquée. Pour une langue ajoutée depuis, associe la locale dans `localeMap` : un code explicite est envoyé avec un avertissement, pas refusé.

### Erreurs structurées

Un échec de fournisseur ne remonte jamais comme une erreur SDK brute, qui pourrait porter des en-têtes ou une clé : verbatra lève une erreur structurée avec un code stable et un message fixe, sans secret ([Codes d'erreur des fournisseurs](/docs/error-codes#provider-error-codes)). Seul son propre sous-lot est touché. Pour openai-compatible et LibreTranslate, un `PROVIDER_ERROR` nomme l'hôte et le port du `baseUrl` (jamais son chemin, sa requête ni ses informations d'utilisateur), comme `The translation provider request to localhost:11434 failed: the connection was refused.` ; Google Cloud Translation nomme `translation.googleapis.com`, jamais la chaîne de requête qui porte sa clé.

### Limites de tokens de sortie

Les fournisseurs LLM plafonnent les tokens de chaque réponse. Un modèle qui s'arrête au plafond lève `OUTPUT_TRUNCATED` :

> The provider stopped because the output-token limit was reached. Reduce the batch size or raise the configured max output tokens.

verbatra redécoupe d'abord un sous-lot tronqué en deux moitiés, en descendant jusqu'à une seule entrée, et ne retient qu'une entrée qui déborde encore. Pour régler cela durablement, baisse `maxBatchSize` ou augmente `maxTokens` (Anthropic) ou `maxOutputTokens`. Un modèle de raisonnement puise ses tokens de raisonnement cachés dans le même budget et peut l'épuiser avant d'écrire quoi que ce soit : donne-lui donc une marge généreuse. Les fournisseurs de traduction automatique n'ont pas de cas de troncature.

### Signalements de révision

Chaque traduction acceptée passe par les mêmes contrôles post-traduction, et une traduction suspecte est signalée pour révision plutôt que rejetée. Voir les [raisons de révision](/docs/error-codes#review-reason-codes) et [Réviser dans Studio](/docs/review-in-studio).
