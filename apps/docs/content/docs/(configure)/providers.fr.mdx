verbatra livre six fournisseurs derrière une seule interface : Anthropic, OpenAI, Gemini et openai-compatible (un serveur compatible OpenAI, local ou auto-hébergé) sont des grands modèles de langage, et DeepL et Google Cloud Translation sont des services de traduction automatique. Tu en sélectionnes un dans le bloc `provider` de ta [configuration](/docs/config-file), par `id`. Chaque identifiant de modèle sur cette page est un exemple, pas une recommandation : les catalogues de modèles changent, donc vérifie la liste actuelle de ton fournisseur.

## Lequel choisir ?

Tout fournisseur fonctionne avec tout format et toute commande ; le choix porte sur le coût, la qualité, la confidentialité, et la façon d'obtenir une clé.

- **Petit projet ou projet perso, tu le veux gratuit ?** Utilise **Gemini**. Il a une vraie offre d'API gratuite, donc tu peux traduire une appli entière à coût zéro. Récupère une clé sur [Google AI Studio](https://aistudio.google.com/apikey) et définis `GEMINI_API_KEY`. L'offre gratuite est limitée en débit (voir la note plus bas), ce qui ne compte que sur une grosse première exécution.
- **La meilleure qualité de traduction pour une appli en production ?** Utilise **Anthropic** ou **OpenAI**. Les deux sont des LLM payants et lisent `ANTHROPIC_API_KEY` ou `OPENAI_API_KEY`.
- **Gros volume, piloté par glossaire, ou pas de LLM dans la boucle ?** Utilise **DeepL**. C'est une API de traduction automatique dédiée avec une offre gratuite et une payante, et elle prend en charge un glossaire natif par id. Elle ne traduit pas les chaînes portant des placeholders (voir la note plus bas) ; pour celles-là, utilise un fournisseur LLM.
- **Déjà sur Google Cloud, ou tu veux la couverture de langues la plus large avec une simple clé d'API ?** Utilise **Google Cloud Translation**. C'est l'API de traduction automatique dédiée de Google (le niveau Basic, v2), facturée via ton projet Google Cloud. Comme DeepL, elle ne traduit pas les chaînes portant des placeholders.
- **Hors ligne, sans coût, ou tes chaînes ne doivent jamais quitter ton réseau ?** Utilise **openai-compatible**. Il pointe verbatra vers un serveur d'inférence local ou auto-hébergé (LM Studio, Ollama, vLLM) au lieu d'une API hébergée. Pas de compte, pas de clé d'API, et aucune sortie réseau au-delà de ta machine ou de ton LAN.

Pas sûr ? Commence sur l'offre gratuite de Gemini, puis change de fournisseur plus tard en modifiant un seul `id` dans ta configuration. Rien d'autre ne change.

## Les clés viennent de l'environnement

verbatra ne lit jamais une clé d'API depuis la configuration. Chaque fournisseur hébergé lit exactement une variable d'environnement :

| Id du fournisseur | Variable d'environnement |
| --- | --- |
| `anthropic` | `ANTHROPIC_API_KEY` |
| `openai` | `OPENAI_API_KEY` |
| `gemini` | `GEMINI_API_KEY` |
| `deepl` | `DEEPL_API_KEY` |
| `google-translate` | `GOOGLE_TRANSLATE_API_KEY` |

Définis la variable dans `.env` (que `verbatra init` ajoute au `.gitignore`) ou exporte-la dans ton shell ou le coffre de secrets de ta CI. Quand la variable est absente ou vide, le fournisseur échoue avec une erreur structurée `MISSING_API_KEY` dont le message nomme la variable mais n'inclut jamais une valeur de clé. Ne commite jamais une vraie clé.

`openai-compatible` est différent : la plupart des serveurs locaux n'ont besoin d'aucune clé, donc il n'est pas dans ce tableau. Voir sa propre section plus bas pour le fonctionnement de sa résolution de clé.

## Anthropic

```ts
provider: {
  id: "anthropic",
  options: {
    model: "claude-sonnet-4-6", // example model id
    maxTokens: 4096,
  },
}
```

Lit `ANTHROPIC_API_KEY`. `model` et `maxTokens` sont tous deux requis. `maxTokens` plafonne les tokens qu'une seule réponse peut produire ; c'est l'option de limite de tokens de sortie de ce fournisseur (les autres l'appellent `maxOutputTokens`). Le `requestTimeoutMs` optionnel est aussi accepté ; voir [Délai de requête](#délai-de-requête).

## OpenAI

```ts
provider: {
  id: "openai",
  options: {
    model: "gpt-5.4-mini", // example model id
    maxOutputTokens: 4096,
  },
}
```

Lit `OPENAI_API_KEY`. `model` et `maxOutputTokens` sont tous deux requis. Le `requestTimeoutMs` optionnel est aussi accepté ; voir [Délai de requête](#délai-de-requête).

## Gemini

```ts
provider: {
  id: "gemini",
  options: {
    model: "gemini-2.5-flash", // example model id
    maxOutputTokens: 4096,
  },
}
```

Lit `GEMINI_API_KEY`. `model` et `maxOutputTokens` sont tous deux requis. Le `requestTimeoutMs` optionnel est aussi accepté ; voir [Délai de requête](#délai-de-requête).

<Callout title="L'offre gratuite et ses limites">
Gemini est le point de départ recommandé pour les petits projets parce que son API a une offre gratuite. Crée une clé sur [Google AI Studio](https://aistudio.google.com/apikey), sans facturation requise. L'offre gratuite plafonne les requêtes par minute et par jour (les chiffres exacts dépendent du modèle et changent avec le temps, donc vérifie les limites actuelles de Google), et verbatra découpe le travail en sous-lots séquentiels, donc une première exécution sur beaucoup de locales peut atteindre ces plafonds. Une brève limite de débit ou erreur serveur est retentée automatiquement avec un court backoff, mais cela ne lisse que des accrocs momentanés, pas un plafond durable. Si tu atteins le plafond, traduis une locale à la fois ou baisse `maxBatchSize`, puis relance : verbatra ne reprend que ce qui manque encore, donc les exécutions peuvent être répétées sans risque.
</Callout>

## DeepL

```ts
provider: {
  id: "deepl",
  options: {},
}
```

Lit `DEEPL_API_KEY`. DeepL est une API de traduction automatique, pas un LLM : il n'a pas de champ `model` et pas de limite de tokens de sortie. Il prend deux options facultatives : `glossaryId`, qui nomme un glossaire que tu as déjà créé dans DeepL, et `requestTimeoutMs` (voir [Délai de requête](#délai-de-requête)) :

```ts
provider: {
  id: "deepl",
  options: {
    glossaryId: "<your-glossary-id>",
  },
}
```

DeepL se dégrade en douceur au lieu d'échouer quand il ne peut pas honorer un réglage, et rapporte chaque dégradation comme un avis sur l'exécution :

- Une carte de termes `glossary` configurée n'est pas appliquée (DeepL n'utilise qu'un id de glossaire pré-créé), rapporté comme `GLOSSARY_IGNORED`.
- `tone` se mappe sur la formalité de DeepL : `formal` devient plus formel, `informal` devient moins formel, `neutral` ou un ton absent est omis. Sur une clé de l'offre gratuite, la formalité n'est pas prise en charge, donc un ton non par défaut se dégrade vers le défaut, rapporté comme `FORMALITY_DOWNGRADED`.

<Callout title="DeepL et les placeholders">
DeepL ne peut pas préserver les placeholders ni les jetons ICU, donc il n'envoie pas les chaînes qui en contiennent : ces entrées sont retenues (laissées non traduites) et rapportées avec un avis `PLACEHOLDER_UNSUPPORTED`. Les chaînes sans placeholder se traduisent normalement. Pour traduire des chaînes portant des placeholders, utilise un fournisseur LLM (Anthropic, OpenAI, Gemini ou openai-compatible).
</Callout>

## Google Cloud Translation

<AvailableFrom version="0.10.0" />

```ts
provider: {
  id: "google-translate",
  options: {},
}
```

Lit `GOOGLE_TRANSLATE_API_KEY`. Comme DeepL, Google Cloud Translation est une API de traduction automatique, pas un LLM : il n'a pas de champ `model`, pas de limite de tokens de sortie, et pas d'option de glossaire en v1. Il prend une option facultative, `requestTimeoutMs` (voir [Délai de requête](#délai-de-requête)).

Ce fournisseur vise le niveau Basic (v2) de Cloud Translation, authentifié avec une simple clé d'API d'un projet Google Cloud où l'API Cloud Translation est activée. Il n'utilise pas le niveau Advanced (v3), qui s'authentifie avec un compte de service ou des Application Default Credentials plutôt qu'une seule variable d'environnement, et qui ne rentre donc pas dans la règle de verbatra limitant les clés à une variable d'environnement.

Cloud Translation n'a ni réglage de formalité ni glossaire générique au niveau Basic, donc un `tone` ou un `glossary` configuré n'est jamais appliqué. Chacun est rapporté comme un avis plutôt que discrètement ignoré :

- `tone` rapporte toujours `FORMALITY_DOWNGRADED` quand il est défini à `formal` ou `informal` ; `neutral` ou un ton absent est omis.
- Une carte de termes `glossary` fournie rapporte toujours `GLOSSARY_IGNORED`.

<Callout title="Google Cloud Translation et les placeholders">
Comme DeepL, Google Cloud Translation ne peut pas préserver les placeholders ni les jetons ICU, donc il n'envoie pas les chaînes qui en contiennent : ces entrées sont retenues (laissées non traduites) et rapportées avec un avis `PLACEHOLDER_UNSUPPORTED`. Les chaînes sans placeholder se traduisent normalement. Pour traduire des chaînes portant des placeholders, utilise un fournisseur LLM (Anthropic, OpenAI, Gemini ou openai-compatible).
</Callout>

<Callout title="Google Cloud Translation et les codes de locale">
Les codes de locale sont validés comme du BCP-47 bien formé avant tout appel réseau (par exemple `en` ou `pt-BR`) ; un code malformé comme `en_US` échoue avec `INVALID_REQUEST` en nommant le code fautif. Contrairement à DeepL, Cloud Translation autorise librement les codes de destination régionaux, donc cette vérification ne porte que sur la syntaxe, pas sur une liste fixe autorisée. Une locale de destination ou une paire de langues que l'API de Google elle-même ne prend pas en charge échoue quand même comme `INVALID_REQUEST` structuré une fois que la requête atteint Google.
</Callout>

## openai-compatible

Pointe verbatra vers un serveur qui parle l'API Chat Completions d'OpenAI : LM Studio, Ollama, vLLM et similaires fonctionnent tous. L'id nomme le protocole réseau, pas l'endroit où le serveur tourne, donc une API hébergée qui parle le même protocole rentre ici aussi.

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct", // example: whatever your server exposes
    maxOutputTokens: 1024,
  },
}
```

`baseUrl`, `model` et `maxOutputTokens` sont requis. Contrairement à tout autre fournisseur, `baseUrl` vit dans la configuration plutôt que dans l'environnement : c'est une adresse réseau que tu connais déjà (une IP LAN ou `localhost`), pas un secret. Elle doit être une URL absolue valide avec le schéma `http` ou `https` ; tout le reste, y compris un schéma manquant, fait échouer la validation de la configuration immédiatement.

`baseUrl` doit inclure le segment de chemin d'API de ton serveur, typiquement `/v1` : LM Studio, Ollama et vLLM servent tous leurs routes compatibles OpenAI sous `/v1`. Un `baseUrl` sans lui reste une URL syntaxiquement valide, donc il passe la validation de configuration et échoue à la place au moment de la requête en atteignant le mauvais chemin.

Une API hébergée qui parle le même protocole fonctionne de la même façon. L'API de chat completions de Mistral en est un exemple :

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "https://api.mistral.ai/v1",
    model: "mistral-large-latest", // example: check Mistral's current model list
    maxOutputTokens: 4096,
    apiKeyEnvVar: "MISTRAL_API_KEY",
  },
}
```

`apiKeyEnvVar` nomme la variable d'environnement contenant ta clé pour ce serveur. C'est le même fournisseur `openai-compatible` pointé vers un autre point d'accès, pas un fournisseur Mistral dédié. Le `requestTimeoutMs` optionnel est accepté ici aussi, et c'est pour ce fournisseur qu'il compte le plus : voir [Délai de requête](#délai-de-requête).

### Les clés sont optionnelles

La plupart des serveurs d'inférence locaux n'ont besoin d'aucune clé d'API, donc `openai-compatible` résout sa clé en trois niveaux, dans l'ordre :

1. **`apiKeyEnvVar`**, un champ de configuration optionnel nommant une variable d'environnement où lire une vraie clé. Si tu définis ce champ et que la variable nommée est absente ou vide, verbatra échoue avec `MISSING_API_KEY` au lieu de retomber en silence, puisque tu as explicitement dit qu'une clé est requise.
2. **`OPENAI_COMPATIBLE_API_KEY`**, une variable d'environnement de convention, lue quand `apiKeyEnvVar` n'est pas défini. Si elle est définie et non vide, verbatra l'utilise ; sinon, verbatra continue sans erreur.
3. **Le placeholder `"local"`**, envoyé quand aucun des deux niveaux ci-dessus ne résout quoi que ce soit. C'est une chaîne fixe, non secrète, pas une vraie clé, et c'est exactement ce qui fait qu'un serveur local sans clé fonctionne sans aucune configuration.

`apiKeyEnvVar` ne peut jamais nommer `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` ou `DEEPL_API_KEY` : la validation de configuration rejette ça d'emblée, donc une configuration ne peut pas pointer ce fournisseur vers la clé d'un fournisseur hébergé par son nom. Le client ne lit jamais non plus `OPENAI_API_KEY` lui-même et passe toujours une valeur de clé explicite au SDK sous-jacent, donc une clé hébergée ne peut jamais atteindre un `baseUrl` personnalisé.

<Callout type="warn" title="Une vraie clé sur du http en clair voyage en clair">
verbatra autorise le `http://` en clair vers n'importe quel hôte, y compris une adresse LAN, sans restriction au-delà du schéma http ou https. C'est intentionnel et sûr dans le cas courant sans clé : rien de secret ne circule sur le réseau.

C'est un vrai risque seulement quand tu configures aussi une clé (via `apiKeyEnvVar` ou `OPENAI_COMPATIBLE_API_KEY`) **et** que `baseUrl` est du `http://` en clair vers un hôte non loopback : cette clé voyage alors sur ton réseau sans chiffrement. Si ton serveur exige une vraie clé et est joignable au-delà de localhost, utilise `https://` pour lui. verbatra ne détecte pas cette combinaison et n'avertit pas à son sujet aujourd'hui ; traite-la comme ta propre responsabilité.
</Callout>

### Choisir un modèle local

Préfère un modèle ajusté par instructions, sans raisonnement et avec une bonne couverture multilingue. verbatra demande un unique objet JSON strict et le valide, donc tu veux un modèle qui suit de façon fiable les consignes de format. `qwen2.5-14b-instruct` est un choix par défaut raisonnable ; prends le plus grand modèle de ce type que ton matériel exécute bien.

<Callout type="warn" title="Évite les modèles de raisonnement et fortement quantifiés">
Les modèles de raisonnement (thinking) et les builds fortement quantifiés (qat ou à faible nombre de bits) sont ici les sources d'échec habituelles : ils ont tendance à émettre de la prose de raisonnement autour de la réponse ou à renvoyer du JSON tronqué, et l'un comme l'autre fait échouer les contrôles de schéma et d'intégrité de verbatra. Si un modèle capable de raisonnement est inévitable, donne-lui de la place pour raisonner et répondre : voir [Limites de tokens de sortie](#limites-de-tokens-de-sortie) pour l'ajustement de `maxOutputTokens` et `maxBatchSize`.
</Callout>

Un mauvais modèle local échoue bruyamment, pas en silence : verbatra valide chaque réponse du fournisseur contre un schéma canonique et la passe par les contrôles d'intégrité, donc un modèle qui émet de la prose de raisonnement ou du JSON tronqué est rejeté avec une erreur `INVALID_RESPONSE` ou `OUTPUT_TRUNCATED` au lieu d'écrire une traduction corrompue.

### Analyse tolérante pour les modèles locaux et plus petits

`openai-compatible` demande le même format de réponse strict et contraint par schéma que le fournisseur hébergé `openai`. La seule différence est au retour : les modèles locaux et plus petits ont plus tendance à envelopper une réponse par ailleurs correcte dans de la prose ou une clôture de code Markdown malgré la consigne contraire, donc `openai-compatible` extrait le premier objet JSON équilibré n'importe où dans la réponse avant l'analyse, là où le fournisseur hébergé ne le fait pas. Sa sortie passe quand même par exactement la même validation de schéma et les mêmes contrôles d'intégrité que tout autre fournisseur : la sortie d'un modèle local est une entrée non fiable, et une réponse malformée ou aux placeholders discordants est rejetée de la même façon.

<Callout title="Pas dans verbatra init">
`verbatra init` ne propose pas `openai-compatible` comme option de génération, puisqu'il n'a pas une unique variable d'environnement requise à demander. Ajoute le bloc de fournisseur ci-dessus à ta configuration à la main ; tout le reste de cette page (glossaire, ton, limites de tokens de sortie) s'applique à lui comme à tout fournisseur LLM.
</Callout>

## Ton et glossaire selon les fournisseurs

Les champs de configuration optionnels `tone` et `glossary` (voir [Fichier de configuration](/docs/config-file)) sont appliqués par fournisseur :

- **Ton.** Les fournisseurs LLM (Anthropic, OpenAI, Gemini et openai-compatible) reçoivent le ton avec la requête et ont pour instruction de le respecter. DeepL le mappe sur la formalité, avec la dégradation de l'offre gratuite décrite plus haut. Google Cloud Translation n'a aucun contrôle de formalité, donc un ton non neutre rapporte toujours `FORMALITY_DOWNGRADED`.
- **Glossaire.** Les fournisseurs LLM reçoivent la carte de termes et ont pour instruction de traiter ses termes comme contraignants. DeepL ignore une carte de termes (avec un avis `GLOSSARY_IGNORED`) et applique uniquement son `glossaryId` natif. Google Cloud Translation n'a aucun glossaire en v1, donc une carte de termes fournie rapporte toujours `GLOSSARY_IGNORED`.

## Comportement partagé par chaque fournisseur

### Découpage en lots

Le travail d'une locale est découpé en sous-lots séquentiels d'au plus `maxBatchSize` entrées (50 par défaut ; voir [Fichier de configuration](/docs/config-file)), pour qu'une requête trop grosse ne puisse pas faire échouer toute la locale. Un sous-lot échoué est retenu et retenté automatiquement à l'exécution suivante pendant que les autres sous-lots avancent quand même. DeepL et Google Cloud Translation découpent en plus un sous-lot en autant de requêtes que leurs propres plafonds par requête l'exigent, de façon transparente.

### Nouvelles tentatives

Les échecs transitoires (une réponse de limite de débit ou une erreur serveur) sont retentés automatiquement avec un court backoff : les clients SDK d'OpenAI, d'Anthropic et de DeepL retentent par défaut, et verbatra ajoute une nouvelle tentative équivalente de son cru pour Gemini, dont le SDK ne le fait pas. Les nouvelles tentatives lissent des accrocs momentanés ; un échec durable remonte quand même comme une erreur structurée. Google Cloud Translation n'a aucune nouvelle tentative aujourd'hui, à aucun niveau : une réponse de limite de débit ou d'erreur serveur remonte immédiatement comme `RATE_LIMITED` ou `PROVIDER_UNAVAILABLE`, et le comportement habituel de reprise d'un sous-lot retenu à l'exécution suivante s'applique quand même.

### Délai de requête

Chaque fournisseur borne chaque requête sortante, pour qu'un serveur qui accepte la connexion mais ne répond jamais ne puisse pas bloquer une exécution ni garder ouvert le verrou d'écriture d'une locale. Cette borne, c'est `requestTimeoutMs`, un entier positif facultatif en millisecondes accepté dans les `options` des six fournisseurs (`anthropic`, `openai`, `gemini`, `deepl`, `google-translate` et `openai-compatible`) :

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct",
    maxOutputTokens: 1024,
    requestTimeoutMs: 300000, // 5 minutes
  },
}
```

Si tu l'omets, verbatra applique sa propre valeur par défaut de `120000` ms (deux minutes) : assez longue pour ne pas couper un gros lot légitimement lent, assez courte pour qu'un serveur figé mais vivant ne bloque pas une locale indéfiniment. Augmente-la quand un modèle local lent ou un gros `maxBatchSize` demande plus de temps ; baisse-la pour échouer plus vite. Quand la borne est atteinte, cette requête échoue avec le code réessayable `TIMEOUT` et seul son propre sous-lot est touché : les clés reviennent à l'exécution suivante.

DeepL est la seule exception à l'annulation : son client ne peut pas interrompre une requête déjà en vol, donc au délai dépassé verbatra cesse d'attendre et poursuit, mais la requête déjà envoyée va à son terme chez DeepL. Google Cloud Translation, qui utilise une simple requête HTTP en interne, annule immédiatement au délai dépassé, comme tout autre fournisseur sauf DeepL.

### Erreurs structurées

Un échec de fournisseur ne remonte jamais comme une erreur SDK brute, qui pourrait porter des en-têtes de requête ou une clé. verbatra classe chaque échec selon son statut HTTP ou sa classe d'erreur SDK et lève une erreur structurée avec un code stable et un message fixe, sans secret :

| Code | Signification |
| --- | --- |
| `MISSING_API_KEY` | La variable d'environnement requise est absente ou vide. Le message nomme la variable, jamais une valeur. |
| `INVALID_REQUEST` | La requête a échoué à la validation avant tout appel réseau : un champ malformé, un code de locale que DeepL n'accepte pas (un code source régional, ou un `en` ou `pt` nu en cible), ou un code de locale qui n'est pas du BCP-47 bien formé pour Google Cloud Translation. Corrige la configuration ou la requête ; réessayer n'aidera pas. |
| `RATE_LIMITED` | HTTP 429 ou une erreur de limite de débit du SDK. Pour Google Cloud Translation, cela couvre aussi un HTTP 403 dont le corps nomme un motif de quota (une limite quotidienne ou par minute), car l'API de Google réutilise le 403 à la fois pour les échecs de quota et d'identifiants. Attends et réessaie plus tard, ou augmente le quota Cloud Translation de ton projet. |
| `TIMEOUT` | Un délai réseau ou de requête dépassé ; aucune réponse n'est arrivée à temps. Réessayer peut aider, et [`requestTimeoutMs`](#délai-de-requête) relève la borne. |
| `AUTH_FAILED` | HTTP 401 ou 403 : la clé est invalide, révoquée ou sans permission. Pour Google Cloud Translation, vérifie que `GOOGLE_TRANSLATE_API_KEY` est une clé valide et sans restriction pour un projet où l'API Cloud Translation est activée. Réessayer n'aidera pas. |
| `PROVIDER_UNAVAILABLE` | HTTP 5xx : le fournisseur a échoué de son côté, et la requête elle-même n'a jamais été en cause. Les réessais des couches inférieures absorbent déjà un 5xx transitoire, donc un 5xx qui atteint ce code est une panne durable. Attends et réessaie plus tard. |
| `OUTPUT_TRUNCATED` | Le modèle a atteint sa limite de tokens de sortie ; voir plus bas. |
| `INVALID_RESPONSE` | La sortie était malformée, incomplète, ou a échoué à la réconciliation avec la requête. |
| `PROVIDER_REFUSED` | Le modèle a refusé de répondre. |
| `PROVIDER_BLOCKED` | La requête ou la réponse a été bloquée ou filtrée pour raison de sécurité. |
| `PROVIDER_ERROR` | Tout ce qui est inclassable. Quand l'échec est un problème de transport reconnaissable, le message le nomme (connexion refusée, nom d'hôte non résolu, connexion fermée, hôte injoignable, certificat TLS non vérifié) et dit quoi vérifier ; sinon il se replie sur un message statique sans secret. |

Un échec n'affecte que son propre sous-lot : les clés échouées sont retenues et reprises à l'exécution suivante.

Pour `openai-compatible`, un `PROVIDER_ERROR` nomme en plus l'hôte et le port du `baseUrl` configuré, puisqu'un point d'accès que tu héberges toi-même est justement celui qui devient injoignable : `The translation provider request to localhost:11434 failed: the connection was refused. Check that the endpoint is running and that the configured host and port are right, then run again.` Seule la composante hôte de l'URL est utilisée, donc un chemin, une requête ou des informations d'utilisateur présents dans `baseUrl` n'atteignent jamais un message. Google Cloud Translation rapporte de la même façon contre son hôte fixe, `translation.googleapis.com` ; la chaîne de requête portant la clé d'API n'atteint jamais non plus un message.

### Limites de tokens de sortie

Les quatre fournisseurs LLM plafonnent le nombre de tokens qu'une seule réponse peut produire. Quand un modèle s'arrête parce qu'il a atteint ce plafond, verbatra lève `OUTPUT_TRUNCATED` au lieu d'un échec générique de réponse malformée, avec un message fixe :

> The provider stopped because the output-token limit was reached. Reduce the batch size or raise the configured max output tokens.

Chacun des deux leviers le résout : baisse `maxBatchSize` dans ta configuration pour que chaque requête produise une réponse plus petite, ou augmente le plafond par réponse du fournisseur (`maxTokens` pour Anthropic, `maxOutputTokens` pour OpenAI, Gemini et openai-compatible). DeepL et Google Cloud Translation ne sont pas concernés : ni l'un ni l'autre n'a de cas de troncature de tokens de sortie. verbatra se rétablit aussi de lui-même : quand un sous-lot est tronqué, il le redivise en moitiés et réessaie, en descendant jusqu'à une seule entrée, de sorte que les clés qui tiennent dans une requête plus petite sont quand même traduites et que seule une entrée isolée qui déborde encore est retenue pour la prochaine exécution.

<Callout title="Les modèles de raisonnement puisent dans le même budget">
Un modèle de raisonnement (thinking) puise ses tokens de raisonnement cachés dans le même budget de tokens de sortie que celui qu'il utilise pour émettre les traductions JSON. Il peut épuiser ce budget rien qu'en raisonnant et s'arrêter avant d'écrire la moindre sortie, ce qui se manifeste par `OUTPUT_TRUNCATED`. Si tu utilises un modèle de raisonnement, donne-lui de la marge : préfère un `maxOutputTokens` plus élevé (`maxTokens` pour Anthropic) ou un `maxBatchSize` plus petit pour que chaque requête ait de la place à la fois pour le raisonnement et pour la réponse.
</Callout>

### Signalements de révision

Les traductions acceptées de chaque fournisseur passent par les mêmes contrôles post-traduction, et un résultat suspect (par exemple un résultat identique à sa source, ou qui a manqué un terme de glossaire) est signalé dans la file de révision plutôt que rejeté. Les codes de raison et la façon de traiter la file sont couverts dans [Sûreté de la traduction](/docs/translation-safety) et [Réviser les traductions dans Studio](/docs/review-in-studio).
