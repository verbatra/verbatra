description: Cada clave de configuración con su tipo, valor por defecto y restricciones, más el orden de descubrimiento y qué pasa cuando la validación falla.
---
verbatra lee un único objeto de configuración pequeño y sin secretos, y lo valida antes de hacer ningún trabajo. Esta página es la referencia completa: cada clave, dónde puede vivir el archivo y cómo falla una configuración mala.

<Callout title="Las claves vienen del entorno">
Ninguna clave de API se lee jamás de este archivo. Cada proveedor lee su clave de una variable de entorno, así que la configuración es segura de confirmar. Consulta [Proveedores](/docs/providers).
</Callout>

## Una configuración mínima

```ts
import { defineConfig } from "@verbatra/sdk";

export default defineConfig({
  sourceLocale: "en",
  targetLocales: ["de", "fr"],
  format: "i18next-json",
  files: {
    pattern: "locales/{locale}.json",
  },
  provider: {
    id: "gemini",
    options: {
      model: "gemini-2.5-flash", // example model id; use your provider's current one
      maxOutputTokens: 4096,
    },
  },
});
```

`defineConfig` es un helper de identidad de `@verbatra/sdk`. Devuelve su argumento sin cambios y existe solo para darte inferencia de tipos y autocompletado en el editor.

<Callout title="Autocompletado de modelos en TypeScript">
Cuando escribes la configuración en TypeScript, tu editor ofrece para `options.model` los IDs de modelo conocidos del proveedor seleccionado, acotados por el `id` de proveedor que elegiste. La lista viene del propio SDK de ese proveedor, así que se mantiene al día con la versión del SDK que tengas instalada, y un modelo de otro proveedor (por ejemplo un modelo de Claude bajo `id: "gemini"`) es un error de tipos. Es solo una ayuda de escritura: en tiempo de ejecución `model` se valida como una cadena no vacía, así que un modelo recién salido que el SDK aún no lista sigue funcionando aunque el editor lo marque. DeepL no tiene campo `model`, y el `model` de openai-compatible es lo que exponga tu servidor, así que ninguno de los dos está restringido.
</Callout>

## Cada clave

| Clave | Tipo | Por defecto | Propósito |
| --- | --- | --- | --- |
| `sourceLocale` | string | obligatoria | El locale en el que están escritas tus cadenas de origen. |
| `targetLocales` | array de strings | obligatoria | Los locales a los que traducir. |
| `format` | string | obligatoria | El adaptador de formato de tus archivos de locale. |
| `files.pattern` | string | obligatoria | La ruta de cada archivo de locale, con un token `{locale}`. |
| `files.localeStyle` | `"literal"`, `"posix"` o `"android"` | `"literal"` | Cómo se escribe el token `{locale}` para cada locale. |
| `provider` | objeto | obligatoria | El proveedor de traducción, seleccionado por `id`. |
| `glossary` | objeto o string | ninguno | Términos de origen a términos de destino preferidos, en línea o como ruta a un archivo JSON. |
| `tone` | `"formal"`, `"informal"` o `"neutral"` | ninguno | El registro que deben usar las traducciones. |
| `prune` | boolean | `false` | Elimina las claves huérfanas de los archivos de destino y del bloqueo. |
| `generatePlurals` | boolean | `false` | Sintetiza las formas plurales CLDR que necesita un idioma de destino. |
| `maxBatchSize` | entero positivo | `50` | El máximo de entradas enviadas en una sola solicitud al proveedor. |
| `maxTokens` | entero positivo | ninguno | Un presupuesto de tokens para toda la ejecución, a través de todas las llamadas al proveedor. |
| `budgetBehavior` | `"warn"` o `"stop"` | `"warn"` | Qué pasa una vez alcanzado `maxTokens`. |
| `$schema` | string | ninguno | Un puntero al documento JSON Schema, solo para editores. Se ignora en tiempo de ejecución. |

Las claves de nivel superior desconocidas se rechazan, con `$schema` como única excepción. Por eso mismo una clave de API no puede vivir en la configuración: las claves vienen del entorno, no del archivo.

<AvailableFrom version="0.9.0" />

### Locales y archivos

- **`sourceLocale`** debe ser una cadena no vacía.
- **`targetLocales`** debe contener al menos un locale, no debe incluir `sourceLocale`, y dos entradas no pueden ser iguales sin distinguir mayúsculas de minúsculas (por ejemplo `["de", "DE"]` se rechaza), porque cada locale se convierte en el nombre de su propia hoja de Excel al exportar.
- **`format`** es uno de `i18next-json`, `vue-i18n-json`, `next-intl-json`, `ngx-translate-json`, `xliff`, `yaml`, `arb`, `properties`, `apple-strings`, `apple-xcstrings`, `android-xml` o `gettext-po`. Consulta [Formatos](/docs/formats).
- **`files.pattern`** debe contener el token `{locale}`, que verbatra reemplaza con cada locale: `locales/{locale}.json` se resuelve a `locales/de.json`. Las rutas se resuelven contra el directorio de trabajo. El patrón es una ruta literal, no un glob, y `{locale}` es el único token que entiende, así que una configuración direcciona exactamente un archivo por locale. Si tu proyecto reparte sus cadenas entre varios archivos de namespace por locale, mira [Diseños con namespaces](/docs/formats#diseños-con-namespaces). La única excepción es `apple-xcstrings`, donde todos los locales comparten un único archivo de catálogo: el token sigue siendo obligatorio en el patrón, pero se resuelve a la misma ruta sin importar el locale. Consulta [Xcode String Catalogs](/docs/formats#xcode-string-catalogs-xcstrings).
- **`files.localeStyle`** decide en qué se expande el token:
  - `literal`, el valor por defecto, usa la etiqueta configurada tal cual, que es lo que necesitan
    los diseños JSON, YAML, XLIFF, ARB, properties y `.lproj` de Apple.
  - `posix` reemplaza `-` por `_`, para gettext (`locale/pt_BR/LC_MESSAGES/messages.po`) y el
    diseño Java `messages_{locale}.properties`.
  - `android` expande el token a un directorio de recursos completo de Android, escrito como
    `res/{locale}/strings.xml`: `values` para el locale de origen, y luego `values-de`,
    `values-pt-rBR` y `values-b+zh+Hans`.

  Un estilo rechaza un locale que no puede escribir correctamente para ese estilo, en lugar de
  escribir un directorio que la plataforma ignoraría en silencio.

### provider

Un objeto seleccionado por `id`: `anthropic`, `openai`, `gemini`, `deepl` u `openai-compatible`. Cada proveedor toma sus propias `options` (modelo, límite de tokens y campos específicos del proveedor), y las claves de opción desconocidas se rechazan. Las opciones por proveedor están documentadas en [Proveedores](/docs/providers).

### glossary

Un mapa de términos de origen a términos de destino preferidos, en línea o como ruta a un archivo JSON con la misma forma (un objeto plano de claves string a valores string):

```ts
export default defineConfig({
  // ...
  glossary: {
    "Sign in": "Anmelden",
  },
  // or: glossary: "glossary.json",
});
```

Las dos formas son mutuamente excluyentes; no hay fusión entre ellas. Una ruta de archivo relativa se resuelve contra el directorio del archivo de configuración cargado, o contra el directorio de trabajo cuando la configuración se pasa como override en memoria. El archivo debe estar codificado en UTF-8 y no superar 1 MiB, y se lee una vez cuando la configuración carga: verbatra no lo vigila en busca de cambios, así que edítalo y reinicia para recoger una actualización. Un archivo ausente, JSON inválido o un valor que no sea un mapa plano de strings hace fallar la carga de la configuración con `CONFIG_INVALID`, nombrando la ruta resuelta.

<AvailableFrom version="0.4.0" pkg="@verbatra/studio" />

Las dos formas también se diferencian en quién puede cambiarlas. Solo la forma de archivo se puede editar desde [Verbatra Studio](/docs/review-in-studio), que reescribe ese archivo JSON término a término y nunca toca tu módulo de configuración; un glosario en línea se queda de solo lectura allí, porque vive dentro de código ejecutable. Prefiere la forma de archivo si quieres gestionar los términos desde el panel.

Cómo se aplica el glosario depende del proveedor: los proveedores LLM reciben el mapa resuelto con la solicitud y se les instruye para tratar sus términos como vinculantes, mientras que DeepL ignora un mapa de términos y aplica en su lugar un glosario configurado por id. Consulta [Proveedores](/docs/providers).

### tone

Uno de `"formal"`, `"informal"` o `"neutral"`. Los proveedores LLM lo reciben con la solicitud y se les instruye para respetarlo; DeepL lo asigna a su ajuste de formalidad. Consulta [Proveedores](/docs/providers) para los detalles por proveedor, incluida la degradación del nivel gratuito de DeepL.

### prune

Desactivado por defecto. Cuando es true, las claves presentes en un archivo de destino pero ausentes del origen (las claves huérfanas del diff) se eliminan del archivo escrito y de [el archivo de bloqueo](/docs/the-lock-file). Solo se eliminan claves huérfanas, nunca otra cosa. Una opción `prune` por ejecución en `translate` (la opción `--prune` de la CLI) tiene prioridad sobre el valor de la configuración.

### generatePlurals

Desactivado por defecto. Cuando es true, verbatra sintetiza las formas plurales CLDR que un idioma de destino requiere pero el origen no aporta (por ejemplo few y many en polaco). Soportado solo para proyectos i18next-JSON traducidos por un proveedor LLM; DeepL, los formatos que no son i18next y los idiomas de destino desconocidos recurren al aviso de plurales por locale. No hay opción de CLI, así que defínelo en la configuración; la entrada de `translate()` del SDK acepta un override de `generatePlurals` por ejecución que tiene prioridad.

### maxBatchSize

Por defecto `50`. Las entradas faltantes más las modificadas de un locale se dividen en sublotes secuenciales que no superan este tamaño, así que una solicitud sobredimensionada al proveedor no puede hacer fallar el locale entero. Un sublote fallido se retiene y se reintenta en la siguiente ejecución mientras los demás siguen avanzando. Debe ser un entero positivo; los valores cero, negativos o fraccionarios se rechazan. Solo por configuración: no hay opción de CLI ni override por ejecución.

### maxTokens y budgetBehavior

`maxTokens` es un presupuesto de tokens para toda la ejecución: tokens de entrada más de salida, sumados a través de cada llamada al proveedor (traducción principal y generación de plurales por igual) y a través de cada locale de destino. Se comprueba después de cada sublote completado, nunca dentro de uno, así que el sublote cuya finalización cruza el techo ya fue enviado, se acepta con normalidad y sus tokens siguen contando: un tope blando a posteriori, no una comprobación previa dura. Solo por configuración, sin opción de CLI.

`budgetBehavior` decide qué pasa una vez alcanzado el techo:

- `"warn"` (el valor por defecto) señala el exceso y deja que la ejecución continúe exactamente como si no hubiera presupuesto configurado.
- `"stop"` retiene cada clave aún no intentada durante el resto de la ejecución: las candidatas restantes del locale actual, y las candidatas de cada locale de destino posterior por completo (su diff y su informe de huérfanas siguen corriendo; solo se salta la llamada al proveedor). Las claves retenidas conservan su hash anterior en el bloqueo y se reintentan automáticamente en la siguiente ejecución, igual que ya lo hace una llamada al proveedor fallida.

Definir `maxTokens` también limita cómo se puede paralelizar una ejecución: una ejecución real que lo combine con `--concurrency` por encima de `1` se rechaza con código de salida `2` (`CONCURRENCY_BUDGET_CONFLICT`) antes de cualquier llamada al proveedor. La razón: locales que se traducen a la vez no pueden compartir un mismo presupuesto de tokens de forma fiable, así que verbatra rechaza en lugar de arriesgarse a un tope inexacto. Una ejecución en seco queda exenta. Quita el presupuesto o deja la concurrencia en `1`.

Con `"warn"`, que el presupuesto salte nunca cambia el código de salida del comando. Con `"stop"` sí puede: un locale cuyas claves se retuvieron se informa como `partial` cuando algunas claves sí llegaron y como `failed` cuando no llegó ninguna, y ambos salen con `1`. `budgetBehavior` sin `maxTokens` se acepta y no tiene efecto. Contra un proveedor sin tokens (DeepL, que no informa de uso que medir) la salvaguarda se declara inerte (`supported: false` en el `budget` del resumen de la ejecución) en lugar de producir un salto falso.

<Callout title="Dos maxTokens distintos">
El `maxTokens` de nivel superior es el presupuesto de toda la ejecución descrito aquí. El proveedor Anthropic también tiene su propio `options.maxTokens`, que limita una sola respuesta. No tienen relación; consulta [Proveedores](/docs/providers).
</Callout>

## Orden de descubrimiento

verbatra busca hacia arriba desde el directorio de trabajo y usa la primera fuente que encuentra. Que haya varias fuentes presentes no es un error; gana la primera coincidencia. El orden de búsqueda es:

1. `package.json` (una propiedad `"verbatra"`)
2. `.verbatrarc`
3. `.verbatrarc.json`
4. `.verbatrarc.yaml`
5. `.verbatrarc.yml`
6. `.verbatrarc.js`
7. `.verbatrarc.cjs`
8. `.verbatrarc.ts`
9. `verbatra.config.js`
10. `verbatra.config.cjs`
11. `verbatra.config.ts`

Para cargar un archivo explícito en lugar de buscar, pasa `--config <path>`; una ruta relativa se resuelve contra el directorio de trabajo. En el SDK, un `configOverride` en memoria tiene prioridad sobre un `configPath` explícito, que a su vez tiene prioridad sobre la búsqueda. Consulta las [Recetas del SDK](/docs/programmatic-api).

## Validación en el editor

<AvailableFrom version="0.9.0" />

`@verbatra/sdk` publica el esquema de configuración como un documento JSON Schema, generado durante la compilación a partir del mismo esquema zod con el que valida el SDK, así que nunca puede describir una forma distinta de la que realmente se ejecuta. Una vez instalado queda en:

```
node_modules/@verbatra/sdk/dist/config-schema.json
```

Apunta tu editor a él y una configuración declarativa gana autocompletado de claves, comprobación de tipos y de valores de enumeración, y un aviso inmediato ante una clave mal escrita.

Hay que decirle al editor qué documento usar; nada se valida por sí solo. Hay dos formas de hacerlo.

**Una clave `$schema` dentro del archivo.** `.verbatrarc.json` y `.verbatrarc` aceptan una clave `$schema` de nivel superior, que verbatra admite e ignora:

```json
{
  "$schema": "./node_modules/@verbatra/sdk/dist/config-schema.json",
  "sourceLocale": "en",
  "targetLocales": ["de", "fr"],
  "format": "i18next-json",
  "files": { "pattern": "locales/{locale}.json" },
  "provider": { "id": "gemini", "options": { "model": "gemini-2.5-flash", "maxOutputTokens": 4096 } }
}
```

La clave `$schema` es una convención de los editores, no un requisito de la especificación JSON Schema: VS Code y los editores que siguen la misma convención la leen, y los demás no. `.verbatrarc` no tiene extensión, así que ahí el editor necesita además una entrada de correspondencia de archivos antes de tratar el archivo como JSON, por lo que la clave sola no basta.

**Una correspondencia explícita en el editor.** En VS Code, asocia los archivos en los ajustes del espacio de trabajo, lo que también cubre la forma sin extensión:

```json
{
  "json.schemas": [
    {
      "fileMatch": [".verbatrarc", ".verbatrarc.json"],
      "url": "./node_modules/@verbatra/sdk/dist/config-schema.json"
    }
  ]
}
```

Una configuración YAML (`.verbatrarc.yaml`, `.verbatrarc.yml`) lleva un comentario en vez de una clave, que lee el YAML Language Server:

```yaml
# yaml-language-server: $schema=./node_modules/@verbatra/sdk/dist/config-schema.json
sourceLocale: en
targetLocales: [de, fr]
```

Dos de los lugares de búsqueda no se pueden cubrir. La propiedad `"verbatra"` dentro de `package.json` no, porque `package.json` ya valida contra su propio esquema y no hay manera de asociar un segundo a una sola propiedad. Las formas ejecutables (`.verbatrarc.js`, `.verbatrarc.cjs`, `.verbatrarc.ts`, `verbatra.config.js`, `verbatra.config.cjs`, `verbatra.config.ts`) no lo necesitan: `defineConfig` les da el tipo `VerbatraConfigInput` completo, así que TypeScript ya las comprueba, y encima con el autocompletado de modelos acotado por proveedor.

### Lo que el documento no puede comprobar

El documento lleva cada clave, su tipo, sus valores de enumeración, qué claves son obligatorias, la regla del token `{locale}` en `files.pattern` y el rechazo de claves desconocidas. Tres reglas se aplican en tiempo de ejecución pero no tienen expresión en el borrador 2020-12 de JSON Schema, así que el editor calla sobre ellas y verbatra las reporta al cargar la configuración:

- `targetLocales` no debe incluir `sourceLocale`. Comparar dos valores hermanos no tiene vocabulario en el borrador.
- `targetLocales` no debe contener dos locales que solo difieran en mayúsculas y minúsculas.
- `provider.options.apiKeyEnvVar` (solo en openai-compatible) no debe nombrar la variable de entorno de un proveedor alojado. Expresarlo obligaría a fijar esos nombres de variable dentro de un documento publicado, que luego se separaría del código que los posee.

Esa es la lista completa. Una configuración que el editor muestra limpia todavía puede fallar por una de esas tres reglas, así que un editor en verde es una primera pasada rápida, no un sustituto de ejecutar `verbatra check`.

## El directorio de trabajo y .env

Ejecuta verbatra desde la raíz de tu proyecto, o pasa `--cwd` apuntando a ella. El directorio de trabajo es el ancla única de todo lo que verbatra resuelve: la búsqueda de configuración empieza ahí y sube, `.env.local` y `.env` se cargan desde ahí para `translate`, `watch`, `doctor` y `studio`, y la ruta de cada archivo de locale se resuelve contra él. Mantener las tres cosas en el mismo sitio es lo que hace que un simple `verbatra translate` funcione.

La precedencia del entorno es, de mayor a menor: una variable ya definida en tu entorno real, luego `.env.local`, luego `.env`. Una variable ya presente nunca se sobrescribe.

## Cuando la carga falla

La carga de la configuración falla con uno de dos códigos de error estructurados:

- **`CONFIG_NOT_FOUND`**: la búsqueda no encontró ninguna configuración en ninguno de los sitios de arriba, o la ruta explícita de `--config` no existe.
- **`CONFIG_INVALID`**: se encontró una configuración pero no se pudo usar. Esto cubre un archivo que no parsea, una configuración que falla la validación de esquema y una ruta de archivo de glosario que no se pudo resolver. El mensaje lista cada problema de validación con la ruta de su clave, y una clave de nivel superior no reconocida gana la pista de que las claves de API se leen del entorno, no de la configuración. Un error crudo del parser o del sistema de archivos nunca escapa.

La CLI informa de cualquiera de los dos fallos y sale con el código `2`, el código de salida de errores de frontera. Consulta [CI y códigos de salida](/docs/ci-and-exit-codes).
