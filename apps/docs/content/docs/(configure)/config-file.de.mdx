verbatra liest ein geheimnisfreies Konfigurationsobjekt und validiert es vor jeder Arbeit. Kein API-Schlüssel wird je daraus gelesen ([Provider](/docs/providers#keys-kommen-aus-der-umgebung)), die Konfiguration bleibt also gefahrlos committbar.

## Eine minimale Konfiguration

```ts title="verbatra.config.ts"
import { defineConfig } from "@verbatra/sdk";

export default defineConfig({
  sourceLocale: "en",
  targetLocales: ["de", "fr"],
  format: "i18next-json",
  files: {
    pattern: "locales/{locale}.json",
  },
  provider: {
    id: "gemini",
    options: {
      model: "gemini-2.5-flash", // example model id; use your provider's current one
      maxOutputTokens: 4096,
    },
  },
});
```

`defineConfig` gibt sein Argument unverändert zurück und typisiert es nur: `options.model` vervollständigt die Modell-IDs des gewählten Providers, während zur Laufzeit jeder nicht-leere String akzeptiert wird.

## Jeder Key

Unbekannte Keys werden auf jeder Ebene außer `$schema` abgelehnt. Genau deshalb kann auch kein API-Schlüssel in der Konfiguration leben.

| Key | Typ | Default | Seit | Wirkung |
| --- | --- | --- | --- | --- |
| `$schema` | String | keiner | 0.9.0 | Zeigt einem Editor das [JSON-Schema](#validierung-im-editor); zur Laufzeit ignoriert. |
| `sourceLocale` | Locale-Code | erforderlich | 0.1.0 | Die Locale, in der deine Quellstrings geschrieben sind. |
| `targetLocales` | Array von Locale-Codes | erforderlich | 0.1.0 | Mindestens eine; nie `sourceLocale`, nie zwei, die sich nur in der Groß- und Kleinschreibung unterscheiden. |
| `format` | Format-Id | erforderlich | 0.1.0 | Das [Format](/docs/formats) deiner Locale-Dateien, oder eine `custom:`-Id für einen [Adapter von außerhalb](/docs/custom-format-adapters). |
| `files.pattern` | String | erforderlich | 0.1.0 | Der Pfad zu jeder Locale-Datei, mit einem `{locale}`-Token. |
| `files.localeStyle` | `"literal"`, `"posix"`, `"android"` | `"literal"` | 0.7.0 | Wie `{locale}` im Pfad geschrieben wird. |
| `provider.id` | Provider-Id | erforderlich | 0.1.0 | Der Übersetzungs-Provider, oder `none` für keine maschinelle Übersetzung. |
| `provider.options` | Objekt | erforderlich, außer bei `none` | 0.1.0 | Die eigenen Optionen des Providers, pro Provider aufgeführt unter [Provider](/docs/providers). |
| `glossary` | Objekt oder Dateipfad | keines | 0.1.0 | Feste Übersetzungen, verbotene Wiedergaben und Begriffe, die unübersetzt bleiben. |
| `tone` | `"formal"`, `"informal"`, `"neutral"` | keiner | 0.1.0 | Das Register, in dem übersetzt wird, angewendet [pro Provider](/docs/providers#tonfall-und-glossar-über-die-provider-hinweg). |
| `prune` | Boolean | `false` | 0.3.0 | Entfernt verwaiste Keys aus Zieldateien und der Lock-Datei; `translate --prune` überschreibt es. |
| `generatePlurals` | Boolean | `false` | 0.3.0 | Synthetisiert die CLDR-Pluralformen, die eine Zielsprache braucht. |
| `fuzzyCache.enabled` | Boolean | im Block erforderlich | 0.11.0 | Verwendet die Übersetzung eines nur leicht geänderten Quellstrings wieder. |
| `fuzzyCache.threshold` | Zahl, `0.5` bis `1` | `0.9` | 0.11.0 | Wie ähnlich alte und neue Quelle für eine Wiederverwendung sein müssen. |
| `humanEdits` | `"protect"`, `"suggest"`, `"overwrite"` | `"protect"` | 0.12.0 | Was ein Lauf mit einem veralteten Key macht, den ein Mensch geschrieben hat. |
| `pinnedKeys` | String-Array | keiner | 0.12.0 | Key-Muster (`*` passt auf eine beliebige Zeichenfolge), die kein maschineller Schreibvorgang je anfasst. |
| `network.policy` | `"any"`, `"local-only"`, `"allowlist"` | `"any"` | 0.12.0 | Zu welchen Hosts sich ein Provider verbinden darf. Siehe [Netzwerkzugriff einschränken](/docs/network-policy). |
| `network.allowedHosts` | String-Array | keiner; bei `"allowlist"` erforderlich | 0.12.0 | Zusätzlich erlaubte Hosts: Namen, `*.suffix`-Platzhalter, IPs oder CIDR-Bereiche. |
| `sensitiveData.mode` | `"off"`, `"warn"`, `"block"`, `"redact"` | `"off"` | 0.12.0 | Was ein Lauf mit [sensiblen Inhalten](/docs/data-handling#schutz-für-sensible-inhalte) vor dem Senden macht. |
| `sensitiveData.detectors` | Array von Detektor-IDs | `secret`, `email`, `iban`, `credit-card` | 0.12.0 | Aktive Detektoren; `phone`, `ip`, `private-host` sind optional. |
| `sensitiveData.patterns` | String-Array | keiner | 0.12.0 | Reguläre Ausdrücke für eigene Begriffe, etwa Codenamen. |
| `sensitiveData.allow` | String-Array | keiner | 0.12.0 | Nie gemeldete Treffer; `*` ist ein Platzhalter. |
| `maxBatchSize` | positive Ganzzahl | `50` | 0.3.0 | Die meisten Einträge, die in einer Provider-Anfrage gesendet werden. |
| `maxLength` | Zuordnung von Key zu positiver Ganzzahl | keines | 0.11.0 | Längenbudgets pro Key in Graphemclustern. |
| `maxTokens` | positive Ganzzahl | keines | 0.5.0 | Ein Token-Budget für den ganzen Lauf. |
| `budgetBehavior` | `"warn"`, `"stop"` | `"warn"` | 0.5.0 | Ob das Erreichen von `maxTokens` nur warnt oder das Senden stoppt. |
| `rates.asOf` | Datum `YYYY-MM-DD` | im Block erforderlich | 0.11.0 | Das Datum, an dem du die Raten gelesen hast. |

| `extract.literals.ignore` | String-Array | keiner | 0.11.0 | Exakte Texte, die `doctor --literals` zurückhält. |
| `extract.unused.ignore` | String-Array | keiner | 0.11.0 | Keys oder `*`-Muster, die `diff --unused` nie als ungenutzt meldet. |

### Locales und Dateien

- **`files.pattern`** muss `{locale}` enthalten, das einzige Token, das es versteht: `locales/{locale}.json` wird zu `locales/de.json`, aufgelöst gegen die Projektwurzel. Es ist ein wörtlicher Pfad, nie ein Glob, eine Konfiguration adressiert also eine Datei pro Locale; für mehrere Namespace-Dateien siehe [Namespace-Layouts](/docs/formats#namespace-layouts). `apple-xcstrings` braucht das Token trotzdem, aber jede Locale löst sich zum selben Katalog auf ([Xcode String Catalogs](/docs/formats#xcode-string-catalogs-xcstrings)).
- **`files.localeStyle`** entscheidet, wozu das Token expandiert:
  - `literal` schreibt das Tag so, wie es konfiguriert ist; das brauchen die JSON-, YAML-, XLIFF-, ARB-, Properties- und Apple-`.lproj`-Layouts.
  - `posix` ersetzt `-` durch `_`, für gettext und Javas `messages_{locale}.properties`: Aus `pt-BR` wird `pt_BR`, aus `zh-Hant-TW` wird `zh_Hant_TW`. Eine Variante wie `de-1996` hat keine posix-Schreibweise. `gettext-po` schreibt Schriften auf die gettext-Art (nächster Abschnitt).
  - `android` expandiert zu einem kompletten Ressourcenverzeichnis, geschrieben als `res/{locale}/strings.xml`: `values` für die Quelle, dann `values-de`, `values-pt-rBR`, `values-b+zh+Hans`.

  Ein Style lehnt eine Locale ab, die er nicht schreiben kann, statt ein Verzeichnis zu schreiben, das die Plattform ignoriert.

### gettext-Locale-Namen

<AvailableFrom version="0.12.0" />

Mit `format: "gettext-po"` und `localeStyle: "posix"` wird eine Datei auf die gettext-Art benannt, `language_REGION@modifier`, während die Konfiguration den BCP-47-Code behält:

| Code in der Konfiguration | Dateiname |
| --- | --- |
| `pt-BR` | `pt_BR` |
| `es-419` | `es_419` |
| `sr-Latn` | `sr@latin` |
| `sr-Latn-RS` | `sr_RS@latin` |
| `uz-Cyrl` | `uz@cyrillic` |
| `ks-Deva-IN` | `ks_IN@devanagari` |
| `zh-Hant-TW` | `zh_TW` |
| `sr-Cyrl-RS` | `sr_RS` |

Eine Schrift, die Sprache und Region bereits vorgeben, fällt weg, deshalb scheitert es mit `LOCALE_PATH_COLLISION`, sowohl `zh-TW` als auch `zh-Hant-TW` zu konfigurieren. Eine Schrift ohne gettext-Modifikator, etwa `zh-Hant` ohne Region, scheitert mit `LOCALE_LAYOUT_INVALID`. [`verbatra init`](/docs/cli/init) liest diese Namen zurück, und ein neu angelegter Katalog verwendet sie in seinem `Language`-Header. Andere Formate behalten unter `posix` die ICU-Schreibweise (`sr_Latn`).

### Locale-Codes

<AvailableFrom version="0.12.0" />

Jeder Locale-Code muss ein Tag sein, den `Intl.getCanonicalLocales` akzeptiert, mit einem Sprach-Subtag aus zwei oder drei Buchstaben; sonst scheitert das Laden mit `CONFIG_INVALID` und nennt Feld und Code. `pt_BR` wird abgelehnt (schreib `pt-BR` und setz `localeStyle: "posix"`), ebenso ein Sprachname wie `german`. Ein gültiger, aber nicht kanonischer Code wie `zh-hant-tw` oder das veraltete `iw` funktioniert so, wie er dasteht, und [`verbatra doctor`](/docs/cli/doctor) schlägt die kanonische Form vor. verbatra benennt nie eine Datei um, und ein umgeschriebener Code behält seinen Zustand ([Ein umgeschriebener Locale-Code](/docs/the-lock-file#ein-umgeschriebener-locale-code)).

### provider

`provider.id` wählt einen der [Provider](/docs/providers) oder `none`. Ab 0.12.0 scheitert ein falsch platzierter Key unter `provider`, etwa `localeMap`, mit `CONFIG_INVALID`. Jeder Provider außer `none` akzeptiert `options.localeMap` und `options.requestTimeoutMs` ([Provider](/docs/providers#an-den-provider-gesendete-locale-codes)). Bei `none` darf `options` fehlen und muss sonst `{}` sein ([Ohne maschinelle Übersetzung arbeiten](/docs/human-only-workflow)).

### glossary

Begriffe, die auf eine feste Weise übersetzt werden, inline oder als Pfad zu einer JSON-Datei mit derselben Form; die beiden Formen werden nie zusammengeführt. Version 1 ordnet jedem Quellbegriff die Übersetzung zu, die jede Locale verwendet:

```ts title="verbatra.config.ts"
export default defineConfig({
  // ...
  glossary: {
    "Sign in": "Anmelden",
  },
  // or: glossary: "glossary.json",
});
```

Ein relativer Pfad wird gegen das Verzeichnis der Konfigurationsdatei aufgelöst. Die Datei muss UTF-8-kodiert und höchstens 1 MiB groß sein und wird einmal beim Laden gelesen. Eine fehlende Datei, ungültiges JSON oder eine ungültige Form scheitert mit `CONFIG_INVALID` und nennt den Pfad sowie bei Version 2 das Feld. Leg einen Begriff `__proto__` in eine Datei: In einem Literal in `verbatra.config.ts` macht JavaScript daraus den Prototyp.

#### Glossar pro Locale (Version 2)

<AvailableFrom version="0.12.0" />

Version 2 gibt jedem Begriff eine Übersetzung pro Locale, verbotene Wiedergaben und Begriffe, die so bleiben, wie sie geschrieben sind:

```json title="glossary.json"
{
  "version": 2,
  "terms": [
    {
      "source": "Dashboard",
      "targets": { "de": "Übersicht", "fr": "Tableau de bord" },
      "forbidden": { "de": ["Instrumententafel"] },
      "note": "The start page after sign-in",
      "partOfSpeech": "noun"
    },
    { "source": "Sign in", "target": "Anmelden", "caseSensitive": true }
  ],
  "doNotTranslate": ["verbatra", { "term": "Acme", "caseSensitive": false }]
}
```

| Feld | Bedeutung |
| --- | --- |
| `version` | Immer `2`; Pflicht, und jede andere Zahl scheitert. |
| `terms[].source` | Der Quellbegriff; jeder Begriff kommt einmal vor. |
| `terms[].target` | Die Übersetzung für jede Locale ohne eigenen Eintrag in `targets`. |
| `terms[].targets` | Übersetzungen pro Locale. Eine Locale nimmt ihren eigenen Eintrag, dann den ihrer Basissprache (`de` deckt `de-AT` ab), dann `target`; verglichen werden kanonische Codes ohne Groß- und Kleinschreibung. |
| `terms[].forbidden` | Wiedergaben, die eine Locale nie verwenden darf; eine regionale Locale befolgt auch die Liste ihrer Basissprache. |
| `terms[].caseSensitive` | Begriff, Übersetzungen und verbotene Wiedergaben mit Groß- und Kleinschreibung vergleichen. Default `false`. |
| `terms[].note`, `terms[].partOfSpeech` | Freitext-Kontext, den ein LLM-Provider als Daten erhält. |
| `doNotTranslate` | Begriffe, die unübersetzt übernommen werden. Ein reiner String behält auch seine Groß- und Kleinschreibung; bei `{ "term", "caseSensitive": false }` darf sie sich ändern. |

Jeder Begriff braucht ein `target`, einen Eintrag in `targets` oder eine `forbidden`-Liste und darf seine eigene Übersetzung nicht verbieten, keine Locale doppelt nennen und nicht zusätzlich in `doNotTranslate` stehen. Der [Cache](/docs/the-cache)-Fingerprint jeder Locale deckt nur ihre eigenen Begriffe ab. Eine Datei der Version 1 funktioniert mit demselben Fingerprint weiter; [`updateGlossaryTerm`](/docs/sdk/config#updateglossaryterm) aus dem SDK schreibt sie nur für eine Änderung, die Version 1 nicht ausdrücken kann, als Version 2 neu.

<AvailableFrom version="0.4.0" pkg="@verbatra/studio" /> Nur die Dateiform lässt sich aus [Studio](/docs/review-in-studio) heraus bearbeiten, Begriff für Begriff; ein Inline-Glossar ist dort nur lesbar. Welche Provider das Glossar anwenden, steht unter [Provider](/docs/providers#tonfall-und-glossar-über-die-provider-hinweg); die Ausgabe jedes Providers wird danach geprüft und mit `GLOSSARY_TERM_MISSED` oder `GLOSSARY_FORBIDDEN_TERM` markiert ([Review-Gründe](/docs/error-codes#review-reason-codes)).

### generatePlurals

Wenn true, synthetisiert verbatra die CLDR-Pluralformen, die ein Ziel braucht, der Quelle aber fehlen, etwa `few` und `many` im Polnischen; Ordinal-Keys (`<key>_ordinal_<category>`) folgen den CLDR-Ordinalregeln. Nur `i18next-json` mit einem LLM-Provider unterstützt das. Alles andere, und eine Locale ohne CLDR-Regeln, bekommt stattdessen die Plural-Warnung pro Locale (mit der Annahme `one` und `other` für Kardinalzahlen, `other` für Ordinalzahlen). Es gibt kein CLI-Flag; `translate()` im SDK nimmt einen Override pro Lauf.

### fuzzyCache

`fuzzyCache: { enabled: true }` lässt einen Key, dessen Quelle sich geändert hat, die Übersetzung seiner früheren Form wiederverwenden, wenn beide mindestens `threshold` ähnlich sind, immer als `FUZZY_CACHE_REUSE` markiert; die Sicherheitsregeln stehen unter [Unscharfe Wiederverwendung](/docs/the-cache#unscharfe-wiederverwendung). `--no-cache` umgeht es zusammen mit dem restlichen Cache.

### humanEdits und pinnedKeys

`humanEdits` betrifft einen veralteten Key, dessen Wert ein Mensch geschrieben hat (Provenance `human`, `import` oder `external`, siehe [Provenance](/docs/the-lock-file#herkunft-wer-welchen-wert-geschrieben-hat)):

- `"protect"` behält den Wert und sendet den Key nicht.
- `"suggest"` behält den Wert und fragt den Provider nach einem Vorschlag, der nie geschrieben wird.
- `"overwrite"` übersetzt ihn neu; `translate --include-human` macht das für einen Lauf.

Ein Key, der auf `pinnedKeys` passt (zum Beispiel `["legal.*", "brand.name"]`), wird nie maschinell geschrieben, egal was `humanEdits` sagt. Siehe [Menschliche Übersetzungen behalten](/docs/protecting-human-translations).

### network

Siehe [Netzwerkzugriff einschränken](/docs/network-policy).

```ts title="verbatra.config.ts"
network: { policy: "local-only", allowedHosts: ["gpu.lan"] }
```

### maxBatchSize

Fehlende und geänderte Einträge gehen in sequenziellen [Sub-Batches](/docs/providers#batching) von höchstens dieser Größe hinaus. Kein CLI-Flag überschreibt es.

### maxLength

Eine Zuordnung von Übersetzungs-Key zum längsten Wert, den er halten darf, für Strings unter einer Layout-Vorgabe:

```ts title="verbatra.config.ts"
maxLength: {
  "nav.dashboard": 18,
  "cta.submit": 12,
}
```

- **Nur hier.** Kein Budget wird aus einer Beschreibung oder den Metadaten eines Formats abgeleitet. Keys werden wörtlich verglichen, nie als Globs; ein Key, der nicht in der Zuordnung steht, wird nie gemessen.
- **Graphemcluster.** Die Länge zählt wahrgenommene Zeichen, Leerraum eingeschlossen: Ein Emoji oder ein Buchstabe mit Akzent zählt als eines, ebenso ein CJK-Zeichen, obwohl es etwa doppelt so breit dargestellt wird. Die Grenze ist inklusiv.
- **Wann geprüft wird.** Bei jedem Wert, den `translate` für den Key erzeugt, Cache-Wiederverwendungen eingeschlossen. Ein aktueller Key wird nicht gemessen, ein neues Budget markiert also nichts, bis sich seine Quelle ändert; [`verbatra export --include-unchanged`](/docs/cli/export) misst jeden aktuellen Wert sofort.
- **Beratend.** Eine Überschreitung wird trotzdem geschrieben und gelockt und als [`MAX_LENGTH_EXCEEDED`](/docs/error-codes#max_length_exceeded) zum Review markiert.

### maxTokens und budgetBehavior

`maxTokens` ist ein Budget für den ganzen Lauf: Eingabe- plus Ausgabe-Tokens, summiert über jeden Provider-Aufruf (Übersetzung und Pluralgenerierung) und jede Ziel-Locale. `translate --max-tokens <n>` setzt für einen Lauf eine strengere Obergrenze, die immer stoppt; es gilt der niedrigere Wert (ab 0.12.0).

`budgetBehavior` entscheidet, was dann passiert:

- `"warn"`, der Default, zählt die Ausgaben und vermerkt die Überschreitung; der Lauf geht weiter, als wäre kein Budget gesetzt.
- `"stop"` <AvailableFrom version="0.11.0" /> macht es zur Obergrenze (DeepL, Google Cloud Translation und LibreTranslate eingeschlossen). Vor jeder Anfrage projiziert der Lauf ihre Kosten genauso wie [die Vorab-Schätzung](/docs/estimating-cost) und lehnt eine ab, die `maxTokens` überschreiten würde. Die Keys dieser Anfrage werden zurückgehalten, ebenso jeder noch nicht versuchte Key: der Rest der aktuellen Locale und jede spätere Locale, deren Vergleich und Verwaisten-Meldung trotzdem laufen. Zurückgehaltene Keys behalten ihren vorherigen Lock-Hash und werden beim nächsten Lauf erneut versucht.

Zählung unter `"stop"`:

- Nach jeder Anfrage wird die Summe auf den vom Provider gemeldeten Verbrauch abgeglichen, ein Lauf kann also knapp über `maxTokens` enden; wie weit und warum, steht unter [dem `budget` der Laufzusammenfassung](/docs/sdk/run-summary#die-anatomie-der-runsummary). Maschinenübersetzungs-Provider melden keine Tokens und werden über die Projektion budgetiert.
- Eine fehlgeschlagene oder abgeschnittene Anfrage bleibt voll belastet, und zurückgehaltene Arbeit bekommt keinen Lock-Eintrag.
- Die Projektion enthält einen festen Aufschlag für den LLM-Prompt (Systemregeln und Antwortschema), der auch für die Maschinenübersetzungs-Provider angerechnet wird. Eine Anfrage wird als ganzer Batch projiziert, ein `maxTokens` unterhalb der Projektion eines Batches lehnt ihn also bei jedem Lauf ab; der Hinweis sagt dann, `maxBatchSize` zu senken oder `maxTokens` zu erhöhen.

Geltungsbereich und Exit-Codes:

- Das Budget begrenzt einen `translate`-Lauf, nie eine Neuübersetzung eines einzelnen Eintrags; `watch` startet pro Lauf ein frisches. Ein echter Lauf mit Budget lehnt `--concurrency` über `1` ab ([`CONCURRENCY_BUDGET_CONFLICT`](/docs/error-codes#concurrency_budget_conflict)).
- Unter `"warn"` ändert sich der Exit-Code nie. Unter `"stop"` ist eine Locale mit zurückgehaltenen Keys `partial`, wenn einige Keys angekommen sind, und `failed`, wenn keiner ankam; beide enden mit Exit `1`.
- `budgetBehavior` ohne `maxTokens` hat keine Wirkung.

<Callout title="Zwei verschiedene maxTokens">
Das Top-Level-`maxTokens` ist dieses Budget für den ganzen Lauf; Anthropics davon unabhängiges `provider.options.maxTokens` begrenzt eine Antwort ([Provider](/docs/providers#anthropic)).
</Callout>

### rates

Wird nur von [`verbatra translate --estimate`](/docs/estimating-cost) gelesen, wo auch steht, wie aus Raten Geld wird; ein echter Lauf ignoriert es.

```ts title="verbatra.config.ts"
rates: {
  asOf: "2026-01-15",
  currency: "USD",
  table: {
    "gemini/gemini-2.5-flash": { inputPerMillionTokens: 0.1, outputPerMillionTokens: 0.4 },
    deepl: { perMillionCharacters: 25 },
  },
}
```

Ein `table`-Key ist `provider/model` für einen Provider mit Modell und die blanke Id für einen ohne (`deepl`, `google-translate`). Ein Eintrag wird entweder nach Tokens abgerechnet (`inputPerMillionTokens` und `outputPerMillionTokens`) oder nach Zeichen (`perMillionCharacters`), nie beides; eine negative Rate wird abgelehnt. `openai-compatible` und `libretranslate` stellen keine Rechnung, deshalb wird ihre Menge ohne Rate gemeldet. Ein Eintrag in der falschen Einheit wird abgelehnt.

### extract

Wird nur von [`verbatra extract`](/docs/cli/extract), [`verbatra doctor --literals`](/docs/cli/doctor#nicht-übersetzte-literale) und [`verbatra diff --unused`](/docs/cli/diff#ungenutzte-quell-keys) gelesen.

```ts title="verbatra.config.ts"
extract: {
  framework: "i18next",
  roots: ["src", "app"],
  exclude: ["generated"],
  literals: { ignore: ["Acme Inc."] },
  unused: { ignore: ["emails.*"] },
}
```

- **`framework`** ist eine geschlossene Menge ([Aufrufformen](/docs/cli/extract#was-er-findet)); ein Framework ohne Extractor wird abgelehnt.
- **`roots`** werden gegen die Projektwurzel aufgelöst; nichts außerhalb davon wird gelesen.
- **`exclude`** ergänzt Verzeichnisnamen (keine Pfade), die überall unterhalb eines Roots passen, zur [immer übersprungenen Menge](/docs/cli/extract#grenzen-des-scans).
- **`literals.ignore`** trifft den ganzen Text eines Literals nach dem Zusammenfassen von Leerraum und dem Auflösen von Zeichenreferenzen (`Tom & Jerry`); ein zurückgehaltenes Literal wird als unterdrückt gemeldet.
- **`unused.ignore`** nimmt exakte Keys oder `*`-Muster für Keys, die nur außerhalb des gescannten Quellcodes verwendet werden, abgeglichen mit dem dekodierten Key, den der Bericht zeigt (`Welcome. Enjoy`); ein Treffer wird als ignoriert gemeldet.

## Suchreihenfolge

verbatra sucht vom Arbeitsverzeichnis aus aufwärts und verwendet die erste Quelle, die es findet. Die Suche endet beim nächsten Verzeichnis, das `.git` enthält, sonst bei deinem Home-Verzeichnis oder, wenn das Home-Verzeichnis nicht darüber liegt, beim Arbeitsverzeichnis selbst; sie greift also nie eine Konfiguration oberhalb deines Repositorys auf:

1. `package.json` (eine `"verbatra"`-Eigenschaft)
2. `.verbatrarc`
3. `.verbatrarc.json`
4. `.verbatrarc.yaml`
5. `.verbatrarc.yml`
6. `.verbatrarc.js`
7. `.verbatrarc.cjs`
8. `.verbatrarc.ts`
9. `verbatra.config.js`

`--config <path>` lädt stattdessen genau eine Datei, relativ zum Arbeitsverzeichnis. Im SDK hat ein In-Memory-`configOverride` Vorrang vor `configPath`, das Vorrang vor der Suche hat ([SDK-Rezepte](/docs/programmatic-api)).

## Validierung im Editor

<AvailableFrom version="0.9.0" />

`@verbatra/sdk` liefert ein JSON Schema aus, erzeugt aus dem zod-Schema, mit dem das SDK validiert, und die Doku-Seite stellt dasselbe Dokument unter einer festen URL bereit, die bei einer globalen Installation, mit `npx`, in einem Monorepo mit Hoisting und für einen entfernten Agenten funktioniert:

```text
https://verbatra.kreitz-webdev.de/schema/v1/config.json
```

Offline, oder um das Schema an die installierte Version zu binden, verweist du stattdessen auf die Kopie im Paket: `./node_modules/@verbatra/sdk/dist/config-schema.json`. Die [JSON Schemas](/docs/cli/output#schemas) der `--json`-Ausgabe liegen daneben.

`.verbatrarc.json` und `.verbatrarc` akzeptieren einen `$schema`-Key, den VS Code liest:

```json title=".verbatrarc.json"
{
  "$schema": "https://verbatra.kreitz-webdev.de/schema/v1/config.json",
  "sourceLocale": "en",
  "targetLocales": ["de", "fr"],
  "format": "i18next-json",
  "files": { "pattern": "locales/{locale}.json" },
  "provider": { "id": "gemini", "options": { "model": "gemini-2.5-flash", "maxOutputTokens": 4096 } }
}
```

Das endungslose `.verbatrarc` braucht zusätzlich eine Dateizuordnung, die eine Workspace-Zuordnung liefert:

```json title=".vscode/settings.json"
{
  "json.schemas": [
    {
      "fileMatch": [".verbatrarc", ".verbatrarc.json"],
      "url": "https://verbatra.kreitz-webdev.de/schema/v1/config.json"
    }
  ]
}
```

Eine YAML-Konfiguration nimmt einen Kommentar für den YAML Language Server:

```yaml title=".verbatrarc.yaml"
# yaml-language-server: $schema=https://verbatra.kreitz-webdev.de/schema/v1/config.json
sourceLocale: en
targetLocales: [de, fr]
format: i18next-json
files:
  pattern: "locales/{locale}.json"
provider:
  id: gemini
  options:
    model: gemini-2.5-flash
    maxOutputTokens: 4096
```

Die `package.json`-Eigenschaft kann kein Schema bekommen; die ausführbaren Formen werden stattdessen durch `defineConfig` typisiert.

### Was das Dokument nicht prüfen kann

Diese Regeln lassen sich in JSON Schema nicht ausdrücken, deshalb prüft sie nur das Laden der Konfiguration: die Regeln für `targetLocales` und [Locale-Codes](#locale-codes), die Keys von [`localeMap`](/docs/providers#an-den-provider-gesendete-locale-codes) und [`apiKeyEnvVar`](/docs/providers#openai-compatible), gültige Adressen und Bereiche in [`network.allowedHosts`](/docs/network-policy), `sensitiveData.patterns` innerhalb der [Sicherheitsregeln für Muster](/docs/data-handling#schutz-für-sensible-inhalte) und die Begriffsregeln eines Inline-Glossars der [Version 2](#glossar-pro-locale-version-2).

## Das Arbeitsverzeichnis und .env

Das Arbeitsverzeichnis (wo du verbatra ausführst, oder `--cwd`) ist der Startpunkt der Konfigurationssuche; welche Befehle `.env.local` und `.env` von dort laden, steht unter [Umgebungsdateien](/docs/cli#umgebungsdateien). Die Projektwurzel ist das Verzeichnis der Konfigurationsdatei, die die Suche gefunden hat: Locale-Pfade, `verbatra.lock.json`, der Cache, die Provenienzdatei und `.verbatra-local/` werden gegen sie aufgelöst, sodass ein Lauf aus einem Unterverzeichnis mit denselben Dateien arbeitet wie ein Lauf neben der Konfiguration. Mit `--config` ist das Arbeitsverzeichnis die Wurzel, und eine Konfigurationsdatei an anderer Stelle bekommt einen Hinweis auf stderr, weil ihr Glossarpfad weiter gegen ihr eigenes Verzeichnis aufgelöst wird. Ein relativer Pfad, den du selbst übergibst, etwa bei `--out` oder `check --file`, wird gegen das Arbeitsverzeichnis aufgelöst.

## Wenn das Laden fehlschlägt

- [`CONFIG_NOT_FOUND`](/docs/error-codes#config_not_found): an keinem der durchsuchten Orte eine Konfiguration, oder der `--config`-Pfad existiert nicht.
- [`CONFIG_INVALID`](/docs/error-codes#config_invalid): Eine Konfiguration wurde gefunden, ist aber nicht verwendbar. Die Meldung listet jedes Problem mit seinem Key-Pfad, und ein unbekannter Key auf jeder Ebene bekommt den Hinweis, dass API-Schlüssel aus der Umgebung kommen. Ein Parse-Fehler nennt die Datei (bei YAML mit Zeile und Spalte), zitiert aber nie ihren Inhalt, und jede Meldung läuft durch die Schlüssel-Redaktion.

Die CLI endet in beiden Fällen mit Exit `2`.
