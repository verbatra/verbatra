verbatra incluye seis proveedores detrás de una sola interfaz: Anthropic, OpenAI, Gemini y openai-compatible (un servidor local o autoalojado compatible con OpenAI) son modelos de lenguaje grandes, y DeepL y Google Cloud Translation son servicios de traducción automática. Seleccionas uno en el bloque `provider` de tu [configuración](/docs/config-file), por `id`. Cada id de modelo en esta página es un ejemplo, no una recomendación: los catálogos de modelos cambian, así que consulta la lista actual de tu proveedor.

## ¿Cuál elijo?

Cualquier proveedor funciona con cualquier formato y comando; la elección va de coste, calidad, privacidad y cómo consigues una clave.

- **¿Proyecto pequeño o secundario, y lo quieres gratis?** Usa **Gemini**. Tiene un nivel de API gratuito de verdad, así que puedes traducir una app entera a coste cero. Consigue una clave en [Google AI Studio](https://aistudio.google.com/apikey) y define `GEMINI_API_KEY`. El nivel gratuito tiene límite de tasa (mira la nota más abajo), que solo importa en una primera ejecución grande.
- **¿La mejor calidad de traducción para una app de producción?** Usa **Anthropic** u **OpenAI**. Ambos son LLM de pago y leen `ANTHROPIC_API_KEY` u `OPENAI_API_KEY`.
- **¿Alto volumen, dirigido por glosario, o sin LLM de por medio?** Usa **DeepL**. Es una API dedicada de traducción automática con un nivel gratuito y uno de pago, y soporta un glosario nativo por id. No traduce cadenas con marcadores de posición (mira la nota más abajo); para esas, usa un proveedor LLM.
- **¿Ya estás en Google Cloud, o quieres la cobertura de idiomas más amplia con una simple clave de API?** Usa **Google Cloud Translation**. Es la API dedicada de traducción automática de Google (el nivel Basic, v2), facturada a través de tu proyecto de Google Cloud. Como DeepL, no traduce cadenas con marcadores de posición.
- **¿Sin conexión, sin coste, o tus cadenas no pueden salir de tu red?** Usa **openai-compatible**. Apunta verbatra a un servidor de inferencia local o autoalojado (LM Studio, Ollama, vLLM) en lugar de a una API alojada. Sin cuenta, sin clave de API y sin salida de red más allá de tu propia máquina o LAN.

¿No lo tienes claro? Empieza en el nivel gratuito de Gemini y cambia de proveedor más tarde editando un solo `id` en tu configuración. Nada más cambia.

## Las claves vienen del entorno

verbatra nunca lee una clave de API de la configuración. Cada proveedor alojado lee exactamente una variable de entorno:

| Id de proveedor | Variable de entorno |
| --- | --- |
| `anthropic` | `ANTHROPIC_API_KEY` |
| `openai` | `OPENAI_API_KEY` |
| `gemini` | `GEMINI_API_KEY` |
| `deepl` | `DEEPL_API_KEY` |
| `google-translate` | `GOOGLE_TRANSLATE_API_KEY` |

Define la variable en `.env` (que `verbatra init` añade a `.gitignore`) o expórtala en tu shell o en el almacén de secretos de tu CI. Cuando la variable no está definida o está vacía, el proveedor falla con un error estructurado `MISSING_API_KEY` cuyo mensaje nombra la variable pero nunca incluye el valor de una clave. Nunca confirmes una clave real.

`openai-compatible` es distinto: la mayoría de los servidores locales no necesitan clave, así que no está en esta tabla. Mira su propia sección más abajo para saber cómo resuelve su clave.

## Anthropic

```ts
provider: {
  id: "anthropic",
  options: {
    model: "claude-sonnet-4-6", // example model id
    maxTokens: 4096,
  },
}
```

Lee `ANTHROPIC_API_KEY`. `model` y `maxTokens` son ambos obligatorios. `maxTokens` limita los tokens que puede producir una sola respuesta; es la opción de límite de tokens de salida de este proveedor (los demás la llaman `maxOutputTokens`). El `requestTimeoutMs` opcional también se acepta; consulta [Tiempo de espera de solicitud](#tiempo-de-espera-de-solicitud).

## OpenAI

```ts
provider: {
  id: "openai",
  options: {
    model: "gpt-5.4-mini", // example model id
    maxOutputTokens: 4096,
  },
}
```

Lee `OPENAI_API_KEY`. `model` y `maxOutputTokens` son ambos obligatorios. El `requestTimeoutMs` opcional también se acepta; consulta [Tiempo de espera de solicitud](#tiempo-de-espera-de-solicitud).

## Gemini

```ts
provider: {
  id: "gemini",
  options: {
    model: "gemini-2.5-flash", // example model id
    maxOutputTokens: 4096,
  },
}
```

Lee `GEMINI_API_KEY`. `model` y `maxOutputTokens` son ambos obligatorios. El `requestTimeoutMs` opcional también se acepta; consulta [Tiempo de espera de solicitud](#tiempo-de-espera-de-solicitud).

<Callout title="El nivel gratuito y sus límites">
Gemini es el punto de partida recomendado para proyectos pequeños porque su API tiene un nivel gratuito. Crea una clave en [Google AI Studio](https://aistudio.google.com/apikey), sin necesidad de facturación. El nivel gratuito limita las solicitudes por minuto y por día (los números exactos dependen del modelo y cambian con el tiempo, así que consulta los límites actuales de Google), y verbatra divide el trabajo en sublotes secuenciales, así que una primera ejecución sobre muchos locales puede toparse con esos topes. Un error breve de límite de tasa o de servidor se reintenta automáticamente con una pequeña espera, pero eso solo suaviza tropiezos momentáneos, no un tope sostenido. Si llegas al tope, traduce un locale cada vez o baja `maxBatchSize`, y vuelve a ejecutar: verbatra solo recoge lo que sigue faltando, así que repetir ejecuciones es seguro.
</Callout>

## DeepL

```ts
provider: {
  id: "deepl",
  options: {},
}
```

Lee `DEEPL_API_KEY`. DeepL es una API de traducción automática, no un LLM: no tiene campo `model` ni límite de tokens de salida. Toma dos opciones opcionales: `glossaryId`, que nombra un glosario que ya has creado en DeepL, y `requestTimeoutMs` (consulta [Tiempo de espera de solicitud](#tiempo-de-espera-de-solicitud)):

```ts
provider: {
  id: "deepl",
  options: {
    glossaryId: "<your-glossary-id>",
  },
}
```

DeepL se degrada con elegancia en lugar de fallar cuando no puede respetar un ajuste, e informa de cada degradación como un aviso en la ejecución:

- Un mapa de términos `glossary` configurado no se aplica (DeepL solo usa un id de glosario creado de antemano), informado como `GLOSSARY_IGNORED`.
- `tone` se asigna a la formalidad de DeepL: `formal` pasa a más formal, `informal` a menos formal, `neutral` o un tono ausente se omite. Con una clave del nivel gratuito, la formalidad no está soportada, así que un tono distinto del predeterminado se degrada al predeterminado, informado como `FORMALITY_DOWNGRADED`.

<Callout title="DeepL y los marcadores de posición">
DeepL no puede preservar marcadores de posición ni tokens ICU, así que no envía las cadenas que los contienen: esas entradas se retienen (quedan sin traducir) y se informan con un aviso `PLACEHOLDER_UNSUPPORTED`. Las cadenas sin marcadores de posición se traducen con normalidad. Para traducir cadenas con marcadores de posición, usa un proveedor LLM (Anthropic, OpenAI, Gemini u openai-compatible).
</Callout>

## Google Cloud Translation

<AvailableFrom version="0.10.0" />

```ts
provider: {
  id: "google-translate",
  options: {},
}
```

Lee `GOOGLE_TRANSLATE_API_KEY`. Como DeepL, Google Cloud Translation es una API de traducción automática, no un LLM: no tiene campo `model`, ni límite de tokens de salida, ni opción de glosario en v1. Toma una opción opcional, `requestTimeoutMs` (consulta [Tiempo de espera de solicitud](#tiempo-de-espera-de-solicitud)).

Este proveedor apunta al nivel Basic (v2) de Cloud Translation, autenticado con una clave de API simple de un proyecto de Google Cloud con la Cloud Translation API activada. No usa el nivel Advanced (v3), que se autentica con una cuenta de servicio o Application Default Credentials en lugar de una única variable de entorno, y por tanto no encaja con la regla de verbatra de claves solo por variable de entorno.

Cloud Translation no tiene ajuste de formalidad ni glosario genérico en el nivel Basic, así que un `tone` o `glossary` configurado nunca se aplica. Cada uno se informa como un aviso en lugar de descartarse en silencio:

- `tone` siempre informa `FORMALITY_DOWNGRADED` cuando se define como `formal` o `informal`; `neutral` o un tono ausente se omite.
- Un mapa de términos `glossary` proporcionado siempre informa `GLOSSARY_IGNORED`.

<Callout title="Google Cloud Translation y los marcadores de posición">
Como DeepL, Google Cloud Translation no puede preservar marcadores de posición ni tokens ICU, así que no envía las cadenas que los contienen: esas entradas se retienen (quedan sin traducir) y se informan con un aviso `PLACEHOLDER_UNSUPPORTED`. Las cadenas sin marcadores de posición se traducen con normalidad. Para traducir cadenas con marcadores de posición, usa un proveedor LLM (Anthropic, OpenAI, Gemini u openai-compatible).
</Callout>

<Callout title="Google Cloud Translation y los códigos de locale">
Los códigos de locale se validan como BCP-47 bien formado antes de cualquier llamada de red (por ejemplo, `en` o `pt-BR`); un código malformado como `en_US` falla con `INVALID_REQUEST` nombrando el código en cuestión. A diferencia de DeepL, Cloud Translation permite códigos de destino regionales libremente, así que esta comprobación es solo de sintaxis, no una lista fija permitida. Un locale de destino o un par de idiomas que la propia API de Google no soporte igualmente falla como `INVALID_REQUEST` estructurado en cuanto la solicitud llega a Google.
</Callout>

## openai-compatible

Apunta verbatra a un servidor que habla la API Chat Completions de OpenAI: LM Studio, Ollama, vLLM y similares funcionan todos. El id nombra el protocolo de cable, no dónde corre el servidor, así que una API alojada que hable el mismo protocolo también encaja aquí.

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct", // example: whatever your server exposes
    maxOutputTokens: 1024,
  },
}
```

`baseUrl`, `model` y `maxOutputTokens` son obligatorios. A diferencia de todos los demás proveedores, `baseUrl` vive en la configuración y no en el entorno: es una dirección de red que ya conoces (una IP de LAN o `localhost`), no un secreto. Debe ser una URL absoluta válida con esquema `http` o `https`; cualquier otra cosa, incluido un esquema ausente, hace fallar la validación de la configuración de inmediato.

`baseUrl` debe incluir el segmento de ruta de la API de tu servidor, normalmente `/v1`: LM Studio, Ollama y vLLM sirven todos sus rutas compatibles con OpenAI bajo `/v1`. Un `baseUrl` sin él sigue siendo una URL sintácticamente válida, así que pasa la validación de la configuración y en su lugar falla en tiempo de solicitud al llegar a la ruta equivocada.

Una API alojada que hable el mismo protocolo funciona igual. La API de chat completions de Mistral es un ejemplo:

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "https://api.mistral.ai/v1",
    model: "mistral-large-latest", // example: check Mistral's current model list
    maxOutputTokens: 4096,
    apiKeyEnvVar: "MISTRAL_API_KEY",
  },
}
```

`apiKeyEnvVar` nombra la variable de entorno que contiene tu clave para ese servidor. Es el mismo proveedor `openai-compatible` apuntado a otro endpoint, no un proveedor dedicado de Mistral. El `requestTimeoutMs` opcional también se acepta aquí, y es donde más importa: consulta [Tiempo de espera de solicitud](#tiempo-de-espera-de-solicitud).

### Las claves son opcionales

La mayoría de los servidores de inferencia locales no necesitan clave de API, así que `openai-compatible` resuelve su clave en tres niveles, en orden:

1. **`apiKeyEnvVar`**, un campo opcional de la configuración que nombra una variable de entorno de la que leer una clave real. Si defines este campo y su variable nombrada no está definida o está vacía, verbatra falla con `MISSING_API_KEY` en lugar de caer en silencio al siguiente nivel, porque dijiste explícitamente que se requiere una clave.
2. **`OPENAI_COMPATIBLE_API_KEY`**, una variable de entorno por convención, leída cuando `apiKeyEnvVar` no está definido. Si está definida y no vacía, verbatra la usa; si no, verbatra sigue adelante sin error.
3. **El marcador `"local"`**, enviado cuando ninguno de los anteriores resuelve nada. Es una cadena fija y no secreta, no una clave real, y es exactamente lo que hace que un servidor local sin clave funcione con cero configuración.

`apiKeyEnvVar` nunca puede nombrar `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` ni `DEEPL_API_KEY`: la validación de la configuración lo rechaza de plano, así que una configuración no puede apuntar este proveedor a la clave de un proveedor alojado por su nombre. El cliente tampoco lee nunca `OPENAI_API_KEY` por su cuenta y siempre pasa un valor de clave explícito al SDK subyacente, así que una clave alojada nunca puede llegar a un `baseUrl` personalizado.

<Callout type="warn" title="Una clave real sobre http en claro viaja sin cifrar">
verbatra permite `http://` en claro hacia cualquier host, incluida una dirección de LAN, sin más restricción que el esquema http o https. Esto es intencional y seguro en el caso común sin clave: nada secreto va por el cable.

Es un riesgo real solo cuando además configuras una clave (vía `apiKeyEnvVar` u `OPENAI_COMPATIBLE_API_KEY`) **y** `baseUrl` es `http://` en claro hacia un host que no es loopback: esa clave entonces viaja por tu red sin cifrar. Si tu servidor requiere una clave real y es accesible más allá de localhost, usa `https://` para él. verbatra hoy no detecta esta combinación ni avisa de ella; trátala como tu propia responsabilidad.
</Callout>

### Elegir un modelo local

Prefiere un modelo ajustado por instrucciones, sin razonamiento y con buena cobertura multilingüe. verbatra pide un único objeto JSON estricto y lo valida, así que quieres un modelo que siga de forma fiable las indicaciones de formato. `qwen2.5-14b-instruct` es un valor por defecto razonable; elige el mayor modelo de ese tipo que tu hardware ejecute bien.

<Callout type="warn" title="Evita los modelos de razonamiento y muy cuantizados">
Los modelos de razonamiento (thinking) y los builds muy cuantizados (qat o de pocos bits) son aquí las fuentes de fallo habituales: tienden a emitir prosa de razonamiento alrededor de la respuesta o a devolver JSON truncado, y cualquiera de las dos cosas hace fallar las comprobaciones de esquema e integridad de verbatra. Si un modelo con razonamiento es inevitable, dale espacio para razonar y responder: consulta [Límites de tokens de salida](#límites-de-tokens-de-salida) para el ajuste de `maxOutputTokens` y `maxBatchSize`.
</Callout>

Un modelo local malo falla de forma ruidosa, no en silencio: verbatra valida cada respuesta del proveedor contra un esquema canónico más las comprobaciones de integridad, así que un modelo que emite prosa de razonamiento o JSON truncado se rechaza con un error `INVALID_RESPONSE` u `OUTPUT_TRUNCATED` en lugar de escribir una traducción corrupta.

### Parseo tolerante para modelos locales y más pequeños

`openai-compatible` solicita el mismo formato de respuesta estricto y restringido por esquema que el proveedor alojado `openai`. La única diferencia está a la vuelta: los modelos locales y más pequeños tienden más a envolver una respuesta por lo demás correcta en prosa alrededor o en una valla de código Markdown a pesar de que se les pide que no, así que `openai-compatible` extrae el primer objeto JSON balanceado en cualquier parte de la respuesta antes de parsear, cosa que el proveedor alojado no hace. Su salida pasa igualmente por exactamente la misma validación de esquema y las mismas comprobaciones de integridad que la de cualquier otro proveedor: la salida de un modelo local es entrada no de fiar, y una respuesta malformada o con marcadores de posición discordantes se rechaza de la misma manera.

<Callout title="No está en verbatra init">
`verbatra init` no ofrece `openai-compatible` como opción de scaffold, porque no tiene una única variable de entorno obligatoria por la que preguntar. Añade a mano el bloque de proveedor de arriba a tu configuración; todo lo demás de esta página (glosario, tono, límites de tokens de salida) le aplica como a cualquier proveedor LLM.
</Callout>

## Tono y glosario entre proveedores

Los campos opcionales `tone` y `glossary` de la configuración (consulta [Archivo de configuración](/docs/config-file)) se aplican por proveedor:

- **Tono.** Los proveedores LLM (Anthropic, OpenAI, Gemini y openai-compatible) reciben el tono con la solicitud y se les instruye para respetarlo. DeepL lo asigna a la formalidad, con la degradación del nivel gratuito descrita arriba. Google Cloud Translation no tiene ningún control de formalidad, así que un tono no neutro siempre informa `FORMALITY_DOWNGRADED`.
- **Glosario.** Los proveedores LLM reciben el mapa de términos y se les instruye para tratar sus términos como vinculantes. DeepL ignora un mapa de términos (con un aviso `GLOSSARY_IGNORED`) y aplica solo su `glossaryId` nativo. Google Cloud Translation no tiene glosario alguno en v1, así que un mapa de términos proporcionado siempre informa `GLOSSARY_IGNORED`.

## Comportamiento que todo proveedor comparte

### Lotes

El trabajo de un locale se divide en sublotes secuenciales de como mucho `maxBatchSize` entradas (por defecto 50; consulta [Archivo de configuración](/docs/config-file)), así que una solicitud sobredimensionada no puede hacer fallar el locale entero. Un sublote fallido se retiene y se reintenta automáticamente en la siguiente ejecución mientras los demás sublotes siguen avanzando. DeepL y Google Cloud Translation además reparten un sublote entre tantas solicitudes como exijan sus propios topes por solicitud, de forma transparente.

### Reintentos

Los fallos transitorios (una respuesta de límite de tasa o un error de servidor) se reintentan automáticamente con una pequeña espera: los clientes de los SDK de OpenAI, Anthropic y DeepL reintentan por defecto, y verbatra añade un reintento propio equivalente para Gemini, cuyo SDK no lo hace. Los reintentos suavizan tropiezos momentáneos; un fallo sostenido sigue aflorando como un error estructurado. Google Cloud Translation no tiene reintento alguno hoy, en ninguna capa: una respuesta con límite de tasa o error de servidor aflora de inmediato como `RATE_LIMITED` o `PROVIDER_UNAVAILABLE`, y sigue aplicando el comportamiento habitual de recoger un sublote retenido en la siguiente ejecución.

### Tiempo de espera de solicitud

Cada proveedor acota cada solicitud saliente, para que un servidor que acepta la conexión pero nunca responde no pueda atascar una ejecución ni mantener abierto el bloqueo de escritura de un locale. Ese límite es `requestTimeoutMs`, un entero positivo opcional en milisegundos que se acepta en las `options` de los seis proveedores (`anthropic`, `openai`, `gemini`, `deepl`, `google-translate` y `openai-compatible`):

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct",
    maxOutputTokens: 1024,
    requestTimeoutMs: 300000, // 5 minutos
  },
}
```

Si lo omites, verbatra aplica su propio valor por defecto de `120000` ms (dos minutos): suficiente para no cortar un lote grande legítimamente lento, y lo bastante corto para que un servidor colgado pero vivo no bloquee un locale indefinidamente. Súbelo cuando un modelo local lento o un `maxBatchSize` grande necesiten más tiempo; bájalo para fallar antes. Cuando el límite se agota, esa solicitud falla con el código reintentable `TIMEOUT` y solo afecta a su propio sublote, así que las claves vuelven en la siguiente ejecución.

DeepL es la única excepción a la cancelación: su cliente no puede abortar una solicitud ya en vuelo, así que al agotarse el tiempo verbatra deja de esperar y sigue, pero la solicitud que ya envió se resuelve en DeepL. Google Cloud Translation, que usa una solicitud HTTP simple por dentro, cancela de inmediato al agotarse el tiempo, como cualquier otro proveedor salvo DeepL.

### Errores estructurados

Un fallo de proveedor nunca aflora como un error crudo del SDK, que podría llevar cabeceras de la solicitud o una clave. verbatra clasifica cada fallo por su estado HTTP o la clase de error del SDK y levanta un error estructurado con un código estable y un mensaje fijo y sin secretos:

| Código | Significado |
| --- | --- |
| `MISSING_API_KEY` | La variable de entorno requerida no está definida o está vacía. El mensaje nombra la variable, nunca un valor. |
| `INVALID_REQUEST` | La solicitud falló la validación antes de cualquier llamada de red: un campo malformado, un código de locale que DeepL no acepta (un código de origen regional, o un `en` o `pt` escueto como destino), o un código de locale que no es BCP-47 bien formado para Google Cloud Translation. Corrige la configuración o la solicitud; reintentar no ayudará. |
| `RATE_LIMITED` | HTTP 429 o un error de límite de tasa del SDK. En Google Cloud Translation, esto también cubre un HTTP 403 cuyo cuerpo nombra un motivo de cuota (un límite diario o por minuto), porque la API de Google reutiliza el 403 tanto para fallos de cuota como de credenciales. Espera y reintenta más tarde, o aumenta la cuota de Cloud Translation de tu proyecto. |
| `TIMEOUT` | Un tiempo de espera de red o de solicitud; no llegó respuesta a tiempo. Reintentar puede ayudar, y [`requestTimeoutMs`](#tiempo-de-espera-de-solicitud) sube el límite. |
| `AUTH_FAILED` | HTTP 401 o 403: la clave es inválida, está revocada o carece de permisos. En Google Cloud Translation, comprueba que `GOOGLE_TRANSLATE_API_KEY` sea una clave válida y sin restricciones para un proyecto con la Cloud Translation API activada. Reintentar no ayudará. |
| `PROVIDER_UNAVAILABLE` | HTTP 5xx: el proveedor falló en su propio lado, y la solicitud en sí nunca tuvo la culpa. Los reintentos de las capas inferiores ya absorben un 5xx transitorio, así que uno que llega a este código es una caída sostenida. Espera y reintenta más tarde. |
| `OUTPUT_TRUNCATED` | El modelo alcanzó su límite de tokens de salida; mira abajo. |
| `INVALID_RESPONSE` | La salida era malformada, incompleta o falló la reconciliación contra la solicitud. |
| `PROVIDER_REFUSED` | El modelo se negó a responder. |
| `PROVIDER_BLOCKED` | La solicitud o la respuesta fue bloqueada o filtrada por seguridad. |
| `PROVIDER_ERROR` | Cualquier cosa inclasificable. Cuando el fallo es un problema de transporte reconocible, el mensaje lo nombra (conexión rechazada, nombre de host no resuelto, conexión cerrada, host inalcanzable, certificado TLS no verificado) y dice qué comprobar; si no, recurre a un mensaje estático y sin secretos. |

Un fallo solo afecta a su propio sublote: las claves fallidas se retienen y se recogen de nuevo en la siguiente ejecución.

Para `openai-compatible`, un `PROVIDER_ERROR` nombra además el host y el puerto del `baseUrl` configurado, porque un endpoint que alojas tú mismo es el que de verdad se queda inalcanzable: `The translation provider request to localhost:11434 failed: the connection was refused. Check that the endpoint is running and that the configured host and port are right, then run again.` Solo se usa el componente de host de la URL, así que ninguna ruta, consulta ni información de usuario del `baseUrl` llega jamás a un mensaje. Google Cloud Translation informa de la misma manera contra su host fijo, `translation.googleapis.com`; la cadena de consulta que lleva la clave de API tampoco llega nunca a un mensaje.

### Límites de tokens de salida

Los cuatro proveedores LLM limitan cuántos tokens puede producir una sola respuesta. Cuando un modelo se detiene porque alcanzó ese tope, verbatra levanta `OUTPUT_TRUNCATED` en lugar de un fallo genérico de respuesta malformada, con un mensaje fijo:

> The provider stopped because the output-token limit was reached. Reduce the batch size or raise the configured max output tokens.

Cualquiera de las dos palancas lo resuelve: baja `maxBatchSize` en tu configuración para que cada solicitud produzca una respuesta más pequeña, o sube el tope por respuesta del proveedor (`maxTokens` para Anthropic, `maxOutputTokens` para OpenAI, Gemini y openai-compatible). DeepL y Google Cloud Translation no se ven afectados: ninguno tiene caso de truncado por tokens de salida. verbatra también se recupera por sí solo: cuando un sub-lote se trunca, lo divide en mitades y lo reintenta, bajando hasta una sola entrada, de modo que las claves que caben en una solicitud más pequeña se traducen igualmente y solo una entrada aislada que sigue desbordándose se retiene para la siguiente ejecución.

<Callout title="Los modelos de razonamiento gastan el mismo presupuesto">
Un modelo de razonamiento (thinking) gasta sus tokens de razonamiento ocultos del mismo presupuesto de tokens de salida que usa para emitir las traducciones JSON. Puede agotar ese presupuesto solo razonando y detenerse antes de escribir ninguna salida, lo que aparece como `OUTPUT_TRUNCATED`. Si usas un modelo de razonamiento, dale margen de sobra: prefiere un `maxOutputTokens` más alto (`maxTokens` para Anthropic) o un `maxBatchSize` más pequeño para que cada solicitud tenga espacio tanto para el razonamiento como para la respuesta.
</Callout>

### Señales de revisión

Las traducciones aceptadas de todos los proveedores pasan por las mismas comprobaciones posteriores a la traducción, y un resultado sospechoso (por ejemplo uno idéntico a su origen, o uno que se saltó un término del glosario) se marca hacia la cola de revisión en lugar de rechazarse. Los códigos de motivo y cómo trabajar la cola se cubren en [Seguridad de la traducción](/docs/translation-safety) y [Revisión en Studio](/docs/review-in-studio).
