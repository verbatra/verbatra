---
verbatra incluye siete proveedores detrás de una sola interfaz: Anthropic, OpenAI, Gemini y openai-compatible (un servidor local o autoalojado compatible con OpenAI) son grandes modelos de lenguaje, y DeepL, Google Cloud Translation y LibreTranslate (un servidor autoalojado) son servicios de traducción automática. Un octavo valor, `none`, desactiva la traducción automática por política; consulta [none](#none). Seleccionas uno en el bloque `provider` de tu [configuración](/docs/config-file), por `id`. Cada id de modelo en esta página es un ejemplo, no una recomendación: los catálogos de modelos cambian, así que consulta la lista actual de tu proveedor. Qué idiomas cubre cada proveedor y cómo le pasa verbatra tus códigos de locale lo tienes en [Soporte de idiomas](/docs/language-support).

## ¿Cuál elijo?

Cualquier proveedor funciona con cualquier formato y comando; la elección depende del coste, la calidad, la privacidad y de cómo consigues una clave. Qué recibe cada proveedor, y qué dice su empresa sobre retención y entrenamiento, está en [Tratamiento de datos y privacidad](/docs/data-handling).

- **¿Proyecto pequeño o secundario, y lo quieres gratis?** Usa **Gemini**. Tiene un nivel de API gratuito de verdad, así que puedes traducir una app entera a coste cero. Consigue una clave en [Google AI Studio](https://aistudio.google.com/apikey) y define `GEMINI_API_KEY`. El nivel gratuito tiene límite de tasa (consulta la nota más abajo), que solo importa en una primera ejecución grande. Fuera del EEE, Suiza y el Reino Unido, Google puede usar las peticiones del nivel gratuito para mejorar sus productos y que las lean revisores humanos, así que no pongas textos confidenciales en el nivel gratuito; consulta [Tratamiento de datos y privacidad](/docs/data-handling#retención-y-tratamiento-de-datos-del-proveedor).
- **¿La mejor calidad de traducción para una app de producción?** Usa **Anthropic** u **OpenAI**. Ambos son LLM de pago y leen `ANTHROPIC_API_KEY` u `OPENAI_API_KEY`.
- **¿Alto volumen, dirigido por glosario, o sin LLM de por medio?** Usa **DeepL**. Es una API dedicada de traducción automática con un nivel gratuito y uno de pago, y soporta un glosario nativo por id. No traduce cadenas con placeholders (consulta la nota más abajo); para esas, usa un proveedor LLM.
- **¿Ya estás en Google Cloud, o quieres la cobertura de idiomas más amplia con una simple clave de API?** Usa **Google Cloud Translation**. Es la API dedicada de traducción automática de Google (el nivel Basic, v2), facturada a través de tu proyecto de Google Cloud. Como DeepL, no traduce cadenas con placeholders.
- **¿Sin conexión, sin coste, o tus cadenas no pueden salir de tu red?** Usa **openai-compatible**. Apunta verbatra a un servidor de inferencia local o autoalojado (LM Studio, Ollama, vLLM) en lugar de a una API alojada. Sin cuenta, sin clave de API y sin salida de red más allá de tu propia máquina o LAN.
- **¿Una política prohíbe los modelos de lenguaje, pero tus cadenas tampoco pueden salir de tu red?** Usa **libretranslate**. Apunta verbatra a un servidor [LibreTranslate](https://github.com/LibreTranslate/LibreTranslate) autoalojado: traducción automática neuronal clásica sin modelo de lenguaje, sin cuenta y sin factura por carácter. Consulta [LibreTranslate](#libretranslate).
- **¿Nada de traducción automática, porque un contrato o una política de la empresa lo prohíbe?** Usa **none**. No se construye ningún proveedor ni se lee ninguna clave de API: verbatra rellena claves solo desde la memoria de traducción y pasa cualquier otra clave a una persona. Consulta [Flujo solo humano](/docs/human-only-workflow).

¿No lo tienes claro? Empieza en el nivel gratuito de Gemini con textos que no sean confidenciales y cambia de proveedor más tarde editando un solo `id` en tu configuración. Nada más cambia.

## Las claves vienen del entorno

verbatra nunca lee una clave de API de la configuración. Cada proveedor alojado lee exactamente una variable de entorno:

| Id de proveedor | Variable de entorno |
| --- | --- |
| `anthropic` | `ANTHROPIC_API_KEY` |
| `openai` | `OPENAI_API_KEY` |
| `gemini` | `GEMINI_API_KEY` |
| `deepl` | `DEEPL_API_KEY` |
| `google-translate` | `GOOGLE_TRANSLATE_API_KEY` |

Define la variable en `.env` (que `verbatra init` añade a `.gitignore`) o expórtala en tu shell o en el almacén de secretos de tu CI. Cuando la variable no está definida o está vacía, el proveedor falla con un error estructurado `MISSING_API_KEY` cuyo mensaje nombra la variable pero nunca incluye el valor de una clave. El SDK lo lanza al construir el proveedor y lo envuelve como `PROVIDER_CONSTRUCTION_FAILED`, así que la CLI imprime ese código seguido de `(cause: MISSING_API_KEY)`, y su registro de error `--json` lleva `"causeCode": "MISSING_API_KEY"`. Desde 0.12.0 el error lleva además el nombre de la variable como `envVar` en el `ProviderError`, y la CLI añade un `hint` que nombra exactamente esa variable para definirla (`next: Set GEMINI_API_KEY in the environment or in a .env file in the project directory.` en stderr). Nunca confirmes una clave real.

`openai-compatible` y `libretranslate` son distintos: la mayoría de los servidores autoalojados no necesitan clave, así que no están en esta tabla. Consulta sus propias secciones más abajo para saber cómo resuelve cada uno su clave.

## Anthropic

```ts
provider: {
  id: "anthropic",
  options: {
    model: "claude-sonnet-4-6", // example model id
    maxTokens: 4096,
  },
}
```

Lee `ANTHROPIC_API_KEY`. `model` y `maxTokens` son ambos obligatorios. `maxTokens` limita los tokens que puede producir una sola respuesta; es la opción de límite de tokens de salida de este proveedor (los demás la llaman `maxOutputTokens`). El `requestTimeoutMs` opcional también se acepta; consulta [Tiempo de espera de petición](#tiempo-de-espera-de-petición).

## OpenAI

```ts
provider: {
  id: "openai",
  options: {
    model: "gpt-5.4-mini", // example model id
    maxOutputTokens: 4096,
  },
}
```

Lee `OPENAI_API_KEY`. `model` y `maxOutputTokens` son ambos obligatorios. El `requestTimeoutMs` opcional también se acepta; consulta [Tiempo de espera de petición](#tiempo-de-espera-de-petición).

## Gemini

```ts
provider: {
  id: "gemini",
  options: {
    model: "gemini-2.5-flash", // example model id
    maxOutputTokens: 4096,
  },
}
```

Lee `GEMINI_API_KEY`. `model` y `maxOutputTokens` son ambos obligatorios. El `requestTimeoutMs` opcional también se acepta; consulta [Tiempo de espera de petición](#tiempo-de-espera-de-petición).

<Callout title="El nivel gratuito y sus límites">
Gemini es el punto de partida recomendado para proyectos pequeños porque su API tiene un nivel gratuito. Crea una clave en [Google AI Studio](https://aistudio.google.com/apikey), sin necesidad de facturación. El nivel gratuito limita las peticiones por minuto y por día (los números exactos dependen del modelo y cambian con el tiempo, así que consulta los límites actuales de Google), y verbatra divide el trabajo en sublotes secuenciales, así que una primera ejecución sobre muchos locales puede toparse con esos topes. Un error breve de límite de tasa o de servidor se reintenta automáticamente con una pequeña espera, pero eso solo suaviza tropiezos momentáneos, no un tope sostenido. Si llegas al tope, traduce un locale cada vez o baja `maxBatchSize`, y vuelve a ejecutar: verbatra solo recoge lo que sigue faltando, así que repetir ejecuciones es seguro. Las condiciones de datos del nivel gratuito también difieren de las del nivel de pago: fuera del EEE, Suiza y el Reino Unido, Google puede usar las peticiones del nivel gratuito para mejorar sus productos. Consulta [Tratamiento de datos y privacidad](/docs/data-handling#retención-y-tratamiento-de-datos-del-proveedor).
</Callout>

## DeepL

```ts
provider: {
  id: "deepl",
  options: {},
}
```

Lee `DEEPL_API_KEY`. DeepL es una API de traducción automática, no un LLM: no tiene campo `model` ni límite de tokens de salida. Admite tres opciones, todas opcionales: `glossaryId`, que nombra un glosario que ya has creado en DeepL, `requestTimeoutMs` (consulta [Tiempo de espera de petición](#tiempo-de-espera-de-petición)) y `localeMap` (consulta [Códigos de locale enviados al proveedor](#códigos-de-locale-enviados-al-proveedor)):

```ts
provider: {
  id: "deepl",
  options: {
    glossaryId: "<your-glossary-id>",
  },
}
```

DeepL se degrada de forma controlada en lugar de fallar cuando no puede respetar un ajuste, e informa de cada degradación como un aviso en la ejecución:

- Una traducción de `glossary` o un término de `doNotTranslate` configurado para el locale de destino no se aplica (DeepL solo usa un id de glosario creado de antemano), informado como `GLOSSARY_IGNORED`. Las traducciones prohibidas por sí solas no generan aviso: se comprueban después de traducir, nunca se aplican.
- `tone` se asigna a la formalidad de DeepL: `formal` pasa a más formal, `informal` a menos formal, `neutral` o un tono ausente se omite. Con una clave del nivel gratuito, la formalidad no está soportada, así que un tono distinto del predeterminado se degrada al predeterminado, informado como `FORMALITY_DOWNGRADED`. Tampoco todos los idiomas de destino tienen control de formalidad (el sueco y el chino no lo tienen, por ejemplo): desde 0.12.0 verbatra pide la formalidad con `prefer_more` y `prefer_less` de DeepL, así que un idioma así vuelve al registro predeterminado de DeepL con un aviso `FORMALITY_DOWNGRADED` en lugar de hacer fallar la petición.

<AvailableFrom version="0.12.0" />

verbatra incluye la tabla de idiomas de DeepL, fechada y tomada de [la documentación de DeepL](https://developers.deepl.com/docs/getting-started/supported-languages), y comprueba tu configuración contra ella antes de que una ejecución gaste nada: un idioma de origen o de destino que DeepL no incluye en su lista se rechaza con `LOCALE_UNSUPPORTED_BY_PROVIDER`, y un tono o un glosario que DeepL no puede aplicar para un locale es un aviso. Un `glossaryId` nativo solo funciona cuando los dos idiomas están en la lista de glosarios de DeepL (32 idiomas, como `DE`, `EN`, `FR`, `JA` y `ZH`). Consulta [Comprobar el soporte de idiomas de un proveedor](#comprobar-el-soporte-de-idiomas-de-un-proveedor).

<Callout title="DeepL y los placeholders">
DeepL no puede preservar placeholders ni tokens ICU, así que no envía las cadenas que los contienen: esas entradas se retienen (quedan sin traducir) y se informan con un aviso `PLACEHOLDER_UNSUPPORTED`. Las cadenas sin placeholders se traducen con normalidad. Para traducir cadenas con placeholders, usa un proveedor LLM (Anthropic, OpenAI, Gemini u openai-compatible).
</Callout>

## Google Cloud Translation

<AvailableFrom version="0.10.0" />

```ts
provider: {
  id: "google-translate",
  options: {},
}
```

Lee `GOOGLE_TRANSLATE_API_KEY`. Como DeepL, Google Cloud Translation es una API de traducción automática, no un LLM: no tiene campo `model`, ni límite de tokens de salida, ni opción de glosario en v1. Admite dos opciones, ambas opcionales: `requestTimeoutMs` (consulta [Tiempo de espera de petición](#tiempo-de-espera-de-petición)) y `localeMap` (consulta [Códigos de locale enviados al proveedor](#códigos-de-locale-enviados-al-proveedor)).

Este proveedor apunta al nivel Basic (v2) de Cloud Translation, autenticado con una clave de API simple de un proyecto de Google Cloud con la Cloud Translation API activada. No usa el nivel Advanced (v3), que se autentica con una cuenta de servicio o Application Default Credentials en lugar de una única variable de entorno, y por tanto no encaja con la regla de verbatra de claves solo por variable de entorno.

Cloud Translation no tiene ajuste de formalidad ni glosario genérico en el nivel Basic, así que un `tone` o `glossary` configurado nunca se aplica. De cada uno se informa con un aviso en lugar de descartarse en silencio:

- `tone` siempre notifica `FORMALITY_DOWNGRADED` cuando se define como `formal` o `informal`; `neutral` o un tono ausente se omite.
- Una traducción de `glossary` o un término de `doNotTranslate` para el locale de destino siempre notifica `GLOSSARY_IGNORED`.

<AvailableFrom version="0.12.0" />

verbatra incluye también la tabla de idiomas de Cloud Translation, fechada y tomada de [la página de idiomas admitidos de Google](https://docs.cloud.google.com/translate/docs/languages), y rechaza un idioma que no está en ella antes de que una ejecución gaste nada. Un código regional cuyo idioma solo aparece en la lista como un todo, como `de-AT` cuando la tabla tiene `de`, se envía tal como está escrito con un aviso, ya que Google puede aceptarlo o generalizarlo. Consulta [Comprobar el soporte de idiomas de un proveedor](#comprobar-el-soporte-de-idiomas-de-un-proveedor).

<Callout title="Google Cloud Translation y los placeholders">
Como DeepL, Google Cloud Translation no puede preservar placeholders ni tokens ICU, así que no envía las cadenas que los contienen: esas entradas se retienen (quedan sin traducir) y se informan con un aviso `PLACEHOLDER_UNSUPPORTED`. Las cadenas sin placeholders se traducen con normalidad. Para traducir cadenas con placeholders, usa un proveedor LLM (Anthropic, OpenAI, Gemini u openai-compatible).
</Callout>

<Callout title="Google Cloud Translation y los códigos de locale">
El código que se envía para cada locale (tras la [asignación de códigos de locale](#códigos-de-locale-enviados-al-proveedor)) se valida como BCP-47 bien formado antes de cualquier llamada de red (por ejemplo, `en` o `pt-BR`); un código malformado como `en_US` falla con `INVALID_REQUEST` nombrando el código en cuestión. A diferencia de DeepL, Cloud Translation permite códigos de destino regionales libremente, así que esta comprobación es solo de sintaxis, no una lista fija de valores permitidos. Un locale de destino o un par de idiomas que la propia API de Google no soporte igualmente falla como `INVALID_REQUEST` estructurado en cuanto la petición llega a Google.
</Callout>

## openai-compatible

Apunta verbatra a un servidor que habla la API Chat Completions de OpenAI: LM Studio, Ollama, vLLM y similares funcionan todos. El id nombra el protocolo de comunicación, no dónde se ejecuta el servidor, así que una API alojada que hable el mismo protocolo también encaja aquí.

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct", // example: whatever your server exposes
    maxOutputTokens: 1024,
  },
}
```

`baseUrl`, `model` y `maxOutputTokens` son obligatorios. A diferencia de todos los demás proveedores, `baseUrl` vive en la configuración y no en el entorno: es una dirección de red que ya conoces (una IP de LAN o `localhost`), no un secreto. Debe ser una URL absoluta válida con esquema `http` o `https`; cualquier otra cosa, incluido un esquema ausente, hace fallar la validación de la configuración de inmediato.

`baseUrl` debe incluir el segmento de ruta de la API de tu servidor, normalmente `/v1`: LM Studio, Ollama y vLLM sirven todas sus rutas compatibles con OpenAI bajo `/v1`. Un `baseUrl` sin él sigue siendo una URL sintácticamente válida, así que pasa la validación de la configuración y en su lugar falla en tiempo de petición al llegar a la ruta equivocada.

Una API alojada que hable el mismo protocolo funciona igual. La API de chat completions de Mistral es un ejemplo:

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "https://api.mistral.ai/v1",
    model: "mistral-large-latest", // example: check Mistral's current model list
    maxOutputTokens: 4096,
    apiKeyEnvVar: "MISTRAL_API_KEY",
  },
}
```

`apiKeyEnvVar` nombra la variable de entorno que contiene tu clave para ese servidor. Es el mismo proveedor `openai-compatible` apuntado a otro endpoint, no un proveedor dedicado de Mistral. El `requestTimeoutMs` opcional también se acepta aquí, y es en este proveedor donde más importa: consulta [Tiempo de espera de petición](#tiempo-de-espera-de-petición).

### Las claves son opcionales

La mayoría de los servidores de inferencia locales no necesitan clave de API, así que `openai-compatible` resuelve su clave en tres niveles, en orden:

1. **`apiKeyEnvVar`**, un campo opcional de la configuración que nombra una variable de entorno de la que leer una clave real. Si defines este campo y su variable nombrada no está definida o está vacía, verbatra falla con `MISSING_API_KEY` en lugar de caer en silencio al siguiente nivel, porque dijiste explícitamente que se requiere una clave.
2. **`OPENAI_COMPATIBLE_API_KEY`**, una variable de entorno por convención, leída cuando `apiKeyEnvVar` no está definido. Si está definida y no vacía, verbatra la usa; si no, verbatra sigue adelante sin error.
3. **El placeholder `"local"`**, enviado cuando ninguno de los anteriores resuelve nada. Es una cadena fija y no secreta, no una clave real, y es exactamente lo que hace que un servidor local sin clave funcione con cero configuración.

`apiKeyEnvVar` nunca puede nombrar `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `DEEPL_API_KEY` ni `GOOGLE_TRANSLATE_API_KEY`: la validación de la configuración lo rechaza de plano, así que una configuración no puede apuntar este proveedor a la clave de un proveedor alojado por su nombre. El cliente tampoco lee nunca `OPENAI_API_KEY` por su cuenta y siempre pasa un valor de clave explícito al SDK subyacente, así que una clave alojada nunca puede llegar a un `baseUrl` personalizado.

<Callout type="warn" title="Una clave real sobre http en claro viaja sin cifrar">
verbatra permite `http://` en claro hacia cualquier host, incluida una dirección de LAN, sin más restricción que el esquema http o https. Esto es intencional y seguro en el caso común sin clave: no hay nada secreto en la comunicación.

Es un riesgo real solo cuando además configuras una clave (vía `apiKeyEnvVar` u `OPENAI_COMPATIBLE_API_KEY`) **y** `baseUrl` es `http://` en claro hacia un host que no es loopback: esa clave entonces viaja por tu red sin cifrar. Si tu servidor requiere una clave real y es accesible más allá de localhost, usa `https://` para él. verbatra hoy no detecta esta combinación ni avisa de ella; trátala como tu propia responsabilidad.
</Callout>

### Elegir un modelo local

Prefiere un modelo ajustado por instrucciones, sin razonamiento y con buena cobertura multilingüe. verbatra pide un único objeto JSON estricto y lo valida, así que quieres un modelo que siga de forma fiable las indicaciones de formato. `qwen2.5-14b-instruct` es un valor por defecto razonable; elige el mayor modelo de ese tipo que tu hardware ejecute bien.

<Callout type="warn" title="Evita los modelos de razonamiento y muy cuantizados">
Los modelos de razonamiento (thinking) y las compilaciones muy cuantizadas (qat o de pocos bits) son aquí las fuentes de fallo habituales: tienden a emitir prosa de razonamiento alrededor de la respuesta o a devolver JSON truncado, y cualquiera de las dos cosas hace fallar las comprobaciones de esquema e integridad de verbatra. Si un modelo con razonamiento es inevitable, dale espacio para razonar y responder: consulta [Límites de tokens de salida](#límites-de-tokens-de-salida) para el ajuste de `maxOutputTokens` y `maxBatchSize`.
</Callout>

Un modelo local malo falla de forma ruidosa, no en silencio: verbatra valida cada respuesta del proveedor contra un esquema canónico más las comprobaciones de integridad, así que un modelo que emite prosa de razonamiento o JSON truncado se rechaza con un error `INVALID_RESPONSE` u `OUTPUT_TRUNCATED` en lugar de escribir una traducción corrupta.

### Parseo tolerante para modelos locales y más pequeños

`openai-compatible` solicita el mismo formato de respuesta estricto y restringido por esquema que el proveedor alojado `openai`. La única diferencia está a la vuelta: los modelos locales y más pequeños tienden más a envolver una respuesta por lo demás correcta en prosa o en un bloque de código Markdown a pesar de que se les pide que no, así que `openai-compatible` extrae el primer objeto JSON balanceado en cualquier parte de la respuesta antes de parsear, cosa que el proveedor alojado no hace. Su salida pasa igualmente por exactamente la misma validación de esquema y las mismas comprobaciones de integridad que la de cualquier otro proveedor: la salida de un modelo local es entrada no confiable, y una respuesta malformada o con placeholders discordantes se rechaza de la misma manera.

<Callout title="Genéralo con verbatra init">
`verbatra init --provider openai-compatible --base-url <url> --model <name>` escribe este bloque por ti, con `maxOutputTokens: 4096`. Añade `--api-key-env-var <NAME>` cuando el servidor necesite una clave bajo una variable propia; `init` escribe solo el nombre de la variable, nunca un valor. Consulta [verbatra init](/docs/cli/init#proveedores). Todo lo demás de esta página (glosario, tono, límites de tokens de salida) le aplica como a cualquier proveedor LLM.
</Callout>

## LibreTranslate

<AvailableFrom version="0.12.0" />

Apunta verbatra a un servidor [LibreTranslate](https://github.com/LibreTranslate/LibreTranslate) autoalojado. LibreTranslate es traducción automática neuronal clásica (modelos de Argos Translate), no un modelo de lenguaje, así que encaja en una empresa que prohíbe los LLM pero acepta traducción automática que ejecuta ella misma. verbatra solo llama a su API HTTP; la licencia AGPL-3.0 del propio servidor no se extiende a tu proyecto.

```ts
provider: {
  id: "libretranslate",
  options: {
    baseUrl: "http://localhost:5000",
  },
}
```

`baseUrl` es obligatorio: la raíz de la API de LibreTranslate, sin `/translate`, como `http://localhost:5000` o `https://translate.internal.example/api`. Tiene que ser una URL absoluta `http` o `https`. Dos opciones son opcionales: `requestTimeoutMs` (consulta [Tiempo de espera de petición](#tiempo-de-espera-de-petición)) y `localeMap` (consulta [Códigos de locale enviados al proveedor](#códigos-de-locale-enviados-al-proveedor)). No hay modelo ni límite de tokens de salida. Los idiomas que ofrece son los modelos instalados en tu servidor, así que arráncalo con los que necesites, por ejemplo:

```bash
docker run -p 5000:5000 libretranslate/libretranslate --load-only en,de,fr
```

La clave es opcional. Un servidor arrancado sin `--api-keys` acepta todas las peticiones, así que verbatra solo lee `LIBRETRANSLATE_API_KEY` cuando está definida y la envía como `api_key` de la petición; si no lo está, no se envía nada y `verbatra doctor` supera su comprobación de la clave de API. Un servidor que sí exige una clave hace fallar la ejecución con `MISSING_API_KEY` nombrando `LIBRETRANSLATE_API_KEY`, y una clave que rechaza falla con `AUTH_FAILED`. `verbatra init --provider libretranslate --base-url <url>` escribe este bloque.

LibreTranslate no tiene control de formalidad ni glosario, así que un tono `formal` o `informal` notifica `FORMALITY_DOWNGRADED`, y una traducción de glosario o un término de `doNotTranslate` notifica `GLOSSARY_IGNORED`. Aun así, su salida se comprueba contra el glosario para la revisión.

<Callout title="LibreTranslate y los placeholders">
A diferencia de DeepL y Google Cloud Translation, LibreTranslate traduce las cadenas con placeholders. verbatra sustituye cada placeholder por un marcador numerado antes de enviarla, así que `Hello {{name}}` viaja como `Hello {0}`, y vuelve a poner el original después, dondequiera que el motor haya movido el marcador. Un valor solo vuelve cuando cada marcador regresa exactamente una vez; si no, se retiene con un aviso `PLACEHOLDER_UNSUPPORTED` en lugar de escribirse, y la comprobación de integridad sigue ejecutándose sobre todo lo que se escribe. Un valor que aún lleva sintaxis ICU una vez enmascarados sus placeholders (un `plural` o un `select`, por ejemplo) nunca se envía: se retiene de la misma manera. Tradúcelos a mano o con un proveedor LLM.
</Callout>

Antes de una ejecución, verbatra no puede saber qué modelos tiene instalados tu servidor, así que cada locale se evalúa como `unverified` con un aviso `LOCALE_UNVERIFIED_BY_PROVIDER`, nunca se rechaza. `verbatra doctor --locales --live` obtiene la propia lista `/languages` del servidor y evalúa cada locale contra ella. Consulta [Comprobar el soporte de idiomas de un proveedor](#comprobar-el-soporte-de-idiomas-de-un-proveedor).

## none

<AvailableFrom version="0.12.0" />

Desactiva la traducción automática por política. Úsalo cuando un NDA o una norma de la empresa prohíbe enviar cadenas a cualquier servicio de traducción, así que cada traducción tiene que venir de una persona.

```ts
provider: { id: "none" }
```

`options` puede omitirse; si se indica, debe ser `{}`. Nunca se construye un proveedor, no se lee ninguna clave de API y no se hace ninguna petición de red. `translate` y `watch` rellenan una clave solo desde [la memoria de traducción](/docs/the-cache) e informan de cualquier otra clave ausente o cambiada como `unfilled`, sin tocarla; `translate` termina entonces con el código `3`. [Studio](/docs/cli/studio) y el [servidor MCP](/docs/cli/mcp) nunca ofrecen sus acciones que gastan en el proveedor, ni siquiera con `--allow-spend`, y `retranslateEntry` del SDK falla con `MACHINE_TRANSLATION_DISABLED`. Su memoria de traducción es un compartimento propio, así que un proyecto que cambia desde un proveedor automático empieza vacío salvo que traspase entradas con `tmx export` antes del cambio y `tmx import` después. `verbatra init --provider none` lo prepara. El flujo completo está en [Flujo solo humano](/docs/human-only-workflow).

## Tono y glosario entre proveedores

Los campos opcionales `tone` y `glossary` de la configuración (consulta [Archivo de configuración](/docs/config-file)) se aplican por proveedor:

- **Tono.** Los proveedores LLM (Anthropic, OpenAI, Gemini y openai-compatible) reciben el tono con la petición y se les instruye para respetarlo. DeepL lo asigna a la formalidad, con la degradación del nivel gratuito descrita arriba. Google Cloud Translation y LibreTranslate no tienen ningún control de formalidad, así que un tono no neutro siempre notifica `FORMALITY_DOWNGRADED`.
- **Glosario.** Cada petición lleva solo los términos del glosario de su propio locale de destino. Los proveedores LLM reciben las traducciones, las traducciones `forbidden`, los términos de `doNotTranslate` y las notas como datos, y se les instruye para tratar las traducciones como vinculantes, no usar nunca una traducción prohibida y copiar tal cual los términos de `doNotTranslate`. DeepL no puede aplicarlos (con un aviso `GLOSSARY_IGNORED`) y aplica solo su `glossaryId` nativo. Google Cloud Translation y LibreTranslate no tienen glosario alguno, así que una traducción o un término de `doNotTranslate` siempre notifica `GLOSSARY_IGNORED`. Sea cual sea el proveedor, su salida se comprueba contra los términos del locale y se marca para revisión con `GLOSSARY_TERM_MISSED` o `GLOSSARY_FORBIDDEN_TERM`.

## Comportamiento que todo proveedor comparte

### Lotes

El trabajo de un locale se divide en sublotes secuenciales de como mucho `maxBatchSize` entradas (por defecto 50; consulta [Archivo de configuración](/docs/config-file)), así que una petición sobredimensionada no puede hacer fallar el locale entero. Un sublote fallido se retiene y se reintenta automáticamente en la siguiente ejecución mientras los demás sublotes siguen avanzando. DeepL y Google Cloud Translation además reparten un sublote entre tantas peticiones como exijan sus propios topes por petición, de forma transparente.

### Reintentos

Los fallos transitorios (una respuesta de límite de tasa o un error de servidor) se reintentan automáticamente con una pequeña espera: los clientes de los SDK de OpenAI, Anthropic y DeepL reintentan por defecto, y verbatra añade un reintento propio equivalente para Gemini, cuyo SDK no lo hace. Los reintentos suavizan tropiezos momentáneos; un fallo sostenido sigue aflorando como un error estructurado. Google Cloud Translation y LibreTranslate no tienen reintento alguno hoy, en ninguna capa: una respuesta con límite de tasa o error de servidor aflora de inmediato como `RATE_LIMITED` o `PROVIDER_UNAVAILABLE`, y sigue aplicando el comportamiento habitual de recoger un sublote retenido en la siguiente ejecución.

### Tiempo de espera de petición

Cada proveedor acota cada petición saliente, para que un servidor que acepta la conexión pero nunca responde no pueda atascar una ejecución ni mantener abierto el bloqueo de escritura de un locale. Ese límite es `requestTimeoutMs`, un entero positivo opcional en milisegundos que se acepta en las `options` de los siete proveedores (`anthropic`, `openai`, `gemini`, `deepl`, `google-translate`, `openai-compatible` y `libretranslate`):

```ts
provider: {
  id: "openai-compatible",
  options: {
    baseUrl: "http://192.168.178.74:1234/v1",
    model: "qwen2.5-14b-instruct",
    maxOutputTokens: 1024,
    requestTimeoutMs: 300000, // 5 minutes
  },
}
```

Si lo omites, verbatra aplica su propio valor por defecto de `120000` ms (dos minutos): suficiente para no cortar un lote grande legítimamente lento, y lo bastante corto para que un servidor colgado pero vivo no bloquee un locale indefinidamente. Súbelo cuando un modelo local lento o un `maxBatchSize` grande necesiten más tiempo; bájalo para fallar antes. El límite se aplica a cada intento, no a la llamada completa. El cliente de un proveedor reintenta una respuesta HTTP `429` o `5xx` unas cuantas veces con una pausa corta (los clientes de Anthropic, OpenAI, `openai-compatible` y Gemini también reintentan un intento que agotó el tiempo, y todos menos Gemini reintentan además un error de conexión), y cada reintento vuelve a tener el `requestTimeoutMs` completo. Así, una llamada que sigue recibiendo un límite de tasa, un error del servidor o una conexión rechazada falla con esa causa (`RATE_LIMITED`, `PROVIDER_UNAVAILABLE` o `PROVIDER_ERROR` indicando el rechazo), no con `TIMEOUT`: `TIMEOUT` significa que un intento no recibió respuesta dentro del límite. La contrapartida es que un servidor colgado tarda más en darse por perdido: hasta tres intentos de `requestTimeoutMs` cada uno, más las pausas, con Anthropic, OpenAI, `openai-compatible` y Gemini. Cuando una llamada falla, solo afecta a su propio sublote, así que las claves vuelven en la siguiente ejecución.

El cliente de DeepL usa `requestTimeoutMs` como espera mínima de cada uno de sus intentos y hace hasta cinco, así que un endpoint de DeepL colgado es el que más tarda en fallar. Además es la única excepción a la cancelación: su cliente no puede abortar una petición ya en vuelo, así que cuando interrumpes una ejecución, la petición que ya envió se resuelve en DeepL. Google Cloud Translation y LibreTranslate envían cada uno una sola petición HTTP simple sin reintentos, así que el límite cubre la llamada completa, y cancelan de inmediato como los proveedores LLM.

### Códigos de locale enviados al proveedor

<AvailableFrom version="0.12.0" />

Tus archivos, el archivo de bloqueo y la memoria de traducción siempre usan los códigos de locale de tu configuración. Los proveedores no siempre coinciden con ellos: DeepL recibe un idioma de origen sin su región y llama `ZH-HANT` al chino tradicional donde tu configuración dice `zh-Hant` o `zh-TW`. Por eso verbatra traduce el código en el último momento, solo para la petición que envía:

| Proveedor | Locale de origen | Locale de destino |
| --- | --- | --- |
| DeepL | Solo el idioma: `en-US` se envía como `EN`, `zh-Hant-TW` como `ZH`. | `zh-Hant`, `zh-TW`, `zh-HK` y `zh-MO` se envían como `ZH-HANT`; `zh-Hans`, `zh-CN` y `zh-SG` como `ZH-HANS`. Una variante de DeepL se conserva (`EN-GB`, `EN-US`, `PT-BR`, `PT-PT`, `ES-419`, `FR-CA`, `FR-FR`, `DE-CH`, `DE-DE`). El español con una región de Latinoamérica o del Caribe (`MX`, `AR`, `CO`, `CL`, `PE`, `VE`, `EC`, `GT`, `CU`, `BO`, `DO`, `HN`, `PY`, `SV`, `NI`, `CR`, `PA`, `UY`, `PR`, `US`, o `419`) se envía como `ES-419`, así que `es-MX` se convierte en `ES-419`. Cualquier otra región o escritura se descarta: `de-AT` se envía como `DE`, `es-ES` como `ES`. |
| Google Cloud Translation | `zh-Hant` (y `zh-HK`, `zh-MO`) se envía como `zh-TW`, `zh-Hans` (y `zh-SG`) como `zh-CN`, y `nb` como `no`. Cualquier otro código se envía tal como está escrito. | Igual que el origen. |
| LibreTranslate | Solo el idioma: `de-AT` se envía como `de`, `en-US` como `en`. `pt-BR` se conserva, y el chino se envía como `zh-Hans` o `zh-Hant` (`zh-TW` pasa a `zh-Hant`). | Igual que el origen. |
| Anthropic, OpenAI, Gemini, openai-compatible | Tal como está escrito, con el nombre en inglés del idioma (ver más abajo). | Tal como está escrito, con el nombre en inglés del idioma, la escritura y la región (ver más abajo). |

DeepL no tiene un inglés ni un portugués genéricos como destino, así que un destino que acaba siendo un `en` o `pt` escueto (por ejemplo `en-AU`) se rechaza con `LOCALE_UNSUPPORTED_BY_PROVIDER` antes de que empiece la ejecución (consulta [Comprobar el soporte de idiomas de un proveedor](#comprobar-el-soporte-de-idiomas-de-un-proveedor)). Asígnalo a `EN-GB`, `EN-US`, `PT-BR` o `PT-PT`; una entrada de `localeMap` que siga enviando un `EN` o `PT` escueto falla con `INVALID_REQUEST` antes de cualquier petición.

Un proveedor LLM recibe además el nombre en inglés de cada locale, buscado a partir del locale de tu configuración: `sr-Latn` llega con `{ "name": "Serbian (Latin)", "script": "Latin" }` y `pt-BR` con `{ "name": "Portuguese (Brazil)", "region": "Brazil" }`, y una regla de sistema fija le pide al modelo que escriba en la escritura y la variante regional indicadas. Un código para el que Node.js no tiene nombre se envía sin él. [Seguridad de la traducción](/docs/translation-safety) muestra la forma completa.

Cuando la normalización integrada no es lo que quieres, añade `localeMap` a las `options` del proveedor. Asigna a un locale de tu configuración el código exacto que recibe el proveedor, y una entrada siempre gana a la normalización integrada:

```ts
provider: {
  id: "deepl",
  options: {
    localeMap: {
      "en-AU": "EN-GB",
      "fr-BE": "FR-FR",
    },
  },
}
```

Cada clave debe ser `sourceLocale` o uno de los `targetLocales`, escrita exactamente como en tu configuración; cualquier otra clave hace fallar la carga de la configuración con `CONFIG_INVALID`, nombrando la clave. Cada valor debe ser una cadena no vacía de 64 caracteres como máximo, que verbatra envía sin cambios: DeepL y Google Cloud Translation la reciben como código de idioma, y un proveedor LLM la recibe en la petición en lugar del código de locale, así que ahí también funciona un valor como `"pt-BR (Brazilian Portuguese)"`. Los nombres de idioma en inglés que recibe un proveedor LLM siguen saliendo de la clave, el locale de tu configuración, no del valor. Un valor que el propio proveedor rechace hace fallar ese sublote con un error estructurado, como cualquier otro fallo del proveedor. `localeMap` lo aceptan todos los proveedores salvo `none`, y solo bajo `options`: escrito directamente bajo `provider`, hace fallar la carga de la configuración con `CONFIG_INVALID` (desde 0.12.0). Cambiarlo no vuelve a traducir las claves que ya están al día: solo las cadenas de origen nuevas o cambiadas se envían con el código nuevo. Un `localeMap` no vacío forma parte de la huella de la [memoria de traducción](/docs/the-cache), así que cambiarlo abre un compartimento de memoria aparte: las traducciones hechas con los códigos antiguos no se reutilizan para los nuevos.

### Comprobar el soporte de idiomas de un proveedor

<AvailableFrom version="0.12.0" />

Un locale que el proveedor no puede traducir antes solo fallaba al enviar su petición, cuando otros locales quizá ya se habían pagado. Ahora verbatra comprueba cada locale configurado antes de gastar nada, contra lo que sabe del proveedor configurado:

| Proveedor | Se evalúa contra | Se rechaza antes de la ejecución | Genera un aviso |
| --- | --- | --- | --- |
| DeepL | La tabla de idiomas de DeepL que incluye verbatra, con el soporte de glosario y de formalidad por idioma | Un idioma de origen o de destino que DeepL no incluye en su lista | Un glosario para un par fuera de los idiomas de glosario de DeepL, un tono para un idioma sin formalidad, un código que solo aparece en parte en la lista |
| Google Cloud Translation | La tabla de idiomas de Cloud Translation (NMT) que incluye verbatra | Un idioma que Google no incluye en su lista | Cualquier glosario, cualquier tono `formal` o `informal` (el nivel Basic no tiene ninguno de los dos), un código regional cuyo idioma solo aparece en la lista como un todo |
| LibreTranslate | Nada antes de una ejecución: los idiomas son los modelos instalados en tu servidor. Con `doctor --live`, la propia lista `/languages` del servidor | Nunca antes de una ejecución | Cada locale, como `LOCALE_UNVERIFIED_BY_PROVIDER`, hasta que `doctor --live` lo comprueba; cualquier glosario, cualquier tono `formal` o `informal` |
| Anthropic, OpenAI, Gemini, openai-compatible | Nada: un LLM acepta cualquier idioma | Nunca | Un idioma fuera de la lista de idiomas bien probados de [Soporte de idiomas](/docs/language-support#comprobar-el-soporte-antes-de-una-ejecución) |
| none | No aplica: no se llama a ningún proveedor | Nunca | Nunca |

[`verbatra doctor`](/docs/cli/doctor#soporte-de-locales) informa del veredicto de cada locale en su comprobación Locale support, y `verbatra doctor --locales` imprime el código con el que se envía cada locale, si el proveedor lo admite y si puede aplicar un glosario y un ajuste de formalidad para él. `verbatra translate` (también una ejecución en seco y una estimación), `watch` al arrancar y la retraducción de una sola clave rechazan un locale no admitido con `LOCALE_UNSUPPORTED_BY_PROVIDER` y salen con `2`, antes de construir ningún proveedor o leer ninguna clave, así que no empieza ningún locale de la ejecución. Los avisos nunca rechazan nada: `translate` los informa como avisos en el locale afectado (`LOCALE_UNVERIFIED_BY_PROVIDER`, `LOCALE_NOT_WELL_TESTED`, `GLOSSARY_UNSUPPORTED_BY_PROVIDER`, `FORMALITY_UNSUPPORTED_BY_PROVIDER`).

Las tablas son copias fechadas de la documentación de los proveedores, y los proveedores añaden idiomas. `verbatra doctor --live` obtiene primero la lista actual del proveedor, del endpoint `/v3/languages` de DeepL, del endpoint `languages` de Cloud Translation o del `/languages` de tu servidor LibreTranslate, lo que no consume cuota de traducción. Solo envía esa única petición cuando la variable de la clave de API del proveedor está definida (LibreTranslate no necesita ninguna para ello) y la [política de red](/docs/network-policy) permite el host del proveedor; si no, explica por qué y usa la tabla incluida. La lista en vivo solo se usa para el informe; `translate` siempre evalúa contra la tabla incluida. Para usar un idioma que el proveedor añadió después de la fecha de esa tabla, asigna el locale explícitamente en `localeMap`: un código de una entrada explícita se considera fiable y se envía con un aviso en lugar de rechazarse.

### Errores estructurados

Un fallo de proveedor nunca aflora como un error en bruto del SDK, que podría llevar cabeceras de la petición o una clave. verbatra clasifica cada fallo por su estado HTTP o la clase de error del SDK y levanta un error estructurado con un código estable y un mensaje fijo y sin secretos:

| Código | Significado |
| --- | --- |
| `MISSING_API_KEY` | La variable de entorno requerida no está definida o está vacía. El mensaje nombra la variable, nunca un valor. En LibreTranslate, cuya clave es opcional, significa que el servidor exigió una clave y `LIBRETRANSLATE_API_KEY` no está definida. |
| `INVALID_REQUEST` | La petición falló la validación antes de cualquier llamada de red: un campo malformado, un código que DeepL no acepta (una entrada de `localeMap` con un código de origen regional, o un destino que acaba siendo un `en` o `pt` escueto), o un código que no es BCP-47 bien formado para Google Cloud Translation. En LibreTranslate cubre además un idioma para el que tu servidor no tiene modelo y una petición que supera su `--char-limit` o su `--batch-limit`. Corrige la configuración o la petición; reintentar no ayudará. |
| `RATE_LIMITED` | HTTP 429 o un error de límite de tasa del SDK. En Google Cloud Translation, esto también cubre un HTTP 403 cuyo cuerpo nombra un motivo de cuota (un límite diario o por minuto), porque la API de Google reutiliza el 403 tanto para fallos de cuota como de credenciales. Espera y reintenta más tarde, o aumenta la cuota de Cloud Translation de tu proyecto. |
| `TIMEOUT` | Un tiempo de espera de red o de petición; no llegó respuesta a tiempo. Reintentar puede ayudar, y [`requestTimeoutMs`](#tiempo-de-espera-de-petición) sube el límite. |
| `AUTH_FAILED` | HTTP 401 o 403: la clave es inválida, está revocada o carece de permisos. En Google Cloud Translation, comprueba que `GOOGLE_TRANSLATE_API_KEY` sea una clave válida y sin restricciones para un proyecto con la Cloud Translation API activada. Reintentar no ayudará. |
| `PROVIDER_UNAVAILABLE` | HTTP 5xx: el proveedor falló en su propio lado, y la petición en sí nunca tuvo la culpa. Los reintentos de las capas descritas arriba ya absorben un 5xx transitorio, así que uno que llega a este código es una caída sostenida. Espera y reintenta más tarde. |
| `OUTPUT_TRUNCATED` | El modelo alcanzó su límite de tokens de salida; consulta más abajo. |
| `INVALID_RESPONSE` | La salida era malformada, incompleta o falló la reconciliación contra la petición. |
| `PROVIDER_REFUSED` | El modelo se negó a responder. |
| `PROVIDER_BLOCKED` | La petición o la respuesta fue bloqueada o filtrada por seguridad. |
| `PROVIDER_ERROR` | Cualquier cosa inclasificable. Cuando el fallo es un problema de transporte reconocible, el mensaje lo nombra (conexión rechazada, nombre de host no resuelto, conexión cerrada, host inalcanzable, certificado TLS no verificado) y dice qué comprobar; si no, recurre a un mensaje estático y sin secretos. |
| `NETWORK_POLICY_VIOLATION` | La [política de red](/docs/network-policy) rechazó la petición justo antes de enviarla: el nombre de host resolvió a una dirección que la política no permite, o una respuesta redirigió a un host rechazado. El mensaje nombra solo el host. Reintentar no ayuda. |

Un fallo solo afecta a su propio sublote: las claves fallidas se retienen y se recogen de nuevo en la siguiente ejecución.

Para `openai-compatible`, un `PROVIDER_ERROR` nombra además el host y el puerto del `baseUrl` configurado, porque un endpoint que alojas tú mismo es el que de verdad se queda inalcanzable: `The translation provider request to localhost:11434 failed: the connection was refused. Check that the endpoint is running and that the configured host and port are right, then run again.` Solo se usa el componente de host de la URL, así que ninguna ruta, consulta ni información de usuario del `baseUrl` llega jamás a un mensaje. LibreTranslate nombra de la misma manera el host de su `baseUrl`, y Google Cloud Translation informa de la misma manera contra su host fijo, `translation.googleapis.com`; la cadena de consulta que lleva la clave de API tampoco llega nunca a un mensaje.

### Límites de tokens de salida

Los cuatro proveedores LLM limitan cuántos tokens puede producir una sola respuesta. Cuando un modelo se detiene porque alcanzó ese tope, verbatra levanta `OUTPUT_TRUNCATED` en lugar de un fallo genérico de respuesta malformada, con un mensaje fijo:

> The provider stopped because the output-token limit was reached. Reduce the batch size or raise the configured max output tokens.

Cualquiera de las dos palancas lo resuelve: baja `maxBatchSize` en tu configuración para que cada petición produzca una respuesta más pequeña, o sube el tope por respuesta del proveedor (`maxTokens` para Anthropic, `maxOutputTokens` para OpenAI, Gemini y openai-compatible). DeepL, Google Cloud Translation y LibreTranslate no se ven afectados: ninguno tiene un caso de truncado por tokens de salida. verbatra también se recupera por sí solo: cuando un sublote se trunca, lo divide en mitades y lo reintenta, bajando hasta una sola entrada, de modo que las claves que caben en una petición más pequeña se traducen igualmente y solo una entrada aislada que sigue desbordándose se retiene para la siguiente ejecución.

<Callout title="Los modelos de razonamiento gastan el mismo presupuesto">
Un modelo de razonamiento (thinking) gasta sus tokens de razonamiento ocultos del mismo presupuesto de tokens de salida que usa para emitir las traducciones JSON. Puede agotar ese presupuesto solo razonando y detenerse antes de escribir ninguna salida, lo que aparece como `OUTPUT_TRUNCATED`. Si usas un modelo de razonamiento, dale margen de sobra: prefiere un `maxOutputTokens` más alto (`maxTokens` para Anthropic) o un `maxBatchSize` más pequeño para que cada petición tenga espacio tanto para el razonamiento como para la respuesta.
</Callout>

### Señales de revisión

Las traducciones aceptadas de todos los proveedores pasan por las mismas comprobaciones posteriores a la traducción, y un resultado sospechoso (por ejemplo uno idéntico a su origen, o uno que se saltó un término del glosario) se marca hacia la cola de revisión en lugar de rechazarse. Los códigos de motivo y cómo trabajar la cola se cubren en [Seguridad de la traducción](/docs/translation-safety) y [Revisión en Studio](/docs/review-in-studio).
