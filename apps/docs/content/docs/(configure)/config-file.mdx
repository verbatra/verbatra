verbatra reads one small, non-secret config object and validates it before it does any work. This page is the full reference: every key, where the file can live, and how a bad config fails.

<Callout title="Keys come from the environment">
No API key is ever read from this file. Each provider reads its key from an environment variable, so the config stays safe to commit. See [Providers](/docs/providers).
</Callout>

## A minimal config

```ts
import { defineConfig } from "@verbatra/sdk";

export default defineConfig({
  sourceLocale: "en",
  targetLocales: ["de", "fr"],
  format: "i18next-json",
  files: {
    pattern: "locales/{locale}.json",
  },
  provider: {
    id: "gemini",
    options: {
      model: "gemini-2.5-flash", // example model id; use your provider's current one
      maxOutputTokens: 4096,
    },
  },
});
```

`defineConfig` is an identity helper from `@verbatra/sdk`. It returns its argument unchanged and exists only to give you type inference and editor autocomplete.

<Callout title="Model autocomplete in TypeScript">
When you author the config in TypeScript, your editor offers the selected provider's known model IDs for `options.model`, narrowed by the provider `id` you chose. The list comes from that provider's own SDK, so it stays current with the SDK version you have installed, and a model from another provider (for example a Claude model under `id: "gemini"`) is a type error. This is an authoring aid only: at runtime `model` is validated as a non-empty string, so a brand-new model the SDK has not listed yet still works even though the editor flags it. DeepL has no `model` field, and openai-compatible's `model` is whatever your server exposes, so neither is restricted.
</Callout>

## Every key

| Key | Type | Default | Purpose |
| --- | --- | --- | --- |
| `sourceLocale` | string | required | The locale your source strings are written in. |
| `targetLocales` | string array | required | The locales to translate into. |
| `format` | string | required | The format adapter for your locale files. |
| `files.pattern` | string | required | The path to each locale file, with a `{locale}` token. |
| `files.localeStyle` | `"literal"`, `"posix"`, or `"android"` | `"literal"` | How the `{locale}` token is spelled for each locale. |
| `provider` | object | required | The translation provider, selected by `id`. |
| `glossary` | object or string | none | Source terms to preferred target terms, inline or as a JSON file path. |
| `tone` | `"formal"`, `"informal"`, or `"neutral"` | none | The register translations should use. |
| `prune` | boolean | `false` | Remove orphaned keys from target files and the lock. |
| `generatePlurals` | boolean | `false` | Synthesize the CLDR plural forms a target language needs. |
| `fuzzyCache` | object | off | Reuse a translation for a source string that changed only slightly. |
| `maxBatchSize` | positive integer | `50` | The maximum entries sent in a single provider request. |
| `maxLength` | object | none | Per-key maximum lengths for translated values, counted in grapheme clusters. |
| `maxTokens` | positive integer | none | A whole-run token budget across every provider call. |
| `budgetBehavior` | `"warn"` or `"stop"` | `"warn"` | What happens once `maxTokens` is reached. |
| `rates` | object | none | Dated provider rates, so `translate --estimate` can report a currency figure. |
| `extract` | object | none | Source-scanning settings for [`verbatra extract`](/docs/cli/extract), `verbatra doctor --literals`, and `verbatra diff --unused`: the framework, the source roots, and the literal and unused-key ignore lists. |
| `$schema` | string | none | A pointer to the JSON Schema document, for editors only. Ignored at runtime. |

Unknown top-level keys are rejected, with `$schema` as the single exception. This is also why an API key cannot live in the config: keys come from the environment, not the file.

### Locales and files

- **`sourceLocale`** must be a non-empty string.
- **`targetLocales`** must contain at least one locale, must not include `sourceLocale`, and no two entries may be case-insensitively equal (for example `["de", "DE"]` is rejected), since each locale becomes its own Excel worksheet name on export.
- **`format`** is one of `i18next-json`, `vue-i18n-json`, `next-intl-json`, `ngx-translate-json`, `xliff`, `yaml`, `arb`, `properties`, `apple-strings`, `apple-xcstrings`, `android-xml`, `gettext-po`, `ini`, or `resx`, or a `custom:` identifier naming a format supplied by an adapter from outside verbatra. See [Formats](/docs/formats) and [Custom format adapters](/docs/custom-format-adapters).
- **`files.pattern`** must contain the `{locale}` token, which verbatra replaces with each locale: `locales/{locale}.json` resolves to `locales/de.json`. Paths resolve against the working directory. The pattern is a literal path, not a glob, and `{locale}` is the only token it understands, so one config addresses exactly one file per locale. If your project splits strings across several namespace files per locale, see [Namespace layouts](/docs/formats#namespace-layouts). The one exception is `apple-xcstrings`, where every locale shares one catalogue file: the token is still required in the pattern, but it resolves to the same path regardless of locale. See [Xcode String Catalogs](/docs/formats#xcode-string-catalogs-xcstrings).
- **`files.localeStyle`** decides what the token expands to:
  - `literal`, the default, uses the configured tag as written, which is what the JSON, YAML,
    XLIFF, ARB, properties, and Apple `.lproj` layouts all need.
  - `posix` replaces `-` with `_`, for gettext (`locale/pt_BR/LC_MESSAGES/messages.po`) and the
    Java `messages_{locale}.properties` layout.
  - `android` expands the token to a whole Android resource directory, written as
    `res/{locale}/strings.xml`: `values` for the source locale, then `values-de`, `values-pt-rBR`,
    and `values-b+zh+Hans`.

  A style refuses a locale it cannot spell correctly for that style, rather than writing a
  directory the platform would silently ignore.

### provider

An object selected by `id`: `anthropic`, `openai`, `gemini`, `deepl`, or `openai-compatible`. Each provider takes its own `options` (model, token limit, and provider-specific fields), and unknown option keys are rejected. The per-provider options are documented on [Providers](/docs/providers).

### glossary

A map of source terms to preferred target terms, either inline or as a path to a JSON file holding the same shape (a flat object of string keys to string values):

```ts
export default defineConfig({
  // ...
  glossary: {
    "Sign in": "Anmelden",
  },
  // or: glossary: "glossary.json",
});
```

The two forms are mutually exclusive; there is no merge between them. A relative file path resolves against the directory of the loaded config file, or against the working directory when the config is passed as an in-memory override. The file must be UTF-8 encoded and no larger than 1 MiB, and it is read once when the config loads: verbatra does not watch it for changes, so edit it and restart to pick up an update. A missing file, invalid JSON, or a value that is not a flat string map fails config loading with `CONFIG_INVALID`, naming the resolved path.

<AvailableFrom version="0.4.0" pkg="@verbatra/studio" />

The two forms also differ in who can change them. Only the file form can be edited from [Verbatra Studio](/docs/review-in-studio), which rewrites that JSON file one term at a time and never touches your config module; an inline glossary stays read-only there, because it lives inside executable code. Prefer the file form if you want to manage terms from the dashboard.

How the glossary is applied depends on the provider: the LLM providers receive the resolved map with the request and are instructed to treat its terms as binding, while DeepL ignores a term map and applies a glossary configured by id instead. See [Providers](/docs/providers).

### tone

One of `"formal"`, `"informal"`, or `"neutral"`. The LLM providers receive it with the request and are instructed to honor it; DeepL maps it to its formality setting. See [Providers](/docs/providers) for the per-provider details, including DeepL's free-tier degradation.

### prune

Off by default. When true, keys present in a target file but absent from the source (the diff's orphaned keys) are removed from the written file and [the lock file](/docs/the-lock-file). Only orphaned keys are ever removed. A per-run `prune` option on `translate` (the CLI `--prune` flag) overrides the config value.

### generatePlurals

Off by default. When true, verbatra synthesizes the CLDR plural forms a target language requires but the source does not supply (for example Polish few and many). Supported only for i18next-JSON projects translated by an LLM provider; DeepL, non-i18next formats, and unknown target languages fall back to the per-locale plural warning. There is no CLI flag, so set this in the config; the SDK `translate()` input accepts a per-run `generatePlurals` override that takes precedence.

### fuzzyCache

<AvailableFrom version="0.11.0" />

Off unless you set it. `fuzzyCache: { enabled: true }` lets a key whose source text changed reuse the translation of its earlier form instead of going to the provider, as long as the two are at least `threshold` alike. `threshold` is a similarity ratio from `0.5` to `1` and defaults to `0.9`. A reuse is reported separately from an exact cache hit, is always flagged for review with the `FUZZY_CACHE_REUSE` reason, passes the same integrity checks as any other candidate value, and is never written back into the cache. An entry whose numerals differ from the current source is refused whatever it scores. A reused key is written but not locked, so it stays changed and is offered again on every later run until a real translation lands. `threshold` tunes how much provider spend you avoid, not how safe the reuse is; see [the cache](/docs/the-cache) for why, and do not enable this unless someone works the review queue. Config-only: there is no CLI flag, though `--no-cache` bypasses it along with the rest of the cache.

### maxBatchSize

Default `50`. A locale's missing-plus-changed entries are split into sequential sub-batches no larger than this, so one oversized provider request cannot fail the whole locale. A failed sub-batch is withheld and retried next run while the others still make progress. Must be a positive integer; zero, negative, or fractional values are rejected. Config-only: there is no CLI flag and no per-run override.

### maxLength

<AvailableFrom version="0.11.0" />

Optional. A map from translation key to the longest translated value that key may hold, for a string under a layout constraint: a nav label, a button, a table header.

```ts
maxLength: {
  "nav.dashboard": 18,
  "cta.submit": 12,
}
```

This map is the only place a budget is read from. verbatra never derives one from an entry's description or from a format's own length metadata, so a budget is exactly where you wrote it and nothing can quietly override it. Keys are matched literally, not as globs or prefixes, and a key absent from the map has no budget and is never measured.

Length is counted in grapheme clusters: the characters a reader perceives, rather than UTF-16 code units or Unicode code points. An emoji assembled from several code points counts as one, and so does a letter followed by a combining accent. A CJK character also counts as one, even though most fonts render it about twice as wide as a Latin letter, so set budgets for those locales with that in mind. The value is measured exactly as written, leading and trailing whitespace included, and the comparison is inclusive: a value of exactly the budget passes, one grapheme more does not.

A budget is checked whenever `translate` produces a value for that key: a fresh translation, a value reused from the cache, and a value fanned out to a key that shares its source text. It is not a sweep over the whole catalog. A key that is already translated and still in step with its source is not retranslated, so it is not measured either, and adding a budget to a finished project therefore flags nothing until that key's source text next changes. To measure every current translation against its budget right now, run [`verbatra export --include-unchanged`](/docs/cli/export): the export recomputes the review columns for every row it writes, and the flag is what puts the already up-to-date keys in the file. A plain `export` writes only the missing and stale rows, so it would skip exactly the keys this paragraph is about.

A budget must be a positive integer. Exceeding it is advisory, never blocking: the translation is still written to the locale file and still recorded in the lock file, and the key is reported as `MAX_LENGTH_EXCEEDED` on the run summary's `needsReview` list, in Studio's Review queue, and in the workbook's review columns. See [Translation safety](/docs/translation-safety).

### maxTokens and budgetBehavior

`maxTokens` is a whole-run token budget: input plus output tokens, summed across every provider call (main translation and plural generation alike) and across every target locale. Config-only, no CLI flag.

`budgetBehavior` decides what happens once the ceiling is reached:

- `"warn"` (the default) counts the spend, flags the overrun, and lets the run continue exactly as if no budget were configured. Nothing is withheld.
- `"stop"` turns the figure into a ceiling. Before each provider request the run projects what that request will cost, using the same projection [the pre-run estimate](/docs/estimating-cost) reports, and refuses to send one that would take the run past `maxTokens`. That request's keys are withheld, and so is every not-yet-attempted key for the rest of the run: the current locale's remaining candidates, and every later target locale's candidates entirely (their diff and orphan reporting still runs; only the provider call is skipped). Withheld keys keep their prior lock hash and are retried automatically next run, the same way a failed provider call already is.

Every request the run sends is checked this way, including each half of a request verbatra re-splits after a truncated response, so a cascade of retries cannot outrun a single reservation. After each request the counted total is reconciled to the usage the provider actually reported, because the provider is the authority on what was billed. A request that reports more than it was projected to cost lands that difference after the fact, so a run can finish above `maxTokens` by the last admitted request's difference, and by no more: nothing further is sent once it does. Two things sit outside what a reservation can bound, because they happen inside a request it already admitted: the provider layer sends one repair call of its own when keys come back missing, so one admitted batch can cost up to about twice its projection, and the count is only as good as what the provider reports. Both land at reconciliation, and nothing further is admitted once they do. A request that fails or comes back truncated keeps its whole projection charged rather than being refunded, because such a call has usually already billed for its prompt. Work already translated stays written and locked, and a withheld key keeps the baseline it had, so a stopped run leaves no half-written locale file and no lock entry claiming work that was withheld.

The ceiling bounds one run, not a session, and it covers `translate` and nothing else. `watch` starts a fresh budget for every run it triggers, so a watch session can spend up to `maxTokens` again on each source edit; use it to bound a run, not a day's work. Retranslating a single entry from [the Studio dashboard](/docs/studio) or the agent tools runs on its own path with its own provider, and no budget caps that spend.

Setting `maxTokens` also constrains how a run may be parallelized: a live run that combines it with `--concurrency` above `1` is refused with exit `2` (`CONCURRENCY_BUDGET_CONFLICT`) before any provider call. The ceiling itself would still hold, but which locale loses its remaining work would depend on the order the locales happen to interleave, so the same project would not produce the same run twice. A dry run is exempt. Drop the budget or leave concurrency at `1`.

Under `"warn"` a budget trip never changes the command's exit code. Under `"stop"` it can: a locale whose keys were withheld is reported as `partial` when some keys still landed and `failed` when none did, and both exit `1`. `budgetBehavior` without `maxTokens` is accepted and has no effect. A provider that reports no token usage of its own (DeepL, Google Cloud Translation) is budgeted from the projection instead, so a ceiling set against one of them withholds work like any other; `supported: false` on the run summary's `budget` says the figure is verbatra's own count rather than the provider's.

The projection includes a fixed allowance for the prompt verbatra sends an LLM provider (its system rules and response schema), and that allowance is added for DeepL and Google Cloud Translation too, even though they receive no prompt. A request is projected as a whole batch, so under `"stop"` a `maxTokens` below what one batch projects refuses that batch on every run, and the run never gets past it. The refusal notice says so when it happens: lower `maxBatchSize` so each request projects less, or raise `maxTokens`.

<Callout title="Two different maxTokens">
The top-level `maxTokens` is the whole-run budget described here. The Anthropic provider also has its own `options.maxTokens`, which caps a single response. They are unrelated; see [Providers](/docs/providers).
</Callout>

### rates

<AvailableFrom version="0.11.0" />

Optional, and read by nothing but [`verbatra translate --estimate`](/docs/cli/translate). verbatra ships no prices of its own: they belong to a third party and change without notice, so a number baked into a release would go stale quietly. You supply them, and you record the date you read them.

```ts
rates: {
  asOf: "2026-01-15",
  currency: "USD",
  table: {
    "gemini/gemini-2.5-flash": { inputPerMillionTokens: 0.1, outputPerMillionTokens: 0.4 },
    deepl: { perMillionCharacters: 25 },
  },
}
```

`asOf` is a calendar date written `YYYY-MM-DD`, and `currency` a three-letter uppercase code. Both are required, and both are printed beside every figure derived from the card, so a stale number is visibly stale. `table` is keyed by rate key: `provider/model` for a provider configured with a model, and the bare provider id for one without (`deepl`, `google-translate`). A token-billed entry carries `inputPerMillionTokens` and `outputPerMillionTokens`; a character-billed one carries `perMillionCharacters`. Mixing the two shapes in a single entry is rejected, as is a negative rate.

The block changes nothing about a live run: not what is sent, not what is billed, not what is written. A rate key with no entry is reported as an explicit absence rather than a cost of zero, and an entry in the wrong unit for its provider is refused rather than applied. See [Estimating cost](/docs/estimating-cost) for how the figure is computed and what it deliberately leaves out.

### extract

<AvailableFrom version="0.11.0" />

Optional, and used only by [`verbatra extract`](/docs/cli/extract), [`verbatra doctor --literals`](/docs/cli/doctor#untranslated-literals), and [`verbatra diff --unused`](/docs/cli/diff#unused-source-keys). Every other command ignores it.

```ts
extract: {
  framework: "i18next",
  roots: ["src", "app"],
  exclude: ["generated"],
  literals: { ignore: ["Acme Inc."] },
  unused: { ignore: ["emails.*"] },
}
```

`framework` names the translation framework whose call sites the scan looks for. The set is closed, and `i18next` is the one member today, covering the `t(...)`, `$t(...)`, and `<object>.t(...)` shapes. A framework with no extractor is rejected rather than accepted and silently ignored.

`roots` lists the directories to walk, resolved against the working directory. At least one is required, and nothing outside them is ever read.

`exclude` adds directory names to the always-skipped set, which already covers `node_modules`, `.git`, `.next`, `.turbo`, `.verbatra`, `dist`, `build`, and `coverage`. Names, not paths: an entry matches a directory of that name anywhere under a root.

`literals.ignore` lists exact texts that [`verbatra doctor --literals`](/docs/cli/doctor#untranslated-literals) holds back everywhere, such as a brand name. An entry matches a literal whose whole text is the same once whitespace is collapsed and character references such as `&amp;` are decoded, so write `Tom & Jerry`, not `Tom &amp; Jerry`. A held-back literal is still reported as suppressed, never dropped.

`unused.ignore` lists the keys `diff --unused` must not report as unused, for a key referenced only from outside the scanned source, such as a server template, a CMS, or a test fixture. Each entry is an exact key, or a pattern in which `*` matches any run of characters, such as `emails.*`. It matches the decoded key the report shows (`Welcome. Enjoy`, not the escaped `Welcome\. Enjoy`). A matched key is reported as ignored rather than left out. `unused` accepts no other field.

Unknown keys inside the block are rejected, exactly as they are at the top level.

## Discovery order

verbatra searches upward from the working directory and uses the first source it finds. The search stops at the nearest ancestor directory containing a `.git` entry (or at your home directory if none is found), so it will not wander above your repository into an unrelated config. Multiple present sources are not an error; the first match wins. The search order is:

1. `package.json` (a `"verbatra"` property)
2. `.verbatrarc`
3. `.verbatrarc.json`
4. `.verbatrarc.yaml`
5. `.verbatrarc.yml`
6. `.verbatrarc.js`
7. `.verbatrarc.cjs`
8. `.verbatrarc.ts`
9. `verbatra.config.js`
10. `verbatra.config.cjs`
11. `verbatra.config.ts`

To load one explicit file instead of searching, pass `--config <path>`; a relative path resolves against the working directory. In the SDK, an in-memory `configOverride` takes precedence over an explicit `configPath`, which takes precedence over the search. See [Programmatic API](/docs/programmatic-api).

## Editor validation

<AvailableFrom version="0.9.0" />

`@verbatra/sdk` ships the config schema as a JSON Schema document, generated at build time from the same zod schema the SDK validates with, so it can never describe a different shape than the one that runs. It installs at:

```
node_modules/@verbatra/sdk/dist/config-schema.json
```

Point an editor at it and a declarative config gets key completion, type and enum checking, and an immediate warning on a misspelled key.

An editor needs to be told which document to use; nothing validates automatically. There are two ways to tell it.

**An in-file `$schema` key.** `.verbatrarc.json` and `.verbatrarc` accept a top-level `$schema` key, which verbatra accepts and ignores:

```json
{
  "$schema": "./node_modules/@verbatra/sdk/dist/config-schema.json",
  "sourceLocale": "en",
  "targetLocales": ["de", "fr"],
  "format": "i18next-json",
  "files": { "pattern": "locales/{locale}.json" },
  "provider": { "id": "gemini", "options": { "model": "gemini-2.5-flash", "maxOutputTokens": 4096 } }
}
```

The `$schema` key is an editor convention, not a requirement of the JSON Schema specification: VS Code and editors that follow the same convention read it, and others do not. `.verbatrarc` has no extension, so an editor also needs a file-match entry before it treats the file as JSON at all, which means the key alone is not enough there.

**An explicit editor mapping.** In VS Code, map the files in your workspace settings instead, which covers the extensionless form as well:

```json
{
  "json.schemas": [
    {
      "fileMatch": [".verbatrarc", ".verbatrarc.json"],
      "url": "./node_modules/@verbatra/sdk/dist/config-schema.json"
    }
  ]
}
```

A YAML config (`.verbatrarc.yaml`, `.verbatrarc.yml`) takes a comment rather than a key, read by the YAML Language Server:

```yaml
# yaml-language-server: $schema=./node_modules/@verbatra/sdk/dist/config-schema.json
sourceLocale: en
targetLocales: [de, fr]
```

Two of the discovery places cannot be served. The `"verbatra"` property inside `package.json` cannot, because `package.json` already validates against its own schema and there is no way to attach a second one to a single property. The executable forms (`.verbatrarc.js`, `.verbatrarc.cjs`, `.verbatrarc.ts`, `verbatra.config.js`, `verbatra.config.cjs`, `verbatra.config.ts`) do not need one: `defineConfig` gives them the full `VerbatraConfigInput` type, so TypeScript already checks them, with provider-narrowed model completion on top.

### What the document cannot check

The document carries every key, its type, its enum values, which keys are required, the `{locale}` token rule on `files.pattern`, and the rejection of unknown keys. Three rules are enforced at runtime but have no expression in JSON Schema draft 2020-12, so an editor stays silent about them and verbatra reports them when the config loads:

- `targetLocales` must not include `sourceLocale`. Comparing two sibling values has no vocabulary in the draft.
- `targetLocales` must not contain two locales that differ only in case.
- `provider.options.apiKeyEnvVar` (openai-compatible only) must not name a hosted provider's environment variable. Expressing it would hard-code the hosted variable names into a shipped document, which would then drift from the code that owns them.

That is the complete list. A config the editor shows as clean can still fail one of these three, so a green editor is a fast first pass, not a substitute for running `verbatra check`.

## The working directory and .env

Run verbatra from your project root, or pass `--cwd` pointing at it. The working directory is the single anchor for everything verbatra resolves: the config search starts there and walks upward, `.env.local` and `.env` are loaded from there by `translate`, `watch`, `doctor`, and `studio`, and each locale file path is resolved against it. Keeping all three in the same place is what makes a plain `verbatra translate` work.

Environment precedence is, highest first: a variable already set in your real environment, then `.env.local`, then `.env`. A variable already present is never overwritten.

## When loading fails

Config loading fails with one of two structured error codes:

- **`CONFIG_NOT_FOUND`**: the search found no config in any of the places above, or the explicit `--config` path does not exist.
- **`CONFIG_INVALID`**: a config was found but could not be used. This covers a file that fails to parse, a config that fails schema validation, and a glossary file path that could not be resolved. The message lists every validation issue with its key path, and an unrecognized top-level key gains the hint that API keys are read from the environment, not the config. A raw parser or file-system error never escapes.

The CLI reports either failure and exits with code `2`, the boundary-error exit code. See [CI and exit codes](/docs/ci-and-exit-codes).
