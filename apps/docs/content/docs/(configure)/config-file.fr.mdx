verbatra lit un petit objet de configuration sans secret et le valide avant de faire le moindre travail. Aucune clé d'API n'est jamais lue depuis ce fichier : chaque fournisseur lit sa clé depuis une variable d'environnement (voir [Fournisseurs](/docs/providers#les-clés-viennent-de-lenvironnement)), donc la configuration peut être commitée sans risque.

## Une configuration minimale

```ts title="verbatra.config.ts"
import { defineConfig } from "@verbatra/sdk";

export default defineConfig({
  sourceLocale: "en",
  targetLocales: ["de", "fr"],
  format: "i18next-json",
  files: {
    pattern: "locales/{locale}.json",
  },
  provider: {
    id: "gemini",
    options: {
      model: "gemini-2.5-flash", // example model id; use your provider's current one
      maxOutputTokens: 4096,
    },
  },
});
```

`defineConfig` renvoie son argument tel quel et ne fait que le typer : `options.model` propose les identifiants de modèle du fournisseur sélectionné, tandis qu'à l'exécution n'importe quelle chaîne non vide est acceptée.

## Chaque clé

Les clés inconnues sont rejetées à chaque niveau, à la seule exception de `$schema`, et c'est aussi pourquoi une clé d'API ne peut pas se trouver dans la configuration.

| Clé | Type | Défaut | Depuis | Rôle |
| --- | --- | --- | --- | --- |
| `$schema` | chaîne | aucun | 0.9.0 | Pointe un éditeur vers le [JSON Schema](#validation-dans-léditeur) ; ignoré à l'exécution. |
| `sourceLocale` | code de locale | requis | 0.1.0 | La locale dans laquelle tes chaînes source sont écrites. |
| `targetLocales` | tableau de codes de locale | requis | 0.1.0 | Au moins une ; jamais `sourceLocale`, jamais deux égales sans tenir compte de la casse. |
| `format` | id de format | requis | 0.1.0 | Le [format](/docs/formats) de tes fichiers de locale, ou un id `custom:` pour un [adaptateur extérieur](/docs/custom-format-adapters). |
| `files.pattern` | chaîne | requis | 0.1.0 | Le chemin de chaque fichier de locale, avec un jeton `{locale}`. |
| `files.localeStyle` | `"literal"`, `"posix"`, `"android"` | `"literal"` | 0.7.0 | Comment `{locale}` est écrit dans le chemin. |
| `provider.id` | id de fournisseur | requis | 0.1.0 | Le fournisseur de traduction, ou `none` pour aucune traduction automatique. |
| `provider.options` | objet | requis, sauf pour `none` | 0.1.0 | Les options propres au fournisseur, listées par fournisseur sur [Fournisseurs](/docs/providers). |
| `glossary` | objet ou chemin de fichier | aucun | 0.1.0 | Traductions fixes, traductions interdites et termes à ne pas traduire. |
| `tone` | `"formal"`, `"informal"`, `"neutral"` | aucun | 0.1.0 | Le registre des traductions, appliqué [selon le fournisseur](/docs/providers#ton-et-glossaire-selon-les-fournisseurs). |
| `prune` | booléen | `false` | 0.3.0 | Supprime les clés orphelines des fichiers cibles et du fichier de verrouillage ; `translate --prune` prime. |
| `generatePlurals` | booléen | `false` | 0.3.0 | Synthétise les formes plurielles CLDR dont une langue cible a besoin. |
| `fuzzyCache.enabled` | booléen | requis dans le bloc | 0.11.0 | Réutilise la traduction d'une chaîne source qui n'a que peu changé. |
| `fuzzyCache.threshold` | nombre, de `0.5` à `1` | `0.9` | 0.11.0 | À quel point l'ancienne et la nouvelle source doivent se ressembler pour une réutilisation. |
| `humanEdits` | `"protect"`, `"suggest"`, `"overwrite"` | `"protect"` | 0.12.0 | Ce que fait une exécution d'une clé obsolète écrite par une personne. |
| `pinnedKeys` | tableau de chaînes | aucun | 0.12.0 | Des motifs de clés (`*` correspond à n'importe quelle suite de caractères) qu'aucune écriture automatique ne touche jamais. |
| `network.policy` | `"any"`, `"local-only"`, `"allowlist"` | `"any"` | 0.12.0 | Les hôtes auxquels un fournisseur peut se connecter. Voir [Restreindre l'accès réseau](/docs/network-policy). |
| `network.allowedHosts` | tableau de chaînes | aucun ; requis pour `"allowlist"` | 0.12.0 | Hôtes autorisés en plus : noms, jokers `*.suffix`, IP ou plages CIDR. |
| `maxBatchSize` | entier positif | `50` | 0.3.0 | Le maximum d'entrées envoyées dans une seule requête fournisseur. |
| `maxLength` | table de clé vers entier positif | aucun | 0.11.0 | Longueurs maximales par clé, en groupes de graphèmes. |
| `maxTokens` | entier positif | aucun | 0.5.0 | Un budget de tokens pour toute l'exécution. |
| `budgetBehavior` | `"warn"`, `"stop"` | `"warn"` | 0.5.0 | Si atteindre `maxTokens` ne fait qu'avertir ou arrête les envois. |
| `rates.asOf` | date `YYYY-MM-DD` | requis dans le bloc | 0.11.0 | La date à laquelle tu as lu les tarifs. |
| `rates.currency` | trois lettres majuscules | requis dans le bloc | 0.11.0 | La devise de chaque tarif, comme `USD` ou `EUR`. |
| `rates.table` | table de clé de tarif vers tarif | requis dans le bloc | 0.11.0 | Les tarifs indexés par `provider/model` ou par id de fournisseur. |
| `extract.framework` | `"i18next"` | requis dans le bloc | 0.11.0 | Les appels que l'analyse du code source recherche. |
| `extract.roots` | tableau de chaînes | requis dans le bloc | 0.11.0 | Les répertoires à analyser, au moins un. |
| `extract.exclude` | tableau de chaînes | aucun | 0.11.0 | Des noms de répertoire à ignorer en plus de l'ensemble intégré. |
| `extract.literals.ignore` | tableau de chaînes | aucun | 0.11.0 | Des textes exacts que `doctor --literals` retient. |
| `extract.unused.ignore` | tableau de chaînes | aucun | 0.11.0 | Des clés ou motifs `*` que `diff --unused` ne signale jamais comme inutilisés. |

### Locales et fichiers

- **`files.pattern`** doit contenir `{locale}`, le seul jeton qu'il comprend : `locales/{locale}.json` se résout en `locales/de.json`, par rapport au répertoire de travail. C'est un chemin littéral, jamais un glob, donc une configuration adresse un fichier par locale ; pour plusieurs fichiers d'espace de noms, voir [Dispositions avec espaces de noms](/docs/formats#dispositions-avec-espaces-de-noms). `apple-xcstrings` a quand même besoin du jeton, mais chaque locale se résout vers le même catalogue ([Xcode String Catalogs](/docs/formats#xcode-string-catalogs-xcstrings)).
- **`files.localeStyle`** décide en quoi le jeton se développe :
  - `literal` écrit l'étiquette telle qu'elle est configurée, ce dont ont besoin les dispositions JSON, YAML, XLIFF, ARB, properties et `.lproj` d'Apple.
  - `posix` remplace `-` par `_`, pour gettext et la disposition Java `messages_{locale}.properties` : `pt-BR` devient `pt_BR`, `zh-Hant-TW` devient `zh_Hant_TW`, `es-419` devient `es_419`. Une variante comme `de-1996` n'a pas d'écriture posix. `gettext-po` écrit les écritures à la manière de gettext (section suivante).
  - `android` se développe en un répertoire de ressources complet, écrit sous la forme `res/{locale}/strings.xml` : `values` pour la source, puis `values-de`, `values-pt-rBR`, `values-b+zh+Hans`.

  Un style refuse une locale qu'il ne sait pas écrire plutôt que d'écrire un répertoire que la plateforme ignorerait.

### Noms de locale gettext

<AvailableFrom version="0.12.0" />

Avec `format: "gettext-po"` et `localeStyle: "posix"`, un fichier est nommé à la manière de gettext, `language_REGION@modifier`, tandis que la configuration garde le code BCP 47 :

| Code dans la configuration | Nom de fichier |
| --- | --- |
| `pt-BR` | `pt_BR` |
| `es-419` | `es_419` |
| `sr-Latn` | `sr@latin` |
| `sr-Latn-RS` | `sr_RS@latin` |
| `uz-Cyrl` | `uz@cyrillic` |
| `ks-Deva-IN` | `ks_IN@devanagari` |
| `zh-Hant-TW` | `zh_TW` |
| `sr-Cyrl-RS` | `sr_RS` |

Une écriture que la langue et la région impliquent déjà est omise, donc configurer à la fois `zh-TW` et `zh-Hant-TW` échoue avec `LOCALE_PATH_COLLISION`. Une écriture sans modificateur gettext, comme `zh-Hant` sans région, échoue avec `LOCALE_LAYOUT_INVALID`. [`verbatra init`](/docs/cli/init) relit ces noms, et un catalogue créé les utilise dans son en-tête `Language`. Les autres formats gardent sous `posix` l'écriture ICU (`sr_Latn`).

### Codes de locale

<AvailableFrom version="0.12.0" />

Chaque code de locale doit être une étiquette qu'accepte `Intl.getCanonicalLocales`, avec une sous-étiquette de langue de deux ou trois lettres ; sinon le chargement échoue avec `CONFIG_INVALID`, en nommant le champ et le code. `pt_BR` est rejeté (écris `pt-BR` et règle `localeStyle: "posix"`), tout comme un nom de langue tel que `german`. Un code valide mais pas canonique, comme `zh-hant-tw` ou l'obsolète `iw`, fonctionne tel qu'il est écrit, et [`verbatra doctor`](/docs/cli/doctor) suggère la forme canonique. verbatra ne renomme jamais un fichier ; quand tu réécris un code, la prochaine exécution de `translate` reprend son état de verrouillage, de mémoire et de provenance ([Un code de locale réécrit](/docs/the-lock-file#un-code-de-locale-réécrit)).

### provider

`provider.id` sélectionne `anthropic`, `openai`, `gemini`, `deepl`, `google-translate`, `openai-compatible`, `libretranslate` (depuis 0.12.0) ou `none`. Seuls `id` et `options` sont autorisés sous `provider` ; depuis 0.12.0, toute autre clé, comme un `localeMap` mal placé, échoue avec `CONFIG_INVALID`. Tous les fournisseurs sauf `none` acceptent `options.localeMap` et `options.requestTimeoutMs` ([Fournisseurs](/docs/providers#codes-de-locale-envoyés-au-fournisseur)). Pour `none`, `options` peut être omis et doit sinon valoir `{}` ([Travailler sans traduction automatique](/docs/human-only-workflow)).

### glossary

Des termes traduits d'une façon fixe, en ligne ou comme chemin vers un fichier JSON de la même forme ; les deux formes ne fusionnent jamais. La version 1 associe chaque terme source à la traduction qu'utilise chaque locale :

```ts title="verbatra.config.ts"
export default defineConfig({
  // ...
  glossary: {
    "Sign in": "Anmelden",
  },
  // or: glossary: "glossary.json",
});
```

Un chemin relatif se résout par rapport au répertoire du fichier de configuration. Le fichier doit être en UTF-8, ne pas dépasser 1 MiB, et il est lu une fois au chargement. Un fichier absent, un JSON invalide ou une forme invalide échoue avec `CONFIG_INVALID`, en nommant le chemin et, pour la version 2, le champ. Garde un terme `__proto__` dans un fichier : dans un littéral de `verbatra.config.ts`, JavaScript le transforme en prototype.

#### Glossaire par locale (version 2)

<AvailableFrom version="0.12.0" />

La version 2 donne à chaque terme une traduction par locale, des traductions interdites, et des termes à garder tels qu'ils sont écrits :

```json title="glossary.json"
{
  "version": 2,
  "terms": [
    {
      "source": "Dashboard",
      "targets": { "de": "Übersicht", "fr": "Tableau de bord" },
      "forbidden": { "de": ["Instrumententafel"] },
      "note": "The start page after sign-in",
      "partOfSpeech": "noun"
    },
    { "source": "Sign in", "target": "Anmelden", "caseSensitive": true }
  ],
  "doNotTranslate": ["verbatra", { "term": "Acme", "caseSensitive": false }]
}
```

| Champ | Signification |
| --- | --- |
| `version` | Toujours `2` ; obligatoire, et tout autre nombre échoue. |
| `terms[].source` | Le terme source ; chaque terme apparaît une seule fois. |
| `terms[].target` | La traduction pour chaque locale sans entrée propre dans `targets`. |
| `terms[].targets` | Les traductions par locale. Une locale prend sa propre entrée, puis celle de sa langue de base (`de` couvre `de-AT`), puis `target`, en comparant les codes canoniques sans tenir compte de la casse. |
| `terms[].forbidden` | Les traductions qu'une locale ne doit jamais utiliser ; une locale régionale respecte aussi la liste de sa langue de base. |
| `terms[].caseSensitive` | Comparer le terme, les traductions et les traductions interdites en tenant compte de la casse. `false` par défaut. |
| `terms[].note`, `terms[].partOfSpeech` | Un contexte en texte libre, envoyé comme données à un fournisseur LLM. |
| `doNotTranslate` | Les termes recopiés sans traduction. Une simple chaîne garde aussi sa casse ; `{ "term", "caseSensitive": false }` peut la changer. |

Chaque terme a besoin d'un `target`, d'une entrée dans `targets` ou d'une liste `forbidden`, et ne peut pas interdire sa propre traduction, nommer deux fois une locale ni figurer aussi dans `doNotTranslate`. Une requête ne porte que les termes de sa locale cible, et l'empreinte de [cache](/docs/the-cache) de chaque locale ne couvre que ceux-là. Un fichier version 1 continue de fonctionner avec la même empreinte ; [`updateGlossaryTerm`](/docs/sdk/config#updateglossaryterm) du SDK ne le réécrit en version 2 que pour une modification que la version 1 ne sait pas exprimer.

<AvailableFrom version="0.4.0" pkg="@verbatra/studio" />

Seule la forme fichier se modifie depuis [Studio](/docs/review-in-studio), un terme à la fois ; un glossaire en ligne y reste en lecture seule. Les fournisseurs LLM ont pour instruction de traiter les traductions comme contraignantes, d'éviter les traductions interdites et de garder les termes à ne pas traduire ; DeepL, Google Cloud Translation et LibreTranslate ne peuvent pas les appliquer. La sortie de chaque fournisseur est vérifiée ensuite et signalée `GLOSSARY_TERM_MISSED` ou `GLOSSARY_FORBIDDEN_TERM` ([raisons de révision](/docs/error-codes#review-reason-codes)).

### generatePlurals

Quand il vaut true, verbatra synthétise les formes plurielles CLDR dont une cible a besoin mais que la source n'a pas, comme few et many pour le polonais ; les clés ordinales (`<key>_ordinal_<category>`) suivent les règles ordinales CLDR. Seul `i18next-json` avec un fournisseur LLM le prend en charge. Tout le reste, et une locale sans règles CLDR, reçoit à la place l'avertissement de pluriel par locale (en supposant `one` et `other` pour les cardinaux, `other` pour les ordinaux). Il n'y a pas d'option CLI ; `translate()` du SDK accepte une surcharge par exécution.

### fuzzyCache

<AvailableFrom version="0.11.0" />

`fuzzyCache: { enabled: true }` laisse une clé dont la source a changé réutiliser la traduction de sa forme antérieure quand les deux se ressemblent au moins à hauteur de `threshold`, au lieu d'appeler le fournisseur. Une réutilisation :

- est comptée à part des succès de cache exacts et toujours signalée pour révision avec `FUZZY_CACHE_REUSE` ;
- passe les mêmes contrôles d'intégrité que n'importe quelle autre valeur candidate, et n'est jamais réécrite dans le cache ;
- est refusée quel que soit son score quand ses caractères numériques diffèrent de la source actuelle ;
- est écrite mais pas verrouillée : la clé reste modifiée et est proposée à nouveau à chaque exécution jusqu'à ce qu'une vraie traduction arrive.

`threshold` règle la dépense que tu évites, pas la sûreté de la réutilisation ([pourquoi](/docs/the-cache)) : n'active donc cela que si quelqu'un traite la file de révision. Il n'y a pas d'option CLI ; `--no-cache` le contourne avec le reste du cache.

### humanEdits et pinnedKeys

<AvailableFrom version="0.12.0" />

`humanEdits` couvre une clé obsolète dont la valeur vient d'une modification dans Studio ou via le SDK (`human`), d'un livrable importé (`import`) ou d'une modification hors de verbatra (`external`), comme l'enregistre la [provenance](/docs/the-lock-file#la-provenance-de-chaque-valeur) :

- `"protect"` garde la valeur ; la clé n'est pas envoyée, reste obsolète dans `check` et apparaît comme protégée.
- `"suggest"` garde la valeur mais interroge le fournisseur ; la réponse est une suggestion gardée dans la mémoire, jamais écrite.
- `"overwrite"` la retraduit comme n'importe quelle clé obsolète ; `translate --include-human` fait cela pour une seule exécution.

Une clé qui correspond à `pinnedKeys` (par exemple `["legal.*", "brand.name"]`) n'est jamais traduite, suggérée ni retraduite, quoi que dise `humanEdits`, et un agent IA ne peut pas la modifier ; une personne le peut toujours. Une valeur sans enregistrement de provenance (`unrecorded`) n'est pas protégée. Voir [Garder les traductions humaines](/docs/protecting-human-translations).

### network

<AvailableFrom version="0.12.0" />

`"local-only"` autorise les adresses loopback, privées et uniques locales plus `allowedHosts` ; `"allowlist"` n'autorise que `allowedHosts`. `VERBATRA_NETWORK_POLICY` peut imposer une politique plus stricte en CI. Voir [Restreindre l'accès réseau](/docs/network-policy).

```ts title="verbatra.config.ts"
network: { policy: "local-only", allowedHosts: ["gpu.lan"] }
```

### maxBatchSize

Les entrées manquantes et modifiées d'une locale partent en sous-lots séquentiels d'au plus cette taille, pour qu'une requête trop grosse ne puisse pas faire échouer toute la locale ; un sous-lot échoué est retenté à l'exécution suivante pendant que les autres avancent. Il n'y a ni option CLI ni surcharge par exécution.

### maxLength

<AvailableFrom version="0.11.0" />

Une table associant une clé de traduction à la plus longue valeur qu'elle peut contenir, pour les chaînes soumises à une contrainte de mise en page :

```ts title="verbatra.config.ts"
maxLength: {
  "nav.dashboard": 18,
  "cta.submit": 12,
}
```

- **Seulement ici.** Aucun budget n'est déduit d'une description ni des métadonnées d'un format. Les clés sont comparées littéralement, jamais comme des globs ; une clé absente de la table n'est jamais mesurée.
- **Groupes de graphèmes.** La longueur compte les caractères perçus : un emoji de plusieurs points de code ou une lettre avec un accent combinant compte pour un, tout comme un caractère CJK, bien qu'il s'affiche environ deux fois plus large. Les espaces comptent, et la limite est inclusive.
- **Quand c'est vérifié.** Sur chaque valeur que `translate` produit pour la clé, réutilisations du cache comprises. Une clé à jour n'est pas mesurée, donc un nouveau budget ne signale rien tant que sa source ne change pas ; [`verbatra export --include-unchanged`](/docs/cli/export) mesure tout de suite chaque valeur actuelle.
- **Consultatif.** Un dépassement est quand même écrit et verrouillé, et signalé comme `MAX_LENGTH_EXCEEDED` dans `needsReview`, dans la file de Révision de Studio et dans les colonnes de révision du classeur.

### maxTokens et budgetBehavior

`maxTokens` est un budget pour toute l'exécution : tokens d'entrée plus de sortie, sommés sur chaque appel fournisseur (traduction et génération de pluriels) et sur chaque locale cible. `translate --max-tokens <n>` fixe pour une exécution un plafond plus strict qui s'arrête toujours ; le chiffre le plus bas s'applique (depuis 0.12.0).

<AvailableFrom version="0.11.0" />

`budgetBehavior` décide de ce que fait le fait de l'atteindre :

- `"warn"`, la valeur par défaut, compte la dépense et signale le dépassement ; l'exécution continue comme si aucun budget n'était défini.
- `"stop"` en fait un plafond (appliqué depuis 0.11.0, DeepL, Google Cloud Translation et LibreTranslate compris). Avant chaque requête, l'exécution projette son coût de la même façon que [l'estimation préalable](/docs/estimating-cost) et refuse une requête qui dépasserait `maxTokens`. Les clés de cette requête sont retenues, ainsi que chaque clé pas encore tentée : le reste de la locale en cours et chaque locale suivante, dont la comparaison et le rapport d'orphelines tournent quand même. Les clés retenues gardent leur hash de verrouillage précédent et sont retentées à l'exécution suivante.

Le décompte sous `"stop"` :

- Chaque requête est vérifiée, y compris chaque moitié d'une requête redécoupée après une réponse tronquée.
- Après chaque requête, le total est réconcilié avec l'usage que le fournisseur a remonté. Une requête qui coûte plus que projeté reporte l'écart après coup : une exécution peut donc finir au-dessus de `maxTokens` de l'écart de cette seule requête, et plus rien n'est envoyé.
- Une requête admise peut coûter jusqu'à près du double de sa projection à cause de la requête de réparation que la couche fournisseur envoie elle-même pour les clés manquantes ; cela aussi arrive à la réconciliation.
- Une requête échouée ou tronquée reste entièrement comptée, puisque le fournisseur a généralement facturé son prompt.
- Une exécution arrêtée ne laisse aucun fichier à moitié écrit ni aucune entrée de verrouillage pour du travail retenu.
- La projection inclut une allocation fixe pour le prompt LLM (règles système et schéma de réponse), ajoutée aussi pour les fournisseurs de traduction automatique. Une requête est projetée comme un lot entier, donc un `maxTokens` inférieur à la projection d'un lot le refuse à chaque exécution ; l'avis dit alors de baisser `maxBatchSize` ou d'augmenter `maxTokens`.
- DeepL, Google Cloud Translation et LibreTranslate ne remontent aucun usage de tokens et sont budgétés à partir de la projection ; `budget.supported: false` dans le résumé d'exécution indique le décompte propre de verbatra.

Portée et codes de sortie :

- Le budget borne une exécution de `translate`. `watch` démarre un budget neuf pour chaque exécution qu'il déclenche, et une retraduction d'une seule entrée depuis [Studio](/docs/review-in-studio) ou un outil d'agent n'est jamais plafonnée.
- Une exécution réelle avec `maxTokens` et `--concurrency` supérieur à `1` est refusée avec le code de sortie `2` (`CONCURRENCY_BUDGET_CONFLICT`), parce que la locale qui perd du travail dépendrait de l'entrelacement. Un dry run est exempté.
- Sous `"warn"`, le code de sortie ne change jamais. Sous `"stop"`, une locale dont des clés ont été retenues est `partial` si certaines clés sont arrivées et `failed` si aucune ne l'est ; les deux sortent avec `1`.
- `budgetBehavior` sans `maxTokens` n'a aucun effet.

<Callout title="Deux maxTokens différents">
Le `maxTokens` de premier niveau est ce budget de toute l'exécution. Le `provider.options.maxTokens` d'Anthropic plafonne une seule réponse ; ils n'ont aucun lien. Voir [Fournisseurs](/docs/providers#anthropic).
</Callout>

### rates

<AvailableFrom version="0.11.0" />

Lu uniquement par [`verbatra translate --estimate`](/docs/estimating-cost) ; une exécution réelle l'ignore. verbatra ne livre aucun prix, c'est donc toi qui les fournis, avec la date à laquelle tu les as lus.

```ts title="verbatra.config.ts"
rates: {
  asOf: "2026-01-15",
  currency: "USD",
  table: {
    "gemini/gemini-2.5-flash": { inputPerMillionTokens: 0.1, outputPerMillionTokens: 0.4 },
    deepl: { perMillionCharacters: 25 },
  },
}
```

Une clé de `table` est `provider/model` pour un fournisseur avec un modèle, et l'id seul pour un fournisseur sans modèle (`deepl`, `google-translate`). Une entrée est soit facturée aux tokens (`inputPerMillionTokens` et `outputPerMillionTokens`), soit facturée aux caractères (`perMillionCharacters`), jamais les deux ; un tarif négatif est rejeté. `openai-compatible` et `libretranslate` n'envoient aucune facture, donc leur quantité est indiquée sans tarif. Une clé de tarif manquante est signalée comme absente, jamais comme nulle, et une entrée dans la mauvaise unité est refusée.

### extract

<AvailableFrom version="0.11.0" />

Lu uniquement par [`verbatra extract`](/docs/cli/extract), [`verbatra doctor --literals`](/docs/cli/doctor#littéraux-non-traduits) et [`verbatra diff --unused`](/docs/cli/diff#clés-source-inutilisées).

```ts title="verbatra.config.ts"
extract: {
  framework: "i18next",
  roots: ["src", "app"],
  exclude: ["generated"],
  literals: { ignore: ["Acme Inc."] },
  unused: { ignore: ["emails.*"] },
}
```

- **`framework`** est un ensemble fermé ; `i18next` couvre `t(...)`, `$t(...)` et `<object>.t(...)`. Un framework sans extracteur est refusé.
- **`roots`** se résolvent par rapport au répertoire de travail ; rien en dehors d'eux n'est lu.
- **`exclude`** ajoute des noms de répertoire (pas des chemins), reconnus n'importe où sous une racine, à l'ensemble toujours ignoré `node_modules`, `.git`, `.next`, `.turbo`, `.verbatra`, `dist`, `build` et `coverage`.
- **`literals.ignore`** correspond au texte complet d'un littéral une fois les espaces regroupés et les références de caractères décodées : écris donc `Tom & Jerry`, pas `Tom &amp; Jerry`. Un littéral retenu est signalé comme masqué.
- **`unused.ignore`** prend des clés exactes ou des motifs `*` pour les clés utilisées uniquement hors du code analysé (un template serveur, un CMS). Il correspond à la clé décodée qu'affiche le rapport (`Welcome. Enjoy`, pas `Welcome\. Enjoy`), et une correspondance est signalée comme ignorée.

## Ordre de découverte

verbatra cherche vers le haut depuis le répertoire de travail et utilise la première source qu'il trouve, en s'arrêtant au répertoire le plus proche qui contient `.git` (ou à ton répertoire personnel), donc il ne prend jamais une configuration située au-dessus de ton dépôt :

1. `package.json` (une propriété `"verbatra"`)
2. `.verbatrarc`
3. `.verbatrarc.json`
4. `.verbatrarc.yaml`
5. `.verbatrarc.yml`
6. `.verbatrarc.js`
7. `.verbatrarc.cjs`
8. `.verbatrarc.ts`
9. `verbatra.config.js`
10. `verbatra.config.cjs`
11. `verbatra.config.ts`

`--config <path>` charge un seul fichier à la place, relatif au répertoire de travail. Dans le SDK, un `configOverride` en mémoire prime sur `configPath`, qui prime sur la recherche ([Recettes SDK](/docs/programmatic-api)).

## Validation dans l'éditeur

<AvailableFrom version="0.9.0" />

`@verbatra/sdk` livre un JSON Schema généré à partir du schéma zod avec lequel le SDK valide :

```text
node_modules/@verbatra/sdk/dist/config-schema.json
```

`.verbatrarc.json` et `.verbatrarc` acceptent une clé `$schema`, que VS Code lit :

```json title=".verbatrarc.json"
{
  "$schema": "./node_modules/@verbatra/sdk/dist/config-schema.json",
  "sourceLocale": "en",
  "targetLocales": ["de", "fr"],
  "format": "i18next-json",
  "files": { "pattern": "locales/{locale}.json" },
  "provider": { "id": "gemini", "options": { "model": "gemini-2.5-flash", "maxOutputTokens": 4096 } }
}
```

Le `.verbatrarc` sans extension a aussi besoin d'une correspondance de fichiers, que donne une association dans l'espace de travail :

```json title=".vscode/settings.json"
{
  "json.schemas": [
    {
      "fileMatch": [".verbatrarc", ".verbatrarc.json"],
      "url": "./node_modules/@verbatra/sdk/dist/config-schema.json"
    }
  ]
}
```

Une configuration YAML prend un commentaire pour le YAML Language Server :

```yaml title=".verbatrarc.yaml"
# yaml-language-server: $schema=./node_modules/@verbatra/sdk/dist/config-schema.json
sourceLocale: en
targetLocales: [de, fr]
```

La propriété du `package.json` ne peut pas recevoir de schéma ; les formes exécutables sont typées par `defineConfig` à la place.

### Ce que le document ne peut pas vérifier

Ces règles n'ont aucune expression en JSON Schema, donc seul le chargement de la configuration les vérifie :

- `targetLocales` ne doit pas inclure `sourceLocale`, ni deux locales qui ne diffèrent que par la casse.
- Un code de locale doit passer `Intl.getCanonicalLocales` (la grammaire ne voit pas une variante répétée comme `de-1996-1996`).
- Chaque clé de `provider.options.localeMap` doit être `sourceLocale` ou une locale cible.
- `apiKeyEnvVar` (openai-compatible) ne doit pas nommer la variable de clé d'un fournisseur hébergé.
- Une entrée de `network.allowedHosts` doit être une adresse ou une plage valide (pas un octet au-delà de 255, un préfixe CIDR trop long ni un IPv6 mal formé).
- Un glossaire version 2 en ligne doit respecter les règles des termes décrites sous [glossary](#glossaire-par-locale-version-2).

## Le répertoire de travail et .env

Le répertoire de travail (là où tu lances verbatra, ou `--cwd`) ancre tout : la recherche de configuration y démarre, les chemins de locale se résolvent par rapport à lui, et `translate`, `watch`, `doctor`, `studio` et `mcp` y chargent `.env.local` et `.env`. Une variable déjà définie dans l'environnement l'emporte sur `.env.local`, qui l'emporte sur `.env`.

## Quand le chargement échoue

- [`CONFIG_NOT_FOUND`](/docs/error-codes#config_not_found) : aucune configuration à aucun des endroits cherchés, ou le chemin `--config` n'existe pas.
- [`CONFIG_INVALID`](/docs/error-codes#config_invalid) : une configuration a été trouvée mais n'est pas utilisable : elle ne s'analyse pas, échoue à la validation ou nomme un fichier de glossaire illisible. Le message liste chaque problème avec son chemin de clé, et une clé de premier niveau inconnue ajoute l'indice que les clés d'API viennent de l'environnement. Un échec d'analyse nomme le fichier (avec la ligne et la colonne pour YAML) mais ne cite jamais son contenu, et chaque message passe par la rédaction des clés.

La CLI sort avec `2` dans les deux cas.
