Der MCP-Server von verbatra spricht den stdio-Transport: Dein MCP-Client startet ihn als Kindprozess und spricht über stdin und stdout mit ihm, es gibt also keinen Port, keine URL und nichts, was du selbst am Laufen halten musst. Jeder Client braucht dieselben drei Antworten: welcher Befehl den Server startet, welches Verzeichnis das Projekt ist und woher ein Provider-Key kommt, falls der Agent überhaupt Geld ausgeben darf. Diese Seite beantwortet sie einmal und zeigt dann die Konfigurationssyntax jedes Clients. Die Tools selbst, ihre Eingaben und Ergebnisse sind unter [`verbatra mcp`](/docs/cli/mcp) dokumentiert.

<AvailableFrom version="0.2.0" pkg="@verbatra/mcp" />

## Einen Startbefehl wählen

Zwei Befehle starten denselben Server:

| Befehl | Braucht | Liest `.env`-Dateien |
| --- | --- | --- |
| `npx -y @verbatra/mcp` | keine Installation: npx holt `@verbatra/mcp` bei Bedarf und startet sein `verbatra-mcp`-Binary | nein |
| `npx verbatra mcp` | `@verbatra/cli` und `@verbatra/mcp`, beide im Projekt installiert | ja: `.env.local`, dann `.env`, aus dem Arbeitsverzeichnis oder dem `--cwd`-Verzeichnis |

`npx -y @verbatra/mcp` ist in allen Beispielen unten der Standard, weil es in jedem Projekt funktioniert. Wechsle zu `npx verbatra mcp`, wenn das Projekt beide Pakete schon als Dev-Dependencies hat und sein Provider-Key bereits in `.env.local` liegt:

```npm
npm install --save-dev @verbatra/cli @verbatra/mcp
```

Zwei Befehle, die richtig aussehen, funktionieren in einem Projekt ohne diese Installationen nicht. `npx -y @verbatra/cli mcp` installiert nur die CLI, die `@verbatra/mcp` bei Bedarf lädt und nie installiert, und endet deshalb mit Exit-Code `2` und `Verbatra's MCP server requires @verbatra/mcp`. `npx verbatra mcp` ohne lokales `@verbatra/cli` lässt npx in der Registry nach einem Paket namens `verbatra` suchen, das nicht die CLI von verbatra ist: Der Befehl schlägt fehl, und er könnte das Paket von jemand anderem ausführen, falls dieser Name je registriert wird.

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Jedes Release von `@verbatra/mcp` veröffentlicht den Server direkt nach dem npm-Paket auch in der [offiziellen MCP Registry](https://registry.modelcontextprotocol.io) als `io.github.verbatra/verbatra`, sodass ein Client, der die Registry durchsucht, ihn dort findet.

## Welches Verzeichnis das Projekt ist

Der Server lädt die Konfiguration und löst jede Locale-Datei aus seinem Arbeitsverzeichnis auf, oder aus dem Verzeichnis, das `--cwd` nennt. Ohne `--cwd` tritt eine Umgebungsvariable `CLAUDE_PROJECT_DIR`, die ein vorhandenes Verzeichnis nennt, an die Stelle des Arbeitsverzeichnisses. Ohne `--config` sucht er von dort aus aufwärts nach einer Konfigurationsdatei und hält am nächsten `.git`-Verzeichnis an, aber die Tools lösen Pfade weiterhin vom Arbeitsverzeichnis selbst aus auf. Richte den Server auf das Verzeichnis aus, in dem `verbatra.config.ts` liegt.

Clients unterscheiden sich darin, in welchem Verzeichnis sie einen Server starten:

| Client | Arbeitsverzeichnis | Was zu tun ist |
| --- | --- | --- |
| Claude Code | nicht dokumentiert, aber `CLAUDE_PROJECT_DIR` ist auf den Projektstamm gesetzt | nichts: ohne `--cwd` nimmt der Server `CLAUDE_PROJECT_DIR` |
| Cursor | nicht dokumentiert | `--cwd ${workspaceFolder}` übergeben |
| VS Code | der Workspace-Ordner | nichts, oder `cwd` setzen |
| Windsurf | nicht dokumentiert | `--cwd` mit absolutem Pfad übergeben |
| Claude Desktop | nicht dokumentiert, und es gibt kein Projekt | `--cwd` mit absolutem Pfad übergeben |

## Keys und Ausgaben

Der Server startet nur lesend. Ohne erlaubte Ausgaben stellt er jedes Tool außer `translation.retranslateEntry` und `translation.translatePending` bereit, und keines dieser Tools ruft einen Provider auf oder liest einen Key: Status und Glossar lesen, einen Lauf mit `translation.estimate` bepreisen und eine Übersetzung mit `translation.editEntry` von Hand schreiben funktioniert alles ganz ohne Key. Für dieses Setup lässt du Key und Spend-Schalter komplett aus der Client-Konfiguration weg.

Damit der Agent Geld ausgeben darf, schaltest du zwei Dinge ein:

- **Den Spend-Schalter.** Füge `--allow-spend` zu den Argumenten des Servers hinzu, oder setze `VERBATRA_MCP_ALLOW_SPEND` in seiner Umgebung auf `1`, `true`, `yes` oder `on`. Das Flag gewinnt gegenüber der Variable. Mit `npx verbatra mcp` kann die Variable auch in `.env.local` oder `.env` des Projekts stehen, die dieser Befehl zuerst liest; `npx -y @verbatra/mcp` liest keine `.env`-Datei. Eine Konfiguration mit `provider: { id: "none" }` hält beide Spend-Tools verborgen, egal was du setzt.
- **Den Provider-Key.** Der Server liest dieselbe Umgebungsvariable wie die CLI, zum Beispiel `ANTHROPIC_API_KEY`; welche deine ist, steht unter [Provider](/docs/providers). Er liest nie einen Key aus seinen Argumenten oder aus einer Client-Konfigurationsdatei.

Schreib nie einen Key in eine Datei, die du committest: `.mcp.json`, `.cursor/mcp.json` und `.vscode/mcp.json` sind dafür gedacht, mit dem ganzen Team geteilt zu werden. Jeder Client unten hat einen Weg, dem Server einen Key zu übergeben, ohne dass die Datei ihn enthält: eine geerbte Umgebung, einen Verweis auf eine Variable oder eine Abfrage, die den Wert außerhalb der Datei speichert.

Auch mit erlaubten Ausgaben weisen die Anweisungen des Servers den Agenten an, zuerst `translation.estimate` aufzurufen und auf dein ausdrückliches Ja zu warten, bevor er ein Spend-Tool aufruft.

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.estimate`, der Provider `none` und diese Server-Anweisungen kamen mit diesem Release.

## Claude Code

Füge den Server im Projektstamm hinzu:

```bash
claude mcp add --transport stdio --scope project verbatra -- npx -y @verbatra/mcp
```

Alles nach `--` ist die eigene Befehlszeile des Servers und wird unverändert durchgereicht, also gehören die Flags von verbatra dahinter und die eigenen Optionen von Claude Code (`--transport`, `--scope`, `--env`) davor. `--scope` entscheidet, wo der Eintrag gespeichert wird:

| Scope | Gespeichert in | Wer ihn bekommt |
| --- | --- | --- |
| `local` (der Standard) | `~/.claude.json`, unter dem Pfad dieses Projekts | du, nur in diesem Projekt |
| `project` | `.mcp.json` im Projektstamm, zum Committen gedacht | alle, die das Projekt öffnen |
| `user` | `~/.claude.json` | du, in jedem Projekt |

`--scope project` schreibt diese `.mcp.json`, die du auch von Hand schreiben und committen kannst:

```json
{
  "mcpServers": {
    "verbatra": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@verbatra/mcp"]
    }
  }
}
```

Claude Code bittet jede Person, einen Server mit Projekt-Scope aus `.mcp.json` vor der ersten Nutzung in einer interaktiven Sitzung freizugeben.

Claude Code gibt dem Server die Umgebung mit, mit der du `claude` gestartet hast, dazu `CLAUDE_PROJECT_DIR` mit dem Projektstamm. Die committete Datei enthält also weder Key noch Spend-Schalter: Wer im Team die Spend-Tools will, schaltet sie für eine Sitzung zu, mit dem Key bereits in der eigenen Shell exportiert:

```bash
VERBATRA_MCP_ALLOW_SPEND=1 claude
```

Mit dem Startbefehl `npx verbatra mcp` holt sich der Server den Key zusätzlich aus `.env.local` oder `.env` des Projekts, er muss dann gar nicht exportiert sein.

Übergib keinen Key mit `--env` zusammen mit `--scope project`: `--env KEY=value` schreibt den Wert selbst in den Eintrag, und mit diesem Scope ist der Eintrag `.mcp.json`.

Mit `claude mcp list` siehst du, ob der Server sich verbindet. Die vollständige Befehlsreferenz steht in der [MCP-Dokumentation von Claude Code](https://code.claude.com/docs/en/mcp).

### Das verbatra-Plugin

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Statt den Server von Hand hinzuzufügen, kannst du das verbatra-Plugin für Claude Code installieren. Es bringt die drei [verbatra-Skills](/docs/agent-recipes#das-skills-paket), diesen MCP-Server und einen Hook mit, der Locale-Dateien prüft, nachdem Claude sie bearbeitet hat. Installier es für das Projekt, aus einer Shell im Projektstamm:

```bash
claude plugin marketplace add verbatra/skills
claude plugin install verbatra@verbatra --scope project
```

`--scope project` trägt das Plugin in die `.claude/settings.json` des Projekts ein und hält es aus deinen anderen Projekten heraus. Alle im Team installieren es trotzdem einmal selbst: Bis dahin meldet Claude Code es als nicht installiert und zeigt den `claude plugin install`-Befehl dafür an. Der Server braucht zum Starten eine verbatra-Konfiguration, deshalb würde er mit dem Standard-Scope `user` in jedem Projekt starten, das du öffnest, und in jedem ohne verbatra fehlschlagen. In Claude Code selbst machen `/plugin marketplace add verbatra/skills` und `/plugin install verbatra@verbatra` dasselbe; wähl **Project scope**, wenn [die Installation nach einem Scope fragt](https://code.claude.com/docs/en/discover-plugins#install-plugins).

- **Der Server.** Das Plugin startet `npx -y @verbatra/mcp` in der Version, die es festlegt, mit `--cwd` auf dem Projekt, das in Claude Code offen ist. Hat das Projekt noch keine Konfiguration, führe dort zuerst `npx verbatra init` aus.
- **Ausgaben sind aus.** Die Spend-Tools bleiben verborgen, bis du die Plugin-Option `allowSpend` einschaltest, die das Plugin als `VERBATRA_MCP_ALLOW_SPEND` an den Server übergibt. Deshalb schaltet ein `claude`, das du mit dieser Variable startest, beim Server des Plugins keine Ausgaben ein. Setz die Option mit `--config allowSpend=true` bei `claude plugin install` oder später in `/config`. Claude Code ignoriert Plugin-Optionen in der `.claude/settings.json` eines Projekts, eine committete Datei schaltet Ausgaben für das Team also nie ein. Scopes und Optionen stehen in der [Plugin-Referenz von Claude Code](https://code.claude.com/docs/en/plugins-reference).
- **Der Key kommt aus deiner Umgebung.** Das Plugin hat keine Option für einen Key. Der Server liest die Variable deines Providers aus der Umgebung, mit der du `claude` gestartet hast, genau wie oben.
- **Der Hook für Locale-Dateien.** Nachdem Claude eine Datei bearbeitet oder schreibt, die eine Locale-Datei sein kann, führt der Hook das projekteigene `verbatra check --qa` aus. Wenn eine committete Übersetzung einen Platzhalter, Inline-Markup oder ICU kaputt macht, gibt er die Befunde an Claude zurück, damit es sie behebt. Er nutzt nur die `@verbatra/cli` aus dem `node_modules` des Projekts, ab Version 0.12.0, lädt nichts herunter und ruft keinen Provider auf. In einem Projekt ohne lokale `@verbatra/cli` tut er nichts.

## Cursor

Cursor liest die Server eines Projekts aus `.cursor/mcp.json` und deine eigenen aus `~/.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "verbatra": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@verbatra/mcp", "--cwd", "${workspaceFolder}"]
    }
  }
}
```

`${workspaceFolder}` ist die Variable von Cursor für den Projektstamm. Um Ausgaben zu erlauben, fügst du den Schalter hinzu und reichst den Key per Verweis weiter, sodass die Datei nur den Namen der Variable enthält und der Wert aus der Umgebung kommt, in der Cursor läuft:

```json
{
  "mcpServers": {
    "verbatra": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@verbatra/mcp", "--cwd", "${workspaceFolder}", "--allow-spend"],
      "env": {
        "ANTHROPIC_API_KEY": "${env:ANTHROPIC_API_KEY}"
      }
    }
  }
}
```

Leg einen Eintrag mit erlaubten Ausgaben besser in `~/.cursor/mcp.json` ab statt in der committeten Projektdatei, wenn nicht alle im Team Geld ausgeben sollen. Siehe die [MCP-Dokumentation von Cursor](https://cursor.com/docs/mcp).

## VS Code

VS Code (der Agent-Modus von GitHub Copilot) liest die Server eines Workspace aus `.vscode/mcp.json`. Der Schlüssel auf oberster Ebene heißt dort `servers`, nicht `mcpServers`, und VS Code startet einen Server im Workspace-Ordner, also ist kein `--cwd` nötig:

```json
{
  "servers": {
    "verbatra": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@verbatra/mcp"]
    }
  }
}
```

Um Ausgaben zu erlauben, deklarierst du den Key als Input. VS Code fragt ihn beim ersten Start des Servers ab und speichert den Wert sicher, außerhalb der Datei:

```json
{
  "inputs": [
    {
      "type": "promptString",
      "id": "anthropic-key",
      "description": "Anthropic API key",
      "password": true
    }
  ],
  "servers": {
    "verbatra": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@verbatra/mcp", "--allow-spend"],
      "env": {
        "ANTHROPIC_API_KEY": "${input:anthropic-key}"
      }
    }
  }
}
```

Alternativ lädt `"envFile": "${workspaceFolder}/.env.local"` den Key aus einer ignorierten Datei, die du schon hast. Mit **MCP: Open User Configuration** öffnest du eine `mcp.json`, die für alle deine Workspaces gilt. Siehe die [Referenz zur MCP-Konfiguration von VS Code](https://code.visualstudio.com/docs/agents/reference/mcp-configuration).

## Windsurf

Der Cascade-Agent von Windsurf liest seine Server aus einer einzigen `mcp_config.json` für alle Projekte, also nennst du das Projekt mit einem absoluten `--cwd`:

```json
{
  "mcpServers": {
    "verbatra": {
      "command": "npx",
      "args": ["-y", "@verbatra/mcp", "--cwd", "/path/to/your/project"]
    }
  }
}
```

Um Ausgaben zu erlauben, fügst du `--allow-spend` zu `args` hinzu und reichst den Key per Verweis weiter, mit `"env": { "ANTHROPIC_API_KEY": "${env:ANTHROPIC_API_KEY}" }`. Wo die Datei liegt und die restliche Syntax stehen in der [MCP-Dokumentation von Cascade](https://docs.devin.ai/desktop/cascade/mcp).

## Claude Desktop

Claude Desktop liest `claude_desktop_config.json`, die es dir unter **Settings**, **Developer**, **Edit Config** öffnet:

- macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`
- Windows: `%APPDATA%\Claude\claude_desktop_config.json`

Es kennt kein Projekt, also muss `--cwd` ein absoluter Pfad sein:

```json
{
  "mcpServers": {
    "verbatra": {
      "command": "npx",
      "args": ["-y", "@verbatra/mcp", "--cwd", "/path/to/your/project"]
    }
  }
}
```

Um Ausgaben zu erlauben, fügst du `--allow-spend` zu `args` hinzu und einen `env`-Block mit der Variable deines Providers, zum Beispiel `"env": { "ANTHROPIC_API_KEY": "..." }`. Diese Datei gehört dir allein und liegt außerhalb jedes Repositorys, der Wert bleibt also auf deinem Rechner; kopier ihn nie in eine Projektdatei. Beende Claude Desktop nach jeder Änderung vollständig und starte es neu. Die Diagnosen des Servers gehen nach stderr, und Claude Desktop schreibt sie unter macOS in `mcp-server-verbatra.log` in `~/Library/Logs/Claude` und unter Windows in `%APPDATA%\Claude\logs`. Siehe [Connect to local MCP servers](https://modelcontextprotocol.io/docs/develop/connect-local-servers).

## Jeder andere stdio-Client

Jeder Client, der einen lokalen stdio-Server starten kann, funktioniert genauso. Gib ihm:

- den Befehl `npx` mit den Argumenten `-y @verbatra/mcp`, oder den absoluten Pfad zu einem installierten `verbatra-mcp`-Binary;
- `--cwd /path/to/your/project`, außer du weißt, dass der Client Server im Projektstamm startet;
- `--config <path>`, wenn die Konfigurationsdatei nicht dort liegt, wo die Aufwärtssuche sie findet;
- `--allow-spend` und die Key-Variable des Providers nur dann, wenn der Agent Geld ausgeben soll, mit dem Key über den eigenen Secret- oder Umgebungsmechanismus des Clients.

Der Server schreibt nur Protokollnachrichten nach stdout und jede Logzeile nach stderr, also ist das Server-Log eines Clients die Stelle, an der du nachschaust, wenn er sich nicht verbindet. Ein Konfigurationsfehler wird dort gemeldet, bevor der Server überhaupt antwortet, und der Prozess beendet sich.

## Die Verbindung prüfen

Bitte den Agenten, `project.snapshot` aufzurufen. Das Tool liest die Konfiguration, ruft keinen Provider auf und liefert Quell-Locale, Ziel-Locales, Format und Provider-ID, sodass ein falsches Arbeitsverzeichnis oder eine fehlende Konfiguration sofort auffällt. Fehlen die Spend-Tools, obwohl sie da sein sollten, prüf den Spend-Schalter und ob der Provider der Konfiguration `none` ist.
