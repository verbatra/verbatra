Verbatra Studio ist normalerweise eine Oberfläche für Menschen: du öffnest das Loopback-Dashboard und klickst dich durch den Projektzustand, die Drift, die Review-Warteschlange und Bearbeitungen. Mit dem Opt-in-Flag `--expose-agent-tools` registriert Studio dieselben Review-Aktionen zusätzlich als WebMCP-Tools, sodass ein KI-Agent im Browser (zum Beispiel Gemini oder Claude in Chrome), der auf demselben offenen, authentifizierten Tab sitzt, sie strukturiert bedienen kann, statt am DOM zu raten.

Das ist dafür da, ein bestehendes verbatra-Projekt im Dialog zu bedienen: Zustand und Drift ansehen, die Review-Warteschlange abarbeiten, Einträge bearbeiten und (nur wenn du zusätzlich Ausgaben erlaubst) ausstehende Keys neu übersetzen und übersetzen. Es ist nicht für die Projekteinrichtung und nicht für Fernzugriff gedacht.

<Callout title="Experimentell und hinter einem Browser-Flag">
WebMCP ist eine neue, sich noch entwickelnde Browser-Fähigkeit. Heute braucht es dafür einen bestimmten Chrome-Build mit einem experimentellen Flag, und die Schnittstelle kann sich ändern, während der Standard reift. Behandle das als Vorschau-Funktion.
</Callout>

## Was WebMCP ist

WebMCP lässt eine Seite Tools an `document.modelContext` registrieren, die ein im Browser ansässiger KI-Agent dann aufrufen kann. Studio nutzt das, um seine Review-Aktionen als benannte Tools anzubieten. Jeder Tool-Aufruf läuft weiterhin über genau denselben authentifizierten RPC wie das Dashboard, über denselben Loopback-Origin, mit derselben Eingabevalidierung und denselben Capability-Gates. Die Tools zu registrieren gibt einem Agenten nichts, was der offene, authentifizierte Tab nicht schon hatte: ein Agent, der das DOM steuert, konnte jede einzelne dieser Aktionen schon erreichen. Die Oberfläche deckt sich mit diesem einen offenen Tab und fügt keine neue Netzwerk-Exposition hinzu.

### Voraussetzungen im Browser

- Ein WebMCP-fähiger Browser. Heute heißt das Chrome 149 oder neuer mit aktiviertem `chrome://flags/#enable-webmcp-testing`, oder ein späterer Browser mit nativer Unterstützung.
- `document.modelContext` muss vorhanden sein. Fehlt es, registriert Studio nichts und das Dashboard bleibt unverändert.
- Ein echter Browsing-Kontext. Headless funktioniert das nicht; der Agent bedient den offenen, laufenden Tab.
- Keine Konfigurations- oder CSP-Änderung auf Studios Seite. Die WebMCP-Permissions-Policy `tools` steht standardmäßig auf `self`, was genau Studios Same-Origin-Fall ist, also muss nichts gewährt werden.

## Schalte es ein

Agent-Tools sind standardmäßig aus. Schalte sie mit dem Flag am `studio`-Befehl ein:

```bash
verbatra studio --expose-agent-tools
```

Oder setze den Fallback über die Umgebung:

```bash
VERBATRA_STUDIO_AGENT_TOOLS=1 verbatra studio
```

Flag und Umgebungsvariable werden genau wie bei `--allow-spend` aufgelöst: `1`, `true`, `yes` oder `on` (Groß- und Kleinschreibung egal) zählt als an, und das CLI-Flag gewinnt gegen die Variable. Ist keines von beiden gesetzt, wird kein Tool registriert. Alle Flags stehen unter [`verbatra studio`](/docs/cli/studio).

Öffne dann die ausgegebene Loopback-URL in deinem WebMCP-fähigen Browser. Der Agent auf diesem Tab entdeckt die registrierten Tools und kann sie aufrufen.

## Der Tool-Katalog

Mit aktiviertem Opt-in registriert Studio zwanzig Tools. Ohne `--allow-spend` sind es achtzehn: die beiden Ausgaben-Tools entfallen vollständig. Tool-Namen tragen ein Präfix und nutzen Unterstriche (zum Beispiel `verbatra_project_snapshot`).

### Lese-Tools (vierzehn)

Sieh dir den Projektzustand an, ohne etwas zu ändern. Diese sind als nur lesend markiert.

| Tool | Was es zurückgibt |
| --- | --- |
| `verbatra_project_snapshot` | aufgelöster Projektzustand und Capabilities |
| `verbatra_status_check` | Abdeckungsübersicht pro Locale |
| `verbatra_status_diff` | Drift pro Locale (fehlende, geänderte, verwaiste Keys) |
| `verbatra_glossary_get` | das aufgelöste Glossar: die Übersetzungen jedes Begriffs für alle Locales und pro Locale, verbotene Wiedergaben, Kontext, woran jede Ziel-Locale gebunden ist, und die unübersetzten Begriffe |
| `verbatra_lock_state` | der Zustand der Lock-Datei |
| `verbatra_history_list` | jüngste Commit-Historie der Locale-Dateien |
| `verbatra_key_integrity` | Platzhalter-, Inline-Markup-, ICU- und ICU-Zweig-Integrität für einen Key |
| `verbatra_review_queue` | jeder maschinell geschriebene Wert, den noch niemand freigegeben hat, aus den committeten Dateien |
| `verbatra_usage_summary` | Token-Verbrauch und Budget des letzten Laufs |
| `verbatra_key_value` | die Quell- und Zielwerte für einen Key und eine Locale |
| `verbatra_locale_values` | die Quell- und Zielwerte für jeden Key in jeder Ziel-Locale |
| `verbatra_locale_integrity` | jeder übersetzte Key, der die Prüfungen für Platzhalter, Inline-Markup, ICU oder ICU-Zweige nicht besteht, pro Ziel-Locale |
| `verbatra_key_context` | Quell- und Zielwert eines Keys, seine Beschreibung und die Glossareinträge, die seine Quelle verwendet |
| `verbatra_translation_estimate` | was `verbatra_translation_translatePending` senden und kosten würde, optional für eine Teilmenge der `locales`, ohne einen Provider aufzurufen |

`verbatra_key_integrity` ist anders geformt als `key.integrity` des stdio-MCP-Servers. Sein `result` ist `{ locales: [...] }`, und jede Zeile trägt `locale` direkt neben den Prüffeldern (`hasPlaceholders`, `matches`, `missing`, `extra`, `icuValid`, `icuArmsMatch`, `icuArmDetails`, `markupMatches`, `markupDetails`), ohne `entries`-Array. Eine Locale erscheint nur, wenn sich die Quelle des Keys dort seit der Baseline geändert hat: Eine Locale, in der der Key noch keinen Baseline-Eintrag hat, unverändert ist oder fehlt, hat gar keine Zeile. Eine leere `locales`-Liste heißt also, dass nichts zu prüfen war, nicht dass der Key bestanden hat. [`key.integrity`](/docs/cli/mcp#inputs-und-ergebnisse) liefert dagegen eine Zeile für jede Locale im Umfang und verschachtelt dieselben Felder in einem `entries`-Array, das in diesen Fällen leer ist.

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

Seit `@verbatra/studio` 0.6.0 melden `verbatra_key_value` und `verbatra_locale_values` außerdem, wer jeden vorhandenen Wert geschrieben hat (Herkunft, Provider und Modell bei Maschinenübersetzung sowie Prüfstatus), `verbatra_status_check` und `verbatra_lock_state` zählen die Werte jeder Locale nach Herkunft, und `verbatra_status_diff` nennt die Herkunft des aktuellen Werts jedes geänderten Keys. Siehe [Die Lock-Datei](/docs/the-lock-file#herkunft-wer-welchen-wert-geschrieben-hat).

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

`verbatra_locale_integrity` führt dieselben Prüfungen wie `verbatra_key_integrity` für jeden Key aus, der in der Quelle und in einer Ziel-Locale vorkommt, egal wie sein Sync-Zustand ist, und liefert die Daten für den Filter **Integrity problems** auf der Seite Translations. Sein `result` ist `{ locales: [{ locale, entries }] }`, und jeder Eintrag trägt `key` und die Prüffelder. Aufgeführt werden nur fehlerhafte Keys, eine leere `entries`-Liste heißt also, dass jede Übersetzung dieser Locale besteht; ein fehlender Key hat keine Übersetzung zum Prüfen und taucht nie auf. Jeder Aufruf liest und parst jede Locale-Datei einmal. Der optionale Parameter `locales` beschränkt den Bericht auf die genannten Ziel-Locales.

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

`verbatra_key_context` liefert, was der Editor des Dashboards für einen Key und eine Locale zeigt: `source`, `target` und seine `provenance`, wenn ein Wert existiert, `description`, wenn die Quelldatei eine angibt, und `glossary`, die Begriffe, deren Quelle im Quelltext vorkommt, als `{ terms, doNotTranslate }` mit der Übersetzung und den verbotenen Wiedergaben, an die diese Locale gebunden ist, und `maxLength`, wenn die Config ein Längenbudget für den Key setzt. Gib den Wert, den du schreiben willst, als optionalen Parameter `draft` mit, dann trägt das Ergebnis auch `draftCheck`: für jeden zutreffenden Begriff `targetUsed` und `forbiddenUsed` und für jeden unübersetzt zu lassenden Begriff `kept`, beurteilt nach den Regeln, mit denen ein Übersetzungslauf eine Übersetzung zur Prüfung markiert. Glossarwerte laufen durch dieselbe Schwärzung wie bei `verbatra_glossary_get`.

<AvailableFrom version="0.7.0" pkg="@verbatra/studio" />

Die Review-Warteschlange kommt aus den committeten Dateien: `verbatra_review_queue` listet jeden Wert mit der Herkunft `machine`, `memory`, `fuzzy` oder `agent`, den niemand freigegeben hat, dieselbe Warteschlange, die jedes Teammitglied sieht, und behält einen Wert, den ein Agent bearbeitet hat, weil diese Bearbeitung noch einen Blick von einer Person braucht. Sein optionaler Parameter `includeApproved` listet zusätzlich die freigegebenen. Bis `@verbatra/studio` 0.6.0 listete es nur die Markierungen des letzten Laufs, und die Buttons **Approve** und **Reject** im Dashboard hatten kein Agent-Tool.

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

Auch die Sammelaktionen der Review-Seite, **Approve selected**, **Reject selected** und **Retranslate selected**, haben kein Agent-Tool. Eine Sammelentscheidung trifft weiterhin eine Person, und eine Sammel-Neuübersetzung würde einen einzigen Agent-Aufruf für bis zu 20 Einträge auf einmal Geld ausgeben lassen, also übersetzt ein Agent einen Eintrag pro Aufruf von `verbatra_translation_retranslateEntry` neu. Eine Sammel-Neuübersetzung aus dem Dashboard zieht aus demselben Budget wie einzelne Neuübersetzungen, ein Platz pro Eintrag, sodass beide zusammen nie über 20 neu übersetzte Einträge pro gleitender Minute kommen.

### Schreib-Tools (vier)

`verbatra_translation_editEntry` bearbeitet den Wert einer Locale an Ort und Stelle. Es läuft durch dasselbe Integritäts-Gate wie jeder andere verbatra-Schreibvorgang: ein Wert, der eine der Prüfungen nicht besteht, wird abgelehnt, und nichts wird geschrieben. Eine akzeptierte Bearbeitung schreibt die Locale-Datei und rückt den Lock-Eintrag des Keys vor, genau wie eine Bearbeitung im Dashboard. Bearbeiten braucht kein Ausgaben-Flag; es berührt nur deine lokalen Dateien und ruft nie einen Provider auf, ungebremst ist es aber nicht: Es ist auf 20 Bearbeitungen pro gleitender Minute begrenzt, und ein zweiter Aufruf für dieselbe Locale und denselben Key, während einer noch läuft, wird mit `ALREADY_IN_PROGRESS` (HTTP 409) abgelehnt statt eingereiht, damit zwei Aufrufer nicht in einen Wettlauf um einen Eintrag geraten.

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

Eine Bearbeitung über `verbatra_translation_editEntry` wird in `verbatra.provenance.json` mit der Herkunft `agent` festgehalten, eine Bearbeitung aus dem Dialog des Dashboards dagegen als `human`. Das Tool setzt das selbst; ein Agent kann es nicht wählen.

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

`verbatra_translation_retranslateEntry` lehnt einen Key, dessen Wert ein Mensch geschrieben, importiert oder außerhalb von verbatra geändert hat, mit `KEY_PROTECTED` ab und einen gepinnten Key mit `KEY_PINNED`; der Agent kann beides nicht übersteuern. `verbatra_translation_editEntry` lehnt einen gepinnten Key ab. Im Dashboard wird ein Mensch, der so einen Key neu übersetzt, zuerst gefragt und kann **Replace anyway** wählen. Siehe [Menschliche Übersetzungen schützen](/docs/protecting-human-translations).

<AvailableFrom version="0.4.0" pkg="@verbatra/studio" />

`verbatra_glossary_write` ändert einen Glossarbegriff und gibt das Glossar in seinem neuen Stand zurück: eine Übersetzung für alle Locales oder für eine `locale`, die verbotenen Wiedergaben (`forbidden`) dieser Locale, eine `note`, eine `partOfSpeech`, `caseSensitive` oder mit `doNotTranslate`, ob der Begriff in jeder Locale unübersetzt bleibt. Eine `translation` von `null` löscht diese Übersetzung, und der Begriff wird entfernt, sobald nichts anderes mehr übrig ist. Es arbeitet nur mit einem dateibasierten Glossar: ein inline in der Konfiguration geschriebenes Glossar, oder gar keines, wird abgelehnt statt umgewandelt, und kein Parameter nennt eine Datei, denn das Ziel stammt allein aus der geladenen Konfiguration. Wie das Bearbeiten gibt es nichts aus und wird ohne `--allow-spend` registriert. Es ist auf 20 Schreibvorgänge pro gleitender Minute begrenzt.

<AvailableFrom version="0.7.0" pkg="@verbatra/studio" />

`verbatra_review_approve` und `verbatra_review_reject` halten eine Review-Entscheidung über den aktuellen Wert eines Keys in `verbatra.provenance.json` fest, genau wie die Buttons **Approve** und **Reject** im Dashboard. Es gibt sie, damit eine Person den Agenten eine Entscheidung weitergeben lassen kann, nie damit ein Agent seine eigene Arbeit freigibt: Beide Beschreibungen sagen dem Agenten, sie nur auf ausdrückliche Anweisung des Nutzers aufzurufen, und beide verlangen `reviewer`, den Namen der Person, die entschieden hat, 1 bis 64 Zeichen, gespeichert in der committeten Datei. Beide nehmen außerdem `locale`, `key` und `expectedValue`, den Text, den der Nutzer geprüft hat; ein anderer aktueller Wert wird mit `REVIEW_VALUE_CHANGED` abgelehnt. `verbatra_review_reject` entfernt den Wert, damit er ersetzt wird, ohne Rückgängig auf dieser Oberfläche. Beide teilen sich das Ratenlimit für Review-Entscheidungen, standardmäßig 60 Aufrufe pro rollierender Minute. **Approve all in** für eine Locale hat wie die anderen Sammelaktionen kein Agent-Tool.

### Ausgaben-Tools (zwei)

Diese rufen einen Übersetzungs-Provider auf und werden nur registriert, wenn Studio zusätzlich mit `--allow-spend` läuft:

- `verbatra_translation_retranslateEntry`: übersetzt einen Key und eine Locale neu.
- `verbatra_translation_translatePending`: übersetzt alles derzeit Ausstehende.

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

`verbatra_translation_translatePending` nimmt zwei optionale Parameter. `locales` grenzt den Lauf auf diese konfigurierten Ziel-Locales ein und lässt die anderen unberührt; eine unbekannte Locale wird mit `UNKNOWN_LOCALE` abgelehnt, bevor irgendetwas ausgegeben wird. `maxTokens` ist eine harte Token-Obergrenze für den Aufruf, genau wie [`verbatra translate --max-tokens`](/docs/cli/translate): Eine Anfrage, die sie überschreiten würde, wird zurückgehalten statt gesendet, und setzt die Konfiguration ebenfalls `maxTokens`, gilt der niedrigere der beiden Werte. Frag die Zahl vorher mit `verbatra_translation_estimate` ab: Es liefert dasselbe Ergebnis wie `translate --estimate --json`, wird mit oder ohne `--allow-spend` registriert und ruft nie einen Provider auf. Siehe [Kosten abschätzen](/docs/estimating-cost).

Beide schicken ihre Ergebnisse durch das Integritäts-Gate, bevor irgendetwas die Platte erreicht, und für beide gelten Studios bestehende Ratenlimits (Neuübersetzen 20 pro gleitender Minute, Translate-pending 5 pro gleitender Minute plus eine Sperre gegen parallele Läufe). `verbatra_translation_retranslateEntry` trägt zusätzlich dieselbe Sperre pro Eintrag wie das Bearbeiten: ein gleichzeitiger zweiter Aufruf für dieselbe Locale und denselben Key wird mit `ALREADY_IN_PROGRESS` (HTTP 409) abgelehnt. Ohne `--allow-spend` fehlen sie im Tool-Set, und der Server registriert die zugrunde liegenden Endpunkte gar nicht erst: Ausgaben, die du beim Start nicht gewährt hast, sind für einen Agenten nicht erreichbar.

### Wenn ein Aufruf fehlschlägt

Jedes Tool liefert den RPC-Envelope des Dashboards selbst als JSON, ein fehlgeschlagener Aufruf lautet also `{ "ok": false, "error": { "code": ..., "message": ... } }`. Neben den Domänen-Codes, die das SDK meldet (eine Ablehnung durch die Integritätsprüfungen, ein unbekanntes Locale oder ein unbekannter Key), `METHOD_RATE_LIMITED` für einen Aufruf über seinem Ratenlimit und der oben beschriebenen Ablehnung mit `ALREADY_IN_PROGRESS` stammen die Codes aus der RPC-Schicht selbst:

- `REQUEST_INVALID`: Der Request-Body war kein JSON-Objekt, das eine Methode nennt, oder die Antwort des Servers war kein Envelope, den der Tab lesen konnte.
- `METHOD_UNKNOWN`: Die Methode ist keine, die Studio kennt, oder sie ist in dieser Sitzung nicht registriert, wie eine Ausgaben-Methode ohne `--allow-spend`.
- `PARAMS_INVALID`: Die Parameter haben die Validierung nicht bestanden; der Fehler trägt eine `issues`-Liste, die jedes fehlerhafte Feld nennt.
- `SESSION_EXPIRED`: Der Server akzeptiert das Sitzungscookie des Tabs nicht mehr, meist weil Studio mit einem neuen Token neu gestartet wurde. Der Tab ruft den Server nicht mehr auf und zeigt den Bildschirm Session expired; öffne die URL, die das laufende Studio ausgegeben hat, um eine neue Sitzung zu starten.

<AvailableFrom version="0.6.0" pkg="@verbatra/studio" />

Eine Ablehnung mit `METHOD_RATE_LIMITED` trägt zusätzlich `retryAfterSeconds` in `error`, mit derselben Zahl im `Retry-After`-Header der Antwort: die Sekunden, bis der Aufruf wieder passt. Eine Ablehnung mit `BATCH_TOO_LARGE`, für einen Stapel mit mehr Einträgen, als ein Fenster erlaubt, trägt keins von beiden, denn ein Stapel dieser Größe passt nie: Schick weniger Einträge. `verbatra_project_snapshot` meldet die Limits für Neuübersetzen und Review-Entscheidungen unter `capabilities.limits`, jeweils als `{ windowMs, max }`, damit ein Agent seine Aufrufe takten kann, statt in die Limits zu laufen.

## Der Degraded-Mode-Hinweis

Die Registrierung hat drei mögliche Ausgänge, und nur einer davon ist ein Problem.

**Nichts versucht, nichts gemeldet.** Fehlt `document.modelContext` (ein Browser ohne WebMCP oder Chrome ohne das Flag) oder hast du das Opt-in nicht gesetzt, versucht Studio überhaupt keine Registrierung. Das Dashboard bleibt unverändert und die Konsole bleibt still. Das ist der vorgesehene No-Op, kein Fehler.

**Achtzehn Tools und kein Hinweis.** Ohne `--allow-spend` versucht Studio achtzehn Registrierungen statt zwanzig: die beiden Ausgaben-Tools werden übersprungen, bevor sie überhaupt versucht werden. Achtzehn Tools sind die gesunde Zahl für eine Sitzung ohne Ausgaben, ihr Fehlen ist also der erwartete Zustand und löst nie einen Hinweis aus.

**Der Hinweis.** Hat Studio eine Registrierung versucht und der Browser sie abgelehnt, zeigt das Dashboard oben im Inhaltsbereich eine Warnung, auf jeder Ansicht:

> Agent tools degraded: 2 of the agent tool registrations failed with SecurityError. The dashboard itself is unaffected. The browser console lists every failing tool.

Zahl und Fehlername sind die echten aus diesem Durchlauf. Der Hinweis hat kein Bedienelement zum Schließen und bleibt für die Lebensdauer der Seite stehen. Ein Neuladen des Tabs startet einen frischen Registrierungsdurchlauf, denn der Status wird nur im Speicher gehalten.

### Was im Degraded-Modus weiterhin funktioniert

Ein fehlschlagendes Tool bricht nie die nachfolgenden ab, also bleibt jedes Tool, das sich registriert hat, aufrufbar und die Oberfläche ist meist teilweise nutzbar statt ausgefallen. Das Dashboard bleibt unberührt: die menschliche Oberfläche, die RPCs und jedes Capability-Gate verhalten sich genau so, wie sie es bei ausgeschalteter Oberfläche täten, und keine Locale-Datei ist betroffen.

### Die Konsole lesen

Studio schreibt eine einzige zusammengefasste Zeile auf Error-Ebene, nicht eine Zeile pro Tool, denn eine gemeinsame Ursache lässt jedes Tool identisch scheitern:

```text
Verbatra agent tools: 2 of 20 tool registrations failed. verbatra_status_diff (SecurityError: ...); verbatra_key_value (SecurityError: ...)
```

Der erste Satz nennt, wie viele der versuchten Registrierungen fehlgeschlagen sind, und von wie vielen Versuchen: hier zwanzig, weil diese Sitzung mit `--allow-spend` gestartet wurde, und achtzehn in einer Sitzung ohne das Flag. Danach folgt jedes fehlschlagende Tool als `name (ErrorName: message)`, getrennt durch Semikolons. Der Fehlername benennt die Ursache: es ist der `name` des Werts, mit dem der Browser abgelehnt hat, meist eine `DOMException` wie `SecurityError` oder `InvalidStateError`.

Ein Durchlauf, der die Tool-Schleife nie erreicht hat, meldet eine andere Zeile und löst den Hinweis nicht aus:

```text
Verbatra agent tools: registration did not start (TypeError: Failed to fetch).
```

Das heißt, der Projekt-Snapshot-Aufruf, der entscheidet, ob die Oberfläche freigeschaltet ist, ist beim Laden fehlgeschlagen, sodass kein Tool versucht wurde.

### Was du dagegen tun kannst

Keine Studio-Einstellung behebt eine abgelehnte Registrierung, denn die Ablehnung kommt vom Browser. In der Praxis:

- Lies zuerst den Fehlernamen in der Konsole. Er benennt die Ursache genauer als der Hinweis.
- Lade den Tab neu. Die Registrierung läuft einmal pro Seitenaufruf, eine vorübergehende Ablehnung verschwindet also.
- Prüfe die Voraussetzungen im Browser oben erneut. Ein fehlendes Flag oder ein Browser ohne WebMCP führt zum stillen No-Op, nie zu diesem Hinweis; wenn du den Hinweis siehst, ist die Oberfläche also angelaufen.
- Nutze weiter die Tools, die sich registriert haben, oder arbeite im Dashboard, das ohnehin unbetroffen ist.

## Sicherheitsmodell

Behalte diese Punkte im Kopf, bevor du Agent-Tools einschaltest.

- **Standardmäßig aus.** Du schaltest sie ausdrücklich mit `--expose-agent-tools` (oder `VERBATRA_STUDIO_AGENT_TOOLS`) ein.
- **Ausgaben brauchen beide Flags.** Die beiden Ausgaben-Tools erscheinen nur, wenn du sowohl `--expose-agent-tools` als auch `--allow-spend` übergibst. Keines der Flags impliziert das andere. Lese- und Schreib-Tools geben nichts aus.
- **Keine neue Netzwerk-Exposition.** Jeder Tool-Aufruf nutzt denselben authentifizierten Loopback-RPC wie das Dashboard. Studio bindet sich weiterhin nur an `127.0.0.1`, und das Browser-Sitzungstoken authentifiziert weiterhin jede Anfrage.
- **Übersetzbare Strings sind nicht vertrauenswürdig.** Tools, die aus dem Projekt stammenden Text zurückgeben können (Locale-Strings, Key-Namen, Glossarbegriffe, Commit-Betreffzeilen, Platzhalter-Tokens), markieren ihren Inhalt als nicht vertrauenswürdig, damit ein konsumierender Agent diese Werte als Daten behandelt und nicht als Anweisungen.

### Das akzeptierte Ausgabenrisiko

Das gehört klar gesagt: Sind `--allow-spend` und `--expose-agent-tools` beide an, kann ein autonomer Agent Provider-Ausgaben auslösen, ohne dass ein Mensch jeden Klick bestätigt. Studio baut keinen Freigabedialog pro Aufruf ein: der Server kann einen vom Agenten ausgelösten Aufruf nicht von einem menschlichen Klick in derselben Sitzung unterscheiden, ein solcher Dialog würde also falsche Sicherheit geben und den Sinn der Funktion zunichtemachen. Die Ratenlimits oben begrenzen die Kosten weiterhin, aber ein Agent kann von sich aus bis an diese Obergrenze laufen.

Schalte agentengesteuerte Ausgaben bewusst frei. Wenn ein Agent nur den Zustand ansehen und Einträge von Hand korrigieren soll, starte Studio ohne `--allow-spend`: Agent-Tools funktionieren in diesem Lese- und Bearbeitungsmodus vollständig, und kein Tool erreicht einen Provider.
