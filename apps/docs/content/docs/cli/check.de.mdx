---
title: verbatra check
description: Melde, welche Keys pro Locale fehlen oder veraltet sind, ohne Dateien zu schreiben.
---
Melde pro Ziel-Locale, wie viele Keys fehlen, veraltet oder aktuell sind, und beende den Lauf mit einem Code, auf den ein CI-Schritt verzweigen kann. `check` führt dasselbe Lesen und Diffen aus, das [`verbatra translate`](/docs/cli/translate) direkt vor dem Provider-Aufruf ausführen würde, und hört dann auf: kein Provider-Aufruf, keine geschriebenen Dateien, keine Aktualisierung der [Lock-Datei](/docs/the-lock-file) und kein API-Key nötig.

## Synopsis

```bash
verbatra check [flags]
```

## Flags

| Flag | Argument | Standard | Wirkung |
| --- | --- | --- | --- |
| `--cwd` | `<path>` | aktuelles Verzeichnis | Konfiguration und Locale-Dateien von diesem Verzeichnis aus auflösen |
| `--config` | `<path>` | wird gesucht | diese Konfigurationsdatei laden, statt eine zu suchen |
| `--locales` | `<list>` | alle konfigurierten Ziele | kommagetrennte Teilmenge der Ziel-Locales, die geprüft wird |
| `--consistency` | keins | aus | zusätzlich pro Locale jeden Quellstring melden, der unter verschiedenen Keys unterschiedlich übersetzt ist; nur ein Bericht, der Exit-Code ändert sich nie |
| `--json` | keins | aus | einen [JSON-Envelope](/docs/ci-and-exit-codes#json-ausgabe) auf stdout ausgeben, der die Prüf-Zusammenfassung unter `result` trägt, oder bei einem fehlgeschlagenen Lauf den Fehlercode; die menschenlesbare Fehlerzeile geht weiter auf stderr |

Ein Key fehlt, wenn die Quelle ihn hat und das Ziel nicht; er ist veraltet, wenn sich der Quellstring seit der letzten Übersetzung geändert hat. Ein Locale ist synchron, wenn es keines von beidem hat. Ein leerer oder unbekannter `--locales`-Wert wird mit Exit `2` abgelehnt, statt stillschweigend nichts zu prüfen; ein Tippfehler in einem Locale-Namen lässt ein CI-Gate also nie durch. Du willst die konkreten Key-Listen hinter den Zählern? Das ist [`verbatra diff`](/docs/cli/diff).

## Konsistenzbericht

<AvailableFrom version="0.11.0" />

`--consistency` ergänzt einen zweiten, nur lesenden Bericht: pro Ziel-Locale jeden Quellstring, den zwei oder mehr Keys unterschiedlich übersetzen. Jeder Fund nennt den Quellstring, jede abweichende Übersetzung und die Keys, die sie tragen, damit du dich für eine Formulierung entscheiden und den Rest von Hand angleichen kannst. Nichts wird für dich geändert.

Es ist ein Bericht und sonst nichts. Er ändert nie den Exit-Code, macht kein Locale unsynchron, hält keinen Wert zurück, schreibt keinen um und markiert keinen Key zur Prüfung. Wie der Rest von `check` ruft er keinen Provider auf und braucht keinen API-Key.

Der Vergleich folgt einem Satz von Regeln, für Quelle und Übersetzung gleichermaßen:

- Werte werden nach Unicode-NFC-Normalisierung, dem Umwandeln von `\r\n` in `\n` und dem Entfernen von Leerraum am Anfang und Ende verglichen, `"Save "` und `"Save"` gelten also als derselbe String. Leerraum innerhalb des Werts und Groß- und Kleinschreibung zählen.
- Verglichen werden nur aktuelle Keys. Ein fehlender Key hat noch keine Übersetzung, und die Übersetzung eines veralteten Keys gehört zu einem älteren Quelltext, den `check` ohnehin meldet.
- Keys werden nie gruppiert, wenn sich Beschreibung, Bedeutung, Plural-Kennzeichen oder gettext-`msgctxt` unterscheiden, denn diese Metadaten sind genau dafür da, eine andere Übersetzung zu erlauben.
- Pluralformen werden pro Form verglichen. Ein Format, das jede Form unter einem eigenen Key ablegt (i18next, Apple `.stringsdict` und `.xcstrings`, Android `<plurals>`, gettext `msgstr[n]`), gruppiert die Formen `one` und `other` eines Keys nie miteinander, auch wenn ihr Quelltext identisch ist; dieselbe Form unter verschiedenen Keys wird weiterhin verglichen.
- Eine Übersetzung, die mit ihrer eigenen Quelle identisch ist, ist hier kein Fund; ein Übersetzungslauf markiert das bereits als `EQUALS_SOURCE` zur Prüfung.

Gruppen sind nach Quellstring sortiert, Übersetzungen nach Wert und Keys nach Namen, derselbe Katalog ergibt also immer denselben Bericht. Mit `--json` trägt jedes Locale in `result.locales` ein Array `inconsistencies` aus `{ source, context?, description?, meaning?, isPlural, pluralForm?, translations: [{ value, keys }] }`; ohne das Flag fehlt das Feld.

### Bekannte Einschränkungen

- i18next-Kontextvarianten werden gemeldet. i18next kodiert einen Kontext als Key-Suffix (`invite_male`, `invite_female`), das sich nicht von einem gewöhnlichen snake_case-Key unterscheiden lässt. Zwei Kontextvarianten mit gleichem Quelltext, aber unterschiedlicher Übersetzung erscheinen deshalb als Fund. Wenn dein Format es unterstützt, gib ihnen eine abweichende Beschreibung oder Bedeutung, dann werden sie nie gruppiert; andernfalls ignoriere den Fund.
- gettext-Einträge mit `#, fuzzy` zählen als Übersetzungen. Der gettext-Adapter übernimmt das Fuzzy-Flag nicht, deshalb wird ein Fuzzy-`msgstr` wie ein geprüfter verglichen und kann in einem Fund auftauchen. Prüfe oder bereinige Fuzzy-Einträge, bevor du dich auf den Bericht verlässt.
- Plural-Keys in einem Format ohne Pluralkonzept zählen als gewöhnliche Keys. Die Adapter für `yaml`, `ngx-translate-json`, `xliff`, `properties`, `ini` und `resx` kennen keine Pluralformen, deshalb sind `item_one` und `item_other` für sie zwei unabhängige Keys. Haben zwei solche Formen eines Keys den gleichen Quelltext, aber eine unterschiedliche Übersetzung, erscheinen sie als Fund. Wenn dein Format es unterstützt, gib ihnen eine abweichende Beschreibung oder Bedeutung, dann werden sie nie gruppiert; andernfalls ignoriere den Fund.
- `custom:`-Formate bekommen keinen Resolver für Pluralformen. verbatra weiß nur, wie seine eingebauten Adapter Pluralformen benennen. Speichert ein Adapter eines Drittanbieters jede Form unter einem eigenen Key, werden die Formen eines Keys deshalb als eine Gruppe verglichen und können als Fund erscheinen, wenn sie den gleichen Quelltext haben. Gib den Formen eine abweichende Beschreibung oder Bedeutung, oder ignoriere den Fund.

## Beispiele

```bash
# fail the build when translations drifted
verbatra check

# machine-readable status for two locales
verbatra check --locales de,fr --json

# also list source strings translated more than one way
verbatra check --consistency
```

## Exit-Codes

| Code | Bedeutung |
| --- | --- |
| `0` | synchron: kein Locale hat einen fehlenden oder veralteten Key |
| `1` | nicht synchron: mindestens ein Locale hat einen fehlenden oder veralteten Key (der Bericht wird trotzdem ausgegeben) |
| `2` | konnte nicht laufen: ein Fehler des gesamten Laufs oder ein Verwendungsfehler (einschließlich eines leeren oder unbekannten `--locales`-Werts) |

Exit `1` heißt "nicht synchron", nicht Fehlschlag: der Lauf selbst war erfolgreich, das Ergebnis ist nur nicht komplett grün.

Auf einem Projekt, dessen Quell-Locale-Datei noch nicht vorhanden ist, kann `check` gar nicht laufen: Es scheitert als Ganzes mit `SOURCE_UNREADABLE` und endet mit `2`. [`verbatra doctor`](/docs/cli/doctor) prüft die Einrichtung selbst und liefert auch für ein solches Projekt noch einen Bericht.
