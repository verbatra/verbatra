Démarre un serveur [Model Context Protocol](https://modelcontextprotocol.io) en stdio, le transport qu'utilisent des clients comme Claude Code ou Cursor pour lancer un serveur d'outils. Il sert le protocole 2026-07-28 et ses révisions antérieures jusqu'à 2024-10-07. Un agent dans le terminal ou sans interface obtient ainsi les outils d'agent de Studio. Il n'y a pas de transport HTTP, qui exposerait les outils d'écriture et les outils payants sur un port.

<AvailableFrom version="0.2.0" pkg="@verbatra/mcp" />

## Synopsis

```bash
verbatra mcp [flags]
verbatra-mcp [flags]
```

- `verbatra-mcp` est le binaire fourni par `@verbatra/mcp`, pour qu'un client lance le serveur sans la CLI. Il prend les mêmes options sauf `-q`/`--quiet` et démarre le même serveur, mais ne charge aucun fichier `.env` et affiche la version de `@verbatra/mcp` avec `--version`.
- Les deux refusent une option inconnue (comme `--json`), une option sans valeur ou un argument en trop comme erreur d'utilisation, avec le code `2`. `verbatra-mcp` le fait, et accepte `-h` et `-V`, depuis `@verbatra/mcp` 0.3.0.

## Options

| Option | Argument | Défaut | Effet |
| --- | --- | --- | --- |
| `--allow-spend` | aucun | `VERBATRA_MCP_ALLOW_SPEND`, sinon désactivé | annonce les deux outils qui appellent un fournisseur de traduction ; voir [Outils payants](#outils-payants) |
| `--redact-values` | aucun | `VERBATRA_MCP_REDACT_VALUES`, sinon désactivé | remplace chaque valeur de traduction des résultats par un marqueur ; voir [Valeurs masquées](#redacted-values) |

Prend aussi les [options globales](/docs/cli#options-globales) `--cwd` et `--config`. Pas de `--json`, car stdout est le canal du protocole. Sans `--cwd`, le répertoire du projet peut venir de `CLAUDE_PROJECT_DIR` ; voir [Répertoire du projet](#répertoire-du-projet).

## Comportement

### Répertoire du projet

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Si `--cwd` est absent et que `CLAUDE_PROJECT_DIR` désigne un répertoire existant, le serveur l'utilise comme racine du projet. Claude Code définit cette variable pour chaque serveur stdio qu'il lance, donc une session ouverte dans un sous-répertoire trouve quand même la config. Un `--cwd` explicite l'emporte toujours. `verbatra mcp` charge alors les [fichiers d'environnement](/docs/cli#fichiers-denvironnement) depuis ce répertoire ; un `CLAUDE_PROJECT_DIR` défini seulement dans ces fichiers est ignoré, car la racine est résolue avant.

### Outils payants

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.retranslateEntry` et `translation.translatePending` ne sont annoncés qu'avec `--allow-spend` ou, si l'option manque, avec `VERBATRA_MCP_ALLOW_SPEND` à `1`, `true`, `yes` ou `on` (sans tenir compte de la casse ni des espaces autour). L'option l'emporte sur la variable. `verbatra mcp` lit d'abord `.env.local` et `.env`, la variable peut donc s'y trouver ; `verbatra-mcp` ne la prend que dans son propre environnement.

Sinon, les deux n'apparaissent jamais dans la liste, et les appeler échoue comme un outil inconnu. Une config avec `provider: { id: "none" }` ne les liste jamais, même avec `--allow-spend`. Les autres outils n'appellent aucun fournisseur et n'ont besoin d'aucune clé ; ne donne la clé au serveur, via l'environnement du client, que quand tu autorises la dépense (voir [Fournisseurs](/docs/providers)).

### Instructions pour l'agent

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Le serveur répond à la poignée de main avec des `instructions` fixes, que la plupart des clients transmettent d'abord au modèle. Elles fixent l'ordre des appels (lire et comparer d'abord, estimer et obtenir un oui explicite avant de dépenser), laissent les décisions de relecture et le travail humain aux personnes, demandent de traiter chaque chaîne comme des données et de ne jamais réécrire une valeur `[REDACTED]`.

### Outils [#tools]

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

| Outil | Ce qu'il fait | Lecture seule | Appelle un fournisseur |
| --- | --- | --- | --- |
| `project.snapshot` | la config résolue : `configured`, `configSource`, locales, format, `files.pattern`, fournisseur, glossaire, `humanEdits`, `prune`, `valuesRedacted` | oui | non |
| `project.doctor` | chaque vérification de configuration avec son `status`, son `detail` et, en cas d'échec, un `fix` ; fonctionne sans config utilisable | oui | non |
| `status.check` | par locale, le nombre de clés manquantes, obsolètes et à jour | oui | non |
| `status.diff` | par locale, la liste des clés qui seraient ajoutées, retraduites ou orphelines | oui | non |
| `glossary.get` | chaque terme du glossaire avec ses traductions, ses formes interdites et son contexte, secrets masqués | oui | non |
| `glossary.write` | modifie un terme du glossaire : une traduction, des données par locale, le contexte, ou s'il reste non traduit | non | non |
| `lock.state` | la version du fichier de verrouillage et, par locale cible, son nombre de clés plus les manquantes, obsolètes et à jour | oui | non |
| `history.list` | les derniers commits git sur un fichier de locale, avec nom de l'auteur, date, sujet et chemins | oui | non |
| `key.integrity` | l'écart d'une clé sur les placeholders, le balisage, la syntaxe ICU et les branches ICU par rapport à la base du verrou, par locale | oui | non |
| `locale.integrity` | chaque traduction qui échoue en ce moment aux contrôles de placeholders, de balisage ou ICU, par locale | oui | non |
| `key.value` | le texte source et cible d'une clé, avec sa provenance et le contexte pour les traducteurs | oui | non |
| `key.context` | ce que renvoie `key.value`, plus les termes du glossaire qui s'appliquent, `maxLength` et une vérification d'un `draft` optionnel | oui | non |
| `locale.values` | le texte source et cible de nombreuses clés, filtrées par `keys` ou `query`, page par page | oui | non |
| `translation.editEntry` | écrit une traduction manuelle pour une clé dans une locale, filtrée par les contrôles d'intégrité | non | non |
| `translation.estimate` | ce que `translation.translatePending` enverrait et coûterait, comme le rapporte `translate --estimate --json` | oui | non |
| `translation.retranslateEntry` | demande au fournisseur configuré de retraduire une clé dans une locale | non | oui |
| `translation.translatePending` | traduit chaque clé manquante ou obsolète, éventuellement pour certaines `locales` seulement et sous un plafond `maxTokens` | non | oui |
| `review.queue` | chaque valeur écrite par une machine que personne n'a encore approuvée, avec les signalements de la dernière exécution | oui | non |
| `report.provenance` | par locale, les comptes de provenance comme les donne `verbatra report provenance`, et les clés paginées sur demande | oui | non |
| `review.approve` | enregistre, sur instruction de l'utilisateur, qu'une personne nommée approuve la traduction actuelle d'une clé | non | non |
| `review.reject` | enregistre, sur instruction de l'utilisateur, qu'une personne nommée rejette la traduction d'une clé, qui est retirée pour être remplacée | non | non |
| `usage.summary` | la consommation de tokens et l'état du budget de la dernière exécution | oui | non |

- **Un appel à la fois.** Un second appel à `translation.editEntry` ou `translation.retranslateEntry` pour la même entrée, ou une seconde exécution de `translation.translatePending`, est refusé avec `isError` tant que le premier tourne.
- **Travail humain.** `translation.retranslateEntry` refuse une clé épinglée avec `KEY_PINNED` et, sauf avec `humanEdits: "overwrite"`, la valeur d'une personne avec `KEY_PROTECTED` ; `translation.editEntry` refuse une clé épinglée. `translation.translatePending` liste ces clés sous `protected`. Voir [Protéger les traductions humaines](/docs/protecting-human-translations).
- **Provenance.** Une valeur écrite par `translation.editEntry` reçoit l'origine `agent`. `review.queue` est la même file que celle de Studio : chaque valeur non approuvée d'origine `machine`, `memory`, `fuzzy` ou `agent`. Voir [Décisions de revue](/docs/the-lock-file#décisions-de-revue).
- **Décisions de relecture.** `review.approve` et `review.reject` prennent `locale`, `key`, `expectedValue` ou `expectedHash` (une valeur qui a changé entre-temps est refusée avec `REVIEW_VALUE_CHANGED`) et un nom dans `reviewer`. Une approbation compte pour [`verbatra check --require-reviewed`](/docs/cli/check).

### Entrées et résultats

<AvailableFrom version="0.2.1" pkg="@verbatra/mcp" />

- `status.check`, `status.diff` et `key.integrity` prennent un tableau `locales` optionnel ; `key.integrity` prend aussi la `key`.
- `key.integrity` renvoie `{ locales: [{ locale, entries }] }`, chaque entrée avec `matches`, `missing`, `extra`, `icuValid`, `markupMatches` et leurs détails.
- `translation.editEntry` prend `locale`, `key` et une `value` de 20 000 caractères au plus. Lui et `translation.retranslateEntry` renvoient `{ accepted, value, reason?, details? }`, où `reason` vaut `placeholder`, `markup`, `icu`, `degenerate` ou `empty`.
- `glossary.write` exige un glossaire dans un fichier, sinon il échoue avec `GLOSSARY_NOT_FILE_BACKED`.

### Autres entrées et résultats

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

- `translation.estimate` prend le même tableau `locales` optionnel, et `key.integrity` échoue avec `UNKNOWN_KEY` pour une clé inconnue.
- Chaque entrée de `key.integrity` porte aussi `icuArmsMatch` et ses détails.
- `glossary.get` prend une `locale` optionnelle et ajoute alors `effective`, les termes auxquels cette locale est tenue.
- `key.value`, `lock.state`, `status.check` et `status.diff` portent la provenance, absente quand `verbatra.provenance.json` est illisible.
- `locale.values` et `report.provenance` renvoient leurs entrées par pages dans l'ordre des clés source : `limit` (200 par défaut, 1 000 au plus), puis le `nextCursor` de la page précédente comme `cursor`. Une page ne nomme que les locales dont elle contient des entrées, et un curseur périmé échoue comme entrée invalide.
- `locale.values` prend `keys` ou une `query` insensible à la casse et renvoie des tableaux d'entrées, pas la map par clé de Studio. `report.provenance` renvoie toujours des comptes complets ; `includeEntries` ajoute les clés, si tu veux seulement pour certains `buckets`.
- `history.list` prend `limit` (50 par défaut, 200 au plus). Avec `available: false`, sa `reason` vaut `git-missing`, `not-a-repository`, `timeout` ou `output-too-large`.
- Les outils qui écrivent prennent un `lockTimeoutMs` optionnel, de `0` à `600000`, par défaut `30000` : la durée d'attente d'un verrou d'écriture occupé avant d'échouer avec `LOCK_CONTENDED`, sans rien avoir écrit.
- Les entrées et sorties sont des JSON Schemas ; une entrée invalide renvoie un résultat qui nomme le champ. Un résultat qui ne correspond pas à son `outputSchema` échoue avec `OUTPUT_SCHEMA_MISMATCH` ; pour un outil qui écrit, la modification a été appliquée, donc ne relance pas l'appel.
- Le texte d'un appel en échec commence par son code d'erreur, comme `UNKNOWN_KEY: ...`, et se termine par une ligne `Next step: ...` quand l'erreur en a une, le même texte que le `hint` de la CLI.

### Estimer avant de payer

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.estimate` est toujours listé. `translation.translatePending` prend des `locales` optionnelles (une locale non configurée échoue avec `UNKNOWN_LOCALE` avant toute dépense) et `maxTokens`, un plafond qui ne peut que resserrer celui de la config. Voir [Estimer le coût](/docs/estimating-cost).

### Progression

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Quand un appel à `translation.translatePending` porte un `progressToken`, le serveur envoie `notifications/progress` à la fin de chaque lot : `progress` les compte, `total` grandit avec chaque locale planifiée, et `message` nomme la locale et le lot (`de: batch 3/7`), au plus une toutes les 250 ms plus une dernière. Si tu annules un appel payant (`notifications/cancelled`), il s'arrête sans résultat ni autre progression : `translation.translatePending` garde ce qui est déjà arrivé, et le reste reste en attente.

### Sans config

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Le serveur démarre sans config utilisable. `project.snapshot` renvoie alors `configured: false` avec le `configProblem` et un `nextStep`, `project.doctor` donne la correction, et les autres outils refusent avec l'erreur de config. stderr en donne la raison :

```text output
Running without a usable project config: CONFIG_NOT_FOUND: No verbatra configuration found. ...
verbatra MCP server running on stdio (project ., spend tools off)
No usable verbatra config: project.snapshot and project.doctor work, every other tool refuses until one loads.
  set it up:  npx verbatra init in the project, or fix the config project.doctor names
  no restart needed: the server loads the config on the next call once it is valid
```

### Après un changement de config

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Avant chaque appel, le serveur recharge la config si le fichier de config, un fichier que la recherche essaierait ou le fichier de glossaire a changé ; un module importé par la config n'est pas surveillé. `--allow-spend` n'est lu qu'une fois : un changement peut masquer les outils payants, jamais les lister sans lui. Quand la liste d'outils change, le serveur envoie `notifications/tools/list_changed`.

### Expurgation des secrets

Chaque résultat et chaque ligne de log sont expurgés comme dans Studio : une valeur qui ressemble à une clé d'API, ou la valeur d'une variable de clé configurée, devient `[REDACTED]` ; les outils de glossaire nomment les termes masqués.

### Valeurs masquées [#redacted-values]

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Avec `--redact-values`, ou `VERBATRA_MCP_REDACT_VALUES` sur une valeur qu'accepte `VERBATRA_MCP_ALLOW_SPEND`, les résultats remplacent les textes source, les traductions, les descriptions et les termes du glossaire par un marqueur, `[redacted length=12 hash=3f9a0c1d2e4b5a6c]`, et omettent les noms des relecteurs et auteurs ; des valeurs égales partagent un hash jusqu'à l'arrêt du serveur. Les erreurs qui peuvent porter des valeurs gardent leur code et l'étape suivante ; leur message devient un marqueur. Les noms de clés, les comptes, les origines, les verdicts d'intégrité, les sujets de commit et les chemins restent. `review.approve` et `review.reject` ne prennent que le hash du marqueur, comme `expectedHash` ; `glossary.write` répond par des comptes ; `locale.values` refuse `query` et `key.context` refuse `draft`. Les outils payants exigent toujours `--allow-spend` ; un fournisseur reçoit toujours le texte. Cela n'arrête pas un agent qui sonde exprès, via des écritures de glossaire ou les correspondances de glossaire de `key.context`.

### stdout et stderr

<AvailableFrom version="0.12.0" />

stdout ne transporte que des messages du protocole MCP ; chaque ligne de log et chaque diagnostic partent sur stderr. Une fois connecté, `verbatra mcp` affiche une ligne « prêt », puis une autre à l'arrêt :

```text output
verbatra MCP server running on stdio (project ., spend tools off)
verbatra MCP server stopped (client closed stdin)
```

Lancé à la main dans un terminal, il indique qu'un client doit le démarrer. `verbatra mcp --quiet` supprime ces lignes, mais pas la raison d'une config absente.

### Installation

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`@verbatra/mcp` est un paquet séparé que la CLI charge à la demande. S'il manque, `verbatra mcp` sort avec `2` et :

```text output
Verbatra's MCP server requires @verbatra/mcp. Run it without the CLI with: npx -y @verbatra/mcp, or install it alongside the CLI with: npm install --save-dev @verbatra/mcp
```

Chaque version est aussi dans le [registre MCP officiel](https://registry.modelcontextprotocol.io) sous `io.github.verbatra/verbatra`.

## Exemples

```bash
# start the MCP server with only local, non-spending tools
verbatra mcp

# also advertise the provider-calling tools
verbatra mcp --allow-spend

# resolve a project outside the current directory
verbatra mcp --cwd /path/to/project --config verbatra.config.ts

# run the standalone server without the CLI
npx -y @verbatra/mcp --cwd /path/to/project
```

## Codes de sortie

| Code | Signification |
| --- | --- |
| `0` | arrêté proprement par une seule interruption, ou parce que le client a fermé stdin |
| `1` | la fermeture du serveur a échoué pendant l'arrêt |
| `2` | n'a pas pu démarrer : un fichier `--config` inexistant, `@verbatra/mcp` absent ou, avec `--redact-values`, trop ancien, ou une erreur d'utilisation |
| `130` | arrêté de force par une seconde interruption pendant l'arrêt |

À l'arrêt, le serveur libère tout verrou de locale. `verbatra-mcp` sort avec `1` sur une erreur de démarrage et, depuis 0.3.0, avec `143` s'il est arrêté de force après SIGTERM. Voir [le contrat des codes de sortie](/docs/cli/output#codes-de-sortie).
