<AvailableFrom version="0.11.0" />

Fais entrer ou sortir une mémoire de traduction au format TMX, le format d'échange des principales plateformes de traduction. `tmx import` verse la mémoire d'un autre outil dans [la mémoire de traduction de ce projet](/docs/the-cache), pour que les exécutions suivantes réutilisent ces chaînes au lieu de les repayer ; `tmx export` réécrit la mémoire vers l'extérieur. Aucune des deux directions n'appelle de fournisseur, ne lit de clé d'API ni ne touche au réseau.

## Synopsis

```bash
verbatra tmx <direction> [file] [flags]
```

- `<direction>` : `import` ou `export` ; toute autre valeur est refusée avec `INVALID_DIRECTION`.
- `[file]` : le fichier TMX à lire ou à écrire, par défaut `verbatra-memory.tmx` dans le répertoire de travail.

## Options

| Option | Argument | Défaut | Effet |
| --- | --- | --- | --- |
| `--locales` | `<list>` | chaque locale cible configurée | importe ou exporte seulement ce sous-ensemble de locales cibles, séparées par des virgules |
| `--dry-run` | aucun | désactivé | import uniquement : valide et rapporte sans modifier la mémoire ; un export la refuse avec `INVALID_DIRECTION` |
| `--overwrite` | aucun | désactivé | import uniquement : laisse une unité importée remplacer une traduction que la mémoire possède déjà ; un export la refuse avec `INVALID_DIRECTION` |

La commande accepte aussi les [options globales](/docs/cli#options-globales) `--cwd`, `--config` et `--json`. Ici, `--cwd` est le répertoire depuis lequel la config, la mémoire et un `[file]` relatif sont résolus.

## Comportement

### Ce qu'une unité importée doit satisfaire

Un fichier venu d'un autre outil est une entrée non fiable, et une unité présente dans la mémoire peut être réutilisée sans que personne ne soit consulté à nouveau. Chaque traduction candidate passe donc par le même [contrôle d'intégrité](/docs/translation-safety) que la sortie d'un fournisseur, vérifié à son entrée dans la mémoire :

- ses placeholders correspondent à ceux de son propre segment source,
- ses balises HTML ou XML en ligne correspondent à celles du segment source, si bien qu'une balise injectée comme `<img onerror>` est refusée,
- c'est un message ICU valide pour l'adaptateur du format configuré,
- elle n'a pas dégénéré en sortie incontrôlée,
- elle n'est pas vide là où la source contient du texte.

Une unité dont le segment source est vide ne désigne aucune chaîne et est refusée aussi. Le balisage en ligne (`bpt`, `ept`, `ph`, `it`) est aplati en texte, de sorte que la vérification des placeholders repère un balisage qui portait quelque chose d'important ; le texte d'un élément `sub` est un flux à part (une infobulle, un texte alternatif) et il est écarté. Les propriétés d'un segment, y compris les `x-origin` et `x-review` qu'écrit un export verbatra, sont ignorées : la mémoire n'enregistre aucune origine.

Rien n'est écarté en silence : chaque refus, chaque unité inutilisable, chaque unité sans segment dans ta locale source, chaque unité aplatie et chaque texte `sub` écarté est compté par motif.

<AvailableFrom version="0.12.0" />

Chaque unité refusée est aussi listée avec sa position, son motif et, quand la vérification sait le nommer, ce qui ne va pas, par exemple `unit 12: icu ({count} plural: missing arm "few" required by the target language)`.

### Faire correspondre les étiquettes de langue

Un fichier TMX écrit les langues comme le faisait l'outil de son auteur. La règle de correspondance ne devine jamais :

1. Les deux côtés passent en minuscules et les tirets bas deviennent des tirets, donc `pt_BR`, `pt-br` et `pt-BR` sont une seule locale. Une correspondance exacte l'emporte.
2. Sinon, une locale configurée qui est un préfixe par sous-étiquettes de l'étiquette correspond, la plus longue d'abord (recherche RFC 4647) : avec `de` et `de-AT`, `de-AT-1996` va vers `de-AT` et `de-CH-1901` vers `de`.
3. Une étiquette plus courte atteint aussi une locale configurée qui n'ajoute qu'une région ou une variante, jamais une écriture : `de` va vers `de-DE` et `pt` vers `pt-BR`, mais `sr` jamais vers `sr-Latn`.
4. Des étiquettes dont l'écriture ou la région diffère ne correspondent jamais : `zh-CN` n'est jamais stocké comme `zh-TW`, ni `de-AT` comme `de-CH`.
5. Une étiquette n'est ambiguë que lorsque les locales qu'elle pourrait atteindre ne sont pas sur une même chaîne de préfixes, comme `pt` avec `pt-BR` et `pt-AO` configurées.

Chaque segment est résolu en une seule passe contre la locale source et toutes les cibles configurées, même avec `--locales`, donc une cible `pt-BR` dans un projet dont la source est `pt` n'est jamais lue comme la source. Les segments source sont classés comme les segments cibles : une étiquette exacte l'emporte sur une correspondance par préfixe, des valeurs identiques s'accordent, et des segments de même rang aux valeurs différentes (`en-US` "Color" et `en-GB` "Colour") font refuser l'unité. Une config dont la source et une cible se normalisent en la même étiquette est refusée d'emblée.

Deux segments cibles qui atteignent la même locale ne laissent jamais simplement gagner le dernier : une étiquette exacte l'emporte sur une correspondance par préfixe, et deux segments de même rang aux valeurs différentes ne stockent rien pour cette locale et comptent l'unité comme conflictuelle. Les étiquettes sans correspondance sont comptées par étiquette, les éléments `tu` hors du premier `body` aussi, et un `srclang` d'en-tête qui n'est pas ta locale source est signalé.

### Quand le fichier et la mémoire se contredisent

La mémoire du projet l'emporte : une traduction importée qui diffère d'une traduction déjà présente est refusée et comptée comme conservée, sauf si tu passes `--overwrite`. Dans un même fichier, la première unité pour une source gagne et les répétitions comptent comme doublons, donc importer deux fois le même fichier n'écrit rien la seconde fois.

Les unités importées sont stockées sous l'empreinte de configuration actuelle du projet : elles sont réutilisées exactement tant que le fournisseur, le modèle, le ton, le glossaire et `localeMap` ne changent pas. Réimporte le fichier après un tel changement. Un fichier de mémoire écrit par un verbatra plus récent reste intact ; les comptes sont tout de même rapportés, comme lors d'un dry run.

### Les unités importées et la réutilisation floue

Le texte source d'une unité acceptée rejoint l'index contre lequel la [réutilisation floue](/docs/the-cache) évalue les chaînes modifiées, donc une source importée qui diffère d'une de tes chaînes peut servir pour celle-ci. Une telle réutilisation passe quand même le contrôle d'intégrité face à ta vraie entrée et porte le marqueur de relecture `FUZZY_CACHE_REUSE`. Une source importée identique à une de tes chaînes mais au hash différent (ton entrée a une description, un sens ou un marqueur de pluriel que TMX ne peut pas porter) n'est jamais réutilisée. Retire `fuzzyCache` de ta config pour n'autoriser que les correspondances exactes.

### Ce qu'écrit l'export

Un `tu` par chaîne source distincte, avec le segment source et un segment cible par locale exportée, sous un en-tête TMX 1.4b (`srclang`, `creationtool`, `creationtoolversion`, `segtype`, `o-tmf`). Seules les entrées sous l'empreinte de configuration actuelle sont écrites. Les étiquettes de langue sont écrites en forme BCP 47 (`en_US` devient `en-US`), les caractères que XML 1.0 ne peut pas représenter sont retirés et comptés, et une mémoire vide produit un fichier valide et vide. Les entrées sans texte source stocké, héritées d'un ancien cache, sont écartées et comptées.

<AvailableFrom version="0.12.0" />

Chaque segment cible porte `<prop type="x-origin">` (`machine`, `human`, `import` ou `unknown`) tiré de `verbatra.provenance.json`, et un segment `machine` porte aussi `<prop type="x-review">` (`approved`, `unreviewed` ou `rejected`). Si le fichier de provenance ou le fichier de lock est illisible, aucune propriété n'est écrite et le résultat indique `provenanceMarkers: "unavailable"`. Voir [Preuves de traduction automatique](/docs/provenance-evidence#tmx).

Le fichier n'est écrit que dans le répertoire de travail. Un chemin qui ne nomme aucun fichier, sort du répertoire de travail ou vise un fichier dont dépend le projet (un fichier de locale, le fichier de lock, de provenance ou de cache, un fichier de config, le fichier de glossaire) est refusé avec `TMX_OUTPUT_CONFLICT` avant la lecture de la mémoire, y compris après résolution des liens symboliques. Si l'écriture échoue sur le disque, l'exécution s'arrête avec `TMX_UNWRITABLE`, en nommant le fichier et le code du système de fichiers.

### Sortie JSON

Avec `--json`, l'[enveloppe JSON](/docs/cli/output#sortie-json) porte le résultat de l'import ou de l'export :

```ts
// tmx import
{ dryRun: boolean; file: string; units: number; locales: ImportTmxLocaleResult[];
  unmatchedLanguages: TmxLanguageReport[]; ambiguousLanguages: TmxLanguageReport[];
  memoryWritable: boolean; /* plus the skipped, unmatched and conflicting unit counts */ }

// tmx export
{ path: string; units: number; locales: { locale: string; units: number }[];
  withoutSource: number; illegalCharactersRemoved: number;
  provenanceMarkers: "written" | "unavailable" }
```

Chaque locale de l'import rapporte les comptes `added`, `unchanged`, `overwritten`, `kept`, `duplicates`, `conflicting`, `rejected` par motif, et la liste `refusals`.

### Retour dans le terminal

<AvailableFrom version="0.12.0" />

Les deux directions affichent une ligne de progression sur stderr. `tmx import` suggère ensuite `verbatra translate`, ou le vrai import après un dry run ; `tmx export` ne suggère rien :

```text
verbatra: importing legacy.tmx into the memory... done (0.2s)
next: verbatra translate (reuses the imported memory before calling a provider)
```

`--quiet` supprime ces lignes. Voir [Sortie dans le terminal](/docs/cli/output#sortie-dans-le-terminal).

## Exemples

```bash
# verser la mémoire d'un autre outil dans ce projet
verbatra tmx import legacy.tmx

# rapporter ce qui entrerait, sans rien changer
verbatra tmx import legacy.tmx --dry-run

# laisser gagner le fichier là où il contredit la mémoire
verbatra tmx import legacy.tmx --overwrite

# écrire la mémoire dans verbatra-memory.tmx
verbatra tmx export

# seulement l'allemand, vers un chemin choisi
verbatra tmx export out/memory.tmx --locales de
```

## Codes de sortie

| Code | Signification |
| --- | --- |
| `0` | le fichier a été lu ou écrit ; les unités ignorées ou refusées sont rapportées, ce n'est pas un échec |
| `2` | exécution impossible : une erreur de config, un fichier TMX absent, illisible ou invalide (`SOURCE_INVALID`), un chemin d'export refusé (`TMX_OUTPUT_CONFLICT`), une écriture échouée (`TMX_UNWRITABLE`) ou une erreur d'utilisation |

Pour un fichier invalide, le message nomme la ligne, la colonne et l'unité où il a échoué ; les déclarations d'entités et les sous-ensembles DTD internes sont refusés d'emblée, et un doctype externe est ignoré, jamais téléchargé. Voir [le contrat des codes de sortie](/docs/cli/output#codes-de-sortie).
