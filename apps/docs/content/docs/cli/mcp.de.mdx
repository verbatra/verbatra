Startet einen [Model-Context-Protocol](https://modelcontextprotocol.io)-Server über stdio, den Transport, mit dem Clients wie Claude Code oder Cursor einen Tool-Server starten. Er bedient Protokollrevision 2026-07-28 und frühere Revisionen bis zurück zu 2024-10-07. Ein Agent im Terminal oder ohne Oberfläche bekommt damit Studios Agent-Tools. Einen HTTP-Transport gibt es nicht: Er würde die schreibenden und kostenpflichtigen Tools an einem Port anbieten.

<AvailableFrom version="0.2.0" pkg="@verbatra/mcp" />

## Synopsis

```bash
verbatra mcp [flags]
verbatra-mcp [flags]
```

- `verbatra-mcp` ist das Binary aus `@verbatra/mcp`, mit dem ein Client den Server ganz ohne CLI starten kann. Es nimmt dieselben Flags außer `-q`/`--quiet` und startet denselben Server, lädt aber keine `.env`-Datei und gibt bei `--version` die Version von `@verbatra/mcp` aus.
- Beide lehnen ein unbekanntes Flag (etwa `--json`), ein Flag ohne Wert oder ein überzähliges Argument als Nutzungsfehler mit Exit `2` ab. `verbatra-mcp` tut das, und kennt `-h` und `-V`, ab `@verbatra/mcp` 0.3.0.

## Flags

| Flag | Argument | Standard | Wirkung |
| --- | --- | --- | --- |
| `--allow-spend` | keins | `VERBATRA_MCP_ALLOW_SPEND`, sonst aus | bietet die beiden Tools an, die einen Übersetzungs-Provider aufrufen; siehe [Kostenpflichtige Tools](#kostenpflichtige-tools) |
| `--redact-values` | keins | `VERBATRA_MCP_REDACT_VALUES`, sonst aus | ersetzt jeden Übersetzungswert in Tool-Ergebnissen durch eine Markierung; siehe [Geschwärzte Werte](#redacted-values) |

Nimmt außerdem die [globalen Flags](/docs/cli#globale-flags) `--cwd` und `--config`. Ein `--json` gibt es nicht, weil stdout der Protokollkanal ist. Ohne `--cwd` kann das Projektverzeichnis aus `CLAUDE_PROJECT_DIR` kommen; siehe [Projektverzeichnis](#projektverzeichnis).

## Verhalten

### Projektverzeichnis

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Fehlt `--cwd` und nennt `CLAUDE_PROJECT_DIR` ein vorhandenes Verzeichnis, nimmt der Server es als Projektverzeichnis. Claude Code setzt diese Variable für jeden stdio-Server, den es startet. Ein ausdrückliches `--cwd` gewinnt immer. `verbatra mcp` lädt dann die [Umgebungsdateien](/docs/cli#umgebungsdateien) aus diesem Verzeichnis; ein `CLAUDE_PROJECT_DIR`, das nur in diesen Dateien steht, wird ignoriert, weil das Projektverzeichnis vorher feststeht.

Die Konfigurationssuche beginnt dort, und das Verzeichnis der gefundenen Konfiguration ist die [Projektwurzel](/docs/config-file#das-arbeitsverzeichnis-und-env), gegen die jeder Tool-Pfad aufgelöst wird, sodass ein Server aus einem Unterverzeichnis trotzdem mit den Dateien des Projekts arbeitet.

### Kostenpflichtige Tools

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.retranslateEntry` und `translation.translatePending` werden nur mit `--allow-spend` angeboten, oder, wenn das Flag fehlt, mit `VERBATRA_MCP_ALLOW_SPEND` auf `1`, `true`, `yes` oder `on` (Groß- und Kleinschreibung und umgebende Leerzeichen egal). Das Flag gewinnt gegen die Variable. `verbatra mcp` liest vorher `.env.local` und `.env`, die Variable darf also dort stehen; `verbatra-mcp` nimmt sie nur aus seiner eigenen Umgebung.

Sonst tauchen die beiden nie in der Liste auf, und ein Aufruf scheitert als unbekanntes Tool. Eine Konfiguration mit `provider: { id: "none" }` listet sie nie, auch nicht mit `--allow-spend`. Alle anderen Tools rufen keinen Provider auf und brauchen keinen Schlüssel; gib dem Server den Schlüssel über die Umgebung des Clients erst, wenn du Ausgaben erlaubst (siehe [Provider](/docs/providers)).

### Anweisungen für den Agenten

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Der Server beantwortet den Handshake mit festen `instructions`, die die meisten Clients zuerst an das Modell geben. Sie legen die Reihenfolge der Aufrufe fest (zuerst lesen und vergleichen, vor jeder Ausgabe schätzen und ein ausdrückliches Ja einholen), überlassen Review-Entscheidungen und menschliche Arbeit den Menschen, behandeln jeden String als Daten und schreiben nie einen `[REDACTED]`-Wert zurück.

### Tools

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

| Tool | Was es tut | Nur lesend | Ruft einen Provider auf |
| --- | --- | --- | --- |
| `project.snapshot` | die aufgelöste Konfiguration: `configured`, `configSource`, Locales, Format, `files.pattern`, Provider, Glossar, `humanEdits`, `prune`, `valuesRedacted` | ja | nein |
| `project.doctor` | jede Setup-Prüfung mit `status`, `detail` und, wenn sie fehlschlug, einem `fix`; funktioniert auch ohne brauchbare Konfiguration | ja | nein |
| `status.check` | pro Locale die Zahl fehlender, veralteter und aktueller Keys | ja | nein |
| `status.diff` | pro Locale die Keys, die hinzukämen, neu übersetzt würden oder verwaist sind | ja | nein |
| `glossary.get` | jeden Glossarbegriff mit Übersetzungen, verbotenen Wiedergaben und Kontext, mit geschwärzten Secrets | ja | nein |
| `glossary.write` | einen Glossarbegriff ändern: eine Übersetzung, Daten pro Locale, Kontext, oder ob er unübersetzt bleibt | nein | nein |
| `lock.state` | die Version der Lock-Datei und pro Ziel-Locale die Zahl der Keys plus fehlende, veraltete und aktuelle | ja | nein |
| `history.list` | die letzten Git-Commits an einer Locale-Datei, mit Autorname, Datum, Betreff und Pfaden | ja | nein |
| `key.integrity` | die Abweichung eines Keys bei Platzhaltern, Markup, ICU-Syntax und ICU-Zweigen gegenüber der Lock-Basis, pro Locale | ja | nein |
| `locale.integrity` | jede Übersetzung, die gerade die Prüfung von Platzhaltern, Markup oder ICU nicht besteht, pro Locale | ja | nein |
| `key.value` | Quell- und Zieltext eines Keys, mit Herkunft und Kontext für Übersetzer | ja | nein |
| `key.context` | was `key.value` liefert, dazu die passenden Glossarbegriffe, `maxLength` und eine Prüfung eines optionalen `draft` | ja | nein |
| `locale.values` | Quell- und Zieltext vieler Keys, gefiltert nach `keys` oder `query`, seitenweise | ja | nein |
| `translation.editEntry` | eine manuelle Übersetzung für einen Key in einer Locale schreiben, geprüft durch die Integritätschecks | nein | nein |
| `translation.estimate` | was `translation.translatePending` senden und kosten würde, wie `translate --estimate --json` es meldet | ja | nein |
| `translation.retranslateEntry` | den konfigurierten Provider einen Key in einer Locale neu übersetzen lassen | nein | ja |
| `translation.translatePending` | jeden fehlenden oder veralteten Key übersetzen, wahlweise nur für einige `locales` und unter einer `maxTokens`-Obergrenze | nein | ja |
| `review.queue` | jeden maschinell geschriebenen Wert, den noch niemand freigegeben hat, mit den Markierungen des letzten Laufs | ja | nein |
| `report.provenance` | pro Locale die Herkunftszahlen wie bei `verbatra report provenance`, auf Wunsch mit den Keys, seitenweise | ja | nein |
| `review.approve` | auf Anweisung des Nutzers festhalten, dass eine namentlich genannte Person die aktuelle Übersetzung eines Keys freigibt | nein | nein |
| `review.reject` | auf Anweisung des Nutzers festhalten, dass eine namentlich genannte Person die Übersetzung eines Keys ablehnt; sie wird entfernt und ersetzt | nein | nein |
| `usage.summary` | Token-Verbrauch und Budgetstand des letzten Laufs | ja | nein |

- **Ein Aufruf zur Zeit.** Ein zweiter Aufruf von `translation.editEntry` oder `translation.retranslateEntry` für denselben Eintrag, oder ein zweiter Lauf von `translation.translatePending`, wird mit `isError` abgelehnt, solange der erste läuft.
- **Menschliche Arbeit.** `translation.retranslateEntry` lehnt einen gepinnten Key mit `KEY_PINNED` ab und, außer bei `humanEdits: "overwrite"`, den Wert einer Person mit `KEY_PROTECTED`; `translation.editEntry` lehnt einen gepinnten Key ab. `translation.translatePending` listet solche Keys unter `protected`. Siehe [Menschliche Übersetzungen schützen](/docs/protecting-human-translations).
- **Herkunft.** Ein über `translation.editEntry` geschriebener Wert bekommt die Herkunft `agent`. `review.queue` ist dieselbe Warteschlange, die Studio zeigt: jeder nicht freigegebene Wert mit Herkunft `machine`, `memory`, `fuzzy` oder `agent`. Siehe [Review-Entscheidungen](/docs/the-lock-file#review-entscheidungen).
- **Review-Entscheidungen.** `review.approve` und `review.reject` nehmen `locale`, `key`, `expectedValue` oder `expectedHash` (ein inzwischen geänderter Wert wird mit `REVIEW_VALUE_CHANGED` abgelehnt) und den Namen in `reviewer`. Eine Freigabe zählt für [`verbatra check --require-reviewed`](/docs/cli/check).

### Inputs und Ergebnisse

<AvailableFrom version="0.2.1" pkg="@verbatra/mcp" />

- `status.check`, `status.diff` und `key.integrity` nehmen ein optionales Array `locales`; `key.integrity` nimmt außerdem den `key`.
- `key.integrity` liefert `{ locales: [{ locale, entries }] }`, jeder Eintrag mit `matches`, `missing`, `extra`, `icuValid`, `markupMatches` und den zugehörigen Details.
- `translation.editEntry` nimmt `locale`, `key` und einen `value` mit höchstens 20.000 Zeichen. Es und `translation.retranslateEntry` liefern `{ accepted, value, reason?, details? }`, wobei `reason` `placeholder`, `markup`, `icu`, `degenerate` oder `empty` ist.
- `glossary.write` braucht ein dateibasiertes Glossar, sonst scheitert es mit `GLOSSARY_NOT_FILE_BACKED`.

### Weitere Eingaben und Ergebnisse

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

- `translation.estimate` nimmt dasselbe optionale Array `locales`, und `key.integrity` scheitert bei einem unbekannten Key mit `UNKNOWN_KEY`.
- Jeder Eintrag von `key.integrity` enthält außerdem `icuArmsMatch` mit den zugehörigen Details.
- `glossary.get` nimmt eine optionale `locale` und ergänzt dann `effective`, die Begriffe, an die diese Locale gebunden ist.
- `key.value`, `lock.state`, `status.check` und `status.diff` enthalten die Herkunft; sie fehlt, wenn `verbatra.provenance.json` nicht lesbar ist.
- `locale.values` und `report.provenance` liefern ihre Einträge seitenweise in der Reihenfolge der Quell-Keys: `limit` (Standard 200, höchstens 1.000), danach das `nextCursor` der vorigen Seite als `cursor`. Eine Seite nennt nur die Locales, zu denen sie Einträge enthält, und ein veralteter Cursor scheitert als ungültige Eingabe.
- `locale.values` nimmt `keys` oder eine `query` ohne Beachtung der Groß- und Kleinschreibung und liefert Arrays von Einträgen statt der Map nach Key wie in Studio. `report.provenance` liefert immer vollständige Zahlen; `includeEntries` ergänzt die Keys, auf Wunsch nur für einige `buckets`.
- `history.list` nimmt `limit` (Standard 50, höchstens 200). Bei `available: false` ist sein `reason` `git-missing`, `not-a-repository`, `timeout` oder `output-too-large`.
- Die schreibenden Tools nehmen ein optionales `lockTimeoutMs`, `0` bis `600000`, Standard `30000`: so lange wartet der Aufruf auf eine gehaltene Schreibsperre, bevor er mit `LOCK_CONTENDED` scheitert, ohne etwas geschrieben zu haben.
- Inputs und Outputs sind JSON-Schemas; ein falscher Input liefert ein Ergebnis, das das Feld nennt. Ein Ergebnis, das nicht zu seinem `outputSchema` passt, scheitert mit `OUTPUT_SCHEMA_MISMATCH`; bei einem schreibenden Tool wurde die Änderung trotzdem ausgeführt, also nicht wiederholen.
- Der Text eines fehlgeschlagenen Aufrufs beginnt mit seinem Fehlercode, etwa `UNKNOWN_KEY: ...`, und endet mit einer Zeile `Next step: ...`, wenn der Fehler einen nächsten Schritt hat, demselben Text wie `hint` in der CLI.

### Erst schätzen, dann ausgeben

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.estimate` ist immer gelistet. `translation.translatePending` nimmt optional `locales` (eine nicht konfigurierte scheitert mit `UNKNOWN_LOCALE`, bevor etwas ausgegeben wird) und `maxTokens`, eine Obergrenze, die die der Konfiguration nur verschärfen kann. Siehe [Kosten schätzen](/docs/estimating-cost).

### Fortschritt

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Schickt ein Aufruf von `translation.translatePending` ein `progressToken` mit, sendet der Server `notifications/progress` pro fertigem Batch: `progress` zählt sie, `total` wächst mit jeder geplanten Locale, und `message` nennt Locale und Batch (`de: batch 3/7`), höchstens eine alle 250 ms plus eine letzte. Brichst du einen kostenpflichtigen Aufruf ab (`notifications/cancelled`), stoppt er ohne Ergebnis und weiteren Fortschritt: `translation.translatePending` behält, was schon ankam, der Rest bleibt offen.

### Ohne Konfiguration

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Der Server startet ohne brauchbare Konfiguration. `project.snapshot` liefert dann `configured: false` mit dem `configProblem` und einem `nextStep`, `project.doctor` nennt die Lösung, und jedes andere Tool lehnt mit dem Konfigurationsfehler ab. Auf stderr steht der Grund:

```text output
Running without a usable project config: CONFIG_NOT_FOUND: No verbatra configuration found. ...
verbatra MCP server running on stdio (project ., spend tools off)
No usable verbatra config: project.snapshot and project.doctor work, every other tool refuses until one loads.
  set it up:  npx verbatra init in the project, or fix the config project.doctor names
  no restart needed: the server loads the config on the next call once it is valid
```

### Nach einer Konfigurationsänderung

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Vor jedem Aufruf lädt der Server die Konfiguration neu, wenn sich die Konfigurationsdatei, eine Datei, die die Suche prüfen würde, oder die Glossardatei geändert hat; ein Modul, das die Konfiguration importiert, wird nicht beobachtet. `--allow-spend` wird nur einmal gelesen, eine Änderung kann die kostenpflichtigen Tools also verbergen, sie ohne den Schalter aber nie listen. Ändert sich die Tool-Liste, sendet der Server `notifications/tools/list_changed`.

### Secrets werden geschwärzt

Jedes Ergebnis und jede Log-Zeile wird wie in Studio geschwärzt: Ein Wert, der wie ein API-Schlüssel aussieht, oder der Wert einer konfigurierten Schlüsselvariable wird zu `[REDACTED]`; die Glossar-Tools nennen geschwärzte Begriffe.

### Geschwärzte Werte [#redacted-values]

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Mit `--redact-values`, oder mit `VERBATRA_MCP_REDACT_VALUES` auf einem Wert, den `VERBATRA_MCP_ALLOW_SPEND` akzeptiert, ersetzen die Ergebnisse Quelltexte, Übersetzungen, Beschreibungen und Glossarbegriffe durch eine Markierung, `[redacted length=12 hash=3f9a0c1d2e4b5a6c]`, und lassen Namen von Reviewern und Autoren weg; gleiche Werte teilen sich einen Hash, bis der Server stoppt. Fehler, die Werte tragen können, behalten Code und nächsten Schritt; ihre Meldung wird zur Markierung. Key-Namen, Zahlen, Herkünfte, Integritätsurteile, Commit-Betreffs und Pfade bleiben. `review.approve` und `review.reject` nehmen nur den Hash der Markierung, als `expectedHash`; `glossary.write` antwortet mit Zahlen; `locale.values` lehnt `query` ab und `key.context` lehnt `draft` ab. Kostenpflichtige Tools brauchen weiter `--allow-spend`; ein Provider bekommt weiter den Text. Einen Agenten, der gezielt sondiert, stoppt das nicht, etwa über Glossar-Schreibvorgänge oder die Glossartreffer von `key.context`.

### stdout und stderr

<AvailableFrom version="0.12.0" />

stdout trägt nur MCP-Protokollnachrichten; jede Log-Zeile und jede Diagnose geht auf stderr. Sobald er verbunden ist, schreibt `verbatra mcp` eine Bereitschaftszeile und eine weitere beim Stoppen:

```text output
verbatra MCP server running on stdio (project ., spend tools off)
verbatra MCP server stopped (client closed stdin)
```

Startest du ihn von Hand im Terminal, sagt er, dass ein Client ihn starten soll. `verbatra mcp --quiet` lässt diese Zeilen weg, aber nicht den Grund für eine fehlende Konfiguration.

### Installation

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`@verbatra/mcp` ist ein eigenes Paket, das die CLI bei Bedarf lädt. Fehlt es, endet `verbatra mcp` mit `2` und:

```text output
Verbatra's MCP server requires @verbatra/mcp. Run it without the CLI with: npx -y @verbatra/mcp, or install it alongside the CLI with: npm install --save-dev @verbatra/mcp
```

Jedes Release steht außerdem in der [offiziellen MCP Registry](https://registry.modelcontextprotocol.io) als `io.github.verbatra/verbatra`.

## Beispiele

```bash
# start the MCP server with only local, non-spending tools
verbatra mcp

# also advertise the provider-calling tools
verbatra mcp --allow-spend

# resolve a project outside the current directory
verbatra mcp --cwd /path/to/project --config verbatra.config.ts

# run the standalone server without the CLI
npx -y @verbatra/mcp --cwd /path/to/project
```

## Exit-Codes

| Code | Bedeutung |
| --- | --- |
| `0` | sauber gestoppt durch einen einzelnen Interrupt, oder weil der Client stdin geschlossen hat |
| `1` | das Schließen des Servers ist beim Herunterfahren fehlgeschlagen |
| `2` | konnte nicht starten: eine fehlende `--config`-Datei, ein fehlendes oder, mit `--redact-values`, zu altes `@verbatra/mcp`, oder ein Nutzungsfehler |
| `130` | durch einen zweiten Interrupt beim Herunterfahren hart gestoppt |

Beim Stoppen gibt der Server jede Locale-Sperre frei. `verbatra-mcp` endet bei einem Startfehler mit `1` und, ab 0.3.0, mit `143`, wenn es nach SIGTERM hart gestoppt wird. Siehe [den Exit-Code-Vertrag](/docs/cli/output#exit-codes).
