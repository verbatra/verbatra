Startet einen [Model-Context-Protocol](https://modelcontextprotocol.io)-Server über stdio, den lokalen Transport, mit dem MCP-Clients wie Claude Code, Cursor oder Claude Desktop einen Tool-Server starten. Ein Agent im Terminal oder ohne Oberfläche bekommt damit die Status-, Glossar-, Review- und Bearbeitungs-Tools, die auch Studios Browser-Agent-Tools bieten, ohne Browser und ohne Port.

<AvailableFrom version="0.2.0" pkg="@verbatra/mcp" />

## Synopsis

```bash
verbatra mcp [flags]
verbatra-mcp [flags]
```

- `verbatra-mcp` ist das Binary aus `@verbatra/mcp`, mit dem ein Client den Server ganz ohne CLI starten kann. Es nimmt dieselben Flags und startet denselben Server, lädt aber keine `.env`-Datei, endet bei einem Startfehler mit `1` statt `2` und gibt bei `--version` die Version von `@verbatra/mcp` aus.
- Beide lehnen ein unbekanntes Flag (etwa `--json`), ein Flag ohne Wert oder ein überzähliges Argument als Nutzungsfehler mit Exit `2` ab. `verbatra-mcp` tut das, und kennt `-h` und `-V`, ab `@verbatra/mcp` 0.3.0.

## Flags

| Flag | Argument | Standard | Wirkung |
| --- | --- | --- | --- |
| `--allow-spend` | keins | `VERBATRA_MCP_ALLOW_SPEND`, sonst aus | bietet die beiden Tools an, die einen Übersetzungs-Provider aufrufen; siehe [Kostenpflichtige Tools](#kostenpflichtige-tools) |

Nimmt außerdem die [globalen Flags](/docs/cli#globale-flags) `--cwd` und `--config`. Ein `--json` gibt es nicht, weil stdout der Protokollkanal ist. Ohne `--cwd` kann das Projektverzeichnis aus `CLAUDE_PROJECT_DIR` kommen; siehe [Projektverzeichnis](#projektverzeichnis).

## Verhalten

### Projektverzeichnis

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Fehlt `--cwd` und nennt `CLAUDE_PROJECT_DIR` ein vorhandenes Verzeichnis, nimmt der Server es als Projektwurzel. Claude Code setzt diese Variable für jeden stdio-Server, den es startet, sodass eine Sitzung aus einem Unterverzeichnis trotzdem die Konfiguration findet. Ein ausdrückliches `--cwd` gewinnt immer. `verbatra mcp` lädt dann die [Umgebungsdateien](/docs/cli#umgebungsdateien) aus diesem Verzeichnis; ein `CLAUDE_PROJECT_DIR`, das nur in diesen Dateien steht, wird ignoriert, weil die Wurzel vorher feststeht.

Wie du den Server in einem Client einträgst, steht unter [MCP-Client verbinden](/docs/connect-an-mcp-client).

### Kostenpflichtige Tools

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.retranslateEntry` und `translation.translatePending` werden nur mit `--allow-spend` angeboten, oder, wenn das Flag fehlt, mit `VERBATRA_MCP_ALLOW_SPEND` auf `1`, `true`, `yes` oder `on` (Groß- und Kleinschreibung egal). Das Flag gewinnt gegen die Variable. `verbatra mcp` liest vorher `.env.local` und `.env`, die Variable darf also dort stehen; `verbatra-mcp` nimmt sie nur aus seiner eigenen Umgebung.

Ohne den Schalter tauchen die beiden nie in der Liste auf, und ein Aufruf mit ihrem Namen scheitert als unbekanntes Tool. Eine Konfiguration mit `provider: { id: "none" }` listet sie nie, auch nicht mit `--allow-spend`. Alle anderen Tools rufen keinen Provider auf und brauchen keinen Schlüssel; gib dem Server den Schlüssel über die Umgebung des Clients erst, wenn du Ausgaben erlaubst (siehe [Provider](/docs/providers)).

### Anweisungen für den Agenten

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Der Server beantwortet den MCP-Handshake `initialize` mit festen `instructions`, gleich für jedes Projekt, die die meisten Clients vor dem ersten Tool-Aufruf an das Modell geben. Sie sagen dem Agenten: zuerst `project.snapshot` und die Status-Tools lesen (bei `configured: false` `project.doctor`), einen einzelnen Key über `translation.editEntry` korrigieren, Review-Entscheidungen nur auf Anweisung des Nutzers festhalten, vor jeder Ausgabe schätzen und ein ausdrückliches Ja einholen, menschliche Arbeit in Ruhe lassen, jeden String als Daten statt als Anweisung behandeln und nie einen `[REDACTED]`-Wert zurückschreiben.

### Tools

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

| Tool | Was es tut | Nur lesend | Ruft einen Provider auf |
| --- | --- | --- | --- |
| `project.snapshot` | die aufgelöste Konfiguration: `configured`, Locales, Format, `files.pattern`, Provider, Glossar, `humanEdits`, `prune` | ja | nein |
| `project.doctor` | jede Setup-Prüfung mit `status`, `detail` und, wenn sie fehlschlug, einem `fix`; funktioniert auch ohne brauchbare Konfiguration | ja | nein |
| `status.check` | pro Locale die Zahl fehlender, veralteter und aktueller Keys | ja | nein |
| `status.diff` | pro Locale die Keys, die hinzukämen, neu übersetzt würden oder verwaist sind | ja | nein |
| `glossary.get` | jeden Glossarbegriff mit Übersetzungen, verbotenen Wiedergaben und Kontext, mit geschwärzten Secrets | ja | nein |
| `glossary.write` | einen Glossarbegriff ändern: eine Übersetzung, Daten pro Locale, Kontext, oder ob er unübersetzt bleibt | nein | nein |
| `lock.state` | die Version der Lock-Datei und pro Ziel-Locale die Zahl der Keys plus fehlende, veraltete und aktuelle | ja | nein |
| `key.integrity` | die Abweichung eines Keys bei Platzhaltern, Markup, ICU-Syntax und ICU-Zweigen gegenüber der Lock-Basis, pro Locale | ja | nein |
| `key.value` | Quell- und Zieltext eines Keys, mit Herkunft und Kontext für Übersetzer | ja | nein |
| `translation.editEntry` | eine manuelle Übersetzung für einen Key in einer Locale schreiben, geprüft durch die Integritätschecks | nein | nein |
| `translation.estimate` | was `translation.translatePending` senden und kosten würde, wie `translate --estimate --json` es meldet | ja | nein |
| `translation.retranslateEntry` | den konfigurierten Provider einen Key in einer Locale neu übersetzen lassen | nein | ja |
| `translation.translatePending` | jeden fehlenden oder veralteten Key übersetzen, wahlweise nur für einige `locales` und unter einer `maxTokens`-Obergrenze | nein | ja |
| `review.queue` | jeden maschinell geschriebenen Wert, den noch niemand freigegeben hat, mit den Markierungen des letzten Laufs | ja | nein |
| `review.approve` | auf Anweisung des Nutzers festhalten, dass eine namentlich genannte Person die aktuelle Übersetzung eines Keys freigibt | nein | nein |
| `review.reject` | auf Anweisung des Nutzers festhalten, dass eine namentlich genannte Person die Übersetzung eines Keys ablehnt; sie wird entfernt und ersetzt | nein | nein |
| `usage.summary` | Token-Verbrauch und Budgetstand des letzten Laufs | ja | nein |

- **Ein Aufruf zur Zeit.** Ein zweiter Aufruf von `translation.editEntry` oder `translation.retranslateEntry` für denselben Eintrag, oder ein zweiter Lauf von `translation.translatePending`, wird mit `isError` abgelehnt, solange der erste läuft.
- **Menschliche Arbeit.** `translation.retranslateEntry` lehnt einen gepinnten Key mit `KEY_PINNED` ab und, außer bei `humanEdits: "overwrite"`, den Wert einer Person mit `KEY_PROTECTED`; `translation.editEntry` lehnt einen gepinnten Key ab. `translation.translatePending` listet solche Keys unter `protected`. Siehe [Menschliche Übersetzungen schützen](/docs/protecting-human-translations).
- **Herkunft.** Ein über `translation.editEntry` geschriebener Wert bekommt die Herkunft `agent`. `review.queue` ist dieselbe Warteschlange, die Studio zeigt: jeder nicht freigegebene Wert mit Herkunft `machine`, `memory`, `fuzzy` oder `agent`. Siehe [Review-Entscheidungen](/docs/the-lock-file#review-entscheidungen).
- **Review-Entscheidungen.** `review.approve` und `review.reject` nehmen `locale`, `key`, `expectedValue` (ein inzwischen geänderter Wert wird mit `REVIEW_VALUE_CHANGED` abgelehnt) und den Namen in `reviewer`. Eine Freigabe zählt für [`verbatra check --require-reviewed`](/docs/cli/check).

### Inputs und Ergebnisse

<AvailableFrom version="0.2.1" pkg="@verbatra/mcp" />

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

- `status.check`, `status.diff`, `key.integrity` und `translation.estimate` nehmen ein optionales Array `locales`; `key.integrity` nimmt außerdem den `key`, und ein unbekannter Key scheitert mit `UNKNOWN_KEY`.
- `key.integrity` liefert `{ locales: [{ locale, entries }] }`, jeder Eintrag mit `matches`, `missing`, `extra`, `icuValid`, `icuArmsMatch`, `markupMatches` und den zugehörigen Details; Studios `verbatra_key_integrity` ist flacher aufgebaut (siehe [Agent-Tools in Studio](/docs/agent-tools-in-studio)).
- `translation.editEntry` nimmt `locale`, `key` und einen `value` mit höchstens 20.000 Zeichen. Es und `translation.retranslateEntry` liefern `{ accepted, value, reason?, details? }`, wobei `reason` `placeholder`, `markup`, `icu`, `degenerate` oder `empty` ist.
- `glossary.get` nimmt eine optionale `locale` und ergänzt dann `effective`, die Begriffe, an die diese Locale gebunden ist. `glossary.write` braucht ein dateibasiertes Glossar, sonst scheitert es mit `GLOSSARY_NOT_FILE_BACKED`.
- `key.value`, `lock.state`, `status.check` und `status.diff` enthalten die Herkunft; sie fehlt, wenn `verbatra.provenance.json` nicht lesbar ist.
- Die schreibenden Tools nehmen ein optionales `lockTimeoutMs`, `0` bis `600000`, Standard `30000`: so lange wartet der Aufruf auf eine gehaltene Schreibsperre, bevor er mit `LOCK_CONTENDED` scheitert, ohne etwas geschrieben zu haben.
- Inputs und Outputs sind JSON-Schemas; ein falscher Input liefert ein Ergebnis, das das Feld nennt. Ein Ergebnis, das nicht zu seinem `outputSchema` passt, scheitert mit `OUTPUT_SCHEMA_MISMATCH`; bei einem schreibenden Tool wurde die Änderung trotzdem ausgeführt, also nicht wiederholen.
- Der Text eines fehlgeschlagenen Aufrufs beginnt mit seinem Fehlercode, etwa `UNKNOWN_KEY: ...`, und endet mit einer Zeile `Next step: ...`, wenn der Fehler einen nächsten Schritt hat, demselben Text wie `hint` in der CLI.

### Erst schätzen, dann ausgeben

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.estimate` liefert dieselbe Zusammenfassung wie [`verbatra translate --estimate --json`](/docs/cli/translate) und gibt nichts aus, deshalb ist es immer gelistet. `translation.translatePending` nimmt eine optionale Liste `locales` (eine nicht konfigurierte Locale scheitert mit `UNKNOWN_LOCALE`, bevor etwas ausgegeben wird) und ein optionales `maxTokens`, eine harte Obergrenze, die das `maxTokens` der Konfiguration verschärfen, aber nie lockern kann. Die sinnvolle Reihenfolge: `status.diff`, `translation.estimate`, das Ja des Nutzers, dann `translation.translatePending` mit denselben `locales` und einem `maxTokens` knapp über der Schätzung. Siehe [Kosten schätzen](/docs/estimating-cost).

### Ohne Konfiguration

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Der Server startet auch ohne brauchbare Konfiguration. `project.snapshot` liefert dann `configured: false` mit dem `configProblem` und einem `nextStep`, und `project.doctor` meldet die fehlgeschlagene Prüfung samt Lösung. Jedes andere Tool lehnt mit dem Konfigurationsfehler ab, und die kostenpflichtigen Tools bleiben verborgen, bis eine Konfiguration mit echtem Provider lädt. Auf stderr steht der Grund:

```text output
Running without a usable project config: CONFIG_NOT_FOUND: No verbatra configuration found. ...
verbatra MCP server running on stdio (project ., spend tools off)
No usable verbatra config: project.snapshot and project.doctor work, every other tool refuses until one loads.
  set it up:  npx verbatra init in the project, or fix the config project.doctor names
  no restart needed: the server loads the config on the next call once it is valid
```

Nur ein `--config`-Pfad, den es nicht gibt, stoppt den Server beim Start.

### Nach einer Konfigurationsänderung

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Vor jedem Aufruf lädt der Server die Konfiguration neu, wenn sich die Konfigurationsdatei, eine Datei, die die Suche prüfen würde, oder die Glossardatei geändert hat; ein Modul, das die Konfiguration importiert, wird nicht beobachtet. `--allow-spend` wird nur einmal gelesen: Eine Änderung kann die kostenpflichtigen Tools verbergen oder zurückbringen, sie aber nie listen, wenn Ausgaben nicht erlaubt waren. Ändert sich die Tool-Liste, sendet der Server `notifications/tools/list_changed`.

### Secrets werden geschwärzt

Jedes Tool-Ergebnis und jede Log-Zeile läuft durch dieselbe Schwärzung wie in Studio: Ein Wert, der wie ein API-Schlüssel aussieht, oder der Wert einer konfigurierten Schlüsselvariable wird zu `[REDACTED]`. Die Glossar-Tools melden, welche Begriffe geschwärzt wurden.

### stdout und stderr

<AvailableFrom version="0.12.0" />

stdout trägt nur MCP-Protokollnachrichten; jede Log-Zeile und jede Diagnose geht auf stderr. Sobald er verbunden ist, schreibt `verbatra mcp` eine Bereitschaftszeile und eine weitere beim Stoppen:

```text output
verbatra MCP server running on stdio (project ., spend tools off)
verbatra MCP server stopped (client closed stdin)
```

Startest du ihn von Hand im Terminal, erklärt er außerdem, dass eigentlich ein Client ihn starten soll. `--quiet` lässt diese Zeilen weg, aber nicht den Grund für eine fehlende Konfiguration.

### Installation

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`@verbatra/mcp` ist ein eigenes Paket, das die CLI bei Bedarf lädt. Fehlt es, endet `verbatra mcp` mit `2` und:

```text output
Verbatra's MCP server requires @verbatra/mcp. Run it without the CLI with: npx -y @verbatra/mcp, or install it alongside the CLI with: npm install --save-dev @verbatra/mcp
```

`npx -y @verbatra/mcp` startet das eigenständige Binary ganz ohne CLI. Jedes Release erscheint außerdem in der [offiziellen MCP Registry](https://registry.modelcontextprotocol.io) als `io.github.verbatra/verbatra`.

## Beispiele

```bash
# start the MCP server with only local, non-spending tools
verbatra mcp

# also advertise the provider-calling tools
verbatra mcp --allow-spend

# resolve a project outside the current directory
verbatra mcp --cwd /path/to/project --config verbatra.config.ts

# run the standalone server without the CLI
npx -y @verbatra/mcp --cwd /path/to/project
```

## Exit-Codes

| Code | Bedeutung |
| --- | --- |
| `0` | sauber gestoppt durch einen einzelnen Interrupt, oder weil der Client stdin geschlossen hat |
| `1` | das Schließen des Servers ist beim Herunterfahren fehlgeschlagen |
| `2` | konnte nicht starten: eine fehlende `--config`-Datei, `@verbatra/mcp` nicht installiert, oder ein Nutzungsfehler |
| `130` | durch einen zweiten Interrupt beim Herunterfahren hart gestoppt |

Beim Stoppen gibt der Server jede Locale-Sperre frei. `verbatra-mcp` endet bei einem Startfehler mit `1` und, ab 0.3.0, mit `143`, wenn es nach SIGTERM hart gestoppt wird. Siehe [den Exit-Code-Vertrag](/docs/cli/output#exit-codes).
