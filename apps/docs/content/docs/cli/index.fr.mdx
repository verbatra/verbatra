`@verbatra/cli` fournit le binaire `verbatra`, une surcouche légère de [`@verbatra/sdk`](/docs/sdk). Ces commandes font le travail :

| Commande | Rôle |
| --- | --- |
| [`init`](/docs/cli/init) | crée une config verbatra et un `.env.example` pour ce projet |
| [`extract`](/docs/cli/extract) | analyse le code de ton application à la recherche des appels de traduction et ajoute les nouvelles clés au fichier de la locale source |
| [`translate`](/docs/cli/translate) | traduit chaque locale cible une fois, puis termine |
| [`watch`](/docs/cli/watch) | retraduit à chaque changement de la source jusqu'à interruption |
| [`check`](/docs/cli/check) | signale les clés manquantes ou obsolètes par locale, en lecture seule |
| [`diff`](/docs/cli/diff) | liste les clés exactes qui seraient ajoutées, retraduites ou orphelines par locale, en lecture seule |
| [`report`](/docs/cli/report) | affiche un rapport en lecture seule : `report provenance` liste les traductions qu'une machine a écrites et celles qu'une personne a relues |
| [`doctor`](/docs/cli/doctor) | valide la configuration du projet et signale tous les problèmes d'un coup, sans appeler de fournisseur |
| [`pseudo`](/docs/cli/pseudo) | génère une pseudo-locale à partir des chaînes source, sans appeler de fournisseur |
| [`types`](/docs/cli/types) | génère les déclarations TypeScript pour les clés de ton catalogue et les arguments de leurs messages, sans appeler de fournisseur |
| [`export`](/docs/cli/export) | exporte les chaînes non traduites pour un traducteur humain, en classeur Excel, en un fichier CSV ou TSV par locale ou en un fichier XLIFF par locale pour un outil de TAO |
| [`import`](/docs/cli/import) | réimporte un classeur rempli ou un fichier délimité dans les fichiers de locale |
| [`tmx`](/docs/cli/tmx) | importe une mémoire de traduction TMX venant d'un autre outil dans la mémoire de ce projet, ou exporte la mémoire de ce projet dans un fichier TMX |
| [`studio`](/docs/cli/studio) | démarre Verbatra Studio, le tableau de bord local de traduction |
| [`mcp`](/docs/cli/mcp) | démarre un serveur MCP en stdio qui expose les outils de verbatra à un client MCP |

## Installation et invocation

Installe `@verbatra/cli` comme dépendance de développement, puis lance le binaire via ton gestionnaire de paquets :

| Gestionnaire de paquets | Installation | Lancement |
| --- | --- | --- |
| npm | `npm install --save-dev @verbatra/cli` | `npx verbatra <command>` |
| pnpm | `pnpm add --save-dev @verbatra/cli` | `pnpm verbatra <command>` (ou `pnpm exec verbatra <command>`) |
| yarn | `yarn add --dev @verbatra/cli` | `yarn verbatra <command>` |
| bun | `bun add --dev @verbatra/cli` | `bun run verbatra <command>` |

Il te faut Node.js `>=22.14.0`.

Tu veux essayer une commande avant d'installer ? `npx @verbatra/cli <command>` (npm) ou `pnpm dlx @verbatra/cli <command>` (pnpm) fonctionnent tous les deux sans installation locale préalable.

## Conventions partagées

- `--cwd <path>` résout la config et les fichiers de locale depuis ce répertoire au lieu du répertoire courant. Toutes les commandes l'acceptent.
- `--config <path>` charge ce fichier de config au lieu d'en chercher un. Toutes les commandes sauf `init` l'acceptent ; l'ordre de recherche est décrit dans [Le fichier de configuration](/docs/config-file).
- `--json` affiche une [enveloppe](/docs/ci-and-exit-codes#sortie-json) lisible par machine sur stdout, une ligne par enregistrement, et garde stdout propre pour le piping.
  - Branche-toi sur son champ `ok` : un succès porte les données de la commande sous `result`, et une exécution échouée porte le même code d'erreur stable que nomme la ligne stderr. La ligne d'erreur lisible par un humain va sur stderr dans les deux cas.
  - `extract`, `translate`, `watch`, `check`, `diff`, `report`, `doctor`, `pseudo`, `types`, `export`, `import`, `tmx` et `init` le prennent en charge ; `studio` et `mcp` non.
  - `mcp` n'écrit jamais rien sur stdout, puisque stdout est le canal du protocole MCP ; voir [`verbatra mcp`](/docs/cli/mcp).
- `--help` et `--version` affichent leur sortie et terminent avec `0`. Une commande ou une option inconnue termine avec `2`.

## Sortie dans le terminal

<AvailableFrom version="0.12.0" />

Les résultats vont sur stdout. La progression, les avis, les suggestions, les avertissements et les erreurs vont sur stderr, et verbatra les adapte selon la destination de stderr :

- Dans un terminal interactif, les libellés fixes comme `error`, `[ok]` et `next:` sont colorés, et une étape qui dure plus de 300 ms affiche un spinner ASCII (`| / - \`).
- Quand stderr est redirigé ou envoyé dans un pipe, que `CI` a une valeur autre que `0` ou `false`, ou que `TERM` vaut `dumb`, la sortie se compose de lignes simples, uniquement ajoutées, sans couleur ni animation.
- `--json` n'ajoute jamais de couleur, d'animation ni de nouvelles lignes : stdout et stderr restent exactement comme décrit dans [Sortie JSON](/docs/ci-and-exit-codes#sortie-json).

| Flag ou variable | Effet |
| --- | --- |
| `-q`, `--quiet` | n'affiche que les résultats, les avertissements et les erreurs : supprime les lignes de progression, les suggestions `next:` et les lignes informatives sur stderr, tandis que le résumé du résultat, avis compris, reste. Il fonctionne avant ou après le nom de la commande |
| `--no-color` | ne colore jamais la sortie |
| `NO_COLOR`, `NODE_DISABLE_COLORS`, `VERBATRA_NO_COLOR` | toute valeur non vide désactive la couleur ; `VERBATRA_NO_COLOR` l'emporte aussi sur `FORCE_COLOR` |
| `FORCE_COLOR` | `1`, `2`, `3`, `true` ou une valeur vide active la couleur même quand stderr n'est pas un terminal, et `0` la désactive ; `--no-color` et `VERBATRA_NO_COLOR` restent prioritaires |
| `VERBATRA_NO_SPINNER` | toute valeur non vide remplace le spinner par des lignes statiques `label... done (1.2s)`, pour les lecteurs d'écran et les enregistrements de terminal |

Les mots d'état sont en ASCII simple (`[ok]`, `[warn]`, `[fail]`, `[skip]`), pour que la sortie se lise de la même façon dans tout terminal et tout journal. Chaque ligne passe par le même masquage des clés que le reste de la sortie, et seuls les libellés fixes sont colorés, jamais une clé, un chemin ni un message.

## Fichiers d'environnement

`translate`, `watch`, `doctor`, `studio` et `mcp` chargent `.env.local` puis `.env` depuis le répertoire de travail avant de s'exécuter. `doctor --literals` fait exception : il ne lit aucune clé d'API, donc il ne charge aucun des deux fichiers. Une variable déjà définie dans ton environnement réel l'emporte toujours. Les clés d'API sont lues uniquement depuis l'environnement, jamais depuis le fichier de config ni une option : voir [Fournisseurs](/docs/providers). Les commandes en lecture seule (`check`, `diff`, `report`), les commandes de remise (`export`, `import`), `extract`, `pseudo`, `types` et `tmx` n'appellent jamais de fournisseur et ne chargent aucun fichier `.env`.

## Codes de sortie

Le code de sortie est le contrat sur lequel une étape CI ou un script se branche :

| Code | Signification |
| --- | --- |
| `0` | succès (aussi `--help` et `--version`) |
| `1` | `translate` ou `import` a terminé mais certaines locales ont échoué ou sont ressorties partielles, `check` a trouvé une locale désynchronisée, `diff` a trouvé des changements en attente (ou, avec `--unused`, une analyse complète a trouvé une clé source inutilisée), `report provenance` n'a pas pu lire `verbatra.provenance.json`, `doctor` a trouvé un problème de configuration (comme une locale que le fournisseur ne prend pas en charge) ou, avec `--literals`, un littéral non traduit, ou `types --check` a trouvé la déclaration commitée obsolète |
| `2` | impossible de s'exécuter : une erreur globale (config, source, fournisseur, verrou) ou une erreur d'utilisation |
| `3` | `translate` dans un projet [100 % humain](/docs/human-only-workflow) (`provider: { id: "none" }`) s'est terminé proprement, mais a laissé des clés pour une traduction humaine |
| `130` | `translate` ou `import` a été interrompu avec Ctrl-C (SIGINT) après avoir libéré ses verrous d'écriture, ou `watch`, `studio` ou `mcp` a été arrêté de force par une seconde interruption |
| `143` | `translate` ou `import` a été arrêté avec SIGTERM après avoir libéré ses verrous d'écriture |

Chaque page de commande détaille comment ces codes s'y appliquent. Voir [CI et codes de sortie](/docs/ci-and-exit-codes) pour les brancher dans un pipeline.
