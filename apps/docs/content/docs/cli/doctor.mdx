title: verbatra doctor
description: Validate the project setup without calling a provider or reading an API key.

<AvailableFrom version="0.9.0" />

Answer one question before you run anything else: is this project set up correctly? `doctor` validates the config, the format adapter, the provider, the API key variable, the network policy, the source locale file, and whether the provider supports every configured locale, then reports every problem it found at once. It spends nothing: no provider is constructed, no network request is made, no file is written, and no API key value is ever read. The one exception is `--live`, which sends the provider's key with a single request for its language list.

Reach for it on a fresh checkout, right after [`verbatra init`](/docs/cli/init), or whenever another command failed and you want the whole list rather than the first error. [`verbatra check`](/docs/cli/check) is the cheapest validation once a project already works, but it reads the locale files and stops at the first whole-run error, so it cannot tell you what is wrong with a project that has no source file yet.

## Synopsis

```bash
verbatra doctor [flags]
```

## Flags

| Flag | Argument | Default | Effect |
| --- | --- | --- | --- |
| `--cwd` | `<path>` | current directory | resolve config and locale files from this directory |
| `--config` | `<path>` | search for one | load this config file instead of searching for one |
| `--literals` | none | off | scan the source roots of the [`extract` block](/docs/config-file#extract) for hardcoded user-facing strings instead of checking the setup (see [Untranslated literals](#untranslated-literals)) |
| `--locales` | none | off | after the checks, list for every target locale the code it is sent as, whether the provider supports it, and whether it can apply a glossary and a formality setting (see [Locale support](#locale-support)) |
| `--live` | none | off | fetch the provider's current language list before the Locale support check, which uses no translation quota; implies `--locales` (see [Locale support](#locale-support)) |
| `--json` | none | off | print one [JSON envelope](/docs/ci-and-exit-codes#json-output) on stdout carrying the report under `result`; the human-readable error line still goes to stderr |

## What it checks

A setup run reports ten checks, in the order below. Seven of them can fail; Plural rules, Locale codes, and Locale state are informational and never do.

| Check | Passes when |
| --- | --- |
| Configuration | a config file was found and passes validation |
| Format adapter | the configured `format` resolves to a file adapter |
| Provider | the configured `provider.id` resolves to a provider factory |
| API key environment variable | the variable that provider reads its key from is set |
| Network policy | the effective [network policy](/docs/network-policy) permits the host the configured provider connects to, and any proxy it would use; the detail names the policy, where it comes from, and the host |
| Source locale file | the source locale file exists at its resolved path, is a regular file, and parses under the configured format |
| Plural rules | always (informational): names the ICU and CLDR versions verbatra reads plural categories from, and any target locale ICU has no plural rules for |
| Locale codes | always (informational): names every configured locale code that is valid but not in canonical BCP 47 form, with the canonical form to use |
| Locale state | always (informational): names every locale the lock file, the translation memory, or the provenance file holds state for that your config does not list, and says whether the next `translate` run carries it over |
| Locale support | the provider supports the source locale and every target locale; the detail counts supported and unverified locales, names the unsupported ones, and counts warnings (see [Locale support](#locale-support)) |

<AvailableFrom version="0.12.0" />

The Plural rules check is informational and never fails: a target locale it names still translates, and its plural checks assume `one` and `other` for cardinal keys and `other` for ordinal keys. Ordinal keys (`<key>_ordinal_<category>`) are always checked against the CLDR ordinal rules, so French ordinals need only `one` and `other`.

<AvailableFrom version="0.12.0" />

The Locale codes check is informational and never fails either. A code such as `zh-hant-tw`, `en-us`, or the deprecated `iw`, `in`, or `tl` is valid, so it loads and translates as written, and this check suggests `zh-Hant-TW`, `en-US`, `he`, `id`, or `fil` instead. File names follow the code in your config, so nothing is renamed until you change it yourself. A code that is not valid BCP 47 at all, such as `en_US`, never reaches this check: it fails the Configuration check. See [Locale codes](/docs/config-file#locale-codes).

<AvailableFrom version="0.12.0" />

The Locale state check is informational and never fails either. It reads `verbatra.lock.json`, `verbatra.cache.json`, and `verbatra.provenance.json` and names every locale they hold state for that your config does not list, such as `pt_BR` left behind after you respelled it `pt-BR`. For each one it says whether the next `translate` run carries it over to the configured spelling (see [A respelled locale code](/docs/the-lock-file#a-respelled-locale-code)), whether the configured code already has state of its own, whether two spellings compete for it, or whether it matches no configured locale at all. Remove the state of a locale you no longer translate, or respell the configured locale to match it.

Every check runs even when an earlier one failed, so one run reports every independent problem. The only exception is the config itself: when it cannot be loaded, the nine checks that need it are skipped instead of reaching a verdict. Such a check prints as `[skip]` in the human report and carries `"status": "skipped"` in the `--json` envelope.

Five details are worth knowing:

- The API key is checked **by name only**. `doctor` asks whether the variable is set, never what it holds. The value is not read, not printed, and never sent anywhere, unless you pass `--live`, which sends it to the provider's language list endpoint and nowhere else. See [Providers](/docs/providers) for which variable each provider uses.
- The `openai-compatible` provider is the exception. It falls back to a placeholder key, so a missing variable is fine. It only fails when your config names its own variable through `provider.options.apiKeyEnvVar` and that variable is unset.
- With [`provider: { id: "none" }`](/docs/human-only-workflow), the Provider check passes and reports that machine translation is disabled by policy, the API key check passes without looking at any variable, the Network policy check passes because no provider is ever called, and the Locale support check is skipped as not applicable.
- A missing **target** locale file is not a problem: [`verbatra translate`](/docs/cli/translate) creates it. Target files are not checked at all.
- The **source** locale file is read and parsed, not merely probed for. A directory standing in for it, an empty file, and malformed content all fail this check with the same message [`verbatra check`](/docs/cli/check) would give, because those are exactly the cases that make every other command fail. When the configured `format` resolves to no adapter there is nothing to parse with, so the check falls back to existence alone and says so.

Like [`verbatra translate`](/docs/cli/translate), `doctor` loads `.env.local` and then `.env` from the working directory before it looks at the environment, so a key kept in a dotenv file counts as set. With `--literals` it loads neither file.

## Locale support

<AvailableFrom version="0.12.0" />

The Locale support check asks, before anything is spent, whether the configured provider can translate each configured locale. DeepL and Google Cloud Translation are judged against a dated language table verbatra ships for each, taken from the provider's documentation; an LLM provider accepts any locale. The check fails on a locale the provider does not support, which is exactly the locale [`verbatra translate`](/docs/cli/translate) would refuse with `LOCALE_UNSUPPORTED_BY_PROVIDER`, and passes with warnings otherwise. [Language support](/docs/language-support#checking-support-before-a-run) explains the three verdicts and lists the tables.

Add `--locales` to see the verdict per locale, after the checks:

```text
verbatra doctor
  ...
  [fail] Locale support: Provider "deepl", language table of 2026-09-28 (static): 2 of 3 target locales supported, 0 unverified; unsupported: "chr". 1 warning.
  locale support (deepl, language table of 2026-09-28, static)
    en  sent as EN  source, supported
    de  sent as DE  supported  glossary: yes  formality: yes
    sv  sent as SV  supported  glossary: yes  formality: no
      warning [FORMALITY_UNSUPPORTED_BY_PROVIDER] Provider "deepl" has no formality control for "sv", so the configured formal tone is not applied and the provider's default register is used.
    chr  sent as CHR  unsupported  glossary: no  formality: no
1 problem found (run verbatra doctor again after fixing it)
```

Each line names the configured locale, the code the provider receives (after [`localeMap`](/docs/providers#locale-codes-sent-to-the-provider), marked `(localeMap)` when an entry set it), the verdict, and whether the provider can apply a glossary and a `formal` or `informal` tone for that language. A warning is advisory: a glossary or tone the provider cannot apply, a code that is only partly listed, or a language outside the list LLM providers are known to translate well.

`--live` fetches the provider's current language list first, from DeepL's `/v3/languages` or Cloud Translation's `languages` endpoint, and judges against it instead. It is the one flag that makes `doctor` send a request, and that request uses no translation quota. It is sent only when the provider's API key variable is set and the [network policy](/docs/network-policy) permits the provider's host; otherwise, or when the request fails, the report uses the shipped table and a `live language list` line says why. An LLM provider has no list to fetch. `--locales` and `--live` cannot be combined with `--literals`, which replaces the setup checks; doing so is a usage error (`INVALID_OPTION`, exit `2`).

With `--json`, the report travels in the envelope under `result.locales`, whether or not you pass `--locales`:

```ts
interface LocaleCapabilityReport {
  provider: string;                  // the configured provider id
  coverage: "listed" | "open";       // "open" for an LLM provider, which accepts any locale
  tableVersion: string;              // the table's date (YYYY-MM-DD), or the well-tested list's
  tableOrigin: "static" | "live";    // "live" only when --live fetched the list
  live?: { status: "refreshed" | "skipped" | "failed"; detail: string }; // only with --live
  source: {
    locale: string;
    providerCode: string;            // the code the provider receives
    mapped: boolean;                 // true when localeMap set providerCode
    support: "supported" | "unverified" | "unsupported";
    warnings: { code: string; message: string }[];
  };
  locales: {
    locale: string;
    providerCode: string;
    mapped: boolean;
    support: "supported" | "unverified" | "unsupported";
    glossary: boolean;               // the provider can apply a glossary for this language pair
    formality: boolean;              // the provider can apply a formal or informal tone
    warnings: { code: string; message: string }[];
  }[];
}
```

`result.locales` is absent when the config could not be loaded, for an unknown provider, and for `provider: { id: "none" }`.

## Untranslated literals

<AvailableFrom version="0.11.0" />

`verbatra doctor --literals` looks for the one i18n bug no other check can see: a user-facing string that never made it into a catalog. It walks the source roots of your [`extract` block](/docs/config-file#extract) and reports every hardcoded string that reads as user-facing text but does not go through a translation call. It reads your source and never writes it, constructs no provider, reads no API key variable, and loads no `.env` file, so it passes in a job that holds no secrets. In this mode only two checks run: the configuration and the literal scan.

Every finding names its file, line, and column. Its text has whitespace collapsed and, in JSX, character references such as `&amp;` decoded, and it is cut to at most 80 characters:

```text
verbatra doctor
  [ok  ] Configuration: Loaded /app/verbatra.config.ts.
  [fail] Untranslated literals: Scanned 42 source files: 2 untranslated literals found (1 suppressed).
    src/components/Header.tsx:12:9  "Welcome back"
    src/pages/settings.tsx:40:22  "Save changes"
    suppressed (directive) src/pages/legal.tsx:8:5  "Acme Inc."
1 problem found (run verbatra doctor again after fixing it)
```

What counts as a finding:

- JSX text, such as `<p>Welcome back</p>`, in `.tsx`, `.jsx`, and `.js` files.
- The value of a user-facing JSX attribute: `alt`, `title`, `placeholder`, `label`, `aria-label`, and the other text-carrying `aria-*` attributes.
- A string anywhere else that reads as prose, meaning two or more words. A single word outside JSX, such as an event name or an option value, is not reported.

What is never reported: a string passed to a recognised translation call (`t(...)`, `$t(...)`, `i18n.t(...)`, or `t` renamed out of `useTranslation`, as in `const { t: translate } = useTranslation()`, from that line to the end of the enclosing block) or rendered inside `<Trans>` or `<Translation>`, an object key, an import specifier, a class name or CSS value, a test id or `data-*` attribute, an attribute that holds ids or a keyword rather than text (such as `aria-describedby`, `aria-labelledby`, `aria-controls`, `rel`, `sandbox`, `allow`, `autoComplete`, `referrerPolicy`, or `crossOrigin`), a URL, a literal in a type position (including one after `as` or `satisfies`; the value before them, as in `"Welcome" as const`, is still checked), a logging message, the message of a constructed error (`new ValidationError(...)`) or of a built-in error called without `new` (`throw Error(...)`), a comparison operand, a template literal carrying an expression, a string with no letters (punctuation, whitespace, a number, an emoji, a symbol), and anything in test, story, declaration, or config files.

Calls that take a query, a format, or a name rather than copy are skipped too: a string passed directly as an argument of `describe` (zod), `query`, `execute`, `prepare`, `format`, or `parse`, a string in the array passed directly to `z.enum`, every string argument of `setItem`, `getItem`, and `removeItem`, and the first argument of `on`, `off`, `once`, `emit`, `addEventListener`, and a member `get` or `set` call such as `cookies().get(...)`. Only the direct arguments are skipped: copy nested deeper in such a call, such as in a callback (`query(() => ({ message: "..." }))`), an object, or JSX, is still reported. A function that only happens to end in `Error`, such as `setError` or `showError`, is not skipped, so the message you pass it is still reported.

To hold one literal back, put `// verbatra-ignore-next-line` above it (in JSX, `{/* verbatra-ignore-next-line */}`), or `// verbatra-ignore-line` at the end of its own line. A next-line directive targets the next line that holds code (blank lines and comment-only lines are skipped) and covers every literal that starts on that line. When a JSX opening tag starts there, it also covers all of that tag's attributes, even when the tag spans several lines. Text and nested elements on later lines are not covered, so give each of them its own directive. For a string that is fine everywhere, such as a brand name, list it under `extract.literals.ignore` in [the config file](/docs/config-file#extract). An entry matches the text as it is reported, with character references decoded, so write `Tom & Jerry`, not `Tom &amp; Jerry`. A held-back literal is still listed as suppressed, with the reason, so nothing disappears silently.

The check fails when it finds a literal, and also when a file could not be scanned. A file the scanner cannot read to the end (an unterminated comment or template literal, or a JSX element that never closes or is closed by the tag of an element around it), cannot open at all, or considers too large is listed as not scanned and the rest of the scan carries on, but the run is never reported as clean. A generic function type like `type Fn = <T>(x: T) => T` or a type parameter list like `<const T extends object = {}>(x: T) => x` in a `.tsx` file is read as ordinary code, so it never fails the file, and an element with type arguments of any length, like `<Table<Row>>`, is still read as JSX. A project with no `extract` block fails the check with a message naming the block. With `--json`, the scan travels in the envelope under `result.literals`, split into `findings`, `suppressed`, and `diagnostics`.

## Examples

```bash
# report every setup problem at once
verbatra doctor

# validate a project in another directory, with an explicit config
verbatra doctor --cwd apps/web --config verbatra.config.ts

# machine-readable report for a CI preflight step
verbatra doctor --json

# list hardcoded user-facing strings in your source, with no key set
verbatra doctor --literals

# what the provider supports for each target locale
verbatra doctor --locales

# the same, against the provider's current language list
verbatra doctor --live
```

A run with two problems looks like this:

```text
verbatra doctor
  [ok  ] Configuration: Loaded /app/verbatra.config.ts.
  [ok  ] Format adapter: Format "i18next-json" resolves to an adapter.
  [ok  ] Provider: Provider "anthropic" resolves to a factory.
  [fail] API key environment variable: The ANTHROPIC_API_KEY environment variable is not set.
  [ok  ] Network policy: any host (config: unset; VERBATRA_NETWORK_POLICY: unset). Provider "anthropic" connects to api.anthropic.com: permitted.
  [fail] Source locale file: The source locale file was not found at /app/locales/en.json.
  [ok  ] Plural rules: ICU 78.3 (CLDR 48.0) supplies the plural rules; every target locale has CLDR plural rules.
  [ok  ] Locale codes: Every configured locale code is in canonical BCP 47 form.
  [ok  ] Locale state: Every locale with state in verbatra.lock.json, verbatra.cache.json, and verbatra.provenance.json is configured.
  [ok  ] Locale support: Provider "anthropic" is an LLM and accepts any locale (well-tested list of 2026-09-28).
2 problems found (run verbatra doctor again after fixing them)
```

## Terminal feedback

<AvailableFrom version="0.12.0" />

`doctor` shows one line while it runs its checks (`checking the setup and fetching the provider's language list` under `--live`), or `scanning the source for literals` with a running file count on an interactive terminal under `--literals`. Its report and its own hint stay on stdout:

```text
verbatra: checking the setup... done (0.2s)
```

These lines go to stderr, so stdout and `--json` output stay exactly as described above, and `--quiet` drops them. See [Terminal output](/docs/cli#terminal-output) for color, the spinner and the variables that control them.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | every check passed |
| `1` | at least one check failed (the full report is still printed), including a locale the provider does not support; with `--literals`, a literal was found or a file could not be scanned |
| `2` | could not run: a usage error (such as `--locales` or `--live` together with `--literals`), or an explicit `--config` path that does not exist |

Exit `1` means "it ran, and it found problems". Exit `2` is reserved for `doctor` being unable to run at all, which is why a missing config file found by search is a failed check and exit `1`, while a `--config` path pointing at nothing is exit `2`.
