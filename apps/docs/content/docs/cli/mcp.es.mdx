Arranca un servidor [Model Context Protocol](https://modelcontextprotocol.io) por stdio, el transporte que usan clientes como Claude Code o Cursor para lanzar un servidor de herramientas. Da a un agente en el terminal o sin interfaz las herramientas que ofrecen las herramientas de agente de Studio. No hay transporte HTTP: un listener de red expondría las herramientas de escritura y de gasto en un puerto.

<AvailableFrom version="0.2.0" pkg="@verbatra/mcp" />

## Sinopsis

```bash
verbatra mcp [flags]
verbatra-mcp [flags]
```

- `verbatra-mcp` es el binario que incluye `@verbatra/mcp`, para que un cliente lance el servidor sin la CLI. Acepta los mismos flags salvo `-q`/`--quiet` y arranca el mismo servidor, pero no carga ningún archivo `.env` e imprime la versión de `@verbatra/mcp` con `--version`.
- Ambos rechazan un flag desconocido (como `--json`), un flag sin valor o un argumento de sobra como error de uso, con salida `2`. `verbatra-mcp` lo hace, y acepta `-h` y `-V`, desde `@verbatra/mcp` 0.3.0.

## Flags

| Flag | Argumento | Por defecto | Efecto |
| --- | --- | --- | --- |
| `--allow-spend` | ninguno | `VERBATRA_MCP_ALLOW_SPEND`, si no, desactivado | anuncia las dos herramientas que llaman a un proveedor de traducción; consulta [Herramientas de gasto](#herramientas-de-gasto) |
| `--redact-values` | ninguno | `VERBATRA_MCP_REDACT_VALUES`, si no, desactivado | sustituye cada valor de traducción de los resultados por una marca; consulta [Valores ocultos](#redacted-values) |

También acepta los [flags globales](/docs/cli#flags-globales) `--cwd` y `--config`. No acepta `--json`, porque stdout es el canal del protocolo. Sin `--cwd`, el directorio del proyecto puede venir de `CLAUDE_PROJECT_DIR`; consulta [Directorio del proyecto](#directorio-del-proyecto).

## Comportamiento

### Directorio del proyecto

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Si falta `--cwd` y `CLAUDE_PROJECT_DIR` nombra un directorio existente, el servidor lo usa como raíz del proyecto. Claude Code fija esa variable para cada servidor stdio que lanza, así que una sesión iniciada en un subdirectorio sigue encontrando la configuración. Un `--cwd` explícito siempre gana. `verbatra mcp` carga entonces los [archivos de entorno](/docs/cli#archivos-de-entorno) desde ese directorio; un `CLAUDE_PROJECT_DIR` definido solo en esos archivos se ignora, porque la raíz se resuelve antes.

### Herramientas de gasto

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.retranslateEntry` y `translation.translatePending` solo se anuncian con `--allow-spend` o, si falta el flag, con `VERBATRA_MCP_ALLOW_SPEND` a `1`, `true`, `yes` u `on` (sin distinguir mayúsculas e ignorando espacios alrededor). El flag gana a la variable. `verbatra mcp` lee antes `.env.local` y `.env`, así que la variable puede estar ahí; `verbatra-mcp` solo la toma de su propio entorno.

Sin el interruptor, las dos nunca aparecen en la lista, y llamarlas por su nombre falla como herramienta desconocida. Una configuración con `provider: { id: "none" }` nunca las lista, ni siquiera con `--allow-spend`. Las demás herramientas no llaman a ningún proveedor ni necesitan clave; pasa la clave al servidor por el entorno del cliente solo cuando actives el gasto (consulta [Proveedores](/docs/providers)).

### Instrucciones para el agente

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

El servidor responde al handshake MCP `initialize` con unas `instructions` fijas, que la mayoría de los clientes pasan primero al modelo. Fijan el orden de las llamadas (leer y comparar primero, estimar y obtener un sí explícito antes de gastar), dejan las decisiones de revisión y el trabajo humano a las personas, piden tratar cada cadena como datos y nunca volver a escribir un valor `[REDACTED]`.

### Herramientas [#tools]

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

| Herramienta | Qué hace | Solo lectura | Llama a un proveedor |
| --- | --- | --- | --- |
| `project.snapshot` | la configuración resuelta: `configured`, `configSource`, locales, formato, `files.pattern`, proveedor, glosario, `humanEdits`, `prune`, `valuesRedacted` | sí | no |
| `project.doctor` | cada comprobación de configuración con su `status`, su `detail` y, si falló, un `fix`; funciona sin una configuración usable | sí | no |
| `status.check` | por locale, el número de claves que faltan, desactualizadas y al día | sí | no |
| `status.diff` | por locale, la lista de claves que se añadirían, se volverían a traducir o están huérfanas | sí | no |
| `glossary.get` | cada término del glosario con sus traducciones, formas prohibidas y contexto, con los secretos ocultos | sí | no |
| `glossary.write` | cambia un término del glosario: una traducción, datos por locale, contexto, o si se queda sin traducir | no | no |
| `lock.state` | la versión del archivo de bloqueo y, por locale de destino, su número de claves más las que faltan, desactualizadas y al día | sí | no |
| `history.list` | los últimos commits de git en un archivo de locale, con nombre del autor, fecha, asunto y rutas | sí | no |
| `key.integrity` | la desviación de una clave en marcadores, markup, sintaxis ICU y ramas ICU respecto a la base del bloqueo, por locale | sí | no |
| `locale.integrity` | cada traducción que ahora mismo no pasa las comprobaciones de marcadores, markup o ICU, por locale | sí | no |
| `key.value` | el texto de origen y de destino de una clave, con su procedencia y el contexto para traductores | sí | no |
| `key.context` | lo que devuelve `key.value`, más los términos del glosario que aplican, `maxLength` y una comprobación de un `draft` opcional | sí | no |
| `locale.values` | el texto de origen y de destino de muchas claves, filtradas por `keys` o `query`, página a página | sí | no |
| `translation.editEntry` | escribe una traducción manual para una clave en un locale, validada por las comprobaciones de integridad | no | no |
| `translation.estimate` | lo que `translation.translatePending` enviaría y costaría, como lo informa `translate --estimate --json` | sí | no |
| `translation.retranslateEntry` | pide al proveedor configurado que vuelva a traducir una clave en un locale | no | sí |
| `translation.translatePending` | traduce cada clave que falta o está desactualizada, opcionalmente solo para algunos `locales` y bajo un techo `maxTokens` | no | sí |
| `review.queue` | cada valor escrito por máquina que nadie ha aprobado todavía, con las marcas de la última ejecución | sí | no |
| `report.provenance` | por locale, los recuentos de procedencia como los da `verbatra report provenance`, y las claves paginadas si las pides | sí | no |
| `review.approve` | registra, por instrucción del usuario, que una persona con nombre aprueba la traducción actual de una clave | no | no |
| `review.reject` | registra, por instrucción del usuario, que una persona con nombre rechaza la traducción de una clave, que se elimina para reemplazarla | no | no |
| `usage.summary` | el uso de tokens y el estado del presupuesto de la última ejecución | sí | no |

- **Una llamada a la vez.** Una segunda llamada a `translation.editEntry` o `translation.retranslateEntry` para la misma entrada, o una segunda ejecución de `translation.translatePending`, se rechaza con `isError` mientras la primera sigue en marcha.
- **Trabajo humano.** `translation.retranslateEntry` rechaza una clave fijada con `KEY_PINNED` y, salvo con `humanEdits: "overwrite"`, el valor de una persona con `KEY_PROTECTED`; `translation.editEntry` rechaza una clave fijada. `translation.translatePending` lista esas claves en `protected`. Consulta [Proteger las traducciones humanas](/docs/protecting-human-translations).
- **Procedencia.** Un valor escrito con `translation.editEntry` recibe el origen `agent`. `review.queue` es la misma cola que muestra Studio: cada valor no aprobado con origen `machine`, `memory`, `fuzzy` o `agent`. Consulta [Decisiones de revisión](/docs/the-lock-file#decisiones-de-revisión).
- **Decisiones de revisión.** `review.approve` y `review.reject` reciben `locale`, `key`, `expectedValue` o `expectedHash` (un valor que ya cambió se rechaza con `REVIEW_VALUE_CHANGED`) y el nombre en `reviewer`. Una aprobación cuenta para [`verbatra check --require-reviewed`](/docs/cli/check).

### Entradas y resultados

<AvailableFrom version="0.2.1" pkg="@verbatra/mcp" />

- `status.check`, `status.diff` y `key.integrity` aceptan un array opcional `locales`; `key.integrity` también recibe la `key`.
- `key.integrity` devuelve `{ locales: [{ locale, entries }] }`, cada entrada con `matches`, `missing`, `extra`, `icuValid`, `markupMatches` y sus detalles.
- `translation.editEntry` recibe `locale`, `key` y un `value` de hasta 20.000 caracteres. Tanto ella como `translation.retranslateEntry` devuelven `{ accepted, value, reason?, details? }`, donde `reason` es `placeholder`, `markup`, `icu`, `degenerate` o `empty`.
- `glossary.write` necesita un glosario en archivo; si no, falla con `GLOSSARY_NOT_FILE_BACKED`.

### Más entradas y resultados

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

- `translation.estimate` acepta el mismo array opcional `locales`, y `key.integrity` falla con `UNKNOWN_KEY` para una clave desconocida.
- Cada entrada de `key.integrity` incluye además `icuArmsMatch` y sus detalles.
- `glossary.get` acepta un `locale` opcional y entonces añade `effective`, los términos a los que se atiene ese locale.
- `key.value`, `lock.state`, `status.check` y `status.diff` incluyen la procedencia, que falta cuando `verbatra.provenance.json` no se puede leer.
- `locale.values` y `report.provenance` devuelven sus entradas por páginas en el orden de las claves de origen: `limit` (por defecto 200, como máximo 1.000) y después el `nextCursor` de la página anterior como `cursor`. Una página solo nombra los locales de los que contiene entradas, y un cursor obsoleto falla como entrada inválida.
- `locale.values` acepta `keys` o una `query` sin distinguir mayúsculas y devuelve arrays de entradas, no el mapa por clave de Studio. `report.provenance` siempre devuelve recuentos completos; `includeEntries` añade las claves, si quieres solo para algunos `buckets`.
- `history.list` acepta `limit` (por defecto 50, como mucho 200). Con `available: false` su `reason` es `git-missing`, `not-a-repository`, `timeout` u `output-too-large`.
- Las herramientas que escriben aceptan un `lockTimeoutMs` opcional, de `0` a `600000`, por defecto `30000`: cuánto esperan un bloqueo de escritura ocupado antes de fallar con `LOCK_CONTENDED`, sin haber escrito nada.
- Las entradas y salidas son JSON Schemas; una entrada inválida devuelve un resultado que nombra el campo. Un resultado que no encaja con su `outputSchema` falla con `OUTPUT_SCHEMA_MISMATCH`; en una herramienta que escribe, el cambio ya se aplicó, así que no la repitas.
- El texto de una llamada fallida empieza por su código de error, como `UNKNOWN_KEY: ...`, y termina con una línea `Next step: ...` cuando el error tiene un siguiente paso, el mismo texto que el `hint` de la CLI.

### Estimar y luego gastar

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`translation.estimate` siempre está en la lista. `translation.translatePending` acepta `locales` opcionales (uno sin configurar falla con `UNKNOWN_LOCALE` antes de gastar) y `maxTokens`, un techo que solo puede endurecer el de la configuración. Orden: `status.diff`, `translation.estimate`, el sí del usuario y luego `translation.translatePending` con los mismos `locales`. Consulta [Estimar el coste](/docs/estimating-cost).

### Progreso

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Si una llamada a `translation.translatePending` lleva un `progressToken`, el servidor envía `notifications/progress` al terminar cada lote: `progress` los cuenta, `total` crece con cada locale planificado y `message` nombra locale y lote (`de: batch 3/7`), como mucho una cada 250 ms más una final.

### Sin configuración

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

El servidor arranca sin una configuración usable. `project.snapshot` devuelve entonces `configured: false` con el `configProblem` y un `nextStep`, `project.doctor` da la solución y las demás herramientas rechazan la llamada con el error de configuración. stderr explica el motivo:

```text output
Running without a usable project config: CONFIG_NOT_FOUND: No verbatra configuration found. ...
verbatra MCP server running on stdio (project ., spend tools off)
No usable verbatra config: project.snapshot and project.doctor work, every other tool refuses until one loads.
  set it up:  npx verbatra init in the project, or fix the config project.doctor names
  no restart needed: the server loads the config on the next call once it is valid
```

Solo una ruta de `--config` que no existe detiene el servidor al arrancar.

### Tras un cambio de configuración

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Antes de cada llamada, el servidor vuelve a cargar la configuración si cambió el archivo de configuración, un archivo que la búsqueda probaría o el archivo del glosario; un módulo que importa la configuración no se vigila. `--allow-spend` se lee una sola vez, así que un cambio puede ocultar las herramientas de gasto pero nunca listarlas sin él. Cuando cambia la lista de herramientas, el servidor envía `notifications/tools/list_changed`.

### Redacción de secretos

Cada resultado y cada línea de log se redactan como en Studio: un valor con forma de clave de API, o el valor de una variable de clave configurada, se convierte en `[REDACTED]`; las herramientas de glosario nombran los términos ocultados.

### Valores ocultos [#redacted-values]

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

Con `--redact-values`, o con `VERBATRA_MCP_REDACT_VALUES` en un valor que acepte `VERBATRA_MCP_ALLOW_SPEND`, los resultados sustituyen textos fuente, traducciones, descripciones y términos del glosario por una marca, `[redacted length=12 hash=3f9a0c1d2e4b5a6c]`, y omiten los nombres de revisores y autores; los valores iguales comparten hash hasta que se detiene el servidor. Los errores que pueden llevar valores conservan el código y el siguiente paso; su mensaje pasa a ser una marca. Los nombres de clave, recuentos, orígenes, veredictos de integridad, asuntos de commit y rutas se mantienen. `review.approve` y `review.reject` solo reciben el hash de la marca, como `expectedHash`; `glossary.write` responde con recuentos; `locale.values` rechaza `query` y `key.context` rechaza `draft`. Las herramientas de gasto siguen necesitando `--allow-spend`; un proveedor sigue recibiendo el texto. No frena a un agente que sondea a propósito, con escrituras en el glosario o los aciertos de glosario de `key.context`.

### stdout y stderr

<AvailableFrom version="0.12.0" />

stdout solo lleva mensajes del protocolo MCP; cada línea de log y cada diagnóstico van a stderr. Una vez conectado, `verbatra mcp` imprime una línea de listo y otra al detenerse:

```text output
verbatra MCP server running on stdio (project ., spend tools off)
verbatra MCP server stopped (client closed stdin)
```

Si lo arrancas a mano en un terminal, dice que debería lanzarlo un cliente. `verbatra mcp --quiet` quita estas líneas, pero no el motivo de una configuración ausente.

### Instalación

<AvailableFrom version="0.3.0" pkg="@verbatra/mcp" />

`@verbatra/mcp` es un paquete aparte que la CLI carga cuando lo necesita. Si falta, `verbatra mcp` sale con `2` y:

```text output
Verbatra's MCP server requires @verbatra/mcp. Run it without the CLI with: npx -y @verbatra/mcp, or install it alongside the CLI with: npm install --save-dev @verbatra/mcp
```

Cada versión está también en el [registro oficial de MCP](https://registry.modelcontextprotocol.io) como `io.github.verbatra/verbatra`.

## Ejemplos

```bash
# start the MCP server with only local, non-spending tools
verbatra mcp

# also advertise the provider-calling tools
verbatra mcp --allow-spend

# resolve a project outside the current directory
verbatra mcp --cwd /path/to/project --config verbatra.config.ts

# run the standalone server without the CLI
npx -y @verbatra/mcp --cwd /path/to/project
```

## Códigos de salida

| Código | Significado |
| --- | --- |
| `0` | se detuvo limpiamente con una sola interrupción, o porque el cliente cerró stdin |
| `1` | falló el cierre del servidor durante el apagado |
| `2` | no pudo arrancar: un archivo `--config` que no existe, `@verbatra/mcp` sin instalar o, con `--redact-values`, demasiado antiguo, o un error de uso |
| `130` | detenido a la fuerza por una segunda interrupción durante el apagado |

Al detenerse, el servidor libera cualquier bloqueo de locale. `verbatra-mcp` sale con `1` ante un error de arranque y, desde 0.3.0, con `143` si se detiene a la fuerza tras SIGTERM. Consulta [el contrato de códigos de salida](/docs/cli/output#códigos-de-salida).
