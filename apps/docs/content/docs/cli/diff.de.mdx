---
title: verbatra diff
description: Zeige die Keys, die pro Locale hinzugefügt oder neu übersetzt würden oder verwaist sind, ohne Dateien zu schreiben.
---
Liste pro Ziel-Locale die genauen ausstehenden Keys: die, die ein Lauf hinzufügen würde (im Ziel fehlend), die, die er neu übersetzen würde (Quelle seit der letzten Übersetzung geändert), und die inzwischen verwaisten (im Ziel, aber aus der Quelle verschwunden). `diff` führt dasselbe Lesen und Diffen aus, das [`verbatra translate`](/docs/cli/translate) direkt vor dem Provider-Aufruf ausführen würde, und hört dann auf: kein Provider-Aufruf, keine geschriebenen Dateien, keine Aktualisierung der [Lock-Datei](/docs/the-lock-file) und kein API-Key nötig.

## Synopsis

```bash
verbatra diff [flags]
```

## Flags

| Flag | Argument | Standard | Wirkung |
| --- | --- | --- | --- |
| `--cwd` | `<path>` | aktuelles Verzeichnis | Konfiguration und Locale-Dateien von diesem Verzeichnis aus auflösen |
| `--config` | `<path>` | wird gesucht | diese Konfigurationsdatei laden, statt eine zu suchen |
| `--locales` | `<list>` | alle konfigurierten Ziele | kommagetrennte Teilmenge der Ziel-Locales, die verglichen wird |
| `--unused` | keins | aus | zusätzlich die Roots des [`extract`-Blocks](/docs/config-file#extract) scannen und die Keys der Quell-Locale auflisten, die keine Aufrufstelle nennt (siehe [Ungenutzte Quell-Keys](#ungenutzte-quell-keys)) |
| `--json` | keins | aus | einen [JSON-Envelope](/docs/ci-and-exit-codes#json-ausgabe) auf stdout ausgeben, der die Diff-Zusammenfassung unter `result` trägt, oder bei einem fehlgeschlagenen Lauf den Fehlercode; die menschenlesbare Fehlerzeile geht weiter auf stderr |

Ein Locale hat ausstehende Änderungen, wenn es mindestens einen Key zum Hinzufügen oder Neuübersetzen hat. Verwaiste Keys werden gemeldet, zählen aber nie als ausstehend, weil ein Standardlauf sie nicht entfernt (das tut nur [`verbatra translate --prune`](/docs/cli/translate)). Ein leerer oder unbekannter `--locales`-Wert wird mit Exit `2` abgelehnt, statt stillschweigend nichts zu vergleichen. Während [`verbatra check`](/docs/cli/check) die Frage "wie viel hat gedriftet" mit Zählern beantwortet, beantwortet `diff` die Frage "welche Keys" mit den Listen selbst.

## Ungenutzte Quell-Keys

<AvailableFrom version="0.11.0" />

`orphaned` beantwortet "welche Ziel-Keys sind aus der Quelle verschwunden". `--unused` beantwortet eine andere Frage: Welche Keys in deiner Quell-Locale-Datei nennt deine Anwendung nirgends mehr? Es scannt die `roots` des [`extract`-Blocks](/docs/config-file#extract) mit demselben Leser, den [`verbatra extract`](/docs/cli/extract) nutzt, und listet jeden Key der Quell-Locale auf, den keine Aufrufstelle nennt. Die beiden Listen werden nie zusammengeführt: Ein Key kann in `de` verwaist und unabhängig davon in der Quelle ungenutzt sein.

Es bleibt rein lesend. Nichts wird entfernt, umgeschrieben oder umsortiert, kein Provider wird erzeugt und kein API-Key gelesen. Ob du einen Key löschst, entscheidest du.

Ein Key, den der Code noch erreichen kann, wird nie aufgelistet:

- Eine Referenz irgendwo unterhalb der Roots zählt, auch in einer Datei, die keine Route importiert.
- Eine Plural- oder Kontextvariante eines referenzierten Keys gilt als referenziert: `t("items", { count })` deckt `items_one` und `items_other` ab, und `t("friend", { context })` deckt `friend_male`, `place_ordinal_one` und Ähnliches ab. Das entspricht dem, wie `translate` generierte Pluralformen aus der Liste verwaister Keys heraushält.
- Auch jeder Key unter einem referenzierten Eltern-Key zählt, also deckt `t("nav", { returnObjects: true })` `nav.home` ab.

Der Bericht trägt einen `status`:

| `status` | Bedeutung |
| --- | --- |
| `complete` | nichts im Scan stellt die Liste infrage |
| `unreliable` | der Scan ist auf etwas gestoßen, das einen Key erreichen kann, den er nicht benennen kann; ein aufgelisteter Key kann also noch in Gebrauch sein. `unreliableBecause` sagt, worauf: `dynamic-keys` (ein Key, der kein einzelner statischer String ist, auch ein Key mit Namespace), `indirect-key-sites` (eine `keyPrefix`-Option, eine `Trans`-Komponente oder ein `i18nKey`-Attribut) oder `incomplete-scan` (eine Datei oder ein Verzeichnis, das nicht bis zum Ende gelesen werden konnte). Jeder Fund kommt mit Datei und Zeile. |
| `not-run` | es gab nichts zu scannen, und es wird überhaupt kein Key aufgelistet. `reason` ist `EXTRACT_NOT_CONFIGURED` (kein `extract`-Block), `EXTRACT_FS_UNSUPPORTED` (das Dateisystem eines SDK-Aufrufers kann keine Verzeichnisse auflisten) oder `NO_SOURCE_FILES` (keine Quelldatei unterhalb der Roots) |

Ein Key, der nur von außerhalb des gescannten Quellcodes referenziert wird (ein Server-Template, ein CMS, eine Test-Fixture), gehört in [`extract.ignoreUnused`](/docs/config-file#extract). Ein getroffener Key erscheint unter `ignored`, nie unter `unused`, und fällt nie stillschweigend weg.

## Beispiele

```bash
# list the pending keys per locale (exit 1 if any are pending)
verbatra diff

# machine-readable key lists for tooling or a PR comment
verbatra diff --json

# also list the source keys your code no longer names (exit 1 if a complete scan finds any)
verbatra diff --unused
```

## Exit-Codes

| Code | Bedeutung |
| --- | --- |
| `0` | keine ausstehenden Änderungen: kein Locale hat einen Key zum Hinzufügen oder Neuübersetzen, und mit `--unused` hat kein vollständiger Scan einen ungenutzten Key gefunden |
| `1` | ausstehende Änderungen: mindestens ein Locale hat einen fehlenden oder geänderten Key, oder mit `--unused` hat ein `complete`-Scan mindestens einen ungenutzten Key gefunden (verwaiste Keys, ignorierte Keys und ein `unreliable`- oder `not-run`-Bericht erzeugen allein nie `1`) |
| `2` | konnte nicht laufen: ein Fehler des gesamten Laufs oder ein Verwendungsfehler (einschließlich eines leeren oder unbekannten `--locales`-Werts) |
