---
title: verbatra translate
description: Translate every target locale once, then exit.
---
Run one translation pass over every target locale, then exit. `translate` reads the source locale, diffs it against [the lock file](/docs/the-lock-file), sends only the new or changed strings to the provider, runs the [integrity checks](/docs/translation-safety), writes the locale files, and updates the lock. Anything still current is never re-sent, so you never pay twice for an unchanged string.

## Synopsis

```bash
verbatra translate [flags]
```

## Flags

| Flag | Argument | Default | Effect |
| --- | --- | --- | --- |
| `--cwd` | `<path>` | current directory | resolve config and locale files from this directory |
| `--config` | `<path>` | search for one | load this config file instead of searching for one |
| `--locales` | `<list>` | every configured target locale | translate only this comma-separated subset; an unconfigured locale fails the run with `UNKNOWN_LOCALE` before anything is read or spent, and an empty list is a usage error, exit `2` |
| `--dry-run` | none | off | preview changes without calling a provider or writing files (no API key needed) |
| `--prune` | none | the config's `prune` option, otherwise off | remove orphaned keys (in a target file but absent from source) from the written file and the lock |
| `--lock-timeout` | `<seconds>` | `600` | how long to wait for a held per-locale write lock before failing; must be a bare positive integer of seconds (a value like `60s`, `0`, or `-1` is a usage error, exit `2`) |
| `--concurrency` | `<n>` | `1` | translate up to `n` target locales at once; must be a positive integer |
| `--max-tokens` | `<n>` | the config's `maxTokens` | a hard token ceiling for this run alone; when the config also sets `maxTokens`, the lower of the two applies; must be a positive integer (a value like `10k` or `0` is a usage error, exit `2`) |
| `--no-cache` | none | off (cache on) | bypass the local [translation-memory cache](/docs/the-cache) (`verbatra.cache.json`) for this run |
| `--include-human` | none | off | also retranslate stale keys whose value a person wrote, imported, or changed outside verbatra, for this run only (`humanEdits: "overwrite"`); [pinned keys](/docs/protecting-human-translations#pinning-keys) stay untouched |
| `--json` | none | off | print one [JSON envelope](/docs/ci-and-exit-codes#json-output) on stdout carrying the run summary under `result` (the [`RunSummary` shape](/docs/sdk)), or the error code on a failed run; the human-readable error line still goes to stderr |
| `--estimate` | none | off | estimate what the run would send and what it would cost, then exit without calling a provider; implies `--dry-run`, so no API key is needed |

By default a run deletes nothing: orphaned keys are reported and left in place. `--prune` removes exactly those keys and nothing else, and overrides the config's `prune` option for this run. Before it runs, `translate` loads `.env.local` and then `.env` from the working directory; a variable already set in the real environment wins.

`--dry-run` constructs no provider at all, so it needs no API key and cannot spend anything: it reads the source and target files, diffs them against the lock file, and reports exactly what a real run would change. It writes nothing (no locale file, no lock update, no run-status snapshot), it neither reads nor writes the cache, and it takes no per-locale write lock, so it never waits on a run already in progress. The `.env` load above still happens on a dry run; there is simply no key to read. That makes it a complete way to try verbatra on a real project before creating a provider account.

In a [human-only](/docs/human-only-workflow) project (`provider: { id: "none" }`) a dry run is the one exception to the cache rule: it reads the translation memory, still writing nothing, so its plan lists the same `cacheHits` and `unfilled` keys a live run would, and `--estimate` reports nothing to send and nothing billed.

<AvailableFrom version="0.12.0" />

`--estimate` adds a pre-run cost estimate to that dry run: how many keys would be sent, how many provider requests they would be split into, and the quantity the configured provider actually bills for (estimated prompt and completion tokens for an LLM, estimated source characters for DeepL or Google Cloud Translation, and no cost at all for a self-hosted `openai-compatible` endpoint). It implies `--dry-run`, so it spends nothing and writes nothing. A currency figure appears only when the config carries a `rates` block covering the configured provider and model; without one the quantity is still reported and the missing rate key is named, rather than a cost of `0.00` being invented. Every figure is printed beside the date those rates were read, and beside a line naming what the estimate leaves out. See [Estimating cost](/docs/estimating-cost).

<AvailableFrom version="0.11.0" />

`--locales de,fr` narrows the run to a subset of the configured targets. Locales left out are untouched: their files, their lock entries, and their cache entries all stay as they were. It is the flag to reach for on a rate-limited free tier, where translating one locale at a time is the only way through, and it is also the fastest way to re-run a single locale that came out partial. The run-status snapshot always describes the most recent run alone, so a subset run narrows it to that subset.

`--lock-timeout` tunes how long a locale waits for a contended [write lock](/docs/the-lock-file) before the run fails with `LOCK_CONTENDED`: raise it when another run legitimately holds the lock for a while, lower it to fail fast in CI.

<AvailableFrom version="0.12.0" />

`--max-tokens` caps what one run may spend without touching the config. It is always a hard stop: a provider request that would pass the ceiling is withheld rather than sent, whatever `budgetBehavior` says, and its keys are listed as `budgetWithheld` in the summary. The ceiling is counted the same way as a configured [`maxTokens` budget](/docs/config-file#maxtokens-and-budgetbehavior). When the config also sets `maxTokens`, the lower of the two applies, so the flag can tighten the budget but never loosen it. A run the ceiling cut short exits `1`, as a locale that came out partial always does. Run `--estimate` first to pick a sensible figure.

`--concurrency` runs several target locales in parallel to finish a large project faster. It is refused with exit `2` when a token budget applies, from the config's `maxTokens` or from `--max-tokens`, because the ceiling would still hold but which locale loses its remaining work would depend on the order the locales interleave, so the same project would not produce the same run twice (a dry run is exempt). If a whole-run error (in practice a corrupt lock file) surfaces once locales are already running, no further locale is started, and the ones in flight finish and release their write locks before the command exits with `2`, so the run leaves no lock behind for the next one to wait on. As a run advances, progress is printed to stderr (one line per locale start, provider sub-batch, and locale finish), so a `--json` run's stdout stays a single clean summary. `--no-cache` skips the [translation-memory cache](/docs/the-cache) for the run, making exactly the provider calls it would with no cache present.

## Examples

```bash
# translate once using the config it finds
verbatra translate

# preview the keys that would be pruned, spending nothing
verbatra translate --prune --dry-run

# one locale at a time, which is what a rate-limited free tier needs
verbatra translate --locales de

# size and price the run without spending anything
verbatra translate --estimate

# stop before the run passes 50000 tokens
verbatra translate --max-tokens 50000

# also retranslate stale keys a person wrote
verbatra translate --include-human
```

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | every target locale came out complete |
| `1` | the run finished but one or more locales failed or came out partial |
| `2` | could not run: a whole-run error (config, source, format, provider, or lock), or a usage error |
| `3` | human-only project (`provider: { id: "none" }`): the run finished cleanly, but keys are left for a human translation |

<AvailableFrom version="0.9.0" />

One locale failing is not fatal: the run finishes, exits `1`, and the per-locale detail sits in the summary. A **partial** locale exits `1` as well. That is a locale whose file was written but still has keys missing, typically because a provider sub-batch failed or the integrity gate refused a translation, and shipping it as a success would leave a half-translated file in your repository unnoticed.

Exit `3` only happens in a [human-only](/docs/human-only-workflow) project. No provider is called there: keys the translation memory covers are written, and every other missing or changed key is listed as `unfilled` and left untouched. A failed or partial locale still wins and exits `1`. Hand the `unfilled` keys off with [`verbatra export`](/docs/cli/export).

<AvailableFrom version="0.12.0" />

Stale keys whose value a person wrote, imported, or changed outside verbatra are kept by default: they are listed as `protected`, are not sent to the provider, and stay stale for `verbatra check`. A line on stderr says how many were left. They do not change the exit code, except in a human-only project, where they count toward exit `3` like `unfilled` keys. `--include-human` retranslates them for one run. See [Protecting human translations](/docs/protecting-human-translations).
