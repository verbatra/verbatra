---
title: verbatra init
description: Crée une config verbatra et un exemple de .env pour ce projet, détectés depuis tes fichiers de locale, en interactif ou entièrement sans surveillance.
---
Échafaude un projet : `init` écrit un `verbatra.config.ts` et un `.env.example` qui nomme la variable de clé d'API de ton fournisseur (jamais une valeur de clé), et s'assure que `.gitignore` couvre `.env`, `.env.local`, `.verbatra-local/` et `verbatra.cache.json`. Il regarde d'abord les fichiers de locale déjà présents dans le projet, donc dans la plupart des projets le fournisseur est la seule chose que tu as à lui indiquer.

## Synopsis

```bash
verbatra init [flags]
```

## Options

| Option | Argument | Défaut | Effet |
| --- | --- | --- | --- |
| `--cwd` | `<path>` | répertoire courant | analyse ce répertoire et y écrit la config et les fichiers d'environnement |
| `--provider` | `<id>` | aucun (requis) | fournisseur pour lequel générer la config : `anthropic`, `openai`, `gemini`, `deepl`, `google-translate`, `openai-compatible`, `libretranslate` ou `none` |
| `--format` | `<id>` | détecté, sinon `i18next-json` | le format des fichiers de locale, l'un des ids de [Formats](/docs/formats) |
| `--source` | `<locale>` | détectée, sinon `en` | la locale source dans laquelle tes chaînes sont écrites |
| `--targets` | `<locales>` | détectées, sinon `de` | locales cibles vers lesquelles traduire, séparées par des virgules |
| `--path` | `<pattern>` | détecté, sinon la structure habituelle du format (voir [Détection](#détection)) | motif des fichiers de locale ; doit contenir le jeton `{locale}` |
| `--model` | `<name>` | le défaut de l'échafaudage | le modèle ; requis pour `openai-compatible`, optionnel pour `anthropic`, `openai` et `gemini` |
| `--base-url` | `<url>` | aucun | l'URL du serveur ; `openai-compatible` et `libretranslate` uniquement, et requis dans ce cas |
| `--api-key-env-var` | `<name>` | `OPENAI_COMPATIBLE_API_KEY` | la variable d'environnement dans laquelle `openai-compatible` lit sa clé ; `openai-compatible` uniquement |
| `--yes` | aucun | désactivé | ne pose jamais de question, et prend le défaut pour tout ce qui n'est ni passé ni détecté |
| `--force` | aucun | désactivé | écrase un `verbatra.config.ts` existant dont le contenu diffère |
| `--json` | aucun | désactivé | affiche une [enveloppe JSON](/docs/ci-and-exit-codes#sortie-json) décrivant ce qui a été écrit ; ne pose jamais de question |
| `--agent` | aucun | désactivé | écrit en plus la section verbatra pour les agents de code dans `AGENTS.md` ou `CLAUDE.md`, et le serveur MCP verbatra, dépense désactivée, dans `.mcp.json` (voir [Préparer les agents de code](#préparer-les-agents-de-code)) |

Une option l'emporte toujours. Tout ce que tu omets est détecté depuis le projet, puis demandé quand stdin est un terminal et que ni `--yes` ni `--json` ne sont donnés, et sinon pris depuis son défaut, uniquement sous `--yes`. Dans un terminal, appuyer sur Entrée accepte la valeur proposée, et cela compte comme ta réponse. Une option donnée avec une valeur vide, comme `--targets ''`, est une erreur d'utilisation (`INVALID_OPTION`), jamais une demande de la valeur par défaut. Dans un terminal, chaque réponse est vérifiée dès que tu la donnes : un fournisseur ou un format inconnu, un code de locale mal formé, une liste de locales cibles qui nomme la locale source ou aucune locale, un motif sans `{locale}`, ou une URL de base qui n'est pas une URL ou contient des identifiants est expliqué sur stderr et redemandé, jusqu'à trois fois, pour que les réponses déjà données soient conservées. Une troisième réponse invalide arrête `init` avec le code d'erreur de cette réponse (comme `INVALID_LOCALE` ou `INVALID_OPTION`), nomme la question et l'option à passer à la place, et rien n'est écrit.

## Détection

`init` parcourt le répertoire à la recherche de fichiers qu'un adaptateur de format revendique, en sautant les répertoires cachés, `node_modules` et les sorties de build courantes, et trouve la partie de chaque chemin qui écrit une locale : un nom de fichier comme `de.json`, `messages_pt_BR.properties` ou `app_en.arb`, ou un répertoire comme `locales/de/`, `de.lproj/` ou le `values-de/` d'Android. Le motif de fichier qui couvre le plus de locales l'emporte, et il remplit :

- `format` : le seul format dont l'adaptateur lit chaque fichier trouvé. Tous les adaptateurs JSON lisent `.json`, donc pour des fichiers JSON c'est une seule dépendance correspondante dans `package.json` (`i18next`, `vue-i18n`, `next-intl` ou `@ngx-translate/core`) qui tranche.
- `files.pattern` et `files.localeStyle` : `posix` quand les fichiers écrivent `pt_BR`, `android` pour les répertoires `values-*`, `literal` sinon.
- `sourceLocale` : la langue source d'un catalogue `.xcstrings`, sinon `en` ou l'unique locale `en-*` trouvée, sinon la seule locale trouvée.
- `targetLocales` : toutes les autres locales trouvées.

Un fichier à côté des fichiers de locale qui contient des chaînes sous aucun nom de locale, comme `messages.properties` à côté de `messages_de.properties`, `Strings.resx` à côté de `Strings.de.resx`, ou un `app.pot` gettext, est signalé comme `unqualifiedSourceFile`. verbatra lit la source depuis le fichier que son motif nomme pour la locale source et ne peut pas pointer vers un tel fichier, donc dans ce cas `init` ne devine pas la locale source : passe `--source`, même avec `--yes`, et les étapes suivantes t'indiquent vers quel fichier renommer ou copier le fichier de base.

Sans aucun fichier de locale, ce sont les dépendances seules qui décident du format, et `files.pattern` et `files.localeStyle` prennent la structure habituelle du format choisi :

| Format | `files.pattern` | `files.localeStyle` |
| --- | --- | --- |
| `i18next-json` | `locales/{locale}.json` | aucun (`literal`) |
| `vue-i18n-json` | `src/locales/{locale}.json` | aucun (`literal`) |
| `next-intl-json` | `messages/{locale}.json` | aucun (`literal`) |
| `ngx-translate-json` | `src/assets/i18n/{locale}.json` | aucun (`literal`) |
| `xliff` | `locales/{locale}.xlf` | aucun (`literal`) |
| `yaml` | `locales/{locale}.yml` | aucun (`literal`) |
| `arb` | `lib/l10n/app_{locale}.arb` | `posix` |
| `properties` | `src/main/resources/messages_{locale}.properties` | `posix` |
| `apple-strings` | `{locale}.lproj/Localizable.strings` | aucun (`literal`) |
| `apple-xcstrings` | `{locale}Localizable.xcstrings` | aucun (`literal`) |
| `android-xml` | `app/src/main/res/{locale}/strings.xml` | `android` |
| `gettext-po` | `locales/{locale}/LC_MESSAGES/messages.po` | `posix` |
| `ini` | `locales/{locale}.ini` | aucun (`literal`) |
| `resx` | `Resources/Strings.{locale}.resx` | aucun (`literal`) |

Un catalogue `apple-xcstrings` est un seul fichier partagé par toutes les locales, et verbatra ne le crée jamais : crée-le d'abord dans Xcode. `--format`, `--path` et `--source` restreignent la détection au lieu d'être écrasés par elle : `--format yaml` ne regarde donc que les fichiers YAML.

`init` ne choisit jamais au hasard entre des égaux. Quand plusieurs formats lisent les fichiers (du JSON brut sans dépendance i18n, par exemple), il sort avec `2` et `FORMAT_AMBIGUOUS`, et quand plusieurs motifs de fichiers sont à égalité (un fichier par namespace, comme `locales/{locale}/common.json` et `locales/{locale}/auth.json`), il sort avec `2` et `LAYOUT_AMBIGUOUS`. Les deux listent les candidats ; passe `--format` ou `--path` pour en choisir un. Dans un terminal, il te pose la question à la place, en proposant le premier candidat.

## Exécutions sans surveillance

Sans terminal, ou avec `--json`, `init` ne pose jamais de question. Une valeur ni passée, ni détectée, ni fixée par défaut par `--yes` est une erreur : `init` sort avec `2` et `MISSING_OPTIONS`, et nomme d'un coup chaque option manquante. Une erreur due à une ambiguïté ou à une option invalide liste aussi les options encore manquantes, pour qu'une seule exécution dise à un agent tout ce qu'il doit passer. `--provider` n'a pas de défaut, pas plus que `--base-url` et `--model` pour `openai-compatible` ou `--base-url` pour `libretranslate`, donc ceux-là sont toujours nécessaires. Voici la commande qu'un agent lance :

```bash
npx verbatra init --provider gemini --yes --json
```

Avec `--json`, stdout porte exactement une enveloppe. Son `result` :

```ts
interface InitResult {
  configPath: string;                  // absolute path of verbatra.config.ts, or of the config --agent kept
  files: { path: string; action: "created" | "overwritten" | "updated" | "unchanged" }[];
  config: {                            // the config that was validated and written
    sourceLocale: string;
    targetLocales: string[];
    format: string;
    files: { pattern: string; localeStyle?: "posix" | "android" };
    provider: { id: string; options: Record<string, unknown> };
  } | null;
  sources: {                           // where each value came from
    provider: "flag" | "prompt";
    format: "flag" | "prompt" | "files" | "dependencies" | "default";
    pattern: "flag" | "prompt" | "detected" | "default";
    sourceLocale: "flag" | "prompt" | "detected" | "default";
    targetLocales: "flag" | "prompt" | "detected" | "default";
  } | null;
  apiKeyEnvVar: string | null;         // the variable to set; null for provider none
  detection: {
    format: { id: string; from: "input" | "files" | "dependencies" } | null;
    layout: {
      pattern: string;
      localeStyle: "literal" | "posix" | "android";
      locales: string[];
      sourceLocale: string | null;
      unqualifiedSourceFile: string | null;
      files: string[];
    } | null;
    ambiguities: { subject: "format" | "layout"; candidates: string[] }[];
    confidence: "high" | "medium" | "low" | "none";
    reasons: string[];                 // one sentence per decision or doubt
  } | null;
  agent: {                             // null sans --agent
    instructionsFile: "AGENTS.md" | "CLAUDE.md";
    mcpServer: "added" | "present" | "differs";
    configKept: boolean;               // true when --agent kept an existing config
  } | null;
  nextSteps: { description: string; command: string | null }[];
}
```

`confidence` vaut `high` quand les fichiers seuls ont tout décidé, `medium` quand une convention ou une dépendance a comblé un manque (par exemple prendre `en` comme source) ou qu'un manque est resté ouvert (par exemple la locale source du répertoire `values` non qualifié d'Android, qui n'en nomme aucune), `low` quand aucun fichier de locale n'appuyait le format, et `none` quand rien n'a été détecté. Un `default` dans `sources` est la valeur à revérifier. `nextSteps` se termine par les commandes exactes à lancer ensuite, comme `npx verbatra doctor`.

Une enveloppe d'erreur pour `FORMAT_AMBIGUOUS`, `LAYOUT_AMBIGUOUS`, `INVALID_PROVIDER` ou `INVALID_FORMAT` porte aussi un tableau `candidates` avec les valeurs parmi lesquelles choisir. Toute erreur d'utilisation qui laisse des options sans réponse porte aussi un tableau `missing` qui les nomme, comme `"--source <locale>"`.

## Fournisseurs

`--provider none` génère une configuration [100 % humaine](/docs/human-only-workflow) sans `options` et n'écrit aucun `.env.example`, puisqu'aucune clé d'API n'est jamais lue.

`--provider openai-compatible` génère la config d'un serveur local ou auto-hébergé à partir de `--base-url` et `--model`, avec `maxOutputTokens: 4096`. Sa clé est optionnelle : un serveur qui n'en a pas besoin laisse `OPENAI_COMPATIBLE_API_KEY` non définie, et `--api-key-env-var` nomme une autre variable pour un serveur qui en a besoin. `init` écrit le nom de cette variable dans la config et dans `.env.example`, jamais une valeur, et refuse une URL de base qui contient des identifiants, une query string ou un fragment, comme `https://user:key@host` ou `https://host/v1?api-key=...`, par lesquels une clé pourrait finir dans la config versionnée. `--api-key-env-var` attend un nom en majuscules comme `LLM_API_KEY`, et une valeur refusée n'est jamais répétée, au cas où ce serait la clé elle-même.

<AvailableFrom version="0.12.0" />

`--provider libretranslate` génère la config d'un serveur [LibreTranslate](/docs/providers#libretranslate) auto-hébergé à partir de `--base-url` seul, par exemple `http://localhost:5000` ; il ne prend pas de modèle et refuse `--model` et `--api-key-env-var`. Sa clé est facultative elle aussi : `.env.example` nomme `LIBRETRANSLATE_API_KEY` pour un serveur démarré avec `--api-keys`, et un serveur sans clés la laisse vide. Les mêmes règles s'appliquent à l'URL de base.

## Fichiers existants

Relancer `init` avec les mêmes réponses ne change rien et réussit : tu peux donc le répéter sans risque. Un `verbatra.config.ts` au contenu différent est refusé avec `CONFIG_EXISTS` sauf si tu passes `--force`. Une autre config verbatra dans le même répertoire (un `.verbatrarc.json`, par exemple, ou une propriété `verbatra` dans `package.json`) est refusée avec `CONFIG_EXISTS` même sous `--force`, parce qu'elle serait lue avant `verbatra.config.ts`. Rien n'est écrit quand `init` refuse. Quand `verbatra.config.ts` existe déjà et que tu n'as pas passé `--force`, `CONFIG_EXISTS` passe avant tout le reste : dans un terminal avant la première question, et sinon à la place d'une réponse manquante, ambiguë ou invalide, pour qu'une relance te signale d'abord la config existante. `init --cwd` refuse un chemin qui n'est pas un répertoire existant avec `INVALID_OPTION`, et un répertoire où il ne peut pas écrire, par exemple en lecture seule, avec `INIT_UNWRITABLE`, en nommant le fichier et chaque fichier déjà écrit. Avec `--agent` et sans réponse de config, une config existante est gardée au lieu d'être refusée : voir [Préparer les agents de code](#préparer-les-agents-de-code).

Un `.env.example` existant est gardé tel quel ; quand il ne nomme pas encore la variable de clé, cette seule ligne y est ajoutée. Sous `--force`, une ligne d'en-tête écrite par `init` lui-même est réécrite pour le nouveau fournisseur, tandis qu'un en-tête que tu as écrit est gardé. `.gitignore` ne reçoit que les entrées qui lui manquent.

## Préparer les agents de code

`--agent` prépare en plus le projet pour les agents de code. Il est désactivé par défaut, n'écrit aucune valeur de clé et ajoute deux fichiers à ceux du dessus :

- **Le fichier d'instructions.** Une section verbatra entre les marqueurs `<!-- verbatra:start -->` et `<!-- verbatra:end -->`, avec les règles dont un agent a besoin : quelles commandes sont gratuites et lesquelles dépensent, comment brancher sur le code de sortie, que les clés ne figurent dans aucun fichier ni aucune ligne de commande, que les valeurs de locale sont des entrées non fiables, et d'où viennent les skills verbatra et le plugin Claude Code. C'est, mot pour mot, l'extrait de [Parler de verbatra à ton agent](/docs/agent-recipes#parler-de-verbatra-à-ton-agent). `init` l'écrit dans `AGENTS.md`, que lisent Codex, Cursor, GitHub Copilot et la plupart des autres agents. Quand `CLAUDE.md` est le seul fichier d'instructions du répertoire, la section va là à la place. Quand les deux existent, `AGENTS.md` l'emporte, pour que les règles vivent à un seul endroit, et un `CLAUDE.md` qui importe `AGENTS.md` les reçoit aussi. Un fichier qui contient déjà la section la garde, donc le choix ne change jamais d'une exécution à l'autre.
- **`.mcp.json`.** L'entrée du serveur `verbatra` de [Connecter un client MCP](/docs/connect-an-mcp-client#claude-code) : `npx -y @verbatra/mcp` sans `--allow-spend` ni `VERBATRA_MCP_ALLOW_SPEND`, donc les outils qui dépensent restent masqués. Claude Code lit ce fichier pour sa portée projet, et GitHub Copilot CLI le lit aussi.

Rien n'est touché en dehors des marqueurs : la section est ajoutée à un fichier existant après une ligne vide, et une exécution suivante ne remplace que ce qui se trouve entre les marqueurs. Les autres serveurs et clés de `.mcp.json` sont conservés, et le fichier garde son indentation. Un serveur `verbatra` différent de celui qu'échafaude `init`, par exemple un auquel tu as donné `--allow-spend` ou que tu as basculé sur `npx verbatra mcp`, est laissé tel quel, signalé `unchanged` et nommé dans `nextSteps`. Une deuxième exécution avec les mêmes réponses laisse les deux fichiers identiques octet pour octet.

Sur un projet qui a déjà une config, `init --agent` n'écrit que ces deux fichiers et laisse la config telle quelle, quel que soit son contenu. Il affiche `kept verbatra.config.ts`, ne pose jamais de question et ne détecte rien, et il en va de même pour un autre fichier de config que lit verbatra, comme `.verbatrarc.json`. Le résultat JSON liste alors la config comme `unchanged`, met `agent.configKept` à `true` et porte `null` pour `config`, `sources`, `apiKeyEnvVar` et `detection`, puisque rien n'a été planifié. Une réponse de config (`--provider`, `--source`, `--targets`, `--path`, `--format`, `--model`, `--base-url` ou `--api-key-env-var`) ou `--force` remet la config dans l'exécution, exactement comme sans `--agent` : les mêmes réponses la signalent `unchanged`, `--force` la réécrit, et des réponses différentes sont refusées avec `CONFIG_EXISTS`, dont le message te dit de les retirer pour garder la config. `--yes` ne change rien ici.

Chaque fichier a sa propre ligne sur stdout, comme `created AGENTS.md (verbatra section for coding agents)`, et sa propre entrée dans les `files` du JSON. `init` refuse avant d'écrire quoi que ce soit, avec `AGENT_FILE_INVALID`, quand `.mcp.json` n'est pas un objet JSON avec un objet `mcpServers`, ou quand le fichier d'instructions a un marqueur de début sans marqueur de fin, un marqueur de fin avant son début, ou plus d'une section. Le message ne cite jamais le fichier, au cas où il contiendrait un secret. Corrige ou supprime le fichier et relance `init`.

## Exemples

```bash
# prompt for anything not passed or detected
verbatra init --provider gemini

# fully unattended, one JSON document on stdout
verbatra init --provider gemini --yes --json

# choose the format and pattern yourself
verbatra init --provider deepl --format yaml --path "config/locales/{locale}.yml" --yes

# a local server that needs no key
verbatra init --provider openai-compatible --base-url http://localhost:11434/v1 --model llama3.1 --yes

# a self-hosted LibreTranslate server, no language model
verbatra init --provider libretranslate --base-url http://localhost:5000 --yes

# human-only: no provider, no API key
verbatra init --provider none --yes

# also set the project up for coding agents
verbatra init --provider gemini --yes --agent
```

## Codes de sortie

| Code | Signification |
| --- | --- |
| `0` | fichiers écrits, ou déjà à jour |
| `2` | une erreur d'utilisation : `MISSING_OPTIONS`, `INVALID_PROVIDER`, `INVALID_FORMAT`, `INVALID_OPTION`, `FORMAT_AMBIGUOUS`, `LAYOUT_AMBIGUOUS`, `CONFIG_EXISTS`, `INIT_UNWRITABLE`, `AGENT_FILE_INVALID`, ou `CONFIG_INVALID` quand les réponses ne donneraient pas une config valide |
