---
title: verbatra doctor
description: Valida la configuración del proyecto sin llamar a un proveedor ni leer una clave de API.
---
<AvailableFrom version="0.9.0" />

Comprueba si un proyecto está bien configurado y recibe todos los problemas en un solo informe. `doctor` no construye ningún proveedor, no escribe ningún archivo y nunca lee el valor de una clave de API (solo `--live` envía una petición). Úsalo después de [`verbatra init`](/docs/cli/init) o cuando otro comando falle.

## Sinopsis

```bash
verbatra doctor [flags]
```

## Flags

| Flag | Argumento | Por defecto | Efecto |
| --- | --- | --- | --- |
| `--literals` | ninguno | desactivado | en lugar de revisar la configuración, busca strings visibles para el usuario escritos a mano en las raíces de código del [bloque `extract`](/docs/config-file#extract) (ver [Literales sin traducir](#literales-sin-traducir)) |
| `--locales` | ninguno | desactivado | tras las comprobaciones, lista por locale de destino el código enviado, el soporte del proveedor, el glosario y la formalidad (ver [Soporte de locales](#soporte-de-locales)) |
| `--live` | ninguno | desactivado | primero descarga la lista de idiomas actual del proveedor, sin gastar cuota de traducción; implica `--locales` |

También acepta los [flags globales](/docs/cli#flags-globales) `--cwd`, `--config` y `--json`. `--locales` y `--live` no se pueden combinar con `--literals` (`INVALID_OPTION`, salida `2`).

## Comportamiento

### Qué comprueba

<AvailableFrom version="0.12.0" />

Una ejecución de configuración informa de estas comprobaciones, en este orden. Plural rules, Plural completeness, Locale codes y Locale state son informativas y nunca fallan.

| Comprobación | Pasa cuando |
| --- | --- |
| Configuration | se encontró un archivo de configuración y pasa la validación |
| Format adapter | el `format` configurado se resuelve a un adaptador de archivos |
| Provider | el `provider.id` configurado se resuelve a una factoría de proveedor |
| API key environment variable | la variable de la que ese proveedor lee su clave está definida |
| Network policy | la [política de red](/docs/network-policy) efectiva permite el host del proveedor y cualquier proxy que usaría |
| Source locale file | el archivo de locale de origen existe en su ruta resuelta, es un archivo normal y se analiza con el formato configurado |
| Plural rules | siempre: nombra las versiones de ICU y CLDR en uso y cualquier locale de destino sin reglas de plural en ICU |
| Plural completeness | siempre: nombra cada plural de destino al que le falta una categoría CLDR que usa su idioma (diez como máximo; [`verbatra check`](/docs/cli/check#categorías-de-plural) los lista todos) |
| Locale codes | siempre: nombra cada código válido pero no canónico, como `en-us` o `iw`, con su forma canónica (ver [Códigos de locale](/docs/config-file#códigos-de-locale)) |
| Locale state | siempre: nombra cada locale con estado en el archivo de bloqueo, la caché o el archivo de procedencia que la configuración no lista, y si `translate` lo [traslada](/docs/the-lock-file#un-código-de-locale-reescrito) |
| Locale support | el proveedor admite la locale de origen y cada locale de destino (ver [Soporte de locales](#soporte-de-locales)) |

Cada comprobación se ejecuta aunque una anterior haya fallado. La única excepción es la configuración: si no se puede cargar, las comprobaciones que la necesitan aparecen como `[skip]` (`"status": "skipped"` en JSON). Una comprobación fallida lleva además un `fix`, un siguiente paso en imperativo que se imprime como línea `fix:` y viaja como `"fix"` en JSON, para que un agente actúe sin analizar `detail`.

Una ejecución con dos problemas:

```text output
verbatra doctor
  [ok  ] Configuration: Loaded /app/verbatra.config.ts.
  [ok  ] Format adapter: Format "i18next-json" resolves to an adapter.
  [ok  ] Provider: Provider "anthropic" resolves to a factory.
  [fail] API key environment variable: The ANTHROPIC_API_KEY environment variable is not set.
         fix: Set ANTHROPIC_API_KEY in the environment or in a .env file in the project directory.
  [ok  ] Network policy: any host (config: unset; VERBATRA_NETWORK_POLICY: unset). Provider "anthropic" connects to api.anthropic.com: permitted.
  [fail] Source locale file: The source locale file was not found at /app/locales/en.json.
         fix: Create the source locale file, or fix `files.pattern` and `sourceLocale` in the config so they point at it.
  ...
  [ok  ] Locale support: Provider "anthropic" is an LLM and accepts any locale (well-tested list of 2026-09-28).
2 problems found (run verbatra doctor again after fixing them)
```

### Claves y archivos

- La clave de API se comprueba **solo por nombre**: `doctor` pregunta si la variable está definida, nunca qué contiene. La variable de cada proveedor está en [Proveedores](/docs/providers).
- `openai-compatible` recurre a una clave de relleno, así que solo falla cuando la configuración nombra su propia variable en `provider.options.apiKeyEnvVar` y esa variable no está definida. `libretranslate` nunca hace fallar la comprobación, porque su clave es opcional.
- Con [`provider: { id: "none" }`](/docs/human-only-workflow), las comprobaciones Provider, API key y Network policy pasan, y Locale support se omite.
- Que falte un archivo de **destino** no es problema: `translate` lo crea. El archivo de **origen** se analiza, así que un directorio, un archivo vacío o un contenido mal formado la hacen fallar.
- `doctor` carga primero `.env.local` y luego `.env`, así que una clave en un archivo dotenv cuenta como definida. Con `--literals` no carga ninguno.

### Soporte de locales

<AvailableFrom version="0.12.0" />

La comprobación Locale support pregunta si el proveedor puede traducir cada locale configurada. DeepL y Google Cloud Translation se evalúan contra una tabla de idiomas fechada que verbatra incluye; un proveedor LLM acepta cualquier locale. Falla justo en la locale que [`verbatra translate`](/docs/cli/translate) rechazaría con `LOCALE_UNSUPPORTED_BY_PROVIDER` y, si no, pasa con avisos. [Soporte de idiomas](/docs/language-support#comprobar-el-soporte-antes-de-una-ejecución) explica los veredictos.

`--locales` imprime el veredicto por locale después de las comprobaciones:

```text output
  locale support (deepl, language table of 2026-09-28, static)
    en  sent as EN  source, supported
    de  sent as DE  supported  glossary: yes  formality: yes
    sv  sent as SV  supported  glossary: yes  formality: no
      warning [FORMALITY_UNSUPPORTED_BY_PROVIDER] Provider "deepl" has no formality control for "sv", so the configured formal tone is not applied and the provider's default register is used.
    chr  sent as CHR  unsupported  glossary: no  formality: no
```

Cada línea nombra la locale, el código que recibe el proveedor (tras [`localeMap`](/docs/providers#códigos-de-locale-enviados-al-proveedor), marcado con `(localeMap)`), el veredicto y si se aplican un glosario y un tono `formal` o `informal`. Un aviso es solo orientativo.

`--live` evalúa en cambio contra la lista actual del proveedor (DeepL `/v3/languages`, Cloud Translation `languages`, LibreTranslate `/languages`). Para LibreTranslate, que no incluye tabla, es la única forma de obtener un veredicto distinto de `unverified`. La petición solo se envía si la variable de la clave está definida (LibreTranslate no la necesita) y la [política de red](/docs/network-policy) permite el host; si no, o si falla, se usa la tabla incluida y una línea `live language list` explica por qué.

### Literales sin traducir

<AvailableFrom version="0.11.0" />

`--literals` encuentra strings visibles para el usuario que nunca llegaron a un catálogo. Recorre las raíces de código de tu [bloque `extract`](/docs/config-file#extract), lee tu código sin escribirlo nunca, no construye proveedor, no lee ninguna clave y no carga ningún `.env`. Solo se ejecutan dos comprobaciones: Configuration y Untranslated literals. Cada hallazgo nombra archivo, línea y columna, con los espacios colapsados, las referencias de caracteres de JSX decodificadas y 80 caracteres como máximo:

```text output
  [fail] Untranslated literals: Scanned 42 source files: 2 untranslated literals found (1 suppressed).
    src/components/Header.tsx:12:9  "Welcome back"
    src/pages/settings.tsx:40:22  "Save changes"
    suppressed (directive) src/pages/legal.tsx:8:5  "Acme Inc."
```

Se informa de: texto JSX en archivos `.tsx`, `.jsx` y `.js`, atributos JSX visibles para el usuario (`alt`, `title`, `placeholder`, `label`, `aria-label` y los demás `aria-*` con texto) y cualquier otro string de dos o más palabras.

Nunca se informa de:

- un string pasado a `t(...)`, `$t(...)`, `i18n.t(...)` o a un `t` renombrado de `useTranslation`, o renderizado dentro de `<Trans>` o `<Translation>`;
- claves de objeto, especificadores de import, nombres de clase, valores CSS, ids de test, `data-*` y atributos de id o palabra clave (`aria-describedby`, `aria-labelledby`, `aria-controls`, `rel`, `sandbox`, `allow`, `autoComplete`, `referrerPolicy`, `crossOrigin`), URLs y strings sin letras;
- literales en posición de tipo (el valor antes de `as` o `satisfies` sí se comprueba), mensajes de log, mensajes de error (`new ValidationError(...)`, `throw Error(...)`), operandos de comparación y template literals con una expresión;
- argumentos directos de `describe` (zod), `query`, `execute`, `prepare`, `format`, `parse`, `z.enum`, `setItem`, `getItem` y `removeItem`, y el primer argumento de `on`, `off`, `once`, `emit`, `addEventListener` y de un `get` o `set` sobre un objeto; el texto más anidado y los mensajes pasados a funciones como `setError` sí se informan;
- todo lo que esté en archivos de test, story, declaración o configuración.

Para retener un literal, pon `// verbatra-ignore-next-line` encima (en JSX, `{/* verbatra-ignore-next-line */}`) o `// verbatra-ignore-line` al final de su línea. Una directiva de siguiente línea apunta a la siguiente línea con código y, en una etiqueta JSX de apertura, a todos sus atributos. Un string que vale en todas partes lo añades a `extract.literals.ignore` con las referencias decodificadas (`Tom & Jerry`). Los literales suprimidos se siguen listando con su motivo.

La comprobación falla con un hallazgo y con un archivo que no pudo abrir, leer hasta el final o que consideró demasiado grande (el escaneo continúa). Un proyecto sin bloque `extract` la hace fallar.

### Salida JSON

Con `--json`, el [sobre](/docs/cli/output#salida-json) lleva el informe en `result`. `ok` es verdadero exactamente cuando el comando termina con `0`:

```ts
interface DoctorResult {
  ok: boolean;                 // true exactly when the command exits 0
  checks: DoctorCheck[];       // one per check, always in the same order
  literals?: LiteralScan;      // only with --literals: findings, suppressed, diagnostics
  locales?: LocaleCapabilityReport; // per-locale provider support, with or without --locales
}

interface DoctorCheck {
  id:
    | "config"
    | "format-adapter"
    | "provider"
    | "api-key"
    | "network-policy"
    | "source-file"
    | "plural-rules"
    | "plural-completeness"
    | "locale-codes"
    | "locale-state"
    | "locales"
    | "untranslated-literals";
  title: string;               // stable, human-readable name
  status: "pass" | "fail" | "skipped";  // only "fail" makes ok false
  detail: string;              // why it reached that verdict; never an API key value
  fix?: string;                // the next step, only on a failed check
}

interface LocaleCapabilityReport {
  provider: string;
  coverage: "listed" | "open";       // "open" for an LLM provider
  tableVersion: string;              // the table's date (YYYY-MM-DD)
  tableOrigin: "static" | "live";    // "live" only when --live fetched the list
  live?: { status: "refreshed" | "skipped" | "failed"; detail: string }; // only with --live
  source: {
    locale: string;
    providerCode: string;
    mapped: boolean;
    support: "supported" | "unverified" | "unsupported";
    warnings: { code: string; message: string }[];
  };
  locales: {
    locale: string;
    providerCode: string;            // the code the provider receives
    mapped: boolean;                 // true when localeMap set providerCode
    support: "supported" | "unverified" | "unsupported";
    glossary: boolean;
    formality: boolean;
    warnings: { code: string; message: string }[];
  }[];
}
```

`result.locales` no aparece cuando no se pudo cargar la configuración, con un proveedor desconocido ni con `provider: { id: "none" }`.

### Información en el terminal

<AvailableFrom version="0.12.0" />

Mientras se ejecuta, `doctor` muestra una línea en stderr (`checking the setup`, o `scanning the source for literals` con un recuento de archivos), que `--quiet` omite. El informe se queda en stdout. Consulta [Salida en el terminal](/docs/cli/output#salida-en-el-terminal).

## Ejemplos

```bash
# report every setup problem at once
verbatra doctor

# validate a project in another directory, with an explicit config
verbatra doctor --cwd apps/web --config verbatra.config.ts

# machine-readable report for a CI preflight step
verbatra doctor --json

# list hardcoded user-facing strings, with no key set
verbatra doctor --literals

# what the provider supports for each target locale
verbatra doctor --locales

# the same, against the provider's current language list
verbatra doctor --live
```

## Códigos de salida

| Código | Significado |
| --- | --- |
| `0` | todas las comprobaciones pasaron |
| `1` | al menos una comprobación falló, incluida una locale no admitida; con `--literals`, se encontró un literal o no se pudo escanear un archivo |
| `2` | no pudo ejecutarse: un error de uso o una ruta `--config` explícita que no existe |

Una configuración que la búsqueda no encuentra, o que no pasa la validación, es una comprobación fallida (salida `1`), porque informar de ello es justo la tarea del comando. Consulta [el contrato de códigos de salida](/docs/cli/output#códigos-de-salida).
