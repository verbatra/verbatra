`@verbatra/cli` liefert das `verbatra`-Binary, einen dünnen Wrapper über [`@verbatra/sdk`](/docs/sdk). Diese Befehle erledigen die Arbeit:

<Cards>
  <Card title="init" href="/docs/cli/init">Eine verbatra-Konfiguration und `.env.example` für dieses Projekt anlegen.</Card>
  <Card title="extract" href="/docs/cli/extract">Deinen Anwendungscode nach Übersetzungsaufrufen durchsuchen und die neuen Keys in der Quell-Locale-Datei ergänzen.</Card>
  <Card title="translate" href="/docs/cli/translate">Jedes Ziel-Locale einmal übersetzen, dann beenden.</Card>
  <Card title="watch" href="/docs/cli/watch">Bei jeder Quelländerung neu übersetzen, bis unterbrochen wird.</Card>
  <Card title="check" href="/docs/cli/check">Melden, welche Keys pro Locale fehlen oder veraltet sind, nur lesend.</Card>
  <Card title="diff" href="/docs/cli/diff">Die genauen Keys pro Locale listen, die hinzugefügt oder neu übersetzt würden oder verwaist sind, nur lesend.</Card>
  <Card title="report" href="/docs/cli/report">Einen nur lesenden Bericht ausgeben: `report provenance` listet, welche Übersetzungen eine Maschine geschrieben und welche eine Person geprüft hat.</Card>
  <Card title="doctor" href="/docs/cli/doctor">Die Projekteinrichtung prüfen und alle Probleme auf einmal melden, ohne einen Provider aufzurufen.</Card>
  <Card title="pseudo" href="/docs/cli/pseudo">Aus den Quellstrings eine Pseudo-Locale erzeugen, ohne einen Provider aufzurufen.</Card>
  <Card title="types" href="/docs/cli/types">TypeScript-Deklarationen für deine Katalog-Keys und ihre Nachrichtenargumente erzeugen, ohne einen Provider aufzurufen.</Card>
  <Card title="export" href="/docs/cli/export">Unübersetzte Strings für eine menschliche Übersetzerin exportieren, als Excel-Arbeitsmappe, als je eine CSV- oder TSV-Datei pro Locale oder als je eine XLIFF-Datei pro Locale für ein CAT-Tool.</Card>
  <Card title="import" href="/docs/cli/import">Eine ausgefüllte Arbeitsmappe oder Datei mit Trennzeichen zurück in die Locale-Dateien importieren.</Card>
  <Card title="tmx" href="/docs/cli/tmx">Einen TMX-Übersetzungsspeicher aus einem anderen Tool in den Speicher dieses Projekts importieren oder den Speicher dieses Projekts als TMX-Datei exportieren.</Card>
  <Card title="studio" href="/docs/cli/studio">Verbatra Studio starten, das lokale Übersetzungs-Dashboard.</Card>
  <Card title="mcp" href="/docs/cli/mcp">Einen stdio-MCP-Server starten, der die Tools von verbatra für einen MCP-Client bereitstellt.</Card>

## Installieren und aufrufen

Installiere `@verbatra/cli` als Dev-Dependency und starte das Binary anschließend über deinen Paketmanager:

| Paketmanager | Installation | Aufruf |
| --- | --- | --- |
| npm | `npm install --save-dev @verbatra/cli` | `npx verbatra <command>` |
| pnpm | `pnpm add --save-dev @verbatra/cli` | `pnpm verbatra <command>` (oder `pnpm exec verbatra <command>`) |
| yarn | `yarn add --dev @verbatra/cli` | `yarn verbatra <command>` |
| bun | `bun add --dev @verbatra/cli` | `bun run verbatra <command>` |

Du brauchst Node.js `>=22.14.0`.

Willst du einen Befehl vor der Installation ausprobieren? `npx @verbatra/cli <command>` (npm) oder `pnpm dlx @verbatra/cli <command>` (pnpm) funktionieren beide ohne vorherige lokale Installation.

## Globale Flags

Diese Flags bedeuten bei jedem Befehl, der sie nimmt, dasselbe. Die Befehlsseiten führen deshalb nur ihre eigenen Flags auf. Die letzte Spalte nennt die Befehle, die ein Flag nicht nehmen.

| Flag | Argument | Standard | Wirkung | Nicht bei |
| --- | --- | --- | --- | --- |
| `--cwd` | `<path>` | aktuelles Verzeichnis | liest Konfiguration und Locale-Dateien aus diesem Verzeichnis; `init` schreibt seine Dateien dorthin | keinem |
| `--config` | `<path>` | danach suchen | lädt diese Konfigurationsdatei, statt nach einer zu suchen; siehe die [Suchreihenfolge](/docs/config-file) | `init` |
| `--json` | keins | aus | gibt einen maschinenlesbaren [Envelope](/docs/cli/output#json-ausgabe) auf stdout aus, eine Zeile pro Datensatz; Fehler gehen weiter nach stderr | `mcp`, `studio` |
| `-q`, `--quiet` | keins | aus | gibt nur Ergebnisse, Warnungen und Fehler aus: keinen Fortschritt, keine Hinweise, keine Infozeilen; wirkt vor oder nach dem Befehlsnamen | keinem |
| `--no-color` | keins | Farbe im Terminal | färbt die Ausgabe nie ein; siehe [Terminalausgabe](/docs/cli/output#terminalausgabe) | keinem |
| `-h`, `--help` | keins | aus | gibt die Hilfe des Programms oder des Befehls aus und endet mit `0` | keinem |
| `-V`, `--version` | keins | aus | gibt die Version der CLI aus und endet mit `0` | keinem |

Ein unbekannter Befehl oder ein unbekanntes Flag endet mit `2`, ebenso ein nacktes `verbatra` ohne Befehl: Es gibt die Hilfe auf stderr aus und schlägt `verbatra init` vor, wenn keine Konfiguration gefunden wird. `mcp` schreibt nie auf stdout, weil stdout sein Protokollkanal ist, und lehnt `--json` deshalb mit `USAGE_ERROR` ab. Ab 0.12.0 endet ein `--cwd`, das kein vorhandenes Verzeichnis nennt, bei jedem Befehl mit `2` und [`INVALID_OPTION`](/docs/error-codes#invalid_option), bevor etwas gelesen oder geschrieben wird.

## Umgebungsdateien

`translate`, `watch`, `doctor`, `studio` und `mcp` laden `.env.local` und dann `.env` aus dem Arbeitsverzeichnis, bevor sie laufen. `doctor --literals` ist die Ausnahme: Dieser Aufruf liest keinen API-Key und lädt deshalb keine der beiden Dateien. Eine bereits in deiner echten Umgebung gesetzte Variable gewinnt immer, und ein Wert in `.env.local` gewinnt gegen dieselbe Variable in `.env`. API-Keys werden nur aus der Umgebung gelesen, nie aus der Konfigurationsdatei oder einem Flag: siehe [Provider](/docs/providers). Die nur lesenden Befehle (`check`, `diff`, `report`), die Übergabe-Befehle (`export`, `import`), `extract`, `init`, `pseudo`, `types` und `tmx` rufen nie einen Provider auf und laden keine `.env`-Dateien.
