`@verbatra/cli` liefert das `verbatra`-Binary, einen dünnen Wrapper über [`@verbatra/sdk`](/docs/sdk). Vierzehn Befehle erledigen die Arbeit:

| Befehl | Was er tut |
| --- | --- |
| [`init`](/docs/cli/init) | eine verbatra-Konfiguration und `.env.example` für dieses Projekt anlegen |
| [`extract`](/docs/cli/extract) | deinen Anwendungscode nach Übersetzungsaufrufen durchsuchen und die neuen Keys in der Quell-Locale-Datei ergänzen |
| [`translate`](/docs/cli/translate) | jedes Ziel-Locale einmal übersetzen, dann beenden |
| [`watch`](/docs/cli/watch) | bei jeder Quelländerung neu übersetzen, bis unterbrochen wird |
| [`check`](/docs/cli/check) | melden, welche Keys pro Locale fehlen oder veraltet sind, nur lesend |
| [`diff`](/docs/cli/diff) | die genauen Keys pro Locale listen, die hinzugefügt oder neu übersetzt würden oder verwaist sind, nur lesend |
| [`doctor`](/docs/cli/doctor) | die Projekteinrichtung prüfen und alle Probleme auf einmal melden, ohne einen Provider aufzurufen |
| [`pseudo`](/docs/cli/pseudo) | aus den Quellstrings eine Pseudo-Locale erzeugen, ohne einen Provider aufzurufen |
| [`types`](/docs/cli/types) | TypeScript-Deklarationen für deine Katalog-Keys und ihre Nachrichtenargumente erzeugen, ohne einen Provider aufzurufen |
| [`export`](/docs/cli/export) | unübersetzte Strings für eine menschliche Übersetzerin exportieren, als Excel-Arbeitsmappe oder als je eine CSV- oder TSV-Datei pro Locale |
| [`import`](/docs/cli/import) | eine ausgefüllte Arbeitsmappe oder Datei mit Trennzeichen zurück in die Locale-Dateien importieren |
| [`tmx`](/docs/cli/tmx) | einen TMX-Übersetzungsspeicher aus einem anderen Tool in den Speicher dieses Projekts importieren oder den Speicher dieses Projekts als TMX-Datei exportieren |
| [`studio`](/docs/cli/studio) | Verbatra Studio starten, das lokale Übersetzungs-Dashboard |
| [`mcp`](/docs/cli/mcp) | einen stdio-MCP-Server starten, der die Tools von verbatra für einen MCP-Client bereitstellt |

## Installieren und aufrufen

Installiere `@verbatra/cli` als Dev-Dependency und starte das Binary anschließend über deinen Paketmanager:

| Paketmanager | Installation | Aufruf |
| --- | --- | --- |
| npm | `npm install --save-dev @verbatra/cli` | `npx verbatra <command>` |
| pnpm | `pnpm add --save-dev @verbatra/cli` | `pnpm verbatra <command>` (oder `pnpm exec verbatra <command>`) |
| yarn | `yarn add --dev @verbatra/cli` | `yarn verbatra <command>` |
| bun | `bun add --dev @verbatra/cli` | `bun run verbatra <command>` |

Du brauchst Node.js `>=22.14.0`.

Willst du einen Befehl vor der Installation ausprobieren? `npx @verbatra/cli <command>` (npm) oder `pnpm dlx @verbatra/cli <command>` (pnpm) funktionieren beide ohne vorherige lokale Installation.

## Gemeinsame Konventionen

- `--cwd <path>` löst die Konfiguration und die Locale-Dateien von diesem Verzeichnis statt vom aktuellen aus auf. Jeder Befehl akzeptiert es.
- `--config <path>` lädt diese Konfigurationsdatei, statt eine zu suchen. Jeder Befehl außer `init` akzeptiert es; die Suchreihenfolge steht in [Konfigurationsdatei](/docs/config-file).
- `--json` gibt einen maschinenlesbaren [Envelope](/docs/ci-and-exit-codes#json-ausgabe) auf stdout aus, eine Zeile pro Datensatz, und hält stdout sauber zum Weiterleiten.
  - Verzweige auf sein `ok`-Feld: ein Erfolg trägt die Daten des Befehls unter `result`, ein fehlgeschlagener Lauf trägt denselben stabilen Fehlercode, den auch die stderr-Zeile nennt. Die menschenlesbare Fehlerzeile geht in beiden Fällen auf stderr.
  - `extract`, `translate`, `watch`, `check`, `diff`, `doctor`, `pseudo`, `types`, `export`, `import`, `tmx` und `init` unterstützen es; `studio` und `mcp` nicht.
  - `mcp` schreibt überhaupt nichts auf stdout, da stdout der MCP-Protokollkanal ist; siehe [`verbatra mcp`](/docs/cli/mcp).
- `--help` und `--version` geben ihre Ausgabe aus und beenden sich mit `0`. Ein unbekannter Befehl oder ein unbekanntes Flag beendet sich mit `2`.

## Terminalausgabe

<AvailableFrom version="0.12.0" />

Ergebnisse gehen auf stdout. Fortschritt, Hinweise, Tipps, Warnungen und Fehler gehen auf stderr, und verbatra passt sie daran an, wohin stderr geht:

- In einem interaktiven Terminal sind feste Labels wie `error`, `[ok]` und `next:` eingefärbt, und ein Schritt, der länger als 300 ms dauert, zeigt einen ASCII-Spinner (`| / - \`).
- Wenn stderr umgeleitet oder in eine Pipe geschrieben wird, `CI` auf einen anderen Wert als `0` oder `false` gesetzt ist oder `TERM` den Wert `dumb` hat, besteht die Ausgabe aus schlichten, nur angehängten Zeilen ohne Farbe und ohne Animation.
- `--json` fügt nie Farbe, Animation oder neue Zeilen hinzu: stdout und stderr bleiben genau so, wie unter [JSON-Ausgabe](/docs/ci-and-exit-codes#json-ausgabe) beschrieben.

| Flag oder Variable | Wirkung |
| --- | --- |
| `-q`, `--quiet` | gibt nur Ergebnisse, Warnungen und Fehler aus: lässt Fortschrittszeilen, `next:`-Tipps und informative stderr-Zeilen weg, während die Ergebniszusammenfassung samt ihren Hinweisen bleibt. Es wirkt vor oder nach dem Befehlsnamen |
| `--no-color` | färbt die Ausgabe nie ein |
| `NO_COLOR`, `NODE_DISABLE_COLORS`, `VERBATRA_NO_COLOR` | jeder nicht leere Wert schaltet die Farbe ab; `VERBATRA_NO_COLOR` übersteuert auch `FORCE_COLOR` |
| `FORCE_COLOR` | `1`, `2`, `3`, `true` oder ein leerer Wert schaltet die Farbe ein, auch wenn stderr kein Terminal ist, und `0` schaltet sie ab; `--no-color` und `VERBATRA_NO_COLOR` haben trotzdem Vorrang |
| `VERBATRA_NO_SPINNER` | jeder nicht leere Wert ersetzt den Spinner durch statische Zeilen `label... done (1.2s)`, für Screenreader und Terminalaufzeichnungen |

Statuswörter sind reines ASCII (`[ok]`, `[warn]`, `[fail]`, `[skip]`), damit die Ausgabe in jedem Terminal und Log gleich lesbar ist. Jede Zeile durchläuft dieselbe Schlüsselschwärzung wie die übrige Ausgabe, und eingefärbt werden nur die festen Labels, nie ein Schlüssel, ein Pfad oder eine Meldung.

## Umgebungsdateien

`translate`, `watch`, `doctor`, `studio` und `mcp` laden `.env.local` und dann `.env` aus dem Arbeitsverzeichnis, bevor sie laufen. `doctor --literals` ist die Ausnahme: Dieser Aufruf liest keinen API-Key und lädt deshalb keine der beiden Dateien. Eine bereits in deiner echten Umgebung gesetzte Variable gewinnt immer. API-Keys werden nur aus der Umgebung gelesen, nie aus der Konfigurationsdatei oder einem Flag: siehe [Provider](/docs/providers). Die nur lesenden Befehle (`check`, `diff`), die Übergabe-Befehle (`export`, `import`), `extract`, `pseudo`, `types` und `tmx` rufen nie einen Provider auf und laden keine `.env`-Dateien.

## Exit-Codes

Der Exit-Code ist der Vertrag, auf den ein CI-Schritt oder Skript verzweigt:

| Code | Bedeutung |
| --- | --- |
| `0` | Erfolg (auch `--help` und `--version`) |
| `1` | `translate` oder `import` lief durch, aber einige Locales schlugen fehl oder blieben unvollständig, `check` fand ein Locale, das nicht synchron ist, `diff` fand ausstehende Änderungen (oder mit `--unused` fand ein vollständiger Scan einen ungenutzten Quell-Key), `doctor` fand ein Einrichtungsproblem oder mit `--literals` ein unübersetztes Literal, oder `types --check` fand die committete Deklaration veraltet |
| `2` | konnte nicht laufen: ein Fehler des gesamten Laufs (Konfiguration, Quelle, Provider, Lock) oder ein Verwendungsfehler |
| `3` | `translate` in einem [rein menschlichen](/docs/human-only-workflow) Projekt (`provider: { id: "none" }`) lief sauber durch, hat aber Keys für eine menschliche Übersetzung übrig gelassen |
| `130` | `translate` oder `import` wurde mit Ctrl-C (SIGINT) abgebrochen, nachdem die Schreibsperren freigegeben waren, oder `watch`, `studio` oder `mcp` wurde durch einen zweiten Interrupt zwangsbeendet |
| `143` | `translate` oder `import` wurde mit SIGTERM beendet, nachdem die Schreibsperren freigegeben waren |

Jede Befehlsseite erklärt, wie diese Codes auf den jeweiligen Befehl zutreffen. Wie du sie in eine Pipeline einbaust, steht in [CI und Exit-Codes](/docs/ci-and-exit-codes).
