---
title: verbatra translate
description: Übersetze jede Ziel-Locale einmal; danach beendet sich der Befehl.
---
Führe genau einen Übersetzungsdurchlauf über jede Ziel-Locale aus; danach beendet sich der Befehl. `translate` liest die Quell-Locale, vergleicht sie mit der [Lock-Datei](/docs/the-lock-file), schickt nur die neuen oder geänderten Strings an den Provider, führt die [Integritätsprüfungen](/docs/translation-safety) aus, schreibt die Locale-Dateien und aktualisiert das Lock. Was noch aktuell ist, wird nie erneut gesendet; du zahlst also nie zweimal für einen unveränderten String.

## Synopsis

```bash
verbatra translate [flags]
```

## Flags

| Flag | Argument | Standard | Wirkung |
| --- | --- | --- | --- |
| `--cwd` | `<path>` | aktuelles Verzeichnis | Konfiguration und Locale-Dateien von diesem Verzeichnis aus auflösen |
| `--config` | `<path>` | wird gesucht | diese Konfigurationsdatei laden, statt eine zu suchen |
| `--locales` | `<list>` | jede konfigurierte Ziel-Locale | nur diese kommagetrennte Teilmenge übersetzen; eine nicht konfigurierte Locale lässt den Lauf mit `UNKNOWN_LOCALE` scheitern, bevor irgendetwas gelesen oder Geld ausgegeben wird, und eine leere Liste ist ein Verwendungsfehler, Exit `2` |
| `--dry-run` | keins | aus | Änderungen vorab ansehen, ohne einen Provider aufzurufen oder Dateien zu schreiben (kein API-Key nötig) |
| `--prune` | keins | die `prune`-Option der Konfiguration, sonst aus | verwaiste Keys (in einer Zieldatei, aber nicht in der Quelle) aus der geschriebenen Datei und dem Lock entfernen |
| `--lock-timeout` | `<seconds>` | `600` | wie lange auf eine gehaltene Schreibsperre einer Locale gewartet wird, bevor der Lauf scheitert; muss eine positive Ganzzahl an Sekunden ohne Einheit und höchstens `3600` sein (ein Wert wie `60s`, `0`, `-1` oder `7200` ist ein Verwendungsfehler, Exit `2`) |
| `--concurrency` | `<n>` | `1` | bis zu `n` Ziel-Locales gleichzeitig übersetzen; muss eine positive Ganzzahl von höchstens `100` sein |
| `--max-tokens` | `<n>` | das `maxTokens` der Konfiguration | eine harte Token-Obergrenze nur für diesen Lauf; setzt die Konfiguration ebenfalls `maxTokens`, gilt der niedrigere der beiden Werte; muss eine positive Ganzzahl sein (ein Wert wie `10k` oder `0` ist ein Nutzungsfehler, Exit `2`) |
| `--no-cache` | keins | aus (Cache an) | den lokalen [Übersetzungsspeicher-Cache](/docs/the-cache) (`verbatra.cache.json`) für diesen Lauf umgehen |
| `--include-human` | keins | aus | für diesen Lauf auch veraltete Keys neu übersetzen, deren Wert ein Mensch geschrieben, importiert oder außerhalb von verbatra geändert hat (`humanEdits: "overwrite"`); [gepinnte Keys](/docs/protecting-human-translations#keys-pinnen) bleiben unangetastet |
| `--json` | keins | aus | einen [JSON-Envelope](/docs/ci-and-exit-codes#json-ausgabe) auf stdout ausgeben, der die Lauf-Zusammenfassung unter `result` trägt (die [`RunSummary`-Form](/docs/sdk)), oder bei einem fehlgeschlagenen Lauf den Fehlercode; die menschenlesbare Fehlerzeile geht weiter auf stderr |
| `--estimate` | keins | aus | schätzen, was der Lauf senden und was er kosten würde, und sich dann beenden, ohne einen Provider aufzurufen; impliziert `--dry-run`, es wird also kein API-Key gebraucht |

Standardmäßig löscht ein Lauf nichts: verwaiste Keys werden gemeldet und bleiben stehen. `--prune` entfernt genau diese Keys und sonst nichts und überschreibt für diesen Lauf die `prune`-Option der Konfiguration. Vor dem Lauf lädt `translate` `.env.local` und dann `.env` aus dem Arbeitsverzeichnis; eine bereits in der echten Umgebung gesetzte Variable gewinnt.

`--dry-run` konstruiert überhaupt keinen Provider, braucht also keinen API-Key und kann keine Kosten verursachen: Es liest Quell- und Zieldateien, vergleicht sie mit der Lock-Datei und meldet genau, was ein echter Lauf ändern würde. Es schreibt nichts (keine Locale-Datei, keine Lock-Aktualisierung, keinen Run-Status-Schnappschuss), es liest und schreibt den Cache nicht und es nimmt keine Schreibsperre pro Locale, wartet also nie auf einen bereits laufenden Lauf. Das Laden von `.env` oben passiert bei einem Dry Run weiterhin; es gibt nur keinen Key zu lesen. Damit ist es ein vollwertiger Weg, verbatra an einem echten Projekt auszuprobieren, bevor du ein Provider-Konto anlegst.

In einem [rein menschlichen](/docs/human-only-workflow) Projekt (`provider: { id: "none" }`) ist ein Dry Run die einzige Ausnahme von der Cache-Regel: Er liest das Translation Memory, schreibt aber weiterhin nichts, sodass sein Plan dieselben `cacheHits`- und `unfilled`-Keys auflistet wie ein echter Lauf, und `--estimate` meldet nichts zu senden und nichts zu bezahlen (`estimated spend: none, machine translation is disabled by policy`). Eine Schätzung endet wie der Dry Run, der sie ist: mit `3`, wenn Keys auf einen Menschen warten, sodass ein Skript aus beiden denselben Code liest.

<AvailableFrom version="0.12.0" />

`--estimate` ergänzt diesen Dry Run um eine Kostenschätzung vor dem Lauf: wie viele Keys gesendet würden, in wie viele Provider-Requests sie aufgeteilt würden und welche Menge der konfigurierte Provider tatsächlich abrechnet (geschätzte Prompt- und Antwort-Tokens bei einem LLM, geschätzte Quellzeichen bei DeepL oder Google Cloud Translation gar keine Kosten bei einem selbst gehosteten `openai-compatible`-Endpunkt und nichts bei einem rein menschlichen Projekt). Es impliziert `--dry-run`, kostet also nichts und schreibt nichts. Ein Geldbetrag erscheint nur, wenn die Konfiguration einen `rates`-Block hat, der den konfigurierten Provider und das Modell abdeckt; ohne einen solchen wird die Menge trotzdem gemeldet und der fehlende Raten-Key benannt, statt Kosten von `0.00` zu erfinden. Jede Zahl wird neben dem Datum ausgegeben, an dem diese Raten gelesen wurden, und neben einer Zeile, die benennt, was die Schätzung auslässt. Siehe [Kosten abschätzen](/docs/estimating-cost).

<AvailableFrom version="0.11.0" />

`--locales de,fr` grenzt den Lauf auf eine Teilmenge der konfigurierten Ziele ein. Ausgelassene Locales bleiben unberührt: ihre Dateien, ihre Lock-Einträge und ihre Cache-Einträge bleiben, wie sie waren. Es ist das Flag für ein ratenbegrenztes kostenloses Kontingent, bei dem eine Locale nach der anderen der einzige Weg durch ist, und zugleich der schnellste Weg, eine einzelne unvollständig gebliebene Locale erneut laufen zu lassen. Der Run-Status-Schnappschuss beschreibt immer nur den jüngsten Lauf; ein Teilmengen-Lauf grenzt ihn also auf diese Teilmenge ein.

`--lock-timeout` stellt ein, wie lange eine Locale auf eine umkämpfte [Schreibsperre](/docs/the-lock-file) wartet, bevor diese Locale mit `LOCK_CONTENDED` scheitert. Die anderen Locales laufen trotzdem, und der Befehl endet mit `1`, mit dem Code in der Zusammenfassung dieser Locale, wie bei jeder anderen fehlgeschlagenen Locale. Erhöhe es, wenn ein anderer Lauf die Sperre berechtigt eine Weile hält, senke es, um in CI schnell zu scheitern. Eine Sperre, die ein auf dieser Maschine nicht mehr laufender verbatra-Prozess hinterlassen hat, wird sofort übernommen statt abgewartet, und Ctrl-C oder SIGTERM gibt die Sperren des Laufs frei, bevor der Befehl mit `130` endet (`143` bei SIGTERM). Es begrenzt nur dieses Warten, das vor jedem Provider-Aufruf passiert: Ist die Datei einer Locale erst geschrieben, wartet das Festhalten in der Lock-Datei bis zum Standard von zehn Minuten, egal was `--lock-timeout` sagt, damit eine geschriebene Datei nie unerfasst bleibt (siehe [Die Schreibsperre](/docs/the-lock-file#die-schreibsperre)).

<AvailableFrom version="0.12.0" />

`--max-tokens` begrenzt, was ein einzelner Lauf ausgeben darf, ohne dass du die Konfiguration anfasst. Es ist immer ein harter Stopp: Eine Provider-Anfrage, die die Obergrenze überschreiten würde, wird zurückgehalten statt gesendet, egal was `budgetBehavior` sagt, und ihre Keys stehen in der Zusammenfassung als `budgetWithheld`. Die Obergrenze wird genauso gezählt wie ein konfiguriertes [`maxTokens`-Budget](/docs/config-file#maxtokens-und-budgetbehavior). Setzt die Konfiguration ebenfalls `maxTokens`, gilt der niedrigere der beiden Werte, das Flag kann das Budget also verschärfen, aber nie lockern. Ein Lauf, den die Obergrenze abgebrochen hat, endet mit Exit `1`, wie es eine teilweise übersetzte Locale immer tut. Führe vorher `--estimate` aus, um eine sinnvolle Zahl zu wählen.

`--concurrency` übersetzt mehrere Ziel-Locales parallel, um ein großes Projekt schneller abzuschließen. Es wird mit Exit `2` abgelehnt, wenn ein Token-Budget gilt, aus dem `maxTokens` der Konfiguration oder aus `--max-tokens`, weil die Obergrenze zwar weiterhin gälte, aber davon abhinge, in welcher Reihenfolge sich die Locales verschränken, welche von ihnen ihre restliche Arbeit verliert; dasselbe Projekt ergäbe also nicht zweimal denselben Lauf (ein Dry Run ist ausgenommen). Taucht ein Fehler des gesamten Laufs (in der Praxis eine beschädigte Lock-Datei) auf, während bereits Locales laufen, wird keine weitere Locale mehr gestartet, und die laufenden schließen ab und geben ihre Schreibsperren frei, bevor der Befehl mit Exit `2` endet; der Lauf lässt also keine Sperre zurück, auf die der nächste warten müsste. Während ein Lauf fortschreitet, wird der Fortschritt auf stderr ausgegeben (eine Zeile pro Locale-Start, Provider-Sub-Batch und Locale-Ende), sodass stdout bei einem `--json`-Lauf eine einzige saubere Zusammenfassung bleibt. `--no-cache` überspringt den [Übersetzungsspeicher-Cache](/docs/the-cache) für den Lauf und macht genau die Provider-Aufrufe, die es ohne vorhandenen Cache machen würde.

## Beispiele

```bash
# translate once using the config it finds
verbatra translate

# preview the keys that would be pruned, spending nothing
verbatra translate --prune --dry-run

# one locale at a time, which is what a rate-limited free tier needs
verbatra translate --locales de

# size and price the run without spending anything
verbatra translate --estimate

# stop before the run passes 50000 tokens
verbatra translate --max-tokens 50000

# also retranslate stale keys a person wrote
verbatra translate --include-human
```

## Exit-Codes

| Code | Bedeutung |
| --- | --- |
| `0` | jede Ziel-Locale kam vollständig durch |
| `1` | der Lauf lief durch, aber eine oder mehrere Locales schlugen fehl oder blieben unvollständig |
| `2` | konnte nicht laufen: ein Fehler des gesamten Laufs (Konfiguration, Quelle, Format, Provider oder eine beschädigte Lock-Datei) oder ein Verwendungsfehler |
| `3` | rein menschliches Projekt (`provider: { id: "none" }`): der Lauf lief sauber durch, aber Keys warten auf eine menschliche Übersetzung |

<AvailableFrom version="0.9.0" />

Eine fehlschlagende Locale ist nicht fatal: der Lauf läuft zu Ende, endet mit `1`, und das Detail pro Locale steht in der Zusammenfassung. Eine **unvollständige** Locale endet ebenfalls mit `1`. Das ist eine Locale, deren Datei geschrieben wurde, der aber weiterhin Keys fehlen, typischerweise weil ein Provider-Sub-Batch fehlschlug oder das Integritäts-Gate eine Übersetzung abgelehnt hat; sie als Erfolg auszuliefern, würde eine halb übersetzte Datei unbemerkt in deinem Repository liegen lassen. Eine Locale, deren Schreibsperre über `--lock-timeout` hinaus umkämpft blieb, scheitert mit `LOCK_CONTENDED` und endet genauso mit `1`.

Die menschenlesbare Ausgabe listet jeden Key, den das [Integritäts-Gate](/docs/translation-safety) abgelehnt hat, unter `integrity-withheld` auf, einen pro Zeile, mit dem Grund (`placeholder`, `markup`, `icu`, `degenerate` oder `empty`) und, wo die Prüfung sie benennen kann, den schuldigen Platzhaltern, Tags oder ICU-Plural-Zweigen. Eine Locale, deren Keys alle abgelehnt wurden, zeigt `failed`, gefolgt von denselben Zählern wie jede andere Locale. Mit `--json` trägt jede Locale dieselben Gründe in `integrityRefusals`.

<AvailableFrom version="0.12.0" />

Exit-Code `3` gibt es nur in einem [rein menschlichen](/docs/human-only-workflow) Projekt. Dort wird kein Provider aufgerufen: Keys, die das Translation Memory abdeckt, werden geschrieben, und jeder andere fehlende oder geänderte Key wird als `unfilled` gemeldet und nicht angefasst. Eine fehlgeschlagene oder unvollständige Locale hat weiterhin Vorrang und endet mit `1`. Gib die `unfilled`-Keys mit [`verbatra export`](/docs/cli/export) weiter.

<AvailableFrom version="0.12.0" />

Veraltete Keys, deren Wert ein Mensch geschrieben, importiert oder außerhalb von verbatra geändert hat, bleiben standardmäßig erhalten: Sie werden als `protected` gelistet, gehen nicht an den Provider und bleiben für `verbatra check` veraltet. Eine Zeile auf stderr sagt, wie viele übrig blieben, und verweist auf `--include-human`. [Angepinnte Keys](/docs/protecting-human-translations#keys-pinnen) zählt sie nicht mit, weil `--include-human` sie nie überschreibt, und sie erscheint nicht, wenn `--include-human` übergeben wurde. Am Exit-Code ändern sie nichts, außer in einem rein menschlichen Projekt, wo sie wie `unfilled`-Keys zum Exit `3` zählen. `--include-human` übersetzt sie für einen Lauf neu. Siehe [Menschliche Übersetzungen schützen](/docs/protecting-human-translations).
