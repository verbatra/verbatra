`@verbatra/cli` incluye el binario `verbatra`, una capa fina sobre [`@verbatra/sdk`](/docs/sdk). Catorce comandos hacen el trabajo:

| Comando | Qué hace |
| --- | --- |
| [`init`](/docs/cli/init) | crea una configuración de verbatra y un `.env.example` para este proyecto |
| [`extract`](/docs/cli/extract) | analiza el código de tu aplicación en busca de llamadas de traducción y añade las claves nuevas al archivo del locale de origen |
| [`translate`](/docs/cli/translate) | traduce cada locale de destino una vez y luego sale |
| [`watch`](/docs/cli/watch) | retraduce en cada cambio del origen hasta que lo interrumpas |
| [`check`](/docs/cli/check) | informa de qué claves faltan o están obsoletas por locale, solo lectura |
| [`diff`](/docs/cli/diff) | lista las claves exactas que se añadirían, se retraducirían o están huérfanas por locale, solo lectura |
| [`doctor`](/docs/cli/doctor) | valida la configuración del proyecto e informa de todos los problemas a la vez, sin llamar a un proveedor |
| [`pseudo`](/docs/cli/pseudo) | genera un pseudolocale a partir de las cadenas de origen, sin llamar a un proveedor |
| [`types`](/docs/cli/types) | genera declaraciones de TypeScript para las claves de tu catálogo y los argumentos de sus mensajes, sin llamar a un proveedor |
| [`export`](/docs/cli/export) | exporta las cadenas sin traducir para un traductor humano, como libro de Excel o como un archivo CSV o TSV por locale |
| [`import`](/docs/cli/import) | importa un libro rellenado o un archivo delimitado de vuelta a los archivos de locale |
| [`tmx`](/docs/cli/tmx) | importa una memoria de traducción TMX de otra herramienta a la memoria de este proyecto, o exporta la memoria de este proyecto como archivo TMX |
| [`studio`](/docs/cli/studio) | arranca Verbatra Studio, el panel local de traducción |
| [`mcp`](/docs/cli/mcp) | arranca un servidor MCP por stdio que expone las herramientas de verbatra a un cliente MCP |

## Instala e invoca

Instala `@verbatra/cli` como dependencia de desarrollo y luego ejecuta el binario a través de tu gestor de paquetes:

| Gestor de paquetes | Instalación | Ejecución |
| --- | --- | --- |
| npm | `npm install --save-dev @verbatra/cli` | `npx verbatra <command>` |
| pnpm | `pnpm add --save-dev @verbatra/cli` | `pnpm verbatra <command>` (o `pnpm exec verbatra <command>`) |
| yarn | `yarn add --dev @verbatra/cli` | `yarn verbatra <command>` |
| bun | `bun add --dev @verbatra/cli` | `bun run verbatra <command>` |

Necesitas Node.js `>=22.14.0`.

¿Quieres probar un comando antes de instalar? `npx @verbatra/cli <command>` (npm) o `pnpm dlx @verbatra/cli <command>` (pnpm) funcionan sin una instalación local previa.

## Convenciones compartidas

- `--cwd <path>` resuelve la configuración y los archivos de locale desde ese directorio en lugar del actual. Todos los comandos lo aceptan.
- `--config <path>` carga ese archivo de configuración en lugar de buscar uno. Todos los comandos excepto `init` lo aceptan; el orden de búsqueda se describe en [Archivo de configuración](/docs/config-file).
- `--json` imprime un [envoltorio](/docs/ci-and-exit-codes#salida-json) legible por máquina en stdout, una línea por registro, manteniendo stdout limpio para usarlo con pipes.
  - Decide según su campo `ok`: un éxito lleva los datos del comando bajo `result`, y una ejecución fallida lleva el mismo código de error estable que nombra la línea de stderr. La línea de error legible por humanos va a stderr en ambos casos.
  - Lo admiten `extract`, `translate`, `watch`, `check`, `diff`, `doctor`, `pseudo`, `types`, `export`, `import`, `tmx` e `init`; `studio` y `mcp` no.
  - `mcp` no escribe nada en stdout en absoluto, porque stdout es el canal del protocolo MCP; consulta [`verbatra mcp`](/docs/cli/mcp).
- `--help` y `--version` imprimen y salen con `0`. Un comando o flag desconocido sale con `2`.

## Salida en el terminal

<AvailableFrom version="0.12.0" />

Los resultados van a stdout. El progreso, los avisos, las sugerencias, las advertencias y los errores van a stderr, y verbatra los adapta según a dónde vaya stderr:

- En un terminal interactivo, las etiquetas fijas como `error`, `[ok]` y `next:` llevan color, y un paso que tarda más de 300 ms muestra un spinner ASCII (`| / - \`).
- Cuando stderr se redirige o va a una tubería, `CI` está definida o `TERM` vale `dumb`, la salida son líneas simples que solo se añaden, sin color ni animación.
- `--json` nunca añade color, animación ni líneas nuevas: stdout y stderr quedan exactamente como se describe en [Salida JSON](/docs/ci-and-exit-codes#salida-json).

| Flag o variable | Efecto |
| --- | --- |
| `-q`, `--quiet` | muestra solo resultados, advertencias y errores: sin líneas de progreso, avisos ni sugerencias `next:`. Funciona antes o después del nombre del comando |
| `--no-color` | nunca colorea la salida |
| `NO_COLOR`, `VERBATRA_NO_COLOR` | cualquier valor no vacío desactiva el color; `VERBATRA_NO_COLOR` también se impone a `FORCE_COLOR` |
| `FORCE_COLOR` | `1`, `2`, `3`, `true` o un valor vacío activa el color aunque stderr no sea un terminal, y `0` lo desactiva; `--no-color` y `VERBATRA_NO_COLOR` siguen teniendo prioridad |
| `VERBATRA_NO_SPINNER` | cualquier valor no vacío sustituye el spinner por líneas estáticas `label... done (1.2s)`, para lectores de pantalla y grabaciones del terminal |

Las palabras de estado son ASCII simple (`[ok]`, `[warn]`, `[fail]`, `[skip]`), así que la salida se lee igual en cualquier terminal y registro. Cada línea pasa por la misma ocultación de claves que el resto de la salida, y solo se colorean las etiquetas fijas, nunca una clave, una ruta ni un mensaje.

## Archivos de entorno

`translate`, `watch`, `doctor`, `studio` y `mcp` cargan `.env.local` y luego `.env` desde el directorio de trabajo antes de ejecutarse. `doctor --literals` es la excepción: no lee ninguna clave de API, así que no carga ninguno de los dos archivos. Una variable ya definida en tu entorno real siempre gana. Las claves de API se leen solo del entorno, nunca del archivo de configuración ni de un flag: consulta [Proveedores](/docs/providers). Los comandos de solo lectura (`check`, `diff`), los comandos de entrega (`export`, `import`), `extract`, `pseudo`, `types` y `tmx` nunca llaman a un proveedor y no cargan archivos `.env`.

## Códigos de salida

El código de salida es el contrato sobre el que un paso de CI o un script toma su decisión:

| Código | Significado |
| --- | --- |
| `0` | éxito (también `--help` y `--version`) |
| `1` | `translate` o `import` terminó pero algunos locales fallaron o quedaron parciales, `check` encontró un locale desincronizado, `diff` encontró cambios pendientes (o, con `--unused`, un análisis completo encontró una clave de origen sin uso), `doctor` encontró un problema de configuración o, con `--literals`, un literal sin traducir, o `types --check` encontró que la declaración confirmada está desactualizada |
| `2` | no se pudo ejecutar: un error de toda la ejecución (configuración, origen, proveedor, bloqueo) o un error de uso |
| `130` | `translate` o `import` se interrumpió con Ctrl-C (SIGINT) tras liberar sus bloqueos de escritura, o `watch`, `studio` o `mcp` fue detenido a la fuerza por una segunda interrupción |
| `143` | `translate` o `import` se detuvo con SIGTERM tras liberar sus bloqueos de escritura |

La página de cada comando detalla cómo se le aplican estos códigos. Consulta [CI y códigos de salida](/docs/ci-and-exit-codes) para conectarlos a una canalización.
