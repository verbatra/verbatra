Use this when a run produced translations you do not want: the wrong tone, the wrong model, a glossary you forgot. verbatra has no undo command and keeps no backups. Version control is the recovery mechanism, which is why the locale files and the lock file are committed: together they are the snapshot you go back to.

You need the project in git, with the state before the run committed.

## What a run writes

A `translate`, `watch` or `import` run writes the files a rollback cares about:

- the target locale files, at your `files.pattern` path;
- `verbatra.lock.json`, one source content hash per translated key.

`verbatra.cache.json` and `.verbatra-local/` are regenerable, gitignored state; never restore them. Every tracked file is written atomically, so there is never a half-written file to repair.

A run also writes `verbatra.provenance.json`, which records who wrote each value. Restore it with the other two. Forgetting it breaks nothing: a record that no longer matches its value reads as `external`, so a mismatch loses information but never claims the wrong author.

## Roll back a completed run

If the run is not committed yet, discard the locale files and the lock file together:

```bash
git checkout HEAD -- locales verbatra.lock.json
```

Restore `verbatra.provenance.json` the same way if it is already committed. If this run created it, git has nothing to restore, so delete it:

```bash
git checkout HEAD -- verbatra.provenance.json   # already committed
rm verbatra.provenance.json                      # created by this run
```

If the run is already committed, revert that commit:

```bash
git revert <commit>
```

Either way, restore the locale files and `verbatra.lock.json` in the same operation. The next section is why.

## Why both files, or neither

The lock file records a hash of the **source** value behind each translation, and nothing about the translated value itself. Reverting one file without the other leaves them describing different points in time.

**Only the locale files.** The lock still says every key is current. On the next run, a key the revert restored is present and its hash matches the source, so it is never sent again: the old value stays in place for good. Only keys the run newly created come back as missing. `check` and `diff` compare against the same baseline, so they report the locale as clean, and nothing tells you those translations are out of date.

**Only the lock file.** The restored hashes are older than the current source, so the affected keys read as changed. The next run translates them again and overwrites the locale files, including hand corrections made since. You pay twice and lose the edits.

**Both.** The hashes and the translations go back to the same point, and the next run behaves as if the bad run never happened.

## Re-run after a rollback

Rolling back and running `verbatra translate` again is a redo, not a second opinion. With the same provider, model, tone, glossary and provider `localeMap`, the [cache](/docs/the-cache#the-fingerprint) fingerprint is unchanged, so the run serves the same translations from `verbatra.cache.json` without calling the provider.

To get a different result, change what made the first one wrong: a new tone, glossary or model changes the fingerprint and retranslates on its own. To re-send the same configuration to the provider, add `--no-cache`:

```bash
verbatra translate --no-cache
```

To rebuild a locale from scratch rather than undo one run, see [How do I re-translate everything?](/docs/faq#how-do-i-re-translate-everything). Deleting the lock file is not a reset: without a baseline nothing is detected as stale, so the next run translates nothing.

## An interrupted or failed run

An interrupted run needs no rollback. Run it again.

Each locale is committed on its own: its file is written, then its lock entries are recorded. An interrupt leaves the finished locales complete and the others untouched, and a re-run picks up the untouched ones. The one gap, between a locale's file write and its lock update, resolves itself: added keys are adopted as they stand, and changed keys still carry their old hash, so they are translated again. No work is lost.

Keys withheld during a run, by a failed check, a failed provider call or a token budget, keep their previous hash, so the next run retries them. See [Troubleshooting](/docs/troubleshooting) for each cause.

An interrupted run releases its write locks. A process killed hard (`kill -9`, a crash) can leave one behind under `.verbatra-local/`; the next run on the same machine sees that the process is gone and reclaims it. A lock it cannot check makes the run wait and then fail with [`LOCK_CONTENDED`](/docs/error-codes#lock_contended), which names the path to delete.

## Before a run you cannot easily undo

- Commit your locale files, `verbatra.lock.json` and `verbatra.provenance.json` first, so `git checkout HEAD --` has something to return to.
- Preview with `verbatra translate --dry-run`, `verbatra diff` or `verbatra check`. None of them calls a provider or writes a file.
- Try one locale first with `--locales <locale>`.
