意図しない翻訳が実行で生成された場合に使います。たとえば、トーンが違う、モデルが違う、用語集を忘れていた、といった場合です。verbatra には取り消しコマンドがなく、バックアップも保持しません。復旧の手段はバージョン管理です。ロケールファイル、ロックファイル、来歴ファイルをコミットするのはそのためで、3 つがそろって、戻り先のスナップショットになります。

git で管理され、実行前の状態がコミットされているプロジェクトが必要です。

## 実行で書き込まれるもの

`translate`、`watch`、`import` の実行は、ロールバックで対象になるファイルを書き込みます。

- ターゲットのロケールファイル（`files.pattern` のパス）
- `verbatra.lock.json`（翻訳されたキーごとに、ソースのコンテンツハッシュを 1 つ記録）

`verbatra.cache.json` と `.verbatra-local/` は、再生成できる、gitignore 済みの状態です。復元しないでください。追跡されるファイルはすべてアトミックに書き込まれるので、修復が必要な書きかけのファイルが残ることはありません。

実行は `verbatra.provenance.json` も書き込みます。各値を誰が書いたかを記録するファイルです。ほかの 2 つと一緒に復元するか、この実行で作成されたものなら削除します。これを忘れると、問題が起きます。元に戻した値は記録と一致しなくなるため、`external` として扱われ、デフォルトの `humanEdits: protect` では人による編集として数えられ、二度と翻訳されません。

## 完了した実行をロールバックする

実行がまだコミットされていない場合は、ロケールファイルとロックファイルをまとめて破棄し、続いて来歴ファイルを破棄します。

```bash
git checkout HEAD -- locales verbatra.lock.json
```

`verbatra.provenance.json` がすでにコミットされている場合は、同じ方法で復元します。この実行で作成されたものなら、git に復元するものがないので削除します。

```bash
git checkout HEAD -- verbatra.provenance.json   # already committed
rm verbatra.provenance.json                      # created by this run
```

実行がすでにコミットされている場合は、そのコミットを元に戻します。

```bash
git revert <commit>
```

どちらの場合も、ロケールファイル、`verbatra.lock.json`、`verbatra.provenance.json` を同じ操作で復元します。理由は次のセクションにあります。

## 3 つのファイルをまとめて戻す理由

ロックファイルは、各訳文の元になった**ソース**値のハッシュを記録します。訳文の値そのものについては、何も記録しません。来歴ファイルは、各値を誰が書いたかを、その値のハッシュに対応づけて記録します。1 つのファイルだけを戻すと、ファイルごとに異なる時点を記述することになります。

**ロケールファイルだけを戻した場合**：ロックファイルは、すべてのキーが最新だと記録したままです。次の実行では、元に戻したキーがファイルにあり、そのハッシュもソースと一致するので、二度と送信されません。古い値がそのまま残り続けます。欠落として戻るのは、実行で新しく作成されたキーだけです。`check` と `diff` は同じベースラインと比較するので、ロケールはクリーンだと報告し、それらの訳文が古いことを知らせるものは何もありません。

**ロックファイルだけを戻した場合**：復元されたハッシュは現在のソースより古いので、該当するキーは変更されたものとして扱われます。次の実行はそれらを再び翻訳し、その後に手で直した内容も含めて、ロケールファイルを上書きします。二重に費用がかかり、編集も失われます。

**来歴ファイルを戻さなかった場合**：元に戻した値は記録と一致しなくなるため、`external` として扱われ、デフォルトの `humanEdits: protect` では二度と翻訳されません。

**3 つすべてを戻した場合**：ハッシュ、記録、訳文が同じ時点に戻り、次の実行は、問題のあった実行がなかったかのように動作します。

## ロールバック後に再実行する

ロールバックしてから `verbatra translate` を再実行するのは、やり直しであって、セカンドオピニオンではありません。プロバイダー、モデル、トーン、verbatra が送る用語集の用語、プロバイダーの `localeMap` が同じなら、翻訳キャッシュの[フィンガープリント](/ja/docs/the-cache#フィンガープリント)は変わりません。そのため実行は、プロバイダーを呼び出さず、`verbatra.cache.json` から同じ訳文を返します。

違う結果を得るには、最初の結果が間違っていた原因を変えます。トーン、用語集、モデルを変えると、フィンガープリントが変わり、自動的に再翻訳されます。同じ設定をもう一度プロバイダーに送るには、`--no-cache` を付けます。

```bash
verbatra translate --no-cache
```

1 回の実行を取り消すのではなく、ロケールをゼロから作り直すには、[すべてを翻訳し直すにはどうすればよいですか？](/ja/docs/faq#すべてを翻訳し直すにはどうすればよいですか)を参照してください。ロックファイルの削除はリセットではありません。ベースラインがなければ何も古いと検出されないので、次の実行は何も翻訳しません。

## 中断または失敗した実行

中断された実行は、ロールバックが不要です。もう一度実行します。

各ロケールは個別に確定します。ファイルが書き込まれ、次にロックファイルのエントリが記録されます。中断されても、完了したロケールは完全な状態で残り、ほかは手つかずのままで、再実行すると手つかずのロケールから再開します。唯一の隙間は、ロケールのファイル書き込みとロックファイルの更新の間にありますが、自然に解消します。追加されたキーはそのまま採用され、変更されたキーは古いハッシュを保っているので、再び翻訳されます。作業が失われることはありません。

実行中に保留されたキー（チェックの失敗、プロバイダー呼び出しの失敗、トークン予算が原因）は、以前のハッシュを保つので、次の実行で再試行されます。それぞれの原因は[トラブルシューティング](/ja/docs/troubleshooting)を参照してください。

中断された実行は、書き込みロックを解放します。強制終了されたプロセス（`kill -9` やクラッシュ）は、`.verbatra-local/` の下に書き込みロックを残すことがあります。同じマシンでの次の実行は、そのプロセスがもう存在しないことを確認して、書き込みロックを回収します。確認できない書き込みロックがあると、実行は待機した後、[`LOCK_CONTENDED`](/ja/docs/error-codes#lock_contended) で失敗し、削除すべきパスが示されます。

## 簡単に取り消せない実行の前に

- ロケールファイル、`verbatra.lock.json`、`verbatra.provenance.json` を先にコミットします。そうすれば、`git checkout HEAD --` で戻る先ができます。
- `verbatra translate --dry-run`、`verbatra diff`、`verbatra check` でプレビューします。どれもプロバイダーを呼び出さず、ファイルも書き込みません。
- `--locales <locale>` で、まず 1 つのロケールを試します。
