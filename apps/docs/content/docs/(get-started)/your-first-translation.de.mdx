---
title: Deine erste Übersetzung
description: Installiere die CLI, erzeuge mit verbatra init eine Konfiguration, sieh dir den Lauf ohne API-Schlüssel in der Vorschau an, setze dann deinen API-Schlüssel und starte deinen ersten translate-Lauf. In unter zehn Minuten von null zur übersetzten Locale-Datei.
---
Fünf Schritte führen dich vom leeren Projekt zur übersetzten Locale-Datei. Alles, was du brauchst, ist Node.js `>=22.14.0` und ein API-Schlüssel für einen Provider, sobald du wirklich übersetzen willst. Die ersten drei Schritte kosten nichts und brauchen kein Konto.

## 1. Installiere die CLI

verbatra ist eine Dev-Dependency:

```bash
npm install --save-dev @verbatra/cli
```

pnpm und yarn funktionieren auch: `pnpm add -D @verbatra/cli` und dann `pnpm verbatra ...`, oder `yarn add -D @verbatra/cli` und dann `yarn verbatra ...`. Die Codeblöcke unten verwenden `npx`, passend zum `npm install` oben.

pnpm braucht einen Schritt mehr. `pnpm add -D @verbatra/cli` installiert korrekt, beendet sich aber mit `1` und `ERR_PNPM_IGNORED_BUILDS` und hinterlässt eine unbeantwortete `pnpm-workspace.yaml`, an der jeder spätere pnpm-Befehl im Projekt genauso scheitert. Führe einmal `pnpm approve-builds` aus und bestätige keinen der beiden Einträge, oder sieh dir in der [Fehlerbehebung](/docs/troubleshooting) die nicht-interaktive Lösung an.

## 2. Erzeuge eine Konfiguration

```bash
npx verbatra init --provider gemini
```

`init` sieht sich zuerst die Locale-Dateien an, die schon in deinem Projekt liegen, und erkennt ihr Format, ihr Pfadmuster und ihre Locales. Mit angeschlossenem Terminal fragt es dann alles ab, was du nicht als Flag übergeben hast, und schlägt dabei vor, was es erkannt hat, oder sonst einen Default:

- den Provider: einer von `anthropic`, `openai`, `gemini`, `deepl`, `google-translate`, `openai-compatible` oder `none` (Flag `--provider`, die einzige Eingabe ohne Default)
- das Format der Locale-Dateien, Default `i18next-json` (`--format`)
- die Quell-Locale, Default `en` (`--source`)
- die Ziel-Locales, kommagetrennt, Default `de` (`--targets`)
- das Muster der Locale-Dateien, Default das übliche Layout des gewählten Formats, `locales/{locale}.json` für `i18next-json` (`--path`)

Übergib `--yes`, um die Abfragen zu überspringen und die erkannten Werte oder die Defaults zu nehmen. Ohne Terminal (zum Beispiel in CI) fragt `init` nie nach: Ein Wert, den es unter `--yes` weder erkennen noch mit einem Default füllen kann, lässt es mit `2` und `MISSING_OPTIONS` enden, und die Meldung nennt die Flags, die du übergeben musst.

`init` schreibt drei Dinge:

- `verbatra.config.ts`: deine Projektkonfiguration, vor dem Schreiben gegen das echte Schema validiert
- `.env.example`: nennt die Umgebungsvariable für den API-Schlüssel des Providers, nie dessen Wert
- `.gitignore`-Einträge für `.env`, `.env.local`, `.verbatra-local/` und `verbatra.cache.json`, angelegt oder ergänzt, damit ein echter API-Schlüssel, lokaler Zustand oder der regenerierbare Cache nie in einem Commit landet

Ein erneutes `init` mit denselben Antworten ändert nichts. Eine `verbatra.config.ts` mit anderem Inhalt wird abgelehnt, außer du übergibst `--force`, und an eine bestehende `.env.example` wird nur die Key-Variable angehängt, wenn sie fehlt. Hat das Projekt noch keine Locale-Datei, kommt `format` aus deinen Dependencies (i18next, vue-i18n, next-intl oder `@ngx-translate/core` wählen das passende JSON-Format), sonst fällt es auf `i18next-json` zurück. Unter `--yes` trägt dieser Default einen TODO-Kommentar zum Ändern; ein Format, das du in der Abfrage übernimmst, nicht. Die Details stehen unter [verbatra init](/docs/cli/init#erkennung). Für Gemini in einem leeren Projekt sieht das Gerüst so aus:

```ts
import { defineConfig } from "@verbatra/cli";

export default defineConfig({
  sourceLocale: "en",
  targetLocales: ["de"],
  format: "i18next-json",
  files: {
    pattern: "locales/{locale}.json",
  },
  provider: {
    id: "gemini",
    options: {
      model: "gemini-2.5-flash",
      maxOutputTokens: 4096,
    },
  },
});
```

## 3. Vorschau ohne API-Schlüssel

Fange mit [`verbatra doctor`](/docs/cli/doctor) an, der Vorabprüfung für genau diese Einrichtung:

```bash
npx verbatra doctor
```

Es führt fünf Prüfungen aus: Die Konfiguration lässt sich laden und validieren, das Format wird zu einem Datei-Adapter aufgelöst, die Provider-ID zu einem Provider, die Umgebungsvariable, aus der dieser Provider seinen API-Schlüssel liest, ist gesetzt, und die Quell-Locale-Datei existiert und lässt sich parsen. Jede Prüfung läuft auch dann, wenn eine frühere fehlschlug; ein Lauf meldet also jedes Problem, statt beim ersten abzubrechen. Es konstruiert keinen Provider, macht keine Netzwerkanfrage, schreibt nichts und liest nie den Wert eines API-Schlüssels. Es ist außerdem die einzige Prüfung, die schon funktioniert, bevor die Quelldatei existiert: führe sie also jetzt aus und noch einmal nach Schritt 4.

Wenn du noch keine Quelldatei hast, lege eine unter dem konfigurierten Muster an, zum Beispiel `locales/en.json`:

```json
{
  "greeting": "Hello, {{name}}!",
  "cart": {
    "empty": "Your cart is empty."
  }
}
```

Sieh dir den Lauf jetzt in der Vorschau an:

```bash
npx verbatra translate --dry-run
```

Ein Dry Run konstruiert überhaupt keinen Provider, braucht also keinen API-Schlüssel und kann keine Kosten verursachen. Er liest deine Dateien, vergleicht sie und gibt dieselbe Zusammenfassung pro Locale aus wie ein echter Lauf, ohne einen einzigen String zu senden oder eine einzige Datei zu schreiben. Nutze ihn, um Format, Dateimuster und Locales zu prüfen, bevor du dich irgendwo anmeldest.

[`verbatra check`](/docs/cli/check) und [`verbatra diff`](/docs/cli/diff) kommen genauso ohne Provider aus: `check` meldet Zahlen pro Locale, `diff` listet die genauen Keys. Anders als `doctor` lesen alle drei die Quelldatei, brauchen sie also zuerst.

Noch etwas funktioniert, bevor du einen API-Schlüssel hast, und es gibt dir etwas zum Anschauen statt zum Lesen:

```bash
npx verbatra pseudo
```

[`verbatra pseudo`](/docs/cli/pseudo) baut aus deinen Quellstrings eine künstliche Locale, akzentuiert, verlängert und in `[` und `]` gefasst, und schreibt sie nach `.verbatra-local/pseudo`. Richte deinen Dev-Server auf dieses Verzeichnis und starte die App darin: Ein abgeschnittener Button, ein aus zwei Fragmenten zusammengeklebter Satz und ein Label, das nie für die Übersetzung extrahiert wurde, fallen sofort auf. Deine echten Locale-Dateien bleiben unangetastet, und die erzeugte Datei ist von den `.gitignore`-Einträgen, die `init` geschrieben hat, bereits abgedeckt.

## 4. Setze deinen API-Schlüssel

API-Schlüssel kommen aus der Umgebung, nie aus der Konfigurationsdatei. Jeder gehostete Provider liest genau eine Variable; für Gemini ist das `GEMINI_API_KEY`. Kopiere das erzeugte Beispiel und trage deinen API-Schlüssel ein:

```bash
cp .env.example .env
```

Öffne dann `.env` und füge deinen API-Schlüssel nach `GEMINI_API_KEY=` ein. `translate`, `watch`, `doctor`, `studio` und `mcp` laden vor einem Lauf `.env.local` und dann `.env` aus dem Arbeitsverzeichnis, und eine Variable, die schon in deiner Shell gesetzt ist, gewinnt immer. Siehe [Provider](/docs/providers) für die Variable jedes Providers.

<Callout title="Noch kein API-Schlüssel? Gemini hat ein kostenloses Kontingent.">
Geminis API hat ein wirklich kostenloses Kontingent und ist damit der günstigste Weg, verbatra auszuprobieren. Hol dir einen API-Schlüssel im [Google AI Studio](https://aistudio.google.com/apikey) und setze `GEMINI_API_KEY`. Das kostenlose Kontingent hat Anfragelimits pro Minute und pro Tag, verteile eine große Erstübersetzung also über die Zeit.
</Callout>

## 5. Übersetze

Mit gesetztem API-Schlüssel führst du denselben Befehl jetzt echt aus:

```bash
npx verbatra translate
```

verbatra liest die Quell-Locale, sieht, dass jeder Key in `de` fehlt, sendet sie in Batches an den Provider, lässt jedes Ergebnis durch das Integritäts-Gate laufen und schreibt `locales/de.json`. Der Lauf endet mit einer Zusammenfassung pro Locale: übersetzte Keys, unveränderte Keys, verwaiste Keys und etwaige Hinweise. Der Exit-Code ist `0`, wenn jede Locale vollständig durchkam, und `1`, wenn eine fehlschlug oder unvollständig blieb (geschrieben, aber mit weiterhin fehlenden Keys); ergänze `--json` für eine maschinenlesbare Zusammenfassung.

## Was gerade passiert ist

Vier Dinge liegen jetzt auf der Platte:

- `locales/de.json`: die Ziel-Locale-Datei. Die Datei hat dieselben Keys wie deine Quelle, in derselben Dokumentreihenfolge, und `{{name}}` hat die Übersetzung intakt überstanden; ein Ergebnis, das den Platzhalter verworfen hätte, wäre zurückgehalten und nicht geschrieben worden.
- `verbatra.lock.json`: die Lock-Datei. Für jede Ziel-Locale bildet sie jeden übersetzten Key auf einen Hash des Quellstrings ab, aus dem die Übersetzung entstanden ist:

  ```json
  {
    "version": 1,
    "locales": {
      "de": {
        "cart.empty": "<source content hash>",
        "greeting": "<source content hash>"
      }
    }
  }
  ```

- `verbatra.provenance.json`: die Herkunftsdatei. Für jeden übersetzten Key hält sie fest, welcher Schreibweg den Wert erzeugt hat (hier `machine`, mit deinem Provider und Modell), damit ein späterer Lauf, `check --json` und `diff --json` Maschinenübersetzung von menschlicher Arbeit unterscheiden können. Siehe [Die Lock-Datei](/docs/the-lock-file#herkunft-wer-welchen-wert-geschrieben-hat).
- `.verbatra-local/`: prozesslokaler Zustand (der Schnappschuss des Lauf-Status und die Schreibsperren pro Locale). `init` hat das Verzeichnis in `.gitignore` eingetragen; committe es nie.

Die Lock-Datei ist die Baseline für jeden künftigen Lauf. Führe `verbatra translate` erneut aus, ohne etwas zu bearbeiten, und nichts wird gesendet: Jeder Key ist bereits aktuell. Ändere einen einzigen Quellstring, und nur dieser Key wird neu übersetzt.

<Callout title="Committe die Lock-Datei">
Committe `verbatra.lock.json` und `verbatra.provenance.json` zusammen mit deinen Locale-Dateien, damit jede Maschine und deine CI mit derselben Baseline vergleichen. Siehe [Die Lock-Datei](/docs/the-lock-file).
</Callout>
