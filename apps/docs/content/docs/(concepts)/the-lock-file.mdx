The lock file, `verbatra.lock.json`, exists so a run can tell what already got translated and skip
it: it is the baseline every run diffs against, and it is what makes verbatra incremental. This
page covers what it stores, how it changes, and what happens when it is contended, missing, or
corrupt.

## What it records

For every target locale, the lock file stores one content hash per translated key, computed from
the source value that produced the existing translation. It contains no translations and no
secrets: just a `version` field and hashes. The hash normalizes Unicode to NFC and line endings to
LF, so re-saving a source file with different normalization or CRLF endings does not mark anything
as changed.

## How drift is detected

When a run diffs a target locale, a source key absent from the target is missing. For a key the
target does have, the current source hash is compared against the hash the lock recorded: a
difference means the source drifted since the key was last translated, so it is changed and gets
retranslated; a match means it is unchanged and never sent to the provider. That is why a second
run with no source edits calls the provider for nothing, and why stale translations cannot hide
behind a key that merely exists. The full pipeline is on [How it works](/docs/how-it-works).

## Adopting an existing project

Pointing verbatra at a repository whose locale files already hold reviewed translations does not
retranslate them. On the first run there is no lock file, so no key can be detected as stale: a
source key the target file already has is unchanged, is never sent to the provider, and keeps its
existing value. Only keys the target file does not have are missing, and only those are translated.
When nothing was accepted, pruned, or generated for a locale, its existing target file is not
rewritten at all.

The run still records the current source hash for every key the target holds, so the first run is
the adoption step: it establishes the baseline at zero provider cost, and from the second run on,
source edits show up as drift the normal way.

Adoption is decided by key presence, never by value, which has two consequences worth knowing
before that first run:

- An empty or untranslated value counts as translated. A target value that is an empty string, or
  that is still the untranslated source text, is a key that exists, so it is unchanged and never
  filled in. Scaffolding tools that pre-create locale files with empty string values run straight
  into this. The fix is to delete the key from the target file: emptying its value does not help,
  because an empty string is still an entry. Once the key is gone, the next run sees it as missing
  and translates it.
- A translation that was already out of date is recorded as current. The lock takes the source hash
  as it is now, so a translation that had already drifted from the source before you adopted the
  project is taken as up to date and will not be revisited. Fix or delete those keys before the
  first run.

Plural generation follows the same adoption rule. A plural form the target file already holds and
that verbatra did not generate itself is kept as it is, never regenerated and never sent to the
provider (a form the lock already tracks is still regenerated when its source changes), so
`generatePlurals` is safe to leave on while adopting a project that carries hand-written plural
forms; only forms genuinely absent from the target are synthesized.

You can see all of this before spending anything: `verbatra diff` lists the exact missing and
changed keys per locale, `verbatra check` reports the same as counts, and
`verbatra translate --dry-run` gives you the full run summary. None of the three calls a provider,
writes a locale file, or writes the lock.

## How it is updated

The lock is updated per locale, and how depends on what ran:

- A full run (translate, watch, or a workbook import) replaces that locale's entries wholesale with
  the run's authoritative result.
- A single-key action (such as a retranslate from Studio) merges only that key's entry, leaving
  every other recorded key untouched.

In both cases one exception applies: a key withheld this run (a failed integrity check, a failed
provider call, or an invalid-ICU source) keeps its prior hash, so the next run still sees it as
needing work and retries it instead of recording it as done. Orphaned keys get no entry. The file
is serialized with sorted keys, so its diffs stay stable and reviewable.

## The write lock

Two runs touching the same locale at the same time (a second terminal, a CI job, a Studio action)
could otherwise both diff a stale baseline and both pay for the same provider call. To prevent
that, every write to a locale and its lock entries happens under a cross-process write lock scoped
to that one locale; a second writer for the same locale waits, then re-reads the lock file fresh
and diffs against a baseline that already includes the first writer's result. Different locales do
not block each other.

When a run translates several locales at once and hits a whole-run error (in practice a corrupt
lock file), it stops claiming new locales and waits for the ones already running to finish, so
every lock the run took is released before the command exits. No locale is started after the run
has already failed, and no lock is orphaned by the failure itself.

Each lock file records the process ID and the host name of the process holding it, and on Linux
also the kernel's boot ID and the process's PID namespace. A process killed hard can still leave
one behind, so a waiting run checks the recorded process: when every identity field the lock
records matches the waiting run's own (so the recorded process ran on this machine, in the same
process table) and that process no longer exists, the run reclaims the lock at once instead of waiting out
`--lock-timeout`. Reclaiming is serialized, so two waiting runs never both take over the same
abandoned lock. A lock recorded on another machine (a shared network drive) or by a verbatra
version older than 0.12.0 carries nothing that can be checked safely, so it is never reclaimed. The
same goes for a lock that records an identity field the waiting run cannot read, or lacks one it
can: it is treated as held by a live process.

One limit remains. Outside Linux, the host name is the only machine identity verbatra records, so
two containers or virtual machines that share a host name and the same `.verbatra-local/`
directory (a shared volume) but not a process table can mistake each other's live lock for an
abandoned one. Give each of them its own host name, or its own working copy.

An interrupt releases the locks a run holds before the process exits: Ctrl-C or SIGTERM during
`translate` or `import`, and the second interrupt that force-stops `watch`.

If a lock cannot be acquired, the run fails with `LOCK_CONTENDED` and names the lock file's path
(under the gitignored `.verbatra-local/` directory). If no verbatra process is running anywhere,
delete that file and retry.

## A respelled locale code

<AvailableFrom version="0.12.0" />

The lock file, the translation memory, and the provenance file key their state by the locale code in your config. When you respell a code, for example `pt_BR` to `pt-BR` with `files.localeStyle` set to `posix` so the file keeps its name, the next `translate` or `watch` run carries the old state over once. It does so when `pt-BR` has no state of its own in a file and that file holds state under exactly one underscore spelling of it, compared case-insensitively. The state moves to `pt-BR` before the locale runs, and the run reports a `LOCALE_STATE_CARRIED_OVER` notice on that locale. A source change made before the rename is then still retranslated, and cached translations are still reused.

State that `pt-BR` already has is never overwritten, and when two spellings compete, such as `pt_BR` and `pt_br`, nothing moves. A run limited with `--locales` moves state only for the locales it runs, `--dry-run` plans with the moved state but writes nothing, and `--no-cache` leaves the translation memory as it is. The `locale-state` check of [`verbatra doctor`](/docs/cli/doctor) names whatever stays behind, and any other locale your config no longer lists.

## Missing or corrupt

A missing lock file is not an error: it is a first run, and with no baseline nothing can be
detected as stale. Source keys the target file does not have are missing and get translated; keys
it does have are unchanged and are left untouched, as described under adoption above.
A lock file that is present but unparseable, structurally wrong, oversized, or at an unsupported
version fails the run with `LOCK_FILE_INVALID` instead of being silently overwritten, so you can
inspect or restore it rather than losing the baseline.

## Provenance: who wrote each value

<AvailableFrom version="0.12.0" />

Next to the lock file, verbatra keeps `verbatra.provenance.json`. Where the lock records which
source text a translation came from, the provenance file records which write path produced the
value that is in the locale file now, and whether anyone reviewed it. Provenance lives in its own
file on purpose: the lock file's format and version are unchanged, so an older verbatra, for example one
pinned in a CI action, keeps reading the lock file and simply ignores the provenance file.

Each record names an origin:

| Origin | Written by |
| --- | --- |
| `machine` | a provider response in `translate` or `watch` (plural forms generated by the provider included) and a single-key retranslate, with the `id` of the provider that answered (a custom `createProvider` in the SDK is recorded under its own `id`) and, when it is the configured provider and has one, the model |
| `memory` | an exact translation-memory hit, including every value a human-only run (provider `none`) fills |
| `fuzzy` | a fuzzy translation-memory hit |
| `human` | a value a person wrote through the SDK's `editEntry`, as the Studio edit dialog does |
| `agent` | a value an AI agent wrote through `editEntry` with `actor: "agent"` |
| `import` | an accepted row from `verbatra import` |

When the files are read, two more origins are derived rather than stored. `unrecorded` is a value
with no record, which is where every key of a project starts after upgrading. `external` is a value
that no longer matches its record, because something outside verbatra changed it: a translator
editing the locale file in a pull request, an older verbatra, or a merge. Each record carries a hash
of the value it describes, which is how a stale record is caught instead of trusted. `check --json`,
`diff --json`, and the SDK's key reads report these interpreted origins; the
[SDK reference](/docs/sdk#loadprovenance) lists the fields.

The file holds no translated text and no timestamps, and its records are sorted with one record per
line, so a run that changes nothing leaves it byte for byte as it was, and two branches that touch
different keys rarely conflict. When they do, take either side: a record that does not match the
value next to it reads as `external`, so the wrong pick only loses information and never names the
wrong author. A write that leaves a value and its source text unchanged keeps the record as it is;
any other write replaces it with a fresh, unreviewed one.

A provenance file that is corrupt stops every write with `PROVENANCE_FILE_INVALID` before a locale
file changes or a provider is called, rather than being overwritten. `check`, `diff`, and the other
reports never fail over it: they leave their provenance fields out until the file is repaired. A
file written by a newer verbatra is left untouched; `translate`, `watch`, and `import` report the
notice `PROVENANCE_VERSION_UNRECOGNIZED`, and a single-key edit simply records nothing. verbatra
never writes a provenance file larger than it can read back: when recording a locale would grow
the file past that size, the previous file is kept and the run reports
`PROVENANCE_FILE_TOO_LARGE`; a single-key edit keeps it silently. The record says which verbatra write path produced a value; it
is not tamper-proof, since anyone who can edit the locale files can edit it too.

### Review decisions

<AvailableFrom version="0.12.0" />

A record can also carry a review decision: `approved` or `rejected`, with an optional `reviewer`
name. Verbatra Studio's Review page writes them, and so do the SDK's `approveEntry` and
`rejectEntry`. Both work on the exact value the reviewer saw and are refused when the value has
changed since, and neither saves a decision it could not record: a provenance file from a newer
verbatra, or one the decision would grow past the size verbatra reads back, fails the call with
`PROVENANCE_FILE_UNWRITABLE` and nothing changes.

- **An approval** changes only the provenance file. It also stores the source hash it was given
  against, so an approval whose source text has changed since reads as unreviewed again. A value
  whose source changed since it was written cannot be approved; edit or retranslate it first.
- **A rejection** removes the value from the locale file and its entry from the lock file, so the
  key reads as missing until the next `translate` run, or a person, writes a new value. The record
  stays behind with a hash of the removed text, and the matching translation-memory entry on this
  machine is dropped so the next run does not put the same text straight back. If a step fails, the
  locale file and the provenance file are restored on failure; when even that fails, the call
  reports `REVIEW_RESTORE_FAILED` and names the files to restore from version control. A process
  killed in the middle of the write cannot be undone this way. A format that cannot drop one
  translation refuses the rejection with `REVIEW_REJECT_UNSUPPORTED` and leaves the file as it was:
  XLIFF, whose writer only updates the targets it is given and keeps every other one.

Any later write that changes the value starts a fresh, unreviewed record, so editing an approved
value sends it back for review. The `reviewer` name is stored in a committed file, so it is public;
verbatra never fills it in on its own.

## Commit it

Commit `verbatra.lock.json` and `verbatra.provenance.json` alongside your locale files. It is the shared baseline your teammates
and your CI diff against; keeping it in version control is what makes incremental runs reproducible
across machines. Never hand-edit it.

Committing both is also what makes a rollback possible. Because the lock records source hashes and
nothing about the translated values, reverting your locale files without this file leaves it
claiming the reverted translations are current, and nothing will retranslate them. See
[Recovery and rollback](/docs/recovery-and-rollback).
