verbatra hat keine eigene Sprachliste. Es akzeptiert jeden gültigen BCP-47-Locale-Code, behandelt
die Strings jeder Sprache gleich und überlässt die Übersetzung deinem Provider. Du kannst also die
Sprachen nutzen, die dein Provider unterstützt, und in einem reinen Handarbeits-Projekt alle. Der
Teil von verbatra ist, jeden Code so zu schreiben, wie der Provider ihn erwartet, jede Übersetzung an
den Pluralregeln ihrer Sprache zu messen und dich vor einem Lauf zu warnen, wenn ein Provider eine
Locale nicht bedienen kann.

## Locale-Codes

<AvailableFrom version="0.12.0" />

Jede Locale in deiner Konfiguration muss ein gültiger BCP-47-Tag sein, etwa `fr`, `pt-BR`,
`sr-Latn`, `zh-Hant-TW` oder `es-419`; ein ungültiger Code lässt das Laden der Konfiguration
scheitern. Unterstriche sind kein BCP 47: Für Dateien namens `pt_BR.json` schreibst du `pt-BR` und
setzt `files.localeStyle` auf `posix`. Ein gültiger Code, der nicht kanonisch ist, etwa `zh-hant-tw`
oder das veraltete `iw`, funktioniert weiter, und [`verbatra doctor`](/docs/cli/doctor) schlägt die
kanonische Form vor. Die Schreibregeln und die Stile für Android und gettext stehen unter
[Locale-Codes](/docs/config-file#locale-codes).

Der Code aus deiner Konfiguration ist der, den verbatra überall speichert: Dateipfade,
[die Lock-Datei](/docs/the-lock-file) und [der Cache](/docs/the-cache). Eine Provider-eigene
Schreibweise gibt es nur innerhalb eines Requests. Schreibst du einen Code um, den du schon
übersetzt, etwa `pt_BR` zu `pt-BR`, bleibt seine Geschichte erhalten; siehe
[Ein umgeschriebener Locale-Code](/docs/the-lock-file#ein-umgeschriebener-locale-code).

## Abdeckung je Provider

Welche Sprachen übersetzt werden und wie gut, entscheidet der Provider. Jede Zeile verlinkt die
eigene Liste des Anbieters.

| Provider | Sprachen | Gesendeter Code | Glossar | Tonfall |
| --- | --- | --- | --- | --- |
| `anthropic` | Keine feste Liste. [Claude multilingual support](https://platform.claude.com/docs/en/build-with-claude/multilingual-support) | Wie geschrieben, plus englische Namen für Sprache, Schrift und Region | Begriffe der Locale im Prompt | Im Prompt |
| `openai` | Keine feste Liste. [Using the OpenAI API in different languages](https://help.openai.com/en/articles/6742369-how-do-i-use-the-openai-api-in-different-languages) | Wie geschrieben, plus Namen | Begriffe der Locale im Prompt | Im Prompt |
| `gemini` | [Gemini language support](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/google-models#languages-gemini) | Wie geschrieben, plus Namen | Begriffe der Locale im Prompt | Im Prompt |
| `openai-compatible` | Was das Modell abdeckt, das du betreibst | Wie geschrieben, plus Namen | Begriffe der Locale im Prompt | Im Prompt |
| `deepl` | [DeepL supported languages](https://developers.deepl.com/docs/getting-started/supported-languages) | Auf DeepLs Codes normalisiert | Nur ein vorab angelegtes DeepL-Glossar per `glossaryId`, für 32 Sprachen | DeepL-Formality für einige Sprachen, nicht mit einem Free-Key |
| `google-translate` | [Cloud Translation language support](https://docs.cloud.google.com/translate/docs/languages) (für die Basic-Stufe v2, die verbatra nutzt, gilt die NMT-Liste) | Für Chinesisch und Norwegisch normalisiert, sonst wie geschrieben | Keins | Keiner |
| `libretranslate` | Die auf deinem Server installierten Modelle; [die Upstream-Liste](https://docs.libretranslate.com/) zeigt, was sich installieren lässt | Nur die Sprache, außer `pt-BR`, `zh-Hans` und `zh-Hant` | Keins | Keiner |
| `none` | Entfällt: Es wird kein Provider aufgerufen | Es wird nichts gesendet | Entfällt | Entfällt |

Was das in der Praxis heißt:

- **LLM-Provider** haben keine geschlossene Liste. Sie versuchen jede Sprache, die du nennst, und die
  Qualität lässt nach, wo Trainingsdaten dünn sind, eine Zielsprache mit wenig Ressourcen verdient
  also ein menschliches Review. [Review-Flags](/docs/translation-safety#review-flags) zeigen auf die
  verdächtigsten Ergebnisse.
- **DeepL und Google Cloud Translation** haben eine geschlossene Liste, die vor einem Lauf geprüft
  wird. Wie LibreTranslate [maskieren sie Platzhalter](/docs/providers#deepl) und halten Werte
  mit ICU-Plural oder -Select zurück.
- **LibreTranslate** bedient die Modelle, die dein Server installiert hat.
- Einen `tone` oder ein Glossar, das ein Provider nicht umsetzen kann, meldet verbatra als Hinweis,
  nie stillschweigend. Siehe
  [Tonfall und Glossar über die Provider hinweg](/docs/providers#tonfall-und-glossar-über-die-provider-hinweg).

### Wie jeder Provider den Code bekommt

<AvailableFrom version="0.12.0" />

DeepL bekommt seine eigenen Varianten (`EN-GB`, `PT-BR`, `ES-419`, `ZH-HANT`) und lässt jede andere
Region oder Schrift weg; es hat kein generisches Englisch- oder Portugiesisch-Ziel, ein reines `en`-
oder `pt`-Ziel scheitert also vor jedem Request. Google Cloud Translation bekommt Chinesisch als
`zh-CN` oder `zh-TW` und `nb` als `no`. LibreTranslate bekommt nur die Sprache, außer brasilianischem
Portugiesisch und den beiden chinesischen Schriften. LLM-Provider bekommen den Code wie geschrieben,
plus den englischen Namen von Sprache, Schrift und Region, und werden angewiesen, in dieser Schrift
und Variante zu schreiben; siehe
[Namen von Sprache, Schrift und Region](/docs/translation-safety#namen-von-sprache-schrift-und-region).

Ist die eingebaute Zuordnung nicht, was du willst, setzt `localeMap` in den `options` des Providers
den genauen Code pro Locale. Die vollständige Zuordnung steht unter
[An den Provider gesendete Locale-Codes](/docs/providers#an-den-provider-gesendete-locale-codes).

## Unterstützung vor einem Lauf prüfen

<AvailableFrom version="0.12.0" />

Bevor etwas ausgegeben wird, beurteilt verbatra jede konfigurierte Locale anhand dessen, was es über
den Provider weiß, und [`verbatra doctor --locales`](/docs/cli/doctor#locale-unterstützung) gibt die
Urteile aus. Jede Locale bekommt eines von dreien:

- **supported**: Der Code, den verbatra sendet, steht in der Tabelle des Providers, oder der
  Provider ist ein LLM.
- **unverified**: Nur die Basissprache steht in der Liste, der Code kommt aus einem expliziten
  `localeMap`-Eintrag, oder der Provider ist ein LibreTranslate-Server, dessen Modelle nur aus seiner
  Live-Liste bekannt sind. Sie wird übersetzt, mit der Warnung `LOCALE_UNVERIFIED_BY_PROVIDER`.
- **unsupported**: Weder der Code noch seine Basissprache steht in der Liste. `translate`, `watch`
  und ein Retranslate eines einzelnen Keys lehnen den ganzen Lauf mit
  [`LOCALE_UNSUPPORTED_BY_PROVIDER`](/docs/error-codes#locale_unsupported_by_provider) ab.

Der ganze Lauf wird abgelehnt, nicht nur eine Locale, damit eine Pipeline nie wegen eines
Konfigurationsfehlers halb übersetzt endet. Lass die Locale mit `--locales` weg, oder, wenn der
Provider die Sprache nach dem Datum der Tabelle hinzugefügt hat, ordne sie in `localeMap` zu: Einem
expliziten Eintrag wird vertraut. Die mitgelieferten Tabellen sind datierte Kopien der Listen der
Anbieter (DeepL mit 125 Codes und Google mit 198, beide vom 2026-09-28); `verbatra doctor --live`
prüft stattdessen gegen die aktuelle Liste.

LLM-Provider akzeptieren jede Sprache, für sie wird also nichts abgelehnt. Ein Ziel außerhalb der
Sprachen, die LLMs bekanntermaßen gut übersetzen, bekommt die Warnung `LOCALE_NOT_WELL_TESTED` als
Anstoß, seine Ausgabe zu reviewen. Die Liste vergleicht die Basissprache, `pt-BR` zählt also als
Portugiesisch: Arabisch (`ar`), Chinesisch (`zh`), Niederländisch (`nl`), Englisch (`en`),
Französisch (`fr`), Deutsch (`de`), Hindi (`hi`), Indonesisch (`id`), Italienisch (`it`), Japanisch
(`ja`), Koreanisch (`ko`), Polnisch (`pl`), Portugiesisch (`pt`), Russisch (`ru`), Spanisch (`es`),
Schwedisch (`sv`), Türkisch (`tr`), Ukrainisch (`uk`) und Vietnamesisch (`vi`).

## Schriften und regionale Varianten

Ein Schrift- oder Regions-Subtag ändert, was der Provider gefragt wird, nicht, wie verbatra etwas
speichert:

| Deine Locale | DeepL | Google Cloud Translation | LibreTranslate | LLM-Provider |
| --- | --- | --- | --- | --- |
| `pt-BR` / `pt-PT` | `PT-BR` / `PT-PT` | `pt-BR` / `pt-PT` | `pt-BR` / `pt` | Portuguese (Brazil) / Portuguese (Portugal) |
| `es-419`, `es-MX` | `ES-419` | `es-419`, `es-MX` | `es` | Spanish (Latin America), Spanish (Mexico) |
| `zh-Hans` / `zh-Hant` | `ZH-HANS` / `ZH-HANT` | `zh-CN` / `zh-TW` | `zh-Hans` / `zh-Hant` | Chinese (Simplified) / Chinese (Traditional) |
| `sr-Latn` / `sr-Cyrl` | `SR` für beide | `sr-Latn` / `sr-Cyrl` | `sr` für beide | Serbian (Latin) / Serbian (Cyrillic) |

DeepL und LibreTranslate behalten eine Schrift nur für Chinesisch, `sr-Latn` und `sr-Cyrl` bekommen
also die Schrift, die die Engine für Serbisch schreibt. Für eine Sprache mit mehr als einer Schrift
ist ein LLM-Provider, dem die Schrift mit Namen genannt wird, die verlässliche Wahl.

Zwei Prüfungen berücksichtigen Schriften ebenfalls: Das Flag `LENGTH_RATIO_OUTLIER` gewichtet
Zeichen nach Schrift, kompakter chinesischer, japanischer oder koreanischer Text wird also nicht
wegen seiner Kürze markiert, und ein Glossarbegriff in einer Schrift ohne Leerzeichen zwischen
Wörtern wird als bloßes Enthaltensein abgeglichen.

## Plurale

<AvailableFrom version="0.12.0" />

verbatra liest, welche Pluralkategorien eine Sprache braucht, aus den CLDR-Regeln in den in Node.js
eingebauten ICU-Daten, Ordinalzahlen eingeschlossen, damit ist jede Sprache abgedeckt, die CLDR
kennt: Englisch hat zwei Kardinalkategorien, Russisch und Polnisch vier, Arabisch und Walisisch
sechs, Japanisch nur `other`. Für eine Locale, für die Node.js keine Regeln hat, wird für
Kardinalzahlen `one` und `other` angenommen. Die Prüfung `plural-rules` von
[`verbatra doctor`](/docs/cli/doctor) nennt so eine Locale.

Wie ein Plural korrekt bleibt, hängt vom Format ab:

- **i18next** kennzeichnet jede Form mit einem CLDR-Suffix (`items_one`, `items_few`). Fehlt der
  Quelle eine Kategorie, die das Ziel braucht, meldet der Lauf `PLURAL_CATEGORIES_INCOMPLETE`; mit
  `generatePlurals: true` und einem LLM-Provider schreibt verbatra die fehlenden Formen. Siehe
  [Eine Sprache hinzufügen](/docs/add-a-language#sprachen-mit-mehr-pluralkategorien).
- **next-intl und ARB** halten einen ganzen ICU-Plural in einem Wert, und ein Wert, dessen Zweige
  nicht zur Zielsprache passen, wird abgelehnt; siehe
  [Plural-Zweige je Zielsprache](/docs/translation-safety#plural-zweige-je-zielsprache).
- **Apple, Android und gettext** reichen genau die Formen durch, die jede Locale hat, und eine
  fehlende Form musst du von Hand ergänzen. gettext behält seinen `Plural-Forms`-Header wie
  geschrieben.

### Plural-Warnungen

<AvailableFrom version="0.12.0" />

[`verbatra check`](/docs/cli/check#pluralkategorien) und `verbatra doctor` warnen vor jedem Plural,
dem eine Kategorie fehlt, die seine Sprache verwendet, in jedem pluralfähigen Format außer gettext,
dessen Formen seinem eigenen Header folgen. DeepL, Google Cloud Translation und LibreTranslate
übersetzen die vorhandenen Formen, erzeugen aber nie neue.

## Sprachen, die von rechts nach links laufen

Arabisch, Hebräisch, Persisch, Urdu und andere Sprachen, die von rechts nach links laufen, brauchen
zum Übersetzen keine Sonderbehandlung: Ein Wert ist Text, er wird gelesen, gesendet, geprüft und so
zurückgeschrieben, wie er ist. verbatra fügt keine Richtungszeichen hinzu, entfernt keine und ordnet
nichts um. Was das für dich heißt:

- **Setz die Richtung in deiner App, nicht in den Strings**, mit dem Attribut `dir`, CSS oder der
  Layoutrichtung deiner Plattform. Die [Inline-Markup-Prüfung](/docs/translation-safety#inline-markup-parität)
  lehnt eine Übersetzung ab, die ein `dir`-Attribut hinzufügt, das die Quelle nicht hat.
- **Richtungsmarken sind Text** und dürfen wegfallen; prüf Übersetzungen, die eine brauchen.
  Offene Einbettungen, Überschreibungen oder Isolierungen (schließt die Quelle ihre) und neue
  Überschreibungen lösen [`BIDI_CONTROLS_CHANGED`](/docs/error-codes#bidi_controls_changed) aus.
- **Eine geänderte Platzhalter-Reihenfolge** löst nur `INTEGRITY_REORDERED` aus, weil eine andere
  Reihenfolge in einer anderen Sprache oft richtig ist.
- **Studio zeigt Werte von rechts nach links** für jede Locale, deren Schrift so läuft, fragt dazu
  den Browser nach der Richtung und geht sonst nach der wahrscheinlichen Schrift der Locale (`ku-Arab`
  von rechts nach links, `ku` von links nach rechts). Nur die Anzeige ändert sich.
- **`verbatra pseudo` hat keinen Rechts-nach-links-Modus**: Es testet die Layoutbreite, nicht die
  Spiegelung.

## Ressourcenarme Sprachen und lokale Modelle

Für eine Sprache, die dein gehosteter Provider schlecht abdeckt, gibt es drei Wege:

- **Ein lokales Modell über `openai-compatible` betreiben.** Es muss ein auf Anweisungen trainiertes
  Chat-Modell sein, das ein JSON-Objekt zurückgibt; siehe
  [Ein lokales Modell wählen](/docs/providers#ein-lokales-modell-wählen).
- **Ein spezialisiertes Übersetzungsmodell außerhalb von verbatra nutzen** und das Ergebnis über den
  [Roundtrip mit der Arbeitsmappe](/docs/manual-translation) zurückholen, der dieselben
  Integritätsprüfungen ausführt. Das sind Übersetzungsmodelle, keine Chat-Modelle, keines lässt sich
  also direkt an `openai-compatible` anschließen:
  [MADLAD-400](https://huggingface.co/google/madlad400-3b-mt) (Apache-2.0, über 400 Sprachen),
  [TranslateGemma](https://huggingface.co/google/translategemma-4b-it) (55 Sprachen,
  Gemma-Nutzungsbedingungen) und [NLLB-200](https://huggingface.co/facebook/nllb-200-distilled-600M)
  (etwa 200 Sprachen, aber CC-BY-NC-4.0, also nicht für ein kommerzielles Produkt). Prüf die Lizenz
  jedes Modells selbst, bevor du dich darauf verlässt.
- **Einen Menschen übersetzen lassen.** Der
  [Arbeitsablauf ohne maschinelle Übersetzung](/docs/human-only-workflow) funktioniert für jede
  Sprache.
