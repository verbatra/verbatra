title: The cache
description: What verbatra.cache.json reuses, how a fingerprint scopes it, and why it never fails a run.
---
verbatra keeps a local translation-memory cache, `verbatra.cache.json`, so a string it has already translated is never sent to a provider twice, even when its key changes. Where [the lock file](/docs/the-lock-file) tracks whether a key is up to date, the cache is keyed by content: it remembers the translation for a piece of source text, independent of which key holds it.

## What it reuses

On a run, before a key goes to the provider, verbatra looks it up in the cache by the hash of its current source content. A hit is served for free, so you never pay for it again. Because the lookup is by content, reuse survives cases the lock file cannot:

- **A renamed key.** Move a string from `home.title` to `landing.title` and its translation is reused, not re-translated.
- **Duplicate content.** Two keys with the same source content share one translation; the second is a cache hit.

A reused value is not trusted blindly. It still passes the same [integrity checks](/docs/translation-safety) against the current source before it is written, so a cached value that no longer fits its key is discarded and the key is translated fresh. Cache hits are reported per locale in the run summary, separate from the keys translated this run.

## Fuzzy reuse

Everything above is an exact match: the source text hashes to the value it hashed to before. Edit one character and that hash changes, so the string is a miss and goes back to the provider. Fuzzy reuse is an opt-in fallback for exactly that case, and it is off unless you ask for it:

```ts title="verbatra.config.ts"
export default defineConfig({
  // ...
  fuzzyCache: { enabled: true, threshold: 0.9 },
});
```

When a key misses, verbatra compares its current source against the source text of every entry in the same locale under the same fingerprint, and scores each one from `0` to `1` as the character edit distance over the length of the longer of the two strings. The closest entry at or above `threshold` is reused; everything below it goes to the provider as an ordinary miss. `threshold` runs from `0.5` to `1` and defaults to `0.9`, which is deliberately strict: on a 70 character sentence it tolerates a handful of edited characters, and on a five character button label it tolerates none at all. Lower it only once you have looked at what it starts letting through.

A fuzzy reuse is a translation of text that is no longer the source text, so it is never presented as an exact hit:

- It passes the same [integrity checks](/docs/translation-safety) as any other candidate value. A near match whose placeholders no longer fit the edited source is refused outright rather than patched up, and the key goes to the provider.
- It is counted and printed apart from exact hits, as `fuzzy-reused`, with the key, the score, and the earlier source text behind each one. `LocaleSummary.fuzzyHits` carries the same three things for SDK and `--json` callers.
- It is never written back into the cache. The reused value stays filed under the source it was actually produced for, so a later run cannot mistake it for an exact hit.

Scoring stays inside one fingerprint bucket, so a changed provider, model, tone or glossary does not start matching again through the back door. It is bounded too: entries whose length alone puts the threshold out of reach are discarded without being scored, no more than 256 of the entries that survive that are scored for any one key, and source text longer than 2000 characters is skipped entirely.

## The fingerprint

Every cached value is scoped to the translation context it was produced in: a short fingerprint over the provider, the model, the tone, and the glossary. Change any of them and prior entries stop matching, so a new tone or an edited glossary re-translates rather than serving a stale result. The format is deliberately not part of the fingerprint; a format change is caught by the integrity check on each hit instead.

## The file

`verbatra.cache.json` is a local, regenerable sidecar next to your lock file. `verbatra init` adds it to `.gitignore`, and `translate`, `watch` and `import` top up an existing `.gitignore` that is missing the entry, so a project scaffolded by an older version picks it up on the next run. Keep it out of version control: unlike the lock file it is a cost optimization, not a shared baseline. It never fails a run. A missing, corrupt, or oversized file degrades to an empty cache and is simply rebuilt on the next run. A file whose `version` this build does not recognize was written by a newer verbatra: it also degrades to an empty cache for the run, but is left on disk untouched rather than rebuilt, so upgrading is not destructive. The run reports a notice and otherwise proceeds normally. To rebuild it from scratch, delete the file.

Fuzzy reuse needs the source text itself, because a hash cannot be measured for similarity, so the file records each source string beside its translations. That is what schema version 2 carries, and it makes the file roughly as large as your source strings rather than a list of hashes. A version 1 file written by an older verbatra is carried forward rather than rejected: its translations keep working as exact hits immediately, and their source text fills back in as later runs touch them.

## Bypassing it

Pass `--no-cache` to [`translate`](/docs/cli/translate) or [`watch`](/docs/cli/watch) to skip the cache for a run: verbatra makes exactly the provider calls it would with no cache present, and leaves any existing cache file untouched. From the SDK, set `cache: false` on the `translate` or `watch` input. A dry run never reads or writes the cache regardless. `--no-cache` covers fuzzy reuse too. To keep exact reuse and turn off only the fuzzy fallback, leave `fuzzyCache` out of the config or set `enabled: false`.

## Limitation

Synthesized plural forms are not cached. When `generatePlurals` fills in a CLDR plural category the source lacks, that generated value is not recorded for reuse, so whenever a run does synthesize it the value comes from the provider, never the cache.
