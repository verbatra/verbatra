verbatra does not trust machine output, and it does not trust the strings it translates either.
Every result passes an integrity gate before it can be written, everything the gate rejects
surfaces as data instead of failing the run, and secrets are kept out of every error path. This
page covers each layer of that model.

## Untrusted strings and the prompt-injection boundary

verbatra never lets a translatable string act like an instruction to the AI. A translatable string
can contain text that looks like an instruction (a UI string that literally reads "ignore your
instructions"), so verbatra treats every one as untrusted input. The system rules sent to an LLM
provider are compile-time constants. All variable input, the entries to translate along with your
glossary and tone, travels only in the user-turn JSON data payload, never spliced into the
instruction channel. Provider output is constrained to a schema and validated as data: a malformed
response fails, and a response containing a key that was never requested fails the whole
sub-batch, because there is no safe partial accept around invented content.

## The integrity gate

A schema-valid translation can still be broken, so one gate recomputes the accept-or-reject
decision directly from the candidate value; the provider's own integrity report is never trusted.
The same gate runs on every write path: a provider-sourced translation, a workbook import row, and
a human-typed edit in Studio. It also runs per key on a reused value. When one translation is
served to several keys with the same source content (a [cache](/docs/the-cache) hit, or the copy
that makes identical text cost a single provider request), each key runs the gate against its own
source entry, and a key whose check fails is withheld rather than written. Sameness is decided by a
content hash that treats text as equal up to Unicode NFC normalization and LF line endings, so two
keys can match without being byte-identical. That is exactly why the gate is re-run per key.

- Placeholder integrity: the translated value must carry the same placeholders as its source,
  compared as a multiset (counts matter, order does not). Drop, add, or alter one and the candidate
  is rejected. What counts as a placeholder is defined per format; see [Formats](/docs/formats).
- ICU integrity: for the ICU formats (next-intl and ARB, which use ICU MessageFormat syntax for
  plurals and select statements), the translated value must still parse as a valid message. A
  candidate that keeps every placeholder but breaks the plural or select structure is rejected
  too. For these formats the placeholder comparison is also branch-aware: a placeholder fabricated
  inside one plural branch is caught even if it legitimately exists in another.
- Fabricated single-brace tokens: for the double-brace formats (i18next, ngx-translate, and YAML), a
  `{name}`-shaped token is ordinary literal text rather than interpolation, so it is not extracted as
  a placeholder and is not required to survive a translation. Inventing one is still rejected: a
  `{name}`-shaped token that appears in the candidate and never appeared in the source is a
  fabrication under any interpolation convention, which is what makes it safe to refuse without
  knowing the project's delimiters. The check runs in that one direction only, so a candidate that
  drops or changes the surrounding literal text is left alone.
- Inline markup parity: the translated value must carry the same inline HTML or XML tags as its
  source, and must carry them well formed. A dropped, invented, renamed, or unbalanced tag breaks
  the rendering of a string the way a dropped placeholder breaks its interpolation, so it is
  refused the same way. See [Inline markup parity](#inline-markup-parity) below.
- Degeneracy: the value must not be structurally degenerate, such as a repetition loop or a length
  that has run away from the source. This catches a model that collapsed into repeating a fragment
  even when every placeholder survived.
- Emptiness: a non-empty source may not be translated to an empty or whitespace-only value.
  Clearing a translation is a separate, deliberate act, and the workbook's `[[CLEAR]]` sentinel is
  the way to do it; see [Manual translation](/docs/manual-translation).

A rejected candidate is withheld as data, never written: it appears on the run summary as an
integrity mismatch, keeps its prior hash in [the lock file](/docs/the-lock-file), and is retried
next run. Withheld is also kept distinct from failed: a key nothing was translated for (the
provider call threw, or the key was still missing after the bounded repair round) is reported as a
provider failure, not an integrity mismatch. Both retry the same way.

On the source side, a source key whose own value is invalid ICU is set aside before translation
and reported, instead of being sent to the provider in a broken state.

### Inline markup parity

Rich text reaches a translatable string as inline markup: a `<b>` around part of an i18next `Trans`
block, an escaped `&lt;b&gt;` inside an Android `<string>`, an `<a href>` in a gettext catalog. None
of that is a placeholder, so before this nothing compared it.

Tags are compared as a multiset of tag names plus attribute names, which is what decides whether
something is a finding:

- Refused: a dropped tag, an invented tag, a renamed tag, a changed set of attribute names, markup
  that comes back unbalanced or mis-nested, such as `<b>a<i>b</b></i>`, and a tag that comes back
  nested inside another of the same name when the source had them as siblings, which is how two
  links silently become one.
- Accepted: the same tags in a different order, because translating a sentence moves its markup
  around, a changed attribute value, because a translated `title` or a localized `href` is a correct
  translation rather than a broken one (within the limits on URL, `srcdoc` and event handler values
  described below), and either spelling of a void element, so `<br>` and `<br/>` are one tag.
- Counted, not just noticed: two adjacent pairs merged into one (`<b>a</b> <b>b</b>` becoming
  `<b>a b</b>`) is refused, because the comparison cannot tell a cosmetic merge from two links
  collapsing into one.
- Compared exactly, so a case change is a finding. The HTML void elements (`<br>`, `<img>`, `<hr>`
  and the rest) need no closing tag in any letter case, so `<BR>` is recognised as one just like
  `<br>`.
- Refused when an attribute name is added or removed, which includes adding a `dir` attribute for a
  right-to-left target. Attribute values are free apart from those limits; the set of names is not.

A source with no markup at all is still protected against markup invented into it. The candidate is
refused for any tag pair, void element or self-closing tag it adds, for a closing tag with no
opening tag (`Hallo</div>`), and for an unclosed opening tag that carries anything beyond its name,
such as `<Enter onfocus=...>` or `<x-key onmouseover=...>`.

An unclosed `<Word>` with nothing but its name, where the name is only letters, digits, hyphens and
underscores, is a bracketed word, such as `<Enter>` in `Druecke <Enter>`. Bracketed words are set
aside on both sides before the source is judged, so a source that carries one is still compared: a
candidate that drops a `<b>` pair beside `<Enter>`, or invents a `<script>` pair beside it, is
refused. Once the source carries tags, bracketed words are counted like tags. Where it carries none,
a bracketed word the candidate adds is read as prose and accepted, unless its name, in any letter
case, is a standard HTML element (`Hallo <script>`), is `image`, which a parser turns into an
`<img>`, or contains a hyphen, which makes it a custom element (`Hallo <my-widget>`).

That name test is deliberately cautious, so an ordinary word that happens to be an element name,
such as `<Del>`, `<Option>`, `<Select>`, `<Input>` or `<Menu>`, is refused when a translation adds
it to a source that does not have it. The workaround is to keep the bracketed word in your source
string too: a translation that carries the same bracketed words as its source is accepted.

Comments, CDATA sections, declarations and processing instructions are not tags, and they are read
the way an HTML parser reads them, because that is where the values end up. `<!-->` and `<!--->` are
complete empty comments, a comment ends at the first `-->` or `--!>`, and a comment with no end
hides the rest of the value. `<![CDATA[`, `<!DOCTYPE html>`, any other `<!...`, `<?...` and a `</`
followed by anything but a letter, such as `</1 x>`, all end at the first `>`, while an empty `</>`
is dropped, as a parser drops it, and a numeric closing tag such as `</0>` is compared as a tag.
Each such construct is compared as a multiset of its text with runs of whitespace collapsed, so one
the candidate adds, drops or rewrites is refused, including a comment whose text was translated.
Tags after a construct's end are compared as usual, so `Hallo <![CDATA[><img src=x onerror=...>]]>`
is refused for both the construct and the `<img>`.

The content of a raw text element is text too, because that is how a parser reads it. After an
opening `script`, `style`, `title`, `textarea`, `xmp`, `iframe`, `noscript`, `noembed` or `noframes`
tag, everything up to its closing tag, in any letter case and followed by whitespace, `/` or `>`, is
text, and everything after `<plaintext>` is text to the end of the value. A tag written inside such
an element is not compared, and a quoted attribute value cannot reach across the closing tag to hide
what follows: `Füge ein <script><b x="</script><img src=x onerror=...>` is refused for the `<img>`.
Where a parser can read that content two ways, the candidate is refused unless it is the source
unchanged, with a detail such as `+<noscript>...</noscript>`: a `script` whose content opens `<!--`,
a `noscript` whose content holds a `<`, since whether scripting is enabled decides how it is read,
and any raw text element whose content holds a `<` after an `svg`, `math` or `select` tag, where it
may not be raw text at all. For the same reason, a CDATA section or an `image` tag in a value where
the source or the candidate opens `svg`, `math` or `select` is refused unless the candidate is the
source unchanged.

The check is deliberately quiet, but it reads tags the way an HTML parser does. A tag starts at `<`
or `</` followed by a letter or, for a numeric rich-text tag such as `<0>`, by digits. Its name runs
to whitespace, `/` or `>`, and a quoted attribute value may contain `>`. So `5 < 10`, `x <= y` and
an escaped `&lt;b&gt;` stay ordinary text, while `<support@example.com>` and `<abbr title="a > b">`
are tags, and a `<` that never reaches its `>` renders nothing and is not a tag. A candidate that
leaves a tag unfinished that way is still refused when its source finishes every tag, with a detail
naming the unfinished start, such as `+<a`. A source whose own tags are malformed is compared all
the same. After setting aside the tags the format reports as placeholders and any bracketed words, a
source counts as malformed when it has an opening tag that is never closed (void elements excepted),
a closing tag with no opening tag, or tags closed in the wrong order. Prose can trip this by
accident: in `a<b and c>d`, the run `<b and c>` is an opening `b` tag with the attributes `and` and
`c` that is never closed, so the source counts as malformed. For such a source only the nesting
check is skipped: its tags are compared as a multiset like any other, so a translation that keeps
`a<b and c>d` exactly is accepted, one that adds an `<img>` beside it is refused, and so is one that
translates the words inside the run (`a<b und c>d`), because a parser reads `und` as a new
attribute. No source is too large to compare either. A candidate is refused only once it carries
more than twice as many tags and constructs as its source, or more than 256 for a smaller source,
with the detail `+more than N inline tags` naming that limit.

Attribute values are free with three exceptions, which exist because a translated value ends up in a
page. The value of a URL attribute (`href`, `src`, `action`, `formaction`, `xlink:href`, `poster`,
`data`, `background`, `ping`, `cite`, `longdesc`, `srcset`, `manifest`, `codebase`, `archive`, and
the SVG animation attributes `to`, `from`, `values` and `by`) is read after decoding numeric
character references and `&colon;`, `&Tab;` and `&NewLine;` and ignoring tabs, line breaks and
leading control characters, and a `javascript:`, `vbscript:` or `data:` scheme in it is refused
unless the source carries that exact value on the same tag and attribute, with a detail such as
`+<a href="javascript:...">`. A `srcdoc` value and an event handler value such as `onclick` that the
source carries must come back byte for byte. A localized `href="/de/docs"` is accepted as before.

Two format-shaped limits follow from comparing whole values. For a format that packs several plural
arms into one value separated by a pipe (Vue I18n), a translation that adds the arms its language
needs repeats the source's markup and is refused. The same happens for an ICU-style plural
(`{count, plural, one {...} other {...}}`) in a format that stores it as plain text rather than
parsing it as ICU (i18next, ngx-translate and YAML): a translation with a different number of arms
than the source repeats or drops the markup inside them and is refused. In both cases the value is
withheld and the previous translation stays, so nothing is lost, but the arms have to be added
without also multiplying the markup.

The check also stands down per tag. A tag the format already reports as a placeholder (an XLIFF
inline element, a next-intl or ARB ICU rich-text tag) is left to the placeholder check, together
with as many closing tags as it has openings, and is never reported twice. An opening tag of that
kind that the candidate leaves unclosed is still refused, named by the closing tag it is missing,
such as `-</g>`. So is one whose nesting with the other tags no longer matches the source, such as a
`<b>` that comes back crossing the `<g>` it sat inside, and one the source carries only as text,
inside a comment or a raw text element, because moving it out would create the element. Every other
tag in the same value is still compared, including a surplus closing tag such as a second `</g>`. A
refusal names the tags behind it, each prefixed with `-` for one the source had and the candidate
dropped or `+` for one the candidate invented.

## Review flags

Passing the gate proves a translation is structurally safe, not that it is good, so a second,
advisory layer flags suspicious results for a human. A review flag never withholds a key and
carries one or more reason codes:

- `LENGTH_RATIO_OUTLIER`: the translation is far shorter or longer than its source (below 0.35x or
  above 3.0x trimmed length; very short sources are skipped). A nudge to look, not a verdict.
- `MAX_LENGTH_EXCEEDED`: the translation is longer than the absolute budget configured for its key
  under [`maxLength`](/docs/config-file). Counted in grapheme clusters, on the value exactly as
  written, and the boundary is inclusive, so a value of exactly the budget is not flagged. A key
  with no configured budget is never measured. Like every reason here it flags rather than blocks:
  an over-budget translation is still written and still locked, because a correct translation that
  overruns a layout budget beats no translation at all.
- `EQUALS_SOURCE`: the translation equals the source verbatim in a different target locale, and
  the source actually had translatable text.
- `GLOSSARY_TERM_MISSED`: a configured glossary term occurs in the source but its mapped target
  term is absent from the translation. Matching is case-insensitive, and the two sides are held to
  different standards on purpose. The source side requires a whole word, so the term `AI` is not
  counted as present inside `Airport` and cannot raise an expectation nobody was given. The target
  side only requires the term to appear somewhere in the translation, because a translated term
  legitimately fuses with the text around it: German compounds (`Benutzerkonto`), Korean particles
  (`계정을`), Japanese loanwords. Demanding a boundary there would flag correct translations in most
  of the languages you would keep a glossary for. A source term written in a script without word
  separators (Han, kana, Thai and similar) has no boundary to anchor to either, so it falls back to
  the same containment rule.
- `INTEGRITY_REORDERED`: the placeholder set matched exactly but landed in a different order than
  the source. Only ever fires on a translation the gate already accepted.
- `PROVIDER_DEGRADED`: the batch this key came from was gracefully degraded by the provider (a
  formality downgrade or an ignored glossary; in the current provider set, DeepL only).
- `FUZZY_CACHE_REUSE`: the value was never translated for this source text. It came from
  [the cache](/docs/the-cache) as a fuzzy reuse of an earlier, near-identical source that has since
  been edited. Similarity is measured in characters, and meaning is not a function of character
  distance: dropping a negation, inverting a modal or swapping a proper noun are all small edits
  that reverse a sentence, and no threshold separates them from a typo fix. So every fuzzy reuse
  carries this reason on every run, whatever it scored. Only ever fires when `fuzzyCache` is
  enabled.

A value reused from [the cache](/docs/the-cache), and a value fanned out to a key that shares its
source text, run through the same review heuristics as a freshly translated one.

Flagged keys surface per locale as `needsReview` on the run summary, and they feed the
needs-review queue: the CLI prints the count, the Excel workbook carries the same signal in its
review columns, and Studio's Review page lists the flagged keys for working through; see
[Review in Studio](/docs/review-in-studio). The only way to clear a flag is to fix the underlying
translation.

## The token budget

Provider spend should have a ceiling you set, not one you discover on the invoice. With
`maxTokens` configured, verbatra tracks cumulative token usage across the whole run and checks it
after each completed sub-batch. What happens at the ceiling is `budgetBehavior`:

- `warn` (the default): the run continues and the summary flags that the budget was exceeded.
- `stop`: no further provider calls are made; every remaining candidate is withheld as
  `budgetWithheld`, keeps its prior lock hash, and is retried next run.

The sub-batch that crosses the ceiling is never undone. Under `warn` the budget never changes the
command's exit code. Under `stop` it can: a locale that had keys withheld is reported as `partial`
when some keys still landed and `failed` when none did, and both exit `1`. With a provider that does not report token usage (DeepL), the guardrail is honestly
inert: the summary marks it unsupported instead of faking a count.

## Errors never leak

API keys come only from environment variables, never from config or arguments, so there is no key
in any value verbatra handles. When a provider SDK call fails, the raw error (which can carry
request headers or credentials) is discarded, never bound, logged, or re-thrown; in its place
verbatra raises a structured error with a stable code (such as `RATE_LIMITED`, `TIMEOUT`, or
`AUTH_FAILED`) and a static, secret-free message. The same rule holds across the run: notices and
summaries carry codes and counts, not secrets.

## Where you see it

All of this is data on the run summary, per locale: translated keys, integrity mismatches,
provider failures, budget-withheld keys, invalid-ICU source keys, review flags, and notices.
Nothing is hidden, and one locale's failure never stops the others. See
[How it works](/docs/how-it-works) for where each check sits in the pipeline.
