Was das Tool verbatra (CLI, SDK, Studio und MCP-Server) von deinem Rechner oder deiner CI schickt,
für ein Security- oder Legal-Review. Für diese Website gilt ihre [Datenschutzerklärung](/privacy).

## Die kurze Antwort

- **Keine Telemetrie**, keine Update-Prüfung und kein verbatra-Server, den es kontaktieren könnte.
- **Ein einziges Ziel nach außen: dein Provider**, nur wenn ein Befehl übersetzt; keins mit
  `provider: { id: "none" }`.
- **Gesendet wird nur, was übersetzt werden muss**: keine unveränderten Keys, keine Cache-Treffer,
  keine geschützten Keys.
- **Alles andere bleibt lokal**: Studio auf `127.0.0.1`, der MCP-Server über stdio.
- **API-Keys kommen nur aus Umgebungsvariablen** und tauchen nie in einer Meldung auf.

## Wie die Daten fließen

```text
 your project (local disk)                               provider (only on translate, watch,
                                                         SDK retranslateEntry, or a Studio /
 +-----------------------------------------+             MCP retranslate or translate-pending)
 | locale files, verbatra.config.ts,       |   HTTPS     +--------------------------+
 | glossary          -- read by verbatra --|------------>| Anthropic / OpenAI /     |
 |                                         |  changed    | Gemini / DeepL / Google  |
 | verbatra.lock.json, provenance file,    |  strings    | or your own server       |
 | verbatra.cache.json, .verbatra-local/   |<------------| (self-hosted)            |
 |                 -- written by verbatra  | translations+--------------------------+
 +-----------------------------------------+
        |                        |
        | 127.0.0.1 only         | stdio
        v                        v
  Studio in your browser   MCP client (your AI agent)
```

Nur der Pfeil zum Provider überquert deine Netzwerkgrenze.

## Wann ein Request gemacht wird

Nur `translate`, `watch`, `retranslateEntry` aus dem SDK und die Aktionen Retranslate und Translate
Pending von Studio und dem MCP-Server (mit `--allow-spend`) rufen einen Provider auf. Alles andere,
Probeläufe und Schätzungen eingeschlossen, ist lokal, außer `verbatra doctor --live`: Es ruft die
Sprachliste von DeepL, Google Cloud Translation oder LibreTranslate ab und sendet dabei deinen
API-Key und sonst nichts.

Ein Lauf von `translate` sendet nur Keys, die gegenüber [der Lock-Datei](/docs/the-lock-file) fehlen
oder geändert sind, abzüglich der Treffer im [Cache](/docs/the-cache), und geteilten Text nur
einmal. Ein veralteter Key, den ein Mensch geschrieben hat, wird nur für einen Vorschlag mit
`humanEdits: "suggest"` gesendet, ein gepinnter Key nie
([Menschliche Übersetzungen behalten](/docs/protecting-human-translations)).

Jeder Request beginnt mit einem DNS-Lookup des Provider-Hosts, dein Resolver sieht diesen Namen also.

## Was jeder Provider bekommt

| Provider | Was gesendet wird | Wohin es geht |
| --- | --- | --- |
| `anthropic`, `openai`, `gemini`, `openai-compatible` | Pro Key: der Key-Name, der Quelltext und die Beschreibung oder Bedeutung, die deine Quelldatei mitführt (eine ARB-`description`, eine XLIFF-Notiz, ein gettext-Kommentar). Pro Request: die Quell- und Zielcodes (nach [`localeMap`](/docs/providers#an-den-provider-gesendete-locale-codes)) und ihre englischen Namen, dein `tone`, die Glossarbegriffe der Ziel-Locale, die Pluralkategorien des Ziels, wenn ein Batch Plurale enthält, die festen Anweisungen von verbatra, der Modellname und ein Limit für Output-Tokens. | `api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com` oder die `baseUrl`, die du konfiguriert hast. Eine `*_BASE_URL`-Variable leitet die gehosteten um, siehe [Netzwerkrichtlinie](/docs/network-policy#gehostete-provider). |
| `deepl` | Der Quelltext jedes Keys, mit Platzhaltern als nummerierte Markierungen in einem ignorierten `<x>`-Tag (ein Wert, dessen Platzhalter nicht geschützt werden können, wird nicht gesendet) <AvailableFrom version="0.12.0" />, die Sprachcodes, eine Formalitätsstufe, wenn dein `tone` bei einem bezahlten Key eine verlangt, und deine `glossaryId`. Keine Key-Namen, Beschreibungen oder Glossarbegriffe. | `api.deepl.com`, oder `api-free.deepl.com` für einen Key, der auf `:fx` endet. |
| `google-translate` | Der Quelltext jedes Keys, mit Platzhaltern als nummerierte Markierungen in einem `translate="no"`-Span (ein Wert, dessen Platzhalter nicht geschützt werden können, wird nicht gesendet) <AvailableFrom version="0.12.0" />, und die Sprachcodes. | `translation.googleapis.com` |
| `libretranslate` | Der Quelltext jedes Keys, mit Platzhaltern durch nummerierte Markierungen ersetzt (ein Wert mit ICU-Syntax wird nicht gesendet), die Sprachcodes und `LIBRETRANSLATE_API_KEY`, wenn gesetzt. | Die `baseUrl`, die du konfiguriert hast. |
| `none` | Nichts. | Nirgendwohin. |

Die SDKs senden außerdem Header mit Bibliothek, Betriebssystem und Node.js-Version. Dein API-Key geht nur an den konfigurierten
Endpunkt (`google-translate` sendet ihn im Query-String `?key=`). Behandle alles in einem
Quell-String, einer Beschreibung oder dem Glossar als gesendet.

## Schutz für sensible Inhalte

<AvailableFrom version="0.12.0" />

`sensitiveData` durchsucht vor jedem Request genau das, was ein Provider laut der Tabelle oben bekommt. Die Standard-Detektoren finden API-Keys, E-Mail-Adressen, IBANs und Kartennummern; `phone`, `ip` und `private-host` schaltest du bei Bedarf zu, und `patterns` ergänzt eigene Begriffe, etwa Codenamen. Damit die Laufzeit begrenzt bleibt, wird ein Muster abgelehnt, das eine Gruppe mit einer Wiederholung oder Alternative wiederholt, mehr als ein `*`, `+` oder `{n,}` enthält oder zu oft verzweigt; es liest nur die ersten 2.000 Zeichen eines Felds.

| `mode` | Wirkung |
| --- | --- |
| `warn` | Sendet wie gewohnt; ein Hinweis nennt die Keys. |
| `block` | Hält den Key zurück, die Locale endet also `partial`. |
| `redact` | Sendet für jeden Treffer im Wert ein Token und setzt den Treffer wieder ein; ein Treffer in einer Beschreibung oder Bedeutung geht als `[redacted]` hinaus. Ein Treffer im Key-Namen oder ein Token, das nicht genau einmal zurückkommt, hält den Key zurück. |

`block` und `redact` lassen außerdem einen passenden Glossarbegriff weg. Standardmäßig ist der Schutz aus; `verbatra init` schreibt `warn`. Bei einem Fehlalarm trägst du den Text in `allow` ein oder entfernst seinen Detektor. `verbatra check --sensitive` führt dieselbe Prüfung ohne Key aus. Namen in freiem Text werden nicht gefunden.

## Was lokal geschrieben wird

| Datei | Enthält | Committen? |
| --- | --- | --- |
| Deine Locale-Dateien | die Übersetzungen | ja |
| `verbatra.lock.json` | einen Hash jedes Quell-Strings, aus dem eine Übersetzung entstand | ja |
| `verbatra.provenance.json` | pro Key, welcher Schreibpfad den Wert erzeugt hat, bei maschineller Ausgabe Provider und Modell, und eine etwaige Review-Entscheidung samt Namen des Reviewers. Kein übersetzter Text, keine Zeitstempel. | ja |
| `verbatra.cache.json` | Quelltext und seine Übersetzungen, pro Provider, Modell, Tonfall, Glossar und `localeMap` | nein, `verbatra init` trägt es in die `.gitignore` ein |
| `.verbatra-local/` | Status, Review-Flags und Token-Verbrauch des letzten Laufs, erzeugte Pseudolocales und Schreibsperren | nein, ignoriert |
| `.env`, `.env.local` | deine API-Keys, falls du sie dort ablegst | nie, `verbatra init` ignoriert beide |

## API-Keys

Keys kommen nur aus [Umgebungsvariablen](/docs/providers#keys-kommen-aus-der-umgebung). Provider-Fehler
und CLI-Ausgaben ersetzen den Wert jeder bekannten Key-Variable und alles, was wie ein API-Key
aussieht, durch `[REDACTED]`.

## Studio und MCP

**Studio** bindet nur an `127.0.0.1`, weist anderen `Host` oder `Origin` ab, verlangt das Token, das
es beim Start ausgibt, und seine Content-Security-Policy blockiert Abrufe aus dem Internet.

**Der MCP-Server** spricht über stdio und öffnet keinen Port. Seine Lese-Tools geben deine Strings,
dein Glossar und deinen Status heraus, außer er läuft mit
[`--redact-values`](/docs/cli/mcp#redacted-values): Dann ist jeder Wert eine Markierung. Key-Namen,
Commit-Betreffs und Pfade werden nicht geschwärzt, und ein Agent, der gezielt sondiert, etwa über
Glossar-Schreibvorgänge, kann weiter etwas über Werte erfahren.

**Historie der Locale-Dateien.** `history.list` liefert für jeden Commit Hash, Datum, Autorname
(fehlt unter `--redact-values`), Betreff und geänderte Pfade, nie die E-Mail.

Wäg das ab: Ein MCP-Client oder ein Browser-Agent, der Studios `--expose-agent-tools` nutzt, ist
meist ein KI-Assistent, und was er liest, geht an sein Modell, unter den Bedingungen dieses
Anbieters. Studios Agent-Tools werden nie geschwärzt: Ein Agent, der den Tab steuert, kann die
Seite ohnehin lesen.

## KI-erzeugte Übersetzungen und Provenance

Artikel 50 des EU AI Act legt Transparenzpflichten für KI-Systeme fest, die Text erzeugen
([AI Act Service Desk, Artikel 50](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-50)).
Ob er für dein Produkt gilt, ist eine Frage für deine Rechtsberatung. verbatra gibt dir ein
Protokoll: Jeder Wert, den ein Provider erzeugt hat, trägt die Herkunft `machine`, mit Provider und
Modell; siehe
[Herkunft: wer welchen Wert geschrieben hat](/docs/the-lock-file#herkunft-wer-welchen-wert-geschrieben-hat).

### Prüfdatei

<AvailableFrom version="0.12.0" />

`verbatra report provenance --json` macht aus diesem Protokoll eine Prüfdatei pro Key; siehe
[Nachweis maschineller Übersetzungen festhalten](/docs/provenance-evidence).

## Checkliste für ein AVV- oder NDA-Review

1. Entscheide, ob Strings dein Netzwerk verlassen dürfen. Wenn nicht, nimm den Provider `none` oder
   einen selbst gehosteten Server und leg `VERBATRA_NETWORK_POLICY=local-only` in der CI fest.
2. Nimm für einen gehosteten Provider bei allem Vertraulichen ein bezahltes Kontingent.
3. Unterschreib die Auftragsverarbeitungsbedingungen des Anbieters, mit Zero Retention, wenn du sie
   brauchst.
4. Prüf, was deine Quelldateien senden: Key-Namen, Beschreibungen und das Glossar (`verbatra check --sensitive`).
5. Halte API-Keys in einem Secret Store oder einer ignorierten `.env` und führ `verbatra doctor` aus.
6. Entscheide, welche KI-Agenten Studio oder den MCP-Server nutzen dürfen und ob er
   `--redact-values` braucht.
7. Committe `verbatra.provenance.json` und archiviere `verbatra report provenance --json` pro
   Release.
