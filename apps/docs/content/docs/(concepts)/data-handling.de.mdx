Diese Seite handelt vom Tool verbatra: der CLI, dem SDK, Studio und dem MCP-Server, die auf deinem
Rechner oder in deiner CI laufen. Sie beantwortet die Frage, die ein Security- oder Legal-Review
zuerst stellt: Was verlässt den Rechner? Die Website, die du gerade liest, ist ein eigenes Thema und
wird in der [Datenschutzerklärung](/privacy) der Website behandelt.

## Die kurze Antwort

- **Keine Telemetrie.** verbatra hat keine Analytics, kein Nutzungs-Reporting, kein
  Crash-Reporting und keinen Update-Check. Es kontaktiert nie einen verbatra-Server, denn es gibt
  keinen.
- **Ein einziges Ziel nach außen: dein Provider.** Die einzigen Netzwerk-Requests, die verbatra
  macht, sind Übersetzungs-Requests an den Provider, den du konfiguriert hast, und nur, wenn ein
  Befehl tatsächlich übersetzt. Mit `provider: { id: "none" }` macht es gar keine.
- **Gesendet wird nur, was übersetzt werden muss.** Keys, die unverändert sind, schon im
  Translation Memory stehen oder für einen Menschen zurückgehalten werden, erreichen den Provider
  nie.
- **Alles andere bleibt lokal.** Locale-Dateien, die Lock-Datei, die Provenance-Datei, das
  Translation Memory und der Laufstatus sind Dateien in deinem Projekt. Studio lauscht nur auf
  `127.0.0.1`, und der MCP-Server spricht über stdio, nicht über einen Netzwerk-Port.
- **API-Keys kommen nur aus Umgebungsvariablen** und tauchen nie in einer Fehlermeldung auf.

## Wie die Daten fließen

```text
 dein Projekt (lokale Platte)                            Provider (nur bei translate,
 +-----------------------------------------+             watch oder einem Retranslate)
 | Locale-Dateien, verbatra.config.ts,     |   HTTPS     +--------------------------+
 | Glossar         -- gelesen von verbatra-|------------>| Anthropic / OpenAI /     |
 |                                         |  geänderte  | Gemini / DeepL / Google  |
 | verbatra.lock.json, Provenance-Datei,   |  Strings    | oder dein eigener Server |
 | verbatra.cache.json, .verbatra-local/   |<------------| (openai-compatible)      |
 |              -- geschrieben von verbatra| Ergebnisse  +--------------------------+
 +-----------------------------------------+
        |                        |
        | nur 127.0.0.1          | stdio
        v                        v
  Studio in deinem Browser  MCP-Client (dein KI-Agent)
```

Der Pfeil zum Provider ist der einzige, der deine Netzwerkgrenze überquert. Die beiden Pfeile unten
bleiben auf deinem Rechner, aber lies den Abschnitt [Studio und MCP](#studio-und-mcp): Was ein
KI-Agent darüber liest, geht dorthin, wohin dieser Agent es schickt.

## Wann ein Request gemacht wird

Einen Provider aufrufen können: `translate` und `watch`, das `retranslateEntry` des SDK und die
Aktionen zum Neu-Übersetzen und zum Übersetzen offener Keys in Studio und im MCP-Server. Studio und
der MCP-Server bieten diese Aktionen nur an, wenn du sie mit `--allow-spend` startest. Alles andere,
darunter `check`, `diff`, `doctor`, `export`, `import`, `tmx`, `extract`, `pseudo`, `types`,
`translate --dry-run` und `translate --estimate`, arbeitet mit lokalen Dateien und sendet nichts.

Ein `translate`-Lauf sendet nur die Keys, die gegenüber [der Lock-Datei](/docs/the-lock-file)
fehlen oder geändert sind, abzüglich aller Keys, die das
[Translation Memory](/docs/the-cache) schon beantwortet. Keys mit identischem Quellinhalt werden
einmal gesendet.

## Was jeder Provider bekommt

| Provider | Was gesendet wird | Wohin es geht |
| --- | --- | --- |
| `anthropic`, `openai`, `gemini`, `openai-compatible` | Für jeden zu übersetzenden Key: der Key-Name, der Quelltext und die Beschreibung oder Bedeutung, die deine Quelldatei dafür mitführt (zum Beispiel eine ARB-`description`, eine XLIFF-Notiz oder ein gettext-Kommentar). Pro Request: die Quell- und Ziel-Locale-Codes (nach deiner [`localeMap`](/docs/providers#an-den-provider-gesendete-locale-codes)) und ihre englischen Sprachnamen, dein `tone`, das komplette Projekt-Glossar, die Pluralkategorien der Zielsprache, wenn der Batch Plural-Keys enthält, die festen Anweisungen von verbatra, der Modellname und ein Limit für Output-Tokens. | `api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com` oder die `baseUrl`, die du für `openai-compatible` konfiguriert hast. Eine `*_BASE_URL`-Variable leitet die gehosteten um, siehe [Netzwerkrichtlinie](/docs/network-policy#gehostete-provider). |
| `deepl` | Der Quelltext jedes Keys ohne Platzhalter, die Quell- und Zielsprachcodes, eine Formalitätsstufe, wenn dein `tone` bei einem bezahlten Key eine verlangt, und deine `glossaryId`, falls gesetzt. Keine Key-Namen, keine Beschreibungen und keine Glossar-Begriffe: DeepL-Glossare liegen in deinem DeepL-Konto. | `api.deepl.com`, oder `api-free.deepl.com` für einen Key, der auf `:fx` endet. |
| `google-translate` | Der Quelltext jedes Keys ohne Platzhalter und die Quell- und Zielsprachcodes. Keine Key-Namen, keine Beschreibungen, kein Glossar. | `translation.googleapis.com` |
| `none` | Nichts. Es wird kein Provider gebaut und kein Key gelesen. | Nirgendwohin. |

`maxLength`-Grenzen werden auf deinem Rechner geprüft und nie gesendet. Der HTTP-Client jedes
Providers hängt außerdem seine üblichen Request-Header an, die die Client-Bibliothek und ihre
Version nennen und, bei den meisten, dein Betriebssystem und deine Node.js-Version. Der Request
trägt deinen API-Key zu dem Provider, zu dem er gehört, und zu niemandem sonst.

Behandle alles in einem Quell-String, einer Beschreibung oder dem Glossar als an den Provider
gesendet. Wenn ein String dein Netzwerk nicht verlassen darf, darf er nicht in einer Datei stehen,
die verbatra mit einem gehosteten Provider übersetzt.

braucht, deinen eigenen Server oder gar keine maschinelle Übersetzung.

## Strings im Haus behalten

- **Keine maschinelle Übersetzung.** `provider: { id: "none" }` macht verbatra zu einem rein
  lokalen Tool: Keys werden aus dem Translation Memory gefüllt oder von Menschen über Export und
  Import. Siehe [Rein menschlicher Workflow](/docs/human-only-workflow).
- **Dein eigenes Modell.** `openai-compatible` schickt Requests an die `baseUrl`, die du setzt,
  etwa Ollama, LM Studio oder vLLM auf deinem Rechner oder in deinem Netz. Siehe
  [Provider](/docs/providers).
- **Erzwing es.** Eine [Netzwerkrichtlinie](/docs/network-policy) wie `local-only` lässt verbatra
  jeden Provider-Host außerhalb deines Netzes ablehnen, bevor ein Request rausgeht, und
  `VERBATRA_NETWORK_POLICY` legt sie aus der Umgebung fest, sodass die Config eines Repositorys sie
  nicht lockern kann.

Alle drei gibt es ab verbatra 0.12.0.

## Was lokal geschrieben wird

| Datei | Enthält | Committen? |
| --- | --- | --- |
| Deine Locale-Dateien | die Übersetzungen | ja |
| `verbatra.lock.json` | einen Hash jedes Quell-Strings, aus dem eine Übersetzung entstand | ja |
| `verbatra.provenance.json` | pro Key, welcher Schreibpfad den Wert erzeugt hat (`machine`, `memory`, `human`, `import` und weitere), bei maschineller Ausgabe Provider und Modell, und ob er reviewt wurde. Kein übersetzter Text und keine Zeitstempel. | ja |
| `verbatra.cache.json` | das Translation Memory: Quelltext und seine Übersetzungen, pro Provider, Modell, Tonfall und Glossar | nein, `verbatra init` trägt es in die `.gitignore` ein |
| `.verbatra-local/run-status.json` | Ergebnis, Review-Flags und Token-Verbrauch des letzten Laufs pro Locale | nein, über `.verbatra-local/` ignoriert |
| `.verbatra-local/pseudo/` | erzeugte Pseudolocales | nein |
| `.env`, `.env.local` | deine API-Keys, falls du sie dort ablegst | nie, `verbatra init` ignoriert beide |

`verbatra init` schreibt eine `.env.example` ohne Key darin. `translate`, `watch`, `doctor`,
`studio` und `mcp` lesen `.env` und `.env.local` aus dem Arbeitsverzeichnis, ohne bereits gesetzte
Variablen zu überschreiben. Ein Key wird nie aus der Config-Datei oder einem
Kommandozeilen-Argument gelesen.

## API-Keys

Jeder Provider liest eine Umgebungsvariable, aufgelistet unter
[Provider](/docs/providers#keys-kommen-aus-der-umgebung). Jede Fehlermeldung eines Providers läuft
durch einen Filter, der den Wert jeder Key-Variable, die verbatra kennt, einschließlich der, die du
für `openai-compatible` mit `apiKeyEnvVar` benennst, und alles, was wie ein gängiger API-Key
aussieht, durch `[REDACTED]` ersetzt. Eine Meldung nennt die Variable, nie ihren Wert.

## Studio und MCP

**Studio** ist ein Webserver auf deinem eigenen Rechner. Er bindet an `127.0.0.1` und verweigert den
Start, wenn er woanders gebunden landet, lehnt jeden Request ab, dessen `Host` nicht `127.0.0.1` auf
seinem Port ist oder der von einem anderen `Origin` kommt, und verlangt das zufällige Token, das er
beim Start ausgibt. Seine Content-Security-Policy erlaubt dem Dashboard, Code und Daten nur von
genau diesem Server zu laden, die Seite holt also nichts aus dem Internet. Studio zeigt die Strings
deines Projekts in deinem Browser und liest die Git-Historie des Projekts, indem es lokal `git log`
ausführt.

**Der MCP-Server** spricht über stdio mit seinem Client und öffnet keinen Port. Seine Lese-Tools
geben die Strings, das Glossar und den Status deines Projekts an den verbundenen MCP-Client zurück.

Das ist der eine Punkt, den du sorgfältig abwägen solltest: Ein MCP-Client oder ein Browser-Agent,
der Studios `--expose-agent-tools` nutzt, ist meist ein KI-Assistent, und was er liest, geht an das
Modell dahinter, zu den Bedingungen dieses Anbieters. verbatra kann das weder sehen noch
einschränken. Verbinde einen Agenten nur, wenn sein Anbieter für diese Strings akzeptabel ist.

## KI-erzeugte Übersetzungen und Provenance

Artikel 50 der EU-KI-Verordnung (AI Act) legt Transparenzpflichten für KI-Systeme fest, die Text
erzeugen, darunter in manchen Fällen die Kennzeichnung solcher Ausgaben als künstlich erzeugt
([AI Act Service Desk, Artikel 50](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-50)).
Ob und wie er für dein Produkt gilt, ist eine Frage für deine Rechtsberatung, nichts, was verbatra
entscheidet.

Was verbatra dir gibt, ist ein Nachweis. Jeder Wert, den ein Provider erzeugt hat, wird mit dem
Ursprung `machine` in `verbatra.provenance.json` festgehalten, samt Provider und Modell, bis der Wert
neu geschrieben wird. Die Freigabe oder Ablehnung durch einen Reviewer wird daneben vermerkt. Werte
von Menschen (`human`, `import`) und aus dem Translation Memory (`memory`, `fuzzy`) werden als solche
festgehalten. Siehe
[Herkunft: wer welchen Wert geschrieben hat](/docs/the-lock-file#herkunft-wer-welchen-wert-geschrieben-hat).

## Checkliste für ein AVV- oder NDA-Review

1. Entscheide, ob Strings dein Netz überhaupt verlassen dürfen. Wenn nicht, nimm
   `provider: { id: "none" }` oder einen selbst gehosteten `openai-compatible`-Server und leg
   `VERBATRA_NETWORK_POLICY=local-only` in der CI fest.
2. Ist ein gehosteter Provider erlaubt, wähl ihn und sein Kontingent anhand der Tabelle oben: für
   alles Vertrauliche ein bezahltes, kein kostenloses.
3. Unterschreib die Bedingungen des Anbieters zur Auftragsverarbeitung und frag nach Zero Data
   Retention, wenn deine Richtlinie das verlangt.
4. Prüf, was deine Quelldateien mitschicken: Key-Namen, Beschreibungen und Kommentare sowie das
   Glossar gehen mit jedem Request an LLM-Provider.
5. Halte API-Keys in deinem CI-Secret-Store oder einer ignorierten `.env` und führ
   `verbatra doctor` aus, um Provider, Key-Variable und Netzwerkrichtlinie zu bestätigen.
6. Entscheide, welche KI-Agenten sich, wenn überhaupt, mit Studio oder dem MCP-Server verbinden
   dürfen, zu den Bedingungen ihres Anbieters.
7. Committe `verbatra.provenance.json`, damit der Nachweis maschinell erzeugter Werte mit deinem
   Code mitreist.
