See how one translation key changed from commit to commit with `keyHistory` and the `history.keyRevisions` MCP tool.

- **What you get:** `keyHistory({ config, locale, key })` lists the commits in which the key's value changed in a target locale, newest first. Each revision has the commit, author date, author name (never the email), subject, the value, where it came from (`origin`, read from the provenance file as committed), whether the key's source text has changed since (`sourceChanged`, from the committed lock-file) and a word-level `diff`. A value in the working tree that is not committed comes back as `workingTree`; when the file on disk cannot be read, for example during a merge conflict, the revisions still come back and `workingTreeUnreadable` is set. `history.keyRevisions` returns the same to an MCP client, read-only.
- **Keys are scrubbed:** every value and both sides of every diff pass `redact`. A value that held an API key comes back with `[REDACTED]` and `valueRedacted: true` and must not be offered for restore. Under `--redact-values`, `history.keyRevisions` replaces values with markers and leaves out word diffs, commit subjects and author names.
- **How far it reads:** up to 200 commits (50 by default), four files at a time, and it starts no new read after 30 seconds; a git call already running keeps its own 10 second limit. A file is parsed only up to 64 KiB for yaml, 128 KiB for xliff, android-xml, resx and apple-strings, and 1 MiB for the other formats, and parsing stops after 3 seconds per call. A commit above those limits, one that cannot be read or parsed, or one with a value over 4096 characters is skipped and counted in `unreadableRevisions`. A commit is only listed as a change when the commit before it was read, so `truncated` also says when a commit could not be compared. `truncated` is also set for a shallow clone.
- **Limits:** renames are not followed, a commit that removes the key is not listed, a change a merge brought in appears on the merge commit, and a key renamed in the source looks new. `apple-strings` also reads the `.stringsdict` file, and `apple-xcstrings` is read for the one locale.
- **Careful with the repository:** it takes a locale and a key, never a path, and the key never reaches git. It runs git with the same safeguards as `localeGitStatus` and pins the log encoding to UTF-8, reads files with `git cat-file blob` and parses them in memory. Author names and subjects lose control and bidirectional formatting characters.
- **`localeHistory` and `history.list` reasons:** both now answer `dubious-ownership`, `bare-repository`, `unsafe-config` and `git-too-old` with `available: false` instead of an empty list. If you map every `LocaleHistoryUnavailableReason` in TypeScript, add those four.
