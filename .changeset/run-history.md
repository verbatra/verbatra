Keep a local history of finished runs, with the cost frozen at the rates of the day, and read it with `runHistory` and the `usage.history` MCP tool.

- **What gets recorded:** every `translate`, `watch`, Studio or MCP translate-pending run, `retranslateEntry` call and `retranslateEntries` batch that left a trace adds one record to `.verbatra-local/run-history.jsonl`: the time, what triggered it, the provider and model, the token usage, the cost, and per locale the counts of translated keys, cache hits, fuzzy hits, generated plural forms, pruned keys, integrity refusals and provider failures. A record holds counts only, never a key name or a text, and the file stays out of git. A dry run is not recorded, a run that left no trace (a `watch` cycle with nothing to do) is not recorded, and a failed or refused run is. A batch of retranslations is one record, and a retranslate record's `entries` counts the entries attempted, a failed provider call included. The newest 1,000 are kept.
- **Cost is frozen:** the `rates` the config held when the run ended are applied then and stored with their currency and `asOf` date, so a later rate change never rewrites an old run. Token-billed providers are priced from the usage they reported. DeepL and Google Cloud Translation report none, so their cost is an estimate from the source characters sent, marked `source-characters`, with the same caveats as `--estimate`; keys the provider failed on are not counted. Where no figure exists the record says so instead of showing zero: `no-rate-on-file`, `rate-unit-mismatch`, `no-usage` (keys were sent and the provider reported no tokens) and `not-billed` (a self-hosted provider or `none`, which carries no `basis` either). A run that sent nothing, such as one served from the cache, is a real zero. When some locales reported usage and others sent keys and reported none, the amount covers only what was reported and carries the caveat `USAGE_PARTIAL`, a lower bound; a locale that reported for only some of its sub-batches cannot be told apart.
- **Coverage:** after the run, one `check` over the locales it touched adds `missing`, `stale` and `upToDate` to each locale. When that pass fails the record says `coverageUnavailable` and still lands.
- **Reading it:** `runHistory({ cwd, limit })` returns the newest records first (50 by default, 200 at most), the number of records the file holds, `unreadableRecords` for lines it could not read, and `unavailable` when the whole file could not be read. `usage.history` returns the same to an MCP client, read-only, with an output schema in both value modes. The result schema is published as `run-history-result.json`.
- **Never in the way of a run:** a bad line, one with an invalid byte included, is dropped alone and counted, and the next record rewrites the file without it. A file that cannot be read at all is left as it is and gets no record. The write waits at most three seconds for the lock-file guard and gives up silently, so a held guard or an unwritable `.verbatra-local` never fails or stalls a finished run. The history lives in the local state directory that `verbatra doctor --data-flow` already lists, which still holds no translations. When the file would pass the 8 MiB read limit, the oldest records are dropped first, and a record that does not match its own schema is not written.
